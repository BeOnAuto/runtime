# @on.auto/coordination

The workflow adapter parses a `WorkflowDefinitionDocument` from YAML in the Open Workflow Specification DSL. This document type is an alias for `JsonObject`; the parser applies the existing DSL checks. It is separate from the named, versioned definition stored in the registry. The adapter runs the workflow machine of [`@on.auto/workflow-engine`](../../packages/workflow-engine), hosted in Node by [`@on.auto/workflow-host`](../../packages/workflow-host). Workflows coordinate functions and control steps; they are not another function type. A workflow is a definition of the type `workflow`.

Public documentation explains [workflows and their availability](../../docs/concepts/workflows.md) and [the workflow format](../../docs/reference/workflow-format.md), published at [on.auto/docs](https://on.auto/docs/). The [workflow storage and failover guide](../../docs/self-host/workflows.md) describes running them for an operator, and the repository-only [workflow run reference](../../docs/engineering/reference/workflow-format.md) holds the implementation details.

## Entry

`src/index.ts` exports:

- `makeWorkflowAdapter({ runs, check, mostDurationMs, longestCallMs, names })`: the workflow adapter, with `WorkflowAdapterDependencies` as its options type. `runs` is the host that starts runs; `check`, an `ExpressionCheck`, checks the expressions of a document when it is saved, which the server makes of `checkedAtSave` of `@on.auto/definitions` and its program pool (see [The expressions of a document](#the-expressions-of-a-document)); `mostDurationMs` is the most a run may last, which `create_definition` checks every duration of a document against and a run is stopped at exactly; `longestCallMs` the most a call of a run may take before its `call_deadline` timer fails the task, when the call's definition is not named as written; `names` the playbook's own names of the capabilities composed, `playbookOwnNamesOf` of `@on.auto/definitions`, which an `emit` may not use. The adapter states that its runs finish later and may take `mostDurationMs`.
- `defineSendRunEvent(runs, names)`: `send_run_event`, which gives a running workflow an event, and refuses one that uses the playbook's own names.
- `workflowMachineOptionsOf(sandbox, names)`: the machine's options, the functions a workflow may call (`run_definition`) and the runtime its expressions see as `$runtime`.
- `definitionCalls(runDefinition)`: calls a saved definition from a workflow. This adapter accepts reasoning functions, workflows and custom definition types; it does not classify every extension as a playbook function.
- `callResultOfEnding(ending)`: the answer of a call for the ending of the run it waits for, which the workflow host is given as its result mapping.
- `callMarginMs`: the minute a call is given beyond the longest its definition may run.
- `workflowFacts`: the capability's type and the facts it declares, `{ type: 'workflow', facts: { onRuns: [], streams: [runPresenter] } }`, the presenter of the run log, for the history of a run and the events of a playbook; exported as a constant, since the playbook's own names it reserves are built before the adapter exists, and the adapter takes them.
- `definitionRunResultOf`, `RunDefinition`, `DefinitionRunRequest` and `DefinitionRunResult`, for the server, which runs a definition called by a workflow through its operations.

## The input of a workflow

`input.schema.document`, when a document has one, is compiled when the document is read, with `compileJsonSchema` of `@on.auto/json-schema` under the bounds a computation function's input schema has, its `what` the `input` and its nesting the 512 levels a workflow holds a value, and kept beside the document as the `inputSchema` of `ReadWorkflow` (`src/document/workflow-document.ts`). A schema the compiler refuses refuses the document when it is saved, at its line and under `/input/schema/document` and the compiler's pointer, in the compiler's words, unless the policy already refused the schema's `format` or `resource`, which then stands alone and the schema is not read; the summary publishes the same document as the `inputSchema` (`inlineSchemaOf`).

A run a caller starts, one whose context names no `trigger`, whether `run_definition` over HTTP, its tool over MCP or a step of a workflow starts it, checks its input against that schema with `checkedInput` of `@on.auto/definitions` and the noun `workflow` before the host is asked to start it (`src/capability/workflow.ts`). An input the schema refuses is `invalid_input` of the kind `input_schema`, each issue at its pointer under `/input` in the sentence a function's refusal gives, and the run is recorded rejected, as a function's refused run is, its history beginning with `run_started` as every run's does, with no run log, since the host never starts it; the input is checked as it is given, before `input.from` shapes it, and the refusal of an input nested past 512 levels stays the operation's, at `/input`. A run a trigger starts gets the trigger's input, `{ schedule: { due } }` or the list holding the event, which the schema does not describe, so it is not checked, and a workflow with no input schema takes any input (`src/capability/input-schema.test.ts`).

## The shape of a workflow's output

`output.shape` at the top of a document names an [output shape](../../packages/definitions/README.md#output-shapes) for the run's output, a key of the runtime's own beside the DSL's `output.as` and `output.schema` (`src/document/workflow-output.ts`). The DSL's own check of the document reads it without the key, so a task's `output.shape` is still refused as a key the DSL does not know; a name that is no shape, or a shape beside `output.schema`, is refused at its line with the words of `declaredShape`. The summary publishes the shape's schema as the `outputSchema` and its name as `details.shape`, beside `calls`. The machine's functions refuse the run's output, after `output.as`, when it does not match the shape, `The output of the workflow does not match the shape <name>: <its issues>`, which ends the run as a `conflict` of the kind `unworkable` (see [the engine](../../packages/workflow-engine/README.md#the-output-of-a-run)); a workflow that names no shape ends as it did, whatever its `output.schema` says.

## The DSL check of a document

`dslProblems` (`src/dsl/dsl-validation.ts`) checks a document against the DSL, before the policy's rejections join its problems, and answers a promise, which the document's reader awaits: the version it names, its names, the schema of the specification, the names of its tasks and the graph of its steps, in that order, each only when those before it found nothing. It reads the document without the runtime's own `output.shape` and without the `kind` and `because` of an error, the runtime's extensions to the DSL's errors.

The schema is `workflowSchema` of `@openworkflowspec/sdk`, the specification's JSON Schema of draft 2020-12, and `@hyperjump/json-schema`, its `draft-2020-12` entry, checks a document against it by interpreting it (`src/dsl/specification-schema.ts`). The SDK's own validation, which `Classes.Workflow.deserialize` runs unless it is given `{ validate: false }`, is Ajv, which compiles each of the SDK's 171 validators into code generated from strings: it costs start-up time wherever it loads and is refused wherever no code may be generated. The interpreting validator reads the same schema as data, generates no code, and compiles the schema into the tree it interprets only when the first document is checked, in about 35 ms; its validation is asynchronous only for that, so the capability's check is a promise. It asserts the formats the schema names, `uri`, `uri-template`, `json-pointer` and `date-time`, registered with the checks of `@hyperjump/json-schema-formats` the library's own formats use, and asserted with `setShouldValidateFormat(true)`, a setting of the library for the whole process, both made once, as the library is loaded (`src/dsl/dsl-libraries.ts`), since Ajv asserted them too and draft 2020-12 otherwise reads a format as an annotation. It gives the same answers: over the 499 workflow documents the runtime's tests check, its corpus and its input logs hold, and the 13,340 made from them by changing one value each, it accepts and refuses exactly the documents Ajv does. Its `date-time` is stricter than Ajv's: it refuses a space or a tab between the date and the time, which the grammar of RFC 3339 does not allow, and a leap second on a day that had none. Nothing calls the SDK's validation; the SDK stays for its schema, its classes and its graph, and importing it still compiles its validators. So the capability imports the SDK, and the validator with the formats it asserts, with the first document it reads, through `specificationSdk` and `schemaValidator` (`src/dsl/dsl-libraries.ts`), the one place each is loaded, and keeps them while the server runs; no module the capability's entry imports reaches either (`src/dsl/library-entries.test.ts`). A server that reads no workflow document never loads them, which took 130 ms, 222 files and 1.4 MiB of a server's start, and the first document read pays for them beside the compiling of the schema: the first save of a workflow without expressions took 175 ms against 34 ms when the two loaded with the capability, and the second 5.2 ms against 4.9 ms (measured on 2026-10-23 on one machine of 16 cores, with Node 26.10.0, at the median of 11 starts and of 9 servers).

The schema is read with two changes that keep what it accepts. A `false` subschema is read as `{ not: {} }`, which refuses the same values, so that every refusal is a keyword of a schema at its place and a property the schema refuses outright is a `not` that allows nothing, wherever the schema refuses it. A task is checked on its own: each reference to `#/$defs/task` is read as any object, and each task `allTaskEntries` of `@on.auto/workflow-engine` walks is checked against `#/$defs/task`, so a document is checked once a task. Checked whole, a list of tasks is checked again for each type of task that may hold it, `do` and `for` among them, and the time doubles with each level the tasks nest, on the one thread every workflow shares: Ajv took 55 ms for 16 levels and about a second for 20; task by task, 30 levels take about a millisecond (`src/dsl/dsl-validation.test.ts`). A task under `use.functions`, which the policy refuses, is not checked further.

The validator answers each refused keyword with its place in the schema, the place of the value it refused and the keywords refused within it, its `DETAILED` output, a tree; its `BASIC` output flattens the tree and leaves out the `$ref` between a choice and the definition it chose, so it cannot say in which branch of a choice a refusal was found. Each refusal is a problem at its pointer, in the capability's words (`src/dsl/schema-problems.ts`), since the validator has none: `It needs <name>` for what a value lacks, `It has <name>, which the DSL does not know here` for what it may not have, `It has more properties than the DSL allows here` for an item of a list of tasks that names more than one, and for the other rules the value the schema gives them, as `It must be an object`, `It must match the pattern "<pattern>"`, `It must be one of "continue", "exit", "end"`, `It must be in the format "uri"`, `It needs at least 1 items` or `It must be at most 65535`. A branch of a `oneOf` or `anyOf` that the value does not take, one whose `const` or `not` it fails or a type of task whose key it lacks, adds nothing, and of the branches it takes, those it goes furthest into stand. A property is unknown only where it has no problem of its own and the branches that would have evaluated it did not fail. A task that every type needs a key for has no type the DSL knows, and a refusal with nothing else to show answers in the words of the choice the value takes no branch of, so a document the schema refuses always has a problem. Ajv stopped at the first keyword it refused, so a document is now answered with every problem the schema finds, and one Ajv refused with nothing but a `oneOf`, such as `input: { schema: 7 }`, is refused at its place rather than read as valid.

Beyond the schema, the version a document names is one of the range the SDK supports, `supportedDslVersions` of its package, `>=1.0.0-0 <=1.0.3`, read with `semver` as the SDK reads it; a name is well-formed Unicode text, since the validator writes the place of a refused value as a URI fragment and a lone surrogate has none; no list of tasks names a task twice; and, when the policy found nothing, the steps connect: `buildGraph` of the SDK over the document as `Classes.Workflow.deserialize(text, { validate: false })` reads it, with a YAML reader that stops at 100 levels of nesting.

## The expressions of a document

Parsing keeps the document with the locator of its YAML and its compiled input schema (`readWorkflowDocument`, `src/document/workflow-document.ts`). When a document is created or updated, the capability's `check` (`src/document/expression-check.ts`) takes every expression it holds, with the names each may read, from `workflowExpressionsOf` of the engine, and checks them as one job of the pool's check worker: an expression that is not one TypeScript expression, or that names what its place lacks, is refused at the line and column of its value in the document and under its pointer, in the words of a document this runtime does not run, as `Line 7, column 24: at /do/0/count/set/n: Cannot find name '$nope'.`; an expression of several lines adds its own line to the line of its value. A document without expressions asks for no check, and a check that a ready checker does not finish within 2 seconds leaves the document unsaved, `invalid_input`, and a save that finds no checker ready is `unavailable`. The tests check with the real check worker, one pool for each test file (`src/testing/expression-checks.ts`), so every workflow they save is valid TypeScript.

## A run of a workflow

`run_definition` of a workflow, once [its input schema](#the-input-of-a-workflow) takes the input of a caller, starts its run with the `started` input: the document, each expression in it the JavaScript its save's check stripped of its types where stripping changed it, at its place (`runnableDocument`, `src/document/workflow-document.ts`), so the engine evaluates what the check passed and strips nothing, the input, the run's limits, a random seed for the draws of the run, and as attributes the org, the playbook, the run id, the definition's name and version, the caller who started it, its reaction depth, `depth`, its call depth, `call_depth`, the call it answers, `called_by`, the trigger that started it, `trigger`, and `lineage`: the id of the `run_started` that began the run and the run at the top of its tree, which the workflow host writes with each record of the run (`@on.auto/workflow-host`). The host builds each record's context from these attributes (`runLogContextOf`), so every record of the run log carries the run's definition, its caller as `by`, its chain and the time of its input, and the engine's state format governs its data alone. The run log is `run-logs/<run id>` under the playbook, beside the run's own stream, `runs/<run id>`, which records that the run finishes later, with an empty record, so the run stays `started` until its workflow settles it; a workflow that ends in its first input settles the run before the deferral, and `run_definition` answers its ending. The limits name, for each task that calls `run_definition` with a `type` and a `name` written out, the longest a run of that definition may take, for the task's `input` when it is written out with no expression in it, `{}` when it is left out, through the run context's `longestRunFor`, and for any input otherwise, through its `longestRunOf`, plus `callMarginMs` (`src/runs/call-limits.ts`), read when the run starts, so a call of a prediction function waits 10 s and a minute for a question written out and its build's longest run and a minute for a build or an input computed at run time, which `src/capability/prediction-calls.test.ts` runs against the prediction capability itself; whether the input holds an expression is the engine's own walk of a template, `holdsAnExpression`; every other call has `longestCallMs`. A retry with the run id of a run that is going answers the run as it stands. A run never starts twice in one log, so a retry with the run id of a run that ended without a final result, `unavailable` or `failed`, is rejected with `conflict`: run the workflow again under a new run id. While the server is stopping, `run_definition` of a workflow is rejected with `unavailable`.

`send_run_event` gives the run an `event_received` input, with an id made when the event has none, the time it was sent, and, when it has no source, `/callers/<caller id>` of the caller who sent it, a source under a prefix the playbook keeps for itself, so that a sent event always says where it came from and no event from outside poses as one. An event the run took before is answered as delivered, since an event is taken once by its id; a run that has not started yet, or has ended, is `not_found`; and a run that cannot take the event at that moment, because its log kept changing or the server is stopping, is `unavailable`. Since a `listen` filter matches on the event's attributes, an event may not take a type or a source of what the playbook records itself: `refusingThePlaybooksOwnAttributes` of `@on.auto/definitions` refuses them with `invalid_input` at `/event/type` and `/event/source`, as `publish_event` does. Its `source` is a URI reference that is not empty, `EventSourceSchema`, and its text follows the rules of a published event too, through `refusingForbiddenCharacters` and `refusingBlankText` of `@on.auto/definitions`: no control character, lone surrogate or noncharacter, and a type, id and subject that hold a character that is not a space.

A call of a workflow, `call: run_definition`, executes the definition it names through the operations for the caller who started the run, under a run id derived from the workflow's run id, the task and the run of the task (`nestedRunId` of `@on.auto/definitions`), so a call started again is the same run. The machine names that run on the call's `waiting` entry through `childOf` (`src/calls/child-run.ts`), which derives it the same way and names nothing for arguments the call would refuse. The call starts it with a lineage, the record that started the call as the cause and the workflow's tree as the correlation, with the reaction depth of the run, and with a call depth one more than the run's and the call it answers, which the server passes in the playbook request of the in-process start, never in its input. A call of a run that finishes later, such as one of another workflow, answers the host that it waits for that run, by its run id; the host gives the call the ending of that run, mapped by `callResultOfEnding`. Arguments that name no definition are rejected as `invalid_arguments`, a `validation` error of the task. A rejection keeps its detail, its `issues`, its `kind` and its `because`, which the error of the task carries for a `catch` to read, and an output of more than 1 MiB fails the call. The detail of a refused input already says each issue in a sentence, so the call adds nothing to it; its issues keep the pointers the step saw, under `/input`. The functions the machine is given word the title of a rejected call (`refusal`): a workflow it ran `stopped` when the rejection came from one of that workflow's steps, `invalid_input`, `unavailable`, `conflict` or `unanswered`, and `refused its input` when its input schema refused the input the call gave it, a rejection of the kind `input_schema` (`InvalidInputKindSchema` of `@on.auto/operations`), and any other definition, or a workflow cancelled, not found or not allowed, says what its reason did in the words of `refusalInWords`.

The summary of a workflow keeps in its `details`, as `calls`, the definitions its `run_definition` tasks name with a `type` and a `name` written out, nested tasks among them, in the order of the document and each once, each with the `steps` that call it, the number of each, its place among the workflow's tasks in the order of the document as `allTaskEntries` of `@on.auto/workflow-engine` walks them, the tasks within a task after it and the steps of a `catch` after those of its `try`, and the name of its task (`src/document/workflow-summary.ts`); it keeps no `details` when it names no definition. Its `description` is the document's `summary`, or else its `title`. A call whose `type` or `name` is an expression names no definition until it runs. `definitionCallOf` is the one reading of a `run_definition` task, its `type` and its `name` where each is written out and the arguments it gives: the summary's calls are read with it, and so are the calls whose longest run bounds the wait of a call (`src/runs/call-limits.ts`). The summary is computed once per save and reaches the playbook's registry in the version's `details`, from which the read of each definition the workflow names answers, in `used_by`, that the workflow calls it in each of those steps (see [Used by](../../packages/definitions/README.md#used-by)).

## Triggers

A document's `schedule` names its triggers, `on`, `cron` and `every`, any one, two or three of them, each a trigger of its own, checked on its own when the definition is saved by `scheduleRejections` (`src/document/workflow-schedule.ts`), which the policy of the engine calls:

- `on`: `one` filter, or `any` of a list of at least one and at most 64, `mostTriggerFilters`, each a literal event filter of the engine (`literalFilterOf`): its `with` names the type of the events it takes as text, and any other attribute it names, such as `source`, `subject`, `caller` or `triggerkind`, as text too, or as a whole number from 1 for `depth`, `calldepth` and `definitionversion`, the least count the context declares (`leastCount` of `@on.auto/operations`); a `data` expression that uses a variable such as `$workflow` is refused, since no run exists when the trigger is matched, and so is a filter of `any` whose type and attributes an earlier one has, in any order of keys. `all` and `until` are refused.
- `cron`: five fields, minute, hour, day of month and month, and day of week, read in UTC by `cronRejectionOf` of `@on.auto/workflow-host`, which refuses an expression that cannot be read or names no time that comes.
- `every`: a duration of the DSL of at least a minute.

`after` is refused, and so is a schedule that names none; two keys of one name cannot be written, since the YAML reader refuses them. `triggersOfDocument` reads the triggers once, at save, in the order the schedule names them, each identified by its kind, `event`, `cron` or `every`, and its reference in the document, `/schedule/on`, `/schedule/cron` or `/schedule/every`: an event trigger with each filter's reference, type and attributes, a cron with its expression and an every with its period in milliseconds. The summary carries them as `triggers`, the `TriggerSchema` of `@on.auto/definitions`, so they travel on the definition's record to the workflow host, which keeps one row a trigger and starts the runs (see `@on.auto/workflow-host`); nothing reads a saved source again for them. `cronRejectionOf` stays in the host, which owns the time arithmetic the check must agree with.

## Emitting an event

An `emit` task publishes an event to the playbook. Its `event.with` takes a `type` and a `source`, and no `id`, which the engine gives it from its call key; a type or a source written out that the playbook records itself is refused when the definition is saved (`emitRejections`), and an event computed at run time that the playbook would not record, `emittedEventsOf(names).refusalOf` of `@on.auto/definitions` over the playbook's own names of the capabilities composed, fails the task with a `validation` error (`emitRefusal`).

## Histories

`runPresenter` presents each event of a run log, `input_applied`, first as `workflow_input_applied`: the kind and key of the input (the run id for a start or a cancel, the timer id, the call key or the event id), the status of an answer, with the kind and because of a rejection that names them as `rejection`, which the summary also says in words, and the type of an event, the count of the steps the input moved and the first five, each with its task, run and outcome, and the kinds of output it made. The engine records one entry for each run of a task the input moved, with the outcome it had when the input ended, so the steps are counted once for each run. The patch is never shown. Keys, types and task references are cut at 256 bytes, so the data stays within 4 KiB at the largest event a run stores (`src/presenting/run-presenter.test.ts`).

It then presents each step entry of the record as an event of its own, in the entry's order (`src/presenting/step-events.ts`): `step_started`, `step_waiting`, `step_finished` for `completed`, `step_failed` for `raised`, `timed_out` and `cancelled`, and `step_skipped`. Each has the record's `at`, its `data` the step's `name`, `reference` cut at 256 bytes, `run` and `times`, with `waits_for` on a wait, the child's `run_id` on the wait of a call, and on a failure its `outcome` and its error's `type` and `title`, cut at 256 bytes and 1 KiB; its summary names the step by its name in words. Its `id` is the record's message id, an underscore and its number among the record's recorded steps, from 1, `<message id>_<number>` (`stepIdSeparator` of `@on.auto/operations`), so it is the same on every read, travels in a path as it is, and a reader resolves it by reading the record; its cause is the step its `caused_by` names, `<message id>_<number>`, when that step is in the same record, and the record itself for `input` or for a step of an earlier record, which the input moved on. Records of earlier formats show no step events.

## Testing

`src/workflows` holds the tests of how a workflow runs, each a document run through the memory driver of the engine (`src/testing/workflows.ts`, `interpret`), with the commands a run gave its ports and the settlement it ended with. `src/input-logs` holds sixteen recorded paths, whose input logs in `input-logs/` are the replay corpus: each replays through the machine to the events it recorded, and each runs today as it was recorded (`RECORD_INPUT_LOGS=1` records them again). The capability and `send_run_event` are tested on a playbook whose workflows run on a host over a private SQLite database in memory (`src/testing/workflow-playbook.ts`), its expressions checked at save by the compiler in a real worker within the 30 s of `checksAwaitedAtMostMs` of `@on.auto/definitions/testing` (`src/testing/expression-checks.ts`), so a check that a busy machine slows is not refused by the 2 s a save allows.

## Source

`src/document` parses a definition document: YAML, the policy, the schedule and its triggers, the issues and the summary, and `src/dsl` checks it against the DSL: the schema of the specification, the problems of its refusals and the rules beyond it. `src/capability` holds the capability, whose guide is the public reference page, served to agents as `workflow`, `src/events` the event operation, `src/calls` what a call of a workflow does, `src/runs` the machine's options, the start of a run, its attributes and the limits of its calls, `src/presenting` the presenter of a run's log, `src/workflows` the tests of how a workflow runs, `src/input-logs` the recorded paths and their corpus, and `src/testing` what the tests share.
