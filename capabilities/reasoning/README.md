# @on.auto/reasoning

The implementation of reasoning functions. It parses each source document into a `ReasoningFunctionDefinitionDocument`, including model settings and the compiled prompt template. The named, versioned `ReasoningFunctionDefinition` is stored separately by `@on.auto/definitions`.

User documentation starts with [Reasoning function format](../../docs/reference/reasoning-format.md), published at [on.auto/docs](https://on.auto/docs/). [Set up a model provider](../../docs/self-host/models.md) and the [model settings reference](../../docs/reference/model-settings.md) are the operator's guides, and the repository-only [complete format](../../docs/engineering/reference/reasoning-format.md) retains contributor details. Update the relevant files alongside behavior changes.

## Using it from code

```ts
import { compileAnswerSchema, LanguageModel, languageModelLayer } from '@on.auto/reasoning';
import { Effect, Result } from 'effect';

const schema = Result.getOrThrow(
  compileAnswerSchema({
    type: 'object',
    properties: { verdict: { enum: ['approve', 'reject'] } },
    required: ['verdict'],
    additionalProperties: false,
  }),
);

const decide = Effect.gen(function* () {
  const model = yield* LanguageModel;
  return yield* model.generate({
    model: 'anthropic/claude-sonnet-4-5',
    instructions: 'Decide whether the expense follows the policy.',
    messages: [{ role: 'user', content: [{ type: 'text', text: 'Dinner for four, 312 EUR, client present.' }] }],
    output: { type: 'json', schema, name: 'verdict' },
    settings: { max_output_tokens: 200 },
    timeout_ms: 30_000,
  });
});

Effect.runPromise(decide.pipe(Effect.provide(languageModelLayer(process.env))));
```

A request has `model`, optional `instructions`, `messages` (roles `user` and `assistant`, each with text parts), `output`, `settings` (`max_output_tokens`, and optionally `temperature`, `top_p`, `seed`, `stop_sequences` and `reasoning`), optional `provider_options`, `timeout_ms`, `signal` and `retries`. Some providers drop sampling settings for newer models and say so in `warnings`. `provider_options` passes options to the provider, keyed by the AI SDK's namespace for it: `anthropic`, `openai`, `azure`, `google`, `vertex`, `googleVertex`, `amazonBedrock`, `bedrock`, or the gateway's name. A call fails as `definition_invalid` before any provider is called when it holds a namespace no configured provider reads, or an option for a gateway its `allowed_provider_options` does not list; which options of the built-in providers a definition may set is checked when the definition is parsed (see [Provider options](../../docs/engineering/reference/reasoning-format.md#provider-options)). `requestIssues(request)` gives the problems of a request before it is sent, and the model's `admit(request)` everything `generate` would refuse before calling a provider: those problems, a model that resolves to no configured provider or is not allowed, and provider options that are not allowed.

A definition whose `output.shape` names an [output shape](../../packages/definitions/README.md#output-shapes) asks for JSON of that shape: its `output` is `{ type: 'json', schema, shape }`, `schema` the shape's compiled by `shapedAnswerSchema(shape)` at the answer's nesting of 128 with the shape's further check, so the answer is checked as any JSON answer is and refused as `output_invalid` with the shape's issues too, and its warnings are the schema's, placed at `/output/shape`. `output.schema` beside it and `format: text` are refused at their lines. The summary publishes the shape's schema as the output schema and its name as `details.shape`, and the overview says the shape.

`makeModelAccess(settings, options)` builds the same model and also returns `status`, and the `catalog` that [`list_models`](../../docs/reference/model-settings.md#listing-the-models) reads, whose `list(provider?)` gives the list. Its options inject a `fetch` and credential sources (`aws`, `google`, `azure`), which is how tests run without a network and how per-tenant credentials will be added, `reportProviderMessage`, which receives the [provider messages](../../docs/reference/model-settings.md#provider-messages) a caller does not see, and `reportOperatorHint`, which receives the [operator hints](../../docs/reference/model-settings.md#operator-hints). A request may carry a `run_id`, which only those reports use; the reasoning function adapter sets it to the run's id.

## Tools

A reasoning function whose front matter names `tools` (each `server/tool`, or `server/*`) runs with the tools of the tool servers configured for its playbook, MCP servers and HTTP APIs alike. `makeReasoningFunctionAdapter` takes the server's `ToolAccess` from [`@on.auto/tool-servers`](../../packages/tool-servers) as `tools`, as a type only: it imports the helpers it needs to parse `tools` and bound a run from `@on.auto/tool-servers/policy`, which loads no transport code; `tools` is required, and a test with no tool server gives `noToolServers` of `@on.auto/tool-servers/testing`; with no server configured, a function that names tools is rejected as `unavailable`, kind `tool_not_offered`, in the words of `namedLinks`. The adapter then says it may change something outside (`mayChangeOutside`), so `run_definition` is destructive. The capability declares as the stream kind it owns `tool-calls`, with the presenter of `@on.auto/tool-servers`, `handCallPresenter`, since the server serves `execute`, which calls a tool as a run of a reasoning function would, beside it: the playbook shows each call made by hand in its events, under the types of a run's calls, `tool_call_started`, `tool_call_answered` and `tool_call_failed`, on a stream of its own whose kind tells it from a run's, as the declarations allow, since a stream kind is checked apart from the facts of a run.

A function that names tools calls tools (`callsTools`), so the start of its run records that, and a run of it that is still `started` is not run again under its id. A run first admits its request with the model's `admit`, so a run whose model is not offered reaches no server and starts no process; it then opens its tools with its id, org, playbook and journal before the model is called, and rejects as `unavailable` with kind `tool_not_offered` (because `tool_server_not_configured`, `tool_not_allowed` or `tool_not_listed`, or for a connection a person added `connection_pending`, `connection_broken` or `connection_not_allowed`) or `tool_server_failed` (because `unreachable`, `failing` or `rate_limited`). Otherwise the request carries `tools`: the offered tools under their model-facing names, `server__tool`, with their input schemas unchanged, whether the calls have ended, a signal that ends them, the bound of the whole run, the most input tokens its model calls may add up to, `mostInputTokens`, and the model's context window, `contextWindow`, where the catalog knows it. Both come from the adapter's `reading`, a `ModelReading` the server gives: `mostInputTokens` from `REASONING_MAX_INPUT_TOKENS`, 2,000,000 unless set (`defaultMostInputTokens`), and `contextWindowOf`, the catalog's `contextWindowOf`, which resolves the model's alias and reads the `context_window` its provider lists for it, through the listing's cache; a run without tools reads no window, and a test that gives no `reading` has the default bound and no window. In the adapter, the AI SDK's loop:

- gives the model the tools in the function's own output mode, text or JSON, beside the `json` tool the Anthropic and Bedrock providers add for a JSON output they do not take in the output mode itself (`@ai-sdk/anthropic` 4.0.70 and `@ai-sdk/amazon-bedrock` 5.0.103 name it `json`), a name with no `__`, so no tool of a tool server takes it (`src/tools/tool-loop.test.ts` pins both), and returns each answer to the model as a tool result, an error result for a tool error, giving each call the room its answer has (`src/tools/turn-meter.ts`): the step is measured where the AI SDK announces it, the bytes of its instructions, messages and tools as it starts, and the input and output tokens the provider counted and the tool calls it holds as it ends, before any tool runs; the step's own bytes a token, its bytes sent over its input tokens, turn the room into bytes, the smaller of the window and what `mostInputTokens` leaves after every step made, less the step's input and output tokens, shared equally by the step's calls, so an answer the model's context cannot hold is cut where it stays valid JSON, with a note, and read whole when no window is known or the provider counted no input tokens; nothing is taken from the window for the output, since the catalog's window is the most input tokens a model takes;
- gives every model call its own deadline, the request's `timeout_ms`, which the time the tools take does not count against, armed when the call starts and ended however it settles, even when the AI SDK reports no end for a call that threw, and bounds the whole run by ten minutes, or one call's deadline when that is longer;
- once the run's calls have ended, or before a step whose projected input, the last step's input and output tokens and its answers' bytes at its ratio, would leave less of `mostInputTokens` than that projection again, runs that step with the tools withheld and the conversation told again as text, since some providers refuse tool messages without the tools' definitions, so the model answers from what it has: the calls in words, and their answers inside a block fenced by 32 random hexadecimal characters drawn for that step, once every result is known, and labelled as the results of the tools the model called, data to answer from and neither instructions nor the user's words, so no result can close the block or pass for the user;
- fails as `tools_stopped` when that last step still calls tools (`no_answer`), when the run reaches its bound (`run_bound`), or when its tool servers failed too often (`server_failed`);
- adds to the result's `warnings`, after the provider's, one `compatibility` warning for each place in a tool's input schema where the provider of the run's model may refuse the schema or not hold the tool's arguments to it, named as the tool's name, `inputSchema#` and the JSON pointer, such as `graph__search inputSchema#/properties/query/maxLength`. The rules are those of a JSON output schema (`src/schema/schema-portability.ts`) that hold for a tool's arguments: a root that is not an object, and for Anthropic models the bounds and `oneOf` they do not enforce and the formats they do not accept, each worded for a tool's arguments. The rules for open objects and optional properties bind strict structured outputs only, and the AI SDK sends tools as not strict (`@ai-sdk/openai` 4.0.83 sets `strict: false` unless a tool asks), so they are left out. A schema of more than 64 KiB or 64 levels is not checked.

Once a run has recorded a tool call, every `unavailable` ending it meets has the kind `tools_unfinished` when every tool it called is one its server marks `readOnlyHint` (`calledOnlyReadOnly` of its tools), and becomes a `Conflict` of the kind `effect_unknown` when any is not (`src/tools/tool-endings.ts`), with because `server_failed`, `model_unavailable`, `run_bound` or `no_answer`, and words that name the tools it called in words, never as `server/tool`. The words of `tools_unfinished` say that a new run, or a workflow's retry, may make it; those of `effect_unknown` that whether the tool changed something is not known, and never ask to try again. The run's sessions end however it ends.

A run that calls tools costs more: every step resends the conversation so far, so a run that reads large answers spends its input tokens quickly, and `REASONING_MAX_INPUT_TOKENS` bounds what one run may spend in the unit the operator pays for. A provider that signals a request too long, HTTP 413 or the body's `error.code` or `error.type` among `context_length_exceeded` and `request_too_large` (`src/adapter/api-call-failure.ts`, beside the content-filter codes), fails as `request_too_long`, which ends the run `conflict` `unworkable` in words that name the signal and, when the run's tools answered, the bytes they answered (`RunTools.answeredBytes`) and the input tokens the provider counted for the last step it answered, advising a page. Without a signal the rejection keeps the status and its reading, the body's code when it carries one, scrubbed of secrets as a message is and cut at 64 characters, and the provider's message when the operator exposes it, and claims no length, whatever the message says.

## What a rejection records

Some rejections come after the model answered, and so after it spent tokens: `output_invalid`, an answer that does not match the schema or is cut off at `max_output_tokens`; `content_refused` from the answer's finish; `tools_stopped` with `no_answer`, whose last step still called tools; and an answer that leaves no room in what a run records. Each of their `InvalidInput`, `Unavailable` or `Conflict` carries a `record` of `usage`, shaped as in the record of a run that succeeded, and `duration_ms`, measured with Effect's `Clock` from the model call to the rejection, or the call's own duration for an answer too large to record; `@on.auto/definitions` keeps it on the run's `run_rejected`. A failure that knows no usage, such as a deadline, the bound of a run that calls tools or tool servers that kept failing, whose SDK call threw, carries none.

## Testing

`makeReasoningFunctionAdapter({ languageModel, offered, clock, tools })` makes the runtime adapter for `makeDefinitionOperations`; the server gives it the language model and offered-model configuration from `makeModelAccess`, plus its `ToolAccess`, and a test the scripted model below. `ReasoningFunctionAdapterOptions` names its options. `clock` is optional: without it, `today` and `now` come from Effect's `Clock`. The 200 ms a render of the prompt may take are counted on the monotonic time of the same clock, the one given or Effect's. A template's tests render it on `standingRenderClock` of `@on.auto/definitions/testing`, which stands still, or on `steppingClock`, moving a millisecond each time it is read, so a render is stopped for its time by that clock and never by a slow machine.

`@on.auto/reasoning/testing` exports a fake for the tests of other packages. `callingTools(calls, then)` scripts a model that calls tools before its reply, as the adapter does, with a signal that aborts when the call is interrupted. `scriptedLanguageModel(...replies)` answers with its replies in order, admits and rejects an invalid request as the real one does, records every request (`requests()`), and provides itself as a `layer`. A reply is a function of the request; `answers(textResult('Hello'))` and `answers(jsonResult({ verdict: 'approve' }))` build the usual ones, and `() => Effect.fail(new RateLimited({ ... }))` scripts a failure.

No test in this package calls a model: the adapter is tested with the AI SDK's mock model and with the real provider packages against a fake `fetch` that answers with each provider's documented response shape.

Two tests wait on real time on purpose, where a slow machine only lengthens the wait: `src/tools/tool-stops.test.ts` sleeps the 1 s of a step's deadline after a model call failed, to show the deadline ended with the call and aborts nothing, and gives a run 100 ms against a tool that sleeps 1 s, so the run times out however slow the machine.

`src/listing/gateway-listing.test.ts` counts the reads a listing makes of an answer that arrives in 80,000 pieces of one byte, one for each piece and one for its end, which shows each piece read once; that the cost stays linear in the pieces is the reader's construction, which keeps the pieces and joins them once at the end (`src/listing/listing-request.ts`), not something the test measures. `src/definition/definition-parsing.test.ts` holds the parse of a document of 5,900 names to 400 ms of the process's CPU, a measure of work rather than of the wall clock, which a busy machine changes little, to show the parse stops counting names past its bound.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/model` holds the interface: the request, the result, the `LanguageModel` service and the request checks. `src/failure` holds one class per failure. `src/schema` holds answer schemas: their limits and their compilation, made with the JSON Schema compiler of [`@on.auto/json-schema`](../../packages/json-schema/README.md), and `checkAnswerSchema`, the report of what in a schema is unsupported, not portable across providers or not checked. `src/settings` reads the settings from the environment with Effect `Config`. `src/adapter` and `src/tools` are the only production code that imports the AI SDK, and `src/adapter` the only code that imports the cloud credential libraries. `src/listing` reads the list of models of each provider, and `src/catalog` keeps the lists, combines them with the declared models and the aliases, applies the allow list, and defines `list_models`. `src/template` is the only code that imports liquidjs: its instance of the shared engine of [`@on.auto/definitions/template`](../../packages/definitions/README.md#templates-of-a-capability), with the registrations that stay this capability's own, its prompt filters and its system block, and compiling and rendering a prompt over the shared parse and render, behind readonly types of its own; `rendering-corpus.json` holds what each template of the rendering tests rendered before the engine moved into the shared factory, and `rendering-corpus.test.ts` holds the engine to it. `src/definition` parses and validates a definition document with the reader of `@on.auto/definitions/document`, which splits it and reads its YAML: the keys of its front matter, the settings, the schemas and the variables a template reads, and gives the capability its `parse` and `summarize`. `src/tools` gives the model a run's tools: the tools as the AI SDK takes them, the last step without them, opening a run's tools and its endings. `src/capability` is the capability: its guide, the public reference page, served to agents as `reasoning-function` and ending with the sentence `onThisServer` makes of what this server offers, preparing the input, rendering the prompt, the request, the answer, the rejections and the record. `src/overview` is the function's overview (see [The overview of a definition](../../packages/definitions/README.md#the-overview-of-a-definition)): what it needs, with the value `input.default` gives a field, what it produces, text or the fields of its JSON answer, its model and each tool, drawn, when it names any, as the function, the model it reasons with and each tool the model may call, and what it is told, its instructions and its message, read from the prompt its compiled template keeps with the line it starts on, by `readableParts` of `@on.auto/definitions/template`, the `{% system %}` block apart; `reference-example.overview.md` is the overview of the example of the public reference page and `reference-tools.overview.md` the overview of that example with the `tools` its section Tools names, which `reasoning-overview.test.ts` writes again and compares byte for byte. `src/testing` holds the fake and what the tests share, including the SDK's mock model.
