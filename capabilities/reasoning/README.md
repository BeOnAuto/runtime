# @on.auto/reasoning

The implementation of reasoning functions. It parses each source document into a `ReasoningFunctionDefinitionDocument`, including model settings and the compiled prompt template. The named, versioned `ReasoningFunctionDefinition` is stored separately by `@on.auto/definitions`.

User documentation starts with [Reasoning function format](../../docs/reference/reasoning-format.md), published at [on.auto/docs](https://on.auto/docs/). [Set up a model provider](../../docs/self-host/models.md) and the [model settings reference](../../docs/reference/model-settings.md) are the operator's guides, and the repository-only [complete format](../../docs/engineering/reference/reasoning-format.md) retains contributor details. Update the relevant files alongside behavior changes.

## Using it from code

```ts
import { compileAnswerSchema, LanguageModel, languageModelLayer } from '@on.auto/reasoning';
import { Effect, Result } from 'effect';

const schema = Result.getOrThrow(
  compileAnswerSchema({
    type: 'object',
    properties: { verdict: { enum: ['approve', 'reject'] } },
    required: ['verdict'],
    additionalProperties: false,
  }),
);

const decide = Effect.gen(function* () {
  const model = yield* LanguageModel;
  return yield* model.generate({
    model: 'anthropic/claude-sonnet-4-5',
    instructions: 'Decide whether the expense follows the policy.',
    messages: [{ role: 'user', content: [{ type: 'text', text: 'Dinner for four, 312 EUR, client present.' }] }],
    output: { type: 'json', schema, name: 'verdict' },
    settings: { max_output_tokens: 200 },
    timeout_ms: 30_000,
  });
});

Effect.runPromise(decide.pipe(Effect.provide(languageModelLayer(process.env))));
```

A request has `model`, optional `instructions`, `messages` (roles `user` and `assistant`, each with text parts), optional `conversation`, the messages of the earlier steps of a run as the AI SDK's model messages, optional `tools`, the definitions of the tools offered (`name`, `description`, `inputSchema`), `output`, `settings` (`max_output_tokens`, and optionally `temperature`, `top_p`, `seed`, `stop_sequences` and `reasoning`), optional `provider_options`, `timeout_ms` and `retries`. `generate` makes one call of the model: it answers with the result, whose `response` is the response messages as JSON text, from which the steps read the tool calls asked for, and `request_bytes` the size of the request sent. Some providers drop sampling settings for newer models and say so in `warnings`. `provider_options` passes options to the provider, keyed by the AI SDK's namespace for it: `anthropic`, `openai`, `azure`, `google`, `vertex`, `googleVertex`, `amazonBedrock`, `bedrock`, or the gateway's name. A call fails as `definition_invalid` before any provider is called when it holds a namespace no configured provider reads, or an option for a gateway its `allowed_provider_options` does not list; which options of the built-in providers a definition may set is checked when the definition is parsed (see [Provider options](../../docs/engineering/reference/reasoning-format.md#provider-options)). `requestIssues(request)` gives the problems of a request before it is sent, and the model's `admit(request)` everything `generate` would refuse before calling a provider: those problems, a model that resolves to no configured provider or is not allowed, and provider options that are not allowed.

A definition whose `output.shape` names an [output shape](../../packages/definitions/README.md#output-shapes) asks for JSON of that shape: its `output` is `{ type: 'json', schema, shape }`, `schema` the shape's compiled by `shapedAnswerSchema(shape)` at the answer's nesting of 128 with the shape's further check, so the answer is checked as any JSON answer is and refused as `output_invalid` with the shape's issues too, and its warnings are the schema's, placed at `/output/shape`. `output.schema` beside it and `format: text` are refused at their lines. The summary publishes the shape's schema as the output schema and its name as `details.shape`.

`makeModelAccess(settings, options)` builds the same model and also returns `status`, and the `catalog` that [`list_models`](../../docs/reference/model-settings.md#listing-the-models) reads, whose `list(provider?)` gives the list. Its options inject a `fetch` and credential sources (`aws`, `google`, `azure`), which is how tests run without a network and how per-tenant credentials will be added, `reportProviderMessage`, which receives the [provider messages](../../docs/reference/model-settings.md#provider-messages) a caller does not see, `reportOperatorHint`, which receives the [operator hints](../../docs/reference/model-settings.md#operator-hints), and `loadEntraIdentity`, which loads one provider's identity library, for that provider without a key. Without it the identity library is absent and that provider without a key is not configured, so a program that composes the core elsewhere, where the library is not installed, bundles no import of it and needs no alias for it. A request may carry a `run_id`, which only those reports use; the reasoning function adapter sets it to the run's id.

## Tools

A reasoning function whose front matter names `tools` (each `server/tool`, or `server/*`) runs with the tools of the tool servers configured for its playbook, MCP servers and HTTP APIs alike. `makeReasoningFunctionAdapter` takes the server's `ToolAccess` from [`@on.auto/tool-servers`](../../packages/tool-servers) as `tools`, as a type only: it imports the helpers it needs to parse `tools` and bound a run from `@on.auto/tool-servers/policy`, which loads no transport code; `tools` is required, and a test with no tool server gives `noToolServers` of `@on.auto/tool-servers/testing`; with no server configured, a function that names tools is rejected as `unavailable`, kind `tool_not_offered`, in the words of `namedLinks`. The adapter then says it may change something outside (`mayChangeOutside`), so `run_definition` is destructive. The capability declares as the stream kind it owns `tool-calls`, with the presenter of `@on.auto/tool-servers`, `handCallPresenter`, since the server serves `execute`, which calls a tool as a run of a reasoning function would, beside it: the playbook shows each call made by hand in its events, under the types of a run's calls, `tool_call_started`, `tool_call_answered` and `tool_call_failed`, on a stream of its own whose kind tells it from a run's, as the declarations allow, since a stream kind is checked apart from the facts of a run.

A function that names tools calls tools (`callsTools`), so the start of its run records that. A run first admits its request with the model's `admit`, so a run whose model is not offered reaches no server and starts no process; it then opens its tools with its id, org, playbook and journal before the model is called, and rejects as `unavailable` with kind `tool_not_offered` (because `tool_server_not_configured`, `tool_not_allowed` or `tool_not_listed`, or for a connection a person added `connection_pending`, `connection_broken`, `connection_not_allowed` or `connection_unavailable`) or `tool_server_failed` (because `unreachable`, `failing` or `rate_limited`).

## Steps

A run proceeds one model call at a time, each call a fact on its stream (`src/steps`). The run's state, `StepState` (`step-state.ts`), is folded by one function, `evolve`, from the run's facts and the content it kept, and the live path and the resume path share it: a live step folds the fact it just recorded with the content it just made, and a resumed run folds the facts of its attempt with the content it reads back by digest (`recorded-steps.ts`). The state never holds what only the memory of an attempt knew. From the state, `nextStep` (`step-decision.ts`) decides what follows: a model call, the tool calls the last answer asked for, the last step without tools, or an ending (`answered`, `failed`, `stopped`, `outcome_unknown`, `unreadable`). `step-loop.ts` performs the decisions until an ending, and `run-steps.ts` makes a run of them.

- A model call (`model-steps.ts`) records `model_call_started`, under the number the decider takes as the next one (`@on.auto/definitions`), performs the call, and records `model_call_answered` or `model_call_failed` with the facts `step-facts.ts` makes of the result or the failure. A call is one step of the AI SDK, `isStepCount(1)`, with the tools as definitions without `execute`, so the library calls no tool. The request is the prompt, the conversation the state holds, the messages of the earlier steps as the library's model messages, and the tools; the number of bytes it sends is measured where the library announces the call, `onLanguageModelCallStart`, and kept on the answer as `request_bytes`.
- The calls the model asked for (`asked-calls.ts`) are read from its response. The library's own result stands for a call of a tool the run does not offer or whose arguments do not parse, so the run adds none of its own. A call of a tool this attempt does not offer, though the attempt that asked did, because its server changed between them, is refused in words the model reads, `noLongerOffered`, and an admitted call carries the tool it is sent through. Each other call is admitted within the run's tally (`callsEnded`, `shownAgain` and the bounds of `@on.auto/tool-servers/policy`): 25 calls, 16 KiB of arguments, a third same call refused and pointed to the earlier result, and an input that is not an object refused. A refused call is not sent and not recorded, and the model reads why.
- The admitted calls (`tool-steps.ts`) run at once. Each records `tool_call_started` from what the tool's `start` gives, under the number the fold of the attempt's facts gives as the next, inside the step's one permit, as a model call does, performs the call, and records its end. The fifth server failure stops the calls still in flight as `cancelled`, in the words "The run stopped its calls once its tool servers failed too often", and the run's bound gives up a call in flight the same way, in the words of the bound. A fact that cannot be written fails the step, and the attempt never goes on without it: a fact another attempt wrote first is a conflict in its own words, and a failure of the database a defect the server reports as an incident.
- Each call has the room its answer may fill (`src/tools/turn-meter.ts`), measured on the request the last model call sent: the call's bytes a token, its bytes sent over its input tokens, turn the room into bytes, the smaller of the window and what `mostInputTokens` leaves after every call made, less the call's input and output tokens, shared equally by the step's calls, so an answer the model's context cannot hold is cut where it stays valid JSON, with a note, and read whole when no window is known or the provider counted no input tokens; nothing is taken from the window for the output, since the catalog's window is the most input tokens a model takes. `mostInputTokens` and the window come from the adapter's `reading`, a `ModelReading` the server gives: `mostInputTokens` from `REASONING_MAX_INPUT_TOKENS`, 2,000,000 unless set (`defaultMostInputTokens`), and `contextWindowOf`, the catalog's `contextWindowOf`, which resolves the model's alias and reads the `context_window` its provider lists for it, through the listing's cache; a run without tools reads no window, and a test that gives no `reading` has the default bound and no window.
- Every model call has its own deadline, the request's `timeout_ms`, which the time the tools take does not count against, armed when the call starts and ended however it settles. A run that calls tools is bounded by ten minutes from its start, as `run_started` recorded it, or one call's deadline when that is longer.
- Once the run's calls have ended, or before a step whose projected input, the last step's input and output tokens and its answers' bytes at its ratio, would leave less of `mostInputTokens` than that projection again, the next step is made with the tools withheld and the conversation told again as text (`src/tools/final-step.ts`), since some providers refuse tool messages without the tools' definitions: the calls in words, and their answers inside a block fenced by 32 random hexadecimal characters drawn for that step, labelled as the results of the tools the model called, data to answer from and neither instructions nor the user's words, so no result can close the block or pass for the user. A tool call in that step ends the run with `no_answer`.
- The model is given the tools in the function's own output mode, text or JSON, beside the `json` tool the Anthropic and Bedrock providers add for a JSON output they do not take in the output mode itself (`@ai-sdk/anthropic` 4.0.70 and `@ai-sdk/amazon-bedrock` 5.0.103 name it `json`), a name with no `__`, so no tool of a tool server takes it (`src/steps/provider-steps.test.ts` pins both).
- The record's `warnings` add, after the provider's, one `compatibility` warning for each place in a tool's input schema where the provider of the run's model may refuse the schema or not hold the tool's arguments to it, named as the tool's name, `inputSchema#` and the JSON pointer, such as `graph__search inputSchema#/properties/query/maxLength` (`src/tools/input-schema-warnings.ts`). The rules are those of a JSON output schema (`src/schema/schema-portability.ts`) that hold for a tool's arguments: a root that is not an object, and for Anthropic models the bounds and `oneOf` they do not enforce and the formats they do not accept, each worded for a tool's arguments. The rules for open objects and optional properties bind strict structured outputs only, and the AI SDK sends tools as not strict (`@ai-sdk/openai` 4.0.83 sets `strict: false` unless a tool asks), so they are left out. A schema of more than 64 KiB or 64 levels is not checked.

`PerformJob` (`src/jobs/jobs.ts`) is the one seam between the steps and the world: a job in, an answer out. A model call job carries the request, its output as data, the schema document of a JSON output and the name of its shape, and answers the `ModelResult`; a tool call job carries the call's id, the tool's model-facing name, its server, its input and its room, and answers the call's end and the reply the model reads. A job holds no closure and no signal, and performing it writes no fact: the steps alone record. `performedInProcess(languageModel, telemetry)` (`src/jobs/performed-in-process.ts`) gives, for a run's offered tools, the implementation of this process: it compiles the output schema, or the shape's, as the definition compiled it, once for all the model calls of an attempt (`requestCompiler` in `src/jobs/compiled-request.ts`), a schema it cannot compile failing the call as `definition_invalid`, calls the model, and sends a tool call through the run's offered tool, under an `execute_tool` span that carries the call's arguments and result only where telemetry records content; a call of a tool it does not offer is answered as a `server_failure` that was never sent. The adapter takes another as `performJob`. `PerformJob`, its jobs and `performedInProcess` are exported from the main entry, so a shell that performs a model call or a tool call per invocation performs it as this process does.

A shell that hands out one job at a time drives the same steps from the facts (`src/steps/step-jobs.ts`). `stepRecordingOf(services, run, tools)` assembles what the steps of a run record through, its model, the base of its requests, its tools, its bounds, its journal and the content it keeps, with no performer; `stateOfTheAttempt(recording, prompt, attempt)` folds the state of the attempt from the calls it recorded and the content they kept, as a resumed run does; `jobsOf(recording, state)` decides what follows and records the start of each job it hands out: one model call, or the calls the last answer asked for, each under the number its start was recorded with, or no job and the ending, after it records an interrupted end for each call left open. `performedJob(perform, job)` performs one job with a `PerformJob` and answers its `JobAnswer`, the model's result or failure with the call's duration, or the tool call's end and reply, and `answerRecorded(recording, state, answer)` records its end and answers the state after it. A start the journal refuses because the run's cancel was recorded ends the steps `cancelled`.

Within one invocation the shell keeps the attempt's state in memory, the `StepState` each of these answers, which holds the content of the attempt's calls, and gives it to the next `answerRecorded` and `jobsOf`; it folds a state from the facts with `stateOfTheAttempt` only as an invocation begins. A run whose playbook keeps no content of its calls, one whose `RunTools.keepsContent` is false, therefore goes on across the jobs of one invocation as the loop carries it, recording the same facts. An invocation after the one that began it finds no content to fold from the facts: `promptOfTheAttempt` ends the run `restarted_without_content`, in the words of `restartedWithoutContent`, and a state folded from its facts ends the steps `unreadable`, which `stepsAnswerOf` words the same (`src/steps/step-jobs.test.ts`).

The rest of what the adapter does around the steps, the shell does itself, with the functions the adapter does it with (`definitionRun` of `src/capability/definition-run.ts` composes them):

- Before the steps, as an invocation begins: `beforeTheSteps(journal, model)`, what the attempt's facts say so far, with `ended`, which records an interrupted end for each call the attempt left open before a rejection ends the run; `promptOfTheAttempt({ content, clock }, { definition, input, run, before })`, the template rendered on the clock on a first attempt, and the prompt the first model call kept on a later one; `admitted(languageModel.admit(requestFor(definition, prompt, run)), before)`, the model's admission; and `withTools({ access, references: definition.tools, run, before }, use)`, which opens the run's tools for `use`, the `RunTools` `stepRecordingOf` takes, and closes them after.
- Around the jobs: the bound of the run, and the stop of the other calls once the tool servers failed too often, which the loop keeps around its own performer; a shell bounds the jobs it hands out itself.
- The ending: `stepsAnswerOf(definition, { state, ending }, recording.tools.definitions)`, the answer checked again, or the rejection the ending is, and `finishedOf(definition, answer)`, the run's record of its prompt, settings, format, result and spending.
- The liveness check on resuming: an attempt is live while the last fact of its run's stream is no older than the longest gap between two facts of a live attempt, `attemptIsLive(quietMs, resumesAfterMs)` of `@on.auto/definitions`, over `ageOfLastAppend` of the run's stream and `resumesAfterMsOf(definition, callMs)` of this package, where `callMs` is the call bound of the tool access. A shell that resumes a run itself makes no attempt of a live one, as `run_definition` refuses one as `stillRunning`; within one process `LiveAttempts` of `@on.auto/definitions` holds one attempt a run besides, which a shell whose invocations do not share a process has only this check for.

The loop of this process makes the same beginning and end of each job around its performer, so a run driven one job at a time from its facts records what the loop records for the same answers, and its steps end the same way (`src/steps/step-jobs.test.ts`).

The content of a run is kept per step, through the content store the server gives the adapter as `content` (`src/steps/kept-content.ts`), when every tool server of the run keeps content (`RunTools.keepsContent`), and always for a run without tools: the messages the call adds, the prompt for the first call, the answers of the tools for a later one, the conversation told again for the last step, under `messages_sha256`, and the response as the library's response messages under `response_sha256`. A step never keeps the whole conversation again, so what a run keeps, scrubs and digests grows with its length and not with its square. The answers of the tools are kept by the tool servers under their `result_sha256`. What a run keeps is scrubbed of the secrets of its tool servers first (`RunTools.scrubJson`), and a run goes on from what it kept, alive as after a resume, so a secret in the prompt or in the model's response is `[redacted]` in every model call the run makes and in every tool call the model asks for. The answer is checked again once scrubbed (`src/steps/steps-answer.ts`): a JSON answer that no longer parses, as one whose number held a secret, or no longer matches its schema ends the run as an `output_invalid` answer does, never as a defect.

A run is not interrupted by its client going away: `@on.auto/definitions` runs its attempt in the scope of the process, so only the process stopping interrupts it, which leaves it to be resumed from its facts. A run a workflow's call asks for runs in that call, which its workflow host stops when it stands by or stops, and the host that takes the workflow over resumes it. `cancel_run` cancels it: where its attempt outlives its client, the process where it is going interrupts it, as the workflow host interrupts the call it cancels, and the capability's `resumes.cancelledAttempt` (`cancelledAttemptOf`, `src/capability/before-the-steps.ts`) ends each call still open as `interrupted`, from the run's facts, and gives the spending so far; otherwise its journal refuses its next start as cancelled, which ends the steps (`src/steps/step-loop.ts`, the calls of the step all settled first, `StepCancelled` carrying the state of the step's last fact) and the run as `RunCancelled`, with the spending of its model calls so far. A run that is still `started` and performed again goes on from its facts (`recorded-steps.ts`), at the version it started with; [A run performed again](../../docs/reference/reasoning-format.md#a-run-performed-again) is its user documentation. Before it renders, admits or opens anything, a resumed attempt folds its facts (`src/steps/attempt-facts.ts`, `src/capability/before-the-steps.ts`): it takes its prompt from what its first model call kept and never renders it again, and an ending it meets before its steps, its model no longer admitted (its provider not configured, the model not allowed, or the definition no longer workable) or its tool servers not opened, is worded as the steps' endings are, with the tools it called and the spending of its model calls, its open calls ended as `interrupted` first. The fold rebuilds the conversation from the kept content, so the request a resumed run sends is the one its first attempt would have sent. A model call that was answered is never paid again. A model call started without an answer is ended as `interrupted` and made again under the next number. A tool call started without an answer is ended as `interrupted` and made again when its fact says `read_only`; when one open call of a step is of a tool that may change something, no open call of that step is made again, every one is ended as `interrupted`, and the run ends with `call_outcome_unknown`, since making it again could repeat what it did. A call of a tool the run no longer offers, because its server changed between the attempts, is refused in words the model reads, `noLongerOffered`, and never sent. A recorded model call failure ends the run as it did, a recorded `run_cancel_requested` ends it cancelled (`@on.auto/definitions`), and a run whose content is not kept, or is gone, ends with `restarted_without_content`. Whatever ends the steps, the run's bound and a cancel among them, ends the calls still open as `interrupted` first (`src/steps/step-loop.ts`), so no ending leaves a start without an end. Every start names its number, so a call is never started a second time, across servers too: of two attempts that go on at once, the one whose start is recorded second meets `taken` before it sends anything. A run declares `resumes.afterMs`, its model call's deadline plus the call bound of its tool access (`ToolAccess.callMs`), the longest gap between two facts of a live attempt, from which `@on.auto/definitions` tells a live attempt from a dead one by the database's clock.

Once a run has recorded a tool call, every `unavailable` ending it meets, and a definition its resumed attempt finds no longer workable, has the kind `tools_unfinished` when every tool it called is one its server marks `readOnlyHint`, and becomes a `Conflict` of the kind `effect_unknown` when any is not (`src/tools/tool-endings.ts`), with because `server_failed`, `model_unavailable`, `definition_refused` for that definition, `run_bound`, `no_answer`, `restarted_without_content` or `call_outcome_unknown`, and words that name the tools it called in words, never as `server/tool`. The words of `tools_unfinished` say that a new run, or a workflow's retry, may make it; those of `effect_unknown` that whether the tool changed something is not known, and never ask to try again. The run's sessions end however it ends.

A run that calls tools costs more: every step resends the conversation so far, so a run that reads large answers spends its input tokens quickly, and `REASONING_MAX_INPUT_TOKENS` bounds what one run may spend in the unit the operator pays for. A provider that signals a request too long, HTTP 413 or the body's `error.code` or `error.type` among `context_length_exceeded` and `request_too_large` (`src/model-calls/api-call-failure.ts`, beside the content-filter codes), fails as `request_too_long`, which ends the run `conflict` `unworkable` in words that name the signal and, when the run's tools answered, the bytes they answered and the input tokens the provider counted for the last step it answered, advising a page. Without a signal the rejection keeps the status and its reading, the body's code when it carries one, scrubbed of secrets as a message is and cut at 64 characters, and the provider's message when the operator exposes it, and claims no length, whatever the message says.

A provider's cost reaches the answer through the middleware that keeps the response id (`src/model-calls/model-call.ts`), as `cost_usd`: a gateway entry names the header its gateway answers the call's cost in, in US dollars, as `cost_header`, or names none and no cost is kept; a provider that is no gateway keeps none, and a header that does not hold a cost of zero or more keeps none either. Each model call's fact keeps its cost, and the record of the run (`src/capability/spending-record.ts`) adds them up beside its tokens.

## What a rejection records

A rejection after any model call of the run ended carries a `record` of the run's spending, the sum of its model calls' facts so far: `usage`, shaped as in the record of a run that succeeded, `duration_ms`, and `cost_usd` where a call answered a cost. That holds for every ending: `output_invalid`, `content_refused`, `no_answer`, an answer that leaves no room in what a run records, the endings of a deadline, the run's bound and tool servers that kept failing, `call_outcome_unknown`, `restarted_without_content`, and the endings a resumed attempt meets before its steps. `@on.auto/definitions` keeps it on the run's `run_rejected`. A rejection before any model call ended carries none.

## Testing

`makeReasoningFunctionAdapter({ languageModel, offered, clock, tools, content })` makes the runtime adapter for `makeDefinitionOperations`; the server gives it the language model and offered-model configuration from `makeModelAccess`, its `ToolAccess`, the ledger's content store and its telemetry, and a test the scripted model below. `ReasoningFunctionAdapterOptions` names its options. `clock` is optional: without it, `today` and `now` come from Effect's `Clock`. The 200 ms a render of the prompt may take are counted on the monotonic time of the same clock, the one given or Effect's. A template's tests render it on `standingRenderClock` of `@on.auto/definitions/testing`, which stands still, or on `steppingClock`, moving a millisecond each time it is read, so a render is stopped for its time by that clock and never by a slow machine.

`@on.auto/reasoning/testing` exports a fake for the tests of other packages. `scriptedLanguageModel(...replies)` answers each model call with the next reply, admits and rejects an invalid request as the real one does, records every request (`requests()`), and provides itself as a `layer`. A reply is a function of the request; `answers(textResult('Hello'))` and `answers(jsonResult({ verdict: 'approve' }))` build the usual ones, `answers(toolCallsResult(calls))` an answer that asks for tool calls, and `() => Effect.fail(new RateLimited({ ... }))` scripts a failure. Its replies are given one by one or in lists (`ScriptedReplies`): `callingTools(calls, then)` is the two replies of a run that calls tools, the answer that asks for the calls and `then`, and `answeringFromTheTools(calls, answer)` answers from what the tools answered, read from the conversation the second call is sent.

No test in this package calls a model: the adapter is tested with the AI SDK's mock model and with the real provider packages against a fake `fetch` that answers with each provider's documented response shape. The steps are tested through `stepsOf` of `src/testing/step-runs.ts`, which runs them on a recording journal, a content store in memory and scripted jobs, and through `providerRun` of `src/testing/provider-runs.ts`, which runs a definition through the adapter, a provider package and a fake MCP server.

Some tests wait on real time on purpose, where a slow machine only lengthens the wait: `src/steps/call-deadlines.test.ts` gives a model call 200 ms against a tool that answers in 300 ms, to show the time of the tools does not count against a call, and a call 100 ms against a provider that never answers; `src/steps/step-stops.test.ts` gives a run a bound of 150 ms.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/model` holds the interface: the request, the result, the `LanguageModel` service and the request checks. `src/failure` holds one class per failure. `src/schema` holds answer schemas: their limits and their compilation, made with the JSON Schema compiler of [`@on.auto/json-schema`](../../packages/json-schema/README.md), and `checkAnswerSchema`, the report of what in a schema is unsupported, not portable across providers or not checked. `src/settings` reads the settings from the environment with Effect `Config`. `src/providers` makes the providers' models and the model access, and `src/model-calls` makes one call to a model through them: with the JSON output of `src/schema/json-output.ts`, they are the only production code that runs the AI SDK, and `src/providers` is the only code that imports the cloud credential libraries: it imports `google-auth-library`, with the AI SDK's Vertex providers, only when model access is built with Vertex configured (`src/providers/vertex-providers.ts`), the AWS credential chain only with Bedrock configured, through `awsCredentialChainOf` of `@on.auto/outbound`, and one provider's identity library only for that provider without a key, through the loader it is given. No entry of the capability reaches any of them but `@on.auto/reasoning/installed-packages`, which imports that identity library for the server (`src/providers/credential-libraries.test.ts`). That optional package, which the capability does not depend on, is imported by `src/providers/installed-packages.ts` alone, the module of the entry `@on.auto/reasoning/installed-packages`, which only the server imports, to pass its `loadEntraIdentity` to `makeModelAccess`; no module the main and testing entries reach imports the package. That entry's `installedPackages` says whether the package is installed by resolving it, without loading it, so a server can read from its settings alone, with `providerStatus` and `offeredModels`, which providers are configured and which models it offers, before it builds the model access, as the server does at start. `src/listing` reads the list of models of each provider, and `src/catalog` keeps the lists, combines them with the declared models and the aliases, applies the allow list, and defines `list_models`. `src/template` is the only code that imports liquidjs: its instance of the shared engine of [`@on.auto/definitions/template`](../../packages/definitions/README.md#templates-of-a-capability), with the registrations that stay this capability's own, its prompt filters and its system block, and compiling and rendering a prompt over the shared parse and render, behind readonly types of its own; `rendering-corpus.json` holds what each template of the rendering tests rendered before the engine moved into the shared factory, and `rendering-corpus.test.ts` holds the engine to it. `src/definition` parses and validates a definition document with the reader of `@on.auto/definitions/document`, which splits it and reads its YAML: the keys of its front matter, the settings, the schemas and the variables a template reads, and gives the capability its `parse` and `summarize`. `src/steps` makes a run one model call at a time, as [Steps](#steps) says: the messages of a step, the calls asked for, the state and its fold, the decision, the facts, the content kept, the model and tool steps and their loop, and the resumption. `src/jobs` holds `PerformJob` and its implementation in this process. `src/tools` holds what the steps share about tools: opening a run's tools, the room of their answers, the last step without them, the warnings of their input schemas and the endings of a run that called them. `src/capability` is the capability: its guide, the public reference page, served to agents as `reasoning-function` and ending with the sentence `onThisServer` makes of what this server offers, preparing the input, rendering the prompt, the request, the answer, the rejections and the record. `src/testing` holds the fake and what the tests share, and `src/provider-testing` the fakes of the providers: their replies and errors, the recording `fetch`, the lists of models and the SDK's mock model.

## Measured

On 2026-10-23, on SQLite, Node 26.11.1 and 16 cores, `MEASURE_ONLY=reasoning pnpm --filter @on.auto/server measure` ran each kind of run against a provider and an MCP server on the loopback, before this change (`main`) and after, twice each, one after the other, while other work held the machine's one-minute load average between 26 and 65:

| Run                                             | Model calls before and after | Median wall time before | Median wall time after |
| ----------------------------------------------- | ---------------------------- | ----------------------- | ---------------------- |
| Without tools                                   | 1 and 1                      | 3.46 and 3.51 ms        | 5.64 and 5.27 ms       |
| Five tool calls, one a step, keeping content    | 6 and 6                      | 19.39 and 19.80 ms      | 36.50 and 35.85 ms     |
| Five tool calls, one a step, keeping no content | 6 and 6                      | 15.14 and 15.55 ms      | 25.21 and 25.24 ms     |
| 25 tool calls in one step, then the last step   | 2 and 2                      | 61.84 and 63.02 ms      | 68.84 and 68.20 ms     |

The model calls a run makes are unchanged, as are those of a run with one tool call (2), three in one step (2), and a last step that still calls tools (2, ending with `no_answer`). One append to a run's stream took a median of 0.78 to 0.81 ms. What a run adds is its facts and its content: a model call appends two facts, and keeps two texts where content is kept, so four appends, about 3.1 to 3.2 ms, a call. The five-call run adds 12 facts and 12 texts, 24 appends, about 19 ms, against 16.1 to 17.1 ms measured; without content, 12 appends, about 9.5 ms, against 9.7 to 10.1 ms; a run without tools 4 appends, about 3.2 ms, against 1.8 to 2.1 ms; and the 25-call run, with two model calls, 8 appends, about 6.3 ms, against 5.2 to 7.0 ms, the rest being the scrub of its 25 calls' arguments and answers, which a step reads and writes once. The time a run adds grows with its model calls and with what each step adds, not with the size of the conversation before it.

The performer compiles a JSON answer's schema once for the model calls of an attempt (`requestCompiler`) rather than at each call: on 2026-10-23, for the schema of the example in [Reasoning functions](../../docs/reference/reasoning-format.md), an attempt of 26 model calls spent a median of 0.58 and 0.67 ms compiling it at each call, and 0.012 and 0.029 ms compiling it once, over five rounds of 2,000 attempts, twice, at a load average above 120. The runs measured above answer in text, so they compile nothing.
