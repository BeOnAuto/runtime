# @on.auto/reasoning

The implementation of reasoning functions. It parses each source document into a `ReasoningFunctionDefinitionDocument`, including model settings and the compiled prompt template. The named, versioned `ReasoningFunctionDefinition` is stored separately by `@on.auto/definitions`.

User documentation starts with [Reasoning function format](../../docs/reference/reasoning-format.md), published at [on.auto/docs](https://on.auto/docs/). [Set up a model provider](../../docs/self-host/models.md) and the [model settings reference](../../docs/reference/model-settings.md) are the operator's guides, and the repository-only [complete format](../../docs/engineering/reference/reasoning-format.md) retains contributor details. Update the relevant files alongside behavior changes.

## Using it from code

```ts
import { compileAnswerSchema, LanguageModel, languageModelLayer } from '@on.auto/reasoning';
import { Effect, Result } from 'effect';

const schema = Result.getOrThrow(
  compileAnswerSchema({
    type: 'object',
    properties: { verdict: { enum: ['approve', 'reject'] } },
    required: ['verdict'],
    additionalProperties: false,
  }),
);

const decide = Effect.gen(function* () {
  const model = yield* LanguageModel;
  return yield* model.generate({
    model: 'anthropic/claude-sonnet-4-5',
    instructions: 'Decide whether the expense follows the policy.',
    messages: [{ role: 'user', content: [{ type: 'text', text: 'Dinner for four, 312 EUR, client present.' }] }],
    output: { type: 'json', schema, name: 'verdict' },
    settings: { max_output_tokens: 200 },
    timeout_ms: 30_000,
  });
});

Effect.runPromise(decide.pipe(Effect.provide(languageModelLayer(process.env))));
```

A request has `model`, optional `instructions`, `messages` (roles `user` and `assistant`, each with text parts), optional `conversation`, the messages of the earlier steps of a run as the AI SDK's model messages, optional `tools`, the definitions of the tools offered (`name`, `description`, `inputSchema`), `output`, `settings` (`max_output_tokens`, and optionally `temperature`, `top_p`, `seed`, `stop_sequences` and `reasoning`), optional `provider_options`, `timeout_ms`, `retries` and `room`. `generate` makes one call of the model: it answers with the result, whose `response` is the response messages as JSON text, from which the steps read the tool calls asked for, and `request_bytes` the size of the request sent. Some providers drop sampling settings for newer models and say so in `warnings`. `provider_options` passes options to the provider, keyed by the AI SDK's namespace for it: `anthropic`, `openai`, `azure`, `google`, `vertex`, `googleVertex`, `amazonBedrock`, `bedrock`, or the gateway's name. A call fails as `definition_invalid` before any provider is called when it holds a namespace no configured provider reads, or an option for a gateway its `allowed_provider_options` does not list; which options of the built-in providers a definition may set is checked when the definition is parsed (see [Provider options](../../docs/engineering/reference/reasoning-format.md#provider-options)). `requestIssues(request)` gives the problems of a request before it is sent, and the model's `admit(request)` everything `generate` would refuse before calling a provider: those problems, a model that resolves to no configured provider or is not allowed, and provider options that are not allowed.

A definition whose `output.shape` names an [output shape](../../packages/definitions/README.md#output-shapes) asks for JSON of that shape: its `output` is `{ type: 'json', schema, shape }`, `schema` the shape's compiled by `shapedAnswerSchema(shape)` at the answer's nesting of 128 with the shape's further check, so the answer is checked as any JSON answer is and refused as `output_invalid` with the shape's issues too, and its warnings are the schema's, placed at `/output/shape`: none, since every shape is portable. `output.schema` beside it and `format: text` are refused at their lines. The summary publishes the shape's schema as the output schema and its name as `details.shape`.

A JSON output is asked for in one of two modes, which `answerModeFor` of `src/model-calls/answer-mode.ts` chooses for each call from the route and the schema alone, never from the model's name, and nothing about it is stored with the definition: `described` through a gateway whose entry does not set `structured_outputs`, which the resolved model tells by `takesSchemas` (`src/model/model-resolution.ts`), and for a schema that is not portable; `portable` otherwise, on every built-in provider and through a gateway with `structured_outputs: true`. In described mode the call asks for text, with the schema as written in the instructions after the request's own (`describedInstructions` of `src/schema/json-output.ts`), and its answer is read as sent or from inside one Markdown code fence that is the whole of it (`answerValueOf` of `src/schema/described-answers.ts`), never coerced, and validated as any JSON answer is. In portable mode the provider is sent the portable form of the schema as the response format (`portableOutput` of `src/schema/json-output.ts`), and the answer is read back into the schema as written before it is validated against it and the shape's further check (`portableAnswerOf` of `src/schema/answer-reading.ts`), so the caller's `json` is always in the form the definition wrote. On a route that `takesSchemas`, a schema that is not one this package reads fails as `definition_invalid` before any provider is called, as before. The result of a JSON call, and its `output_invalid` or `content_refused` failure, carry `output_mode`, `described` or `portable`, which the steps record on `model_call_answered` and `model_call_failed`. The result's `text` is what the model wrote, so the kept response and a resumed attempt read the same bytes; the steps read the final answer again from that text (`keptAnswerOf`), reading it back when the call's fact says `portable` and as written otherwise, so a fact recorded before the portable mode existed reads as it did.

The portable form of a schema (`portableFormOf` of `src/schema/portable-schema.ts`, made once for each schema document and kept beside it) is lowered by `loweredSchema` of `src/schema/portable-lowering.ts` into a subset of JSON Schema every provider family the runtime was measured against accepts under strict structured outputs: `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `anyOf`, `$ref`, `$defs` and `description` alone, every object closed and listing every property in `required`, a `$ref` standing alone, an `anyOf` with nothing beside it but a description, every other schema typed, and one object at the root, which `portableIssues` of `src/schema/portable-checks.ts` checks of every form made. An optional property is sent required, with `null` added to its type and its `enum`, or beside it in an `anyOf` around a `$ref` or a choice, and one that allows `null` itself is sent as it is; a `$ref` with a description or a bound beside it is replaced by its definition, with the words added, since OpenAI refuses keywords beside a `$ref`, and a `$ref` alone points to the lowered definition; an object is closed, so the model cannot add keys an open one allows, and a closed object with no properties is sent with empty `properties` and `required`; a `oneOf` is sent as `anyOf`, a `const` or an `enum` with no type as an `enum` with the type of its values; a map, an object whose only schema is its `additionalProperties`, is sent as a list of entries, each a `key` and a `value`, with the `enum` of its `propertyNames` on `key`; a root that is not one object is sent as the `value` of one; the bounds and formats, `minLength`, `maxLength`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf`, `minItems`, `maxItems`, `uniqueItems`, `minProperties`, `maxProperties` and `format`, are written into the description as words (`src/schema/schema-words.ts`), so no provider enforces them while the model writes and the validator checks them after; and annotations and keywords this package does not check are left out. A schema is not portable, and its answers are asked for in described mode, when it holds a value of any type, an object of any keys, a list of items of any type, required names with no schema in `properties`, `allOf`, `not` or `prefixItems`, an `anyOf` or `oneOf` beside anything but a description, the bounds and a type every choice shares, a count of properties beside optional properties that may be null, an enum that mixes kinds of value, which Gemini refuses, keywords beside a `$ref` other than words and bounds, a definition that refers to itself, rules of the keys of a map that cannot be put into words, or definitions under both `$defs` and `definitions` (`src/schema/portable-flags.ts`); when its form is over the budget, counted with each definition where it is used, as Anthropic counts them (`budgetOf`): more than 16 fields that may be null or are a choice of types, 10 levels of objects, 5,000 properties, 1,000 enum values or 120,000 characters of names and enum values; when the form breaks the checker; or when its round trip fails (`roundTripIssues` of `src/schema/schema-round-trip.ts`): a value the schema accepts, made once with its required properties alone and once with every property, written as a model would write it in the portable form, must match the form and read back to a value the schema accepts, and a schema no such value can be made for is not portable either. The report of what is not portable names each construct at its pointer in the schema as written, and each count over the budget at the root with its `rewrite`, what brings it within, such as `make some of these fields required and of one type, or split the answer`. A definition's warnings are built from that report (`src/definition/definition-schemas.ts`), one for each issue: that answers to the schema cannot be enforced while a model writes them, the construct or the count, that answers are checked after the model writes them, and the `rewrite`, or, for a construct, that part rewritten as the reasoning-function guide says; with them, a warning for each keyword this package does not check, which answers are not checked against. They are the same for every model and every server, and the definition view of `@on.auto/definitions` reads them again from the document whenever a definition is read. Reading back (`readBack`) drops a `null` written for an optional property that does not allow `null` itself, makes a map of its entries, keeping the first value of a key given twice and naming the key as an issue, takes the first choice whose schema the value read back matches, and unwraps the root; a property that is optional and allows `null` may so come back as `null` where the model could have left it out. The issues of an answer read back are placed in the schema as written, as the caller sees them, and `writtenPointerOf` places each at its pointer in what the model wrote, such as `/value/1/value` for `/alice` of a map at the root.

A JSON answer that is not JSON, or misses its schema or the shape's further check, is asked for once more (`answerRepairedOnce` of `src/model-calls/answer-repair.ts`): the same request, in the same mode, with the answer as an assistant message, then, as the user, at most five of its issues at their pointers in what the model wrote, which for an answer in the portable form are the pointers `writtenPointerOf` gives, or that it is not JSON (`repairWords` of `src/schema/repair-words.ts`), and nothing else changed: the tools, their earlier calls and results, and the tool choice stay as the first request had them, so the second request is valid wherever the first was, which a tool choice of `none` is not on Anthropic, whose API refuses the tool blocks of a conversation sent without tools, nor on Bedrock, which drops them. The second answer is read as JSON whatever it asks for, so a tool call in it is not JSON, and no third is asked for. An answer cut off at `max_output_tokens`, stopped by a content filter, refused, or empty is not asked for again; a refusal, a chat completion whose message carries `refusal`, fails as `content_refused`. The request's `room`, which the steps set on every call, holds `input_tokens`, the input tokens the run has left, `context_window` where the run knows the model's, and `ends_at`, when the bound of a run that calls tools ends, in milliseconds since the epoch. The second request is not made when its input, the first request's input tokens with the answer and the issues counted at the first request's tokens per byte, would pass the input tokens left once the first is spent, or, with an answer as long again, the context window, or when less time is left before the call's `timeout_ms` or `ends_at` than the first answer took. A result asked for once more carries `repair`, with the `outcome` `repaired`, the `issues` told, placed in the schema as written, and the second request's `usage`, `cost_usd` and `duration_ms`, while its own `usage`, `cost_usd` and `request_bytes` are those of both requests. An `output_invalid` failure carries `repair` with the `outcome` `invalid` and the same, or `skipped` and `because`, `input_tokens`, `context_window` or `time`, and a `content_refused` of the second answer carries it too. When the second request fails, the answer settles as the first one did, as `output_invalid` with its `usage` and `cost_usd`, and `repair` with the `outcome` `failed`, `because`, the kind its failure is classified as, the `issues` told and `duration_ms`: the model call throws `RepairFailed` of `src/model-calls/answer-settling.ts`, whose cause `attemptedCall` of `src/model-calls/call-attempt.ts` classifies and reports as any failure of a request, and an error it does not classify is a defect as ever. The steps record it on `model_call_answered` and `model_call_failed`, with the `cost_usd` an `output_invalid` or `content_refused` failure carries. The bytes of a request (`request_bytes`), from which the gate reckons tokens per byte, count the schema a provider is sent beside the prompt. The counter `auto.on.json_answers` counts the final answer of every call that asks for JSON, by provider, model and `auto.on.output_mode`, its `auto.on.outcome` `valid`, `valid_after_repair`, `invalid`, `repair_skipped`, `repair_failed` or `refused`; an answer that asks for tools, and a call that fails before any answer, count nothing.

A JSON answer asked for in portable mode, whose schema was sent to the provider, is asked for once more in described mode when the provider refuses the request with HTTP 400 or 422 for its schema (`settledCall` of `src/model-calls/call-settling.ts`): the same request through the same route taken as one that takes no schemas, so with the schema in the instructions and no response format. The refusal is for the schema when `apiCallFailure` (`src/model-calls/api-call-failure.ts`) classifies it `definition_invalid` with `schema_refused`: the body's `error.code` is `invalid_json_schema` or its `error.param` starts with `response_format` or `text.format`, as OpenAI's do, or, where no such code says what was refused, the message speaks of `response_format`, `json_schema`, `output_format`, `output_config`, structured output or a schema, as Anthropic's and a gateway's do, or is Gemini's `Request contains an invalid argument.`, which names no argument and is how Gemini refuses a schema too large to compile. A 400 or 422 for anything else, too long, an API key refused, content refused, a model or a setting, and any other status, 401, 403, 404, 429 and 5xx among them, fail the call as ever. Each request is one attempt, `attemptedCall`, which classifies and reports how it failed, under the call's one deadline. The second request is not made when less time is left before the call's `timeout_ms` or `ends_at` than the refused request took; the call then fails as `definition_invalid` in the words `<provider> refused the request (HTTP <status>): the request was rejected as invalid`, with `schema_refusal`, the `outcome` `skipped`, `because` `time`, and the refused request's `status` and `duration_ms`. Whatever the second request settles carries `schema_refusal` with the `outcome` `described`: an answer, and an `output_invalid` or `content_refused`, through the mode the described call answers in (`Calling.refusal` of `src/model-calls/model-call.ts`), beside `output_mode: 'described'` as on any described call, and any other failure as the attempt classifies it, which marks the failure it has just made. A second refusal with HTTP 400 or 422 fails as `definition_invalid` in the same words, with the `outcome` `refused_again`: the schema was not the cause, and the rejection says to check the model's settings or choose another model. The described answer is asked for once more as any JSON answer is, with the time left counted from the start of the call, so a call asks at most three times, the refused request, the described one and its correction; the AI SDK sends each of them again on HTTP 408, 409, 429 and 5xx when the request's `retries` leave the retries to it, so there may be more HTTP requests. The `usage`, `cost_usd` and `request_bytes` of the call are those of the requests the model answered: a refused request reports no usage, and the steps reckon tokens per byte from `request_bytes` and the input tokens (`tools/turn-meter.ts`), which bytes with no tokens counted would skew; its `duration_ms` includes the refused request. The provider's words for both requests reach `reportProviderMessage`. The counter `auto.on.json_answers` counts the refusal as `schema_refused`, without an output mode, beside the outcome of the final answer, except a refusal the provider repeats for the described request, which the schema did not cause.

`makeModelAccess(settings, options)` builds the same model and also returns `status`, and the `catalog` that [`list_models`](../../docs/reference/model-settings.md#listing-the-models) reads, whose `list(provider?)` gives the list. Its options inject a `fetch` and credential sources (`aws`, `google`, `azure`), which is how tests run without a network and how per-tenant credentials will be added, `reportProviderMessage`, which receives the [provider messages](../../docs/reference/model-settings.md#provider-messages) a caller does not see, `reportOperatorHint`, which receives the [operator hints](../../docs/reference/model-settings.md#operator-hints), `scrubProviderText`, the composer's own scrub of what a provider says, and `loadEntraIdentity`, which loads one provider's identity library, for that provider without a key. Without it the identity library is absent and that provider without a key is not configured, so a program that composes the core elsewhere, where the library is not installed, bundles no import of it and needs no alias for it. `scrubProviderText` runs after the secrets of the settings are redacted, on every word of a provider's wherever it goes: the reports and the hints, and a failure's `provider_message` and error code, and so the call's fact and the caller's rejection, which are made of the failure (`providerTextScrubber` of `src/settings/message-exposure.ts`). A composer passes it for secrets the settings do not hold, such as a key its own `fetch` adds to each request. A request may carry a `run_id`, which only those reports use; the reasoning function adapter sets it to the run's id.

## Tools

A reasoning function whose front matter names `tools` (each `server/tool`, or `server/*`) runs with the tools of the tool servers configured for its playbook, MCP servers and HTTP APIs alike. `makeReasoningFunctionAdapter` takes the server's `ToolAccess` from [`@on.auto/tool-servers`](../../packages/tool-servers) as `tools`, as a type only: it imports the helpers it needs to parse `tools` and bound a run from `@on.auto/tool-servers/policy`, which loads no transport code; `tools` is required, and a test with no tool server gives `noToolServers` of `@on.auto/tool-servers/testing`; with no server configured, a function that names tools is rejected as `unavailable`, kind `tool_not_offered`, in the words of `namedLinks`. The adapter then says it may change something outside (`mayChangeOutside`). The capability declares as the stream kind it owns `tool-calls`, with the presenter of `@on.auto/tool-servers`, `handCallPresenter`, since the server serves `query_connection` and `execute_connection`, which call a tool as a run of a reasoning function would, beside it: the playbook shows each call made by hand in its events, under the types of a run's calls, `tool_call_started`, `tool_call_answered` and `tool_call_failed`, on a stream of its own whose kind tells it from a run's, as the declarations allow, since a stream kind is checked apart from the facts of a run.

A function that names tools calls tools (`callsTools`), so the start of its run records that. A run first admits its request with the model's `admit`, so a run whose model is not offered reaches no server and starts no process; it then opens its tools with its id, org, playbook and journal, and with a way to keep the images its tools answer where the adapter is given one, before the model is called, and rejects as `unavailable` with kind `tool_not_offered` (because `tool_server_not_configured`, `tool_not_allowed` or `tool_not_listed`, or for a connection a person added `connection_pending`, `connection_broken`, `connection_not_allowed` or `connection_unavailable`) or `tool_server_failed` (because `unreachable`, `failing` or `rate_limited`).

The adapter's port `images`, a `KeepRunImage` (`src/steps/kept-content.ts`), keeps an image a tool answers a run as an asset of the run: the run gives the tool access, as the `keepImage` of the caller it opens its tools for, a keeper bound to the run (`imagesKeptOn` of `src/tools/tool-images.ts`), which hands the port the bytes and the call, `{ call_id, server, connection_id?, tool }`, beside the run's playbook, a context of the run's caller, its id and its definition, of the type `reasoning`, and the lineage of the run's start, and answers the asset's id the port gives, or nothing where it kept none. The tool servers then keep the answer with each image kept so named in place of its bytes ([What is recorded](../../packages/tool-servers/README.md#what-is-recorded)). The port is `toolImagesKept` of `@on.auto/generation`, which the server composes over its ledger and content (`packages/server/src/composition/kept-by-runs.ts`); the capability takes it as a port, since one capability imports no other. Without it, as in a test that gives none, an image stays in the answer as the tool sent it.

## Steps

A run proceeds one model call at a time, each call a fact on its stream (`src/steps`). The run's state, `StepState` (`step-state.ts`), is folded by one function, `evolve`, from the run's facts and the content it kept, and the live path and the resume path share it: a live step folds the fact it just recorded with the content it just made, and a resumed run folds the facts of its attempt with the content it reads back by digest (`recorded-steps.ts`). The state never holds what only the memory of an attempt knew. From the state, `nextStep` (`step-decision.ts`) decides what follows: a model call, the tool calls the last answer asked for, the last step without tools, or an ending (`answered`, `failed`, `stopped`, `limit_reached`, `outcome_unknown`, `unreadable`). `step-loop.ts` performs the decisions until an ending, and `run-steps.ts` makes a run of them.

- A model call (`model-steps.ts`) records `model_call_started`, under the number the decider takes as the next one (`@on.auto/definitions`), performs the call, and records `model_call_answered` or `model_call_failed` with the facts `step-facts.ts` makes of the result or the failure. A call is one step of the AI SDK, `isStepCount(1)`, with the tools as definitions without `execute`, so the library calls no tool. The request is the prompt, the conversation the state holds, the messages of the earlier steps as the library's model messages, and the tools; the number of bytes it sends is measured where the library announces the call, `onLanguageModelCallStart`, and kept on the answer as `request_bytes`.
- The calls the model asked for (`asked-calls.ts`) are read from its response. The library's own result stands for a call of a tool the run does not offer or whose arguments do not parse, so the run adds none of its own. A call of a tool this attempt does not offer, though the attempt that asked did, because its server changed between them, is refused in words the model reads, `noLongerOffered`, and an admitted call carries the tool it is sent through. Each other call is admitted within the run's tally and its count (`admission`, `admittedAsSent`, `countedAsSent`, `askedPastTheCount`, `shownAgain` and the bounds of `@on.auto/tool-servers/policy`): 25 calls of tools not marked `reads`, an unmarked tool among them, or, where the function sets `max_tool_calls`, that many calls of any kind, reads and refused repeats included; 256 KiB of arguments, a third same call refused and pointed to the earlier result, and an input that is not an object refused. A refused call is not sent and not recorded, and the model reads why. The admission of a step's calls follows one rule, folded from the run's facts (`call-admission.ts`): first, every call the run has sent and will not send again, one that has a `tool_call_started` and its answer, or was sent as a call that may change something, or whose tool is no longer offered, is counted by the marks its start facts record (a call sent once as one that may change something counts as one), never refused, whatever the order the model asked in; then every other call, one not started or a read whose answer is missing and that would be sent again, is admitted in the order asked, by the mark of its tool as offered now, against what is left of the count, and refused past it, so a call is never sent again as another kind than the kind it was counted as. A call's start follows the step's answer in the stream, so the fold admits the step as the answer is folded, and marks the step to be admitted again when a start fact records what the call was not counted as (`countedAsItsFact`); the step is admitted again from the tally before it where it is next read, before a decision and before the next model call (`withItsAdmission`, `admittedAgain`), so a step whose calls all start as they were counted, as in one attempt, is admitted once. The refusals it withdraws and gives are retold to the meter. A call refused for its arguments or as a repeat, never sent, is not counted.
- The admitted calls (`tool-steps.ts`) run at once. Each records `tool_call_started` from what the tool's `start` gives, under the number the fold of the attempt's facts gives as the next, inside the step's one permit, as a model call does, performs the call, and records its end. The fifth server failure stops the calls still in flight as `cancelled`, in the words "The run stopped its calls once its tool servers failed too often", and the run's bound gives up a call in flight the same way, in the words of the bound. A fact that cannot be written fails the step, and the attempt never goes on without it: a fact another attempt wrote first is a conflict in its own words, and a failure of the database a defect the server reports as an incident.
- Each call has the room its answer may fill (`src/tools/turn-meter.ts`), measured on the request the last model call sent: the call's bytes a token, its bytes sent over its input tokens, turn the room into bytes, the smaller of the window and what `mostInputTokens` leaves after every call made, less the call's input and output tokens, shared equally by the step's calls, so an answer the model's context cannot hold is cut where it stays valid JSON, with a note, and read whole when no window is known or the provider counted no input tokens; nothing is taken from the window for the output, since the catalog's window is the most input tokens a model takes. `mostInputTokens` and the window come from the adapter's `reading`, a `ModelReading` the server gives: `mostInputTokens` from `REASONING_MAX_INPUT_TOKENS`, 2,000,000 unless set (`defaultMostInputTokens`), and `contextWindowOf`, the catalog's `contextWindowOf`, which resolves the model's alias and reads the `context_window` its provider lists for it, through the listing's cache; a run without tools reads no window, and a test that gives no `reading` has the default bound and no window.
- Every model call has its own deadline, the request's `timeout_ms`, which the time the tools take does not count against, armed when the call starts and ended however it settles. A run that calls tools is bounded by ten minutes from its start, as `run_started` recorded it, or one call's deadline when that is longer.
- Once a step has asked for a call past the run's count, or before a step whose projected input, the last step's input and output tokens and its answers' bytes at its ratio, would leave less of `mostInputTokens` than that projection again, the next step is made with the tools withheld and the conversation told again as text (`src/tools/final-step.ts`), since some providers refuse tool messages without the tools' definitions: the calls in words, and their answers inside a block fenced by 32 random hexadecimal characters drawn for that step, labelled as the results of the tools the model called, data to answer from and neither instructions nor the user's words, so no result can close the block or pass for the user. A tool call in that step ends the run with `no_answer`. This is the flow of a function whose `exit_behavior` is `continue`; the answer of a step made so carries `incomplete_details`, `max_input_tokens` where no step asked past the run's count and the meter as it stood when that step started leaves no step after it, else `max_tool_calls`, which also names a last step an earlier release made without tools at its count of every call, and a text answer cut off at `max_output_tokens` carries `max_output_tokens` (`incompleteDetailsOf` of `src/capability/steps-answer.ts`, with `answeredAtALimit` of `src/tools/tool-endings.ts`), which `finishedOf` hands to the core beside the output and the record, and the core records on `run_succeeded`.
- Under `exit_behavior: error`, the document's default, no step is made without tools. A step that asks for a call past the run's count, or a step made when the budget would not cover another after it that asks for a tool, ends the steps `limit_reached`, with the limit and its number, before any of its calls is sent. The state keeps the meter as it stood when its last model call started (`meterBeforeLastCall`), so an attempt that goes on from the facts decides the same. `limitEnding` of `src/tools/tool-endings.ts` makes the rejection: `conflict`, kind `unworkable` where the run called only tools marked `reads`, else `effect_unknown`, with the `because` `max_tool_calls` or `max_input_tokens` and a detail that names the number and what to change.
- The model is given the tools in the function's own output mode, text or JSON, beside the `json` tool the Anthropic and Bedrock providers add for a JSON output they do not take in the output mode itself (`@ai-sdk/anthropic` 4.0.70 and `@ai-sdk/amazon-bedrock` 5.0.103 name it `json`), a name with no `__`, so no tool of a tool server takes it (`src/steps/provider-steps.test.ts` pins both).
- The record's `warnings` add, after the provider's, one `compatibility` warning for each place in a tool's input schema where the provider of the run's model may refuse the schema or not hold the tool's arguments to it, named as the tool's name, `inputSchema#` and the JSON pointer, such as `graph__search inputSchema#/properties/query/maxLength` (`src/tools/input-schema-warnings.ts`). The rules are those of a JSON output schema (`src/schema/schema-portability.ts`) that hold for a tool's arguments: a root that is not an object, and for Anthropic models the bounds and `oneOf` they do not enforce and the formats they do not accept, each worded for a tool's arguments. The rules for open objects and optional properties bind strict structured outputs only, and the AI SDK sends tools as not strict (`@ai-sdk/openai` 4.0.83 sets `strict: false` unless a tool asks), so they are left out. A schema of more than 64 KiB or 64 levels is not checked.

`PerformJob` (`src/jobs/jobs.ts`) is the one seam between the steps and the world: a job in, an answer out. A model call job carries the request, its output as data, the schema document of a JSON output and the name of its shape, and answers the `ModelResult`; a tool call job carries the call's id, the tool's model-facing name, its server, its input and its room, and answers the call's end and the reply the model reads. A job holds no closure and no signal, and performing it writes no fact: the steps alone record. `performedInProcess(languageModel, telemetry)` (`src/jobs/performed-in-process.ts`) gives, for a run's offered tools, the implementation of this process: it compiles the output schema, or the shape's, as the definition compiled it, once for all the model calls of an attempt (`requestCompiler` in `src/jobs/compiled-request.ts`), a schema it cannot compile failing the call as `definition_invalid`, calls the model, and sends a tool call through the run's offered tool, under an `execute_tool` span that carries the call's arguments and result only where telemetry records content; a call of a tool it does not offer is answered as a `server_failure` that was never sent. The adapter takes another as `performJob`. `PerformJob`, its jobs and `performedInProcess` are exported from the main entry, so a shell that performs a model call or a tool call per invocation performs it as this process does.

A shell that hands out one job at a time drives the same steps from the facts (`src/steps/step-jobs.ts`). `stepRecordingOf(services, run, tools)` assembles what the steps of a run record through, its model, the base of its requests, its tools, its bounds, its journal and the content it keeps, with no performer; `stateOfTheAttempt(recording, prompt, attempt)` folds the state of the attempt from the calls it recorded and the content they kept, as a resumed run does; `jobsOf(recording, state)` decides what follows and records the start of each job it hands out: one model call, or the calls the last answer asked for, each under the number its start was recorded with, or no job and the ending, after it records an interrupted end for each call left open. `performedJob(perform, job)` performs one job with a `PerformJob` and answers its `JobAnswer`, the model's result or failure with the call's duration, or the tool call's end and reply, and `answerRecorded(recording, state, answer)` records its end and answers the state after it. A start the journal refuses because the run's cancel was recorded ends the steps `cancelled`.

Within one invocation the shell keeps the attempt's state in memory, the `StepState` each of these answers, which holds the content of the attempt's calls, and gives it to the next `answerRecorded` and `jobsOf`; it folds a state from the facts with `stateOfTheAttempt` only as an invocation begins. A run whose playbook keeps no content of its calls, one whose `RunTools.keepsContent` is false, therefore goes on across the jobs of one invocation as the loop carries it, recording the same facts. An invocation after the one that began it finds no content to fold from the facts: `promptOfTheAttempt` ends the run `restarted_without_content`, in the words of `restartedWithoutContent`, and a state folded from its facts ends the steps `unreadable`, which `stepsAnswerOf` words the same (`src/steps/step-jobs.test.ts`).

The rest of what the adapter does around the steps, the shell does itself, with the functions the adapter does it with (`definitionRun` of `src/capability/definition-run.ts` composes them):

- The definition: `readReasoningFunctionDefinition(source)` reads a definition's source into the `ReasoningFunctionDefinitionDocument` the capability runs, or fails `invalid_input` with its issues, as saving it does (`src/definition/definition-reading.ts`, the capability's own `parse`); every function below takes that document, so a shell reads the version a run started with once and holds it.
- Before the steps, as an invocation begins: `beforeTheSteps(journal, model)`, what the attempt's facts say so far, with `ended`, which records an interrupted end for each call the attempt left open before a rejection ends the run; `promptOfTheAttempt({ content, clock }, { definition, input, run, before })`, the template rendered on the clock on a first attempt, and the prompt the first model call kept on a later one; `admitted(languageModel.admit(requestFor(definition, prompt, run)), before)`, the model's admission; and `withTools({ access, references: definition.tools, run, before }, use)`, which opens the run's tools for `use`, the `RunTools` `stepRecordingOf` takes, and closes them after.
- Around the jobs: the bound of the run, and the stop of the other calls once the tool servers failed too often, which the loop keeps around its own performer; a shell bounds the jobs it hands out itself.
- The ending: `stepsAnswerOf(definition, { state, ending }, recording.tools.definitions, recording.bounds.limits)`, the answer checked again, or the rejection the ending is, and `finishedOf(definition, answer)`, the run's record of its prompt, settings, format, result and spending.
- The liveness check on resuming: an attempt is live while the last fact of its run's stream is no older than the longest gap between two facts of a live attempt, `attemptIsLive(quietMs, resumesAfterMs)` of `@on.auto/definitions`, over `ageOfLastAppend` of the run's stream and `resumesAfterMsOf(definition, callMs)` of this package, where `callMs` is the call bound of the tool access. A shell that resumes a run itself makes no attempt of a live one, as `run_definition` refuses one as `stillRunning`; within one process `LiveAttempts` of `@on.auto/definitions` holds one attempt a run besides, which a shell whose invocations do not share a process has only this check for.

The loop of this process makes the same beginning and end of each job around its performer, so a run driven one job at a time from its facts records what the loop records for the same answers, and its steps end the same way (`src/steps/step-jobs.test.ts`).

The content of a run is kept per step, through the content store the server gives the adapter as `content` (`src/steps/kept-content.ts`), when every tool server of the run keeps content (`RunTools.keepsContent`), and always for a run without tools: the messages the call adds, the prompt for the first call, the answers of the tools for a later one, the conversation told again for the last step, under `messages_sha256`, and the response as the library's response messages under `response_sha256`. A step never keeps the whole conversation again, so what a run keeps, scrubs and digests grows with its length and not with its square. The answers of the tools are kept by the tool servers under their `result_sha256`. What a run keeps is scrubbed of the secrets of its tool servers first (`RunTools.scrubJson`), and a run goes on from what it kept, alive as after a resume, so a secret in the prompt or in the model's response is `[redacted]` in every model call the run makes and in every tool call the model asks for. The answer is checked again once scrubbed (`src/steps/steps-answer.ts`): a JSON answer that no longer parses, as one whose number held a secret, or no longer matches its schema ends the run as an `output_invalid` answer does, never as a defect.

A run is not interrupted by its client going away: `@on.auto/definitions` runs its attempt in the scope of the process, so only the process stopping interrupts it, which leaves it to be resumed from its facts. A run a workflow's call asks for runs in that call, which its workflow host stops when it stands by or stops, and the host that takes the workflow over resumes it. `cancel_run` cancels it: where its attempt outlives its client, the process where it is going interrupts it, as the workflow host interrupts the call it cancels, and the capability's `resumes.cancelledAttempt` (`cancelledAttemptOf`, `src/capability/before-the-steps.ts`) ends each call still open as `interrupted`, from the run's facts, and gives the spending so far; otherwise its journal refuses its next start as cancelled, which ends the steps (`src/steps/step-loop.ts`, the calls of the step all settled first, `StepCancelled` carrying the state of the step's last fact) and the run as `RunCancelled`, with the spending of its model calls so far. A run that is still `started` and performed again goes on from its facts (`recorded-steps.ts`), at the version it started with; [A run performed again](../../docs/reference/reasoning-format.md#a-run-performed-again) is its user documentation. Before it renders, admits or opens anything, a resumed attempt folds its facts (`src/steps/attempt-facts.ts`, `src/capability/before-the-steps.ts`): it takes its prompt from what its first model call kept and never renders it again, and an ending it meets before its steps, its model no longer admitted (its provider not configured, the model not allowed, or the definition no longer workable) or its tool servers not opened, is worded as the steps' endings are, with the tools it called and the spending of its model calls, its open calls ended as `interrupted` first. The fold rebuilds the conversation from the kept content, so the request a resumed run sends is the one its first attempt would have sent. A model call that was answered is never paid again. A model call started without an answer is ended as `interrupted` and made again under the next number. A tool call started without an answer is ended as `interrupted` and made again when its fact says `read_only`; when one open call of a step is of a tool that may change something, no open call of that step is made again, every one is ended as `interrupted`, and the run ends with `call_outcome_unknown`, since making it again could repeat what it did. A call of a tool the run no longer offers, because its server changed between the attempts, is refused in words the model reads, `noLongerOffered`, and never sent. A recorded model call failure ends the run as it did, a recorded `run_cancel_requested` ends it cancelled (`@on.auto/definitions`), and a run whose content is not kept, or is gone, ends with `restarted_without_content`. Whatever ends the steps, the run's bound and a cancel among them, ends the calls still open as `interrupted` first (`src/steps/step-loop.ts`), so no ending leaves a start without an end. Every start names its number, so a call is never started a second time, across servers too: of two attempts that go on at once, the one whose start is recorded second meets `taken` before it sends anything. A run declares `resumes.afterMs`, its model call's deadline plus the call bound of its tool access (`ToolAccess.callMs`), the longest gap between two facts of a live attempt, from which `@on.auto/definitions` tells a live attempt from a dead one by the database's clock.

Once a run has recorded a tool call, every `unavailable` ending it meets, and a definition its resumed attempt finds no longer workable, has the kind `tools_unfinished` when every tool it called is marked `reads`, and becomes a `Conflict` of the kind `effect_unknown` when any is not (`src/tools/tool-endings.ts`), with because `server_failed`, `model_unavailable`, `definition_refused` for that definition, `run_bound`, `no_answer`, `restarted_without_content` or `call_outcome_unknown`, and words that name the tools it called in words, never as `server/tool`. The words of `tools_unfinished` say that a new run, or a workflow's retry, may make it; those of `effect_unknown` that whether the tool changed something is not known, and never ask to try again. The run's sessions end however it ends.

A run that calls tools costs more: every step resends the conversation so far, so a run that reads large answers spends its input tokens quickly, and `REASONING_MAX_INPUT_TOKENS` bounds what one run may spend in the unit the operator pays for. A provider that signals a request too long, HTTP 413, the body's `error.code` or `error.type` among `context_length_exceeded`, `request_too_large` and `string_above_max_length`, or a message in the words providers use for it, Anthropic's `prompt is too long`, OpenAI's `maximum context length` and LiteLLM's `ContextWindowExceededError`, the signal then `its error message` (`src/model-calls/api-call-failure.ts`, beside the content-filter codes), fails as `request_too_long`, which ends the run `conflict` `unworkable` in words that name the signal and, when the run's tools answered, the bytes they answered and the input tokens the provider counted for the last step it answered, advising a page. Without a signal the rejection keeps the status and its reading, the body's code when it carries one, scrubbed of secrets as a message is and cut at 64 characters, and the provider's message when the operator exposes it, and claims no length, whatever else the message says. A 400 whose body's `error.details` carry Google's reason `API_KEY_INVALID` fails as `credentials_rejected`, as a 401 does.

A provider's cost reaches the answer through the middleware that keeps the response id (`src/model-calls/model-call.ts`), as `cost_usd`: a gateway entry names the header its gateway answers the call's cost in, in US dollars, as `cost_header`, or names none and no cost is kept; a provider that is no gateway keeps none, and a header that does not hold a cost of zero or more keeps none either. Each model call's fact keeps its cost, and the record of the run (`src/capability/spending-record.ts`) adds them up beside its tokens.

## What a rejection records

A rejection after any model call of the run ended carries a `record` of the run's spending, the sum of its model calls' facts so far: `usage`, shaped as in the record of a run that succeeded, `duration_ms`, and `cost_usd` where a call answered a cost. That holds for every ending: `output_invalid`, `content_refused`, `no_answer`, an answer that leaves no room in what a run records, the endings of a deadline, the run's bound and tool servers that kept failing, `call_outcome_unknown`, `restarted_without_content`, and the endings a resumed attempt meets before its steps. `@on.auto/definitions` keeps it on the run's `run_rejected`. A rejection before any model call ended carries none.

## Voice

The capability also writes out what a person says, so a person can speak a comment in Studio. It serves two org operations over HTTP alone, each permitted by `playbook:read`: `transcribe`, `POST /voice/transcriptions`, and `get_voice`, `GET /voice`. [Voice](../../docs/reference/http.md#voice) in the HTTP reference documents them, and [Voice model](../../docs/reference/model-settings.md#voice-model) the setting.

- `src/settings` reads `VOICE_MODEL`, `voice_model` in the file, through `src/voice/voice-settings.ts`: a model reference whose provider is an entry of `model_gateways` or `openai`. Any other provider, a value that is not `provider/model`, and `openai` without `OPENAI_API_KEY` are settings errors, which stop the start. Aliases and `allowed_models` do not apply to it. `get_voice` answers `{ model }`, the reference as the settings give it, or `null`.
- `transcribe` takes `{ audio, type, seconds }`: the recording in base64, its media type, `audio/webm`, `audio/ogg`, `audio/mp4` or `audio/wav`, and its length in whole seconds from 1 to 120, as the caller measured it. It refuses `unavailable`, "This runtime has no voice model", where none is set, and `invalid_input` at the field for the rest, before any provider is called. It then sends one multipart request, `file` and `model`, to the provider's `/audio/transcriptions`, the gateway entry's `base_url` with its key, headers and query parameters, or OpenAI's with `OPENAI_BASE_URL` and `OPENAI_API_KEY`, through the model access's `fetch`, with the retries, the redaction and the failure kinds of a model call, within 60 seconds for every attempt. It answers `{ text }`, the answer's `text` without the white space around it.
- A `402` whose body's `error.type` is `credits_exhausted`, `account_closed`, `meter_unavailable` or `model_not_offered` is the refusal of an account that pays for the gateway's calls, made before the model is called: `transcribe` answers it in its words, `error.message`, as `conflict` of that kind for the first two, with `error.resolve_at` and `error.because` where they are given, and as `unavailable` of that kind for the other two, is not tried again, and records nothing. Any other `402` is the gateway unable to serve the call: `transcribe` answers it as a provider unavailable is answered, `unavailable`, "`<provider>` could not serve the request (HTTP 402); try again later", without trying it again, and records `voice_refused` with `because` `provider_unavailable`.
- A transcription is a model call, not a run: it starts no run, the meter admits nothing for it, and nothing of it reaches a playbook. Each call that reaches the provider records one fact on a stream of its own on the org's ledger, `org/<org>/voice/<id>`, through `OrgWriter`, with `ActedContextSchema`: `voice_transcribed`, `{ id, model, type, audio_bytes, seconds, text_characters, cost_usd }`, once the model answered, or `voice_refused`, `{ id, model, type, audio_bytes, seconds, because }`, `because` the failure's kind, once it failed or was refused. `id` is the transcription's, a UUIDv7 the runtime gives it, and `cost_usd` is read from the entry's `cost_header` as a model call's cost is, or `null`. Neither keeps the recording or the text. `VoiceEventSchema` is their schema; their fixtures are beside the module that records them, listed in this package's `recorded-facts.json`, and the server reads them among its known facts.

## The answer check

`answerCheck(models)` of `src/answer-check/answer-check.ts` asks each model the same nine cases through the `LanguageModel` it is given and answers an `AnswerCheckReport`: for each model its `outcome` and its `cases`, each with its `outcome`, `output_mode`, the failure's `detail`, `status` and `provider_message`, up to five `issues`, the `schema_refusal`, `cost_usd` and `duration_ms`. The command `pnpm answer-check <provider/model>...`, `scripts/answer-check.ts` at the repository's root, gives it `languageModelLayer(process.env)`, so the model access `makeModelAccess` builds from the server's own settings, prints the report, and exits with 1 unless every model passed, with a correction or without; [Check your models](../../docs/self-host/models.md#check-your-models) is the operator's guide. The models are asked four at once, the cases of one model in turn, each request for 4,096 output tokens at most within the deadline `timeoutFor` of `src/capability/definition-request.ts` gives a run's call that may write as many.

The cases are in `src/answer-check/check-cases.ts` and their schemas in `check-schemas.ts`: the four shapes; the reference schema, at the portable budget's edge, 16 fields that may be `null` or are a choice and 10 levels of objects once its definitions are inlined, which `check-schemas.test.ts` holds it to; an outline whose sections refer to themselves, so it is described on every route; the tools case, the `categories` shape asked with the tool `city_population` offered, whose calls `tools-case.ts` answers from a table, in three requests at most; and two canaries, a contact card with one field that may be `null` more than the budget and a list whose `maxItems` is 200, the bound of the `categories` shape, kept as a keyword. A canary's output sets `enforced_as_written`, which `answerModeFor` reads to send the schema as written, with no portable form and no budget, so it reaches the provider enforced; nothing else sets it. `src/answer-check/case-findings.ts` finds a case's outcome from the call's result or failure: a `schema_refusal` other than `refused_again` makes it `schema_refused`, whatever the described request answered; otherwise a valid answer is `passed`, or `passed_after_repair` with a `repair`; `output_invalid` and `content_refused` are `invalid`, as is a tools case whose model answers without calling the tool or still calls tools at the third request; `rate_limited`, `provider_unavailable`, `timed_out` and a defect, an `UnclassifiedModelError`, are `unavailable`; and every other failure, `credentials_rejected`, `definition_invalid`, `request_too_long`, `model_not_allowed` and `provider_not_configured`, is `unreachable`. A model's outcome is the worst of its cases, canaries left out, in the order `unreachable`, `schema_refused`, `invalid`, `unavailable`, `passed_after_repair`, `passed`.

Its tests run scripted models, one for each outcome and the tools case's endings, behind two gateway entries, one with `structured_outputs` and one without: `scriptedCheckFetch` of `src/answer-check/scripted-checks.ts` tells the case of each request by its prompt and answers it as each model would, writing an enforced answer in the portable form with `writtenFormOf`, and `src/answer-check/check-harness.ts` runs the check through `languageModelLayer` with that `fetch`.

## Testing

`makeReasoningFunctionAdapter({ languageModel, offered, clock, tools, content })` makes the runtime adapter for `makeDefinitionOperations`; the server gives it the language model and offered-model configuration from `makeModelAccess`, its `ToolAccess`, the ledger's content store and its telemetry, and a test the scripted model below. `ReasoningFunctionAdapterOptions` names its options. `clock` is optional: without it, `today` and `now` come from Effect's `Clock`. The 200 ms a render of the prompt may take are counted on the monotonic time of the same clock, the one given or Effect's. A template's tests render it on `standingRenderClock` of `@on.auto/definitions/testing`, which stands still, or on `steppingClock`, moving a millisecond each time it is read, so a render is stopped for its time by that clock and never by a slow machine.

`@on.auto/reasoning/testing` exports a fake for the tests of other packages. `scriptedLanguageModel(...replies)` answers each model call with the next reply, admits and rejects an invalid request as the real one does, records every request (`requests()`), and provides itself as a `layer`. A reply is a function of the request; `answers(textResult('Hello'))` and `answers(jsonResult({ verdict: 'approve' }))` build the usual ones, `answers(toolCallsResult(calls))` an answer that asks for tool calls, and `() => Effect.fail(new RateLimited({ ... }))` scripts a failure. Its replies are given one by one or in lists (`ScriptedReplies`): `callingTools(calls, then)` is the two replies of a run that calls tools, the answer that asks for the calls and `then`, and `answeringFromTheTools(calls, answer)` answers from what the tools answered, read from the conversation the second call is sent.

No test in this package calls a model: the adapter is tested with the AI SDK's mock model and with the real provider packages against a fake `fetch` that answers with each provider's documented response shape. The steps are tested through `stepsOf` of `src/testing/step-runs.ts`, which runs them on a recording journal, a content store in memory and scripted jobs, and through `providerRun` of `src/testing/provider-runs.ts`, which runs a definition through the adapter, a provider package and a fake MCP server.

Some tests wait on real time on purpose, where a slow machine only lengthens the wait: `src/steps/call-deadlines.test.ts` gives a model call 200 ms against a tool that answers in 300 ms, to show the time of the tools does not count against a call, and a call 100 ms against a provider that never answers; `src/steps/step-stops.test.ts` gives a run a bound of 150 ms.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/model` holds the interface: the request, the result, the `LanguageModel` service and the request checks. `src/failure` holds one class per failure. `src/schema` holds answer schemas: their limits and their compilation, made with the JSON Schema compiler of [`@on.auto/json-schema`](../../packages/json-schema/README.md), and `checkAnswerSchema` of `src/schema/schema-report.ts`, the report of what in a schema is unsupported, keeps its answers from being enforced, or is not checked; `src/schema/schema-portability.ts` holds the rules of the input schemas of tools alone. `src/settings` reads the settings from the environment with Effect `Config`. `src/providers` makes the providers' models and the model access, and `src/model-calls` makes one call to a model through them: with the JSON output of `src/schema/json-output.ts`, they are the only production code that runs the AI SDK, and `src/providers` is the only code that imports the cloud credential libraries: it imports `google-auth-library`, with the AI SDK's Vertex providers, only when model access is built with Vertex configured (`src/providers/vertex-providers.ts`), the AWS credential chain only with Bedrock configured, through `awsCredentialChainOf` of `@on.auto/outbound`, and one provider's identity library only for that provider without a key, through the loader it is given. No entry of the capability reaches any of them but `@on.auto/reasoning/installed-packages`, which imports that identity library for the server (`src/providers/credential-libraries.test.ts`). That optional package, which the capability does not depend on, is imported by `src/providers/installed-packages.ts` alone, the module of the entry `@on.auto/reasoning/installed-packages`, which only the server imports, to pass its `loadEntraIdentity` to `makeModelAccess`; no module the main and testing entries reach imports the package. That entry's `installedPackages` says whether the package is installed by resolving it, without loading it, so a server can read from its settings alone, with `providerStatus` and `offeredModels`, which providers are configured and which models it offers, before it builds the model access, as the server does at start. `src/listing` reads the list of models of each provider, and `src/catalog` keeps the lists, combines them with the declared models and the aliases, applies the allow list, and defines `list_models`. `src/template` is the only code that imports liquidjs: its instance of the shared engine of [`@on.auto/definitions/template`](../../packages/definitions/README.md#templates-of-a-capability), with the registration that stays this capability's own, its system block, since its filters are the engine's, and compiling and rendering a prompt over the shared parse and render, behind readonly types of its own; `rendering-corpus.json` holds what each template of the rendering tests rendered before the engine moved into the shared factory, and `rendering-corpus.test.ts` holds the engine to it. `src/definition` parses and validates a definition document with the reader of `@on.auto/definitions/document`, which splits it and reads its YAML: the keys of its front matter, the settings, the schemas and the variables a template reads, and gives the capability its `parse` and `summarize`. `src/steps` makes a run one model call at a time, as [Steps](#steps) says: the messages of a step, the calls asked for, the state and its fold, the decision, the facts, the content kept, the model and tool steps and their loop, and the resumption. `src/jobs` holds `PerformJob` and its implementation in this process. `src/tools` holds what the steps share about tools: opening a run's tools, keeping the images they answer, the room of their answers, the last step without them, the warnings of their input schemas and the endings of a run that called them. `src/capability` is the capability: its guide, the public reference page, served to agents as `reasoning-function` and ending with the sentence `onThisServer` makes of what this server offers, preparing the input, rendering the prompt, the request, the answer, the rejections and the record. `src/voice` holds voice: the reading of the voice model, the transcriber, which sends a recording through the model access's `fetch` and tries it again, the facts of a transcription, and `transcribe` and `get_voice`. `src/testing` holds the fake and what the tests share, and `src/provider-testing` the fakes of the providers: their replies and errors, the recording `fetch`, the lists of models, the SDK's mock model, and the `fetch` and the dispatch of a transcription.

## Measured

On 2026-10-23, on SQLite, Node 26.11.1 and 16 cores, `MEASURE_ONLY=reasoning pnpm --filter @on.auto/server measure` ran each kind of run against a provider and an MCP server on the loopback, before this change (`main`) and after, twice each, one after the other, while other work held the machine's one-minute load average between 26 and 65:

| Run                                             | Model calls before and after | Median wall time before | Median wall time after |
| ----------------------------------------------- | ---------------------------- | ----------------------- | ---------------------- |
| Without tools                                   | 1 and 1                      | 3.46 and 3.51 ms        | 5.64 and 5.27 ms       |
| Five tool calls, one a step, keeping content    | 6 and 6                      | 19.39 and 19.80 ms      | 36.50 and 35.85 ms     |
| Five tool calls, one a step, keeping no content | 6 and 6                      | 15.14 and 15.55 ms      | 25.21 and 25.24 ms     |
| 25 tool calls in one step, then the last step   | 2 and 2                      | 61.84 and 63.02 ms      | 68.84 and 68.20 ms     |

The model calls a run makes are unchanged, as are those of a run with one tool call (2), three in one step (2), and a last step that still calls tools (2, ending with `no_answer`). One append to a run's stream took a median of 0.78 to 0.81 ms. What a run adds is its facts and its content: a model call appends two facts, and keeps two texts where content is kept, so four appends, about 3.1 to 3.2 ms, a call. The five-call run adds 12 facts and 12 texts, 24 appends, about 19 ms, against 16.1 to 17.1 ms measured; without content, 12 appends, about 9.5 ms, against 9.7 to 10.1 ms; a run without tools 4 appends, about 3.2 ms, against 1.8 to 2.1 ms; and the 25-call run, with two model calls, 8 appends, about 6.3 ms, against 5.2 to 7.0 ms, the rest being the scrub of its 25 calls' arguments and answers, which a step reads and writes once. The time a run adds grows with its model calls and with what each step adds, not with the size of the conversation before it.

The performer compiles a JSON answer's schema once for the model calls of an attempt (`requestCompiler`) rather than at each call: on 2026-10-23, for the schema of the example in [Reasoning functions](../../docs/reference/reasoning-format.md), an attempt of 26 model calls spent a median of 0.58 and 0.67 ms compiling it at each call, and 0.012 and 0.029 ms compiling it once, over five rounds of 2,000 attempts, twice, at a load average above 120. The runs measured above answer in text, so they compile nothing.
