# @on.auto/computation

The implementation of computation functions. A computation function is a program in TypeScript with schemas for its input and output; a run calls the program's function with its input and answers with the value it returns, the same for the same input on every host of the same image, within bounds on its work, its memory, its stack, the values it answers and its time.

User documentation is [Computation function format](../../docs/reference/computation-format.md), published at [on.auto/docs](https://on.auto/docs/): the document, the types, the check at save, the sandbox, the number rules, the endings and the bounds. Update it alongside behaviour changes.

## The document

`parseComputationDocument(source)` reads a document with the shared reader of [`@on.auto/definitions/document`](../../packages/definitions/README.md#reading-function-documents) and gives a `ComputationFunctionDefinitionDocument`: an optional `description`, the `language`, `typescript`, the compiled `input.schema` and `output.schema` when the document has them, or for `output.shape` the [output shape](../../packages/definitions/README.md#output-shapes) it names with its schema compiled as `output.schema`, the `program`, the module, and the line it starts on. A language other than `typescript` is refused with the engine's `oneLanguage`, `The playbook's one language is TypeScript; write the program as a TypeScript function`, at its line. The front matter's keys are `description`, `language`, `input.schema`, `output.schema` and `output.shape`, the last two never together; every other key, `model`, `config`, `tools`, `output.format` and `input.default` among them, is an issue at its line, and the message for empty front matter names `the language`. A schema is compiled with the reader's compiler and validates values nested at most 512 levels.

Parsing keeps the module as it is written. The module is checked when the document is saved, by the capability's `check` (`src/document/document-check.ts`), which asks the pool's check worker of [`@on.auto/definitions`](../../packages/definitions/README.md#the-check-at-save), a step of the save beside `prepare`, against `Input` and `Output`, the schemas as types, with the TypeScript compiler and the sandbox's own library, each problem refused with its line in the document and the compiler's words, in the words of a document that does not parse; a check that a ready checker does not finish within 2 seconds leaves the document unsaved, `invalid_input`, and a save that finds no checker ready is `unavailable`. A run never checks again.

## A run

`makeComputationFunctionAdapter({ pool, deadlineMs, budget, memoryBytes })` makes the capability for `makeDefinitionOperations`; its `check` answers the program its save stripped of its types, which a run hands the pool in place of the document's, so a version saved without one ends in `conflict`, `unworkable`; the server gives it a `ProgramPool` of the engine, with `COMPUTATION_WORKERS` workers. `deadlineMs` is 10,000 and is the capability's `longestAnyRunMs`; `budget` is 20,000 checkpoints and `memoryBytes` 256 MiB. The server gives none of the three, so a run has the bounds of the reference; a test gives a small budget or sandbox, so that the work and memory endings are reached in milliseconds on any machine, long before a deadline, and a short deadline only to a program that spends few checkpoints. The capability reaches nothing outside and changes nothing there, calls no tools, and is stopped when its call is cancelled. A run:

1. refuses an input nested deeper than 512 levels, and one its input schema refuses, as `invalid_input`, with `checkedInput` of `@on.auto/definitions`, one sentence for each issue at its pointer;
2. asks the pool to call the module's default export with the input, in a fresh sandbox of the engine (see [the engine](../../packages/workflow-engine/README.md#the-sandbox)) of `memoryBytes`, 256 MiB, with a stack of 1 MiB, under a budget of 20,000 checkpoints, with the moment the run started as the time of `Date`, the deadline counted from the start of the run and an output of at most `mostOutputBytes`, 1 MiB less 256 bytes for the record;
3. names the checked worker, `checkedWorker` of `@on.auto/definitions`, for every run, with the output schema as the request's context, the shape's for a definition whose output names one, which the worker checks with the shape's further check too, or `null` when the definition has none, so every run of computation and recall functions is served by one worker module and the pool never lets go of a warm worker to start another module's (200 jobs at once on 4 permits took 346 ms on one module, against 6,801 ms alternating between two, at the medians of three; see [the engine](../../packages/workflow-engine/README.md#the-workers-of-the-pool-measured)); with a schema, the worker that runs the program also checks the output against the schema, under the run's deadline, and the thread that serves requests never waits on the check: a 1 MiB output against a recursive schema had taken 1,038 ms there;
4. turns the outcome into the run's ending (`src/run/run-outcome.ts`):

| Outcome of the pool                                                                      | Ending                                                                                                                        |
| ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| answered, the output schema, if any, accepting it                                        | succeeded, with the output and the record `{ language, work, duration_ms, input_bytes, output_bytes }`, `work` in checkpoints |
| mismatched: its worker found the output does not match the output schema                 | `conflict`, kind `unworkable`, with the first three issues in the words of `issuesDetail`, each part cut at 1,024 bytes       |
| raised, a stack overflow the program did not catch among them                            | `conflict`, `unworkable`: `The program raised an error on line N: <its name and message>`, cut at 1,024 bytes                 |
| exhausted by work, by the memory of its sandbox or by the stack of its worker            | `conflict`, `unworkable`, naming the bound, and for memory the checkpoints spent                                              |
| an output that is not JSON, nests deeper than 512 levels, or is over its bytes           | `conflict`, `unworkable`, with the path of the member refused                                                                 |
| exhausted by the deadline, or stopped by the deadline, its worker's heap, no free worker | `unavailable`, with words that name the bound or the number of workers                                                        |
| stopped because the call was cancelled or the server is stopping                         | `unavailable`; the operations record the cancelled run as `failed`                                                            |
| crashed, or refused by a worker although the definition was accepted                     | a defect: the call fails with an incident and the run is `failed`                                                             |

A `conflict` of the kind `unworkable` is recorded with its kind, so the run, the listing and the history show it, and a workflow sees a `runtime` error of status 409 with that kind, which a retry policy matching 503 leaves alone. The words of a run that succeeded say `Its result: ...` from the output, or that it is too long to repeat.

## Bounds

`computationBounds` holds them: a budget of 20,000 checkpoints, a deadline of 10,000 ms, a sandbox of 256 MiB, a stack of 1 MiB, a worker heap of 256 MiB, 4 workers by default and a value depth of 512; the engine's pool adds the worker's own stack of 64 MiB. Each bound has a test that reaches it and ends as [the reference](../../docs/reference/computation-format.md#bounds) says (`src/run/run-endings.test.ts`, and the server's `src/computation` for the deadline over HTTP, a busy pool and a crash). Tests that start workers have 30 seconds, and assert wall-clock time only as a lower bound.

Computation functions run in a self-hosted runtime: the server runs every run in a worker thread, terminated at the run's deadline and let go of after any run the pool had to stop.

## Measurements

`pnpm --filter @on.auto/computation measure` measures, outside the tests (`measure.ts`, with its parts in `measure/`), the checkpoints of the example by its rows and its time at the most rows its input takes, how long each of 22 constructs repeated in a loop takes to spend a run's 20,000 checkpoints, the first job of a worker and warm runs, plain and with an output schema, the JSON round trip of such a run's request, a burst of 200 runs alternating with and without an output schema, a job after its worker was idle a minute, a worker stopped at its deadline, the deepest recursion within the stack of a run, and two programs that keep allocating until their sandbox refuses. Measured on 2026-10-10 on Node 26.10.0 on an Apple M4 Max, 16 cores and 128 GiB, at a load average of about 3 to 4, once the types were stripped at save, so a worker no longer loads a compiler:

| What                                                         | Measured                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

A checkpoint counts the engine's own steps, so a loop whose body is one native operation over a large value spends few of them, and the duration is the bound that stops it: thirteen of the 22 constructs ran for 60 s without spending a run's budget, where the deadline of a run is 10 s. Each run takes a fresh sandbox, so a run costs about a millisecond more than its program, and the first job of a worker pays its start and the compiling of the WebAssembly module, which the worker keeps for every job after: 106 ms, where it was 196 ms while every worker loaded the compiler to strip types at run. Every run of computation and recall functions names the checked worker, so the pool never lets go of a warm worker to start one of another module (see [The workers of the pool](../../packages/workflow-engine/README.md#the-workers-of-the-pool)); a job of each module in turn on a full pool costs twenty times as much.

## Testing

`@on.auto/computation/testing` exports `campaignPace`, the example document, and `campaignRows(count)`, an input of that many rows over four campaigns; the tests that need an outcome a real worker gives only rarely take `scriptedPool` from `@on.auto/workflow-engine/testing`. The tests of this package run real workers, whose checks at save may take 30 s (`checkingWithin` of `@on.auto/definitions/testing`), so a check that a busy machine slows is not refused by the 2 s a save allows, and whose runs may take 30 s, `runsAwaitedAtMostMs` of `computationWith` in `src/testing/computation-runs.ts`, rather than the 10 s of `computationBounds`, which the tests of a refusal and of the summary give it themselves (`src/run/run-stops.test.ts`, `src/run/run-endings.test.ts`, `src/capability/computation-function.test.ts`); the cents of the example are checked against a computation in big integers over 1,000 rows, and `src/run/warm-isolation.test.ts` runs, in one warm worker, a program that raises, one that exhausts its work, one whose output is over its bytes, one that runs out of memory, one that overflows the stack and three that write to `Object.prototype`, to `globalThis` and `Array.prototype`, and to `Math`, then finds none of it in the next program and the example answering with the same checkpoints as on a fresh worker.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/document` holds the document: its type, the front matter's keys and parsing. `src/run` holds a run: its bounds, the input's checks, the call of the pool and the endings. `src/capability` holds the capability, whose guide is the public reference page, served to agents as `computation-function`. `src/overview` is the function's overview (see [The overview of a definition](../../packages/definitions/README.md#the-overview-of-a-definition)): what it needs and what it produces, from its schemas, and one line that the program is TypeScript and is shown under Source; `reference-example.overview.md` is the overview of the example of the public reference page, which `computation-overview.test.ts` writes again and compares byte for byte. `src/testing` holds the example and what the tests share.
