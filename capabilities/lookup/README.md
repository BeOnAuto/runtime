# @on.auto/lookup

The implementation of lookup functions. A lookup function obtains information that already exists, through one tool that only reads or from the playbook's own runs: a run makes one call of the tool its document names and answers with the part of the tool's result that `read` points at, or answers with the outputs of the runs of one definition of the playbook that succeeded, at once. It asks no model and calls no tool that may act.

User documentation is [Lookup function format](../../docs/reference/lookup-format.md), published at [on.auto/docs](https://on.auto/docs/) and served to agents as the guide `lookup-function`: the document, the mark its tool needs, the endings and the bounds. Update it alongside behaviour changes.

## The document

`parseLookupDocument(source, clock)` reads a document with the shared reader of [`@on.auto/definitions/document`](../../packages/definitions/README.md#reading-function-documents) and gives a `LookupFunctionDefinitionDocument` (`src/document`): an optional `description`, the compiled `input.schema` when the document has one, and one of two readings, by its `kind`. A `call` document holds the `call`, `{ server, tool, with?, read? }`, the line its block starts on, `callLine`, and the compiled `output.schema`, which it must have. A `runs` document holds the `runs` it reads, `{ type, name, words?, since? }`, and no output schema. The front matter's keys are `description`, `call`, `runs`, `input.schema` and `output.schema`, so `to`, `expires`, `deliver`, `model`, `input.default` and every other key is an issue at its line, and the message for empty front matter names `the tool it reads through or the runs it reads`. A document with both `call` and `runs` is refused at `runs` with `A lookup function reads through one tool or from the runs of one definition, so it takes call or runs, not both`, one with neither with `A lookup function takes call, to read through one tool, or runs, to read the outputs of the runs of a definition of this playbook`, a `call` without an output schema with `A lookup function answers with what its tool answered, so output.schema says what that is` at the line of `call`, `runs` beside an output schema at `/output/schema` with `A lookup function that reads runs answers with their outputs in a shape of its own, so it takes no output.schema`, and a body with `A lookup function sends no message and asks no model: leave the body after the front matter empty, and say what the function does in description` at its first written line.

The call block is the interaction capability's own: `CallBlockSchema` and `compiledCallBlock` of [`@on.auto/definitions/tool-blocks`](../../packages/definitions/README.md#the-tool-blocks-of-a-capability) read and check it, so the names of the server and the tool, the templates of `with` against `input`, `today` and `now`, the arguments within 256 KiB and the JSON Pointer of `read` are refused in the words an interaction function's call is.

The runs block (`src/document/runs-block.ts`) takes the `type` of a definition, one of `definitionTypeOrder` of `@on.auto/definitions`, the function types and `workflow`, and its `name`, as a definition's name is written, each refused at its line in the words `Expected the type of a definition: …` and `Expected the name of a definition: …`. `words` and `since` are Liquid templates of the shared engine of the tool blocks, `toolBlockEngine`, over `input`, `today` and `now`, checked at save with `templateIssues` of `@on.auto/definitions/tool-blocks` as `a template of runs`, and, written as they are, with no `{{` or `{%`, held to their bounds there (`src/document/runs-bounds.ts`): `words` at most 1,000 characters, and `since` a day, `YYYY-MM-DD`, read as the start of that day in UTC, or a date and time with its offset, as JSON Schema's formats `date` and `date-time` of `@on.auto/json-schema` hold them. A document may name a definition the playbook does not have: it is saved, as a workflow that names one is, and its runs answer no runs.

## The check at save

The capability's `check` (`src/marks`) passes a `runs` document, which calls no tool, and asks the tool access for the one server a `call` names, `listServers(place, server)`, and saves a tool marked `reads` and nothing else, keeping no stripped form:

| The server answers                              | The save is                                                                                                                                                                                                                                         |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the tool, marked `reads`                        | saved                                                                                                                                                                                                                                               |
| the tool, marked `acts`                         | `invalid_input` at the line of `call`: `The post message tool of chat is marked acts, and a lookup function calls only a tool marked reads: use an interaction function, or ask the server's author to mark it read-only.`                          |
| the tool, `unmarked`                            | the same, its mark said as `carries no mark, which counts as acts`                                                                                                                                                                                  |
| no such tool among those it offers the playbook | `invalid_input` at the line of `call`: `The tool server chat offers this playbook no tool named gone; search lists the tools it offers, and the mark of each.`, `the connection chat` for a connection                                              |
| no such server for the playbook                 | `invalid_input` at the line of `call`: `No connection or tool server named chat serves this playbook; search lists those that do, and the mark of each of their tools.`                                                                             |
| the server, unavailable                         | `unavailable`, naming the server in the words of the search, `The tool server chat could not be asked for its tools just now.`, and `A lookup function is saved once its tool is seen to be marked reads, so save it again once chat can be asked.` |

A tool the server lists more than once is saved only when every entry of that name is marked `reads`, and refused in the words of the first entry that is not. The refusal of a tool that acts adds who else may mark it by the kind of its server (`src/marks/mark-words.ts`): for a server whose entry names a provider, a connection's or a settings file's, `; the providers catalogue may also mark it reads, in its entry for <provider>`; for an entry of the settings file without one, `; whoever runs this server may also mark it reads, in the marks of its entry in tool_servers`; and for a connection without a provider, nothing more.

## A run

`makeLookupFunctionAdapter({ tools, runs, mostPagesRead? })` makes the capability for `makeDefinitionOperations`, `tools` the tool access whose `callOnce` and `listServers` it uses, `runs` the ledger's `readRecorded` it reads the playbook's runs through and the `content` it reads the outputs a playbook keeps outside its runs from, and `mostPagesRead` the bound of a read of runs, 10 unless a test gives fewer (`src/capability`). A run of a `call` document is `callRunOf` of `@on.auto/definitions/tool-blocks` with the noun `lookup function` and `requiredMark: 'reads'`: it checks the input against its schema, renders the arguments over `input`, `today` and `now`, and makes one `callOnce`, which reads the mark of the tool as its server lists it for this call and refuses one no longer marked `reads`, or listed more than once with an entry not marked `reads`, as `unopened`, `tool_not_read_only`, before anything is recorded or sent, so the run ends `unavailable` with that kind and its history holds no call. The call is recorded on the run as `tool_call_started`, which says `read_only: true`, and `tool_call_answered` or `tool_call_failed`. What it answered at `read`, checked against `output.schema` at the run and within what a run may record, is the output, `{ server, tool, read }` the record. Since every call is of a tool marked `reads`, a call that was sent and could not finish ends `unavailable`, kind `tools_unfinished`, with `because` `tool_error` or `server_failed`, which a retry may make; an answer it cannot use, or arguments the tool refused, end `conflict`, kind `unworkable`. A run under the id of one that called its tool and did not succeed is `tools_called`, because `only_read`.

A run of a `runs` document (`src/runs`) checks its input, renders `words` and `since` over `input`, `today` and `now`, a rendered value past its bound ending the run `conflict`, `unworkable`, at its pointer, one that is not text likewise, and one that reads what the input does not have `invalid_input`, and then reads the runs of the definition through `succeededRunsPageOf` of `@on.auto/definitions`, a page at a time, newest started first:

- the first page is read after the cursor of the run's own start, the first record of its stream, `runStartCursorIn` of `@on.auto/definitions`, so a run whose first record the ledger recorded after it is never read, whatever time its start was stamped with, in the same millisecond or by another clock;
- each page asks the ledger for the runs since `since`, so the ledger examines no run recorded before it, and the read ends, with `more: false`, when the pages end or at the first run that started before `since`, which the read checks itself since the ledger's bound is of the time it recorded a run;
- an output the playbook keeps outside its run, by its digest, is read before the page is walked, six at once, under one bound for the read, `mostOutputsReadInARun`, 100 outputs, and `mostOutputBytesReadInARun`, 8 MiB; a run whose output is past the bound ends the read with `more: true`, as one past the page bound does. An output the store does not answer for just now is an outage, not a bound: the read issues no more reads and the run is `unavailable`, to be asked again, and so is a run whose reads of kept outputs take past `mostScanMs`, 15 s in all, well inside the 70 s a lookup run may take; only those reads are timed, so the reads of the ledger's pages take as long as they did before outputs were kept; an output missing from the playbook's content or erased holds no word, and is answered by its size where no word is asked;
- a run whose output, as JSON, does not hold every word, as `wordsIn` and `holdsEveryWord` of `src/runs/word-matching.ts` fold them, NFKC and full case folding, is counted and passed over;
- the output of every other run is answered, `{ run_id, definition_version, started_at, finished_at, output }`, while the answer and the record fit the 1,048,576 bytes a run may record together, `mostResultBytes`; the first that does not fit is answered by its size, `{ run_id, definition_version, started_at, finished_at, bytes }`, where that fits, and the read ends with `more: true`;
- the read ends with `more: true` after `mostPagesReadInARun`, 10 pages, so a run examines at most 10,000 runs of the playbook, `mostExaminedInAPage` of `@on.auto/operations` a page, answers at most 1,000 of the definition's, `mostRecordsInAPage` a page, and loads at most 40 MiB, `mostBytesLoadedInAPage` a page. A page of the runs of one type and name measured 1.98 ms at the median on SQLite and 4.12 ms on PostgreSQL ([the measurement of the run filters](../../packages/ledger/README.md#measurement-of-the-run-filters)), so ten take about 20 ms and 41 ms, within the 50 ms the ledger set itself for a read without a read model; ten that each load the most a page loads, measured at 34.0 ms and 22.9 ms each, would take about 340 ms and 230 ms, still far within the 70 seconds a lookup function's run may take.

The run answers `{ runs, more }`, whose JSON Schema, `runsAnswerSchema` of `src/runs/runs-answer.ts`, is the definition's `output_schema`, and records `{ examined, through }`: `examined`, how many runs of the definition that succeeded it walked, answered or not; `through`, how far it went, the time the ledger recorded the start of the oldest run of the playbook a page looked at, of any definition, `lastExamined` of the page, or, where the read stopped inside a page, the start of the run it stopped at, and `null` where it reached none. Its summary's `details` name the definition it reads as `reads: [{ type, name }]`, which `used_by` of that definition reads. The read recomputes the answer's size as each run is examined, so its answer and its record always fit. `describeOutput` says `It examined 3 runs that succeeded and answered with 2.`, and `; older runs are left unread` where `more` is set.

The capability reaches outside, `reachesOutside`, and changes nothing there, `mayChangeOutside` false; its definitions of a `call` call tools, those of `runs` none, and all finish within their call, and run at most `longestCallRunMs`, 70 seconds, its `longestAnyRunMs`. A run cancelled while its call is in flight goes on to its end, `whenCancelled: 'finish'`, as an interaction function's call does. It declares no facts of its own: the tool call facts are the run's. `describeOutput` says what the tool answered, `It asked the thread tool of chat; its answer: …`, in the words of `callOutputInWords`.

## Testing

`@on.auto/lookup/testing` holds documents of a lookup over the thread tool of the fake MCP server's data tools (`lookupDocument`, with `threadInput` and `repliesOutput`), the document that reads the runs of a computation function, the example of the reference page (`runsDocument`, with `campaignInput`), `runsHarness`, which saves and runs definitions through the definition operations over a ledger held in the test's process, beside a computation function that answers its input, or refuses `refusingInput`, and runs and checks of them against the fake MCP server of `@on.auto/tool-servers/served-fakes`, served through the tool access of `@on.auto/tool-servers/testing` (`lookupRuns`: `saved` prepares a document and runs its check, `run` prepares it and runs it on the standing clock). `annotateTool` of the fake server changes the mark a tool is listed with, so a test saves a function and then marks its tool `acts`. The check's refusals by the kind of server are tested over servers given as they are listed (`src/marks/mark-check.test.ts`).

## Source

`src/document` reads the definition and holds the bounds of a read of runs, `src/marks` checks the mark of its tool when it is saved and words the refusals, `src/runs` reads the playbook's runs, fits them to the answer and words it, and matches words, `src/capability` is the capability, its guide, the public reference page served to agents as `lookup-function`, and its words, and `src/testing` what the tests share.
