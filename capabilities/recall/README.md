# @on.auto/recall

The implementation of recall functions. A recall function keeps a view of its playbook's own history: its module, in TypeScript, exports a function `fold` that folds each event its filters name into the view, the host keeps the view as the playbook records events, and a run answers from the view as it stands, applying the module's function `answer`, when it exports one, to it with the run's input.

A recall function answers from what the playbook keeps of its own history, as [Playbook terminology](../../docs/concepts/terminology.md) says. Documents, files and other connected sources are not implemented, and neither is semantic search over text.

User documentation is [Recall function format](../../docs/reference/recall-format.md), published at [on.auto/docs](https://on.auto/docs/): the document, the events, the module's contract, how the view is kept, the endings and the bounds. Update it alongside behaviour changes; `src/document/reference-example.test.ts` checks that its example is the document the tests run, folds to the view it shows and answers the output it shows, and runs its example of the common case, the outputs of one function's runs in a list, within the bound on a view.

## The document

`parseRecallDocument(source)` reads a document with the shared reader of [`@on.auto/definitions/document`](../../packages/definitions/README.md#reading-function-documents) and gives a `RecallFunctionDefinitionDocument`: an optional `description`, an optional `about`, which `AboutSchema` of `@on.auto/definitions/document` bounds and the summary carries into the overview, the `language`, `typescript`, the compiled `input.schema` and `output.schema` when the document has them, `answers`, whether the module exports a function `answer`, `filterExpressions`, the `data` expression of each filter that has one with its pointer and its line, for the check, and the `details` the host folds the view by: the module and the line it starts on, the filters, `initial` and the view's schema. The front matter's keys are `description`, `about`, `language`, `source.events`, `view.initial`, `view.schema`, `input.schema` and `output.schema`; every other key, `model`, `config`, `tools`, `output.format`, `input.default` and `answer` among them, is an issue at its line, and the message for empty front matter names `the language and the events it folds`. A language other than `typescript` is refused with the engine's `oneLanguage`.

The module and the filters' expressions are checked when the document is saved, as one job, by the capability's `check` (`src/document/document-check.ts`), which asks the pool's check worker of [`@on.auto/definitions`](../../packages/definitions/README.md#the-check-at-save), against `View`, `Input`, `Output` and `Event`, each problem refused with its line in the document, a filter's under its pointer; a check that a ready checker does not finish within 2 seconds leaves the document unsaved, `invalid_input`, and a save that finds no checker ready is `unavailable`: parsing keeps the module as it is written, and a document is recognised as answering when its module declares `export function answer` at the start of a line, the one form the check lets an export take. A filter (`src/document/source-filters.ts`) is read with the engine's `literalFilterOf`, so its `type`, `source` and `subject` are written out and it tests no other attribute; its `data` expression names nothing but `$data`, which the check holds it to. `initial` must fit the bound on a view, 524,288 bytes as JSON, and match the view's schema; the shared reader already bounds the front matter's nesting at 72 levels.

`summarize` answers the description, the about, the schemas and the `details`, which the registry keeps with the definition record and never answers, so the host can fold a view without this package's parser.

`recallOverview` (`src/overview`) is the function's overview (see [The overview of a definition](../../packages/definitions/README.md#the-overview-of-a-definition)): what it remembers, each filter as a sentence after `each time`, in the words `eventFilterPhrases` of `@on.auto/definitions` gives every event filter: its event type, `run_started`, `run_succeeded`, `run_failed`, `run_rejected`, `definition_created`, `definition_updated`, `definition_retired` or any other type as an event published to the playbook, and the definition its `subject` or, for a definition's event, its `source` names, every run or definition when it names none, then each other attribute it names in words; what it keeps, the view's schema in words and `initial` unless it is empty, as JSON within `mostInitialViewCharacters`, 300 characters counted as code points by `charactersIn` of `@on.auto/definitions`, and past them named as shown under Source; what it answers, its input and its output, or the view itself for a module without `answer`; and how the view is kept, a diagram from each filter, labelled with its words in plain text by `plainTextOf` of `@on.auto/definitions`, to the view, drawn as a cylinder, and from the view to the answer, the sentence that the view is built from the playbook's history and kept up to date, and one line that the program is TypeScript and is shown under Source. `reference-example.overview.md` and `reference-common-case.overview.md` are the overviews of the two examples of the public reference page, which `recall-overview.test.ts` writes again and compares byte for byte.

## A run

`makeRecallFunctionAdapter({ pool, views, mostFunctions, deadlineMs, budget, memoryBytes })` makes the capability; its `check` answers the module and the filters' expressions its save stripped of their types, which the answer runs and the host's projector folds in place of the document's, so an answering version saved without a module ends in `conflict`, `unworkable`; the server gives it the computation pool and the host's `ViewsPort`. Its `mostActive` is `mostFunctions`, 32 unless the server's `RECALL_MAX_FUNCTIONS` says otherwise, counted by the registry at each save. `deadlineMs` is 10,000 and is the capability's `longestAnyRunMs`; `budget` is the answer's 500 checkpoints and `memoryBytes` its 256 MiB sandbox. The server gives none of the three; a test gives a small budget or sandbox, so that the answer's work and memory endings are reached in milliseconds on any machine, long before a deadline. The capability reaches nothing outside and changes nothing there. A run (`src/run/recall-run.ts`):

1. refuses an input nested deeper than 512 levels, and one its input schema refuses, as `invalid_input`, with `checkedInput` of `@on.auto/definitions`, one sentence for each issue at its pointer;
2. reads the view through the views port and, while the view of the version saved is missing, of an older version, waiting or being built, answers `unavailable` with the kind `rebuilding`, the count folded and the lag in words; while it is stalled, `conflict` with the kind `stalled`, in fixed words with the type and time of the event and the line of the fold, never the fold's own message, the event's values or its id (`src/run/view-words.ts`);
3. without an `answer`, answers the view itself, checked against the output schema on the serving thread, since the view is at most 512 KiB; with one, asks the pool to call the module's `answer` with the view and the input, in a fresh sandbox of 256 MiB with a stack of 1 MiB, under 500 checkpoints, the moment the run started as the time of `Date`, with an output of at most `mostOutputBytes`, 1 MiB less 2,048 bytes for the record, and the checked worker of `@on.auto/definitions` for every answer, with the output schema as its context, or `null` without one, so the worker that calls `answer` also checks its output there;
4. turns the outcome into the run's ending as a computation function's run does (`src/run/answer-endings.ts`), and records `{ language, work, duration_ms, input_bytes, output_bytes, view: { version, checkpoint, checkpoint_at, folded, last_event } }`, so a caller who does not see an event can tell how far the view had read.

A run never waits for the projector. `get_definition` of a recall function adds its `standing` (`src/capability/recall-standing.ts`): the view's state, version, checkpoint, count folded, last event, lag and the time of the playbook's newest record, and for a stalled view the event's id, type and time, the kind of stall, the fold's raw error and its line; a retired function has none.

The host's projector folds pages of events in the pool with `recallFolding`, whose worker is that checked worker too, so each view is checked against its schema where it was folded, and a view or an answer it refuses is worded with `issuesDetail` of `@on.auto/json-schema`, the one wording of the issues a computation output gets.

## Bounds

`recallBounds` holds them: 8 filters, 500 checkpoints of work for a fold and for an answer, a sandbox of 64 MiB for each view of a page and of 256 MiB for an answer, a stack of 1 MiB, a fold deadline and a run deadline of 10,000 ms, a worker heap of 256 MiB, a view of 524,288 bytes, a value depth of 512, twenty overtimes before a fold that runs past its deadline stalls, a page budget of 2,000 ms, ten pages a playbook a pass, and the defaults of the settings, 32 functions a playbook, four rebuilds a playbook and four playbooks at once. Each bound has a test that reaches it: here; in [`@on.auto/workflow-host`](../../packages/workflow-host/README.md#testing) for the projector's, the pages of a pass, the playbooks at once, the half of the pool the projector holds, the tries before a stall and the page budget, each with a smaller value of its setting so that the test fails when the bound is removed; and in the server's `src/recall` over HTTP and MCP.

Recall functions run in a self-hosted runtime: a run answers in a worker of the pool computation functions use, and the server that runs the workflows folds each page of a view in one, using at most half of the workers at once and at least one.

## Measurements

`pnpm --filter @on.auto/recall measure` measures, outside the tests (`measure.ts`, with its parts in `measure/`), the example's fold over 100,000 runs of 100 campaigns in pages of up to 1,000, the way the host's projector folds them, in one warm worker of the pool, the view checked after every fold, and whether 3,000 of them fold to the same view with the same checkpoints in pages of 7 and of 1,000. Measured on 2026-10-10 on Node 26.10.0 on an Apple M4 Max, 16 cores, at a load average of about 3 to 4, on the final build, its fold stripped of its types at save:

| What                                                                      | Measured                                                                     |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 100,000 folds in 100 pages of 1,000, the view written out after each fold | 42.7 s, 2,343 folds a second, about 0.43 ms a fold, to a view of 6,034 bytes |
| the checkpoints of those folds                                            | 0 in all: each fold makes fewer than 10,000 of the engine's polls            |
| 3,000 of them in pages of 7 and in pages of 1,000                         | the same view and the same checkpoints                                       |

A fold writes its view out after it, through the refusing replacer, over the whole view each time, and the next fold is handed that text parsed again: measured by hand the same day over a view of 6,024 bytes shaped like this example's, 1,000 writes took 113 ms, where `JSON.stringify` alone took 45 ms and the replacer before it was made lean 231 ms, and the 1,000 parses 40 ms. The same 100,000 folds took 48.5 s before those changes, and 41.7 s with them while the engine still stripped types at run. Checking the view against its schema added about 50 ms a page. A page of 1,000 of the example's folds took about 0.4 s against its budget of 2 s, so a page never ended early here.

## Testing

`@on.auto/recall/testing` exports `campaignReviews`, the example document, `recallDocument(module, frontMatter)`, a document of a module over every successful run, and `reviewBrief`, a reasoning function whose runs the example folds; `foldOf(body, answerBody)` writes such a module for the package's own tests. The tests of this package run real workers through a fake views port (`src/testing/kept-views.ts`), their checks at save allowed 30 s by `checkingWithin` of `@on.auto/definitions/testing`, so a check that a busy machine slows is not refused by the 2 s a save allows, and the engine's `scriptedPool` for the outcomes a real worker gives only rarely.

The tests that fold a page of the views of the example in a real worker, `src/document/reference-example.test.ts` and `src/run/view-folding.test.ts`, give it `patientPage` of `src/testing/recall-runs.ts`, a page budget, a wait for a worker and a deadline of 30 s each, `checksAwaitedAtMostMs` of `@on.auto/definitions/testing`, so a page that a busy machine slows is not stopped by the 2 s of `recallBounds`, a wait of 5 s or a deadline of 20 s; the stops at those bounds are held by the fold pool's own tests in `@on.auto/workflow-engine`.

## Source

`src/index.ts` is the entry point and `src/testing/index.ts` the entry point of the test support. `src/document` holds the document: its type, the front matter's keys, the filters and parsing. `src/run` holds a run and the folding settings: the bounds, the input's checks, the answer, its endings and the words of a view not ready. `src/capability` holds the capability, its parsing and summary, its standing, and its guide, the public reference page, served to agents as `recall-function`. `src/overview` holds the overview and the words of the filters. `src/testing` holds the example and what the tests share.
