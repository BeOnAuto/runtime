# @on.auto/generation

Generation functions: a playbook produces an asset, an image or audio, from a prompt. A generation function is a definition of the type `generation`, saved and versioned as every function is. Its run renders the prompt from its input, asks a model of the catalogue through a model gateway once, keeps the bytes the model made as content of the playbook, records the asset on a stream of its own, and answers a reference to it with an address its bytes are read at for fifteen minutes, which `get_asset` signs anew each time it reads the asset ([Reading an asset](#reading-an-asset)). An image or audio is made within the run's call. A generation the provider finishes later waits instead: the gateway answers a handle, the run waits, and the runtime asks the gateway how the generation stands until it is made or the run has waited as long as it may. A video is such a generation, and the catalogue the runtime ships names no model that makes one. The asset is kept until it expires, and its content is removed then, once nothing else of the playbook holds the same bytes. [Generation function format](../../docs/reference/generation-format.md) sets out the document for the people who write one.

## The document

```markdown
---
description: A picture of the product for its listing
produces: image
model: gateway/openai/gpt-image-2
input:
  schema: { type: object, required: [product], properties: { product: { type: string }, photo: { type: string } } }
parameters: { size: 1024x1024, quality: high }
references: [/photo]
expires: P30D
---

A studio photograph of {{ input.product }} on a white table.
```

`parseGenerationDocument(source)` (`src/document/document-parsing.ts`) reads it with the shared document reader of `@on.auto/definitions/document`: `produces`, one of `image`, `audio` and `video`; `model`, written `gateway/model`, the gateway's name of `MODEL_GATEWAYS` before the first `/`; `input.schema`, compiled as every input schema is; `parameters`, `size`, `aspect` and `quality` for an image, `voice`, `format` and `duration` for audio, and `size`, `aspect` and `duration` for a video, a parameter of another kind refused at its pointer; `references`, at most 16 JSON Pointers into the input, none twice; `expires`, an ISO 8601 duration from one hour to 3,650 days read by `readDuration` of `@on.auto/workflow-engine/dsl`; and the body, the prompt, a template of `@on.auto/definitions/template` that reads `input`, `today` and `now`. A parse knows nothing of the catalogue, so a saved definition stays readable whatever a later release's catalogue holds.

The check at save, `checkedAgainst(catalog)` of `src/capability/definition-reading.ts`, over `modelChoiceOf` of `src/document/model-check.ts`, refuses each of these at its line: a model the catalogue does not name, with the models of the kind it names; a retired model, naming `gateway/<replacement>`; a model of another kind than `produces`; a parameter outside the model's limits, naming the values it takes; and more references than the model takes. A gateway the runtime is not given is the run's refusal, not the save's.

## The catalogue

`src/catalog/*.yaml` holds one entry for each model, named for it with each `/` a `-`: its `model`, as the gateway names it, its `kind`, the media types of the assets it takes as references, `media_types`, its `limits`, and `retired: { on, replacement }` where the provider retired it (`src/catalog/catalog-entry.ts`). The limits of an image are its `sizes`, `aspects` and `qualities`, the most characters of its prompt, `prompt_characters`, and its `references: { most, bytes }` where it takes any; of audio its `voices`, `formats` and `seconds: { least, most }` where it takes a duration; of a video its `sizes`, its `seconds`, which every video model names, since each video the gateway is asked for names its seconds, and its `references`. A video model names no aspects: the gateway's videos take a `size`, which a provider that takes an aspect has it from, so `aspect` is refused at save for every video. `readGenerationCatalog(shippedFiles)` (`src/catalog/catalog-reading.ts`) reads the folder through the shipped files of `@on.auto/shipped-files`, the root `generationShippedRoots()` gives, as the server starts, refusing an entry that does not decode, whose file is not named for it, a model named twice, `seconds` whose least is past its most, an audio format the runtime keeps no media type for (`src/catalog/media-types.ts`), references without media types or media types without references, and a replacement that is no other model of the same kind or is retired too (`catalogOf` of `src/catalog/generation-catalog.ts`). It answers the entries ordered by model.

The entries name what the gateway the reasoning functions use serves by the listing code of `@on.auto/reasoning`, which leaves these families out of its list of models for conversation: `openai/gpt-image-1-mini` and `openai/gpt-image-2`, and `openai/tts-1`, `openai/tts-1-hd` and `openai/gpt-4o-mini-tts`. Their limits are the provider's published ones where known and narrower where not, such as the six original voices of `openai/tts-1`. The catalogue is seeded with these five entries, none of which produces video, so a function that produces video is refused as it is saved, the catalogue naming no model of that kind; a model is added by a file of its own in `src/catalog`, named for its model, with its `kind`, its `media_types` and its `limits`, and by its name in the list `src/catalog/shipped-catalog.test.ts` holds the folder to, and the server reads it as it starts.

## The gateway

A run reaches a gateway of `MODEL_GATEWAYS`, the settings reasoning reads, given as `GenerationGateway` (`src/gateway/generation-gateway.ts`): its `base_url`, its key, sent as `Authorization: Bearer`, its headers and query parameters, and its `cost_header`. `gatewayRequestOf` (`src/gateway/gateway-requests.ts`) posts JSON to `/images/generations` for an image, `{ model, prompt, n: 1, size, quality, aspect_ratio }`, or multipart to `/images/edits` for an image with references, each reference a file of `image[]`, and JSON to `/audio/speech` for audio, `{ model, input, voice, response_format, duration }`, the voice and the format the first of the model's where the document names none, and JSON to `/videos` for a video, `{ model, prompt, seconds, size }`, `seconds` the document's `duration` as text, or the least the model makes where it names none, so whoever meters the call knows the seconds before it is sent, or multipart with each reference a file of `input_reference`: the OpenAI-compatible paths, since no gateway the runtime is tested against says otherwise, and for a video the unified video API of LiteLLM, which answers every provider's video in one shape (`litellm/videos/main.py` and `litellm/proxy/video_endpoints/endpoints.py` of release 1.101.0, the gateway's). A request follows no redirect (`redirect: 'manual'`, which every platform the runtime runs on takes), so the gateway's key goes nowhere else. `generatedBy` (`src/gateway/gateway-call.ts`) waits 240 seconds at most and reads an image from `data[0].b64_json`, its media type from its bytes, a WebP by both its `RIFF` header and its `WEBP` mark (`src/catalog/media-types.ts`), and audio as it comes, its media type the one the gateway answers, or that of its format where it answers none, and an answer of a type that is no audio refused as `unavailable` naming the type, each within the most the runtime keeps of one asset of its kind, and the cost from the header `cost_header` names, as `costOf` of `@on.auto/reasoning` reads it. A refusal whose error names `moderation_blocked`, `content_policy_violation` or `content_filter` as its code or type, or whose message says the request met a content policy or a safety system, is a `conflict` of the kind `blocked_by_moderation`; a refusal for the gateway's own budget or quota, `402` or an error that names `budget_exceeded`, `insufficient_quota`, `billing_hard_limit_reached` or `quota_exceeded`, or a message that says so, is `unavailable` in those words, whatever its status; `401` and `403` are the gateway's key, `429` its rate, `408`, `409`, `425` and `5xx` its failure, and a `3xx` a redirect it does not follow, each `unavailable`; another `4xx` is a `conflict` of the kind `unworkable`, naming the error code where it is plain. A video is asked for in three calls (`src/gateway/video-call.ts`): its creation, `videoAskedOf`, whose answer is read for its `id`, the handle, at most 1,024 characters, its `status` and the cost the header names, and refused as an image is, or as `unavailable` where it holds no id or says the video failed at once; how it stands, `videoStandingOf`, a `GET` of `/videos/<id>`, the id one segment of the path, within 30 seconds, whose `status` is `completed`, `failed` or anything else, a video still being made, such as `queued`, `in_progress` or `processing`, with its `progress` from 0 to 100 where the gateway says one; and its bytes, `videoFetchedOf`, a `GET` of `/videos/<id>/content`, within 240 seconds and the most the runtime keeps of one video, its media type the gateway's, which must be a video, or `video/mp4` where it names none. A status or the bytes the gateway cannot answer, unreachable, `408`, `409`, `425`, `429` or `5xx`, or a status it garbles, are asked for again later; a `404` is a video the gateway no longer knows, `unavailable`; another refusal is read as a creation's is. A video that failed is `unavailable`, naming its error code where it is plain, or a `conflict` of the kind `blocked_by_moderation` where its error says so.

## A run

`generationRun(ports)` (`src/run/generation-run.ts`) finds the model in the catalogue again and its gateway among those it is given (`src/run/runnable-model.ts`); checks the input (`src/run/prepared-input.ts`); renders the prompt and checks it against the model's characters, counted as code points (`src/run/rendered-prompt.ts`); reads each reference from the input, finds its asset in the projection `assets` of the playbook and refuses one of no asset of this playbook, expired, of a media type or a size the model does not take, or whose content is gone, at its pointer, before anything is asked (`src/run/referenced-assets.ts`); refuses as `oversized` where the playbook keeps all it may already (`src/run/asset-room.ts`); asks the gateway; and keeps the asset (`src/run/finished-run.ts`), or, for a generation the provider finishes later, defers with the handle the gateway answered (`src/run/asked-to-wait.ts`; see [A generation the provider finishes later](#a-generation-the-provider-finishes-later)). A run refused before the gateway answers keeps nothing and records no cost; one the gateway answered and the runtime then refuses, for an asset larger than it keeps of its kind, an answer that holds no image or one that is no audio, keeps nothing and records, on the refusal, `model`, `own_key` and the `cost_usd` the gateway answered, since the call was spent. A run asked again asks the gateway again, so the capability declares `reachesOutside`, and `mayChangeOutside` once it is given a gateway, so that `run_definition` is destructive on a server that can ask one. A run cancelled while it asks goes on to its end, `whenCancelled: 'finish'`, as every capability whose runs finish later does, so a generation the gateway was asked for is always recorded with its handle; an image or audio whose client went away is kept and its run succeeds. A run that waits and is cancelled ends `cancelled` with the cost its request spent on its record (`cancelledWaiting` of `src/waiting/waiting-ends.ts`), its row of the generations waited for closed, so the gateway is asked nothing more of it, nor told to stop.

The run's record holds `model`, `own_key`, which the composer sets, `duration_ms` and, where the gateway answered one, `cost_usd`. Its output is the shape `asset` of `@on.auto/definitions`: `id`, `media_type`, `bytes`, `sha256`, and `address` and `address_until`, signed by `signedContentAddress` of `@on.auto/identity` for fifteen minutes on the origin the composer gives, or `null` where it gives no signer or the origin is neither HTTPS nor a loopback address (`src/assets/asset-reference.ts`). The address names the asset's bytes by the playbook and their digest, `<origin>/v1/orgs/{org}/playbooks/{playbook}/content/{sha256}?until=&sig=`, the content route of the runtime's API (`contentAddressRoutes` of `@on.auto/api`), which answers them with no credential, its signature being its credential, from whatever store keeps the playbook's content, the ledger's own or an object store, so an asset has one address whichever store keeps its bytes, and the route reads it under the key the signer signed it with.

## The asset

`keptAsset` (`src/assets/asset-keeping.ts`) puts the bytes through `RecordedContent.put` of the playbook, then reads the time, which is the asset's `kept_at` and the start of its `expires_at`, so an asset never expires within the hour its own put keeps its content fresh, and appends `asset_kept` to the stream `assets/<id>` of the playbook, a UUIDv7, or for a generation that finished later the UUIDv5 of the deferral its run recorded, through `assetDecider` (`src/assets/asset-decider.ts`), which takes `asset_kept` once, `asset_expired` once after it and `asset_content_removed` once after that. The facts (`src/assets/asset-facts.ts`):

| Fact                    | Data                                                                                                                                                 | Context                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `asset_kept`            | `media_type`, `bytes`, `sha256`, `kind`, `model`, `prompt`, `parameters`, `references` (each `{ id, sha256 }`), `cost_usd?`, `own_key`, `expires_at` | the run's: caller, run and definition |
| `asset_expired`         | `bytes`                                                                                                                                              | `by: runtime`                         |
| `asset_content_removed` | `bytes`, `sha256`                                                                                                                                    | `by: runtime`                         |

The stream kind `assets` is the capability's own, declared in `generationFacts` with its presenter (`src/assets/asset-presenter.ts`), so the playbook's feed shows the three facts and the ledger reads them; their fixtures are under `src/assets/0.56.0/` and in `recorded-facts.json`. `asset_kept` holds its digest, `/sha256`, and `asset_expired` releases every hold of the stream, in the content annotation of their schemas, so the ledger counts the asset among the holders of its bytes from the one fact to the other.

Two projections fold the stream (`src/assets/asset-projections.ts`): `assets_1`, one row an asset, keyed by its id, with `media_type`, `bytes`, `sha256`, `kind`, `model`, `run`, `kept_at`, `expires_at`, null once the asset expired, `expired_at` and `live`, indexed across playbooks on `expires_at` where it is set, `expiring`; and `asset_totals_1`, one row a playbook, keyed `playbook`, with the `bytes` and the count of `assets` it keeps. Their tables are part of the layout of the ledger, and `generationLayoutSteps` (`src/assets/asset-layout.ts`) holds step 11, the one after the memories' step 10, and step 13, which brings the projection of the generations a playbook waits for, each with no statement, since the ledger makes and fills a projection's table it does not find as it opens.

## Reading an asset

`defineGetAsset({ addresses })` (`src/operations/get-asset.ts`) is the playbook's query `get_asset`, `GET /assets/{id}` and the MCP tool of the same name, under `playbook:read` and read-only, which reads an asset again after the address in its run's output has expired. It takes the signer the run takes, `addresses` of `GenerationPorts`, so an asset read and an asset made are addressed alike, and reads through the `PlaybookReader` the dispatcher binds to the call's playbook (`src/operations/asset-read.ts`): the asset's stream, folded by `assetDecider`, for whether its content was removed, then its row of `assets_1`, in that order, so a removal the stream shows is an expiry the row shows too. An id that is no UUID is `invalid_input` at `/id`, and one no row of the playbook holds, an asset of another playbook among them, `not_found`, `There is no such asset in this playbook`. It answers `{ id, media_type, bytes, sha256, model, kept_at, expires_at, expired_at, expired, content_removed, address, address_until }`, each moment ISO 8601 UTC, `expires_at` null once the expiry is recorded and `expired_at` null until then, `expired` true from the moment the asset expires, whether or not its expiry is recorded yet, as the reference checks of a run refuse it from then on (`hasExpired` of `src/assets/asset-projections.ts`), and the address signed by `addressOf`, as the run signs it, for fifteen minutes from the read, or null once the asset has expired and where the composer gives no signer or an origin the runtime signs nothing on. The words of its outcome say the asset has expired by `expired`, so an asset past its time whose expiry is not recorded yet is said to have expired rather than to have no address. The capability is outside the directory listing, and so is the operation: the server leaves it out of the catalog `/directory` lists.

## A generation the provider finishes later

A function that produces video is a generation the provider finishes later, `finishesLater` of `src/capability/run-declarations.ts`: its run asks the gateway to make it and defers, and its record, the deferral the ledger keeps as a fact of the run, `run_deferred`, is what the runtime waits on (`GenerationDeferredSchema` of `src/waiting/generation-wait.ts`, its fixture under `src/waiting/0.56.0/`): what made the asset, `kind`, `model`, `prompt`, `parameters`, `references`, `cost_usd` where the gateway answered one and `own_key`, as `asset_kept` will hold them; `handle`, the gateway's id of what it makes; `kept_for_ms`, how long the asset is kept once it is made; `asked_at`, when the run asked; and `waits_until`, the deferral and `waitMs` after it. The run stands `started`, as a run that waits on a request does, and a workflow's step that calls it waits for it as for any run that finishes later. No code reads the model its record names: how a generation stands is the gateway's answer alone, in the words LiteLLM gives every provider it serves.

`generationsWaiting` (`src/waiting/waiting-rows.ts`), table `generations_due_1`, is a keyed projection of runs, one row a run whose deferral is a generation's, keyed by the run's id: `deferred_id`, the deferral's message id, which the asset's id and the lineage of what follows are made of, `handle`, `gateway`, the name before the first `/` of the model, `deferred_at`, `waits_until`, `open`, and the cadence its reader advances through the ledger's `advanceRow`, a compare-and-set on `deferred_id` and `open`, so a ring of a run that ended or was deferred again changes nothing: `polls`, `progress`, `next_poll_at`, `poll_due_at`, due across playbooks in the lane that calls out, and `ending_due_at`, due in the lane that calls nothing outside. The deferral makes the row with its first poll five seconds after it and its ending at `waits_until`; the run's ending, whatever it is, closes it, so a settled run is due for nothing.

`generationsDue(parts)` (`src/waiting/generations-due.ts`) is the due work of those rows. A poll first advances its row a minute ahead, the poll in flight, and holds the ending until then, so a second ring finds nothing due and the deadline does not end a run while its poll is answered; it reads the run, and asks nothing of a run that no longer waits; it asks the gateway how the generation stands. A generation still being made is polled again after `waitAfterPoll` (`src/waiting/poll-cadence.ts`): 10, 20 and then 30 seconds while the gateway says nothing of its progress, and half the time its progress says is left, from five seconds to a minute, never past `waits_until`; a gateway that could not answer is polled again on the same cadence. A generation that failed, or that the gateway no longer knows, ends the run as the gateway answered, with `model`, `own_key` and `cost_usd` on its record, since the call was spent. A generation made is fetched, its row advanced past the time a fetch may take and the ending held as long; the run is read once more, and nothing is fetched or kept for a run that ended meanwhile; an asset already kept under the id the deferral gives, by a ring that stopped before it settled the run, settles the run without its bytes being asked for again; otherwise the bytes are kept as `asset_kept`, through the same `finishedAsset` of `src/run/finished-run.ts` a run that makes an image takes, under the UUIDv5 of the deferral, so two rings that fetch at once keep one asset, the second meeting the first's `asset_kept` and settling from it. The run is settled through `runSettler` of `@on.auto/definitions`, `succeeded` with the asset's reference and the record a run that makes an image has, its `duration_ms` from `asked_at`; a settlement another made first is left as it is. A poll at or past `waits_until` asks nothing and leaves the run to the deadline: the ending, due at `ending_due_at`, settles a run that still waits as `unavailable` of the kind `generation_timed_out`, saying how long it waited, with the cost it spent on its record. A gateway the runtime is no longer given ends the run as a run that names one would be refused, `model_not_offered`.

LiteLLM's video API is one shape for every provider it serves, but its providers differ beneath it in three ways that reach a run, read in its source at the gateway's release: a video on Vertex AI or the Gemini API stands `processing` rather than `queued` or `in_progress`, which the runtime reads as a video still being made, and says no progress, so it is polled on the cadence for a provider that says none; a video on the Gemini API that failed stands `completed`, and the gateway then refuses its bytes, so its run ends in the words of that refusal, or `generation_timed_out` where the refusal is a `5xx`, rather than in the provider's words; and an error of Vertex AI carries a numeric code, which the words of its failure leave out, and its words of a refusal for safety are not the words the runtime reads as moderation, so such a video ends `unavailable` rather than `blocked_by_moderation`.

## Expiry

`assetsDue({ ledger })` (`src/expiry/assets-due.ts`) is due work of the host, in the lane that calls nothing outside: the rows of `assets_1` whose `expires_at` has passed, the soonest first. Each one appends `asset_expired`, which releases the asset's hold on its bytes and takes it out of `asset_totals_1`, and then asks the ledger to remove its content, `removeUnheld`: where nothing else of the playbook holds the digest and it was last kept more than an hour before, the ledger removes it, `removed`, and the expiry records `asset_content_removed` with the size and the digest; where another holds it, `held`, such as another asset of the same bytes, the content stays until the last of them expires; and where it was kept again within the hour, `fresh`, by whoever is about to record its hold, it stays, and nothing records it. Content found `fresh` at expiry is not tried again: the asset's row is due no more, and nothing else asks for its removal until a later change gives `assets_1` a column to try it again by. The fact that releases precedes the removal, which a hold would refuse, so the result of the removal is a fact of its own. An expiry another performer recorded first is left as it is, and so is its removal. A process that stops between the expiry and the removal leaves the content kept with no holder.

## Bounds

`generationBounds` (`src/capability/generation-ports.ts`) is the default of what a run keeps, which the composer may replace: 20 MiB of one image, 50 MiB of audio and 200 MiB of a video, 2,048 MiB of a playbook's assets together, 90 days for an asset whose function names no `expires`, and 10 minutes, `waitMs`, that a run waits for a generation the provider finishes later. A run of an image or audio takes at most 300 seconds, and one that finishes later at most 240 seconds to ask, `waitMs` to wait and 240 seconds and a minute to fetch its bytes, which is the `longestRunOf` a workflow's step gives it, and the capability's `longestAnyRunMs`, 19 minutes by default. The total of a playbook is a soft bound: each run reads it before it keeps its own asset, so two generations that finish together may take it past its bound by one asset.

## Using it from code

```ts
const capability = makeGenerationFunctionAdapter({
  catalog: Result.getOrThrow(await readGenerationCatalog(shippedFiles)),
  gateways: modelSettings.gateways,
  fetch: (request) => fetch(request),
  ownKey: true,
  ledger,
  content: ledger.content,
  addresses: { signedContentAddress, ownOrigin },
  bounds: generationBounds,
});
const operations = [defineGetAsset({ addresses })];
const dueWork = [assetsDue({ ledger }), generationsDue({ gateways, fetch, ledger, content, addresses, bounds })];
```

The server composes it in `packages/server/src/composition/served-generation.ts`, `get_asset` over the same ports as the capability and outside the catalog of the directory listing, with the projections `assets`, `assetTotals` and `generationsWaiting` in `kept-projections.ts` and the step in `layout-steps.ts` and `AssetEventSchema` among the facts it reads in `known-facts.ts`.

## Testing

The server's `src/generation/` runs a function over HTTP and MCP against a gateway on the loopback, reads its asset at its address, reads it again with `get_asset` and lets it expire, and runs a workflow whose step waits for a video made in time and one that is not, over the shipped files with the film of the tests.
