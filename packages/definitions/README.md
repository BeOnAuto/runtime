# @on.auto/definitions

The definition and run operations of Auto Runtime: create, list, read, update, retire and run a playbook's function and workflow definitions, then inspect their runs and history, and publish events to a playbook. They are defined on the application layer, [`@on.auto/operations`](../operations).

## Definitions, runs and runtime adapters

`Definition` is a named, versioned definition stored in one playbook. A reasoning, interaction, prediction, recall or computation function uses Markdown with YAML front matter; a workflow uses a YAML document. `ListedDefinition` is the same view without the source document. A `Run` executes a definition against particular inputs and records how it ended; `RunDetail` includes the detailed record.

`PlaybookFunctionDefinition` covers `ReasoningFunctionDefinition`, `InteractionFunctionDefinition`, `PredictionFunctionDefinition`, `RecallFunctionDefinition` and `ComputationFunctionDefinition`; `WorkflowDefinition` identifies a stored workflow. `FunctionRun` and `WorkflowRun` identify their runs. The guards `isPlaybookFunctionDefinition`, `isWorkflowDefinition`, `isFunctionRun` and `isWorkflowRun` narrow decoded records by their `type` without copying or modifying them, and the two function guards read the one list of function types, `functionTypeOrder`. A custom adapter is not classified as a playbook function. The generic `Definition` and `Run` types still support extension adapters.

These are stored records with names, versions and audit fields. The adapters' parsed source configurations use the separate names `ReasoningFunctionDefinitionDocument`, `InteractionFunctionDefinitionDocument`, `PredictionFunctionDefinitionDocument`, `RecallFunctionDefinitionDocument`, `ComputationFunctionDefinitionDocument` and `WorkflowDefinitionDocument`.

`Capability` is the low-level adapter contract shared by functions, workflows and custom extension adapters. The server supplies these adapters explicitly. It is deliberately broader than a playbook function: workflows coordinate functions rather than belonging to the five function types. The product taxonomy and supporting assets are defined in [Playbook terminology](../../docs/concepts/terminology.md).

## Defining a runtime adapter

`defineCapability` turns what a capability package declares, a `CapabilityDeclaration`, into a `Capability`. The server passes its capabilities, in an explicit list, to `makeDefinitionOperations`.

This extension interface accepts custom adapters. Product categories use the shared `FunctionType` metadata: `functionTypeOrder`, and `functionCategoryLabels`, `functionResourceLabels` and `functionDescriptions`, each keyed by type.

```ts
import { defineCapability } from '@on.auto/definitions';
import { InvalidInput } from '@on.auto/operations';
import { Effect, Predicate } from 'effect';

const parseGreeting = (source: string) =>
  source.includes('{name}')
    ? Effect.succeed({ template: source.trim() })
    : Effect.fail(
        new InvalidInput({
          detail: 'The greeting names no one',
          issues: [{ detail: 'Line 1: expected {name} where the name goes', pointer: '' }],
        }),
      );

export const greeting = defineCapability({
  type: 'greeting',
  title: 'Greeting',
  guide: { name: 'greeting' },
  noun: { one: 'greeting', other: 'greetings' },
  describeOutput: () => 'It greeted.',
  mediaType: 'text/plain',
  parse: parseGreeting,
  summarize: ({ template }) => ({
    description: `Answers with "${template}"`,
    inputSchema: { type: 'object', properties: { name: { type: 'string' } }, required: ['name'] },
    outputSchema: { type: 'string' },
  }),
  run: ({ template }, input) =>
    Predicate.hasProperty(input, 'name') && Predicate.isString(input.name)
      ? Effect.succeed({ output: template.replace('{name}', input.name), record: { template } })
      : Effect.fail(
          new InvalidInput({
            detail: 'The input names no one',
            issues: [{ detail: 'Expected a string', pointer: '/name' }],
          }),
        ),
});
```

A capability has:

- `type`: 3 to 32 lowercase letters, digits and hyphens, starting with a letter. It is the type of the capability's definitions in routes, in the `type` field and in stream names, so it never changes.
- `title`, and `guide`: the `name` of the guide that holds its format, which the MCP layer serves through `get_guide` and as the resource `guide://<name>`, so that no operation description carries a format. The server makes the guide from the public reference page of the type, `docs/reference/<name without -function>-format.md`, and refuses to start without it. A guide may carry `onThisServer`, one sentence of what this server's configuration offers, such as the providers a reasoning function names its model through, which the guide ends with. `create_definition` names each type with the kind of definition it is and its guide, from the registered capabilities.
- `noun`, its definitions' noun for one and for several, and `describeOutput(output, record?)`, the sentence the operations say of a run's output, given the run's record beside it, which tells an interaction function's call that answered `{}` from a notification. `outputInWords('answer' | 'result')` is the sentence of every capability but that call's: the output in words within 300 characters, counted as code points, the records of a list each in parentheses, or that it is too long to repeat.
- `mediaType`: the media type of its definition documents, such as `text/markdown`.
- `parse(source)`: turns the document into the capability's own value. Parsing is validation: everything that can be checked without running is checked here. It fails with `InvalidInput`, whose issues each say in `detail` where in the document and what is wrong (line and problem). An issue's `pointer` addresses the document as a whole, so it is `''`; the operations answer it under `/source`.
- `summarize(parsed)`: what the operations show about a definition without knowing the type: an optional `description`, optional JSON Schemas of the input a run takes (`inputSchema`) and the output it gives (`outputSchema`), `triggers`, the parsed triggers of a definition that starts runs on its own, as a workflow with a schedule does, in the order its document names them, each with its `kind`, `event`, `cron` or `every`, its `reference` in the document, and its rule: an event trigger's `filters`, each a `reference`, a `type` and the `attributes` it matches, a cron's `expression` or an every's `milliseconds` (`TriggerSchema`), and optional `warnings`: what `parse` found that does not stop the definition from being accepted but may not work everywhere, each a line of text that says where in the document (for reasoning: a schema some providers reject or do not enforce); and optional `details`, a JSON object the registry stores with the definition's record and keeps in its state, but never in a definition an operation answers, so that code which reads the record without the capability's parser can act on it (for recall: the fold, `answer`, the filters, `initial` and the view's schema, which the workflow host folds a view by; for a workflow and a prediction function: `calls`, the definitions it calls, which [Used by](#used-by) reads with the recall function's filters).
- `overview(parsed, name, context)`, optional (`OverviewOf`): the parts of the definition's overview, its `body`, its `sections` and its `appendix`, which the capability composes from its parsed document alone, since each parsed document keeps the texts its overview reads, each with the line of the document it starts on: a reasoning function's prompt in its compiled template, and an interaction function's `to`, `from` and message and a prediction function's brief in their parsed templates; it is given too the name the overview is written for, by which reasoning draws the function, and a `context` that holds the `summary` `prepare` computed, from which a workflow's overview says its triggers and its schemas without computing the summary again (see [The overview of a definition](#the-overview-of-a-definition)). `prepare` answers `overview(name)`, the overview of the definition of that name as data, an `Overview`, which nothing writes as Markdown before a read: its name as the title, its `description` or the line `This <noun> has no description yet.` in the capability's `noun`, and these parts, or, for a capability that declares none, **What it needs** and **What it produces** from the summary's schemas, as two sections.
- `run(parsed, input, context, stripped)`: runs the definition, given the stripped forms its version was saved with, or none. `input` is the caller's JSON value; `context` carries the run's `id`, the `org`, the `playbook`, the `caller` who started it (the identity the call was authorized for), the `definition` that runs, by `name` and `version`, the `journal` through which it records the tool calls it makes (see [Tool calls](#tool-calls)), its `lineage`: `startId`, the id of the `run_started` that began this attempt, and `correlationId`, the id of the run at the top of the tree the run belongs to (see [The lineage of a run](#the-lineage-of-a-run)), its `depth`, the reaction depth of the run (see [The reaction depth of a run](#the-reaction-depth-of-a-run)), its `callDepth`, the number of calls above it (see [The call depth of a run](#the-call-depth-of-a-run)), and `longestRunOf(type, name)` and `longestRunFor(type, name, input)`, the longest a run of the active latest version of that definition may take for any input and for the input given, or nothing for a definition the playbook does not have, which a workflow reads at its start. It answers with the `output`, a JSON value returned to the caller, and a `record`, a JSON object of what happened, stored with the run (for reasoning: the rendered prompt, the model, token usage). It fails with `InvalidInput`, with pointers into the input (`/name` above; the operations answer them under `/input`); with `Unavailable` when something the capability depends on cannot serve now and retrying may work; or with `Conflict` when the definition cannot run as written, which only running it can tell (for reasoning: a model the provider does not have; for computation: a program that raised an error on the input), so the definition must be updated before it can run, with the kind `unworkable` when it says so. A rejection may carry a `record`, a JSON object of what the capability did before it (for reasoning: the tokens and the duration of a model call whose answer it could not use), which the run keeps on its `run_rejected`, held to the same size limit as any record. A capability that starts work which finishes after the call returns, such as a workflow, answers `{ finishesLater: true, record }` instead, the record saying what it started (for a workflow: its run reference); see [Runs that finish later](#runs-that-finish-later).
- `check(parsed, source, saved)`, optional: checks what parsing does not, at a cost a run must not pay, such as the programs and expressions of a document with a compiler, or against the other definitions of the playbook, which `saved`, a `SavedDefinitions`, reads: its `active(type, name)` answers the active version of that definition with its `name`, `version` and schemas, or nothing for one the playbook does not have active (for prediction: the interaction functions a version is approved and a build is sent through), and its `content(sha256)` answers the content the playbook keeps under that digest, through `PlaybookReader.readContent`, or nothing for a digest it does not keep (for prediction: the uploaded dataset a function names); the check answers the forms a run takes in place of the document's own, `StrippedForms`: the `module` and the `expressions` the check stripped of their types, an expression only where stripping changed it. It runs when a definition is created or updated, after `parse` and before anything is recorded, and never when a definition is read or run, since `parse` serves a run too; the save keeps what it answers as the version's `stripped`, beside its `source`, which no read shows. It fails with `InvalidInput`, as `parse` does, or with `Unavailable` when the check could not answer in time, which `create_definition` and `update_definition` answer as `unavailable`, 503, without a kind; see [The check at save](#the-check-at-save).

The compiler holds a capability to its contract. The value `parse` gives is the value `summarize` and `run` take. `parse` may fail only with `InvalidInput`, and `run` only with `InvalidInput`, `Unavailable` or `Conflict` (the union `CapabilityRejection`). Neither may ask for a service: whatever a capability needs, such as a model client, it closes over when it is made. The output must be JSON and the record a JSON object.

TypeScript infers the parsed value from `parse` when `parse` is a function declared elsewhere, as above, or an arrow function. Written inline as `Effect.fnUntraced(function* (source: string) {...})`, `parse` does not give its type to `summarize` and `run`; declare it as a constant first.

`parse` runs on every create, update and run, and its parsed value is not kept, so it must give the same answer for the same document and be quick. A defect in `run`, or an output that is not JSON, fails the run.

A call cancelled while `run` runs, because its client went away or the server is stopping, stops `run` and records the run `failed`. A retry with its id can run it again only if no recorded tool call blocks another attempt; see [Run ids and retries](#run-ids-and-retries). A capability that defines `whenCancelled: 'finish'` is not stopped: the call waits for `run` to end and records its answer. Recording the start and the end of a run is never cut short. An abrupt process crash can still leave a run `started` when it prevents the ending from being recorded.

## The operations

`makeDefinitionOperations(capabilities, facts?, presenters?)` returns the eleven operations for a catalog. All are playbook operations, so their routes are relative to the playbook. `defineCreateDefinition`, `defineListDefinitions`, `defineGetDefinition`, `defineUpdateDefinition`, `defineRetireDefinition`, `defineRunDefinition` and `defineListRuns` make one of them each for a list of capabilities, `defineGetRun(capabilities)` is another, `defineCancelRun(capabilities)` another, `defineGetRunHistory(presenters)` another, and `defineGetPlaybookAnalytics` the last, for a list of capabilities too, `defineListRuns` with the stored types of each status beside them. `get_run_history` and `get_playbook_analytics` are defined with `defineHttpOperation` and so served over HTTP alone: an agent reads what a run did with `list_playbook_events` of `@on.auto/playbooks`, given its `run_id`, and the analytics are Studio's to present; the other nine are also MCP tools; `facts` defaults to `composedFactsOf(capabilities)` and `presenters` to `makeDefinitionPresenters(capabilities, facts)` (see [Reading runs](#reading-runs)), and the server passes both, made once from what it composes. The list must hold at least one capability, and no two of the same type.

| ------------------------ | ------- | ---------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------- |
| `create_definition`      | command | `POST /definitions/{type}`               | `type`, `name`, `source`                                                          | the definition, `201`                            | `not_found`, `invalid_input`, `conflict`, `unavailable` |
| `list_definitions`       | query   | `GET /definitions/{type}`                | `type`, `include_retired` (default `false`)                                       | `{ definitions }`, sorted by name, no documents  | `not_found`                                             |
| `get_definition`         | query   | `GET /definitions/{type}/{name}`         | `type`, `name`                                                                    | the definition, active or retired, with document | `not_found`                                             |
| `update_definition`      | command | `PUT /definitions/{type}/{name}`         | `type`, `name`, `source`                                                          | the definition at its new version                | `not_found`, `invalid_input`, `conflict`, `unavailable` |
| `retire_definition`      | command | `POST /definitions/{type}/{name}/retire` | `type`, `name`                                                                    | the definition                                   | `not_found`, `conflict`                                 |
| `run_definition`         | command | `POST /definitions/{type}/{name}/run`    | `type`, `name`, `input` (any JSON, default `{}`), `run_id` (optional UUID)        | the run                                          | `not_found`, `conflict`, `invalid_input`, `unavailable` |

| `list_runs`              | query   | `GET /runs`                              | `type`, `name`, `status`, `limit`, `cursor`, all optional                         | `{ runs, has_more, next_cursor }`, newest first  | `invalid_input`                                         |

A definition carries `type`, `name`, `version`, `status` (`active` or `retired`), `media_type`, the `description`, `input_schema`, `output_schema` and `warnings` its capability gives when it gives them, `created_at`, `created_by`, `updated_at`, `retired_at` on a retired definition, its document as `source` and its `overview`, the Markdown the read writes from the overview its version was saved with and from what the playbook holds when it reads (see [Used by](#used-by)). `get_definition` adds `standing` when its capability's `standing` answers one (below). Of the `details` its capability gives, which the registry keeps, a definition answers only `details.shape`, the name of its [output shape](#output-shapes), when the details name one, and leaves the rest out (`src/operations/definition-views.ts`). A listed definition is the same without `source`, `overview` and `standing`. Times are ISO 8601 UTC strings read from Effect's `Clock`. `DefinitionSchema`, `ListedDefinitionSchema`, `RunSchema` and `RunDetailSchema` are the schemas.

- `type` is the type a capability states. The published JSON Schema of the field is a plain `{ "type": "string", "enum": [...], "description": ... }` of the known types. Decoding checks the shape and then that a capability of the server serves the type, so a malformed type and one the server does not run are both `invalid_input` at `/type` on every operation that takes one, `list_runs` and `get_playbook_analytics` among them; the second names the types the server runs. Effect would publish the types under `allOf`, because it inlines no `enum` from a check, so each operation replaces that one property of its input's JSON Schema.
- `name` is 3 to 48 lowercase letters, digits and hyphens, starting with a letter, `definitionNamePattern`, which a capability that names another definition in its document checks it by: unique among the definitions of its type in the playbook, and never reused.
- `source` is at most 65536 bytes in UTF-8, checked at decoding. The JSON Schema says `maxLength: 65536`, which every such document meets.
- A document the capability's `parse` rejects is `invalid_input` with the capability's issues under `/source`, and nothing is stored, and so is one its `check` refuses; a check that does not answer in time is `unavailable`, and nothing is stored either.
- `create_definition` meets `conflict` when an active or a retired definition of the type holds the name.
- A definition with triggers is recorded with its `triggers` in the content of `definition_created` and `definition_updated`, which `get_definition` and `list_definitions` show, and a playbook holds at most 1,024 active definitions of one type with triggers, however many each has, `mostReactingDefinitions`: a `create_definition` or `update_definition` that would make one more is `conflict`, counted after the version it replaces; `get_definition` of an active definition with triggers shows `triggers_since`, the id of the record that made its current version, from which what its triggers start is a run of that version. It is one id for the definition, while the workflow host keeps, for each trigger, the record that activated it as it is.
- `update_definition` replaces the document. Every update that changes the document makes a new version, one more than the last; an update with the same document succeeds and records nothing. It meets `not_found` for a missing definition and `conflict` for a retired one.
- `retire_definition` is permanent: a retired definition can be read and listed, but not updated, executed or recreated. Retiring a retired definition succeeds and records nothing.
- Every command also meets `conflict` when the definitions of the type, or the run, changed while it decided.
- `run_definition` runs the active latest version of the definition. It meets `not_found` for a missing definition, and `conflict` for a retired definition, a definition whose stored document its capability no longer parses, or a definition its capability finds cannot run as written.

The queries need `playbook:read` and the commands `playbook:write`. `run_definition` is a command, because it records a run, so a caller that may only read cannot execute a definition.

## Runs

A run carries `run_id`, `type`, `name`, `definition_version`, `status`, `output` when it succeeded, `rejection` (`reason`, `detail`, `issues` for `invalid_input`, for `unavailable` and `conflict` the `kind` and `because` the capability gave, and for `cancelled` the kind of the cancel) when the capability rejected it or the run was cancelled, `started_at`, `started_by`, and `finished_at` once it ended. `get_run` also shows the `record` the capability gave of what it did: of the run that succeeded, of what it did before it rejected the run when its rejection carries a `record`, such as the tokens a model call spent, or of the work it started that finishes later, kept when that work ends rejected or failed and dropped when a retry starts the run again. `run_definition` answers the same run, its record included, as `get_run` does, so the run has one shape on the wire, `RunDetailSchema`, and the words of either read the record beside the output. Its status is `started` while it runs, while work it started finishes after the call returned, or when the process ended before it finished; then `succeeded`, `rejected` or `failed`.

`run_definition` answers with the run when it succeeded, and in status `started` when the capability started work that finishes later. When the capability rejects it with `invalid_input`, `unavailable` or `conflict`, the operation is rejected with that reason, detail and issues, and the rejection is recorded on the run. When the capability breaks down, the call fails with an incident, as any defect does, and the run is recorded as `failed`; the defect itself goes only to the incident reporter. A rejected operation carries no run id, so a caller that wants to read a rejected run later gives it an id.

### Size limits

A run records its values in its facts, which every decision on its stream and every rebuild of a projection reads back, so a run records bounded values. Sizes are counted on the value encoded as JSON, in UTF-8 bytes.

- The `input` may take at most 262144 bytes (256 KiB). A larger input is rejected with `invalid_input` at `/input` when the call is decoded, before anything is recorded.
- The `input` may nest at most 512 levels deep, `mostInputDepth`, as deep as a workflow holds a value; `nestsWithin` measures it, counting each array and object a level. A deeper input is rejected the same way, for every runtime adapter, so that none is recorded deeper than a store takes: on SQLite an input 3,000 levels deep failed to append, while PostgreSQL took it.
- The `output` and the `record` of a capability may take at most 1048576 bytes (1 MiB) together. A capability that answers with more breaks down: the call fails with an incident and the run is recorded as `failed`. The same holds for the record of work that finishes later, and for the output and record it is settled with.

JSON Schema has no keyword for the encoded size of any JSON value, so the published schemas state both limits in the descriptions of `input` and `output`. `mostInputBytes` and `mostResultBytes` export them, so that a capability can keep what it answers within them.

### Run ids and retries

A caller may name a run with `run_id`, a UUID; otherwise the operation makes one, a version 7 UUID. Ids are kept in lowercase. An id belongs to one run: one type, one definition and one input. A call with an id of another definition or another input meets `conflict`.

A run has a **final result** once it succeeded, once the capability rejected its input as invalid, once it was cancelled, or once it ended `unanswered`, the request it made expired or never delivered. A call with the id of a run that has a final result runs nothing: it answers the same run, or the same `invalid_input` rejection, even when the definition has changed or been retired since. A call with the id of a run that waits for work it started to end runs nothing either: it answers the run as it stands, `started`. A call with the id of a run that has no final result and waits for nothing runs the active latest version of the definition again and records another attempt: when the run started within its call and never finished because the process ended, when its call was cancelled, when the capability was unavailable or found a conflict (a retry after the definition was updated runs the new version), and when it failed.

A run that called tools is the exception, because a tool may have changed something: once its stream holds a tool call, a call with its id that would run it again is rejected with `conflict`, kind `tools_called`, and runs nothing, whether the run failed, was rejected as `unavailable` or with a `conflict`, or stays `started` because the process ended; it is never recorded as finished for it, since that could mark a duplicate still running elsewhere as failed. So is a call with the id of a started run whose definition calls tools before any call is recorded: the first attempt may still be in progress, about to call a tool, or may have stopped without recording how it ended, and running a second would let two runs call tools. The capability tells from the parsed definition whether it calls tools (`callsTools`), and the start of a run records it on its `run_started` as `calls_tools: true`; a start is refused while the attempt started last is running and either recorded that it calls tools or the definition calls them now, so a definition that loses its tools while a run of it is going cannot let a second run start under its id. A new run needs another id. A run that called tools and succeeded, or whose input was rejected, is answered again as any other.

So running is **at least once**: the capability may run more than once for one id, when a call is retried after the server stopped during a run, after `unavailable`, a `conflict` the capability found, or a failure, or when two calls with the same id run at the same moment and the ledger lets both start. Each id has **exactly one recorded result**: the first final result recorded for it is never replaced, and every later call with the id answers it. A capability that acts on the world, such as one that sends a message, must tolerate running twice for the same `run.id`.

### Runs that finish later

A capability may state `mostActive`, the most definitions of its type a playbook may keep active, counted by the registry at each save: a creation that would pass it, and an update while the playbook keeps more than it, as when the bound was lowered, is `conflict`, and nothing else changes; a retirement is always taken. It is unbounded unless given; recall takes it from a setting of the server. A capability may state `standing({ org, playbook, name, version, status, details })`, which `get_definition` asks for the definition it reads, with the `details` its summary gave when it has them, and answers as `standing` when it gives one, so a capability that keeps something for a definition beside the ledger, as recall keeps a view and prediction a dataset, says how it stands; without it a definition has none.

A capability may state `longestAnyRunMs`, the longest one run may legitimately take (for reasoning: the deadline of a model call for the most output tokens, 60 seconds and 25 ms a token, 1660000 ms for 64000), `longestRunOf(parsed)`, the longest a run of one definition may take for any input (for reasoning: the larger of the bound of its tool loop and its model's deadline; for a workflow: the longest a workflow may run), and `longestRunFor(parsed, input)`, the longest for an input it knows, which is `longestRunOf` unless it says otherwise; the prepared definition carries them as `longestRunMs` and `longestRunMsFor(input)`, and a run's context as `longestRunOf(type, name)` and `longestRunFor(type, name, input)`; a capability that states neither is given 10 minutes. Prediction is the one capability of this runtime that answers by the input, `questionMs` for a question and the longest of a build for any other input (`@on.auto/prediction`); every other answers the same for every input. A workflow gives a call of a definition it names as written that long, for the call's input when the call writes it out with no expression in it and for any input otherwise, and a minute more, before the call fails, and any other call the longest `longestAnyRunMs` of the capabilities, and a minute more. A capability states `reachesOutside: true` when its runs call systems outside the server, as reasoning calls model providers; `run_definition` then says it reaches outside, which its MCP tool shows as `openWorldHint`. A capability states `mayChangeOutside: true` when those calls may change something there, as reasoning does once a tool server is configured; `run_definition` then says so, which its MCP tool shows as `destructiveHint`, so that an assistant asks before running a definition.

A capability such as a workflow starts work that completes long after the call returns. It states `finishesLater: true`, or a function of the parsed definition when only some of its definitions' runs finish later, as an interaction function's notification to the inbox ends within its call while every other request waits for an answer, and `finishesLaterFor(parsed, input)` when it decides by the input too, which is `finishesLater` unless it says otherwise; the prepared definition carries the answer for an input as `finishesLaterFor(input)`, which the start of each run records as `finishes_later` from the input it has, and its `run` answers `{ finishesLater: true, record }`, the record saying what it started. Such a capability defines `whenCancelled: 'finish'`, so that a call cancelled while `run` runs, because its client went away or the server is stopping, waits for `run` to end and records what it started; `run` must then end within a bounded time (a workflow's start gives up after 10 seconds). The run is recorded as deferred and stays `started`: `run_definition` answers with it in status `started` (still `200`), `get_run` shows it `started` until it is settled, and a retry with its id answers it as it stands without starting the work again.

Whoever started the work settles the run when the work ends, with `runSettler`:

```ts
import { runSettler, type SettleRun } from '@on.auto/definitions';

const settle: SettleRun = runSettler(ledger);

settle(run, { status: 'succeeded', output, record });
settle(run, { status: 'rejected', reason: 'unavailable', detail: 'The worker pool is gone' });
settle(run, { status: 'failed' });
```

`runSettler(ledger)` takes the unbound `Ledger` and gives a `SettleRun`, which takes, after the run and the settlement, the lineage to record the settlement with. It is not an operation and no transport reaches it: the server's composition root, the only code that holds the `Ledger`, makes it and hands it to the capabilities that finish later when it makes them. Each call to `settle` names the run by `org`, `playbook` and `id` (the `RunContext` a capability got carries all three), and binds the ledger to that org and playbook alone, through `streamPrefixOfPlaybook`, after checking the ids are well formed, so it reaches nothing but that playbook's `runs/{id}` stream. It records through the same stream and decider as `run_definition`:

- a run whose start says it finishes later, or that was deferred, and that has not been settled is settled: `succeeded` with its output and record, `rejected` with its reason, detail, kind, because, issues and record as given, `unanswered` with the kind `expired` or `undelivered` among the reasons, or `failed` with its incident; so a run that ends in its first input settles before its deferral is recorded, and the finish of the call that started it then records no deferral;
- a settlement has a key, its status, reason and kind, and for a success the SHA-256 digest of its output as canonical JSON: settling it again with the same key, from any actor, records nothing and answers the run;
- settling a run that already ended with another key, or one that runs within its call, is `conflict`;
- once the run took an answer, `request_answered` (see [The work of a run that finishes later](#the-work-of-a-run-that-finishes-later)), settling it as `unanswered` is `conflict` (`answeredFirst`), decided with the run's state at the append, so an expiry read before the answer cannot end it unanswered however the reads and the answer interleave;
- settling one the playbook does not have, or an ill-formed address, is `not_found`;
- an output and record over the size limit, or not JSON, settle it as `failed`, and the call dies with the defect.

`playbookBoundSettler(writer)` settles the same way through a writer already bound to one playbook, as an operation's `StreamWriter` is, and names the run by its id alone; `playbookBoundAnswerer(writer)` records an answer the same way, so `answer_interaction` records the answer it is given with the caller's ledger.

The settlement is recorded as done by the actor it names, the context's `by`, or else by the playbook's own caller, `playbook:<playbook>`. A deferred run settled as `unavailable` or `failed` has no final result, so a call with its id runs it again, as any other. A call with the id of a run whose start says it finishes later but that recorded no deferral, because the process ended in between, starts it again rather than answering it, so such a run is never left waiting for nothing.

A deferred run takes the facts of its own work until it is settled, tool calls, its answer and the facts its capability declares among them (see [The work of a run that finishes later](#the-work-of-a-run-that-finishes-later)), and refuses them after, with words that say the run has ended. Its state keeps the number of its last tool call, which the decider gives each call as it appends its start, the answer it took and the facts its capability recorded, and whether any call may have changed something outside, which only a tool call of a reasoning run sets. The deferral's context names the definition that ran, its type, name and version, as the endings' does, so the projection of open requests reads what asked from the deferral alone.

### The kind of a conflict

A run rejected with `conflict` records the kind the capability gave, so `get_run`, `list_runs`, the history and the run's words all show it. `unworkable` says the definition cannot run as written for this input, which only changing the definition or the input puts right: a computation function's program that raised an error, gave no output or more than one, did more work or nested deeper than a run may, or answered what the output schema refuses; `run_definition` also answers it, without recording a run, for a stored definition its capability no longer parses. `effect_unknown` says a run called a tool its server does not mark read-only and could not finish, so whether that tool changed something is not known; it carries the `because` of its ending, `server_failed`, `tool_error` or one of a reasoning run's, as `tools_unfinished`, its `unavailable` twin for a run whose every tool only reads, does. `tools_called` says a run of a function that may have called tools is not run again under its id (see [Run ids and retries](#run-ids-and-retries)); it carries the because `only_read` when the run ended without success and every call it recorded has `read_only: true`, whose words say that nothing was changed. `no_active_version` says a function that answers from a version it builds has none active yet, as a prediction function asked a question before any build, which a build puts right. `@on.auto/definitions/testing` has a probe whose mishap `unworkable` rejects that way.

## The check at save

`checkedAtSave(pool, job, deadlineMs)`, the one export of `@on.auto/definitions/check`, a subpath of its own because it names the engine's pool, which nothing else of the main entry needs, checks the programs and the expressions of a document as a job of the engine's pool, `check`, on the permit the pool keeps for checks beside the workers of runs, so a save never waits behind the runs (`src/program-check/save-check.ts`). The computation, recall, prediction and workflow capabilities call it from their `check`, with the document's module, its place, `computation` or `recall`, the schemas of its types, and every expression it holds with the names each may read; a workflow's expressions go as one job, whatever their number, and so do a prediction function's, the `data` expressions of its filters, which read `$data`, with no module. It answers the compiler's issues, each with the expression it belongs to, or `module`, and its line there, which the capability places in the document; or, when there are none, the document's `module` and the expressions stripping changed, by their source, which the capability answers from its `check` and the save keeps (`src/program-check/type-stripping.ts`), so no run strips anything and no runtime holds a compiler; or `InvalidInput` when the job does not answer within `deadlineMs`, 2,000 ms of the server's wall-clock time, counted from when its worker is ready, since the compiler took longer than a save allows over this document: its types should be simpler or its program split, and, since a busy server may also have slowed the check, the words say a later save may succeed; or `Unavailable` when the job stops otherwise: `busy` when no checker came free within that time or was ready within the start the pool allows it, the worker's memory, a cancelled save or the server stopping. The assignment bound stays the fast refusal of the one shape measured to grow the compiler's work with its square; others, such as hundreds of narrowings, meet the deadline. `warmedChecks(pool)` checks one trivial expression, which the server awaits before it accepts a request, so the compiler is loaded before the first save and no save waits behind the warming for the one permit; the pool keeps the worker of the checks however long it idles. A worker that crashes or cannot read the job is a defect.

The job runs in its own worker module, `src/program-check/check-worker.ts`, which loads the compiler once and keeps it, with the sandbox's lib, between checks, so a warm check pays only for the document. The compiler is TypeScript 6, `typescript` 6.0.3 installed under the alias `typescript6`, since TypeScript 7 has no compiler API to call and the repository's own toolchain keeps the name `typescript`; it is a dependency of this package alone. Its options are `strict`, `exactOptionalPropertyTypes`, `isolatedModules`, `erasableSyntaxOnly`, `noEmit` and `noLib`, with the sandbox's lib as the only lib and `types: []` (`src/program-check/checking.ts`). One program holds, each as a file of its own, so a line of the document's program is a line of its file and no offset is subtracted:

- the sandbox's lib and its iterator lib;
- the declarations of the document, `Json`, the types its schemas give, `Input`, `Output`, each definition of a schema's `$defs` or `definitions` as a type of its own named after the schema and the definition, `Input_address`, a character a name cannot hold written as its code point between two `$`, `Input_street$45$address`, so that a `$ref` may recur, and, for a recall function, `View`, each `Json` without its schema, and, for a recall function, `Event`, the playbook's event with its attributes and no extension, so that a misspelt attribute is refused rather than read as an extension (`src/program-check/schema-types.ts`);
- the program, the module of the document;
- the contract, which assigns each entry the place calls to the type the place gives it, the default export to `(input: Input) => Output`, `fold` to `(view: View, event: Event) => View` and `answer` to `(view: View, input: Input) => Output`, so a function of other types is refused with the signature it needs and the compiler's words (`src/program-check/entry-contracts.ts`);
- the expressions, each the body of a function of the names its place gives it, as `any`, since a workflow carries no schema of its data: an expression is checked for its syntax and its names, not its types, and one that closes its parentheses to write statements of its own is refused as not one expression (`src/program-check/expressions-file.ts`, `src/program-check/expression-issues.ts`).

Beside the compiler's diagnostics, a walk of the module (`src/program-check/module-rules.ts`) refuses what the compiler allows and the sandbox must not: an import, a `require`, `eval`, `new Function`, `import()`, `import.meta` and a declared name such as `declare global` (`A program reads nothing but its arguments: it imports no module and builds no code`); any top-level statement but a type, an interface and an exported function, a function the module does not export among them, since the freeze that keeps a page of folds from carrying state reaches only what the module exports (`A module holds its types and its exported functions and nothing else, so that two calls share nothing`); `async`, `await` and an exported generator (`The program is a function that answers at once; it awaits nothing`); and a module without the entry its place needs. The compiler's advice to change its settings, such as `Do you need to change your target library?`, is left out of its words, since a person writing a program cannot change them.

### The sandbox's lib

The lib is the sandbox's own, so a name the sandbox lacks is a name the check lacks. `sandboxLibOf(probe)` (`src/program-check/sandbox-lib.ts`) makes it from the compiler's ES2025 libs without `intl` and `weakref`, less the globals, `Math` members and `Date` methods of the engine's `sandboxRemovals`, the list the prelude removes them by, less the call signature of `DateConstructor` and its constructors of several numbers, which read the server's time zone, less the values of `Intl`, and less every global and member the sandbox answers it does not have, each asked of a fresh instance through the engine's `sandboxAnswers`, the members of an interface asked of a sample of it, which `src/program-check/instance-samples.ts` lists, a strict function among them, so the members that throw in a module, `arguments` and `caller`, go too. The comments go, and the licence notice of the compiler's libs is kept once at the top. The iterator lib stays a module of its own, as the compiler ships it, since its abstract class `Iterator` would collide with the global interface `Iterator` in a script (`lib.es2025.iterator.d.ts`, lines 19 to 22).

The repository has no build step, so the lib is generated by a command, `pnpm --filter @on.auto/definitions sandbox-lib` (`write-sandbox-lib.ts`), and kept under `lib/`, beside `src`, as `sandbox.d.ts.txt` and `sandbox-iterator.d.ts.txt`: text files, which the repository's lint and format do not read as its own declarations. `src/program-check/sandbox-lib.test.ts` generates it again and fails when the kept lib differs, so a new build of the engine, a change to the prelude's list or a new compiler changes the kept lib in the same change. The server's image copies `lib/`.

## Output shapes

A shape is a JSON Schema the runtime owns for what a definition produces, which Auto Studio draws: `series`, `categories`, `table` and `text` (`src/shapes`). Each is data, a schema of draft 2020-12 whose `$id` is `https://on.auto/shapes/<name>` and `title` its name, with `additionalProperties: false` on every record, its bounds beside it as constants, and `further`, the check of what the schema cannot say, run by `@on.auto/json-schema` with the schema's own check so that its issues are worded and bounded as the schema's are: the form of each `at` of a series under its `period`, `YYYY-MM-DD`, `YYYY-Www`, `YYYY-MM`, `YYYY-Qn` or `YYYY`, or an RFC 3339 date and time without one, with the day a day of its month and the week a week of its ISO year, and of its `origin`; each `at` later than the one before it in its line; at most 2,000 points across the lines; a `low` at most and a `high` at least its `value`; a name no line, value or column before it has; one cell in each row for each column; and a text of at most 65,536 bytes in UTF-8. The further check reads any JSON and says nothing of what the schema refuses, so its issues follow the schema's. `outputShapeNamed(name)` answers a shape and `outputShapeNames()` the names, each `{ name, schema, further, check }`, `check` the schema's check of an output, nested at most 512 levels, compiled the first time it is asked; `shapeMismatchOf(shape, output)` words the issues of an output that does not match, at most three; and `declaredShape(shape, besideSchema)` reads the `output.shape` of a document, refusing it at `schema` beside a schema of its own and at `shape` for anything but a shape's name, with the words each capability puts at its line. `rangeHolds({ low, value, high })` is the rule of a point's range that the check applies, exported so a capability that scores numbers before they become a series holds them to the same rule. `seriesShape`, `seriesBounds` and `seriesMarksSchema`, the schema of a series' marks, are exported for a capability whose output is always a series, as a prediction function's is. `shapeNamed(name)` of `@on.auto/definitions/testing` throws for a name that is no shape. A capability whose output names a shape publishes the shape's schema as its `outputSchema` and the name as `details.shape` through `publishedOutputOf({ schema, shape, details })` (`src/shapes/published-output.ts`), the one way a definition says its shape: with a shape it answers the shape's schema and adds `shape` to the capability's own `details`, and without one the definition's own schema and details, each left out when there is none; reasoning, computation, coordination and prediction use it, prediction with the series shape it always answers.

## Reading function documents

`@on.auto/definitions/document` is the reader that every capability whose document is YAML front matter and a body shares, so each capability supplies only its own keys and what its body means:

- `splitDocument(source, definition)` splits the front matter between two lines of three dashes from the body, with the line each starts on; `definition` names the document in the message for a source that does not start with the dashes.
- `frontMatterIn(text, firstLine, shape)` reads the front matter with the YAML rules every capability keeps (YAML 1.2's core schema, strictly, with no anchor, alias or tag and at most 72 levels of nesting) and decodes it with the capability's `FrontMatterShape`: its `sections`, the keys allowed at the top and under each section, of which any other is an issue at its line; its `decode`; and `required`, which the message for empty front matter names, such as `the model` for reasoning and `the language` for computation.
- `DescriptionSchema` is a `description` of a function document's front matter, 1 to 1,000 characters, which the front matter of each of the five function types takes, and `ValueContract`, `{ schema? }`, the compiled schema of an input or an output a parsed document may hold, which the parsed documents of interaction, recall and computation take.
- `issueAt` places an issue at the line of the deepest part of its JSON pointer that the front matter has, `issueText` writes it as `Line 7, /input/schema: ...`, or `Line 7: ...` for the document as a whole, and `reportedIssues` sorts a document's issues by line and bounds how many it reports.

Reasoning reads its documents with it and keeps its own keys, messages and tests; interaction, prediction, recall and computation read their own with the same reader. The JSON Schemas a document holds are compiled by [`@on.auto/json-schema`](../json-schema/README.md), which this reader and every capability import. The subpath is separate from the main entry because it imports the YAML parser, which nothing else in this package needs.

## Templates of a capability

`@on.auto/definitions/template` is the Liquid engine every capability whose documents hold templates shares, as a factory that gives each capability an instance of its own, so what one registers no other sees. `templateEngine(registrations?)` makes one, with the filters and tags every instance keeps, strict filters and variables, own properties only, and the bounds of `templateLimits`, 64 KiB of template, 1,000 names, 200 ms and 5 MB of a render, and with the filters and tags the capability registers, given as a function that answers them: the reasoning function adapter registers its system block and its prompt filters, `money`, `clip` and `words`, and the interaction and prediction capabilities nothing. `parsedTemplate(engine, body, firstLine)` parses a template, refusing one that does not parse with the line of its issue, and answers it with the variables it reads, each with its line in the document, an issue beside it when it uses more names than a template may, and the `text` it was parsed from with its `firstLine`, so that a parsed template is a `TemplateText` the reader of an overview takes as it is. `renderedTemplate(engine, parsed, { variables, emitter, refusalOf, clock })` renders it with the variables it is given into an emitter of the capability's own, which decides what a written value becomes and may refuse one, and answers a missing variable, a bound of the render or a failed filter, with its line, or what `refusalOf` makes of what the emitter threw. The 200 ms of a render are counted from its start on `clock`, a function that answers milliseconds, which every render is given: `renderClockOf(clock)` reads an Effect `Clock` as one, by its monotonic time, and `renderClock` is the one of the clock of the effect that renders, so each capability counts a render on the clock of its run and a test on `steppingClock` of the test support. The engine reaches into liquidjs at two places, each a function of its own. `tagsRemovedFrom` deletes the tags that load or capture templates from the instance's `tags`, since liquidjs unregisters a filter but offers no way to unregister a tag. `contextLimitedBy` writes the limit counted on `clock` into the context's `renderLimit`, since liquidjs counts a render's time on `performance.now()` and takes a limiter only through that field and its constructor, while it exports neither the class of its limiter, whose private members no object of ours can satisfy, nor an option for its clock. `inputVariableIssues(variables, inputSchema, what)` refuses a template that reads anything but `input`, `today` and `now`, or a property a closed input schema does not have, in the words of `what` the template is. `outputText` writes a value as Liquid writes it, an object as `[object Object]`; a rendered value is text, never parsed again as a template.

It serves too the reader of a template for an overview, `readableTemplate` and `readableParts` (see [The overview of a definition](#the-overview-of-a-definition)). The subpath is separate from the main entry because it imports `liquidjs`, which nothing else in this package needs.

## The overview of a definition

Each definition has an overview, the definition in plain words for a person who does not read its document, which Auto Studio shows before the source. It is composed once, when a version is saved, and written as Markdown at each read: `contentOf` asks `prepare(source).overview(name)` for it, an `Overview` with its blocks and its phrases, and the save records it in the version's `content` beside the `source` in its encoded form, through `encodedOverview`, so an older version keeps the overview it was saved with, and a phrase the read resolves is still a phrase when the read comes. The schema of the fact's content takes the overview as any value and decodes nothing of it, so the registry and the fold of a definition's stream carry it encoded: a load of a type's definitions, which every `get_definition`, `create_definition`, `update_definition`, `retire_definition`, `run_definition`, check at save and `list_definitions` makes, as do the workflow host's projector, its reader of triggers and the playbook's facts as events, folds every version of each name and keeps the latest, without decoding an overview. The SQLite and PostgreSQL stores keep each event as JSON text, which a load parses whole, overview and all, so what a fact keeps of an overview is bounded as what is written: a table of fields keeps its first `mostTableRows` rows where it is composed (see `overview.ts` below). `decodedOverview` decodes it, through the one `OverviewSchema`, in two places alone: where a read writes it, in `answeredDefinition`, and where the definition presenter measures it. A change to what a capability composes shows in a definition once a new version of it is saved, and a change to the writer at its next read. What the stored overview cannot hold, since another definition's save would make it stale, the read adds: who uses the definition and what it calls (see [Used by](#used-by)). It then writes the Markdown, so `get_definition`, `create_definition`, `update_definition` and `retire_definition` answer one `overview` text, as they did when the save wrote it. Measured on 2026-10-19 with Node 26.10.0 on a machine of 16 cores, by `pnpm --filter @on.auto/definitions measure:loads` (`measure/measure-loads.ts`), on SQLite: 50 versions of a document of 65,524 bytes, as many fields as one document holds, keep events of 180,841 bytes each, of which the overview takes 5,297, its table cut at 50 rows, beside the source and the input schema the summary gives; a load of their type, the parse of each event included, takes 36 ms of processor time at the median of 15, as does a read of the definition, which decodes and writes its one overview, and 47 to 112 ms of wall time at a load average of 180 to 260 from other work. `src/overview` holds it:

- `overview.ts`, the `Overview`, data and not Markdown, and `OverviewSchema`, the one schema from which the `Overview` and the type of each of its parts derive, through which `encodedOverview` encodes it for the fact and `decodedOverview` decodes it where it is written: a `title`, an `opening` and its parts: a `body`, the blocks a person reads first, with no sections of its own; `sections`, each a `heading` with blocks, which each capability composes and which are written between the body and the appendix; and an `appendix`, sections of the facts the body leaves out. A block is one of six kinds, a `paragraph` of phrases, a `list` of them, a `numbered` list of them, a table of `fields`, each a `name`, `required` and `words`, which `fieldTable(rows)` composes with its first `mostTableRows`, 50, rows and, past them, the count of the rest as `more`, a `quote` of `lines`, each a line of phrases, a message, an instruction or a brief shown as its reader receives it, and a `diagram` of `nodes`, each with a label and a `shape`, a `step` when left out, a `decision`, a `terminal` or a `cylinder` for what is kept, `edges`, each with an optional label and `dashed` or not, and optional `groups` of nodes with a label, each `within` an earlier group it names or at the top. A diagram draws a workflow's steps, how a recall function's view is kept and, for a reasoning function that names tools, the function, its model and each tool the model may call. A phrase is text as it is written, the author's own Markdown among it, a `name`, an `emphasis`, `code`, a `definition`, a `PhrasedDefinition`, its `type`, `name` and an optional `title`, which `definitionPhrase({ type, name, title? })` makes, or a `server` by its name; `listedPhrases(items, 'and' | 'or', separation?)` joins phrases as English lists them, as `listed` of `@on.auto/operations` joins words, and with `'serial-when-items-hold-commas'` separates two items with a serial comma when one of them holds a comma, as the steps of a caller do.
- `markdown-writer.ts`, `markdownOf(overview)`, and `markdownOfKept(kept)`, the same of an overview in the encoded form its fact keeps, which the definition presenter measures: the title as the one heading `#`, the opening, the blocks of the body, each section under `##`, and the appendix last, under the one heading `## Details` with each of its sections under `###`; a name in bold and an emphasis in italics with what would end them escaped, a definition, in the body and the sections, in bold by its `title`, or else by its name in words with its first letter raised, `Month window` for `month-window`, through `readableName` of `src/plain-language/in-words.ts`, and in the appendix by its name as written, in code, and a server in bold by its name, code in a span of backticks longer than any it holds, a list an item a line, a numbered list an item a line from `1.`, a table of fields in GFM with each `|`, backtick and backslash of a cell escaped and its line breaks made spaces, the rows it is given and, for a table whose composition kept the count of the rest, a last row `and n more`, and a diagram as a fenced `mermaid` block, `flowchart LR`, in `mermaid-diagram.ts`, whose node ids are `n1`, `n2` and group ids `g1`, `g2` by position, never the author's words, with each label quoted and its `#`, `"`, `&`, `<`, `>`, backtick and `|` written as Mermaid's entity codes, a step in brackets, a decision in braces, a terminal in a stadium, `([…])`, and a cylinder as `[(…)]`, a dashed edge as `-.->`, and each group a subgraph, nested in the subgraph of the group it is within. A quote is a Markdown block quote, through `blockQuoted(lines)` of `markdown-text.ts`, `> ` before each of its lines and `>` alone for a blank one, with a hard break, a backslash at the end of a line, between two lines of one paragraph, and none on a paragraph's or an item's last line, since a trailing backslash there is text: none before a line that opens a list item, a quote, a heading, a fence, a table, a thematic break or a setext underline, however far it is indented, as in an item nested in another; none after a heading, a thematic break or a setext underline; and none within a fence, indented code, a table or an HTML block. Indented code starts after a blank line, a heading, a closing fence or a thematic break, where a line indented four spaces does not go on with a paragraph. A table runs from a row with a `|` followed by its delimiter row, such as `| --- | :-: |`, to the next blank line, and a line with a `|` that heads no table is a line of its paragraph. An HTML block opens with one of the six kinds of the CommonMark reference that may interrupt a paragraph, `<script`, `<pre`, `<style` or `<textarea`, a comment, a processing instruction, a declaration, a `CDATA` section, or a block element such as `<div>`, and runs to the end its kind names, a comment to `-->` or to `--!>`, at which a browser ends one too, or, for an element, to the next blank line. An overview takes at most `mostOverviewBytes`, 65,536 bytes in UTF-8, its body, its sections and its appendix bounded together, in that order: past the bound, it is cut before the first block that does not fit, so its appendix loses its blocks before its body does, with one last line that says so; a heading of the appendix is written only with at least one of its own blocks, and `## Details` only when a block of the appendix is kept.
- `schema-words.ts`, `schemaBlocks(schema, unknown)`: a JSON Schema in words, through `schema-reading.ts`, which follows a `$ref` within the document, to `#`, `#/$defs/<name>` or `#/definitions/<name>`. An object with `properties` is a table of its fields in its order, each `required` or not, an undocumented one too; any other schema is a sentence; no schema at all is the words `unknown`. ### Used by

No fact records who uses a definition; the registries of the playbook are the index. A capability names what a definition uses in the `details` its `summarize` gives, which the registry keeps: a workflow and a prediction function as `calls`, each a `CalledDefinitionSchema`, a call with its role, `{ type, name, role }`, or a call with the steps that make it, `{ type, name, steps }`, a workflow the definitions its `run_definition` tasks name with a written-out `type` and `name`, in the order of its document and each once, and a prediction function its trainer, `source.through`, with the role `trainer`, then the function that approves a version, `evaluation.activate.approved`, with the role `approver`, both interaction functions; and a recall function as its `filters`. Each step of a call is a `CallingStep`, `{ number, name }`, the number its step has in the definition's diagram and the name of its task, and the details may carry a `title`, the definition's own readable name. `src/used-by` holds the reader: `usersOf(registries, { type, name })`, given every type's registry of the playbook, lists the active definitions but the one named whose details name it, each `{ type, name, title?, relation, steps? }`, its `title` the one its details carry, read only once a use of the definition is found, ordered by type, the five function types in their order, then workflows, then any other type, and then by name. A call with a role is the relation of its role, a trainer's `sends-builds` and an approver's `asks-approval`, and the calls with steps the relation `calls`, once, with every step they carry, so a call has a role or steps and nothing else names a user; a filter on a run event, `run_started`, `run_succeeded`, `run_rejected` or `run_failed`, whose `subject` is `<type>/<name>`, is `remembers-runs`, and a filter on a definition event, `definition_created`, `definition_updated` or `definition_retired`, whose `source` is `/definitions/<type>/<name>`, is `remembers-changes`, since those events carry no subject. A user with two relations is listed once for each. `definitionsCalled(registries, details)` lists the definitions a definition calls, those its `calls` name with their `steps`, in their order, each as the playbook holds it, a `DefinitionCalled`: `active` with its `description` and its `title`, `retired`, or `missing`; a call with a role is not one of them, so a prediction function's trainer is said by its own overview. Every operation that answers a definition with its overview, `get_definition`, `create_definition`, `update_definition` and `retire_definition`, does it through `answeredDefinition` of `src/operations/definition-reading.ts`: given the registry of the definition's own type, which the read loaded or the save left, it loads the registry of every other type it was given, once each, and writes the stored overview with what they hold through `overviewReadFrom(registries, type, stored)` of `src/used-by/overview-at-read.ts`, which decodes it and gives it `usersOf` and `definitionsCalled` through `overviewAtRead(overview, { users, called })`, so a definition saved after a workflow that calls it is answered with that workflow. `overviewAtRead` adds two sections after those the capability composed, each only when it has something to say: **What it calls**, a paragraph for each definition called, in the words of `calledSentence`, then **Used by**, a line for each user, in the words of `callerSentence`; and, after the capability's own appendix, the same two headings, which list the exact names of what is called and of who uses it, each once, in the words of `exactNameWithType`. It writes the whole through `markdownOf`, the body first and the appendix last, so an overview near its bound loses its appendix before its body and keeps its cut line, and `## Details` is written only when a block of the appendix is kept; a definition nothing uses that calls nothing is its stored overview as written. A phrase of the stored overview is written as the writer writes it: a definition by its title, or its name in words, in the body and by its name in the appendix, and a server by its name. `list_definitions` answers no overview. The words of a relation are `calls it`, followed by ` in step <number>, **<the name of its task in words>**` for each step that calls it, `sends it builds to train`, `asks it to approve a version`, `remembers its runs` and `remembers its changes`, each after `The <type's resource label> **<its title, or its name in words>**`.

## The words of a refused value

`wordedIssuesOf(schema, value)` (`src/checking/schema-refusals.ts`) is the one wording of the issues of a value its compiled schema refuses, for every refusal of an input or an answer a person or an agent gives: the input of a reasoning, interaction, recall, computation or prediction function or of a workflow, and the answer of a request. It answers each issue `issuesOf` of `@on.auto/json-schema` found at its pointer, unchanged, with one sentence for its `detail`, built from the schema and the pointer alone, so it is the same code for every field and every domain; `refusedInput(issues)` is the `InvalidInput` whose `detail` is the sentences in order, and `checkedInput(input, schema, noun)` the one check of the input of a run that the reasoning, interaction, prediction, recall and computation capabilities and the workflow capability share: an input nested past 512 levels is refused for the noun, `The input nests more than the 512 levels a computation function takes`, with no kind, as the operation's own bound of 512 levels refuses it first at `/input`, and one its schema refuses in those words, of the kind `input_schema` (`InvalidInputKindSchema` of `@on.auto/operations`), which says the definition refused the input it was given before it ran, so a caller knows to correct the input. `refusedByTheInputSchema({ detail, issues })` is the one place that sets the kind, which `checkedInput` calls and the reasoning capability calls for an input that is not the object its input schema takes. The kind travels with the rejection: `rejectedForInput` records it on the run's `invalid_input` rejection, which `get_run`, `list_runs`, the history of the run and its words show, a retry under the run id answers again, and a workflow's step reads as `$error.kind`. A sentence names the field, then says the rule it broke:

- the field is its name, the path of a nested one in words, `address, then city`, with an item of a list by its place, `lines, then item 2`, then the field's `description` as its author wrote it, its first letter included, without a final full stop, and its `examples`, `such as “ACME-001”`, unless the description says “such as” or holds one of them as a whole word; the value as a whole is `The input`, or `The answer`, as the schema's `what` names it;
- a bound it broke is said as the overview says it, from the keyword and its value alone: `at least 6 characters`, `at most 100`, `more than 0`, `at least 1 item`, `a multiple of 0.5`, `no item twice`;
- a value of another kind is told what the field takes, in the overview's words of the field: `a whole number, from 1 to 100`, `one of: draft, sent, approved`, `a date`;
- a string out of its format is told the form and an example of it, as a bound is said: `a date such as 2026-04-01`, `a date and time such as 2026-04-01T09:30:00Z`, `a time such as 09:30:00Z`, `an email address such as name@example.com`, `a URI such as https://example.com`, `a UUID such as 0f8fad5b-d9cb-469f-a165-70867728950e`, the form from `forms` and the example from `stringFormats` of `@on.auto/json-schema`; the example is left out where the field's description or its examples already give one, by the test the overview's `examplesWordsOf` makes, `field, such as “2026-05-01”: expected a date`, and kept for the value as a whole, whose description and examples the sentence does not say;
- a missing field is said at the field that holds it, `The input: expected the field month`, with the description of the field that is missing, and one the schema does not allow as `expected no field extra`, or `no item 3` in a list;
- a name that `propertyNames` refuses is said as the name and the field that has it, `the name long of names: expected at most 2 characters`, and a name where the names allow none as a field the schema does not allow is, `names: expected no name long`;
- an issue no keyword names keeps the words of the validator, `expected exactly one member to match`, after the field.

There is no `pattern` to word, nor a `format` other than the six, since the dialect refuses them. The issues of a refusal reach a workflow that called the function unchanged, under `/input`, and the workflow's rejection keeps them.

## The checked worker

`checkedWorker`, of the main entry, is the URL of the one worker module that checks values against their schemas where they were computed, for computation and recall functions alike (`src/checking`). The checked worker serves its jobs with `serveJobs` of `@on.auto/workflow-engine/job-loop`: a program with `answerOf` under the output check of the schema its request carries as its context, and a page of folds with `foldAnswerOf` under the view check of each view's schema. Both checks are `schemaCheckOf` of `@on.auto/json-schema` at the value depth of 512, the output check with the further check of the output shape a schema's `$id` names, so the output of a computation function that names a shape is checked as its shape says, the view check words its issues with `issuesDetail`, and the job loop compiles each once for each schema and keeps it while the worker is warm. The computation and recall capabilities name it for every run, the folds of views among them, with a `null` context when there is no output schema, so production runs one worker module. The worker imports the compiler from `@on.auto/json-schema` and nothing of this package's YAML reader, because the reader's modules and the YAML parser had taken a worker from 138 ms to 254 ms to load, measured on a busy machine, a cost paid once for each worker the pool starts.

## Reading runs

`list_runs` lists the runs of a playbook, newest first by the position of the first message of each run stream, so a run started again with the same id keeps the place of its first start, and two started in the same millisecond keep a fixed order. It reads the ledger's selection of the first and the latest message of every run stream (`PlaybookReader.readRecorded({ kind: 'runs', notBeginningWith: ['run_cancel_requested'], definitionType?, name? }, page)`), which leaves out a stream that begins with its caller's cancel, since such a stream holds no run, before the page counts, so a page is full while runs remain and `has_more` is false after the last. `status` is the page's `types`, the stored types of a run's latest message in that status (`storedTypesByStatus`), and `type` and `name` go to the ledger as `definitionType` and `name`, which it reads from the run's first start, `run_started`, so the store answers every filter as it examines the runs, up to 1,000 of them for a page with any filter, and a page of the runs of one definition is full while it finds them; a run started again under its id is always started for the same definition, so its first start names the definition of every start. The operation folds the two with the run decider's `evolve`, so a `ListedRun` is the run as `get_run` shows it, without its `output`, its `record` and the `detail` and `issues` of a rejection: `run_id`, `type`, `name`, `definition_version`, `status`, `started_at`, `started_by`, `finished_at`, and a `rejection` of `reason`, with the `kind` and `because` of `unavailable` and the `kind` of `conflict`. When the latest message is a start, the run shows that start; when the run was started again and has since finished, it shows its first start, since the selection holds no other, while `get_run` shows the latest.

- `status` is answered by the ledger from the stored type of the latest message: `storedTypesByStatus(declared)` in `src/reading/run-status.ts`, given the facts the capabilities composed declare, is the one place that maps a status to the stored types it stands for, `started` to `run_started`, `run_deferred`, a cancel and the facts of the run's work, its tool calls, its answer and every fact the capabilities composed declare.
- `type` and `name` are applied after decoding the first message of each run the page looked at, so a filter that matches rarely answers short or empty pages with `next_cursor`. A type the server does not offer lists the runs recorded under it, if any.
- `limit` is 1 to 100, 20 when left out. A page also ends at 4 MiB of stored data and, with `status`, after looking at 1,000 runs. Every page carries `has_more` and `next_cursor`, null when nothing remains, and a cursor that does not decode, or that another playbook gave, is `invalid_input` at `/cursor`.

`get_run_history` reads the two streams of one run through the ledger's run selection, `runs/{run_id}` and, for a workflow's run log, `run-logs/{run_id}`, one page at a time, oldest first unless `order` is `desc`. Each record is shown through the presenter of its stream kind, as none, one or more events, and hidden when its kind has none; the server gives the presenter of the run log, `runPresenter` of `@on.auto/coordination`, so a workflow's history shows a `workflow_input_applied` event for each input its run took, followed by an event for each step entry of that input. `limit` counts the events a page answers with, step events included, through `eventsPageOf` of `@on.auto/operations`, so a page may end inside the events of one record, with a `next_cursor` that reads on from the next of them. The events follow the ledger's order, within a page and across pages, so reading on from a page's `next_cursor` answers exactly the events after it; it is also the order of their causes, since a message is appended only after the message that caused it, as a child's start after the record of the step that waits for it. A run the playbook does not have is `not_found`. A page that holds a record other than a cancel proves the run exists, and the read is that page alone, however long the run's streams. A page that holds nothing but `run_cancel_requested`, or nothing, reads one more record, the newest of the two streams, newest first and without its data: none, or a cancel alone at the first place of its stream, which is all a stream its caller cancelled before the start ever holds, is `not_found`, and anything else is the run, whose page is answered. That read keeps no horizon, since on PostgreSQL only a read oldest first stays behind the oldest write still open in the ledger's database. So the first page of a run whose records are still behind that horizon is empty, with `has_more` false and `next_cursor` null, and a reader reads it again; and no page loads the run's whole stream, which has no bound on its size.

| `runs`        | a fact a capability declares               | what that capability shows of it, in its words, through the `present` it declares beside the fact's schema                                                                                                                                                                                   |
| `tool-calls`  | `tool_call_started`                        | a call made by hand: `call_id`, `server`, `tool`, `read_only` when marked, `arguments_bytes`, and `arguments_sha256` and `arguments` where kept; `handCallPresenter` of `@on.auto/tool-servers` presents the three                                                                           |
| `tool-calls`  | `tool_call_answered`, `tool_call_failed`   | `is_error` or `because`, `result_bytes`, `duration_ms`, `jsonrpc_id`, `server_request_id`, and `result_sha256` and `answer` where kept, with no `number`, since the stream holds one call                                                                                                    |
| `definitions` | `definition_created`, `definition_updated` | `source_bytes`, `overview_bytes`, the bytes in UTF-8 of the Markdown the overview its content keeps writes, without what a read adds, which is not the size of what the fact stores, the first 300 characters of `description`, `input_schema_bytes`, `output_schema_bytes`, `warning_count` |
| `definitions` | `definition_retired`                       | none                                                                                                                                                                                                                                                                                         |
| `events`      | `event_published`                          | `event_id` and `event_type` cut at 256 bytes, `source` and `subject` cut at 1024, `time`, `data` when it has data, the attributes the playbook `filled`                                                                                                                                      |
| `reactions`   | `reaction_refused`                         | `count`, the last `reason` cut at 1024, and the `minute` it counts; the workflow host records it through `reactionRefusalDecider`, and its context names the workflow and its version, with the playbook as its actor                                                                        |

The run presenter asks the run's capability, by the definition type in the record's context, for the words of its deferral, `runWords`: `deferral(record)` answers the summary and the fields of the record it shows, or nothing, under the public type `deferralType`, `run_deferred` unless the capability names its own, as an interaction function names `interaction_requested`. A fact a capability declares is shown by that capability, whichever run it is on, and a fact no capability composed declares shows as no event. A capability that gives no words for its deferral, as a workflow gives none, shows it as no event: it stays on the run's stream, where `status` and a retry read it, and nothing names it as its cause, so a history goes on from a start to what the run did next, the inputs and steps of a workflow directly. An interaction function's deferral is its request, shown as “waiting for an answer”. Sizes are of the value as JSON in UTF-8, the document's of its own text. A cut is made at a code point, measured as JSON so that escapes count; an issue's `detail` at 256 bytes and its `pointer` at 128; a tool call's `call_id`, `server`, `tool` and `server_request_id` at 256 bytes, its digests and a `jsonrpc_id` that is text at 128. The latest message of a running run may be a tool event, which `list_runs` shows as `started`. A test over the event schemas of both deciders holds every stored type to a decision of its presenter, and the largest record each type can hold to 4 KiB of `data`. Who acted, when, the run, the definition and the chain are never in `data`: they are the row's `metadata`, from the record's context.

## Storage

The definitions of one type in a playbook are one stream, named `definitions/{type}` relative to the playbook. Its events carry a `type` and the fact; the definition's type, name and version, who recorded it and when are the context of the message, a `DefinitionContext` of `@on.auto/operations` that each fact's schema names beside its data, so the decider's `context` gives every event of a decision one and a record without its definition or its version does not decode:

- `definition_created`, version 1 in its context, with the `content`: the `source`, the `overview` composed from it, in its encoded form, which the fold carries without decoding it, and the `description`, `input_schema`, `output_schema`, `warnings` and `details` its capability gave
- `definition_updated`, the new version in its context, with the whole new `content`
- `definition_retired`, the version it retires in its context

`DefinitionEventSchema`, the schema of these events, and `definitionTypeStreamOf(type)`, the name of the stream relative to its playbook, are exported, so code that holds the ledger's store, as the workflow host does, reads a playbook's definitions of one type, and their `details`, without the operations. The search for one version's document, `definitionVersionFold`, is a `Fold` of that stream, which `load` takes: it decides nothing and gives no context.

Each run is a stream of its own, named `runs/{run_id}` relative to the playbook. Its events carry a `type` and the fact, and the context of each, a `RunContext`, holds who acted and when, the run, the definition's type, name and version, and the run's chain, its call, call depth, reaction depth and trigger; `run_cancel_requested` alone carries who asked, when and the run, since a cancel may come before the start, and the run's state reads no more of it:

- `run_started`, with the `input`, `calls_tools: true` when its definition calls tools, `finishes_later` when it finishes after its call, and `output_shape`, the name of the shape its output takes: the shape the definition's summary declares in `details.shape`, read by `shapeNameIn` of `src/shapes/published-output.ts`, when the capability's `answersItsShapeFor(parsed, input)`, true unless the capability declares it, says this run answers it, as a prediction function says of a question and not of a build; `run-requests.ts` takes it from `outputShapeOf(prepared, input)` of `definition-preparation.ts` as it records the start, and the run's state carries it into every `Run`, so `get_run`, `run_definition` and `list_runs` show it; the definition and the chain are the start's context, taken from the command, and a retry records them again
- `run_deferred`, with the `record` of the work that finishes later and the definition that ran; a run that started and never finished has no such event, which is how a retry tells the two apart
- `run_succeeded`, with the `output` and the capability's `record`
- `run_rejected`, with the `rejection`, and the `record` its rejection carried, when it carried one
- `run_failed`
- `tool_call_started`, and `tool_call_answered` or `tool_call_failed`, for each tool call it makes, described under [Tool calls](#tool-calls)
- `request_answered`, the one answer of a request the run waits on, and the facts its capability declares, each recorded through the `work` command, described under [The work of a run that finishes later](#the-work-of-a-run-that-finishes-later)

The context of each of the three endings, and of every later fact, carries the definition and the chain of the attempt, which the decider's `context` takes from the run's latest start in its state, so an ending says what ran without a read of the start; the state reads `started_at` and `started_by` from the start's context as it folds the recorded events, `{ type, data, context }`.

### Cancelling a run

`cancel_run` records `run_cancel_requested` on the run's stream, with the kind `requested` and the `reason`, the caller its context's `by`, or words that name the caller: the request is a fact, so it lands on any server and outlasts a crash. It answers the run as it stands. A run that has ended is `conflict`, and so is a run that runs within its call, since no server can interrupt another request's fiber; a run whose start says it finishes later may be cancelled before its deferral is recorded. Asking again before the run ended records nothing more. The workflow host's follower turns the fact into the effect: for a workflow, the engine's input `cancel_requested`; for a run of another capability that finishes later, `deferredCanceller(capabilities, ledger)`, which settles the run with what the capability's `cancel(run)` answers, a pure decision over the run's record, its kind, its reason, the answer the run took, `answer`, the facts its capability recorded on it, `work`, each with its time, and the run's address, `run`, `cancelledAsAsked` unless the capability states one, and settles a run whose `cancel` throws as `failed`; it settles against the version of the run it read (`runSettlerAsRead`), so a fact recorded since, such as an answer or the end of a delivery that delivered, refuses the settlement as `concurrent_change`, and it reads the run again and decides once more, up to three times more. `runCanceller(ledger)` records the cancels the host makes of the runs its calls wait for, with the kind `deadline` or `parent_ended`, answering `requested`, `ended`, or `unknown_run` for an address a playbook cannot hold. A cancel from the caller is a fact whatever state the run is in: on a stream with no run yet it is the first record, without a definition, and a start that lands after it, of either kind, is refused with `cancelled` and its kind, so the ledger orders the cancel and the start, and the stream still holds no run, so `list_runs` leaves it out and `get_run` and `get_run_history` answer `not_found`; on a run within its call it is recorded, and the attempt its interrupt stops ends `rejected` as `cancelled` with that kind rather than `failed`. `cancel_run` keeps answering `not_found` for a run the playbook does not have, and `conflict` for a run within its call.

A cancelled run ends `rejected` with the reason `cancelled` and its kind, `requested`, `deadline`, `overrun` or `parent_ended`; `RunCancelled` of `@on.auto/operations` is its error, and its problem type `https://on.auto/problems/cancelled`.

### The call depth of a run

A run that a workflow's call starts carries, in `CallLineage`, the number of calls above it, `callDepth`, and the call it answers, `calledBy`: the workflow's run id, the call's reference and its run. The context of `run_started` and of every fact after it carries them as `callDepth` and `calledBy`, so the ending of the run names the call it answers. A start more than 8 calls below the run at the top of its tree, `mostCallDepth`, is refused with `conflict` before anything is recorded.

### The reaction depth of a run

A run started in the process by another run or by a reaction carries a reaction depth, which the playbook request gives the start path in `CallLineage` beside the lineage and never in an input. The context of `run_started` and of every fact after it carries it as `depth` when it is above 0, and the run's context gives it to `run`. The workflow host bounds a chain of reactions by it (`@on.auto/workflow-host`).

### The trigger of a run

A run a workflow's trigger started carries that trigger in `CallLineage`, as the playbook request gives it: its `kind`, `event`, `cron` or `every`, and its `reference`, the place in the document that names it. The context of `run_started` and of every fact after it carries it as `trigger`, and `playbookFactOf` gives it as the attributes `triggerkind` and `triggerreference`, so a trigger filter names `triggerkind: event`. The history says in words which kind started the run, "was started by its event trigger", "by its cron schedule" or "by its every schedule", and gives the trigger in the row's `metadata`; the words never name the reference. `started_by` stays the actor, `playbook:<playbook>`, since who acts is not what fired.

### Starting one version once

`defineStartVersion(capabilities)` is `start_definition_version`, a playbook command that no catalog serves: the workflow host calls it in the process, through the dispatcher, for the runs reactions start, as the playbook's own caller (`playbookCallerOf` of `@on.auto/operations`), with the run's depth and lineage in the request. Its input names a `type`, a `name`, a `version`, an `input` and a `run_id`. Its start only creates: the decider records it when the playbook has no run under that id, or when the run under it ended without a final result, failed or rejected for any reason but `invalid_input`, as with `unavailable` or `conflict`, without tool calls, and was asked the same, so a start the playbook could not take at first goes through on a later delivery; for a run that goes, or that ended with a result, or that another request ended, it refuses with `conflict` of the kind `taken` (`runTaken`), and the command answers the run as it stands and runs nothing, whatever it was asked, also when a second start races it. Otherwise it runs that version of the definition, found in the definition's stream even after a later version or its retirement, and answers as `run_definition` does. A version the definition never had is `not_found`.

### The lineage of a run

Every event of a run is written with its cause and its correlation (see the ledger port of `@on.auto/operations`). The correlation of a run that no other run started is its own run id; a run started by another run, as a workflow starts the function it calls, is given a lineage with its request, which the start path takes from `CallLineage` and passes to `run`, and every event of the run takes the correlation of that lineage. The `run_definition` input never carries one: its decoding refuses a field it does not know. The causes:

| Event                  | Caused by                                                                                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| `run_started`          | nothing for a run no other run started; the cause its lineage gives, the waiting step of a call, otherwise |
| `run_deferred`         | the `run_started` of the attempt, whose position the start path keeps from what `run` answers              |
| `run_cancel_requested` | nothing; its correlation is the one the run's first record has                                             |
| `tool_call_started`    | the `tool_call_answered` before it, the first by the start                                                 |
| `tool_call_answered`   | its `tool_call_started`, or the answer before it for a call the journal has no start of                    |
| the finish of a run    | its last `tool_call_answered`, or its start when it called no tool                                         |
| a settlement           | the cause the settler is given: for a workflow, the last step event of the record that ended its run       |

There is no read model of the definitions or of a run: each call folds the streams it needs. The outcomes of runs, which `get_playbook_analytics` reads, are a table the ledger keeps from these events (see [Analytics](#analytics)). Pure deciders hold the rules: one for the definitions of each type, and one for runs. The handlers pass them who and when in each command.

## Analytics

`defineGetPlaybookAnalytics(capabilities)` makes `get_playbook_analytics`, `GET /analytics` relative to the playbook, under `playbook:read`. It reads the outcomes of the playbook's runs over a window of days in UTC, through `PlaybookReader.readRunOutcomes` (see [`@on.auto/operations`](../operations/README.md#the-outcomes-of-runs)), one statement of the store:

- the window: `days`, 7, 14 or 30, the last days ending today, 7 when nothing is given; or `from` and `to`, both included, at most 366 days, with `to` not before `from` and not after today. A day must name the same day when read back, so `2026-02-30` is refused at `/from` by the input schema. `days` with `from` or `to` is `invalid_input` at `/days`, `from` without `to` at `/to` and `to` without `from` at `/from`, a window that ends before it starts or after today at `/to`, and one longer than 366 days at `/from`. An unknown `days` or parameter is refused as every input is.
- `type` and `name`, as `list_runs` takes them, keep the runs of that type and definition name.
- The answer: `days`; `runs`, with the `total`, `succeeded`, `failed` and `rejected`; `tokens`, the `input`, `output` and `cached` tokens; `duration_ms`, with `p50` and `p95`, or `null`; `by_day`, the `day` and the same three for every day of the window, oldest first, a day without runs included; and `by_function`, each definition's `type`, `name` and `runs`, the number of its runs that ended, the most runs first, then by `type` and `name` in the order of their characters.
- A run counts on the day it first started, once it has ended; a run still `started` counts nowhere. Its duration runs from its latest start to its end, for a run that succeeded or failed, workflows included; a rejected run counts in `runs` and in `tokens`, never in `duration_ms`. A percentile is the nearest rank, the duration at place ⌈p × n⌉ of the durations in order; the operation adds the groups the ledger answers and takes the percentiles in code. Tokens sum what was recorded, over every attempt of a run started again under its id, 0 otherwise, and `cached` is the cache-read part of `input`.

`runOutcomeMapping` is the `RunOutcomeMapping` of the run events, which the server gives the ledger at composition. It reads `run_started`, `run_succeeded`, `run_failed` and `run_rejected`, and leaves the row as it is for anything it does not understand:

| Field                                               | From                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `startedDay`, `startedAt`, `definitionType`, `name` | the first `run_started` of the run, its `at` and its UTC date; a finish without a start gives its own `at` and empty names                                                                                                                                                                                    |
| `lastStartedAt`                                     | the `at` of the latest `run_started`                                                                                                                                                                                                                                                                          |
| `status`                                            | `started` from every start, then `succeeded`, `failed` or `rejected` from the finish                                                                                                                                                                                                                          |
| `durationMs`                                        | the finish's `at` less `lastStartedAt` for a run that succeeded or failed, never below 0; `null` for a rejected run, a run still started, or a finish without a start                                                                                                                                         |
| the tokens                                          | the sums of `record.usage.input.total`, `record.usage.output.total` and `record.usage.input.cache_read` over every finish of the run, each counted when it is a whole number of at least 0; `null` while no finish gave one, so a run rejected after its model spent tokens and then started again keeps them |

`measure/measure-outcomes.ts` measures the ledger's table of run outcomes kept with this mapping, on both stores: the read, the append with and without it, and the fill of a new table version (`pnpm --filter @on.auto/definitions measure:outcomes`). It lives here with the mapping rather than in the ledger, so the ledger depends on nothing in this package; [the ledger's README](../ledger/README.md#measurement-of-the-outcomes) holds the figures.

## Events of a playbook

A playbook takes events from outside and records facts of its own, both in the shape of [CloudEvents 1.0](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md). `CloudEventSchema` is an event as the playbook keeps it: `specversion` `1.0`, `id`, `source`, a URI reference that is not empty, `type` and `time` in RFC 3339, and optionally `subject`, `datacontenttype`, a media type such as `text/plain; charset=utf-8`, `dataschema`, an absolute URI, and `data`, any JSON value that nests at most 510 levels deep, `mostEventDataDepth`, so that a run can hold the whole event in a list, as an input or as what a `listen` task gives; deeper data is `invalid_input` at `/event/data`. Any other attribute is an extension, at most 32 of them, named in 1 to 20 lowercase letters and digits, as CloudEvents recommends, whose value is text, a boolean or an integer from -2147483648 to 2147483647, kept as given. `id` and `type` take at most 256 characters, `source`, `subject` and `dataschema` at most 1,024, and a time at most nine digits of a fraction of a second. As CloudEvents requires, no text holds a control character (U+0000 to U+001F, U+007F to U+009F), a surrogate that is not one of a pair, or a noncharacter, `refusingForbiddenCharacters`; `id`, `type` and `subject` hold a character that is not a space, `refusingBlankText`, both of which `send_run_event` applies too, as it takes a `source` only as `EventSourceSchema`, the URI reference of a published event; and a time's second is 60 only in the last minute of a day in UTC (`events/event-time.ts`).

### Publishing an event

`definePublishEvent(names)` is `publish_event`, a playbook command at `POST /events` under `playbook:write`, which the server serves beside the operations of `makeDefinitionOperations`, given the playbook's own names of the capabilities it composes, `playbookOwnNamesOf(capabilities, facts?)`, which takes the declared facts of a capability before the capability is made, as the server takes the workflow's, `workflowFacts`, `{ type, facts }`, and the facts composed from them, `composedFactsOf(capabilities)` unless the caller has composed them already. Its input is `event`, a CloudEvent whose `specversion`, `id` and `time` may be left out, and it answers `{ id, time, recorded_at }`.

- The playbook fills in what is left out: `specversion` 1.0, an `id`, a version 7 UUID, and as `time` the moment it records the event. With them, the event takes at most 245,760 bytes (240 KiB) as JSON in UTF-8, `mostPublishedEventBytes`, so that it fits a run's input of 256 KiB inside an array; a larger one is `invalid_input` at `/event`.
- `causationid` and `correlationid`, the extension attributes that carry the lineage of the playbook's own facts, and `caller`, `definitionversion`, `depth`, `calldepth`, `calledby`, `triggerkind` and `triggerreference`, those that carry their context (`contextAttributeNames`, see [The playbook's own facts as events](#the-playbooks-own-facts-as-events)), are refused as `invalid_input` at `/event/` and the name, so no event published to a playbook or sent to a run claims a cause, a caller or a depth it does not have.
- The types the playbook records on the streams of its runs and its definitions, every stored type of their events, `event_published` and `reaction_refused`, which this package records itself, and those the capabilities composed declare: the facts on their runs, the public type each gives its deferral, as `interaction_requested`, and every type the presenters of the stream kinds they own show, as the tool tests of reasoning and the inputs and steps of a workflow, the `types` of `playbookOwnNamesOf(capabilities)`, and sources under `/runs/`, `/definitions/` and `/callers/`, the last the source the playbook gives an event a caller sends a run without one (`callerSourcePrefix`), named in words by `reservedSourcesInWords` and checked by `isReservedSource`, are the playbook's own: an event that uses them is `invalid_input` at `/event/type` or `/event/source`. Its `refusingThePlaybooksOwnAttributes` is that check, a filter of an event's schema, which `send_run_event` of `@on.auto/coordination` and a workflow's `emit` apply too, so that no event sent to a run poses as a fact a `listen` filter matches. The server's test holds the list a business cannot publish.
- Each event is a stream of its own, `events/<uuid>`, the uuid a name-based UUID, version 5, of its `source` and `id` in a namespace of its own. The publish records `event_published`, with the event and the attributes the playbook `filled`, who published it and when in its context, an `ActedContext`, on that stream while it is empty. Publishing it again with the same source and id records nothing and answers the first record's `id`, `time` and `recorded_at`, and a different event under the same source and id is `conflict`. The two are compared on what both callers gave: an attribute the playbook filled in for either of them, such as a `time` left out on a retry, is left out of the comparison, so a retry that gives a time to an event first published without one answers the time the playbook filled in. Times are compared as instants (`instantOf` in `events/event-time.ts`), so one instant spelled two ways is one time, to the nanosecond; a leap second counts as the first second of the next day. A publish without an `id` gets a new one, so it is always a new event.

### An event a workflow emits

`eventEmitter(ledger, names)` gives the workflow host an `EmitEvent`: it records an event a workflow's `emit` task made as `event_published` on the event's own stream, as `publish_event` would, its context, an `EmittedContext`, naming the run, the workflow and its version, and `depth`, the reaction depth of that run plus one, under the lineage it is given. The same event again records nothing and answers `already_recorded`; an event the playbook does not take, by `CloudEventSchema`, its reserved types and sources or its bound of 240 KiB, or one whose source and id another event holds, is `refused` and recorded nowhere; a ledger that kept changing fails, so the output is dispatched again. `emittedEventsOf(names).refusalOf(event)` says, in words, why the playbook would not take an event a workflow computed, so the run can fail its task instead. `publishedEventOf(data)` reads a stored `event_published`. `list_playbook_events` says of an emitted event which workflow emitted it.

### The playbook's own facts as events

`playbookFactOf(record)` turns a record the playbook stored into a CloudEvent, or `undefined` for a record that is no fact. It takes a `RecordedFact`, the record as `PlaybookReader.readRecorded` gives it without the page's cursor, its stream named relative to the playbook, and builds the event from the stored event, never from its presentation:

| Record                                                           | `source`                     | `subject`       | `data`                                                                                                                          |
| ---------------------------------------------------------------- | ---------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `run_started`, `run_failed`                                      | `/runs/<id>`                 | `<type>/<name>` | none                                                                                                                            |
| `run_succeeded`                                                  | `/runs/<id>`                 | `<type>/<name>` | its `output` when the whole event takes at most 240 KiB and its data nests at most 510 levels, and its `output_bytes` otherwise |
| `run_rejected`                                                   | `/runs/<id>`                 | `<type>/<name>` | its `reason` and `kind`                                                                                                         |
| `definition_created`, `definition_updated`, `definition_retired` | `/definitions/<type>/<name>` | none            | none                                                                                                                            |

Every other field of the record's context is an extension attribute, a scalar each: `caller` from `by` and `definitionversion`, which every run and definition fact carries, and, present when the context holds them, `depth`, `calldepth`, `calledby`, the calling run's id, `triggerkind` and `triggerreference`. A call's reference and run number stay in the ledger.

The event's `type` is the stored type, its `id` the record's id, the message's own id, and its `time` the time the stored event holds; the record's cause and correlation, when it has them, are its extension attributes `causationid` and `correlationid`. `playbookEventOf(record)` is the event a reader of the playbook's history sees for a record: a fact of the playbook as `playbookFactOf` gives it, or an event published to the playbook as its publisher gave it, the `event` of its `event_published`, which is how the workflow host's projector folds both. So an interaction function's answer is the `output` of its `run_succeeded`, with the subject `interaction/<name>`, and an expiry the `reason` `unanswered` and the `kind` `expired`, both with the actor as the attribute `caller`. Deferrals, tool calls, deliveries, the run logs of workflows and every other stream kind yield no event, and so does a record that does not decode as an event of its stream, or whose context is not the one its fact carries, such as a run fact without its definition, so a reader of the ledger never fails on one. A finish names what ran because the decider records the definition in its context (see [Storage](#storage)).

## Tool calls

A capability whose runs call tools, as reasoning does through tool servers, records each call on the run's own stream as it happens, through the `journal` of its context, which answers whether the fact was recorded:

- `tool_call_started`, before the call is sent: its `number` within the run, which the decider gives it as it appends the fact and the journal answers, the `call_id` the model gave it, the `server` and `tool`, the size of its arguments as the playbook keeps them, scrubbed of the server's secrets (`arguments_bytes`), and their SHA-256 digest, the key they are kept under in the ledger's recorded content (`arguments_sha256`), unless the server's `record_content` is `false`, when the fact carries the size alone, and `read_only` where the server marks the tool so;
- `tool_call_answered`, when the tool answered: the `number`, `is_error` when its answer is an error of its own, the size of the protocol answer as kept, scrubbed (`result_bytes`), and its digest where it was kept (`result_sha256`), `shown_bytes` when the model read less than the whole, `duration_ms`, the `jsonrpc_id` sent and `server_request_id` when the server's entry names where it carries one;
- `tool_call_failed`, when it never answered: the `number`, `because` (`arguments_refused`, `server_failure`, `timed_out`, `cancelled`, or `too_large` for an answer past what one call may take), `detail`, `duration_ms`, and the `jsonrpc_id` and `server_request_id` where there are.

The journal is built with the rest of the context in one place, so runs started directly and by a workflow record alike. It keeps the id of the last answer it recorded and of each call it started, for the causes above. It holds a permit per run, so the calls of one step, made at once, append one at a time, as an append is retried only three times on a version conflict. The decider refuses a tool event once the run has ended, however it ended, and a start that names a number other than the next: a call still in flight then keeps a start and no answer, which reads as an outcome unknown. Whether a tool call may have changed something is what keeps a run that called tools from running again under its id (see [Run ids and retries](#run-ids-and-retries)).

## The work of a run that finishes later

A run that finishes later records facts after the call that started it returned, with no request behind them, as an interaction function's deliveries, which the workflow host makes from the projection of open requests, and the replies its reading takes. The run's facts are the playbook's own and those the capabilities composed declare.

**A request is the playbook's.** The deferral's record of a run that waits on a person is a request in one shape for every capability, `RequestRecordSchema`, `{ to, message, answer_schema?, answerer?, reply?, expires_at, requested_at, deliver?, replies? }`, with `reply`, `deliver` and `replies` as JSON objects here, which the capability that reads them types by its own schemas; `isRequestRecord(record)` reads it, and `takesAnAnswer(record)` says whether it takes an answer.

**An answer is one fact.** `request_answered { answer, claimed_for?, reply? }`, its actor and its time its context's, is the core fact of an answer, recorded by the `answer` command: the decider admits it once, on a deferred run whose record is a request that takes an answer, and keeps it as the run's `answer`; the same answer again, by the digest of its canonical JSON, records nothing, and another is `conflict` (`answeredAlready`), whatever the run's status; on a run that is not waiting it is `conflict` (`endedUnanswered`), and on a run whose cancel was asked before it took one it is `conflict` (`cancelledUnanswered`), so an answer and a cancel never both settle a run. `recordedAnswerOf(fact)` reads a recorded `request_answered` as the state keeps it. A capability may state `answerIssues(answer, { work })`, the issues, each a `pointer` into the answer and a `detail`, that an answer its request's schema takes still has for the run that asked, given the run's work, as a prediction build answers only with the candidates uploaded to it; `answer_interaction` refuses an answer with any `invalid_input`, and a capability that states none takes every answer its schema takes. What follows is the capability's: the interaction capability's due work settles its run from the recorded answer, within the host's sweep.

**A capability declares its facts.** A capability states `facts`, `{ onRuns, streams }`: the facts it records on its runs, each made by `declaredFact(type, schema, present)` from the fact's schema, `factOf(type, data, RunContextSchema)` of `@on.auto/operations`, and the words it shows it in, and the presenters of the stream kinds it owns. `composedFactsOf(capabilities)` puts together the facts and the presenters of every capability composed, each capability named by its `type`, and refuses, when the server composes them, a fact two capabilities declare, naming the fact and both capabilities, a fact under a name the playbook records itself, naming the fact and the capability, a stream kind two capabilities declare, naming the kind and both, and a stream kind the playbook records on itself, `runs`, `definitions`, `events` or `reactions`, `playbookStreamKinds`, naming the kind and the capability; `declaredFactsOf(capabilities)` is its facts alone. `runFactsOf(facts.onRuns)` builds from them the run decider, `decider` and `asRead`, whose event schema holds the playbook's own facts and those declared, each in the shape its capability declares, and which admits as work those declared alone. The server composes the facts once over every capability it composes, the workflow's declared facts among them, and hands the work recorder made of them to the capabilities' due work, as it hands the run settler to the workflow host; the presenters, the playbook's own names and the stored types of a status are built from the same composed facts, which the server passes to `playbookOwnNamesOf`, `makeDefinitionPresenters` and `makeDefinitionOperations`, and the run presenter shows a fact the playbook records itself in the playbook's own words before it looks for a declared one. The run decider every core read uses, `runDecider`, reads a fact of any capability as the run's work, without its schema, so a read of a run never needs the capabilities that wrote it, and records no work: what it settles, cancels and journals is the playbook's own, and nothing writes a fact no capability composed declares. A declared fact sits in the run's state, in order, as `work`, `{ type, data, at }`, which the capability's `cancel` decision and its own rules read.

**Work is a command.** The `work` command, `{ type: 'work', fact }`, appends a fact a capability declares while `takesSettlement(state)` holds, and is refused as the run has ended otherwise (`runEnded`), and for a fact no capability composed declares. `workRecorder(ledger, runFacts)` records a `work` or an `answer` command on a run's stream as the playbook's own caller, `playbook:<playbook>`, with the lineage it is given, after the capability's own rule, given the run as it stands, a `WorkRule`, finds nothing to refuse; it records against the version it read, so a fact recorded since makes it read the run again, three times at most, and it answers the id and the time of what it recorded. An address the playbook cannot hold is `conflict`. A capability's due work and its routes record their facts through it. `nestedRunId(runId, reference, run)` is the id of the run another run starts for the call at `reference`, its `run`th, a UUID v5 of the three, so a start asked again is the same run; a workflow's calls and a prediction build's request and approval are named by it. `definitionVersionIn(reader, playbook, { type, name, version })` reads one version of a definition, its source and stripped forms, from the definitions stream of its type, so the due work of a run reads the version the run was started on. `recordedRunIn(reader, address)` and `recordedRunInPlaybook(reader, id)` read a run as it stands, with its input, whether it awaits a settlement, its work, the answer it took and its reaction and call depths, through a reader of the whole ledger or of one playbook, and answer nothing for a run there is not; `runEventOf(data)` reads one stored run event.

## Testing

`@on.auto/definitions/testing` exports `echo`, a small real capability for the tests of this and other packages. Its definition document is a JSON object with a string `greeting`, an optional string `description`, optional `warnings`, a list of strings, and optional `triggers`, which its summary gives back; a run takes a JSON object and answers `{ greeting, input }`. `nothingSaved` is the `SavedDefinitions` of a playbook with nothing active and no content kept, for a check a test runs outside a save. `steppingClock(stepMs, wall)` is the Effect `Clock` of a test that renders: its monotonic time, which a render counts on, starts at nothing and moves by `stepMs` each time it is read, so it stands still with a step of nothing, while it tells the time and sleeps as `wall` does, the real clock unless given. `standingClock` is it with a step of nothing, `standingRenderClock` the render clock that clock reads as, and `onTheStandingClock(effect)` runs an effect on it, so the tests of every capability render on one clock that stands still. `checkingWithin(pool, deadlineMs)` is the pool whose checks at save may take `deadlineMs`, `checksAwaitedAtMostMs`, 30 s, unless given, for the tests that check a document with the compiler in a real worker, which a busy machine can slow past the 2 s a save allows; the refusal at that deadline is held by a pool that answers it, in `src/program-check/save-check.test.ts`. Those tests keep the 10 s a checker's worker may take to start, `mostCheckStartMs` of `@on.auto/workflow-engine`, after which a check ends `busy`: the first check of a pool starts its worker within it on purpose, since the pool's own tests prove that bound with a worker slow to start. `sectionIn(overview, heading)` is the text an overview writes under one of its `##` headings, up to the next, or nothing for a heading it does not write, `overviewTitled(title, ...opening)` an `Overview` of a title and an opening alone, for a test that records a definition's content itself, and `overviewAsRead(definition, held)` the overview of a definition as a read writes it, through the read's own composition, in a playbook that holds it and each `HeldDefinition` given, with its status, description and details.

## Source

`src/shapes` holds the output shapes, their checks and their words. `src/overview` holds the overview of a definition and its writer, the reader of a template among them, which `src/template.ts` serves, `src/overview-words` the sentences of an overview that more than one capability writes, and `src/used-by` the shape of what a definition calls, the reader of who uses a definition and of what it calls, and the overview as a read writes it. `src/index.ts` is the main entry point, `src/document.ts` the entry point of the reader of function documents, held in `src/document`, the checked worker and the words of a refused value in `src/checking`, `src/template.ts` the entry point of the template engine of the capabilities, held in `src/template`, and `src/testing/index.ts` the entry point of the test support. `src/capability` holds the declaration of a capability and the list of known capabilities. `src/registry` holds the definitions of a capability in a playbook: a definition, the events and commands of its stream, and the decider and its rules. `src/runs` holds a run: its events, commands, state, decider and rules, its size limits, and `runSettler`. `src/operations` holds the eight operations that change and read definitions and runs, `start_definition_version` among them, and how they load and record them. `src/reading` holds `list_runs` and `get_run_history`, `src/analytics` `get_playbook_analytics` and `runOutcomeMapping`, and `src/presenting` the presenters of the four stream kinds. `src/events` holds the events of a playbook: the shape of a CloudEvent, `publish_event` and the stream of a published event, and the playbook's own facts as events. `src/tool-calls` holds the journal of a run's tool calls, and `src/run-work` the work a run records after its start: the decisions on its calls, the recorder of its outbound calls, the words and accounts of its deliveries and deferral, and a run as it was recorded. `src/testing` holds what the tests share, with the capabilities of the tests in `src/testing/capabilities` and their clocks and patient checks in `src/testing/time`. `operations` depends on `capability`, `overview`, `plain-language`, `reading`, `registry`, `run-work`, `runs`, `shapes`, `tool-calls` and `used-by`, and not on `events`; `reading` on `analytics`, `cancellation`, `capability`, `plain-language`, `presenting`, `run-work`, `runs` and the fields and `get_run` of `operations`; `analytics` on `capability` and the fields of `operations`; `events` on `capability`, `registry`, `run-work`, `runs` and the command metadata of `operations`; `presenting` on `capability`, `events`, `overview`, `plain-language`, `registry`, `run-work` and `runs`; `used-by` on `events`, `overview`, `overview-words`, `registry` and the words of `capability`; `overview-words` on `overview`, `plain-language` and the words of `capability`, and on the types alone of `used-by`, an edge that type stripping erases, so nothing that runs goes from the words to `used-by`; `overview` on `capability`, `overview-words`, `plain-language`, `shapes` and `template`; `registry` on the words and the stripped forms of `capability`; and `runs` on `registry`, `shapes` and the work decisions of `run-work`.
