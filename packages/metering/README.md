# @on.auto/metering

The credit arithmetic and admission contracts shared by Cloud and customer-hosted Auto Runtime. A credit is one million integer microcredits. Provider amounts retain decimal precision until the approved tariff converts them; reservations round upward and settlements round once to the nearest microcredit, with ties to even.

This package owns run identities and accounting rules. Customer accounts, payments, private signing keys, and credit issuance belong to the Studio account service. Customer-funded model and compute resources do not incur an Auto resource surcharge.

A run charge is identified by account, deployment, playbook, logical run and charge kind. Retries retain that identity. Provider receipts are identified by account, provider and provider request, so a response and a later gateway log cannot become separate resources.

Quotes bind a run to its definition version, input digest, enforced-limit digest, tariff, deadline and maximum spend. The bound calculator includes sequence and parallel paths, finite repetitions and each branch's category maxima. Resource fractions are aggregated before the reservation rounds upwards. The caller must derive and enforce these bounds from the actual run configuration; a quote hash alone is not spending approval. Approval and the committed reservation belong to the account authority. Unknown resource bounds, unbounded repetitions, oversized plans and unsafe accounting amounts are refused.

`reserveFromLots` chooses eligible source lots for platform, resource and development charges, subject to source expiry and the remaining Cloud Free daily allowance. It finds a complete feasible allocation and prefers earlier expiry, then issuance time, then lot ID. A residual flow network can move tentative category assignments when a later restricted lot requires it. Exact integer preference weights make the source priority lexicographic, including when Free lots share a daily capacity limit. An insufficient request returns no partial reservation and does not mutate the supplied snapshot. The caller commits the result and the daily quota under the same account revision. Snapshots are bounded to 1,024 distinct lots; the service must surface an oversized snapshot for maintenance rather than omit source lots or assume no credits exist.

The allocator is checked against an independent exhaustive enumeration of 5,292 small funding cases in addition to the source, expiry and eligibility examples. A local Node run with 1,024 one-credit lots and a 512-credit request took 390 ms; this is a local sizing observation, not a cloud throughput guarantee.

The implementation is being delivered with the Runtime and Studio pricing-and-metering PRs. The complete approved design and requirement-by-requirement verification record live in Studio's `docs/design/`. Passing the arithmetic suite alone does not establish completion of runtime enforcement or account-service integration.

`licenseVerifier` validates account-service entitlements with the maintained `jose` library, a fixed Ed25519 algorithm, a dedicated token type and audience, and a locally supplied trusted public key set. It never discovers signing keys from a token or requires a signing secret. Trust is scoped to one issuer and deployment ring, with up to eight overlapping public keys for rotation. Runtime release configuration must supply this trust from its protected distribution; customer-editable settings cannot define billing authority.

Entitlements bind account, customer, license, installation, cluster and installation-key fingerprint. They name supported capabilities, tariff and policy versions, generation, issue/validity times, refresh and offline deadlines, and grant/allocation references. Customer-hosted model development is always cloud-only. A standard entitlement requires daily refresh and has at most seven days of validity; an explicitly signed Enterprise offline package can have up to 366 days. No token creates wallet quantities: offline spend still requires a separately recorded source allocation.

`licenseClaims` produces validated claims for the private account-service signer. `readLicenseClaims` checks structure and policy only; it does not authenticate a token. Runtime admission must use `licenseVerifier` with its stored account/cluster/key binding, last trusted generation and trusted clock. Verification rejects altered signatures, wrong keys/algorithms/issuers/audiences/types/rings, stale generations, unsupported policies and expired offline authority. Clock rollback detection, allocation accounting and installation activation remain separate integration requirements.

Installation activation and refresh use a separate Ed25519 proof type. Public installation keys contain only their curve/type/coordinate; private or extra JWK fields are refused. The fingerprint is the canonical public JWK SHA-256 thumbprint in hexadecimal. `installationProofPayload` binds the issuer, ring, purpose, challenge identity, account/cluster/installation, credential, generation, public-key fingerprint, nonce, five-minute validity and request digest. `verifyInstallationProof` verifies the installed public key, signature, proof type, fingerprint, exact payload and server time. The account service must additionally consume the nonce transactionally, check current credential/installation state and retain the original result for retries; signature verification alone is not replay protection.
