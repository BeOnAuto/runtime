# @on.auto/tool-servers

How a playbook reaches the outside world: the tool servers of its org, MCP servers and HTTP APIs described by an OpenAPI document, from two sources, the entries the operator configures and the connections people add to the org (`@on.auto/connections`), and the tools a run is offered from them. The server reads the settings, composes the source of connections and makes one `ToolAccess` at its composition root, which it gives to both capabilities that reach a tool: the reasoning function adapter opens a run's tools through it when a reasoning function names `tools`, and runs the model's tool loop over what it gets back; the interaction function adapter delivers a request, reads the replies to it and tells its party how to answer with one call of one tool each, the tools its function names; and five operations reach the playbook's tool servers through it, `search`, `introspect`, `validate`, `dry_run` and `execute`, the last calling one tool as a run would, by hand (see [Five tools over the tool servers](#five-tools-over-the-tool-servers)).

## Entry points

- `@on.auto/tool-servers`: the settings, with `ServerEntrySchema`, the schema of one entry, `readEntry`, the reading of one entry of the file, with which `@on.auto/connections` reads a connection's entry, its credential placed, into the connection's `ServerSettings`, and whose context's `placedValues`, the values the runtime places by the name of their placeholder, stand in the entry's header and query values once the entry as written is judged, `serverNameProblems`, the check of a server's name, with which it checks a connection's name, and `servedFieldsOf`, the playbooks, tools, `record_content` and `request_id` an entry is served by, as it writes them or by default where it leaves them out, with which it builds the serving of every connection it lists, and `isPinnableUrl` and `headerNamePattern`; `@on.auto/providers` takes the server part of a provider's entry from the fields of `ServerEntrySchema`, as a connection's entry does, and checks a provider's name with `serverNameProblems` and its addresses with `isPinnableUrl`; `namesEveryTool`, whether a tool reference names every tool of its server with `*`, as a reasoning function's `tools` may; the contract of a source of connections, `ConnectionSource` and its types, which `@on.auto/connections` implements, and `noConnections`; `describedToolServers`, `makeToolAccess`, the five operations, `defineSearch` and its org twin `defineSearchInOrg`, with `ProviderOffering` and `OfferedProvider`, the contract of the providers offered to a caller, which `@on.auto/connections` implements, `defineIntrospect`, `defineValidate`, `defineDryRun` and `defineExecute`, `handCallPresenter`, which shows a call made by hand, and the facts of a call that `@on.auto/definitions` builds the run's events from. The access loads the MCP client, its OAuth providers and `node:child_process` (`src/access/linked-access.ts`) through a dynamic import when a run first opens its tools, a search or a read first asks a server or `execute` first calls a tool, so a server that never does any of them never loads them: the server's start loaded 55 files and 0.94 MiB more with them (measured 2026-10-06 with a module load hook, 1,241 files against main's 1,186). Without them it loads 73 files and 176 KiB of this package, the five operations, the reading of the settings of the three types, `describedToolServers` and the naming of the servers of an org and of its connections among them (measured 2026-10-16 with a module load hook over both entries, against 65 files and 155 KiB on main the same day); the reading of an OpenAPI document, its decoding and the tools derived from it (`src/openapi`, `described-servers.ts` and the types aside) load through a dynamic import too, when an entry of type `openapi` is described at start.
- `@on.auto/tool-servers/policy`: the pure helpers a caller needs without connecting to anything (`toolReferenceOf`, `toolReferenceShape`, `writtenOf`, `namesEveryTool`, `runBoundMs` and `runIdKey`). It loads no transport code, so the reasoning function adapter, which parses a function's `tools` and bounds its run, does not load the MCP client wherever it is bundled; it takes `ToolAccess` as a type only.
- `@on.auto/tool-servers/testing`: the fake server and the helpers of the tests (see Testing).

## Settings

`readToolServerSettings(environment, { modelProviders, documentsDirectory? })` reads `TOOL_SERVERS`, JSON, which the server also writes from the configuration file's `tool_servers`: an object with one entry per server, keyed by the name a function writes in `server/tool`, which holds no two hyphens together and none at the end (`endsAtTheFirstSeparator` of `src/names/model-facing-names.ts`), since the model sees a hyphen as an underscore and a tool as `server__tool`. Each entry is one of three types, `mcp`, a remote MCP server spoken to over Streamable HTTP, `stdio`, an MCP server the runtime runs as a process, and `openapi`, an HTTP API described by an OpenAPI document, taken from `url`, `command` or `document` when `type` is left out; nothing in a function says which type it names. Beside `servers`, the settings keep `referencedVariables`, the name of each variable the entries refer to, one with a fallback among them, from which the server learns the variables it reads for itself without decoding `TOOL_SERVERS` again. `ServerSettings` carry `connection`, `null` for an entry of the file and a connection's id for the settings of a connection's link. Each entry carries the tools of its server, in `ServerSettings` as `allowed`, the names or `null`: the tools of the server a function may name and `execute` may call, each named as the server lists it, without the server's name and without `*`. Every tool of the server when it is left out, so an entry always allows at least one tool. It is the operator's one list, for runs and for calls made by hand alike.

The list is checked at start (`src/settings/tool-lists.ts`), at the pointer of the name and never with a value: a name that is not a tool name, such as `graph/search`; `*`, which is what leaving it out means; a name listed twice; and an empty list. Whether a server has a tool is learned from the server, or from its document, never from the settings.

| Field            | Of           | What it holds                                                                                                                                                                              |
| ---------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `type`           | every type   | `mcp`, `stdio` or `openapi`; taken from `url`, `command` or `document` when left out                                                                                                       |
| `url`            | mcp          | The http or https URL of a server spoken to over Streamable HTTP                                                                                                                           |
| `headers`        | mcp, openapi | Headers sent with every request, for an openapi server only what its document's security schemes do not place; the value of a reference is a secret, a value written out is not            |
| `auth`           | mcp, openapi | OAuth client credentials: `issuer`, `client_id`, `client_secret` or `private_key` with `algorithm`, and `scope`                                                                            |
| `command`        | stdio        | An installed, pinned command, never a package downloaded at start such as `npx -y`                                                                                                         |
| `args`           | stdio        | The arguments of the command                                                                                                                                                               |
| `env`            | stdio        | The whole environment of the process, the value of a reference a secret: it inherits nothing else, so give `PATH` or an absolute `command`                                                 |
| `document`       | openapi      | The OpenAPI document, 3.0 or 3.1, in JSON or YAML: an https URL, an http URL on a loopback address, or a path relative to `documentsDirectory`, the configuration file's, that stays in it |
| `base_url`       | openapi      | Where the calls go, in place of the first server the document names; required when it names none or one relative to a file. An https URL, or an http URL on a loopback address             |
| `query_params`   | openapi      | Query parameters sent with every call that the document's security schemes do not place; the value of a reference is a secret, a value written out is not                                  |
| `security`       | openapi      | The credential of each security scheme of the document the entry gives, by the scheme's name (see [The credentials of an HTTP API](#the-credentials-of-an-http-api))                       |
| `org`            | every type   | The org the server serves, a list of orgs, or `*` for every org, required; in `ServerSettings` as `orgs`, the ids or `null` for every org                                                  |
| `playbooks`      | every type   | The playbooks it serves within each of its orgs, the same ids in each; every playbook of each org when left out, and refused beside `*`                                                    |
| `allowed`        | every type   | The tools of the server a function may name; every tool of the server when left out                                                                                                        |
| `record_content` | every type   | Whether the arguments and answers of calls are kept whole, scrubbed, in the playbook's recorded content; `true` when left out, and `false` keeps their sizes alone                         |
| `request_id`     | every type   | The response header, or for an MCP server the key of the metadata of a result, in which the server carries its own id of a request, recorded with each call                                |

A secret is a value resolved from a `${NAME}` reference to the environment when the settings are read, the whole value of a security scheme, the credential after the scheme of a header's resolved value, so that `Authorization: ${GRAPH_HEADER}` holding `Bearer <key>` keeps `<key>` as well, an `auth` credential, or a token minted from one, each kept once however many places hold it (`secretsOfEntry` in `src/settings/entry-references.ts`), and nothing else: a header such as `X-Region: production-eu` or an environment value such as `MODE=production` is not, and is never scrubbed. The scrubber (`src/bounds/secrets.ts`) replaces each secret as written, as it is written inside a JSON string, where a quote, a backslash or a line break in it is escaped, as it is written inside JSON twice, as in a result whose text content is itself JSON, as an address carries it, form-encoded in a query and percent-encoded in a path, as in an answer that echoes the address it was asked at, and in base64, as a Basic credential carries it, so a secret in the recorded arguments or result of a call is caught too. One set of secrets serves a tool access, its runs and its calls made by hand alike: `makeToolAccess` builds it once from the settings with `secretsOfServers`, beside the `runtimeSecrets` of its options, secrets of the runtime that no server's settings hold, such as those of the clients the server reads from `connections.registered_clients`, and hands it to the links and to `preparedCall`, and the token source of an entry with an `auth` block puts each token it mints in it with `replace(server, token)`, under the entry's name, or a connection's id, where the token takes the place of the one before it; the values of a connection's credential join the set with `keep` once its server is prepared, before anything of a call to it is recorded. The set keeps the secrets of the settings for as long as the access lives and, for each entry, its current token and the one that token replaced, since a call in flight at a renewal may still carry the previous token in a result recorded a moment later; so a minted token is scrubbed until the token after the one that replaces it is minted. A value shorter than 8 characters is never scrubbed, since replacing it would erase ordinary words in every message; a reference that resolves to one is still a secret in every other sense, and the operator gives a server a key at least that long. Only `headers`, `query_params`, `security`, `env` and `auth` may hold a reference: one in `url`, `command`, `args`, `document` or `base_url` is refused with its pointer, since a key in an argument shows in the listing of the machine's processes and the URL of a server or of a document is no place for a credential. A value that looks like a credential written out is refused, as a model gateway's key is, and so is a password in a `url`, and a user, a query value or the part of an argument after its `=` that looks like one, as in `--key=sk-live-...`; an argument is judged by what it holds, never by the name it is given, so `--token-file=/run/secrets/notes` is accepted, while a parameter of a URL's query is judged by its name as a key of `query_params` is, so `?api_key=...` is refused where it holds no reference. The settings also refuse an entry with none of `url`, `command` and `document` or with more than one, the fields of another type, a name outside 1 to 32 lowercase letters, digits and hyphens starting with a letter, the name of a model provider or gateway, a missing org, an org or playbook that is not an id, an `Authorization` header beside an `auth` block, an issuer, a `base_url` or a `document` URL that is not https (or http on a loopback address), a `document` path that is absolute or leaves its directory, a header the runtime sets itself (`src/settings/reserved-headers.ts`), `accept`, `content-type`, `content-length` and `host` on every entry, and `mcp-session-id`, `mcp-protocol-version` and `last-event-id` on an `mcp` one, which the MCP client sets, a query parameter without a name, and the refusals of `allowed` above; a key an entry does not hold is refused as any unknown key is. Each problem names its setting and a JSON pointer, never a value; `ToolServerSettingsInvalid` carries them all.

Nothing is learned from a server when the settings are read: they are read without the network and without spawning anything. `describedToolServers(settings, { fetch?, readMs?, reportLeftOut })` then reads, at start, the document of each `openapi` entry and derives its tools (see [An HTTP API as a tool server](#an-http-api-as-a-tool-server)), answering `ToolServers`, the settings with each API described, which `makeToolAccess` takes, or failing with `ToolServerDocumentRefused`, whose problems name each entry and the place in its document; it leaves the other types as they are and, with none of type `openapi`, runs without suspending, so a test may run it synchronously. The server calls it as it composes its services and stops when it fails, and logs at WARN each operation `reportLeftOut` reports.

## A run's tools

`makeToolAccess(settings, { clientInfo, content, reportServerMessage, runtimeSecrets?, connections?, reportLeftOut?, fetch?, now?, timing?, traceMeta? })` holds one link per configured server and one per connection of an org it has used (see [The connections of an org](#the-connections-of-an-org)), each client it opens naming itself to its server as `clientInfo`, the name and version the server passes in from its release, and answers:

- `configured`: whether any server is configured or the source of connections takes connections, since a run may then call a tool; it makes `run_definition` and `execute` destructive.
- `takesConnections`: the source's own, whether people may add connections, which the words of `search` follow when no server serves a playbook.
- `open(context, references)`: the tools of one caller, for its id, org, playbook and journal and the metadata its calls carry, and the `server/tool` references it names, among the servers of the file and the connections of its org alike. A run gives its run id as `auto.on/run_id` (`runIdKey`, which `@on.auto/tool-servers/policy` exports).
- `named(address, references)`: whether every reference names a server that serves the playbook, ready, and a tool its operator allows, without opening a client of any server: the result of `namedLinks`, then, for a connection, its credential read and the operator's rules checked, as its link is made. An interaction function's run checks it at its start. It answers an effect, since the org's connections are read from the ledger.
- `preparedCall(call)`: one call made ready, `{ fields, called }` over one reading of the org's servers: `fields`, the start of the call, the server, the connection's id where it is one, the tool, the size of the scrubbed arguments and, where the entry keeps content, their digest, the arguments kept whole and scrubbed in the playbook's recorded content first, which a delivery, a read or a telling records before it calls; and `called`, the effect of the call itself, as `callOnce` makes it. A connection's server is prepared before `fields` are made, so its credential has joined the secrets and the start is scrubbed of it before any link to it is made.
- `callOnce(call, runCall?)`: one call of one tool for an interaction function, its call, a delivery, a read or a telling (see [One call](#one-call)).
- `lookUp(address, reference)`: `named` for the one reference and, as an effect it runs only when asked, the listing of the server it names, over one reading of the org's servers, which `introspect`, `validate` and `dry_run` read.
- `listServers({ org, playbook }, named?)`: the servers that serve the playbook, or every server that serves the org, by naming it among its orgs or by `*`, when `playbook` is `undefined`, or only the one named, the file's and the org's connections alike, with their tools, the playbooks each serves, as its entry's `playbooks` or `['*']`, and for a connection `connection`, its id, and `provider`, the name of the provider a connection was added from, `null` for one given by hand and for an entry of the file, which the five operations read (see [Five tools over the tool servers](#five-tools-over-the-tool-servers)).
- `listServersInOrg({ org, playbook }, named?)`: what `listServers` answers, as `servers`, and beside it `settings`, the fields of every server that serves the org, whatever `playbook` and `named` keep, the file's and the org's connections in every state, from the same reading of the org's servers and with no client opened, by which the org's `search` judges which providers a server serves already.
- `close()`: ends every session and stops every process, those of connections among them, when the server stops.

`open` fails with `ToolNotOffered` when a reference names a server not configured for the run's org and playbook (`tool_server_not_configured`), a tool the operator does not allow (`tool_not_allowed`), a tool its server does not list (`tool_not_listed`), or a connection that is not ready (`connection_pending`, `connection_broken` or `connection_not_allowed`), and with `ToolServerFailed`, whose tag is `tool_server_failed`, when a server cannot be used (`unreachable`, `failing`, `rate_limited`, or `key_refused` when it answers HTTP 401 to the key the runtime gives it). Otherwise it connects to each named server, lists its tools once, and keeps that listing for the run: a `list_changed` notification changes nothing, and a call to a tool the server no longer has is a tool error. `server/*` offers every listed tool the operator allows.

`RunTools` offers each tool, its description and input schema scrubbed of the secrets of every server as the listing's are, under its model-facing name, `server__tool` for a tool of either kind, with characters outside letters, digits and underscore mapped to underscores, cut to 64 characters with an 8-character hash when longer or when two names would collide. A numeric suffix resolves any remaining collision, so every tool offered in a run has a distinct name. The cut and the suffix take only from the end, and a server's name has no `__` and no `_` at its end once mapped, so every name splits at its first `__` into the server and the rest; a tool a run offers that is not a tool server's, such as the `json` tool a provider makes of a JSON output, holds no `__`, which keeps the two apart. Its description is cut to 4 KiB and the server's input schema is unchanged. It also says whether the calls have ended (`callsEnded`, `ended`, `ending`), whether the run called any tool (`calledAny`), whether every tool it called is one its server marks `readOnlyHint` (`calledOnlyReadOnly`), which decides whether a run that cannot finish ends `tools_unfinished` or `effect_unknown`, and the tools it used in words (`usedInWords`), and lets the run's servers go (`close`).

A call of an offered tool:

1. is refused as a tool error, never sent and never recorded, when the run's calls are spent, its arguments are too large, or it repeats a call made twice already;
2. records `tool_call_started` through the run's journal, which answers the number the run's record gave the call, and is not sent if that fails, the sequence of this step and the next two being the one `journalledCall` (`src/calls/tool-caller.ts`) that `callOnce` shares;
3. is forwarded as a `tools/call` request through the client's `request`, which checks the answer against the protocol's call result and never against an output schema the server declares, so a tool that broke its own schema still answers, with the metadata the opener gave, a run's id under `auto.on/run_id`, within its deadline, waiting out a 429 whose `Retry-After` fits the longest wait, opening a session the server forgot once, and restarting a `stdio` process that exited once per run;
4. records `tool_call_answered` when the tool answered, or `tool_call_failed` when it did not, unless the run was cancelled meanwhile;
5. answers the model: text content as text, structured content only when there is no text, other content as a one-line placeholder, an `isError` result as a tool error, and a failure as a tool error naming the server, all scrubbed of the entry's secrets and minted tokens. A server's `instructions` never reach the model. The answer is whole unless it would not fit the room the caller gives the call, the model's context window less what the conversation holds so far, as the reasoning capability counts it: then it is cut where it stays valid JSON, closing what the cut left open (`cutWhereValid` in `src/bounds/structural-cut.ts`), or at a code point for text that is not JSON, with a note of how much was left out, and `tool_call_answered` records what the model read in `shown_bytes`. A call given no room, as where the catalog does not know the model's window, is read whole and the provider decides.

The call answers a `CallReply`: the model reads its `text` and `isError`, and beside them it carries what was recorded, the `outcome`, `resultBytes`, the size of the whole answer, `shownBytes` where the model read less, `durationMs` and `serverRequestId`, with `not_sent` as the outcome of a call refused inside the playbook or whose start could not be recorded. `RunTools.answeredBytes()` adds up the size of every answer of the run, which the reasoning capability names when a provider refuses a request as too long.

A server failure is also reported to the operator through `reportServerMessage`, bounded and scrubbed, naming the run by `run_id` or a call made by hand by `call_id`, whichever the opener's metadata gives, and the fifth ends the run's calls, with `ending()` saying `failing` or `rate_limited`.

## One call

`callOnce({ org, playbook, reference, input, meta, longestRetryWaitMs? }, runCall?)` (`oneCall` in `src/one-call`) makes one call of one tool for an interaction function: the call of a function that asks a system, a delivery of a request, a read of the replies to it or a telling. It refuses what a run's opening refuses, in the same words: `namedLinks` refuses a server not configured for the playbook's org and playbook, or a tool the operator does not allow, with no client opened; the link of a connection refuses one that is not ready, or whose document cannot be read; then it takes the server's client within the open bound, 10 s (`takenWithin`), letting go of a client that opens later, starts a `stdio` process that exited again within the same bound (`boundedSlot`), lists the server's tools as a run's opening lists them (`listedThrough` of `src/listing/server-listing.ts`), within that bound too, and refuses a tool the server does not list. A caller that passes `runCall`, `{ callId, journal }`, has `tool_call_started` recorded on its run once the tool is found and before the call is sent, and `tool_call_answered` after, through `journalledCall`, the sequence a run's calls follow; a start the journal does not record ends the call path with a defect, and nothing is sent. A caller that passes none records what it records itself, before calling, with the fields `preparedCall` gives, and after, from what its `called` answers. The call waits out a 429 whose `Retry-After` fits the caller's `longestRetryWaitMs`: none for a delivery, a read or a telling, whose schedules honour the wait, and `toolBounds.longestRetryWaitMs` for an interaction function's call. It opens a session the server forgot once, within the open bound. The call carries the metadata its caller gives, as a run's calls do: a call or a delivery gives the run's id under `auto.on/run_id`, a delivery the delivery's id under `auto.on/delivery_id`, the same on every attempt of one request, and a read or a telling its own id under `auto.on/conversation_call_id` (`runIdKey`, `deliveryIdKey` and `conversationCallIdKey`, which `@on.auto/tool-servers/policy` exports). It answers the call whole, `CalledOnce`:

- `unopened`, sent nowhere, refused as `tool_not_offered`, with the `because` and words of `namedLinks`, of a connection that is not ready or, for a tool the server does not list, `tool_not_listed`, or as `tool_server_failed`, when the server could not be reached, no client opened or its tools were not listed within the bound, with the `because` and words of a run's opening, cut at 1 KiB and scrubbed;
- `answered`, with the outcome `result` or `tool_error` and the fields of `tool_call_answered` in `answered`, or `server_failure`, `timed_out` after 30 s, `cancelled`, `arguments_refused` or `too_large` and the fields of `tool_call_failed` in `failed`; the words of a failure cut at 1 KiB and scrubbed, the wait a 429 asked for in `retryAfterMs`, the hints the server gave the tool in its listing as `annotations`, and for a result what the tool answered whole, its `content` blocks and its `structuredContent`, read back from the answer once it is scrubbed of the server's secrets.

What a tool answered is read two ways, in `src/bounds/tool-results.ts`: `resultText`, what a model sees, text content as text and structured content only when there is no text, and `answerDocument`, the document a call's `read` points into, the structured content, else the first text block parsed as JSON, else that text, or none when the tool answered neither.

## The playbook's calls in a conversation

The reads and tellings of an interaction function are calls of the playbook's own, on a stream of their own under the playbook, `conversation-calls/<id>` (`src/own-calls`), decided by the one decider of such calls, `conversationCallDecider`: `replies_read`, one fact appended after a read that found a reply, carrying the fields of the start and the answer of its call, the conversation, the cursor, the replies considered, taken and refused, and the wait a 429 asked for, or `reading_failed` after one that failed, with `because`; and for a telling `telling_started`, before it is sent, and `telling_succeeded` or `telling_failed` after, caused by it. `repliesReadOf`, `readingFailedOf`, `tellingStartedOf` and `tellingEndedOf` build them. `conversationCallPresenter` shows them in a playbook's events, `arguments` and `answer` read from the recorded content where each is within 2 KiB and otherwise their sizes, in words that name the conversation and the tool; no recall function folds them and no trigger takes them.

## Five tools over the tool servers

Five operations at the playbook's scope, under `/tool-servers`, reach the servers that serve the playbook, of either kind and from either source, named as an agent gateway names its five tools, so an agent has one vocabulary whichever it talks to: `search` finds the tools, `introspect` reads one whole, `validate` checks arguments against its input schema, `dry_run` answers what a call would check, and `execute` makes the call. The first four are queries under `playbook:read` that reach outside (`openWorldHint` over MCP), list the servers they need through `listServers` and record nothing; `validate` and `dry_run` are routed by `POST`, since their `arguments` are an object a query string cannot carry, and stay queries. `validate` is defined with `defineHttpOperation` and so served over HTTP alone, since `dry_run` reports the same check of the arguments in its `arguments`; the other four are also MCP tools, and `dry_run` is read-only and idempotent there. `execute` is a command under `playbook:write` for every tool, since a call reaches a system under the entry's credential, which is an act of the playbook. A server is passed on scrubbed: what it writes, the names, descriptions, the keys and values of input schemas and the words of a failure, reaches the caller with every entry's secrets and minted tokens scrubbed out before it is cut, and the operations add no header, environment value, URL, command or credential of their own.

`listServers` lists as `open` does, through the same link (`takenAndListed` in `src/listing/server-listing.ts`), under the same bounds: it takes a client, lists the server's tools within `openMs`, and lets the client go, so an `mcp` session no run holds is ended once the listing has its tools, and a `stdio` process is started when no run started it and kept until `close()`. Listings made at once share the link's client, as runs do, and one listing of an `mcp` server no run holds costs it five requests when the server issues a session id: initialize, its notification, the stream `GET`, `tools/list` and the `DELETE` that ends the session. A server that issues none gets four, since the MCP client sends the `DELETE` only for a session it was given. A listing interrupted meanwhile still lets its client go once the server answers. The tools are those `server/*` would offer a run (`offeredOn`): what the server lists that its entry's `allowed` names, or all it lists when `allowed` is left out, in the server's order, each with its `name`, its `description` cut to 4 KiB as a run cuts it, its input schema as `input_schema` and the hints its server gives it as `annotations`, `readOnlyHint`, `destructiveHint`, `idempotentHint` and `openWorldHint` as booleans and only when it gives any (`src/listing`). A server that cannot be used is `unavailable` with the words `ToolServerFailed` would carry, cut to 1 KiB (`toolBounds.failureBytes`, the bound a delivery's detail has too), and the other servers are listed beside it. When no server serves the playbook, it answers an empty list without loading the MCP client; an HTTP API is asked nothing, since its document is the list.

### Searching the tools

`defineSearch(access)` makes `search`, `GET /tool-servers/search` relative to the playbook (`src/search`). Its input is `terms`, one string of up to 8 words of up to 64 characters separated by spaces, since a query string carries no list, `server` and `only`, `read` or `write`; it answers `{ servers, tools, scopes }`. Each server, sorted by name and a file's entry before a connection of its name, is `{ name, type, record_content, connection?, provider, tool_count }`, `connection` the id of a connection and absent for a file's entry, `provider` the name of the provider a connection was added from and `null` for one given by hand and for a file's entry, its count of the tools its entry allows that `only` keeps, or `{ name, type, record_content, connection?, provider, unavailable, because }`, `key_refused` when it did not accept the key the runtime gives it (HTTP 401), which only the operator can put right, `connection_pending`, `connection_broken` or `connection_not_allowed` for a connection that is not ready, its words its own, otherwise `failing`, `rate_limited` or `unreachable`; each tool is `{ server, tool, summary, read_only }`, the summary the first sentence of its description, at most 300 characters, and `read_only` whether its server marks it `readOnlyHint`; `scopes` names the servers searched. Without `terms` it answers every tool while the servers offer at most 100 together, in the order of the servers and of each server's list, and the servers alone, `tools` empty, when they offer more, with words that say to search by terms. With `terms`, each tool is scored (`scoreOf` in `src/search/search-scoring.ts`, the one scorer of a name, the names of arguments and a description, which ranks the providers of the org's search too): the terms and a tool's name, the names of the properties of its input schema and its description are split into words at anything but a letter or a digit and at case changes, so `listCustomers`, `list_customers` and `list.customers` hold the same two words, compared whatever their case; each word of the terms counts 3 where it is a word of the name, 2 where it is a word of a property's name and 1 where it is a word of the description, and the tools with a score are answered best first, those of one score by name and then by server, at most 100. `only: read` keeps the tools marked read-only, `only: write` the others, before the count and the rule of 100. `server` keeps only the server of that name, and asks no other; a name that no server serving the playbook has is `invalid_input` at `/server`, whose words say so and to call it without `server`. Its words name each server and its tools, twenty at most, or the tools found best first, and say which servers could not be asked, a connection that is not ready in its own words; a playbook with no server is told that whoever runs the server sets one up and, on a runtime whose access `takesConnections`, that a person adds one to the org as a connection, or, where the org's search lists a provider, that a person connects a provider it lists, as the give-tools guide says; the org's search, which `/mcp` and the org endpoint serve beside `add_connection`, names it, `with add_connection where your tools include it`, and the playbook's, which a playbook endpoint serves without it, does not.

`defineSearchInOrg(access, lookUpPlaybook, offering?)` makes the same name at the org's scope, `GET /tool-servers/search` relative to the org, an org query permitted by `org:read` or `playbook:read`, as `list_playbooks` is, since a key that may read a playbook may see what serves it. Its input adds an optional `playbook`: without it, it searches every server that serves the org, by naming it in `org` or by `*`, each with `playbooks`, the playbooks it serves, as the listing gives them, `['*']` for an entry that leaves them out; with it, the servers that serve that playbook, as the playbook's own search has them, each with `playbooks` too, and the words of the playbook's search. A key limited to some playbooks is shown in `playbooks` only the playbooks it may access, and `['*']` as it is; the dispatcher refuses it the search of the whole org, since an org operation that takes `playbook` checks the caller's access to the playbook it is given, and none is given, with the detail `The caller may access only some playbooks of this org; name one of them in playbook`. Given a playbook, it first looks it up with `lookUpPlaybook`, a `PlaybookLookup` that needs `OrgReader` and fails with `NotFound`, since the org's playbooks are the registry's and the dispatcher looks up no playbook of an org operation: the server gives `foundPlaybook` of `@on.auto/playbooks`, so a playbook the org does not have is `not_found` in the words of the playbook's own route, and no server is asked. A name no server of the org, or of the playbook, has is `invalid_input` at `/server`, whose words name the org or the playbook. Over MCP, `/mcp` offers this operation in place of the playbook's, under the same name, its `playbook` its own and optional (see the api README's [playbook argument](../api/README.md#over-mcp)), the org endpoint offers it too, and a playbook endpoint offers the playbook's.

The org's search also answers `providers`, the providers offered to the caller that no server of the org serves yet, each `{ name, title, description }` (`src/search/found-providers.ts`). `offering`, a `ProviderOffering`, answers for a caller the providers it may connect, or nothing where it may not add a connection, and offers none where it is left out. The server gives the search `makeProviderOffering` of `@on.auto/connections`, whose README says which providers it offers, and to whom. Whatever `playbook` narrows the servers to, a provider is served, and so left out, when a server among the `settings` that `listServersInOrg` reads names it as its `provider`. Only a connection made from it does, pending, connected or broken, since an entry of the file carries no provider. Without `terms` they are every such provider by name while there are at most 100, and none when there are more; with `terms`, those `scoreOf` scores, the words of a provider's name and then of its title counting as a name's and its description as a description, best first and then by name, at most 100. `providers` is present, and empty when every provider offered is served, exactly where the offering answers the caller and `server` is not given, and absent otherwise, so a caller who may not add a connection is answered no `providers`; the playbook's search never answers it.

`pnpm --filter @on.auto/tool-servers measure:search` (`measure/search-over-a-document.ts`) searches an HTTP API of 500 operations, each with a summary and two query parameters, 500 times after 50 to warm up, through the dispatcher as a caller would. Measured on 2026-10-13 on a 16-core machine, Node 26.10.0, at a load average of 6 to 23 from other work on the machine, twice: with two terms that match every operation, so 100 tools are scored, sorted and answered, a median of 2.91 and 2.93 ms and a p95 of 3.16 and 3.20 ms; without terms, the server alone, 1.69 and 1.68 ms and 2.03 ms.

### Reading one tool

`defineIntrospect(access)` makes `introspect`, `GET /tool-servers/{server}/tools/{tool}`, `defineValidate(access)` makes `validate`, `POST /tool-servers/{server}/tools/{tool}/validate`, and `defineDryRun(access)` makes `dry_run`, `POST /tool-servers/{server}/tools/{tool}/dry-run` (`src/tool-reads`). `introspect` and `validate` find the tool in the order `execute` checks it (`namedToolOf` in `src/tool-reads/named-tool.ts`), through `lookUp`, which reads the org's servers once for both: its naming, as `named` checks it without opening a client, refuses a server that does not serve the playbook, a connection that is not ready and a tool the operator does not allow as `unavailable` of the kind `tool_not_offered`; the listing of that server refuses a server that cannot be used as `unavailable` of the kind of `ToolServerFailed`, a connection whose document names an address the rules do not allow as `tool_not_offered` with `connection_not_allowed`, and a tool it does not list as `tool_not_listed`. Their words, and `execute`'s, end with what `search` shows, from their own `remedies`, where a function's refusal speaks of the function. `introspect` answers `{ server, tool, description, input_schema, annotations? }`. `validate` takes `arguments`, required and at most 16 KiB as JSON, and compiles the tool's input schema with the runtime's JSON Schema compiler, `compileJsonSchema` of `@on.auto/json-schema` (`src/tool-reads/argument-checks.ts`): it answers `{ valid, issues }`, each issue `{ path, message }` at the pointer of the argument, at most 20 and then one saying how many more there are, as the compiler bounds them; a schema the compiler cannot take, such as one with `pattern`, answers `valid: null` with one issue at the root saying why. It compiles with `otherFormats: 'unchecked'`, so an argument out of one of the six formats the compiler checks is an issue at its pointer, and a `format` other than those, as an OpenAPI document's `int64` or `binary`, is left unchecked while the rest of the schema is checked. `dry_run` refuses a server that does not serve the playbook, and a tool its server does not list, as `introspect` does, and answers for the rest what `execute` would check: `would_run`, `needs`, `playbook:write`, `caller_may`, whether the caller holds it, `playbook_retired`, whether the playbook is retired, as `PlaybookLifecycle` of `@on.auto/operations` gives it, `allowed`, whether `named` passes, `read_only`, `null` when the tool's listing was not read, for a tool the operator does not allow or a server that could not be asked, `arguments`, checked as `validate` checks them, `null` when none were given, and `server`, `{ reachable: 'yes' }` or `{ reachable: 'no', because }` from the listing it just made (`src/tool-reads/dry-run-seen.ts`). `would_run` is the caller's permission, a playbook that is not retired, the operator's list and the server's answer: arguments the schema does not take do not make it false, since `execute` checks no arguments and the tool answers an error of its own.

### Calling a tool by hand

`defineExecute(access)` makes `execute`, `POST /tool-servers/{server}/tools/{tool}/execute` relative to the playbook, a command under `playbook:write` that reaches outside and may change something outside while the access is `configured`, a server set up or connections taken, which makes it destructive over MCP (`src/execute/execute.ts`). It calls one tool of one server with `arguments`, `{}` when left out and at most 16 KiB as JSON, refused at `/arguments` by its input schema, as a run of a reasoning function would call it, and answers what that run's model would see and the document a call reads: `{ call_id, server, tool, outcome, text, answer?, result_bytes, duration_ms, server_request_id?, called_at }`, `succeeded` however the tool answered, with the outcome `result`, `tool_error`, `server_failure`, `timed_out` or `too_large`, and `result_bytes` the size of the answer as kept, scrubbed. `text` is `resultText` and `answer` `answerDocument` of the same answer, scrubbed alike, `answer` left out when the tool answered neither structured content nor text and when it takes more than 64 KiB as JSON.

A call reaches the tool in the one way a run does, through `ToolAccess`: it opens the tools with one reference, under a context whose id is the call's, whose journal records the call and whose metadata carries the call's id under `auto.on/call_id` (`callIdKey`) and no run's id; `namedLinks` refuses a server that does not serve the playbook or a tool the operator does not allow before any client opens, and the opening refuses a tool the server does not list. Then it makes one `call`, admitted, recorded, forwarded, scrubbed and cut as a run's, within `callMs` and `executedAnswerBytes`, and lets the tools go through the `close` of the tools it opened once that call has settled, also when the caller goes away meanwhile: the call is aborted, nothing is answered or recorded of it, and the session is ended once the forwarded call settles; `execute` waits for the call to answer, not for the session to end, so a failure of the call, such as a start the ledger refuses, is still reported as an incident while a server slow to end its session does not hold the answer. A call of an `mcp` server no run holds costs it six requests, initialize, its notification, the stream `GET`, `tools/list`, `tools/call` and the `DELETE`, or five when the server issues no session id; a call and a search made at once share one session. A server failure is reported to the operator under `call_id`.

### What a call made by hand records

A call made by hand is the same happening as a call a run makes, so it records the same facts, `tool_call_started` and then `tool_call_answered` or `tool_call_failed`, with the data of `CallStartedSchema`, `CallAnsweredSchema` and `CallFailedSchema`, on a stream of its own, `tool-calls/<call_id>` (`src/hand-calls`), with the caller as `by` and an acted context, no run. A run's facts carry `number`, the call's place in the run, by which its answer finds its start; a call made by hand carries none, since one stream holds one call, and the stream kind tells the two apart. They are appended through `PlaybookWriter` by the journal of the playbook's own calls, `ownCallJournal(kind, place)` (`src/own-calls`), with the one decider of such calls, `ownCallDecider`, whose turns are the stream kind's, a start once and an ending once after it, built by the same builders from the same recording as a run's, so content is kept and scrubbed where and as a run's is, `record_content` and `request_id` honoured, and the start is recorded before the call is sent: a start the ledger refuses fails the call with an incident and nothing is sent. The ending names the start as its cause. `handCallPresenter` shows them in a playbook's events, `arguments` and `answer` read from the recorded content where each is within 2 KiB and otherwise their sizes: "Someone allowed to change the playbook called the search tool of graph by hand.", "The tool answered." and "The tool failed at its server.", in the words of a run's calls. The reasoning capability declares the stream kind `tool-calls` with this presenter; no recall function folds these facts and no trigger takes them, since the host follows the facts of `runs` and `definitions` alone. `search`, `introspect`, `validate` and `dry_run` record nothing.

## The credentials of an HTTP API

The document's `components.securitySchemes` and the `security` of the document and of each operation decide what a call sends (`src/openapi/security-schemes.ts`). An entry gives a credential by the scheme's name under `security`, a map read at start like `headers`, whose every value holds a reference, one written out refused with the advice a credential written out gets, and is a secret whole as well as its reference's value, so a Basic credential built of a user and a referenced password is scrubbed in its base64. `requirementOf` reads an operation's alternatives, its own `security` or else the document's: the first alternative every scheme of which the entry gives is the one a call sends, as `credentials` of its `ApiOperation`, and no other, unless the operation needs a header the entry's `headers` do not name, when the first alternative the entry gives whose `apiKey` schemes place every such header is the one sent; an `apiKey` in a header or the query goes in its header or query parameter, an `http` scheme of `bearer` as `Authorization: Bearer`, of `basic`, `user:password`, as `Authorization: Basic` and its base64, and an `oauth2` or `openIdConnect` scheme is given by the `auth` block alone, whose token a call sends as a bearer only when the alternative it sends names such a scheme. An empty requirement, an empty alternative, or a document that requires nothing sends no credential; an operation the entry gives no alternative of is left out, its reason naming the alternatives. `securityProblemsOf` refuses the entry at start, at `/<entry>/security/<scheme>`, `/<entry>/headers/<name>`, `/<entry>/query_params/<name>` or `/<entry>/auth`, for a scheme the document does not declare, an `apiKey` in a cookie, an `http` scheme other than `bearer` and `basic`, `mutualTLS`, an `oauth2` or `openIdConnect` scheme given a value, a `basic` value without a colon, a header or query parameter of the entry that a scheme it gives also places, and an `auth` block whose document declares no `oauth2` or `openIdConnect` scheme. The scopes of an `oauth2` requirement are the operation's; the token source asks for `auth.scope` as for an MCP server, so the operator sets it to cover what the operations require.

## An HTTP API as a tool server

An `openapi` entry is a `ServerLink` like the others (`src/clients/server-links.ts`), whose client is the bridge (`src/openapi/api-client.ts`): it answers `listTools` and `call` of the client contract (`src/clients/server-client.ts`), so the rest of `ToolAccess`, the bounds of a run, the scrubbing, the recording, a call's facts and the failures counted against a run are the same code for an MCP server and for an HTTP API, which the shared behaviour suite of `src/access-testing` proves by running the same tests over the fake of each.

At start `describedToolServers` reads the document, from its URL through the server's outbound fetch, without the entry's headers and following no redirect, which is refused naming the entry and its status, since the document chooses where the calls go, within 10 s and 4 MiB, or from its file, refuses one that is neither JSON nor YAML or nests deeper than 128 levels, and decodes it with a schema of the parts the bridge reads alone (`src/openapi/api-document.ts`): the version, the servers, the paths with their operations, parameters and request bodies, and the `components` they refer to. Swagger 2.0 and any version but 3.0 and 3.1 are refused at `/swagger` or `/openapi`, and a part of another shape at its place. A path that does not begin with `/` is refused at `/paths/<path>`, since joined to `base_url` it would extend its host or its port, and so is one with a `.` or `..` segment, written plainly, percent-encoded or split by a tab or a line break, which an address drops, or with a `?` or a `#`. Each operation becomes one tool (`src/openapi/api-tools.ts`):

- its name is the `operationId`, each character outside the grammar of a tool name an underscore and cut at 128 characters, or, without one, the method and the path with the leading `/` dropped, `{x}` as `x` and `/` as `_`, in lower case, read in one pass however many braces the path holds, as the variables of a server's address are, as `get_invoices_id` for `GET /invoices/{id}`; two operations of one name refuse the document, naming both places, as do more than 500 operations;
- its description is the operation's `summary` and `description`, cut at 4 KiB as descriptions are;
- its input schema is one object, closed: each path and query parameter by its name with its schema, and the parameter's `description` where the schema has none, required when the parameter is, as a path parameter always is, and `body` with the schema of the request body when its media type is `application/json` or ends in `+json`, required when the body is. A parameter or a body the operation refers to under `components` is followed, a chain that leads through more than 8 other references refused, the operation's parameter winning over the path's of the same name and place; a parameter given no schema takes any value;
- every schema of `components/schemas` the parameters or the body refer to, and every one those refer to, is copied once into the tool schema's `$defs` and every `#/components/schemas/<name>` rewritten to `#/$defs/<name>`, the one form of reference the runtime's compiler reads, so the schema stands alone for the model and for a check; a reference to anything else, or to a schema the document does not have, refuses the document at its place (`src/openapi/schema-translation.ts`, `src/openapi/input-schemas.ts`). A schema that takes more than 64 KiB as JSON with what it holds under `$defs`, the bound of the runtime's compiler (`jsonSchemaLimits` of `@on.auto/json-schema`), leaves its operation out, its size added up from the size of each component, measured once, before the schema is ever written out whole, and a document whose tools take more than `httpAnswerBytes` listed, the bound of an MCP server's listing, is refused at `/paths`;
- a document of 3.0 has its schemas translated to JSON Schema 2020-12, which the model and the compiler read: `nullable: true` adds `null` to the `type` the schema states, once, and to its `enum`, and is left out with no effect where the schema states no `type`, beside a `$ref`, whose siblings 3.0 ignores, and when it is `false`; a boolean `exclusiveMinimum` or `exclusiveMaximum` becomes the number of its `minimum` or `maximum`; `example` becomes the one value of `examples`, or joins those written beside it; and every other keyword, `format: binary` among them, is kept as written;
- its annotations are `readOnlyHint` for `GET` and `HEAD`, `destructiveHint` for `DELETE`, `idempotentHint` for `GET`, `HEAD`, `PUT` and `DELETE`, and `openWorldHint` for every operation, each only where it holds, so the operator's `allowed`, `search` and a run's read-only calls read an API's tools by these names and hints as they read an MCP server's.

An operation that a call could only fail or send in another form is offered as no tool: `TRACE`, which `fetch` refuses, a `GET` or a `HEAD` that takes a body, which neither can carry, a path parameter of a `style` other than `simple` and a query parameter of a `style` other than `form`, `spaceDelimited`, `pipeDelimited` and `deepObject` among them, whatever its schema, since a call sends a list in a path joined by commas and in a query as repeated keys, or as one key of items joined by commas where the document writes `explode: false`, as the form style does, and a scalar alike either way; an operation that needs a cookie, or a header that neither the entry's `headers` name nor an `apiKey` scheme of the alternative its call sends places, the names compared without regard to case as header names are, and a header parameter named `Accept`, `Content-Type` or `Authorization` ignored, as the OpenAPI specification says; and one that takes an object in its query, its schema or the component it refers to of type `object`, takes a body of another media type, or has two inputs of one name, `body` among them, or whose input schema is over its bound: `reportLeftOut` names it, as `createInvoice (POST /invoices)` or `POST /invoices`, and says why (`src/openapi/left-out.ts`), a header it needs in words that say the entry's `headers` can give it, or, for a header the runtime sets itself (`headersTheRuntimeSets` of `src/settings/reserved-headers.ts`), that the runtime sets it and neither a function nor the entry can give it; the words of a style it does not send name the style alone. A required header the entry's `headers` name is no input of the tool, and its call sends the entry's value as it sends every header of the entry. `describedApi` (`src/openapi/api-description.ts`), which describes a file's entry and a connection alike, gives the rule the names of the entry's headers once, from the settings it describes, beside the security and the auth the entry presents; the headers the credentials of the alternative a call sends place join them (`headersPlacedBy` of `src/openapi/security-schemes.ts`), and where the entry gives no alternative, the headers the `apiKey` schemes of its alternatives name, so that the operation is left out in the words of its security. The calls go to `base_url`, refused with a query or a fragment, or to the first server the document names, refused with either too, its variables given their defaults and a URL relative to where the document was read resolved against it, either without the slashes it ends in, which are dropped once where it is read (`withoutTrailingSlashes` of `@on.auto/config`); a document that names none, names one relative to a file, or one that is neither https nor on a loopback address, is refused at `/<entry>/base_url`.

A call (`src/openapi/api-requests.ts`) fills each path parameter, encoded, a list joined by commas, and the query, form-encoded, a list as repeated keys, or as one key whose items are joined by commas where the document writes the parameter with `explode: false`, a comma inside an item encoded and the commas between them not, and `null` or an empty list left out, then the entry's `query_params` and a credential the operation's alternative places in the query; sends the body as JSON in the operation's media type with the entry's headers, the credentials of the alternative it sends and `accept: application/json`, and no `_meta`, which an HTTP API has no place for; and refuses, as `arguments_refused` and without sending, an argument the operation does not take, a path it cannot fill, a path argument that is empty or holds a `/`, or makes a segment `.` or `..`, which would take the call out of the operation's path, an object outside the body and a missing body the operation needs. Before it is sent, the address is read as a URL and must have the origin of `base_url` and a path at or below its path; one that does not is a defect of the bridge, `AddressOutsideBase`, a failing server to the run, and nothing is sent, so the entry's headers and query never reach another host, port or path. The answer (`src/openapi/api-answers.ts`) is read within the call's deadline and `httpAnswerBytes`, counted as an MCP server's answer is (`counted` of `src/clients/observed-requests.ts`, which the observing fetch of the MCP client is built on: the observing fetch itself finds a request's JSON-RPC id in the body it sends, which a call of an HTTP API has none of): JSON, `application/json` or a type ending in `+json`, is the tool's structured content and its text, a `text/*` answer its text, an empty answer no content, and any other media type, or none, one block noted and not shown, `[binary content (image/png), not shown]`, as content of another type from an MCP server is. A 401 is a key the server refused, minted once more with an `auth` block before it is, a 429 waits out a `Retry-After` that fits the longest wait, as an MCP server's does, and a 5xx is a failing server, each counted toward the run's failures (`AnsweredStatus`, which the failure mapping of `src/clients/server-failures.ts` reads as it reads the MCP client's errors); a 3xx is an error result naming the redirect and its status, since the call is sent with `redirect: 'manual'` and nothing goes to the `Location`, which would carry the entry's headers and token to an address its settings do not name (a call of an MCP server goes through the SDK's transport, which this leaves as it is); any other answer, a 404 among them, is an error result carrying the body's text, a problem document where the API answers one, or the status when it has no body, since to an HTTP API a 404 is an answer about the resource and not a lost session. The answer carries no JSON-RPC id, so the facts of a call of an HTTP API have `jsonrpc_id: null`, and `request_id` names a response header. Listing an HTTP API asks it nothing: the document is the list.

## The connections of an org

A connection is a tool server a person added to an org, a provider of `@on.auto/providers` by its name or a server given by hand, which `@on.auto/connections` keeps; a connection made from a provider whose document lies beside the providers' entries is read with `readEntry` and the providers' folder as its `documentsDirectory`, as a file's entry is read with the configuration's, so its document is a file the link reads, and every other connection's document is a URL. The access takes them from a source, `connections` of its options, a `ConnectionSource` (`src/org-servers/connection-source.ts`), and knows nothing of the ledger: `connectionsOf(org)` answers each connection of the org that is not removed, with its id, `serving`, its name, `type` `mcp` or `openapi`, `provider`, the name of the provider it was added from or `null`, `orgs`, `playbooks`, `allowed`, `record_content` and `request_id`, and its state: `connected`, with `server`, an effect that reads its credential and checks the operator's rules and answers its `ServerSettings` and `reaches`, or `unready`, with the `because` and words of a connection that is pending or broken. `takesConnections` says whether people may add connections. Without a source, `noConnections`, the access has the file's servers alone.

Every way in reads the servers of an org the same way (`src/org-servers/org-access.ts`): the file's entries, then the org's connections, each an `OrgServer` with the settings it serves by, the connection's id or `null` as `connection`, and its link. Within an org a name resolves to the file's entry first: a connection whose name an entry of the file holds, for this org or another, which a later edit of the file can give it, is unavailable, `connection_not_allowed`, in the sentence `add_connection` refuses that name with, `takenByTheConfiguration`, followed by what to do, `remove it and add it again under another name`, and is never called (`withTheFileFirst` and `namedIn` in `src/org-servers/org-servers.ts`, the naming in `src/org-servers/org-naming.ts`).

Each operation reads the org's connections once: the source of `@on.auto/connections` replays the org's stream of connections from the ledger on every reading, as the playbook registry replays the org's playbooks on every status it answers, and keeps nothing between readings, so what an operation reads is what the ledger holds as it starts. A listing, a check of names, an opening and one call each read once; a delivery, a read or a telling reads once for its start and its call together, through `preparedCall`, and `introspect`, `validate` and `dry_run` once for their check and their listing, through `lookUp`. A connection added, removed or broken meanwhile is seen at the next operation.

A connection's link is made when a run, a listing or a call first takes it, and kept by its org and id while the connection stays connected (`src/org-servers/connection-links.ts`), in two steps. The source's `server` reads the credential and checks the rules once for each connection a process holds, and its answer, ready or refused, is kept with the link, but for `connection_broken`: the source records a break, so the next reading lists the connection broken, and where it could not record it the next use reads the credential again and records the break again; within one operation, a check, a start and a call, a connection is prepared once whatever its answer. Once it is ready, the values of its credential join the access's secrets. Then the link: an `openapi` connection's document is read and described with the bounds and refusals `describedToolServers` applies to a file's document, through the connection's fetch, its tools left out reported through `reportLeftOut` (`src/org-servers/connection-linking.ts`). The description fails with one of two tagged errors: `DocumentUnread` (`src/openapi/document-reading.ts`), for a document that could not be read, since its address did not answer in time, answered an error or answered a page that is neither JSON nor YAML, such as a proxy's error page, which is `failing` in its words and read again when the connection is next used; and `DocumentRefused` (`src/openapi/described-api.ts`), for a document refused for what it is, too large, nested too deep, or a description the bounds or the checks of its security and its servers refuse, which is `failing` in its words and kept refused for as long as the process runs, so it is read once. A file's entry takes the problems of either alike, since its documents are read once at start; and a document whose first server, where `base_url` is left out, is an address the rules do not allow is `connection_not_allowed` in the rule's words. The link is the `serverLink` of a file's entry, its settings the connection's with `connection` its id, so the bridge, the MCP client, the bounds, the scrubbing, the recording and the failures are one code for both sources. `named` takes the first step alone and connects nowhere. A preparation or a link that fails in a way the runtime did not foresee, such as a source that dies, is that server's alone: it is listed and refused as `failing` in the failure's words, scrubbed, beside the servers that answer, and is let go, so the next use prepares or links it again. A connection the source no longer lists as connected, because it was removed or broken, has its link stopped at the next reading of its org's servers, by a listing, an opening, a check or a call, and every link is stopped at `close()`, each settled whatever another's stopping does. A removed connection's name may be taken by a new connection, which has a new id and a new link.

The values of a connection's credential, its `secrets` and its `auth` credential, join the access's one set of secrets once its server is prepared (`Secrets.keep`), before its start is recorded and before its link is made, and are scrubbed for as long as the access lives, as a reference's value is for the file; a token minted for a connection is held under its id, so two connections of one name in two orgs never replace each other's tokens. Every request of a connection's link goes through `fetchWithin` (`src/org-servers/fetch-within.ts`), a `FetchLike` that takes a string or a `URL` and the fields its caller gives: the URL is checked with the connection's `reaches`, the rules' answer to its host, and refused before it is sent with `HostRefused`, carrying the rule, and the request is sent with `redirect: 'manual'`, so the runtime's `fetch` follows no redirect. `failureOf` finds `HostRefused` among the causes a client wraps it in, through `causesOf` of `@on.auto/outbound`, the walk `codesOf` takes too, eight causes at most, and answers it as `connection_not_allowed` in the rule's words alone, so a request to a refused host, the authorization server's and a redirect's among them, is refused as the rules refuse it, never as a failing server. The bridge sends every call with `redirect: 'manual'` and only to its base URL's origin and path, and answers a redirect as an error result; the MCP client follows a redirect only within the origin of the request, keeping its method, and sends each hop through the connection's fetch, which checks it again; its token and metadata requests go through the same fetch. So no request of a connection reaches a host the rules do not allow, redirects included.

The bounds are those of the file's servers: of a run, a call, a listing and a document, and a connection's `mcp` link shares its session among the runs and listings that hold it as a file's does. The connections of an org, at most 50 that are not removed, as `@on.auto/connections` bounds them, bound its links.

## Clients

Each entry has one link. An `mcp` link opens a session when a run or a listing first needs it, shares it with every run and listing that holds it while it is open, and ends it explicitly when the last of them lets it go. Session termination is bounded by the open bound, `openMs`; the client closes even if the remote DELETE never answers. A `stdio` link starts its process on first use and keeps it until `close()`; it spawns the command without a shell, with the entry's `env` and nothing else, reports each line the process writes to stderr (at most 100 lines of 2000 characters), and takes at most 4 MiB of output at once: past it the link closes the process and every call it was answering ends `too_large`. Closing a process ends its input, and kills it through its handle after two seconds.

An `openapi` link holds no session: its client is the document's operations and the entry's headers and query parameters, made when a run, a listing or a call first takes it, and taking it asks the API nothing.

With an `auth` block, tokens come from the MCP client's client-credentials or private-key provider, with the issuer pinned: the client sends the credential to no authorization server whose metadata names another issuer. For an `mcp` entry the authorization server is found through the server's protected-resource metadata, as the MCP client does; for an `openapi` entry the provider is given the issuer as the authorization server it already knows (`discoveryState`, the hook of the MCP client for one), so its metadata is read from the issuer by OAuth authorization server metadata or OpenID Connect discovery, since an HTTP API publishes no protected-resource metadata: the client still asks the API for it, at the base URL's path and at its root, once for each token it mints, and goes on without (`src/clients/token-source.ts`). One token is minted for every concurrent run, renewed a minute before it expires (or halfway through a shorter life), and minted again once when the server answers 401; a second 401 is a failure. Every remote request goes through the `fetch` given, the server's outbound fetch, the read of a document, the reads of metadata, the requests of tokens and the calls alike, so `HTTPS_PROXY` and `NODE_EXTRA_CA_CERTS` apply, the `User-Agent` the server's fetch sets where a request sets none, `auto-runtime/<version>`, the name of the runtime's command and the version of the release the server announces to an MCP server in `clientInfo` (`withUserAgent` of `@on.auto/outbound`, given to `describedToolServers` and `makeToolAccess` in `packages/server/src/composition/served-tool-access.ts`), reaches each of them, a `User-Agent` among an entry's `headers` taking its place on the entry's calls alone (`src/access/outbound-requests.test.ts`), and a certificate the server does not trust is a fixed message.

The MCP client has no logging option. The errors it meets, such as a line from a process that is not JSON-RPC or a stream it could not read, reach the client's `onerror`, which reports them through `reportServerMessage` as the messages of their server, scrubbed. They are bounded as the stderr of a `stdio` process is: at most 100 of 2000 characters for each process started or session opened, then one line saying the rest is not shown. The few warnings it writes to the console about how it was configured are left on stderr: catching them would mean patching the global console of the whole server, which every other library writes to as well.

## Telemetry

`traceMeta`, when given, is called as each call of a tool of an `mcp` or `stdio` server is sent, and its keys are added to the call's `_meta`, where the caller's own keys win (`tracedClient` in `src/clients/mcp-client.ts`, applied where `openerOf` opens those clients): the server's gives the current trace as `traceparent`, so a call carries it whether a run, one call or `execute` makes it. An `openapi` call takes none, since its HTTP request carries `traceparent` as a header from the server's instrumentation of `fetch`. A call of a tool of an `mcp` or `stdio` server, made once or by `execute`, is a `tools/call <tool>` client span (`traced` in `src/one-call/traced-calls.ts`, given the type of the server the call opens), naming the server in `auto.on.tool_server`, a connection's id beside it in `auto.on.connection_id`, and how a call that did not end in a result ended in `error.type`, and measured in `mcp.client.operation.duration`, in seconds, whose attributes leave the connection's id out, so a histogram's series stay as few as the servers' names. One call that was never sent names why in `auto.on.tool_call.because`; `execute` leaves a call refused at its opening to its operation's span. An `openapi` call makes no such span, since its HTTP request is already the span beneath the operation. The package takes no OpenTelemetry dependency; its tests read the spans with `recordingTracer` of `@on.auto/operations/testing`.

## What is recorded

The arguments, as `JSON.stringify` writes them, and the protocol answer are scrubbed of the entry's secrets in place, keys, values and numbers alike, and the scrubbed text is the one text a fact describes: its size, measured once, is `arguments_bytes` or `result_bytes`, and where the entry keeps content it is kept whole through the `RecordedContent` port of `@on.auto/operations`, as its UTF-8 bytes of the media type `application/json`, before the fact that names it is appended, and its SHA-256, its own address, is `arguments_sha256` or `result_sha256`, so a fact never names content that is not there. The recording puts the text with that digest expected, so the port checks the bytes against it and, when the playbook already holds the digest, writes nothing, however large the answer (`KeepContent` keeps a text and answers the digest the port kept it under). The digest is present exactly when the content is kept: an entry with `record_content: false` gives its facts the sizes alone, since a digest of a document a reader can guess would confirm the guess, and nothing digests a text that is not kept, so the digest of what was received, before the scrub, is nowhere. When the secrets change between two receipts of one answer, as when a token is minted, each scrubbed text is kept under its own digest and each fact names its own. What the model read is `resultText` of the kept answer, cut at `shown_bytes` where the fact has it; the reply's `resultBytes`, the run's answered bytes and `execute`'s `result_bytes` are the same size of the kept text.

`tool_call_started` carries the call's number in the run, the id the model gave it, the server, the connection's id as `connection_id` where the server is a connection, and the tool, the size of the arguments and their digest where they were kept, and `read_only: true` when the server marked the tool `readOnlyHint` when it was listed. A call ends with one of two facts. `tool_call_answered`, when the tool answered, carries the number, `is_error`, the size of the answer and its digest where it was kept, `shown_bytes` when the model read less than the whole, the duration and the JSON-RPC id. `tool_call_failed`, when it did not, carries the number, `because` (`arguments_refused`, `server_failure`, `timed_out`, `cancelled`, or `too_large` for an answer past the transport's cap, which is not counted among the server's failures since the server answered), the words of the failure as `detail`, cut at 1 KiB and scrubbed, the duration and the JSON-RPC id. An entry with `request_id` adds the server's own id of the request to either. The fields of the facts are written once, as the effect schemas `CallStartedSchema`, `CallAnsweredSchema` and `CallFailedSchema`, which the package exports, and `@on.auto/definitions` builds the run's events from them, adding the call's `number`; who and when are the context of the message, as for every fact. Every fact of a call that names its server names the connection beside it, `connection_id`, where the server is a connection: `tool_call_started` of a run and of a call made by hand, `telling_started`, `replies_read` and `reading_failed` of the playbook's own calls in a conversation, and an interaction function's `delivery_started`; the facts that follow a start find it by its number or its stream, so a history stays unambiguous once another connection takes a removed one's name.

## A manual run against an agent services gateway

The tests never call a real gateway. Once, before relying on one, run a reasoning function against it by hand:

1. In the gateway, create an application for the playbook and an API key for it, and attach a policy that allows the reads the run needs and denies one field you can name.
2. Export the key as `GRAPH_API_KEY` where the server runs. It never goes in the configuration file.
3. Configure the gateway as an `mcp` entry:

   ```yaml
   tool_servers:
     graph:
       url: https://gateway.example.com/mcp
       headers:
         Authorization: Bearer ${GRAPH_API_KEY}
       org: acme
       playbooks: [sales]
       allowed: [search, introspect, validate, execute]
   ```

4. Start the server and create a reasoning function in that playbook with `tools: [graph/*]` whose prompt asks a read-only question the policy allows, including the denied field.
5. Run it with `run_definition`, then read what the run did with `list_playbook_events`, given its `run_id`.

Check that the run succeeded; that its history shows a `tool_call_started` and a `tool_call_answered` for each call, the denial answered with `is_error` and the model's answer saying the field was withheld, and that `get_event` reads each answer whole; that the gateway's audit shows the calls made by the application, each carrying the run's id under `auto.on/run_id`; that `run_definition` for the same `run_id` answers the same run again; and that the server's log holds no key or token.
