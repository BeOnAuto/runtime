## The runtime's own keys

The runtime keeps keys of its own in its secret store, beside the secrets it keeps for others, and names each by a fact in a stream of the runtime's and of no org, `runtime/own-keys`, as `@on.auto/connections` names the clients it registers dynamically in `runtime/client-registrations` (`src/secrets/own-keys.ts`, beside the composition of the store the key is read from, which `src/database/ledger-stores.ts` opens, moves, rotates and logs right before). The one fact, `own_key_kept { purpose, secret_id }`, by the runtime, `by: runtime`, is folded by purpose, the latest last, and the decider, `ownKeysDecider`, refuses a second for a purpose that has one, `conflict` of the kind `taken`, `The runtime keeps a key for retry_state already`. There are three purposes: `retry_state`, the key that signs the state an MCP client sends back when it retries a call, as [`@on.auto/api`](../api/README.md) says; `content_address`, the key that signs the address a person or a browser follows to the bytes a playbook keeps, as [`@on.auto/identity`](../identity/README.md#content-addresses) says; and `link_code`, the key under which the code a person sends back to link an account at another service is kept, as an HMAC (below).

At start, once the secret store is open and rotated, `ownKeysOf` reads the key of each purpose in turn, `retry_state`, `content_address`, then `link_code`, the same way: it folds the stream, and where no key is recorded for the purpose it keeps 32 random bytes in the store, as their base64, and records the fact, which the ledger appends under the version of the stream it read; where the record is refused because another server recorded one first, it forgets the row it kept and folds again, taking that one. It then reads the row, logs under a secret manager `The runtime read the key it keeps for retry_state in AWS Parameter Store under <prefix> in <region>`, or `for content_address`, with the annotations `own_key`, the purpose, and `own_key_id`, the secret's id, which names its parameter, `<prefix>/<own_key_id>`, and gives the API `retryStateKeys` with the key of `retry_state` as `current` and no `previous`, and the routes of the content at a signed address, `contentAddressRoutes`, the key of `content_address`, so every server that shares the ledger signs under the same keys, and a rotation of the secrets key wraps each again and leaves it as it is. A row it cannot read stops the start as an `OwnKeyUnavailable`, named as the server's other start failures are, in words that name the purpose, where secrets are kept as the start's log names it (`secretsKeptBy`), the store's words and the ways out: `The key the runtime keeps for retry_state cannot be read under the key that SECRETS_KEY holds: <the store's words>. A row that is gone, `… is no longer in the secret store, so the server does not start`, or, under a secret manager, `… is no longer in AWS Parameter Store under <prefix> in <region>, the region AWS_REGION names, so the server does not start`, naming the variable the region was read from, since another region or account holds no parameter of the ledger's, one that holds something other than 32 bytes, and a key the store cannot keep at the first start, `… cannot be kept under the key that SECRETS_KEY holds, so the server does not start: <the store's words>`, stop it too; the store is closed before the start fails. A deliberate reset of the runtime's own keys is not offered yet. Nothing of the key is logged, and no key is derived from another.

## The issuer of subject tokens

A runtime whose `PUBLIC_URL` is an https URL is the issuer of the subject tokens its connections exchange at other services (see [Subject tokens](../identity/README.md#subject-tokens)), at `{PUBLIC_URL}/oidc`, whether or not it signs people in; a runtime with no `PUBLIC_URL`, or an http one on the loopback, issues none and answers no path under `/oidc`, so nothing can be exchanged there (`subjectTokenIssuerOf` of `src/subject-tokens/served-subject-tokens.ts`). The issuer `/oidc` is not the server's own authorization server, which answers its metadata and its key set at the root, under a key of its own.

Its key is an RSA key of 2048 bits, signing as `RS256`, kept in the secret store as its JWK and named by a fact in a stream of the runtime's and of no org, `runtime/subject-token-signing-key`, as the runtime's own keys are (above), so every server that shares the ledger signs with the one key and a rotation of the secrets key wraps it again and leaves it as it is (`src/subject-tokens/subject-token-key.ts`). The one fact, `subject_token_signing_key_kept { secret_id }`, by the runtime, `by: runtime`, folds to the key recorded last. At start, once the secret store is open, `subjectTokenKeyKeptBy` folds the stream and reads the secret it names; where none is recorded it makes a key, keeps it and records the fact, which the ledger appends under the version of the stream it read, and the decider, `subjectTokenKeyDecider`, refuses it where another server recorded one first, `conflict` of the kind `taken`; this server then forgets the secret it kept and folds again, taking that one. Where the secret named is gone from the store, or sealed under a key the store no longer has, the key is lost: the server makes a new one and records it in place of the one lost, which the decider takes only while the stream still names the lost one, so of two servers that find it lost at once one replaces it, as the authorization server replaces its own signing key. A subject token is checked by the key set a service fetched or was given, so a new key is uploaded again where a service was given the key set as a file; the server makes its key once and changes it only when it is lost. A secret store that cannot keep or read the key stops the start with the store's own failure.

`src/composition/sign-in-and-stores.ts` opens the issuer beside the stores, and `src/composition/composition-root.ts` serves its two documents beside the client the server registers itself: `GET /oidc/.well-known/openid-configuration` and `GET /oidc/.well-known/jwks.json`, each JSON for any caller with no credential, `access-control-allow-origin: *`, so a page of any origin can save the key set as a file, and `cache-control: public, max-age=300`. Nothing else is served under `/oidc`, and no path gives anyone a token.

## The attempts it makes, and the runs whose process is gone

Each process of the server holds every attempt of a run it makes under a lease in the ledger's database, so a run whose process dies, runs out of memory or is killed is ended or resumed by itself rather than left `started` for ever. The composition root makes one id for the process, a random UUID at each start, which it gives the workflow host as `holder` and the live attempts of the application layer as theirs (`attemptHoldingOf`), with `WORKFLOW_SWEEP_INTERVAL`, so the lease lasts three sweeps and at least 30 seconds from its last renewal; it is not a setting of its own. `liveAttemptsOver` of `src/composition/process-layers.ts` wraps the core's `LiveAttempts` (`src/attempt-leases/leased-attempts.ts`): each attempt, `attempt` or `outliving`, takes its lease before its start is recorded, names it by its fencing token as the core tells it (`acquired`), and lets it go as it ends, or hands it over where its run is still started, as an attempt the server stopped while it ran, and also where the attempt was cut short, interrupted or dying, before it named its token, since its start may already be recorded and only the run's facts tell, which the sweep reads; a lease the database could not take, name or let go is reported as an incident and the attempt runs all the same. A process that stops closes its live attempts before its other work, and its stop begins there: the holding records that it began (`stopping`), and only then are the attempts interrupted and their leases handed over, while the host, which stops later, takes up no run of a gone holder once the stop began, nor one it handed out before (`src/attempt-leases/attempts-work.ts`), so a lease the process hands over as it stops is left for the next server, never taken up by the process that could make no attempt of it any more. The workflow host renews the process's leases at every sweep, whether it runs the workflows or stands by.

The host that runs the workflows ends what a lapsed or handed-over lease of another process names (`src/attempt-leases/attempts-work.ts`, `gone-holders.ts`), through the core's `deadAttemptEnder`, the run's own correlation as its lineage. A run that outlives its call and that no workflow's step made, a reasoning run a client or a trigger started, is resumed at once: the host takes a lease for it, then makes its next attempt with `make_next_attempt`, a playbook operation of its own that no transport serves (`src/attempt-leases/next-attempts.ts`), as the caller who started the run, read again by its id as the server would take it now (`callersByIdOf` of `@on.auto/identity`, `src/attempt-leases/attempt-holding.ts`; the playbook itself for a trigger), with `attemptDied`, so the core claims the attempt and the dispatcher's check decides whether that caller may still run it. The host lets the lease of the process that is gone go only once it holds the resume's own. It hands the resume's lease over where the next attempt was refused because this process is stopping, an interruption the dispatcher's error boundary passes through (`src/dispatch/error-boundary.ts` of `@on.auto/operations`), so the next sweep, here or on another server, takes the run up again; a next attempt that dies once it has begun hands over the lease it shares with the resume, as any attempt cut short does. Every other answer of the dispatch lets the resume's lease go, a failure among them, since the dispatcher answers a defect as `failed`: so a dispatch that fails before the next attempt takes its lease leaves the run started with no lease. Whether a run is one the server resumes is decided before any attempt, from the kind of its starter's id alone (`readsAgain` of `callersByIdOf`): a key in a server that takes credentials or admits nobody, the local developer in local mode, or the playbook itself. A run whose starter is of no such kind, a signed-in person, whose grant comes with each token and is kept nowhere, or the local developer outside local mode, is never resumed: the host names its attempt to the ender with `noNextAttempt`, and the run ends as a run within its call does, in the ender's words for what it had done. A key no longer listed is given no grant, so the check refuses it; a run whose caller is refused, a key removed or narrowed, is ended with `refuse_next_attempt`, as the playbook itself, `unavailable` with the words of the refusal. A run a workflow's step made is the workflow host's to make again, and one that finishes later its settlement's. The host also asks again a caller's cancel the core recorded alone on a run that may still have been live (`src/attempt-leases/cancels-again.ts`), once that run has been quiet as long as it may take and a second more, a minute on where it could not be asked, for an hour at most; an attempt whose process dies meanwhile is ended by its lease with the kind of that cancel.

## The subscriptions of the playbooks

The server runs the loop of `@on.auto/providers` that decides which subscriptions a playbook holds at the services of its connections, so a service tells the runtime at once what happens there (`src/subscriptions`). `subscriptionLoopPortsOf` of `@on.auto/connections` composes its ports, where its README says what each does and the bound of subscriptions through one connection, and the server gives it its parts (`subscriptionLoopPartsOf`): the connection's calls through the tool access, its tool calls and the requests its entry declares (`requestOnce` of the access `makeToolAccess` made, which `requestWaysOf` of `src/composition/served-tool-access.ts` forwards); its one ledger, both as the record of a playbook's subscriptions and as the registry of the org's connections; the secret store; whether it receives over HTTP, as `receive_events` says; the reader of the requests that wait, `waitingRequestsOf` of `@on.auto/interaction`, each open request delivered in a conversation through a connection, its arguments rendered within the bound the tool access gives a request to that connection, `mostRequestBytesTo`; and the reader of the triggers that name a connection, `connectionTriggersOf` of `@on.auto/definitions/connection-triggers`, each filter of an active workflow of the playbook whose `source` is `/connections/<name>`, read from the `definitions` read model as it is, one statement for each hundred active workflows.

The address a service is given for a connection is its events address at `WEBHOOK_URL`, the public address of the runtime (`eventsAddressAt` of `@on.auto/api`), with the connection's id as its query, `connection_id`, which nothing reads back, while the runtime receives over HTTP; with `WEBHOOK_URL` unset the composition answers none, so the loop arranges no webhook and a request is read on its timer. A runtime in local mode, declared or not, takes no `WEBHOOK_URL`: its start stops (`readCredentialSettings`, `src/settings/access-settings.ts`), since local mode acts for every request as the local developer and a service outside could reach it only through a tunnel; a runtime that signs people in, or takes keys, takes one. A runtime that nothing outside can reach is served so whatever its entries declare, and no entry the runtime ships declares a destination arranged for each subscription, which `src/subscriptions/served-subscriptions.test.ts` holds, so a running installation arranges nothing and records nothing new, with `WEBHOOK_URL` and without.

The server serves the events address of `@on.auto/api` only where `WEBHOOK_URL` is set and `receive_events` holds `http` (`src/webhooks/served-events.ts`, mounted beside the answer address by `src/webhooks/delivery-routes.ts`), and answers no route there otherwise. Its ports read what the loop recorded: the destination is the `webhook` destination per subscription of a connection that serves the playbook, and the secrets those of the subscriptions the playbook holds through it, each with its subscription's topic and id, from `event_subscriptions_2` and the secret store (`deliveryDestinationOf` and `deliverySecretsOf` of `@on.auto/connections`), so a delivery is tied to the one subscription whose own secret proves it. An arrival is handed to two consumers of the one port, `arrived`, in this order (`handedOnBy`): first, where it wakes, to `connectionWake` of `@on.auto/interaction` with the playbook's org, the connection and the conversation it names, at the time it arrived: the conversations waiting there through the connection are read no sooner than the reading's shortest wait, by the reading with the connection's own credential, which the host's next wake, within a sweep, performs. Then, where the route hands on the event it carries, `carried`, which it does only for a delivery proven by its own subscription's secret over every byte of its body, the event, the playbook, the connection and that subscription's topic go to the intake of `@on.auto/workflow-host` (`connectionIntakeServedBy`, `src/workflows/connection-intake.ts`, composed over the host's store, its filters' sandbox and the host's clock by `src/workflows/workflows.ts`), which records it where a trigger of the playbook takes it and counts it where none does. What the intake answers, taken, not taken or refused for a connection that does not serve the playbook, leaves the delivery answered `200`; where it could not decide, its failure, its death or the server stopping under it, the request fails, `500`, so a service that sends again does, and the incident names only why it did not decide, the failure's tag, `defect` or `interrupted`, never its cause, which may hold what the delivery carried (`decidedUnlessStopped`, `src/webhooks/stopping-runtime.ts`). A wake that fails fails the request before the intake is asked, as it did before. A delivery that arrives between the service's answer to a subscription and its record is refused like one no secret proves. Each delivery is logged with its address, its outcome, its status and its size, never a header or the body.

A round of the loop, the loop and then the playbook's next due time (`subscriptionRoundOf` of `@on.auto/connections`), and last the names of the places the playbook's triggers listen in, read where they are owed, from the playbook's connections and its triggers read again after the loop (`placeNamesReadOf` of `@on.auto/providers`, `src/subscriptions/served-subscriptions.ts`), calls out of the server, as a delivery does, so it is due work of the workflow host in the lane of the items that call out (`subscriptionRoundsOf`, `src/subscriptions/subscription-rounds.ts`), one item a playbook keyed by the playbook, which the host never hands out while it is in flight: one round of a playbook at a time. A playbook is due when a row of `event_subscriptions_2` says it is, `reconcile_due_at`, which a fact about a subscription sets to its own time and each round sets on every subscription of the playbook to the time it answered, read through the index across playbooks the table keeps; and when a request of it is delivered or answered, or its run ends, which may change where a request waits: the delivery and the answer as the interaction capability's due work records them, through the recorder of work it is given (`recording`), while the runtime arranges a way, and the ending of a run as the follower of the playbooks hands it to a consumer of `run_succeeded`, `run_rejected` and `run_failed`, the facts of `requestPlaceFacts` of `@on.auto/interaction` the follower hands a consumer; and, through the same consumer, the facts of `connectionTriggerFacts` of `@on.auto/definitions/connection-triggers`, a definition saved, saved again, paused, resumed, retired, restored or moved, of which only those of a workflow owe a round (`changesConnectionTriggers`, by the type of the definition the fact's context names), since only a workflow has triggers, so it reads no other record of a playbook for it. Both owe the playbook a round in the process's memory, which the host performs at its next wake, within a sweep; a process that stops in between leaves the request to its timer until the next of these facts, the playbook's next due time, which a round never sets later than `resyncedAfterMs` of `@on.auto/providers` after it ran, the round taking the host's time it was handed, or the start of the next process, which asks again every playbook that listens through a connection (below). A round that fails is tried again after the due work's own wait for its key. The consumer wants the facts of every playbook and reads nothing on a pass to say so. What a followed fact owes is decided as it is delivered: while the runtime arranges a way, each of these facts owes its playbook a round, and otherwise only one of a playbook that holds a subscription or whose active workflows' triggers name a connection (`listensThroughAConnection` of `@on.auto/connections`, a request sent counting for nothing there), one read of the table for each such fact and, where the playbook holds none, one of its active workflows. A pass that follows no such fact reads nothing for the rounds. The server hands its rounds the workflow host's intake of a connection's events (`connectionIntakeServedBy`, `src/workflows/connection-intake.ts`), composed once the store of the workflows is served, so a check of an app on a timer hands each item it lists to the same intake a delivery's event reaches, and an item the intake refuses, or cannot decide on, is held and listed again (`listedTakenIn`, `src/subscriptions/subscription-rounds.ts`); a check needs no address, so every server checks an app whose entry declares a `polling` destination. On a runtime that arranges no way, which takes no inbound connection, such a round's loop has no webhook to arrange, subscribing and removing nothing through a call and moving no request, though it checks the apps it is given, and the round then reads the names of the places, so a server that hears its events over a socket, or reads replies on its timer, names the places its triggers listen in as any other does. A name's read never changes how a round ends.

A change of an org's connections may change what a playbook subscribes to, a connection connected again, removed or set to serve other playbooks, and no fact of the playbook says so. Whether or not the runtime arranges a way, the server follows the orgs' registries as its sockets do (`src/subscriptions/connection-changes.ts`), a further wake-up of the host, woken by the ledger's append signal for a stream of connections, raised in this process, and every minute for a fact another process wrote: it reads the version of each org's registry (`orgStreams`), and for each org whose version moved runs a pass of the relay of `@on.auto/connections` (`connectionChangesRelayed`) over the org's active playbooks (`activePlaybooksOf` of `@on.auto/playbooks`), owing a round, in the memory the facts above owe one in, to each playbook that listens through a connection (`listensThroughAConnection`, with `holdsASentRequest` of `@on.auto/interaction` and `connectionTriggersOf`): one read of its subscription rows, one of its open requests, and its active workflows' rows where neither holds. Where the runtime arranges no way, a request sent counts for nothing, since its reading stays on its timer there, so only a playbook that holds a subscription or whose triggers name a connection is owed a round, which names the places of a connection connected again. The relay's places are kept in the process's memory, so a server that starts asks each playbook that listens once. An org whose facts could not be read, or one of whose playbooks could not be asked, is said in one line and passed again at the next round.

What this server receives of what an app sends, which `list_connections` lists a connection's events by and the save of a workflow's trigger is checked against (`eventsReceivedAt`, `src/connections/connection-policies.ts`, handed to `connectionEventsOver` of `@on.auto/connections` and to the connections' services): a `webhook` made per subscription where it receives over HTTP and `WEBHOOK_URL` is set, the rule by which the subscription round arranges one; never a `webhook` made once for an app, since nothing here routes an app's one address to a playbook; and always a `websocket`, since the server opens sockets. ## The sockets of the connections

A service that sends its events down a socket the runtime opens, rather than to an address of the runtime, is reached by the server alone; Auto's cloud composes no socket. The server keeps one socket for each `websocket` destination and value of an app credential that a connected connection holds unrefused, in every org, and none for any other connection (`src/sockets`). It is a controller, as Kubernetes names one: a loop that never ends and moves the sockets that run toward the sockets wanted, reading the wanted ones from the registries of the connections alone and storing nothing, so a restart or the server that takes over builds the same sockets again from the same facts.

- **The registries it reads.** A round lists each org's registry with its version through the ledger's `orgStreams('connections')` (see the ledger's README), which reads one entry of an index for each org and adds none, and loads a registry, by its own fold, only where its version moved since the last round (`socketsHeldIn` of `@on.auto/connections`); an org no longer listed is dropped. It reads each value from the secret store once, keeps it and its HMAC-SHA-256 under a key it makes as it starts, in memory alone, and forgets a value no connection holds any more (`src/sockets/socket-registries.ts`). Connections whose values have the same digest, in any org, share one socket, since a service sends each message to one of an app's sockets; the decision is `socketStepsOf` of `@on.auto/providers`: open each socket wanted that none runs, close each that runs and is no longer wanted, and hand a running socket its new holders.
- **When it runs.** It is a wake-up of the workflow host of its own, `wakeUps` of the host's options (`src/sockets/served-sockets.ts`, composed by `src/sockets/sockets-of-the-server.ts`): the host makes it and starts its loop when it takes the claim on the workflows, and stops it when it stands by or stops, which interrupts every socket, so only the server that holds the claim keeps sockets and a standby keeps none. A round runs as the loop starts, every 60 seconds after, for a registry another server changed, and at once when this server appends to a registry (the ledger's append signal), as when a connection is connected, broken, removed or its value refused. A wake that is neither due nor signalled reads nothing.
- **What a socket does.** Each is `receivingOverASocket` of `@on.auto/providers`, opened as its destination declares through `opensAsDeclared` (`src/sockets/socket-openings.ts`): the request of `open` goes out through the server's outbound fetch under the connection policy's `reaches`, with the value as a bearer token and the entry's `failure_codes`, and the socket through the `ws` library opened with `https.globalAgent`, so `NODE_USE_ENV_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and `NODE_EXTRA_CA_CERTS` reach it as they reach every other call (see the models page, "Behind an outbound proxy"); it checks the certificate, follows no redirect, takes no compression, closes a socket that sends a message larger than 256 KiB, unacknowledged, and holds at most 16 messages it has not read (`src/sockets/socket-client.ts`). As a socket opens, it makes due every conversation waiting through each connection it serves (`connectionWake` of `@on.auto/interaction`, with no conversation), so a reply sent while no socket was open is read in seconds; a message whose reading names a conversation makes that conversation due for each connection it serves, at most once a second for one connection and conversation, and the reading with each connection's own credential, which the request already does, takes the reply. Where the service refuses the value, the socket stops and records the refusal for each connection that holds it (`appCredentialRefused`), which stays connected and is read on its timer, and no socket is opened with that value again.
- **A reply a socket carries.** A message whose reading carries a person's reply, which only an entry the runtime ships declares (see the README of `@on.auto/providers`), is taken as it arrives instead of only making its conversation due (`src/sockets/socket-replies.ts`): for each connection of the socket recorded in the account the reply names, the playbooks of the connection's org with a request open in the reply's conversation (`playbooksWaitingIn` of `@on.auto/interaction`, the read the wake makes, by the index on `sent_conversation`), and for each, whether a request of that playbook sent through that connection waits for a reply to the message the reply answers (`replyAwaited`); where one does, the reply goes to `replyDelivery`, composed as the due work's reads are, with the same recorder, so one rule takes, refuses or passes over a reply whatever brought it, and a reply seen twice is passed over by its id. Its time is read as `events.time` is, in seconds since the epoch or as an RFC 3339 date-time, or is when it arrived where the message gives none. A connection that took the reply is not woken; every other connection, one recorded in another account or in none yet, and one whose delivery recorded nothing, is woken as before, so the reading stays the fallback: it still runs on its timer, and every waiting conversation is made due as each socket opens. A failure to take the reply is logged as a warning with the org and the connection's id, never the reply, and the wake goes ahead. Nothing is stored for it but the facts the run records, and the cloud, which opens no socket, takes no reply this way.
- **A click a socket carries.** A message whose reading carries a click on a button of a message the connection sent, which only an entry the runtime ships declares (`filter.click`, see the README of `@on.auto/providers`), is handed, where its connection's recorded account is the one it names, to each playbook with a request waiting in its conversation through `clickDelivery` of `@on.auto/interaction`, as a reply is, with the time it was written or, where it names none, the time it arrived. It wakes no read, since a click is in no conversation's history, and a click that cannot be handed is logged with its org and connection, never anything else of it, and acknowledged.
- **An event a socket carries.** A message whose reading carries an event and names the account it is in is handed, after its wake, to the intake every other arrival passes through (`takeIn` of `@on.auto/workflow-host`, built for the sockets by `connectionIntakeServedBy` of `src/workflows/connection-intake.ts` on the clock the workflows use, so a server given no `WEBHOOK_URL`, which builds no intake for an events address, takes events in all the same): once for each connection of the socket recorded in the account the message names, and for each, once for each active playbook of the connection's own org, whose intake refuses a playbook the connection does not serve. A connection recorded in no account, or in another, takes nothing, and a message no connection is in is acknowledged and dropped. A message is acknowledged once the wake and every intake have decided, taken, not taken or refused; where an intake cannot decide, the message is not acknowledged and the service sends it again, which records nothing twice, since an event's stream is keyed by its source and id. Which account a connection is in is what the connection records (see the README of `@on.auto/connections`), as a sign-in names it or as the service answers when asked, never what a message says of the connection; a running socket is handed its connections again, unclosed, when the account one is recorded in changes (`memberKeyOf` of `src/sockets/socket-registries.ts`).
- **Who a connection of a socket is.** After it moves the sockets, a round asks the service, through the call the entry declares as `identity`, who each connection of a socket is and which account it is in, where the entry declares that call and the connection's record holds no answer for its connecting (`src/sockets/socket-identities.ts`). The account is the connection's own, as its socket is, so a call to a tool of the connection is made as the connection itself, with no playbook, through `callAsTheConnection` of `@on.auto/tool-servers`, the way the chat calls its service, in an org with no playbook too (`readAsTheConnection` of `identities`); the way is handed to that read alone (`subscriptionsServedBy`, `src/subscriptions/served-subscriptions.ts`). An entry that asks by an HTTP request is asked through the first of the org's active playbooks the connection serves, since no request is sent as the connection, and an org with no active playbook asks it nothing. Each answer is recorded by the recorder the server's subscriptions build, the runtime's `identify` on the org's connections, and the reads of a round are cut at one round's length from its start on Effect's `Clock`. A failure that passes is asked again at the next round; one that lasts is held back until the connection is connected again or the server starts again, and logged once as a warning with the org and the connection's id, never an account or a value. The connection's state, an entry that declares the call and a record that holds no answer, stays readable from the registry's fold.
- **What it logs.** A socket's opening, each end with its wait, the host it could not open at, and a refusal, each with the provider and the number of connections it serves; never a value, an address, a digest or a message.

`give_credential` checks a value given for a `websocket` destination with the same opening, once (`socketChecksOver` of `@on.auto/connections`, composed in `src/connections/connection-policies.ts`), since the server's connections are given `sockets`, so `list_providers` offers the app credentials a `websocket` destination names (see the README of `@on.auto/connections`).

## Single sign-on (SSO)

A runtime whose members sign in with single sign-on, through their company's own identity provider, sets `OIDC_ISSUER`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET` or `OIDC_CLIENT_SECRET_FILE`, beside `PUBLIC_URL`, or `OIDC_ISSUER` alone where the provider lets a client register itself (below), and may set `OIDC_SCOPES`, `openid profile email` when left out, `OIDC_TOKEN_ENDPOINT_AUTH_METHOD`, and `OIDC_REQUIRED_CLAIM`; each is the parameter of the standards behind the prefix `OIDC_`, and the last is Kubernetes's `--oidc-required-claim`, "A key=value pair that describes a required claim in the ID Token. If set, the claim is verified to be present in the ID Token with a matching value." `readOpenIdConnectSettings` (`src/settings/openid-connect-settings.ts`) reads them where the other sign-in settings are read, and refuses the start, naming the setting, when a client ID or a secret is set without `OIDC_ISSUER`, when `OIDC_ISSUER` is set with one of the client ID and a secret and not the other, when both forms of the secret are, in local mode, without `PUBLIC_URL`, with scopes that lack `openid`, with an issuer that is not an `https` URL or has a query or a fragment, with a secret file that is missing, unreadable or empty, with a `PUBLIC_URL` that is not an `https` URL, since the server then keeps a person's sign-in in cookies only `https` carries, with `OIDC_REQUIRED_CLAIM` where no one signs in, without `PUBLIC_URL` or in local mode, or with an `OIDC_REQUIRED_CLAIM` that is not `claim=value`. That is one pair, split at its first `=`, as Kubernetes splits one flag, so a value may hold a `=`; an environment variable is set once, so there is one claim, where Kubernetes repeats the flag for more. The claim and the value are each taken exactly as written, and the start is refused, not trimmed, where either is empty or begins or ends with a space or a line ending, since Kubernetes's flag trims both and an empty value could not be told from a forgotten one. Without `OIDC_ISSUER`, a runtime with `PUBLIC_URL` signs its members in at its default identity provider (below). The secret is kept `Redacted` and never logged.

With them, the server reads the provider's metadata as it starts (`@on.auto/openid-connect`) and refuses to start on a provider it cannot use. It is then its own OAuth 2.1 authorization server at `PUBLIC_URL`, the one `@on.auto/openid-connect/authorization-server` builds on `oidc-provider`, which it loads only here (`signInServingOf` of `src/sign-in/company-sign-in.ts`, composed at start by `src/lifecycle/served-sign-in.ts`). The server mounts the authorization server beside the API at the Node level, `beside` of `src/lifecycle/http-server.ts`, so a path it answers never reaches the API's routes, and gives it the API's own middleware, `middlewareBesideTheApi` of `@on.auto/api`, so the request id, the security headers, the `Origin` check and CORS, with `Access-Control-Allow-Private-Network` for Studio, hold there too. Where `OIDC_REQUIRED_CLAIM` is set, or the value of a required claim is recorded at the first sign-in (below), the claim is checked first, after the checks of the ID Token and before anything is decided or kept (`admittedAfter` of `src/sign-in/admission.ts`): a person refused for it is given no role, no record and no sign-in. Once the claim is decided, and before the role, the provider's tokens the sign-in still holds are released (`held` of `@on.auto/openid-connect`, where the provider declares a `userinfo_endpoint` or a `revocation_endpoint`): the name of a person who carries the claim is read at the UserInfo endpoint, where their ID Token carried none, and whether their address is verified, where it gave an address and did not say, and both are kept in their record; a refresh token the provider sent unasked is revoked, for a refused person too. ## The members

A server that signs people in, `settings.signIn` set, serves the members of its organization, the operations Studio's Members page calls on Auto's cloud, in the same shape (`src/roles/member-operations.ts`, composed by `signInAndStoresOpened` of `src/composition/sign-in-and-stores.ts`); a server that signs nobody in, in local mode or with keys alone, serves none, so a client tells by the operations a server declares whether it keeps members, never by its address or its kind. The chat, members writing to Auto through a connection, is composed on the same condition (`chatWiringOf` of `src/composition/composition-root.ts`): only a server that signs people in hands the connections the models a member may be answered with, so a server that signs nobody in lists no `chat` on a connection or a provider's way and serves no `set_connection_model`. They are the ports and adapters of Alistair Cockburn's "Hexagonal Architecture" (2005): one contract, the cloud's adapter over its identity service, this one over the ledger and the sign-in's store.

- `list_members`, `GET /members`, a query and an agent's tool, as on the cloud: every person who holds a role at the org, read from the read model `role_assignments_1` a page of 100 at a time, joined at read time with their record in the sign-in's store, `auth_people`, for their name, their address and when they first signed in, the earliest to join first, 500 at most, with `members_total`; a person who holds a role and never signed in, given it by `assign_role`, is listed by their id, joined when it was given. The join is Chris Richardson's API Composition ("Microservices Patterns", 2018), two read stores composed in memory at the query, since a projection of names and addresses would copy personal data into a second place, which the record's own deletion (Forgettable Payloads, Mathias Verraes, 2019) would then have to reach; no projection, key, version or fill changes. Beside them it answers the invitations pending: the role decider's state of the org, folded from its stream as the request is answered, a live aggregation, as Marten's documentation names a stream folded at read time, joined with their rows in `auth_invitations`, the earliest made first, 500 at most, with `invitations_total`; no projection keeps them.
- `invite_member`, `POST /members/invitations`, a command and an agent's tool, and `invite_admin`, `POST /members/admin-invitations`, over HTTP alone (`src/roles/invitation-operations.ts`): the invitation is a link, `{PUBLIC_URL}/invitations/` and a secret of 32 random bytes, whose SHA-256 is the invitation's id, so the server keeps no secret and looks a link up by one hash (`src/roles/invitation-links.ts`). The address is kept in `auth_invitations` before the decider's `invite` records the fact, by the caller as the inviter, a person, so a key or a playbook is refused before anything is kept; the link is in the answer of the call that made it alone. - `resend_invitation`, `POST /members/invitations/{invitation}/resend`, and `revoke_invitation`, `DELETE /members/invitations/{invitation}`, over HTTP alone: the decider's `resend` and `revoke`, refused as `not_found` where the invitation is not pending as the decider reads it.
- The link's page is the authorization server's, `GET /invitations/<secret>` (`src/authorization-server/invitation-link.ts` of `@on.auto/openid-connect`): a link whose invitation is pending is remembered for that browser in a cookie of the server's own, `__Host-Http-invitation`, which holds the secret and lasts an hour, and the browser is sent to Studio at the server's usual link, `no-store` and `no-referrer`; any other shows the page that says the link stopped working. The sign-in hands the secret it carries to the decision at its finish and clears the cookie whatever the outcome; `interactionSignInOf` of `src/sign-in/interaction-sign-in.ts` hashes it, so an id from a listing accepts nothing, and the decider's `enrol` decides with it. The request traces redact the secret, as they redact the token of a connection's link (`src/telemetry/redacted-url.ts`).
- `set_member_role`, `PUT /members/{member}/role`, over HTTP alone: the decider's `assign`, by the caller, so the decider keeps escalation and the org's admin, and its refusals take the approved words of a refusal for a role (`roleRefusalDetail` of `@on.auto/operations`), as the cloud maps them. It takes a person who holds a role and refuses anyone else, `not_found`, a removed person among them, who comes back by a new invitation. With the change it revokes the invitations pending to the member's address.
- `remove_member`, `DELETE /members/{member}`, over HTTP alone: the decider's `deprovision` with the source `manual`, which keeps the org's admin and revokes the invitations pending to the member's address, then the person's sign-ins ended at the authorization server, `personSignedOut` of `@on.auto/openid-connect`, which deletes their sessions and grants, so none of their tokens is read again and Studio and their agents sign in again, and, in the same step, the accounts at other services linked to them forgotten, with the link starts they allowed (`signedOutWithTheirLinks` of `src/roles/member-operations.ts`, over the port `AccountLinks` where a composition gives one). The ledger first: it is what every decision reads, so access ends with the append; the rows second, security state that is deleted and never recorded. Where the rows cannot be deleted, the removal still answers, as the cloud's step beside a change does, and an error line names the call and the org: the person holds no role, so each of their tokens is refused by the decision point, and their sign-ins end as they expire.

No operation checks a role of its own, but `set_member_role` and `set_enrolment` name their caller to the decider as the person who acts, and refuse one that is no person in Studio with the words the dispatcher gives them, and an invitation names its inviter to the decider, which decides whether their role may invite to the role asked.

## The client the server registers itself

With `OIDC_ISSUER` and no client ID or secret, the server registers its client itself, by OAuth 2.0 Dynamic Client Registration (RFC 7591), where the provider declares a registration endpoint, in its OpenID Connect metadata or else in its RFC 8414 metadata (`registeringProviderOf` of `@on.auto/openid-connect`); there is no setting for it, since registering is what a relying party with no client of its own does where the provider offers it, as mod_auth_openidc does, and a person who wants a client of their own sets its ID and it wins. Whether it may is read from what the provider declares and from nothing else, never from its address or its name. It registers as it starts, after the ledger and the secret store are open, so a start meets a provider that offers no registration, refuses the request, cannot be reached or answers a client the relying party cannot sign in as, and stops, in words that name the setting to change and say to register Auto with the provider by hand where it cannot (`refusedAtStart` of `src/sign-in/registration-refusals.ts`). It sends the name `Auto Runtime at` and the host of `PUBLIC_URL`, such as `Auto Runtime at auto.example.com`, so that whoever runs the provider can tell two servers apart (`clientNameAt` of `src/sign-in/company-client.ts`).

The registration is kept as the runtime keeps its own keys and the clients its connections register: a fact, `sign_in_client_registered { issuer, redirect_uri, client_id, secret_id }`, by the runtime, `by: runtime`, in a stream of the runtime's own and of no org, `runtime/sign-in-client-registrations`, apart from the connections' `runtime/client-registrations`, since a server may hold a connection and a sign-in at one issuer; and the client's secret, its method and the end of its secret, sealed in the secret store under the id the fact names, never in the fact, a log line or an answer (`src/sign-in/client-registrations.ts`). The fact is decided by a Decider, `signInClientsDecider`, whose command names the client it replaces, none for the first: it records the new client only while the latest one for the issuer and the redirect URI is the one named, and refuses otherwise, `conflict` of the kind `concurrent_change`, which the ledger appends under the version of the stream it read. So two servers of one database that register at the same moment keep one client: the later one forgets the secret it sealed and signs people in as the client the earlier one recorded, and the client it registered stays unused at the provider, which it logs. No projection or read model folds the stream: it is folded, a handful of facts, where a sign-in needs it, and a projection folds the streams of an org or a playbook alone, so none meets this one.

The server signs people in as the latest client for its issuer and its redirect URI (`registeredClientsOf` of `src/sign-in/registered-clients.ts`), read at each sign-in, so every server of one database uses the client any of them registered last, and its secret is read from the store once for each client. A restart registers nothing. A changed `PUBLIC_URL` is another redirect URI, which has no client yet, so the server registers one at its next start and people consent once more. A client whose secret the store no longer keeps, or keeps sealed under a key it no longer has, or whose secret has ended (`client_secret_expires_at`), is replaced by a new registration, recorded in its place. A pending sign-in notes the client it began as, its `client_id` in base64url as a fourth part of the cookie `__Host-Http-sign-in`, and finishes as that client, which must be one this server registered at this issuer for this redirect URI, since a code is redeemed by the client it was issued to; a runtime with a client given keeps the three parts it always had. Where the token endpoint refuses the client, by `invalid_client` or a challenge, and it is still the latest, the server registers anew once, however many sign-ins it refused at once, and records the new client in its place; that person is told they are not signed in and the next try signs them in. A sign-in that cannot begin because the server could not register again is answered as a sign-in that failed. The registrations are logged with the issuer and the client's ID alone (`logClientRegistered`, `logClientRegisteredElsewhereFirst`, `logClientNotRegistered` of `src/logging/sign-in-logging.ts`).

## The default identity provider

A runtime with `PUBLIC_URL`, no `ACCESS_MODE` and no `OIDC_ISSUER` signs its members in at its default identity provider, the Auto identity service, with their Auto accounts. `defaultIdentityProvider` of `@on.auto/identity`, beside `autoIdentityService`, holds it as data, as Grafana's `defaults.ini` holds its own service in `[auth.grafana_com]` and Tailscale's `--login-server` defaults to its own coordination server: its issuer; its scopes, `openid profile email user:org:read`; and the name of the claim it admits by, `org_id`, with no value. The settings reader alone imports it (`readOpenIdConnectSettings` of `src/settings/openid-connect-settings.ts`, whose test checks that no other module does), and reads it into `openIdConnectByDefault`, settings of the same shape a provider `OIDC_ISSUER` names gives `openIdConnect`. A test gives the reader another default through `defaultIdentityProvider` of `ServerOptions`, which none of the server's own commands sets, so no test reaches the service. What follows acts on those settings and on what the provider declares, never on its address or its name:

- The server makes no contact with the provider as it starts (`signInByDefaultOf` and `asItsClient` of `src/sign-in/company-client.ts`). It reads the provider's metadata and registers its client, as a provider `OIDC_ISSUER` names has it done at start, when the first sign-in begins; sign-ins that begin meanwhile wait for the same, and a failure is tried again at the next sign-in. A sign-in that cannot begin so is answered as a sign-in that failed, and logged with the issuer and what failed (`logSignInNotBegun`); one whose callback comes back after a restart reads them then, and is answered as failed where it cannot. It registers by the name `Auto Runtime at` and the host of `PUBLIC_URL`, and gives `PUBLIC_URL` as its `client_uri` (RFC 7591, §2), so that the provider's consent screen tells one server from another.
- The first sign-in records the value of the claim its ID Token carries, and from then on the claim is checked against that value as against a value `OIDC_REQUIRED_CLAIM` gives (below). `OIDC_REQUIRED_CLAIM` gives the claim and the value in place of the name alone, and then nothing is recorded or read. The start says in its log which of the two holds, naming the claim and never a value.
- `OIDC_CLIENT_ID`, a secret, `OIDC_SCOPES` or `OIDC_TOKEN_ENDPOINT_AUTH_METHOD` without `OIDC_ISSUER` stop the start, naming the setting, since half a set-up is never guessed. `IDENTITY_ISSUER`, `IDENTITY_JWKS` and `IDENTITY_JWKS_URL`, the settings of the identity service whose tokens a runtime admitted before it was its own authorization server, are no longer supported: `readCredentialSettings` (`src/settings/access-settings.ts`) stops the start before it reads anything else of sign-in, naming the first of them that holds a value, rather than leave it unread, since a runtime that ignored it would sign people in a way that whoever runs it did not choose. Where no one signs in, without `PUBLIC_URL` or in local mode, `OIDC_SCOPES` and `OIDC_TOKEN_ENDPOINT_AUTH_METHOD` are not read, as before.
- Everything else is as with a provider `OIDC_ISSUER` names (above): the server is its own authorization server at `PUBLIC_URL`, which must be an `https` URL, the person signs in at the default provider inside its sign-in step, and the API takes an API key or an access token the server issued itself, and no token of the identity service: one authorization server, the server itself, is named in its protected resource metadata, so Studio and every agent sign in the one way.

## The set-up: the value the first sign-in records

Where the settings name a required claim and no value of it, as the default identity provider's do, the server learns the value at its first sign-in and checks every later one against it: trust on first use, as RFC 4251, section 4.1, describes it for a host key ("only accept a host key without checking the first time a host is connected, save the key in a local database, and compare against that key on all future connections"), and after that Kubernetes's required claim. The rule reads the presence and the exact value of the one claim the settings name, compared character for character, and nothing else of the token, never a name, an address or a domain.

The set-up is kept in a stream of the runtime's own and of no org, `runtime/setup`, as facts: `required_claim_set { issuer, claim, value, person }`, by the person who signed in, `person:` and their id, where `issuer` is the `iss` of their ID Token, `claim` the claim's name, `value` the value it carried and `person` their id, never a name or an address; and `setup_reopened {}`, which ends it (`src/sign-in/setup.ts`). Both are decided by one Decider, `setupDecider`, over the value in force, which is the last fact's: `tie` records the claim a sign-in carries where none is in force, and nothing where one is; `reopen` ends the one in force, and does nothing where none is. The ledger appends a fact only under the version of the stream the decision read, so of two first sign-ins at the same moment, on one server or on several of one database, exactly one records its value; the other is decided again on what the first recorded, or reads it where the ledger answers the race as a conflict (`requiredClaimSetBy`), and is checked against it like any later sign-in. No projection or read model folds the stream: it is folded, a handful of facts, at each sign-in that needs it, and a projection folds the streams of an org or a playbook alone, so none meets it.

At the callback (`admittedAfter` of `src/sign-in/admission.ts`), after the checks of the ID Token: a token without the claim is refused; a value `OIDC_REQUIRED_CLAIM` gives is compared and nothing of the set-up is read or written; otherwise the set-up answers the value in force, recording this sign-in's where none is, and the person is admitted only where the issuer, the claim and the value are all equal to it. A person refused is given no role, no record and no session, as for any required claim. Only then are the provider's tokens released and the role decided, `enrol`, and the record and the session kept, as above. The set-up and the role are two writes: a server that stops between them keeps the value and has no admin yet, and the next person carrying that value to sign in is the admin. The value recorded is logged at `info` by the claim's name and the person's id, never the value (`logRequiredClaimSet`); a refusal for it, at `warn`, by the claim's name.

What changes with the server: a restart reads the value in force again; every server of one database reads the same; a changed `PUBLIC_URL` keeps it, since it holds no address, while the server registers its client anew (above); a lost database holds none, so the next sign-in records one again, as it records a new admin.

Whoever runs the server takes it back with `admin reset-setup` (below), which asks `setupReopened(reopening, by)` of `src/sign-in/setup.ts`: it decides `reopen` on `runtime/setup`, which records `setup_reopened` where a value is in force, and then, wherever the stream holds a fact, signs everyone out (`everyoneSignedOut` of `@on.auto/openid-connect`, which ends every sign-in, grant, code and token the authorization server keeps in the sign-in's store, in one statement, and keeps the clients registered there, so every person and every agent signs in again) and logs that set-up is open again (`logSetupReopened`); it answers whether set-up stands open again. So the next sign-in records its own value; a person's id, their roles and their record are not touched, since the id does not depend on the claim. The fact and the sign-out are two writes, to the ledger and to the sign-in's store, with no transaction over both, so the command is idempotent rather than atomic, as a message relay of the transactional outbox is (microservices.io, "Transactional outbox"): the fact is the record of what is to happen, and every run that finds set-up open again by a fact signs everyone out again, which ends nothing where the run before it ended everything. A run that fails or stops between the two is repaired by running it again, and a sign-out the sign-in's store does not confirm fails as `SignOutUnconfirmed`, which the command reports. Only on a stream that holds no fact, a server no sign-in ever tied, it records nothing and signs no one out.

## The chat's tables

What a conversation with Auto in a chat app is remembered by, who in the chat app is linked to whom in Auto, and which messages the server has taken, are kept in tables of their own in the ledger's database, `chat_`, with a layout number of their own, `chat_layout`, as the sign-in's tables are: never in a playbook's ledger, which is kept for good and read by anyone who may read the playbook, so a person's words can be deleted on request (event sourcing chosen per part of a system, and personal data kept out of the log, as Mathias Verraes's "Forgettable Payloads" sets out). No fact refers to them, and no projection reads them. Nothing composes them yet but `admin delete-chat` (below); a server that never opens them never makes them, and a release before them ignores them.

`src/chat/tables/` holds the rows: `chat_arrivals`, one row for each message taken, by the connection, the account, the conversation and the message's own id, whose first insert wins, so a message that reaches two servers at once, or one twice, is answered once (an Idempotent Receiver, Hohpe and Woolf), with its kind and whether its turn has settled; `chat_conversations`, one row for each thread and one for each conversation with no thread, with the id of its key in the secret store and its lease; `chat_messages`, the rows of a conversation in order, each with its author, the id of whoever wrote it and its sealed text; `chat_links`, the person in Auto each member of a chat app is linked to, by ids alone, and when; and `chat_link_starts`, one open start of a link for each member, its `secret` (what the caller stores of the link's value, and once someone allowed it, of its code: a SHA-256, never the value) and the person who allowed it. A newer start of a member replaces the older one in one statement, a start ends once and never one that replaced it (`startEnded` deletes by account, member and secret), and `personForgotten` deletes a person's links and the starts they allowed, the starts first so no link can be made for them in between. `ChatRows` (`chat-rows.ts`) is their port; the same cases hold it on a fake in memory (`src/testing/chat/`), on a SQLite file and on PostgreSQL (`chat-rows-behaviour.ts`, `chat-links-behaviour.ts`), and the layout, a database made at the first layout (`chat-floor.json`) and two connections taking one arrival and one lease at once on a real database (`chat-database-behaviour.ts`). Each statement runs outside any transaction of the ledger, as the sign-in's store does. No column gives a start or a link an age: a start ends by an event alone, when the caller ends it or a newer one replaces it.

`src/chat/store/` holds the rules over the rows (`chatStoreOver`, `chatStoreOpened` of `chat-store.ts`):

- Sealed, by envelope encryption, as the secret store seals a secret (AWS KMS's term): each conversation has a data key of 32 random bytes of its own, kept in the secret store, and each text is sealed with AES-256-GCM under it, its additional authenticated data the row it belongs to, as the JSON of its table, conversation, sequence, author and sender (`null` where there is none, which no sender's id equals), so a sealed text moved to another row, or a row given another author or sender, does not open (`sealed-texts.ts`). A turn reads its conversation's key once (`conversation-key.ts`). No text, name or address is in a column in the clear, and none in an error.
- The lease on a conversation, one turn at a time, is a conditional update of its row, taken where it is free or has passed, as the Lease pattern has it (Gray and Cheriton, 1989): 12 minutes by default, above a turn's 10, `TURN_LEASE_MS`, on a clock handed in, by default the database's own where it has one, so two servers on one PostgreSQL read one clock. It frees a conversation after a turn that died and deletes nothing. A turn appends its rows only while it still holds the lease, the holder fencing the append (`leased-memory.ts`), which implements the memory's port of `@on.auto/chat`.
- What deletes them (`chat-deletions.ts`): a connection removed takes its conversations with their keys, its arrivals, and the links and open link starts of its account; a member who disconnects, their link; and, on request, a conversation, in every thread or in one, and a member, whose every row goes with each thread only they wrote in (a conversation with no threads counts as one), each of the two within one account alone, since a chat app's ids are its account's: the same id in another account is another conversation or another person, and stays. A conversation that goes whole has its key forgotten first, so a run that stops halfway leaves nothing readable, and the next run finishes it; its rows are locked, then its messages deleted, then its row, in one transaction, so a turn that appends at that moment either waits and appends nothing or appends before the messages go (`deletedIn` of `src/chat/tables/stored-conversations.ts`).

## The admin commands

Whoever runs a server has commands for what no screen can do, run beside the server as a one-off admin process, the twelfth factor of The Twelve-Factor App, "Run admin/management tasks as one-off processes", which "should be run in an identical environment as the regular long-running processes of the app" (12factor.net/admin-processes), as `immich-admin`, Mastodon's `tootctl`, `gitlab-rake`, `grafana cli admin` and Keycloak's `kc.sh bootstrap-admin` are: `auto-runtime admin <verb>` from the npm package, which reads the settings of this computer as `auto-runtime start` does (`localSettings`), and `node packages/server/src/admin-command.ts <verb>` in the container, which reads the environment as `src/main.ts` does (`src/admin-command/run-admin-command.ts`). Neither talks to a running server, so a command works with the server running or stopped, and whoever can run it already holds the database and the settings; a channel into the running server, as `status` and `license` use, is served only where `auto-runtime` started the server itself, never by the container's `src/main.ts`. Each command asks nothing and prints its result on standard output, exit code 0, or its refusal on standard error, exit code 1, as `key` does.

A command opens what a decision needs exactly as the server does and nothing else (`src/admin-command/opened-for-a-command.ts`): the settings read by `settingsAtStart` of `src/settings/shipped-settings.ts`, which `startServer` reads them with too; the ledger by `ledgerOpenedAtStart` of `src/composition/ledger-store.ts`, the one opening the composition root uses, so the command checks the facts it holds against the same schemas, extensions' among them, and keeps the same inline projections in the transaction of each append; and the sign-in's store by `signInOpened`. It serves nothing: no listener, no workflows, no sweeps, no due work, no usage ping, no license report; the pool of workers starts no worker and closes with the command. On SQLite it never makes a ledger: a ledger file that is not there is refused before anything is opened, so a command run in the wrong place leaves no file behind (`ledgerFoundIn` of `src/admin-command/ledger-reached.ts`). On PostgreSQL nothing is checked before the opening, so a command pointed at an empty database makes a ledger there, as a server's first start does. It never carries the ledger's layout forward: the ledger is opened with its floor at the layout this release keeps, so a ledger of another release is refused, the server's own words saying why, and one of an earlier release with words of its own, since the server would carry it forward and the command must not under a server of that release (`src/admin-command/ledger-reached.ts`). The sign-in's store is not held to that: `signInOpened` opens it as the server does, through `authStoreOpened` of `@on.auto/openid-connect`, which carries its own layout forward (`authLayoutKept`), so a command of a newer release run beside a server of an older one can carry the sign-in's store to a layout that server does not keep, and that server's sign-ins then fail until it starts on the newer release. Every fact a command records goes through its Decider and the ledger's `execute`, which loads the stream, decides and appends under the version it loaded, deciding again on a clash, three times, as the server's own writes do; so a command and the server, or two commands, never both win a decision, and a command whose ledger changed under it at every try records nothing and says to run it again. On SQLite the command is a second process on the file the server writes: each append is one `BEGIN IMMEDIATE` transaction, a second writer waits for the first's commit, up to SQLite's busy timeout of 5 seconds, and checks the version against what was committed (`src/ledger-layer.test.ts` of `@on.auto/ledger` holds two ledgers on one file to it); so the command runs where the file is, in the server's container. What a command records is the fact, with `by: command` (`byACommand`) and the time; no operating-system user is recorded. A command logs as the server does, by `LOG_FORMAT` and `LOG_LEVEL`, on standard error. The running server reads what a command recorded at the next request that needs it, with no restart.

- `admin delete-chat member <account> <id>` and `admin delete-chat conversation <account> <id> [<thread>]` delete what the chat's tables keep (above), for a request to delete, within the account given, the account a chat app's connection is for: by the id the chat app gives a member, every row they wrote, whatever its author, each thread only they wrote in, with its key forgotten, and their link and open link start; by the id of a conversation there, every thread of it with its arrivals, or the one thread given, whose arrivals stay, since an arrival names no thread. It answers that nothing was deleted only where no row went, arrivals counted. On a database with no chat tables it makes them, empty, as the server's first opening would. It opens the secret store as the server does (`ledgerStoresOpenedBy`) and the chat's tables on the ledger's connection, which `signInOpened` of `src/composition/ledger-store.ts` answers beside the sign-in's store and the command carries as `connection` (`withTheChatOpened` of `src/admin-command/delete-chat.ts`); chat tables of a newer release are refused in their own words. Where nothing is kept, it says so and which ledger it read.
- `admin grant-admin <email>` makes a person who has signed in the admin of the server's organization, `default`, for when every admin has left: among the people the sign-in's store keeps (`auth_people`), it finds the one whose email address, as the identity provider gave it at their latest sign-in, equals the one given, whatever its letter case, and asks the role decider's `recover` for their id (`adminRecovered` of `@on.auto/access-control`) through the org's writer, as the sign-in's `enrol` is asked (`src/admin-command/grant-admin.ts`). The address only finds the person; the facts carry their id, and nothing is granted to an address before its person signs in. Where no one, or more than one person, signed in with the address, it records nothing and refuses, the first saying which ledger it read. It prints the person's name and address, as kept, so a wrong match shows; it logs neither, and ends no session.
- `admin register-client` registers the server with its identity provider again, for when the client it registered was deleted there: the provider then shows the person its own error page and never sends them back, as RFC 6749, 4.1.2.1, says it must for a client it does not know, so the server is never told and nothing it does by itself can learn it (the token endpoint's `invalid_client`, above, comes only after a person came back). It takes the same steps the server takes when the token endpoint refuses the client, and no copy of them: the provider and its place built from the settings by `registeringProviderFor` of `src/sign-in/company-client.ts`, which the server's sign-in uses, the latest client kept for the place, the provider's registration, the secret sealed in the secret store, opened as the server opens it (`ledgerStoresOpenedBy`), and `signInClientsDecider` asked with that client as the one it replaces, `by: command` (`registeredAgain` of `src/sign-in/registered-clients.ts`). The running server signs the next person in as the new client, since it reads the latest at each sign-in; a sign-in under way keeps the client its cookie names. Where a server registers at the same moment, the decider lets one of them in and the command says the other's client is in use, as two servers do. Where `OIDC_CLIENT_ID` gives the client, or no one signs in, it opens nothing and refuses; where the provider offers no registration, refuses it or cannot be reached, it refuses in the words the start uses (`refusedToACommand` of `src/sign-in/registration-refusals.ts`), saying to run the command again where the start says to start the server again. Where people sign in with Auto accounts, the server takes none of the settings those words name (`OIDC_CLIENT_ID` and `OIDC_SCOPES` without `OIDC_ISSUER` stop its start), so the refusal says what happened and to run the command again once that is fixed, and names no setting.
- `admin reset-setup` starts the set-up over (above) and so signs everyone out, and run again it signs everyone out again and says the same, so a run that failed or stopped halfway is repaired by the next. Where `OIDC_REQUIRED_CLAIM` gives the value, which the one recorded never decides, it opens nothing and refuses; where no sign-in ever tied the server, it records nothing and says which ledger it read, so a command pointed at another database shows it; where the sign-in's store does not confirm the sign-out, it refuses and says to run it again.

The composition of main, started in the process with a shutdown timeout longer than the test, stops with an idle keep-alive connection open after a workflow ran, and while a function a workflow called still runs, without waiting for that timeout (`src/lifecycle/shutdown.test.ts`); so no test of a spawned process holds it to how long it takes: `src/main.test.ts` holds main to its exit code alone, `src/workflows/workflow-lifecycle.test.ts` to its exit code, to what it says at its start, to leaving nothing running and to taking the call it was stopped in up again once started again.

The tests start the servers, the `auto-runtime` command and the development runner they run through `spawnForTheTest` of `@on.auto/operations/testing` (`src/testing/processes/spawned-server.ts`, `runtime-command.ts` and `development-process.ts`), which ends each once its test finished, whether it passed, failed or timed out: with SIGTERM, on which the server stops, and with SIGKILL if it is still there `stoppedWithinMs`, 10 s, later; `src/lifecycle/shutdown.test.ts` holds the server's longest stop, `longestStopMs`, under that bound. Two tests start their processes through the code they test instead: `src/development/children.test.ts` through the runner's `startChild`, which starts each child in a process group of its own, and ends each with SIGKILL once its test finished, and `src/background-start/started-in-the-background.test.ts` through `startInBackgroundOf`, whose recording entry ends itself once it has written what the test reads, and whose other entry, `src/testing/entries/stay-until-signalled.ts`, runs until the test signals it through the handle the start hands back, with `endWithTheTest` registered for its pid. The processes the helper starts are attached to the test's worker, in its process group, so a signal to that group, as Ctrl+C in a terminal sends, stops them too; a worker that dies alone runs no hook, and leaves them running until they next write to the output it held. A runtime started in the background, `start --background --instance <id>`, runs in a process group of its own and writes to its log, so nothing of the test's ends it with the test. `src/agent-relay/agent-relay.test.ts` starts one alone, in the test that proves it runs on outside the process group of the agent that started it, and starts a second one the same way once the first was stopped; another has the relay start one as it starts, and a second once the test stopped the first and the relay's grace passed; two of its other tests start the runtime in a terminal, attached, and another starts none, since another program holds its port. `src/agent-relay/relay-replacement.test.ts` starts one in place of a runtime in a terminal that the test stops, and one through the relay of `src/testing/entries/relay-with-short-bounds.ts`, which the test freezes with SIGSTOP and the relay stops and replaces; its third test freezes a runtime in a terminal, which the relay leaves alone, and lets it go on with SIGCONT before it stops it with Ctrl+C. Each test that lets a relay start a runtime registers, before anything starts, `runtimesStartedInTheBackgroundEndedWithTheTest` of `src/testing/processes/background-runtimes.ts`. Once the test finished, it reads the lines the relay writes to the `runtime.log` of the test's home as it acts, `Auto Runtime was started in the background as process <pid>, instance <id>` and `Auto Runtime, process <pid>, ended`, and ends each process started and not ended: with SIGTERM, and with SIGKILL if it is still there `stoppedWithinMs` later, each sent only while its command line, as `ps` reads it, still carries that instance, and the process counts as gone once it no longer does. It asks the port nothing, so a runtime that answers slower than a probe's 2 s, or one whose relay was ended while it held the starting lock, is ended all the same, and a pid used again by another process is not signalled. The suite's teardown does the same with what a test left in the temporary folder of the run, as when its worker died or its hook timed out: `vitest.config.ts` names `src/testing/test-run/test-run-folder.ts` in place of the shared global setup, `aFolderOfTheTestRun` of `@on.auto/operations/test-run-folder` over `runtimesStillRunningInTheBackgroundIn` of `src/testing/processes/runtimes-in-the-background.ts`, which reads the `runtime.log` of each home left there, so a runtime still running in one is ended once the run ends and named, with its home, in the failure of the run.

The relay of `auto-runtime mcp` holds its bounds on Effect's test clock, in `src/agent-relay/relay-watch.test.ts`, `src/agent-relay/relay-losses.test.ts` and `src/runtime-recovery/runtime-stop.test.ts`; `src/agent-relay/relay-replacement.test.ts` runs a relay on real time with a silence of 1 s and a stop of 0.5 s in place of 15 s and 9.1 s, and holds what happens, never how long it took. The waits of its start, for a runtime it starts to answer, for an older one to stop and for one that restarts to come back, probe the port every 100 ms on Effect's clock and end with the relay: a start the relay makes while it relays ends at once when the agent leaves, aborts the probe in flight and frees the starting lock. `src/background-start/background-start.test.ts` holds them on the test clock, by the probes its fake answers and by the time they take, and `src/local-runtime/runtime-commands.test.ts` holds the waits of `stop` and `restart`, which run the same way. Some tests keep a bound on real time on purpose. `src/lifecycle/shutdown.test.ts` holds a request still running to being cut off no sooner than the shutdown timeout less 50 ms, a lower bound a slow machine only lengthens. `src/computation/computation-over-http.test.ts` holds a run that never ends by itself to being refused no sooner than its 10 s deadline less the slack of a timer, and a read of the definition and a run on another worker to answering before that deadline, a race the server wins by the pool's 10 s on the real clock, which the pool keeps and no clock of the server reaches; its saves check within 30 s through `checkingWithin`. `src/reasoning/prompts-and-answers-on-stores.test.ts` holds a reasoning run whose 25 calls each answer 1 MB to reading every answer back within `toolBounds.runMs`, the 600 s a run that calls tools may take, on the real clock on purpose, since that is the bound such a run meets in the server. `src/telemetry/telemetry-shutdown.test.ts` holds the shutdown of telemetry whose collector cannot be reached, and of telemetry whose collector takes its exports and never answers them, to ending before a timer of the same second as its bound, `longestShutdownMs`, started after it, since that shutdown races its exports against a timer of 1 s of the platform, for which the exporters take no clock; the two timers fire in the order they were started, however slow the machine. `src/development/source-changes.test.ts` saves a file again every 500 ms until the watcher reports it. `src/workflows/workflow-lifecycle.test.ts` starts the next server after a stopped one, in the process over the same ledger file, on a stepped clock ahead by the timers of its runs, so they are due at once.

Three subpaths serve the repository's own scripts and no program that runs the server: `./openapi-document` answers the OpenAPI document a throwaway server of this release serves, which `docs:openapi` keeps; `./served-to-an-agent` (`src/testing/agent-texts/served-to-an-agent.ts`) what a throwaway server serves an agent over MCP, read by `servedSurfaceAt` of `@on.auto/api/testing` as the caller of local mode, after `list_playbooks` on its new org, and the page it answers at `/debug`; and `./setting-names` (`src/testing/agent-texts/setting-names.ts`) the name of each setting the server declares, each variable it reads and each key of its configuration file. `agent-texts` lists every text of what is served, the behavioural check shows a model what a client shows of it, and `docs:setting-names:check` finds no setting's name in any of those texts beyond the ones its list still names. All three live under `src/testing`, which the npm package leaves out of a package that offers no `./testing`, so none ships. `src/testing/agent-texts/served-to-an-agent.test.ts` holds what it reads to its page at `/debug`, text for text and name for name.
