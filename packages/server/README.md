# @on.auto/server

The Node.js server of Auto Runtime: `src/main.ts` starts it on the composition root of `src/composition/composition-root.ts`, `dev.ts` restarts it on every save, and `auto-runtime.ts` is the command of the npm package `@on.auto/runtime`, which `npm/pack.ts` packs with the `README.md` in `npm/`; the `Dockerfile` builds its container image.

## Testing

The servers the tests start in the process run on `patientWorkerPool` of `src/testing/servers/worker-pools.ts`, the server's worker pool whose checks at save may take 30 s, through `checkingWithin` of `@on.auto/definitions/testing`, and whose inputs may take 30 s, through `decidingWithin` of `@on.auto/workflow-engine/testing`, so a check or a decision that a busy machine slows is never refused by the 2 s a save allows or the 2,000 ms of an input; `scriptedWorkerPool` answers the outcomes a test scripts before it hands the rest to that pool. The refusal of a check at its deadline stays held by `src/computation/checks-over-http.test.ts` and `src/computation/checks-over-mcp.test.ts`, whose pools answer `stopped: deadline`, and the answer of a start whose input runs past its deadline by `src/workflows/workflow-deadlines.test.ts`, whose evaluations answer `exhausted: deadline`. The servers the tests spawn as processes keep both bounds.

A test that waits for what a workflow's step waits for before the step's timeout ends it runs its server on `movedClock` of `@on.auto/workflow-host/testing` and moves the clock past the timeout once it has seen the state (`src/interaction/interaction-reactions.test.ts`, `src/workflow-calls/workflow-cancels.test.ts`, `src/workflow-runs/workflow-tool-cancellation.test.ts`), and the table of the endings of a run that asks a system gives its calls `patientTiming` of `@on.auto/tool-servers/testing` and only the rows that outlast a call or an opening the short one (`src/asking-a-system/ending-rows.ts`).

The composition of main, started in the process with a shutdown timeout longer than the test, stops with an idle keep-alive connection open after a workflow ran, and while a function a workflow called still runs, without waiting for that timeout (`src/lifecycle/composed-stop.test.ts`); so no test of a spawned process holds it to how long it takes: `src/main.test.ts` holds main to its exit code alone, `src/workflows/workflow-lifecycle.test.ts` to its exit code and what it says at its start, and `src/workflows/workflow-shutdown.test.ts` to its exit code, to leaving nothing running and to taking the call it was stopped in up again once started again.

The tests start the servers, the `auto-runtime` command and the development runner they run through `spawnForTheTest` of `@on.auto/operations/testing` (`src/testing/processes/spawned-server.ts`, `runtime-command.ts` and `development-process.ts`), which ends each once its test finished, whether it passed, failed or timed out: with SIGTERM, on which the server stops, and with SIGKILL if it is still there `stoppedWithinMs`, 10 s, later; `src/lifecycle/shutdown.test.ts` holds the server's longest stop, `longestStopMs`, under that bound. Two tests start their processes through the code they test instead: `src/development/children.test.ts` through the runner's `startChild`, which starts each child in a process group of its own, and ends each with SIGKILL once its test finished, and `src/local-runtime/background-process.test.ts` through `startInBackgroundOf`, whose entry ends itself once it has written what the test reads. The processes the helper starts are attached to the test's worker, in its process group, so a signal to that group, as Ctrl+C in a terminal sends, stops them too; a worker that dies alone runs no hook, and leaves them running until they next write to the output it held. A runtime started in the background, `start --background`, runs in a process group of its own and writes to its log, so nothing of the test's ends it with the test. `src/local-runtime/agent-relay.test.ts` starts one alone, in the test that proves it runs on outside the process group of the agent that started it, and starts a second one the same way once the first was stopped; two of its other tests start the runtime in a terminal, attached, and the third starts none, since another program holds its port. Each of its tests registers, before anything starts, the end of the runtime that answers `/runtime` on the test's port once the test finished, through `runtimeOnThePortEndedWithTheTest` of `src/testing/processes/runtime-command.ts` and `endWithTheTest`, provided the directory it answers lies inside the test's home, the home for a runtime started in a terminal and its `.auto-runtime` for one started in the background, so a runtime of another test that holds the port by then is left alone: it reads the pid there, again and again while a start is under way, as the `starting.lock` in the runtime's home says, for at most 30 s, ends that pid, and stops the test's own wait for it. The launcher keeps no pid file, so a runtime whose worker died before its test finished is found only by the port that test chose.

Some tests keep a bound on real time on purpose. `src/lifecycle/shutdown.test.ts` holds a request still running to being cut off no sooner than the shutdown timeout less 50 ms, a lower bound a slow machine only lengthens. `src/computation/computation-deadline.test.ts` holds a run that never ends by itself to being refused no sooner than its 10 s deadline less the slack of a timer, and a read of the definition and a run on another worker to answering before that deadline, a race the server wins by the pool's 10 s on the real clock, which the pool keeps and no clock of the server reaches; its saves check within 30 s through `checkingWithin`. `src/reasoning/large-answers-on-stores.test.ts` holds a reasoning run whose 25 calls each answer 1 MB to reading every answer back within `toolBounds.runMs`, the 600 s a run that calls tools may take, on the real clock on purpose, since that is the bound such a run meets in the server. `src/telemetry/start-telemetry.test.ts` holds the shutdown of telemetry whose collector cannot be reached to within 1.5 s, since that shutdown races its exports against a timer of 1 s of the platform, for which the exporters take no clock. `src/development/source-changes.test.ts` saves a file again every 500 ms until the watcher reports it, and `src/workflows/workflow-lifecycle.test.ts` waits until the timers of a stopped server's runs are due before it starts the next process, waits a slow machine only lengthens.
