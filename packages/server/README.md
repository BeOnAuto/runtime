## What is composed at start, and what on first use

The composition root composes at start what every request and the host's own work need, in `serve` of `src/composition/composition-root.ts`: the application layer, with the ledger, the playbook registry, the incident reporter and telemetry; the store of secrets and the connections over it; the one pool of workers, which starts no worker before its first job, and whose evaluations decide the steps of workflows and filter the events reactions take; the store of the workflow host, opened with the tables of recall's views and of the datasets of prediction functions; the pool of model processes and the ports over it, which start no process before their first job; the adapters, operations and due work of every capability; the workflow host; and the table of routes, so `list_operations`, the OpenAPI document and the guides are whole from the start. What costs a composition is an entry of the capability registry (`src/capability-registry/capability-registry.ts`), which the root holds, each a `LayerRef` of Effect over the layer that composes it, built the first time it is asked for and kept for the server's life (`composedOnFirstUse`, `src/capability-registry/first-use.ts`): `models`, the model access of reasoning functions, with a client for each configured provider and gateway and the credential libraries some of them load, and `tools`, the access to the tool servers, with the OpenAPI document of each `openapi` entry read and described. The reasoning and interaction adapters, `list_models`, the five operations over the tool servers and the due work of interaction functions are made at start over a language model, a model catalog and a tool access that ask the registry (`src/composition/served-reasoning.ts`, `src/composition/served-tool-access.ts`), so the first request that calls a model, lists the models or uses a tool server, and the first request of an interaction function that comes due, pays the composition inside its own request or due item and its bounds, and every later one finds it composed (`src/reasoning/models-on-first-use.test.ts`). A composition that fails is not kept: the model access cannot fail, and documents the tool access cannot read fail the request that needed them with an incident, whose log line carries the words the start used to stop with, `tool_server_document_refused: The documents of the tool servers could not be read. TOOL_SERVERS: …`, and the next request reads them again (`src/tool-servers/documents-on-first-use.test.ts`). The registry is held in a scope the runtime closes as it is disposed, once the API has closed and before the services built ahead of it (`scopeOfTheRuntime`), since an entry closed answers no ask, and a request still in flight while the server stops its work keeps the models and the tools it uses. The start log still names where the ledger, content and secrets are kept and which model providers are configured, read from the settings with `providerStatus` of [`@on.auto/reasoning`](../../capabilities/reasoning/README.md#source) and `installedPackages` of its `installed-packages` entry, whose `loadEntraIdentity` the model access is given, and the folder of the model files is made and checked at start, while the caches read and check the files in it when a prediction first uses them (`src/prediction/model-cache-folder.test.ts`). `Auto Runtime listening on port <port>` therefore means the server listens: no composition waits behind it. ## The secrets key

## The runtime's own keys

The runtime keeps keys of its own in its secret store, beside the secrets it keeps for others, and names each by a fact in a stream of the runtime's and of no org, `runtime/own-keys`, as `@on.auto/connections` names the clients it registers dynamically in `runtime/client-registrations` (`src/secrets/own-keys.ts`, beside the composition of the store the key is read from, which `src/database/ledger-stores.ts` opens, moves, rotates and logs right before). The one fact, `own_key_kept { purpose, secret_id }`, by the runtime, `by: runtime`, is folded by purpose, the latest last, and the decider, `ownKeysDecider`, refuses a second for a purpose that has one, `conflict` of the kind `taken`, `The runtime keeps a key for retry_state already`. The one purpose is `retry_state`, the key that signs the state an MCP client sends back when it retries a call, as [`@on.auto/api`](../api/README.md) says.

At start, once the secret store is open and rotated, `retryStateKeysOf` folds the stream. Where no key is recorded for the purpose it keeps 32 random bytes in the store, as their base64, and records the fact, which the ledger appends under the version of the stream it read; where the record is refused because another server recorded one first, it forgets the row it kept and folds again, taking that one. It then reads the row, logs under a secret manager `The runtime read the key it keeps for retry_state in AWS Parameter Store under <prefix> in <region>` with the annotations `own_key`, the purpose, and `own_key_id`, the secret's id, which names its parameter, `<prefix>/<own_key_id>`, and gives the API `retryStateKeys` with that key as `current` and no `previous`, so every server that shares the ledger signs under the same key, and a rotation of the secrets key wraps it again and leaves it as it is. A row it cannot read stops the start as an `OwnKeyUnavailable`, named as the server's other start failures are, in words that name the purpose, where secrets are kept as the start's log names it (`secretsKeptBy`), the store's words and the ways out: `The key the runtime keeps for retry_state cannot be read under the key that SECRETS_KEY holds: <the store's words>. Start the server with the key the ledger's secrets were sealed under, or give that key as SECRETS_KEY_PREVIOUS, SECRETS_KEY_FILE_PREVIOUS or SECRETS_KEY_KMS_PREVIOUS beside a new key`, or, under a secret manager, `… cannot be read in AWS Parameter Store under <prefix> in <region>: <the store's words>. Start the server with the keeper the ledger's secrets were kept by, or name that keeper as SECRETS_KEEPER_PREVIOUS beside SECRETS_KEEPER`. The key is a secret like any other, so a move takes it to the current keeper with the rest. A row that is gone, `… is no longer in the secret store, so the server does not start`, or, under a secret manager, `… is no longer in AWS Parameter Store under <prefix> in <region>, the region AWS_REGION names, so the server does not start`, naming the variable the region was read from, since another region or account holds no parameter of the ledger's, one that holds something other than 32 bytes, and a key the store cannot keep at the first start, `… cannot be kept under the key that SECRETS_KEY holds, so the server does not start: <the store's words>`, stop it too; the store is closed before the start fails. A deliberate reset of the runtime's own keys is not offered yet. Nothing of the key is logged, and no key is derived from another.

## Metered composition

`compositionRootWith` accepts a trusted `metering` composition containing the fixed license authority and public keys, clock, HTTPS transport and explicitly provisioned operator API key IDs. It attaches the durable meter to request and background work, using the same SQLite/PostgreSQL connection and encrypted secret store as the server. Production trust provisioning and a reviewed protected release remain pending; this internal composition is not a customer configuration flag for disabling billing in such a release.

The metered composition serves these authenticated operator routes. Existing Host and Origin checks apply, and responses are not cached. Local mode's operator or an API key explicitly listed by the deployment may use them. Ordinary workspace keys and signed-in members cannot inspect or change the installation license.

| Method | Path                           | Purpose                                                                                                       |
| ------ | ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| GET    | `/v1/runtime/license`          | License usability, installation metadata and exact offline source counters. Microcredits are decimal strings. |
| POST   | `/v1/runtime/license/activate` | Activate with `{ "activationKey": "…" }` in the JSON body only.                                               |
| POST   | `/v1/runtime/license/refresh`  | Repair time and refresh the license using the installation key.                                               |
| POST   | `/v1/runtime/license/report`   | Reconcile one page of run endings and deliver signed usage.                                                   |
| POST   | `/v1/runtime/license/close`    | Freeze the named `{ "allocationId": "…" }` for final reporting and acknowledged return.                       |

Activation and close bodies are bounded to 4096 bytes. Credentials are never returned or recorded in failure details. Shutdown stops accepting controls and joins accepted requests and background maintenance before closing storage. Definition inspection and repair remain available without a usable license. Computation and Recall are metered; other run types require complete bounds and currently refuse admission. Local model builds and candidate-upload routes are disabled.

Run `pnpm --filter @on.auto/server exec vitest run src/metering` for the local HTTP acceptance tests. They activate an actual server, run a sandboxed computation, verify one charge across replay, deliver an Ed25519-signed report, exercise automatic maintenance and stop during activation. The authority is a local fixture; Runtime-to-Studio account-service acceptance is still required.
