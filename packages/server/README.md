# @on.auto/server

The Node.js server of Auto Runtime: `src/main.ts` starts it on the composition root of `src/composition/composition-root.ts`, `dev.ts` restarts it on every save, and `auto-runtime.ts` is the command of the npm package `@on.auto/runtime`, which `npm/pack.ts` packs with the `README.md` in `npm/`; the `Dockerfile` builds its container image.

## The secrets key

`src/settings/keeper-settings.ts` reads where the value of each secret rests: by default, or where `SECRETS_KEEPER` is `ledger`, sealed in the ledger's database, and where it is `aws-parameter-store:<prefix>`, in AWS Systems Manager Parameter Store under that prefix, an absolute parameter path of at most 14 segments of letters, digits, `.`, `-` and `_`, the first beginning with neither `aws` nor `ssm`, and no slash at its end, in the region `AWS_REGION` names, or `AWS_DEFAULT_REGION` where that is not set, kept with the name of the variable it was read from; a keeper named with neither stops the start, naming `SECRETS_KEEPER` and `AWS_REGION`. `SECRETS_KEEPER_PREVIOUS` names the keeper being replaced, only beside `SECRETS_KEEPER` and the other of the two.

`src/settings/secrets-settings.ts` reads where the key that wraps the data key of each secret is held, while the ledger keeps secrets, as the current keeper or the previous one; with Parameter Store as the only keeper there is no custodian, a key setting given stops the start in words that say so, and no key file is made: in `SECRETS_KEY`, in the file `SECRETS_KEY_FILE` names, by default `secrets.key` beside a SQLite ledger, or in AWS KMS, under the ARN of a key or of an alias that `SECRETS_KEY_KMS` names, whose region is the ARN's; one of the three at most, and at most one key being replaced beside it, `SECRETS_KEY_PREVIOUS`, `SECRETS_KEY_FILE_PREVIOUS` or `SECRETS_KEY_KMS_PREVIOUS`. `src/secrets/secret-store.ts` makes a custodian of each, `localCustodian` of [`@on.auto/secrets`](../secrets/README.md#the-custodian) for a key in hand and, through `src/secrets/kms-custodians.ts`, its `kmsCustodian` for a key in KMS, and `src/secrets/secret-keepers.ts` a keeper of each keeper named, the `sealedKeeper` of the custodians for the ledger and its `parameterStoreKeeper` for Parameter Store, both from AWS with the proxy settings and `awsCredentialChain(proxy)` of `@on.auto/outbound/aws`, loaded through `import('@on.auto/secrets/aws')` (`src/secrets/aws-adapters.ts`) only where a setting names a key in KMS or a keeper in Parameter Store, so a server without either loads no part of `@aws-sdk/client-kms` or `@aws-sdk/client-ssm`, as `src/secrets/aws-loading.test.ts` holds by the modules its process has loaded. The custodian of an alias resolves it to the key it names with one `DescribeKey` and is pinned to that key until the next start, and a resolution that fails stops the start, `The secrets settings are invalid. SECRETS_KEY_KMS: The KMS alias alias/<name> it names could not be resolved to its key at start: <the custodian's words>`. `src/database/ledger-stores.ts` makes them and starts the store through `src/secrets/secret-store-start.ts`, which probes a current key in KMS before it opens the rows, one data key wrapped, unwrapped and filled with zeros, and a probe that fails stops the start, `The secrets settings are invalid. SECRETS_KEY_KMS: The KMS key <id> it names could not wrap and unwrap a data key at start: <the custodian's words>`; probes a current keeper in Parameter Store with `keeperProbed`, one parameter, `<prefix>/probe-<uuidv7>`, written, read and deleted, and a probe that fails stops the start, `The secrets settings are invalid. SECRETS_KEEPER: AWS Parameter Store under <prefix> could not write, read and delete a parameter at start: <the keeper's words>`; then moves the secrets the previous keeper keeps to the current one, a move that fails stopping the start, `… SECRETS_KEEPER_PREVIOUS: The secrets its keeper keeps could not be moved to the keeper SECRETS_KEEPER names: <the keeper's words>`, rotates, and logs where secrets are kept: `… sealed under the key <kid> that the KMS key <arn> holds, and <count> sealed under the previous key were sealed again under it`, with `, and <count> kept by the previous keeper were moved there` after it where a previous keeper is named, or `Secrets are kept in AWS Parameter Store under <prefix> in <region>, and <count> kept by the previous keeper were moved there`. The line names a prefix, a region and a key's id, never a value, a key or a credential.

## The runtime's own keys

The runtime keeps keys of its own in its secret store, beside the secrets it keeps for others, and names each by a fact in a stream of the runtime's and of no org, `runtime/own-keys`, as `@on.auto/connections` names the clients it registers dynamically in `runtime/client-registrations` (`src/secrets/own-keys.ts`, beside the composition of the store the key is read from, which `src/database/ledger-stores.ts` opens, moves, rotates and logs right before). The one fact, `own_key_kept { purpose, secret_id }`, by the runtime, `by: runtime`, is folded by purpose, the latest last, and the decider, `ownKeysDecider`, refuses a second for a purpose that has one, `conflict` of the kind `taken`, `The runtime keeps a key for retry_state already`. The one purpose is `retry_state`, the key that signs the state an MCP client sends back when it retries a call, as [`@on.auto/api`](../api/README.md) says.

At start, once the secret store is open and rotated, `retryStateKeysOf` folds the stream. Where no key is recorded for the purpose it keeps 32 random bytes in the store, as their base64, and records the fact, which the ledger appends under the version of the stream it read; where the record is refused because another server recorded one first, it forgets the row it kept and folds again, taking that one. It then reads the row, logs under a secret manager `The runtime read the key it keeps for retry_state in AWS Parameter Store under <prefix> in <region>` with the annotations `own_key`, the purpose, and `own_key_id`, the secret's id, which names its parameter, `<prefix>/<own_key_id>`, and gives the API `retryStateKeys` with that key as `current` and no `previous`, so every server that shares the ledger signs under the same key, and a rotation of the secrets key wraps it again and leaves it as it is. A row it cannot read stops the start as an `OwnKeyUnavailable`, named as the server's other start failures are, in words that name the purpose, where secrets are kept as the start's log names it (`secretsKeptBy`), the store's words and the ways out: `The key the runtime keeps for retry_state cannot be read under the key that SECRETS_KEY holds: <the store's words>. Start the server with the key the ledger's secrets were sealed under, or give that key as SECRETS_KEY_PREVIOUS, SECRETS_KEY_FILE_PREVIOUS or SECRETS_KEY_KMS_PREVIOUS beside a new key`, or, under a secret manager, `… cannot be read in AWS Parameter Store under <prefix> in <region>: <the store's words>. Start the server with the keeper the ledger's secrets were kept by, or name that keeper as SECRETS_KEEPER_PREVIOUS beside SECRETS_KEEPER`. The key is a secret like any other, so a move takes it to the current keeper with the rest. A row that is gone, `… is no longer in the secret store, so the server does not start`, or, under a secret manager, `… is no longer in AWS Parameter Store under <prefix> in <region>, the region AWS_REGION names, so the server does not start`, naming the variable the region was read from, since another region or account holds no parameter of the ledger's, one that holds something other than 32 bytes, and a key the store cannot keep at the first start, `… cannot be kept under the key that SECRETS_KEY holds, so the server does not start: <the store's words>`, stop it too; the store is closed before the start fails. A deliberate reset of the runtime's own keys is not offered yet. Nothing of the key is logged, and no key is derived from another.

## Testing

The servers the tests start in the process run on `patientWorkerPool` of `src/testing/servers/worker-pools.ts`, the server's worker pool whose checks at save may take 30 s, through `checkingWithin` of `@on.auto/definitions/testing`, and whose inputs may take 30 s, through `decidingWithin` of `@on.auto/workflow-engine/testing`, so a check or a decision that a busy machine slows is never refused by the 2 s a save allows or the 2,000 ms of an input; `scriptedWorkerPool` answers the outcomes a test scripts before it hands the rest to that pool. The refusal of a check at its deadline stays held by `src/computation/checks-over-http.test.ts` and `src/computation/checks-over-mcp.test.ts`, whose pools answer `stopped: deadline`, and the answer of a start whose input runs past its deadline by `src/workflows/workflow-deadlines.test.ts`, whose evaluations answer `exhausted: deadline`. The servers the tests spawn as processes keep both bounds.

A test that waits for what a workflow's step waits for before the step's timeout ends it runs its server on `movedClock` of `@on.auto/workflow-host/testing` and moves the clock past the timeout once it has seen the state (`src/interaction/interaction-reactions.test.ts`, `src/workflow-calls/workflow-cancels.test.ts`, `src/workflow-runs/workflow-tool-cancellation.test.ts`), and the table of the endings of a run that asks a system gives its calls `patientTiming` of `@on.auto/tool-servers/testing` and only the rows that outlast a call or an opening the short one (`src/asking-a-system/ending-rows.ts`).

The composition of main, started in the process with a shutdown timeout longer than the test, stops with an idle keep-alive connection open after a workflow ran, and while a function a workflow called still runs, without waiting for that timeout (`src/lifecycle/composed-stop.test.ts`); so no test of a spawned process holds it to how long it takes: `src/main.test.ts` holds main to its exit code alone, `src/workflows/workflow-lifecycle.test.ts` to its exit code and what it says at its start, and `src/workflows/workflow-shutdown.test.ts` to its exit code, to leaving nothing running and to taking the call it was stopped in up again once started again.

The tests start the servers, the `auto-runtime` command and the development runner they run through `spawnForTheTest` of `@on.auto/operations/testing` (`src/testing/processes/spawned-server.ts`, `runtime-command.ts` and `development-process.ts`), which ends each once its test finished, whether it passed, failed or timed out: with SIGTERM, on which the server stops, and with SIGKILL if it is still there `stoppedWithinMs`, 10 s, later; `src/lifecycle/shutdown.test.ts` holds the server's longest stop, `longestStopMs`, under that bound. Two tests start their processes through the code they test instead: `src/development/children.test.ts` through the runner's `startChild`, which starts each child in a process group of its own, and ends each with SIGKILL once its test finished, and `src/background-start/started-in-the-background.test.ts` through `startInBackgroundOf`, whose recording entry ends itself once it has written what the test reads, and whose other entry, `src/testing/entries/stay-until-signalled.ts`, runs until the test signals it through the handle the start hands back, with `endWithTheTest` registered for its pid. The processes the helper starts are attached to the test's worker, in its process group, so a signal to that group, as Ctrl+C in a terminal sends, stops them too; a worker that dies alone runs no hook, and leaves them running until they next write to the output it held. A runtime started in the background, `start --background --instance <id>`, runs in a process group of its own and writes to its log, so nothing of the test's ends it with the test. `src/agent-relay/agent-relay.test.ts` starts one alone, in the test that proves it runs on outside the process group of the agent that started it, and starts a second one the same way once the first was stopped; another has the relay start one as it starts, and a second once the test stopped the first and the relay's grace passed; two of its other tests start the runtime in a terminal, attached, and another starts none, since another program holds its port. `src/agent-relay/relay-replacement.test.ts` starts one in place of a runtime in a terminal that the test stops, and one through the relay of `src/testing/entries/relay-with-short-bounds.ts`, which the test freezes with SIGSTOP and the relay stops and replaces; its third test freezes a runtime in a terminal, which the relay leaves alone, and lets it go on with SIGCONT before it stops it with Ctrl+C. Each test that lets a relay start a runtime registers, before anything starts, `runtimesStartedInTheBackgroundEndedWithTheTest` of `src/testing/processes/background-runtimes.ts`. Once the test finished, it reads the lines the relay writes to the `runtime.log` of the test's home as it acts, `Auto Runtime was started in the background as process <pid>, instance <id>` and `Auto Runtime, process <pid>, ended`, and ends each process started and not ended: with SIGTERM, and with SIGKILL if it is still there `stoppedWithinMs` later, each sent only while its command line, as `ps` reads it, still carries that instance, and the process counts as gone once it no longer does. It asks the port nothing, so a runtime that answers slower than a probe's 2 s, or one whose relay was ended while it held the starting lock, is ended all the same, and a pid used again by another process is not signalled. The suite's teardown does the same with what a test left in the temporary folder of the run, as when its worker died or its hook timed out: `vitest.config.ts` names `src/testing/test-run/test-run-folder.ts` in place of the shared global setup, `aFolderOfTheTestRun` of `@on.auto/operations/test-run-folder` over `runtimesStillRunningInTheBackgroundIn` of `src/testing/processes/runtimes-in-the-background.ts`, which reads the `runtime.log` of each home left there, so a runtime still running in one is ended once the run ends and named, with its home, in the failure of the run.

The relay of `auto-runtime mcp` holds its bounds on Effect's test clock, in `src/agent-relay/relay-watch.test.ts`, `src/agent-relay/relay-losses.test.ts` and `src/runtime-recovery/runtime-stop.test.ts`; `src/agent-relay/relay-replacement.test.ts` runs a relay on real time with a silence of 1 s and a stop of 0.5 s in place of 15 s and 9.1 s, and holds what happens, never how long it took. The waits of its start, for a runtime it starts to answer, for an older one to stop and for one that restarts to come back, probe the port every 100 ms on Effect's clock and end with the relay: a start the relay makes while it relays ends at once when the agent leaves, aborts the probe in flight and frees the starting lock. `src/background-start/background-start.test.ts` holds them on the test clock, by the probes its fake answers and by the time they take, and `src/local-runtime/runtime-commands.test.ts` holds the waits of `stop` and `restart`, which run the same way. Some tests keep a bound on real time on purpose. `src/lifecycle/shutdown.test.ts` holds a request still running to being cut off no sooner than the shutdown timeout less 50 ms, a lower bound a slow machine only lengthens. `src/computation/computation-deadline.test.ts` holds a run that never ends by itself to being refused no sooner than its 10 s deadline less the slack of a timer, and a read of the definition and a run on another worker to answering before that deadline, a race the server wins by the pool's 10 s on the real clock, which the pool keeps and no clock of the server reaches; its saves check within 30 s through `checkingWithin`. `src/reasoning/large-answers-on-stores.test.ts` holds a reasoning run whose 25 calls each answer 1 MB to reading every answer back within `toolBounds.runMs`, the 600 s a run that calls tools may take, on the real clock on purpose, since that is the bound such a run meets in the server. `src/telemetry/start-telemetry.test.ts` holds the shutdown of telemetry whose collector cannot be reached to within 1.5 s, since that shutdown races its exports against a timer of 1 s of the platform, for which the exporters take no clock. `src/development/source-changes.test.ts` saves a file again every 500 ms until the watcher reports it, and `src/workflows/workflow-lifecycle.test.ts` waits until the timers of a stopped server's runs are due before it starts the next process, waits a slow machine only lengthens.
