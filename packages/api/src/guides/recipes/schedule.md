# Run a workflow on a schedule

A workflow can start on its own: at set times, in UTC or in a time zone it names, every so often, or whenever an event of a given type is published to the playbook. Read the workflow guide and the triggers guide with get_guide before you write one.

1. Ask the person which workflow to run and when, such as every weekday at 9:00 their time, or whenever the month's books are closed. Find the workflow with list_definitions, `type` workflow, or write one in the format of the workflow guide.
2. Give the workflow a `schedule` as the triggers guide says, with one trigger or up to three, each kept on its own: `cron` with five fields, minute, hour, day of month, month and day of week, read in UTC or in the time zone `time_zone` names beside it; `every` with a duration of at least a minute; and `on` with the type of the events that start it. A run its schedule starts runs as the playbook itself, with its due time, or a list of the event, as its input, and its history says which trigger started it.
3. When the times are the person's own, such as 9:00 their time, put `time_zone` beside `cron` with the IANA name of their time zone, such as `America/New_York` or `Europe/London`, and write the five fields in their time: the runs then stay at their hour when the clocks change for daylight saving. Leave it out only for times meant in UTC. `every` takes no time zone.
4. A run on a clock is given its due time alone, so it finds what is new from that: what came since the time before, such as in the 30 minutes before `schedule.due` for `every: PT30M`. A time skipped while the run before still ran, or one whose run failed, is not run again, so give the workflow an input of its own too, such as `since` and `until`, with which the person runs it by hand for a stretch it missed, and let `input.from` take either: `'${ $data.schedule === undefined ? $data : ({ since: new Date(Date.parse($data.schedule.due) - 1800000).toISOString(), until: $data.schedule.due }) }'`. In a time zone, the stretch between two daily times is 23 or 25 hours on the nights the clocks change.
5. To start a workflow when a step of another one ends, give it `on` with a filter on that step's run: `type: run_succeeded`, a `subject` naming the function, such as `computation/work-out-order`, and `calldepth: 1`, which a run by hand does not carry. Or have the other workflow `emit` an event of a type of your own; in a `for`, it emits one for each item.
6. Show the person the document, and save it with update_definition, or with create_definition for a new workflow, once they agree.
7. Tell the person when it runs next, in their own time, and that every run is kept in the playbook's history. Auto does not list the times ahead, so work the next one out from the trigger. `every` counts from the save that gave the trigger its present form, the workflow's `created_at` where it has not changed since; a later save that leaves it as it is keeps its times.
8. To see how its runs went, call list_runs with `type` workflow and the workflow's `name`, and get_run for one run.
9. A run an event started that was rejected or failed is not started again, and the same event published again is a repeat, which records nothing. list_runs with `status` rejected, or failed, finds such runs, and list_playbook_events given a run's `run_id` shows its input, the list holding the event. To finish its work, run the workflow by hand with the event's `data`, which `input.from` takes as it takes the event: `'${ Array.isArray($data) ? $data[0].data : $data }'`.
