# Give the playbook tools

A reasoning function can call the tools of the tool servers that whoever runs this server set up for the playbook, naming each tool as `server/tool`, or `server/*` for every tool of a server; a connection a person added to the org is named the same way, by its name. Read the reasoning-function guide with get_guide before you write one.

1. Call search to see the tool servers this playbook may use and their tools; when the person named a server, give its name as `server`, and give `terms`, a few words of what the person wants done, to find the tools that fit among many. Call introspect for the input_schema of a tool before writing its arguments.
2. When no server is listed, or not the one the person wants, and search answers `providers`, call add_connection with the name of a provider there that serves what the person wants, or, where none does, with the server's address and how the server takes its key, never the key: for an MCP server, `authorization` first, the credential's `kind` alone, and where the runtime answers that the server offers no consent, how it takes its key. Give the person the link it answers, on which they approve it, signing in or giving the key; then call search again. Where search answers no `providers`, tell the person that whoever runs this server sets tool servers up in its settings file, `auto-runtime.yaml`, under `tool_servers`: the server's address, a header that takes its key from an environment variable, and the org it serves, with `allowed` naming the tools a function may call. The server reads them when it starts again. Nothing more can be done here until then.
3. When a server says it cannot be asked just now, tell the person why, in its words; whoever runs the server can look into it.
4. To learn what a tool answers, call it with execute, with the arguments its input_schema takes, and read its `text`: that is what the function's model will see. Never make a function to look. A tool whose `read_only` is false may change something, so call it only once the person agrees. When a prompt needs an id, such as a channel's, call the tool that lists them and take the id from its answer, confirming the choice with the person.
5. Ask the person what the function should do with the tools, and which of them it needs.
6. Write a reasoning function whose `tools` name those tools in the format of the reasoning-function guide, show it to the person, and save it with create_definition, `type` reasoning, once they agree.
7. Run it with run_definition. A run that called tools and did not succeed is not run again under its id, since a tool may have changed something: read what it called with list_playbook_events, given its `run_id`, and start a new run only if the person still wants one.
8. Tell the person what the run did with the tools, and that the function can call only the tools it names.
