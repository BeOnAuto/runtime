# Connect a service

A playbook's runs act on the services connected to the org, and expect what they act on to be there already: a team with the statuses work moves between, a channel, a label, a folder, a project. A run does not set a service up. You do, here, with the person, before the first run, and you ask for the access that takes when you ask for the connection.

1. Before you connect anything, work out two things with the person: what the playbook's functions and workflows will do at the service, run by run, and what must exist there first for that to work. Name each thing, and whether it is there already.
2. Call search with `terms` for both kinds of work: the tools the playbook's functions will call, and the tools that create what must exist. Where the person named a server, give its name as `server`. Call introspect for the input_schema of a tool before writing its arguments.
3. When no server offers them, and search answers `providers`, call add_connection with the name of the provider that serves what the person wants, and in the same call ask for what setting the service up needs: where search lists a group of `more` under the provider that covers it, name it in `more`, so the person approves once. Where none of the provider's tools can make what must exist, and the service has an HTTP API or an MCP server that can, add that too, by hand: for an MCP server, `authorization` first, the credential's `kind` alone, and where the runtime answers that the server offers no consent or that it cannot connect it by consent, how it takes its key, never the key. Give the person each link add_connection answers, on which they approve it, signing in or giving the key. Where search answers no `providers`, tell the person that whoever runs this server sets tool servers up in its settings file, `auto-runtime.yaml`, under `tool_servers`; the server reads them when it starts again, and nothing more can be done here until then.
4. When a server says it cannot be asked just now, tell the person why, in its words; whoever runs the server can look into it. Where search says a server's connection is `connection_broken` and its words say to reconnect it, call reconnect_connection with its `connection` as `id` and give the person the link it answers, rather than removing the connection and adding it again. Where the service is connected already and lacks the access setting it up takes, list_connections offers the groups the connection may still be granted; ask for one with reconnect_connection, given its name as `more`, and give the person that link.
5. Once list_connections says a connection is connected, read what the service holds with query_connection, and tell the person what you found and what you would reuse.
6. Show the person what you would create and change. Once they agree, make each change with execute_connection and read it back with query_connection. Where no connected tool can make a change, tell the person exactly what to change in the service and where, and read it back once they say it is done. Never make a function or workflow to set a service up.
7. Keep the ids you read, such as the team's and each status's, for the functions that use them. Then tell the person what is set up and what the connection can do, and give the playbook its tools with the give-tools recipe.
