# Connect a service

A playbook's runs act on the services connected to the org, and expect what they act on to be there already: a channel, a folder, a label, a field, the stages work moves through. A run does not set a service up, nor does it check that one is set up. You do, here, with the person, before the first run, and you ask for the access that takes when you ask for the connection.

1. Before you connect anything, work out two things with the person: what the playbook's functions and workflows will do at the service, run by run, and what must exist there first for that to work. Name each thing, and whether it is there already.
2. Call search with `terms` for both kinds of work: the tools the playbook's functions will call, and the tools that create what must exist. Put the service's name in `terms` too: search finds a provider by the words of its name, title and description. Where the person named a server, give its name as `server`. Call introspect for the input_schema of a tool before writing its arguments.
3. When no server offers them, and search answers `providers`, call add_connection with the name of the provider that serves what the person wants, and in the same call ask for what setting the service up needs: where search lists a group of `more` under the provider that covers it, name it in `more`, so the person approves once. Where none of the provider's tools can make what must exist, and the service has an HTTP API or an MCP server that can, add that too, by hand, as step 4 says. Give the person each link add_connection answers, on which they approve it, signing in or giving the key. Where search's answer to a call without `server` has no `providers` at all, no connection can be added here: tell the person that whoever runs this server sets tool servers up in its settings file, `auto-runtime.yaml`, under `tool_servers`; the server reads them when it starts again, and nothing more can be done here until then.
4. Where search lists `providers` but none serves the service, or its provider's tools cannot do what is needed, connect what the service itself offers, by hand, in this order. Where its own documentation names an MCP server, add that, leaving its credential out, since the server says how it authenticates; where add_connection refuses it with an error at `/credential` saying the server names no way of its own to authenticate, call it again with the credential saying how the server takes its key, never the key. Otherwise add its HTTP API, of `type` `openapi`. Give `document` only where the service's documentation states the address of its OpenAPI document. Otherwise write that document yourself from the documentation, describing the calls the job needs and their parameters, and give it as `document_text`, with `base_url`, the address the documentation gives for those calls; the credential says where the key goes, the header or query parameter the documentation names, and with `instructions` and `key_page` where the person makes it. Where the documentation gives no address for those calls, tell the person the service cannot be connected this way. Never guess an address, never ask the person for one, and never ask them to host a file or to write anything technical: the person pastes the key on the page and approves. Where add_connection refuses the document, its words name the place to correct; correct it and call again.
5. When a server says it cannot be asked just now, tell the person why, in its words; whoever runs the server can look into it. Where search says a server's connection is `connection_broken` and its words say to reconnect it, call reconnect_connection with its `connection` as `id` and give the person the link it answers, rather than removing the connection and adding it again. Where the service is connected already and lacks the access setting it up takes, list_connections offers the groups the connection may still be granted; ask for one with reconnect_connection, given its name as `more`, and give the person that link.
6. Once list_connections says a connection is connected, read what the service holds with query_connection, and tell the person what you found and what you would reuse. For an HTTP API whose document you wrote, read with one of its calls first and tell the person what came back: a call the document declares as GET or HEAD is marked reads, which query_connection calls; any other may change something, so call it with execute_connection, once the person agrees. Where the service answers that first read by saying a path or a parameter is wrong, correct the document: read the connection with list_connections, remove it with remove_connection, and add it again with what list_connections answered for it, its `name`, `type`, `credential` and its whole `entry`, with the document corrected in `document_text`; then tell the person they will approve it and paste the key once more, or make a new key where the service shows a key only once.
7. Show the person what you would create and change. Once they agree, make each change with execute_connection and read it back with query_connection. Where no connected tool can make a change, tell the person exactly what to change in the service and where, and read it back once they say it is done. Never make a function or workflow to set a service up or to check that it is set up: that is your work, with these tools, before the first run and whenever something there changes.
8. Keep the ids you read of what must exist, for the functions that use them. Then tell the person what is set up and what the connection can do, and give the playbook its tools with the give-tools recipe.
