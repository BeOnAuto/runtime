# @on.auto/api

The API of Auto Runtime: the handler the server answers every request with. It serves each operation of a catalog three ways: as an HTTP route, as an MCP tool, but for an operation served over HTTP alone, which is a route and no tool, and as an operation of the OpenAPI document of the routes. The routes and the tools run the operation through the same dispatcher, so a call means the same thing whichever way it arrives. The operations themselves are defined on the application layer, [`@on.auto/operations`](../operations).

## Every request

Each request passes through the same chain before it reaches an operation, in this order:

1. It gets an `x-request-id` and the security headers.
2. An `Origin` that is not an origin a page may come from gets `403` `origin_not_allowed`; in local mode, a `Host` that is not a localhost name gets `403` too. The origins a page may come from are `pageOriginsOf` of `@on.auto/identity`, which `src/middleware/validate-origin.ts` and `src/middleware/cors.ts` read for each request, and so does the identity service for the `azp` of a session: the Studio host's, the `origin` of `ApiOptions.studio`, then, where the runtime serves Studio, the origin the API answers at, `publicOriginOf` of `src/discovery/public-addresses.ts`, so that a page the runtime serves calls it as the Studio host's page does, and the origins of `ALLOWED_ORIGINS`.
3. A CORS preflight from an allowed origin gets `204`, and `Access-Control-Allow-Private-Network: true` where it carries `Access-Control-Request-Private-Network: true`, as a browser's does before a page on a public origin reaches a server on a loopback or private address. Every other answer to an allowed origin exposes `x-request-id`, `x-trace-id`, `www-authenticate` and `Date` to the page, so a page reads the server's time. Both are set in one place, `src/middleware/cors.ts`.
4. The caller authenticates with `Authorization: Bearer <key or token>`, or as the local developer in local mode, which ignores a key or token the request presents; a request without a valid key or token gets `401`. Any other credential, of a scheme the API does not know, is a malformed `Authorization` header, `400`, over HTTP and MCP alike. `authenticate` of the `Authenticator` of `@on.auto/identity` is asynchronous and takes the path of the MCP endpoint the request reached, if it reached one, since a signed-in person's access token may name that endpoint as its audience; a refused token's `401` says why in its `detail`, `The token was refused: <the rule or the claim it failed>`, and never names a value of the token. A page at an allowed origin sends the session the identity service gave it as its token, which names no audience: `authenticate` also takes the request's `Origin`, and the session is taken only on a request whose `Origin` is its `azp`, so on the MCP endpoints as over HTTP it serves its own page and never an agent, as the identity package's README sets out.

**Signed-in persons.** With sign-in on, the authenticator carries the protected resource, `PUBLIC_URL` and the Auto identity service's issuer, and the API serves `GET /.well-known/oauth-protected-resource` and the same path followed by `/mcp`, `/orgs/{org}/mcp` and `/orgs/{org}/playbooks/{playbook}/mcp` before the chain checks a credential, as public paths matching that prefix, answering [RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728) metadata: `resource` is `PUBLIC_URL` followed by the path after the prefix, `authorization_servers` the identity service's issuer, `bearer_methods_supported` `["header"]`, `scopes_supported` the scopes a sign-in asks for, `signInScopes` of `@on.auto/identity`: `user:org:read`, which asks the identity service for a token bound to the organization the person signs in to, then the four permissions, which the identity service grants as scopes of its own, and `resource_documentation` the public MCP reference; a path under the prefix that names no endpoint, or an org or playbook id that is not one, is `404`. A `401` then carries `Bearer resource_metadata="<PUBLIC_URL>/.well-known/oauth-protected-resource", scope="<the sign-in scopes>"`, the five separated by spaces, after `error="invalid_token"` when a credential was refused, and its detail says a key or a token. With sign-in off none of this is served, the metadata's path needs a key, and the challenges are `Bearer` and `Bearer error="invalid_token"`. The challenges are built in `src/authentication/challenges.ts` and the metadata in `src/authentication/protected-resource.ts`.

Before that chain, a browser opening `/` (a `GET` that accepts `text/html`) gets a page saying the server is running, with a button that opens Studio on this server: the Studio a person can reach, `studioBaseOf` of `@on.auto/identity`, followed by `?server=<this server's origin>`, which is `<this server's origin>/studio/?server=…` where the runtime serves Studio and `https://studio.on.auto/?server=…` for the default Studio host otherwise. The page needs no key and loads nothing from any server: its styles, its icon and its typefaces, DM Mono and DM Sans, are inside it. The two font files and their SIL Open Font Licenses are in `src/landing/fonts`; `readPageStyle(shippedFiles)` reads them, as files of `@on.auto/api` at the root `apiShippedRoots()` declares (`src/shipped-files/api-roots.ts`), through the `ShippedFiles` of `@on.auto/operations` the server composes, once, and answers the page's styles, which its content security policy hashes, as a `PageStyle`, which the server reads at its start and gives the API as `ApiOptions.pageStyle`, so a typeface that cannot be read stops the start (`src/landing/page-style.ts`, `src/landing/fonts.ts`). Any other request to `/` has no route.

**The served Studio.** A page on a public origin may not reach an address on the person's machine, so a runtime may serve Studio itself, at `/studio/` on its own origin. `ApiOptions.studio` says whether it does: a `HostedStudio`, `served: false`, serves none, and `/studio/` has no route; a `ServedStudio`, `served: true`, carries `host`, a `StudioHost`, which answers a path asked of the Studio host with a `StudioAnswer`, its status, content type, body, the seconds a browser may keep it, the host's validators, `ETag` and `Last-Modified`, and, for a redirect, the path on the host it sends the browser to, or with nothing when the host cannot be reached and nothing was kept. `GET` and `HEAD` under `/studio/` answer what the host answers for the same path under its root, without the query, with its status, its content type, its body, its `ETag` and `Last-Modified`, a redirect's `Location` under `/studio/`, and `Cache-Control` `public, max-age=<seconds>, immutable` for what the host keeps fresh or `no-cache` for the rest; every other method is `405` `method_not_allowed` with `Allow: GET, HEAD`, `/studio` is sent on to `/studio/` with its query by `308`, since the page resolves its files against the folder it was served from, and a path that holds `..`, written or with a dot percent-encoded, is `404` `not_found` before the host is asked (`src/studio/served-studio.ts`). When the host answers nothing, the runtime answers `503` with a page of its own, `src/studio/unreachable-studio.ts`, which runs no script and says that Studio cannot be fetched now and from where. A request at `/studio` or under `/studio/` needs no key, since a browser opening a page sends none, and passes the `Origin` check and, in local mode, the `Host` check as every other request does (`src/middleware/public-paths.ts`). Its answers carry a content security policy of their own, `servedStudioPolicyOf` of `src/studio/studio-policy.ts`, written once from what Studio's build loads: `default-src 'none'; script-src 'self'; worker-src 'self'; style-src 'self' 'unsafe-inline'; font-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`, for its module scripts and the worker of its editor, its style sheets and the style elements it writes as it runs, its fonts and its images, the `data:` images its style sheets hold, and its calls to the runtime, every one from the runtime's origin. The page the host answers holds an inline script, so a `text/html` answer's `script-src` also allows each inline script of that page by its SHA-256, read from the page as the host answered it; every other answer under `/studio/` carries the policy with no hash, set by `src/middleware/response-headers.ts`. Every other path keeps `default-src 'none'; frame-ancestors 'none'`, and the other security headers are the same under `/studio/` as elsewhere.

A path with no route gets `404` `not_found`, and a method the path does not serve gets `405` `method_not_allowed` with an `Allow` header. Every one of these errors is an [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem document.

## Telemetry

`ApiOptions.requests`, when given, is the first middleware of every request: the server's, which traces the request with `@hono/otel` when telemetry is on, sets the `x-trace-id` header and hands the request's span to the operation as `traceParent`. The route runs the operation under that span, `underTraceParent`, which also names the trace in the logs as `trace_id`, and an MCP tool call is a `tools/call <tool>` server span linked to the `traceparent` its `_meta` carries. The API itself takes no OpenTelemetry dependency; CORS allows `traceparent`, `tracestate` and `baggage` and exposes `x-trace-id` whether telemetry is on or not.

`ApiOptions.callContext(request)`, when given, makes the context of a call of the request, an Effect `Context` of the services a shell binds to the invocation that answers it, such as the fetch it reaches the network with, `CallFetch` of `@on.auto/operations`, which the tool access and the consent client send that call's requests through, and the identity it acts as, and every route that dispatches an operation provides it to that operation: an operation route to the call it dispatches, and an MCP endpoint, through the hand-off to the SDK beside the caller (`orgCallOf`), to the call each tool dispatches. The dispatcher leaves those services in place, so an operation and the capabilities it runs read them as they read any service, and a shell binds them to the request rather than to the span of the request. A server that gives none provides an empty context (`noContextOfTheCall`; `src/operations/call-context.test.ts`).

## Over HTTP

`operationRoutes` registers one route per operation. An org operation's route is relative to `/v1/orgs/{org}`, a playbook operation's to `/v1/orgs/{org}/playbooks/{playbook}`; literal segments win over parameters wherever two routes could match the same path.

- **Input.** The operation's input is one object assembled from the path parameters, the query string of a `GET` or a `DELETE`, which take no body (`takesNoBody` of `@on.auto/operations`), and the JSON body of a `POST` or `PUT`. A query is routed by `GET`, or by `POST` where its input is an object a query string cannot carry, as `validate` and `dry_run` of `@on.auto/tool-servers` are, and takes its body then; the method decides nothing else, so such a query is still a read, under the read permission of its scope and marked read-only over MCP. A field may come from only one place; giving it twice is `400` `bad_request`, and so is a query string on a `POST` or `PUT`. Query values arrive as strings and decode with the `strings` encoding; a body decodes with the `json` encoding.
- **Body.** A body must be a JSON object sent as `application/json` in UTF-8, with no `Content-Encoding` other than `identity`, and no larger than 1 MiB. Otherwise it is `413` `content_too_large`, `415` `unsupported_media_type` or `400` `bad_request`.
- **Answer.** A success is the operation's output as JSON with the operation's success status (`200`, or `201` where the operation says so) and `Cache-Control: no-store`.

**An operation served over HTTP alone** (`defineHttpOperation` of `@on.auto/operations`, whose registration carries `servedOverHttpAlone`) takes the body it declares. A `json` body is read as every body above. A command that takes `none` refuses a body with `400` `bad_request`, "This operation takes no body", and a query takes its input from the path and the query string as any query does. An `octet-stream` or `csv` body reaches the handler as a stream, with its media type and the length its `Content-Length` declares, and the input is the path's fields alone; before the body is read, a `Content-Encoding` other than `identity`, a media type other than `application/octet-stream` or `text/csv`, or a charset other than UTF-8 is `415` `unsupported_media_type`, a body without a `Content-Length` is `411` `length_required`, one whose `Content-Length` is not a whole number is `400` `bad_request`, and one whose `Content-Length` passes the operation's most bytes is `413` `content_too_large`, saying the bound. An operation whose answer is JSON is answered as every operation is; one whose answer is a stream is answered with its bytes, the media type its answer declares, its length as `Content-Length`, the success status and `Cache-Control: no-store`. The route counts the bytes it hands over against the length the answer declares, and a stream that ends short of it or runs past it fails as a stream that fails does. The route reads the stream's first chunk before it answers, so a stream that fails before it is a `500` `internal` problem document, whose `instance` names the incident it reports through `reportIncident` with the request id and the call, its operation, org, playbook and caller, as the dispatcher reports an incident. A stream that fails after it is reported the same way, and the answer is aborted: in process its body fails with an opaque error that names the incident and not the failure, and on Node the route's binding, `abortConnection`, destroys the connection, so a client never takes the bytes it received for the whole answer, receives nothing of the failure's words, and receives none of the answer when the failure comes before the adapter sent the status. A client that leaves before the end cancels the stream, and one that leaves while the route waits for the first chunk cancels it then, through the request's signal, and is answered `499` `client_closed_request` with no incident. The refusals of a body, `415`, `413` and its words among them, are defined once, in `src/operations/body-problems.ts`, for a JSON body and a streamed one alike.

An outcome that is not a success becomes a problem document. The problem document has one Effect schema, `ProblemSchema` in `src/problem/problem-document.ts`, whose reasons each carry their status, title and words, and from which its TypeScript type, the table of reasons and statuses `problemOf` reads and the JSON Schema of the OpenAPI document all derive, so the code and the document cannot drift. Its `type` is `https://on.auto/problems/<reason>` and its `title` the reason's, except for a kind that has a type of its own, `kindsWithTypes` of `@on.auto/operations`, which takes the status of its reason and its title from its name: a rejection of the kind `tools_unfinished`, a run whose every tool only reads and that could not finish, is `https://on.auto/problems/tools_unfinished`, titled `Tools unfinished`, with its reason `unavailable` and its status 503, one of the kind `effect_unknown`, a run that called a tool that may change something and could not finish, is `https://on.auto/problems/effect_unknown`, titled `Effect unknown`, with its reason `conflict` and its status 409, one of the kind `tools_called` is `https://on.auto/problems/tools_called`, titled `Tools called`, with its reason `conflict` and its status 409, and one of the kind `rebuilding`, a recall function whose view is still being built, is `https://on.auto/problems/rebuilding`, titled `Rebuilding`, with its reason `unavailable`, its status 503 and `Retry-After`, since trying again later may succeed. The workflow engine raises the same types for them, never a communication or runtime error, and a workflow that ends with one is rejected with its reason and kind.

| Outcome   | Status and reason                                                                                                                                                                                                                                                                                                                                  |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| rejected  | the status of the rejection's reason, such as `403` `forbidden`, `404` `not_found`, `409` `conflict`, `409` `cancelled` for a run that was cancelled, `410` `unanswered` for a run whose request nobody answered or `422` `invalid_input` with an `errors` list, and the rejection's `kind` and `because`, where it has them, as extension members |
| failed    | `500` `internal`, saying nothing about the cause; its `instance` is `urn:uuid:<id>`, the incident id under which the server logs the error                                                                                                                                                                                                         |
| cancelled | `499` `client_closed_request` when the client went away, `503` `unavailable` when the server is stopping                                                                                                                                                                                                                                           |

A route refuses a caller its principal does not admit to the org of the path with `403` `forbidden`, "The caller does not belong to this org", before it reads the input, as the MCP endpoints do; the dispatcher's own check of the org still holds for every call. A `403` `forbidden` also carries `WWW-Authenticate: Bearer error="insufficient_scope"`, and, with sign-in on, the operation's permissions, its registration's `permissions`, any one of which permits it, as `scope` and `resource_metadata` with the root metadata, for a caller of another org as for a caller that lacks the permission; `insufficientScope(resource, permissions, resourcePath?)` of `src/authentication/challenges.ts` builds it. With sign-in off the challenge names no scope, since there is no authorization server to ask. A `503` `unavailable` carries `Retry-After: 5` when a retry of the same request may resolve it, so not for the kind `tools_unfinished`, a run that called tools that only read and could not finish, which the same request answers with `tools_called` and a new run may make, nor for the kinds `tool_not_offered` and `model_not_offered`, which a change of the function or the configuration resolves, or, for a connection whose credential cannot be read just now (`connection_unavailable`), whoever runs the server putting the secret store right: a later try may then pass, but no hint of seconds says when, and one would invite a loop of retries, nor for a rejection whose `because` is `builds_of_the_day`, a prediction function that has had its builds of the day, `stalled`, a dataset stopped at an event, `not_finite`, a model that answers what it cannot, or `not_in_order`, a model whose low is above its likely value or whose high is below it, which no wait resolves (`notResolvedByWaiting`). A `410` `unanswered` carries none: the same request answers it again.

## The OpenAPI document

`openApiDocumentRoutes` serves the catalog a third time, as the OpenAPI 3.1.1 document of the HTTP routes at `GET /v1/openapi.json`, `guideRoutes` serves each guide at `GET /v1/guides/<name>`, and `apiCatalogRoutes` serves the API catalog at `GET /.well-known/api-catalog`, below. All three take the one guide shelf the server builds with `guideShelfOf` and hands to `mcpRoutes` too. The document is built from the catalog when its route is registered, at start, kept as its JSON text and answered with `Content-Type: application/json`. A client built from the document matches the release its `info.version` names: an output schema is a closed object, since the runtime answers exactly those fields, and a later release may add fields. None of the document, a guide and the catalog needs a key: each is added with `routes.addPublic`, as `/health` and the client metadata document are, so its exact path passes the chain without its origin, host and key checks (`src/middleware/middleware-chain.ts`), since it names no secret and is the documentation of the surface; any other path, a guide the shelf does not hold among them, needs a key as every path does, except, with sign-in on, the protected resource metadata at `/.well-known/oauth-protected-resource` and under it, which passes the same checks by its prefix, as [Every request](#every-request) says.

- **Header.** `openapi` is `3.1.1` and `jsonSchemaDialect` JSON Schema 2020-12; `info` has the title `Auto Runtime`, the version the server passes as `serverInfo`, and one paragraph, `src/openapi/document-description.ts`, that opens as the MCP instructions do without naming MCP; `servers` is `[{ url: "/v1" }]`, relative, so the document holds behind any host or gateway. The paths are the catalog's own form, `/orgs/{org}/…` and `/orgs/{org}/playbooks/{playbook}/…`, from `catalogPathOf` of `@on.auto/operations`, which the route table prefixes with `/v1`.
- **Operations.** One per registration. `operationId` is its name, or `<name>_in_org` for an org operation whose name a playbook operation has too; `summary` is its title and `description` its description, the text its MCP tool has; `tags` holds the one resource it acts on, the first segment of its route, `interactions` for `answer_interaction` and `prediction` for the five operations of prediction functions served over HTTP alone (`src/openapi/operation-tags.ts`). `parameters` are the path's fields, `org` and `playbook` by reference to `components.parameters` with their patterns, and, for a `GET`, the input's other fields as query parameters with their schemas, a definition a field names inlined; a `GET` whose input is one of several is refused at start, since query parameters cannot tell them apart. The `requestBody` of a command, and of a query routed by `POST` for an input a query string cannot carry, is `application/json` with the input's schema less its path fields, required when the input, its path fields aside, refuses `{}`, by a field it requires or by a check of the whole input, `refusesEmptyBody` of the registration, or a streamed body's media type with its most bytes in its description; a command that takes no body has none. `responses` holds the success status with the output's schema, or a streamed answer's media type and no schema, and each problem the operation can answer by reference to one response per set of reasons at a status under `components.responses`, named by its reasons, such as `forbidden_or_origin_not_allowed`, and `conflict` or `conflict_or_cancelled` at `409`, by the reasons the operation adds: `bad_request`, `unauthenticated`, `forbidden` and `origin_not_allowed`, `not_found`, `method_not_allowed`, `content_too_large`, `unsupported_media_type`, `invalid_input`, `internal` and `unavailable`, which a server that is stopping answers, for every operation, `conflict` for each command of a playbook, which a retired playbook answers, `length_required` for a streamed body, and the reasons the operation declares. `security` is the `bearer` requirement, without scopes, and an `openIdConnect` requirement for each permission that permits the operation, with that permission as its one scope, such as `[{ bearer: [] }, { openIdConnect: ['playbook:read'] }]`, so a generated client knows what to ask the identity service for; `list_playbooks` and the org's `search`, which `org:read` or `playbook:read` permits, have a requirement of each, since the requirements of `security` are alternatives and every scope of one requirement is required.
- **Schemas.** A registration carries its `output` as a JSON Schema document beside its `input`, or, served over HTTP alone, its `answer`: the JSON answer's schema or the streamed media type and no schema. In the document each input and output schema is self-contained, with its `$defs` inside it and those nothing refers to left out, and has an `$id` of its own, `https://on.auto/schemas/runtime/<operationId>/input` or `/output`, so a `$ref` of `#/$defs/…` resolves within that schema and not against the document.
- **Components.** The problem document's schema, `https://on.auto/schemas/runtime/problem`, the shared responses, the `org` and `playbook` parameters, the `bearer` scheme, of type `http`, whose description says what a key is, when a server is in local mode and what local mode takes, and the `openIdConnect` scheme, whose `openIdConnectUrl` is `IDENTITY_ISSUER` followed by `/.well-known/openid-configuration`, which `openApiDocumentRoutes` takes as `identityIssuer` from the server, and whose description says what a signed-in person's token is, the org it acts in and that its permissions are the scopes it was granted. The document names it whether `PUBLIC_URL` is set or not, since the issuer has a default; a server without `PUBLIC_URL` refuses such a token. No member is an `x-` extension: what the specification cannot say, such as a byte bound or a cursor's meaning, the descriptions say.
- **Guides.** `get_guide` is the path `/guides/{guide}`, under the `guides` tag, with the names of every guide the shelf holds, the recipes among them, as the enum of its parameter and their titles in its description, answering `text/markdown` and needing no key, `security: []`. `GET /v1/guides/<name>` answers a guide's text byte for byte as the MCP resource `guide://<name>` reads it, with `Content-Type: text/markdown; charset=utf-8`; the path of each guide is its own, so the document lists no problem for it.

**The API catalog.** `GET /.well-known/api-catalog` answers the catalog of this server as RFC 9727 describes it, a linkset (RFC 9264) of the media type `application/linkset+json` with the API catalog's profile: one context, the catalog, whose `item` is the API at `/v1`, and one, the API, with its `service-desc`, the document, a `service-doc` for each guide on the shelf, in its order, with its title and `text/markdown`, and its `status`, `/health`. Every anchor and address is absolute on `PUBLIC_URL` when it is set, the `publicUrl` of the protected resource `Routes` carries, and on the origin the request came in on otherwise; `publicOriginOf` in `src/discovery/public-addresses.ts` is the one place that knows where it comes from. Without `PUBLIC_URL`, behind a proxy, the addresses carry the scheme and host the server itself receives, and no `X-Forwarded-*` header is read. The answer, and `HEAD` on it, carries `Link: <origin/.well-known/api-catalog>; rel="api-catalog"`, and `/health` carries `Link: </.well-known/api-catalog>; rel="api-catalog"`, so a client given only the health address finds the catalog. The catalog is not an operation of the document.

**The client metadata document.** Where the runtime signs people in at an `https` `PUBLIC_URL`, it names its client at an authorization server by the address of a Client ID Metadata Document, `{PUBLIC_URL}/oauth/client.json`, as [`@on.auto/tool-servers`](../tool-servers/README.md#the-runtime-as-a-client) sets out, and `clientMetadataRoutes(metadata)` serves it (`src/discovery/client-metadata.ts`): `metadata`, a `ClientMetadataDocument`, is `address`, the address the client is named by, and `document`, the JSON answered there, which the server makes with `clientMetadataDocumentOf` of `@on.auto/tool-servers` from `PUBLIC_URL` and the return address of a consent and passes among its routes, so the API writes neither the path nor a field of the document. `GET` at the path of `address` answers `document` as `application/json` without a key, added with `routes.addPublic`, since an authorization server reads it when a consent starts; another method is `405` with `Allow: GET, HEAD`. Where the server gives none, as where it signs nobody in, a runtime in local mode at an `https` loopback address among them, or its `PUBLIC_URL` is `http`, the path has no route and needs a key as every path does.

**Caching.** The document, each guide, the catalog and the client metadata document change only when the server is released or configured again, so each is answered with a strong `ETag`, the quoted SHA-256 of its bytes, and `Cache-Control: public, max-age=300` (`src/discovery/cached-answer.ts`). The document's, each guide's and the client metadata document's are computed once, at start; the catalog's for its origin, as its bytes are built. A request whose `If-None-Match` names the tag, alone, in a list, weak or not, or `*`, is answered `304` with the tag, the `Cache-Control` and no body, as RFC 9110 says a `GET` or `HEAD` is. Hono answers `HEAD` on a `GET` route with the `GET` answer's status and headers and no body, which the tests check in process and on a Node listener. `/health` stays `Cache-Control: no-store`.

**The kept document.** The server's document is kept in the repository at `docs/assets/openapi.json`, so a client can be generated from it without running a server. `pnpm docs:openapi` (`scripts/openapi-document.ts`) writes it, as `JSON.stringify(document, null, 2)` and a final newline, from what a throwaway server answers at `GET /v1/openapi.json`; the formatter leaves the file alone (`ignorePatterns` in `.oxfmtrc.json`), since it would fold its short arrays. `packages/server/src/openapi/served-document.test.ts` checks it: the document the server answers is, parsed, the kept one, and its `info.version` is the release's, so a change to an operation fails that test until `pnpm docs:openapi` writes the file again. The release pull request sets the file's `info.version` to the version it releases (`extra-files` in `release-please-config.json`), so the file at a release's tag is the document of that release. The script reaches the throwaway server by package name, `@on.auto/server/openapi-document`, the one subpath the server's `exports` names, which this paragraph explains since the server has no README of its own: `src/testing/openapi/served-document-text.ts` of the server starts it with the composition root, on the loopback address with neither `PUBLIC_URL` nor `API_KEYS`, so in local mode, and with a temporary ledger, answers the text of its document, then stops it and removes the ledger. It is under `src/testing` so that neither the image nor the npm package carries it (`packages/server/Dockerfile.dockerignore`, `isShipped` in `packages/server/npm/pack.ts`), and its own test holds its text to a running server's, byte for byte.

## Over MCP

`mcpRoutes` serves the same catalog to agents over the [Model Context Protocol](https://modelcontextprotocol.io), with the official SDK, `@modelcontextprotocol/server`, pinned exactly. It is stateless: each request builds a fresh MCP server for its caller and keeps no session. The answer to a request the SDK handles is an event stream: its headers come at once, and while the request runs the stream carries an SSE comment, `: keepalive`, every 5 s (`heartbeatEveryMs`), in every revision, so a client can tell a call that still runs from a server that has stopped, and no proxy cuts a long call for being idle. A request the SDK refuses before it handles it keeps its JSON answer and its status, and a notification is answered `202`. The stream carries no event ids, so a stream that breaks is not resumed: the closing of a request's stream cancels the request in every revision. When the API closes, which the server does before it disposes of its services when it stops, each request still in flight is answered, after what its stream carried, with the JSON-RPC error `Auto Runtime stopped while it handled this request, so it may or may not have taken effect` (`src/answer-streams/answers-at-stop.ts`), and its stream ends; a request that comes after is answered with a `503` problem, `The server is stopping`. `hearingFetch` wraps an MCP client's `fetch` so that it hears each piece of the answer to each request it posts, heartbeats included, so the client can watch a call by its bytes. It serves the current stateless revision, `2026-07-28`, and the earlier ones the SDK supports: `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05` and `2024-10-07`. An `initialize` in any of them is answered in that revision, with the same tools, results and errors in each, and a client that asks for a revision the SDK does not know is offered `2025-11-25`. So agents built on older SDKs, including the 1.x line of the official one, connect out of the box. Revisions before `2025-06-18` predate `structuredContent`; the SDK sends it regardless, and a client of such a revision reads the same JSON from the text content. MCP sits outside `/v1` because the protocol versions itself.

| Endpoint                                    | Tools                                                                                            | Org and playbook                                              |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| `POST /mcp`                                 | the operations of the catalog the key may call: the org operations, then the playbook operations | the caller's own org; a playbook operation names its playbook |
| `POST /orgs/{org}/mcp`                      | the org operations the key may call, such as `create_playbook`                                   | the org of the URL                                            |
| `POST /orgs/{org}/playbooks/{playbook}/mcp` | the playbook operations the key may call, including function and workflow definitions and runs   | the org and the playbook of the URL                           |

Every endpoint also serves `get_guide` and the guides as resources, and offers as prompts the recipes whose tools it lists, below.

**What no endpoint offers.** An operation served over HTTP alone is listed on no endpoint, so the listings, their bytes and their counts of tools are those of the other operations, and a call of it is the SDK's `-32602`, as for any tool a connection does not list.

**What a key is offered.** A connection lists the tools its key may call: each registration whose `permissions`, the permission of its kind and scope unless its definition names others, include one the caller holds, so a key with `playbook:read` alone sees `list_playbooks`, which answers the playbooks it may access, and the queries inside a playbook, and no command, as the protocol allows a tool list to vary by the authorization presented. A tool the connection does not list is the SDK's `-32602`. The dispatcher still checks every call, so a key limited to some playbooks is refused the others per call.

`/mcp` is the one an agent connects to by default: on one connection it can create a playbook and then work in it. Its org is `org` of the authenticated principal: the org of the API key, which belongs to exactly one, the org a signed-in person's token names, or `local` for the local developer of local mode, who has no key. No argument names an org; an argument `org` is an unknown field, `invalid_input`. The scoped endpoints suit a client that wants a connection locked to one org's playbooks or to one playbook.

All three sit behind the same chain as every other path. Before the SDK runs, a caller the principal does not admit to the org gets `403` `forbidden` on a scoped endpoint, and so does a caller that may not access the playbook of a playbook endpoint, as problem documents whose challenge, with sign-in on, names the four permissions as `scope` and the metadata of the endpoint as `resource_metadata`, or the root metadata when the path's org or playbook id is not one. A caller the endpoint admits whose path names an org or a playbook id that is not one gets `404` `not_found`, "There is no such org" or "There is no such playbook in this org", as an operation route answers, before anything is handed to the SDK. `/mcp` serves a signed-in person the org their token names. `GET`, `DELETE` and every other method get `405` with `Allow: POST`; the SDK would answer them with a JSON-RPC error and no `Allow` header, so they never reach it. A playbook endpoint does not check that its playbook exists: each tool call does, and answers a missing playbook with `not_found`.

**The playbook argument.** On `/mcp`, each playbook operation's tool is derived from the catalog by its scope, so a new playbook operation appears there without new code. Its input schema is the operation's with a required `playbook` first, the playbook id's pattern and the description "The id of the playbook to act in" (added to every member when the input is a union, with any definition no longer referred to removed), and the tool's description is the operation's, since the argument's own description says what it is. A call first decodes `playbook` with the playbook id schema: a call without it, or with one that is not a well-formed id, gets `invalid_input` pointing at `/playbook` before anything else, a format check that reveals nothing. It then takes `playbook` out of the arguments and dispatches the rest to that playbook, so the dispatcher's authorization holds per call: a key limited to other playbooks gets `forbidden`, and a playbook the org does not have `not_found`, as `isError` tool results. No playbook operation can have its own `playbook` field: `@on.auto/operations` refuses to define one, as it reserves `org` and `playbook` for the scope. A playbook operation whose name an org operation also has is not offered on `/mcp`: the org operation, which the catalog accepts under that name only when it takes `playbook` itself, answers there in its place, with its own `playbook` argument and the description it gives it, as `search` searches the whole org without a playbook and one playbook with it. The playbook endpoint offers the playbook operation and the org endpoint the org one, under the same name.

**Tools.** Each operation is one tool: its `name`, `title` and `description` are the operation's, and its `inputSchema` is the operation's input JSON Schema (draft 2020-12), self-contained with an object at the root and its definitions under `$defs`. A tool has no `outputSchema`, though its registration carries one, which the OpenAPI document serves: a client compiles a validator from each output schema it lists and refuses a result that does not match it, and a server that keeps no session and announces no change to its tools cannot tell a client that listed them before an upgrade that a result's shape changed, so the result alone says what it holds. A description says what the tool does, when to use it and when not, the caveats to know before calling and the alternative tool by name, in three to eight sentences and at most 800 characters; the rules of each argument are in its schema's description, at most 300 characters at any depth of the input, and keywords. **Calls.** On a scoped endpoint the org, and the playbook of a playbook endpoint, come from the URL, and the arguments are the whole input; on `/mcp` the org is the caller's own and the playbook an argument. The input is decoded with the `json` encoding. A call goes through the same dispatcher and the same `settle` as an HTTP request, with the caller in the URL's org.

| Outcome                     | Tool result                                                                                                                                                                            |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| succeeded                   | the first text content says in plain words what happened, the second is the output as JSON text, and `structuredContent` is the same output, with no output schema to check it against |
| rejected, failed, cancelled | `isError: true`; the first text content says in plain words what could not be done, and the second is the problem document HTTP would answer with, as JSON; no `structuredContent`     |

Human-readable results name reasoning functions, workflows and runs. They omit ids, versions, formats and status codes, which remain in the structured result. `internalTermsIn` of `@on.auto/operations/testing` finds what they must omit. `get_guide` serves the format of each definition type; no tool description carries one. The words of an outcome take at most 400 characters and those of a refusal at most 600: `withinCharacters` of `@on.auto/operations` keeps the whole sentences that fit and says the rest is in the details below, the JSON beside them.

Each operation supplies `plainLanguage`: a `task` and an `attempt` describing the action, and an `outcome` based on its output. It may also give `remedies` of its own by `because`, which take the place of the shared remedy in the words of its refusals, as `execute` and the reads of one tool name what `search` shows where a function's refusal speaks of the function. Each adapter gives the noun for its definitions and a sentence for a run's result. An endpoint refuses to mount an operation without them.

`unsuccessfulWords` in `@on.auto/operations` supplies failure wording from the rejection's reason and optional `kind`: `taken`, `retired`, `concurrent_change` or `unworkable` for a conflict, and `model_not_offered` for `unavailable`. The message distinguishes a problem the agent can correct from one only the server operator can resolve. A reasoning function naming an unavailable model gets `model_not_offered`, with `because` explaining `provider_not_configured` or `model_not_allowed`; the definition can instead name an allowed model from `list_models`. Request problems identify what is missing, disallowed, taken or retired. Unexpected failures give a reference to quote. HTTP response contracts stay unchanged.

So invalid arguments are a tool result with `isError` and an `invalid_input` problem pointing at each field, as the protocol asks, and an agent can correct them. The SDK's parsing of the arguments drops one named `__proto__`; each endpoint reads the request body before the SDK, within the same 1 MiB, and puts such an argument back before the call is dispatched, so it is rejected as an excess field, `invalid_input` at `/__proto__`, as over HTTP. A tool the endpoint does not list is a JSON-RPC error, `-32602`, from the SDK. A call still running when the server stops gets a `503` `unavailable` problem. A tool that throws instead of settling is reported as an incident, as an HTTP request would be, and answered with the `500` `internal` problem, so the SDK never puts an error message of its own in the result.

**Server identity.** `serverInfo` carries the name and version the server passes in, the root package `@on.auto/runtime` and its release version from the manifest, and the title `Auto Runtime`, which a client shows in place of the name.

**Instructions.** Every endpoint answers `initialize` with instructions built for the caller of the session by `instructionsActingAs` in `src/mcp/instructions.ts`. They open with whom the connection acts as, by name and id, and in which org, `This connection acts as Ada Lovelace (person:user_2ada) in the org acme.` for a signed-in person and the local developer, and `This connection acts as the key build-bot in the org acme.` for a key, whose name is its id, so an agent that reads what a record says of who did something tells the caller it serves from the others. The org is the one the session acts in, the caller's own on `/mcp` and the one the path names on the other endpoints. What follows is the same for every caller of the endpoint, `instructionsFor`: it begins with the claim that whatever the person wants done that keeps working after the conversation, however they put it and in any line of business, is a playbook here, not a document, a plan, a note or a one-off answer, and establishes that Auto Runtime makes and runs playbooks, Studio manages them, and the agent is a separate client. Each playbook contains one brain of reusable functions and its workflows; functions run directly or in workflows, and runs belong to the playbook.

The instructions are composed from the tools the caller may use and the registered definition types. They explain connection scope, put what the person wants kept in a recall function rather than the agent's own notes where the server runs recall functions, require reading the format before writing a definition and ask for its overview, name `list_models` where it is listed and `search` is not, and direct an answer to an outstanding interaction back to the same run. Where `search` and `add_connection` are both listed, they say that a service a playbook will use is connected on this server, whatever connector the agent has of its own: asked to connect, link, sign in to or use one, the agent calls `search` with its words, then `add_connection` with the provider's name, which the person approves on the page it links, and says a service cannot be connected only when no provider or server matches. Scoped connections and read-only callers receive only applicable instructions. `src/mcp/instructions.test.ts` checks these combinations, the opening line of a signed-in person, a key and the local developer, and the 2,000-character limit, about what Claude Code shows of a server's instructions, over the whole text, opening line included, for a person named in 20 characters whose user id takes 32 and whose org id 30, `callerTheInstructionsHold` of `src/bounds/served-bounds.ts`; startup refuses an endpoint whose instructions exceed the bound for that person. A caller whose name, id or org is longer is served the longer text, which a client that shows only 2,000 characters cuts at its end. Tool descriptions and format guides carry the details that do not fit in initialization: `get_guide`'s description names the recipes the connection's tools can follow, `run_definition`'s says that a run that finishes later answers started and `get_run` shows how it ended, `list_models`'s and `search`'s say how a reasoning function names its model and its tools, as the reasoning function's guide does, the prediction function's guide says that a build answers started, `execute`'s and `dry_run`'s say what each does, and those of `list_runs`, `list_playbook_events` and `list_interactions` say that their pages are read on only as the person needs.

### The cost of a listing

The bound on a listing is bytes because a listing is what an agent's client loads whole and holds for the connection. A client that defers its tool listing, and searches it, pays for a tool when it uses it; one that does not pays for the whole listing on every request, so the bound keeps a listing within what such a client loads at about 12,000 tokens. The server's listings take, with every tool and no tool server configured, as `packages/server/src/mcp/served-schemas.test.ts` pins them:

| Endpoint                                    | Tools | Bytes on the wire | Bound  |
| ------------------------------------------- | ----- | ----------------- | ------ |
| `POST /mcp`                                 | 28    | 44,141            | 48,000 |
| `POST /orgs/{org}/mcp`                      | 10    | 12,271            | 13,500 |
| `POST /orgs/{org}/playbooks/{playbook}/mcp` | 20    | 31,808            | 40,000 |

The bound of the org endpoint moved from 12,000 bytes to 13,000 with the tools of connections, the least that held them, since its listing took 12,767 with every tool at its shortest; `add_connection`'s way in by a provider's name took it to 12,869, and the sentence of `search` that names its `providers`, with `add_connection`'s words that `search` lists them, to 12,954, and the kind `authorization` among the kinds of its credential, which a caller names to connect a provider by consent, to 12,970. The bound moved again, to 13,100, the least hundred that holds the listing, when `search` came to name the providers that match a service and `add_connection` to open with a person's account at a service that `search` lists, which took the listing to 13,019, and to 13,200 when the descriptions of `create_playbook` and `list_playbooks` came to open with the requests each answers, which took it to 13,155, and to 13,500 when `add_connection` came to say that a service a playbook will use is connected through it, whatever connector the agent has of its own, and to end by saying that the call grants nothing and no credential passes through it, which took it to 13,435. The descriptions of the org endpoint's tools then came to keep only what an agent needs to call each rightly, leaving to an argument's description what it says of the argument, which took the listing to 11,975, so a shell that adds org operations of its own has room for their tools under the same bound. `add_connection` and the description of its `credential` then came to say that an MCP server given by hand that signs people in itself takes `authorization` by its kind alone, the runtime finding its authorization server, which took it to 12,259, and the guide `templates`, a name more in the enum of `get_guide`'s `guide`, to 12,271. A listing takes 3.9 to 4.2 bytes a token, as two open byte-pair vocabularies of 100,000 and 200,000 count it, so the 48,000 bytes of `/mcp` come to about 11,400 to 12,300 tokens (the rate counted on 2026-10-13 over the `tools/list` answer as it is sent, the server-sent event's framing included). A model's own tokenizer counts differently, by a few percent either way.

**Which errors look how.** An MCP endpoint answers in three shapes:

| Shape                              | When                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| problem document                   | before the SDK runs: `401`, `403` (origin, org or playbook), `400` for a malformed `Authorization` header, `405`                                                                                                                                                                                                                                                                                                         |
| JSON-RPC error with an HTTP status | the SDK rejects the request: `406` when `Accept` lacks `application/json` and `text/event-stream`, `413` for a body over 1 MiB, `415` when `Content-Type` is not `application/json`, `400` with `-32700` for a body that is not JSON or not JSON-RPC, `400` for a request made under a revision the SDK does not support or whose MCP headers disagree with its body, and `-32602` for a tool the endpoint does not list |
| tool result with `isError`         | the operation did not succeed: a rejection, a failure or a cancellation, with plain words first and the problem document as text                                                                                                                                                                                                                                                                                         |

The SDK reports the errors it answers with JSON-RPC to `reportError`, which the server logs as a warning on stderr. Nothing the SDK does writes to stdout.

## The list of models

The server serves `list_models`, an org query of [`@on.auto/reasoning`](../../capabilities/reasoning/README.md#using-it-from-code), like any other operation: `GET /v1/orgs/{org}/models`, with an optional `provider` in the query string, and the read-only tool `list_models` on `/mcp` and `/orgs/{org}/mcp`. It answers in the shape of the OpenAI API's list of models, which gateways such as LiteLLM, Portkey and Vercel's serve too:

```json
{
  "object": "list",
  "data": [
    {
      "id": "anthropic/claude-sonnet-4-5-20250929",
      "object": "model",
      "created": 1759104000,
      "owned_by": "anthropic",
      "name": "Claude Sonnet 4.5",
      "context_window": 200000,
      "max_tokens": 64000
    },
    {
      "id": "house/fast",
      "object": "model",
      "created": 0,
      "owned_by": "gateway",
      "alias": true,
      "resolved_to": "gateway/llama-3.3-70b"
    },
    {
      "id": "openai/*",
      "object": "model",
      "created": 0,
      "owned_by": "gateway",
      "alias": true,
      "resolved_to": "gateway/openai/*",
      "pattern": true
    }
  ],
  "catalog_status": "complete",
  "narrowed": false,
  "listed_at": "2026-10-01T09:30:00.000Z"
}
```

`id` is the model as a definition names it, `owned_by` the provider prefix that serves it, and `created` the provider's release time in seconds, or 0. `name`, `context_window` and `max_tokens` appear only when the provider reports them, `alias: true` for every alias and only for one, `resolved_to` for an alias whose target is not a Bedrock ARN, and `pattern: true` only for an id ending in `*`, which stands for any model id. `catalog_status` is `partial` when a provider could not be asked, `narrowed` is `true` when the operator allows only some models, and `listed_at` is when the oldest list in the answer was read. Its plain words name the models, such as `This server can call 2 models through anthropic and gateway: Claude Sonnet 4.5 and fast. It can also call any openai model.`

## Lifecycle

`createApiHandler` answers a request two ways: `fetch(request)`, in process, and `listener(incoming, outgoing)`, on Node through the Hono adapter. Each request runs with the binding `abortConnection` (`ApiEnv['Bindings']`), which destroys the Node response on `listener` and does nothing in process, where a failed body is the abort. A `RegisterRoutes` function receives `routes.add`, to add a route, `routes.addPublic`, to add one whose exact path needs no key and skips the origin and host checks, as `/health`, the document, the guides and the catalog are, and `routes.onClose`, to add something to close when the API closes. `mcpRoutes` registers the closing of its three MCP handlers, which ends the calls they still serve. `ApiHandler.close` closes everything registered. The server calls it as it shuts down, after it has disposed of its runtime, so a call still running has already been answered as cancelled.

## Exports

`makeAppRuntime(layer)` builds the runtime every call runs in. ## Source

`src/middleware` holds the chain every request passes, `src/authentication` the bearer authentication, and `src/problem` problem documents and how outcomes become them. `src/operations` holds the HTTP routes: the route table, how input is assembled and how an outcome becomes a response. `src/mcp` holds the MCP endpoints, the connection each request builds and its instructions; `src/tools` the tools, their schemas, their definitions and how a result is built; `src/hand-off` how the caller reaches the SDK's server; `src/guides` the guide tool, the resources, the prompts and the guides over HTTP, and the shelf of guides read from the files the API ships, with the recipes; `src/shipped-files` the roots of those files; `src/openapi` the OpenAPI document and its route; `src/discovery` the API catalog, the health route, the client metadata document, the public addresses and the caching of public answers; `src/studio` the Studio the runtime serves and the page it answers when the Studio host cannot be reached; and `src/bounds` the bounds. `src/testing` holds what the tests share.
