# @on.auto/shipped-files

The files a package of the runtime ships beside its code, and the one way they are read: the port a package reads them through, the names of the files, and the reader on disk the server composes. It is a package of its own because every package that ships files names them here, while how they are read is decided once, by the server that composes the packages, so a package reaches this port and never the file system.

## The port

`ShippedFiles` (`src/shipped-files/shipped-files.ts`) is the port through which a package reads the files it ships beside its code: `text(file)`, `bytes(file)` and `list(folder)`, the names of the files directly in a folder, sorted, each a `ShippedFile`, the name of the package the file is shipped in and its path within it, as `{ package: '@on.auto/providers', path: 'src/entries/slack.yaml' }`; `shippedFileIn(folder, name)` is a file of a folder, and `shippedFileName(file)` the name a file goes by in an error and among the files a pool hands its workers, `@on.auto/providers/src/entries/slack.yaml`. No module computes where a file is when it loads, so a host that bundles the modules names the files as the server does, and loads them where `import.meta.url` names no file. A package that ships files declares its root once, a function that answers a `ShippedRoots` of its name, `new URL('../../', import.meta.url)` of the module that names the files, only when it is called, and exports it from the entry that reads them: `providersShippedRoots()`, `apiShippedRoots()` and `checkShippedRoots()` of `@on.auto/definitions/check`. A file a dependency ships, the engine's WebAssembly or the compiler's lib, is named under the package that depends on it, in the folder of the dependency, `node_modules/<dependency>/<its path>`, by `dependencyFileOf(dependent, dependency, path)`, since pnpm's layout lets the dependent alone find it; the reader finds the dependency as Node finds it from the root of that package, in its own `node_modules` and then in that of each folder above it, where the npm package's install puts it, so no module resolves a package when it loads (`sandboxModuleFile` and `sandboxShippedRoots()` of `@on.auto/workflow-engine/dsl`, and the lib `sandboxLibOf` of `@on.auto/definitions` reads). A package names its files and never says how they are read: it takes the reader as a dependency of the function or factory that reads, never from an import of the reader, and the reader never knows what a file is for, so how they are read is one decision, taken once by the server that composes the packages. What a package read it hands on as content, never as a path for another package to read again: `@on.auto/providers` hands the tool servers the texts of the documents beside its entries, and a pool of `@on.auto/workflow-engine` is handed the bytes its workers start with.

## The reader on disk

`shippedFilesOnDisk(roots)` (`src/shipped-files/shipped-files-on-disk.ts`) is the one reader: it reads a file under the root `roots` gives its package, resolves no package but a dependency whose file it is asked for, with `findPackageJSON` of `node:module` from that root, which finds the dependency's own folder whatever its `exports` map says, one that hides its `package.json` and gives no entry to `require` among them, and refuses the file of a package it is given no root for; the server gives it the roots of every package whose files it reads (`packages/server/src/server-options/shipped-roots.ts`). It is the one module of the port that imports `node:fs`; it is an entry of its own, `@on.auto/shipped-files/on-disk`, as the drivers of `@on.auto/ledger` are, so that the main entry, which every package that ships files imports, and the testing entry reach no file system for it (`src/shipped-files/shipped-files-entries.test.ts`).

## Testing

`@on.auto/shipped-files/testing` exports `shippedFilesInMemory(files)` (`src/testing/shipped-files-in-memory.ts`), a `ShippedFiles` over a record of contents by package and by path within it, each a text or bytes, for the unit tests of a package that reads what it ships: a folder lists the files directly under it, and a file it does not hold is refused, as is a folder that holds none, since it holds no empty folder; the same tests run on it and on the reader on disk (`src/shipped-files/shipped-files.test.ts`).
