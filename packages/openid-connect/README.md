# @on.auto/openid-connect

Single sign-on (SSO) for a self-hosted runtime: the runtime as an OpenID Connect relying party of a company's own identity provider, and, at the subpath `./authorization-server`, as the OAuth 2.1 authorization server its members, their agents and Studio sign in at. A runtime that sets `OIDC_ISSUER`, `OIDC_CLIENT_ID` and a client secret signs its members in this way, and so does one that sets `OIDC_ISSUER` alone where the provider lets a client register itself (below), and one with `PUBLIC_URL`, no `ACCESS_MODE` and no `OIDC_ISSUER`, whose members sign in with their Auto accounts through the default identity provider (`defaultIdentityProvider` of `@on.auto/identity`); the server reads those settings and serves the authorization server (`packages/server/src/settings/openid-connect-settings.ts`, `packages/server/src/sign-in/company-sign-in.ts`). It is a package of its own so that Auto's hosted runtime, which never signs anyone in this way, loads none of it, and so that the libraries it is built on, which run on Node, stay out of every other package. The authorization server is a subpath of its own, `@on.auto/openid-connect/authorization-server`, which a server imports only where it signs people in this way, so no other server loads `oidc-provider` or Koa, and the notice `oidc-provider` prints as it loads on a Node release that is not an LTS one is printed by no other.

## The library

The protocol is [openid-client](https://github.com/panva/openid-client), MIT, an OpenID Certified relying party for Node, by the author of `jose`, which the runtime already uses for the tokens of the Auto identity service. It runs on the Fetch API and Web Crypto that Node 20 and later carries, below the runtime's floor of Node 26.10, and its package carries its licence, as do the two it depends on, `oauth4webapi` and `jose`, both MIT. Nothing of the protocol is written here: the authorization request, the exchange of the code, the checks of the answer and of the ID Token, and the keys are the library's.

`openid-client` 6.8.9 asks for `jose` 6.2.15 or later, and the catalog of the runtime pins 6.2.12, which the identity package and Auto's hosted runtime use, so pnpm keeps a second `jose`, 6.2.17, for this package alone. 6.8.9 is the newest release older than the seven days `minimumReleaseAge` waits, and the first whose types hold under `exactOptionalPropertyTypes`, which the runtime's TypeScript sets.

The library's own `discovery` is not used: for two hosts of one vendor it does something else, accepting any issuer there, or a template of one, and here nothing depends on a vendor. The package reads the metadata itself and gives it to the library's `Configuration`.

## Discovery

`relyingPartyOf(settings, requests)` reads the provider's metadata once, as the server starts, at `metadataAddressOf(issuer)`: the issuer with `/.well-known/openid-configuration` added, a terminating `/` taken off first (OpenID Connect Discovery 1.0, §4), so an issuer with a path is read where it says. It takes the metadata only when it names the issuer it was read for identically, character for character (§4.3), and names an `authorization_endpoint`, a `token_endpoint` and a `jwks_uri`, each an `https` URL; otherwise it throws an `UnusableIdentityProviderError` that says which, and the server does not start.

`usableProviderOf(settings, requests)` of `src/provider/client-configuration.ts` reads it, and answers the method below, the `registration_endpoint` the metadata declares where it is an `https` URL, and `signInsAs(client)`, the library's `Configuration` of the provider and one client, which no other module touches. The metadata declares a `userinfo_endpoint` (OpenID Connect Discovery 1.0, §3) or a `revocation_endpoint` (RFC 8414, §2) only where it names it as an `https` URL, as for the registration endpoint; the two are read from this one document, so no request is added to read them.

The client proves itself at the token endpoint with its secret, by the method `OIDC_TOKEN_ENDPOINT_AUTH_METHOD` names, or else by the first of `client_secret_basic`, `client_secret_post` and `client_secret_jwt` that the metadata declares in `token_endpoint_auth_methods_supported`, `client_secret_basic` where it declares none (OpenID Connect Core 1.0, §9). A method the provider does not declare refuses the start.

Every request to the provider, the metadata, the token endpoint, the keys, a registration, the UserInfo endpoint and the revocation endpoint, goes through `requests.fetch`, bounded as the requests to the Auto identity service are: an answer within 10 seconds, of at most 64 KiB, and no redirect followed. A test gives a fetch of its own, so no request leaves the process.

## A client the runtime registers

Where no client is given, the runtime registers one itself, by OAuth 2.0 Dynamic Client Registration (RFC 7591), the finished standard for a client that "sends its own description" and is given a `client_id` and a `client_secret`, which OpenID Connect Dynamic Client Registration 1.0 defines for a relying party too. Whether a provider lets it is read from what the provider declares and nothing else: `registeringProviderOf(settings, requests)` (`src/provider/registered-relying-party.ts`) reads the provider's metadata as `relyingPartyOf` does, takes the `registration_endpoint` it declares, and, where it declares none, reads the authorization server metadata of the same issuer, RFC 8414, at `authorizationServerMetadataAddressOf(issuer)`, the well-known path put between the host and the path of the issuer, a terminating `/` taken off first (RFC 8414, §3.1), as OAuth 2.0 Security Best Current Practice (RFC 9700) and the Model Context Protocol tell a client to read it. It takes that document only where it names the issuer identically (§3.3, the rule the first document is read by), and from it only an `https` `registration_endpoint` (`registrationEndpointOf` of `src/provider/provider-metadata.ts`). A document there that cannot be read, holds no metadata or names another issuer refuses the provider as an `UnusableIdentityProviderError`, and a `404` there is no document; where neither document declares an `https` endpoint, it throws a `ClientRegistrationError` whose `refusal` is `{ notOffered }`, the two addresses it read.

`registered()` sends one request, `POST` with a JSON body, through `requests.fetch` and its bounds, and no initial access token, since none is given (RFC 7591, §3): `redirect_uris`, the one redirect URI; `client_name`, the name the settings give; `client_uri`, only where the settings give one, the page of the client a provider may show beside its name (§2); `response_types` `["code"]`; `grant_types` `["authorization_code"]`; `application_type` `"web"`, OpenID Connect's default, said outright; `token_endpoint_auth_method`, the method chosen above, whose default `client_secret_basic` is RFC 7591's own; and `scope`, the scopes the settings name. The provider "MAY reject or replace any of the client's requested metadata values" (§3.2.1), so the answer is checked, not assumed (`clientRegisteredAt` of `src/provider/client-registration.ts`): it must be a JSON object with a `client_id` and a `client_secret`, each text that is not empty, since the relying party proves itself with a secret; `redirect_uris` that hold the one sent; a `token_endpoint_auth_method` that is one of the three a secret proves itself by, `client_secret_basic` where it answers none (§2: "If unspecified or omitted, the default is `client_secret_basic`"), which is then the method the client proves itself by, whatever was asked; a `client_secret_expires_at` that is `0`, "if it will not expire", or a second still to come, `0` where it answers none; and a `scope` that holds every scope asked, or no `scope`, since the answer carries "all registered metadata" (§3.2.1) and a client registered with none is limited by none. The answer is a `RegisteredClient`, `{ clientId, clientSecret, tokenEndpointAuthMethod, secretExpiresAt }`, its secret `Redacted`; nothing else of it is kept or answered, a `registration_access_token` among it, since nothing here manages a registration (RFC 7592 is Experimental and optional). A refusal is a `ClientRegistrationError`, with the `issuer`, the `redirectUri` and one `refusal`: `{ refused }`, the `error` the provider answered where it has the syntax of an error code, or its status; `{ unreached }`, in the words of the bounds; `{ unusable }`, what the answer lacks; or `{ withoutScopes }`, each scope asked that it left out. `isLastingAt(client, nowMs)` says whether a secret is still to be used. The request is the runtime's own and not the library's `dynamicClientRegistration`, which does a discovery of its own that this package avoids (above).

`relyingPartyOf(clients)` of the registering provider is the relying party of such a client: it takes its client from `clients`, a port the server implements, where it keeps what it registered. `inUse()` answers the client a sign-in begins as, `named(clientId)` the one a sign-in began as, and `refused(client)` is told when the token endpoint refused that client, by `invalid_client` in its answer or by a `401` with a challenge in `WWW-Authenticate`, which RFC 6749, §5.2, requires where the client authenticated in the `Authorization` header; the server registers anew there, and the person signs in again. Its sign-in notes the client it began as in its pending sign-in, `clientId`, and finishes as that client, since a code is redeemed by the client it was issued to (RFC 6749, §4.1.3); a pending sign-in that notes none, or one `clients` does not name, is not finished. The library's `Configuration` of each client is made once and kept by its `client_id`.

## A sign-in

`signInStarted()` answers the address to send the person to and what the sign-in must find again when the person comes back: a fresh `state`, `nonce` and PKCE verifier, drawn by the library for each sign-in, and, for a client the runtime registered, the `clientId` it began as, sent with the code challenge, `S256`, the `scope` the settings name and the redirect URI. `signInFinished(query, pending)` takes the query the provider sent the person back with and those three, and answers one of:

- `{ signedIn: { issuer, subject }, claims: { name, email }, held }`, the `iss` and `sub` of the ID Token as the provider gave them, and of its other claims the two Standard Claims of OpenID Connect Core 1.0, §5.1, that a person's record keeps, `name`, the "End-User's full name in displayable form", and `email`, each where the ID Token holds it as text, and nothing else of it but one: where the settings name a `requiredClaim`, `valueOfTheRequiredClaim` is the value of that claim, where the ID Token holds it as a member of its own and as text, exactly as given, with no trimming and no change of letter case. A claim the ID Token lacks, or holds as a number, a boolean, an array, an object or `null`, answers no value, as Kubernetes takes "Only string values" for its `--oidc-required-claim`. The server compares the value with the one it requires (`OIDC_REQUIRED_CLAIM`, `packages/server/src/sign-in/admission.ts`), and nothing here logs or keeps it;
  and `held`, the provider's tokens the sign-in holds until the server has decided about the person (below), where anything is still to be done with them;
- `{ refusedByTheProvider: code }`, the `error` the provider answered with, at the redirect or at the token endpoint, when it has the syntax RFC 6749 gives an error code;
- `{ failed: code }`, where the answer could not be read, in the words of the bounds above, or the library refused it, by the library's error code, such as `OAUTH_JWT_CLAIM_COMPARISON_FAILED`.

It checks, through the library: the `state`; the `iss` of the answer where the provider sent one, and its presence where the metadata declares `authorization_response_iss_parameter_supported` (RFC 9207); the code exchanged with the verifier; and the ID Token as OpenID Connect Core 1.0, §3.1.3.7 says, its issuer, its audience, its `nonce`, its times with 60 seconds of leeway either way, and its signature, by a key of the provider's `jwks_uri`, which the library reads again for a key it does not know at most once a minute and keeps at most five minutes. The signature is checked although the ID Token comes straight from the token endpoint, where the section lets the client trust TLS instead. No error of the library reaches the caller: they carry the query, the codes and the tokens, so only the code above leaves this package.

## The tokens of a sign-in

The token endpoint answers an access token, and may answer a refresh token the runtime did not ask for: it asks for no `offline_access` of its own and registers a client for `authorization_code` alone, yet a provider may issue one all the same, as one that registers every client for the `refresh_token` grant too does. Neither is kept, logged or answered. Two things may still be done with them, each where the provider declares the endpoint and nothing else, never by its address or its name (`tokensHeldBy` of `src/provider/sign-in-tokens.ts`):

- The person's name, read at the UserInfo endpoint with the access token, where the ID Token carries no `name` as text: OpenID Connect Core 1.0, §5.4, says the claims of `profile` "are returned from the UserInfo Endpoint" where an access token is issued, and a provider may leave them out of the ID Token, while one that puts the name there needs no request for it. That is the rule of oauth2-proxy's claim extractor, which asks its profile URL only for a claim the ID Token lacks. The answer's `sub` must equal the ID Token's, "if they do not match, the UserInfo Response values MUST NOT be used" (§5.3.2), which the library's `fetchUserInfo` checks; of the answer only `name` is taken, as text, as of the ID Token.
- A refresh token, handed back at the revocation endpoint (OAuth 2.0 Token Revocation, RFC 7009), with `token_type_hint` `refresh_token`, the client proving itself as at the token endpoint, by the library's `tokenRevocation`. A refresh token where none is declared is let go of and nothing else happens.

Where either is to be done, the answer holds `held`, whose `released(nameAsked)` does them once the server has decided about the person: the name first, only where the server asks for it, and then the refresh token, whatever the server decided, since revoking a refresh token "SHOULD also invalidate all access tokens based on the same authorization grant" (RFC 7009, §2.1) and so may end the access token the name is read with. Only the token each needs is held, and only until then. Where neither is to be done, nothing is held, and the sign-in's answer is what it was before either endpoint was read. `released` answers `TokensReleased`: the `name`, where one was read; `nameUnread`, where it could not be; and `notRevoked`, where the refresh token could not be handed back; each failure is the provider's error code, the words of the bounds above or the library's code, never anything of the answer, and none is thrown, so a sign-in never fails for either.

## The authorization server

`authorizationServerOf(settings, parts)` of `src/authorization-server/authorization-server.ts` is an OAuth 2.1 authorization server and OpenID Provider built on [oidc-provider](https://github.com/panva/node-oidc-provider) 9.14.0, MIT, by the author of `openid-client` and `jose`, OpenID Certified, pinned exactly since the Client ID Metadata Documents it implements are an experimental feature whose versions change in minor releases. Nothing of the protocol is written here: authorization, PKCE, the `resource` parameter (RFC 8707), `iss` in the answer (RFC 9207), dynamic registration (RFC 7591), revocation (RFC 7009), UserInfo, RP-initiated logout, rotation of refresh tokens and the end of a grant whose refresh token is used again are the library's. Its issuer is the `issuer` it is given, the server's `PUBLIC_URL`, and the library's addresses are built from it.

It answers the paths `answeredPathsOf` names (`src/authorization-server/paths.ts`), the cloud's names where the cloud has one and the library's own otherwise, and nothing under `/auth` but the redirect URI of the upstream sign-in: `/oauth/authorize` and `/oauth/authorize/{uid}`, `/oauth/token`, `/oauth/register` and `/oauth/register/{client}`, `/oauth/revoke`, `/.well-known/jwks.json`, `/.well-known/openid-configuration`, `/.well-known/oauth-authorization-server`, `/me`, `/session/end` with `/confirm` and `/success`, the library's example's `/interaction/{uid}` with `/confirm`, `/abort` and `/federated`, and `signInCallbackPath`. A server mounts it beside its other routes at the Node level: `answers(path)` says whether a path is its, and `listener(request, response)` answers it. The library is a Koa application, and a server built on another framework hands it the Node request, as its documentation lists for Express, Fastify and others.

Before its routes it runs the middleware it is given, `parts.middleware`, a function of the request's method, address and headers that either answers the request, as a refusal or a preflight, or passes it on with the headers to set, so a server's request id, security headers, origin check and CORS hold on these paths as on its own (`behindItsPublicAddress`). It adds `script-src 'none'` to the policy it is given, which the library extends with the hash of the one script it writes where a form submits itself; there it then drops the `'none'`, which a browser ignores beside a hash and reports as an error, so the directive names the hash alone (`withTheHashAlone`). It answers with `Referrer-Policy: same-origin` whatever the middleware gave, as a page of forms needs: the library's own pages post to the server itself, signing out and choosing another account among them, and a browser sends `Origin: null` with a form posted from a page whose policy is `no-referrer` (the Fetch standard, "append a request `Origin` header"), which a server's origin check refuses. Signing out is one step (`logoutSource`): the library's form, confirmed, and the one script that submits it are handed to `parts.pages` as `signingOut`, whose page allows that script by its hash and gives a browser without scripts a button that submits the form. It also takes the protocol and the host of a request from its issuer and never from the request (`provider.proxy` with `X-Forwarded-Proto` and `X-Forwarded-Host` set from the issuer), so a server behind a proxy that ends TLS sets its cookies `Secure` and names its own addresses, whatever a client sent.

The configuration (`src/authorization-server/configuration.ts`): the code flow alone, PKCE `S256` for every client, clients that prove nothing at the token endpoint (`none`), every client given a refresh token where it may use that grant, refresh tokens rotated at each use and lasting 30 days from the latest, access tokens of 15 minutes, opaque, for the issuer or any address under it and naming the issuer as their audience, and for the issuer where a request names no resource but asks for one of `settings.resourceScopes` (`defaultResource`), as an agent that leaves `resource` out would otherwise get a token only UserInfo takes, a grant of 90 days, a session of 7 days unused and 30 days at most, kept in the cookie `__Host-Http-session`, `SameSite=Lax`, and a prompt `select_account` a client may ask, as the library's documentation adds one. A session signs its person in only while `parts.claimsOf` answers for their account: the login prompt's check `no_session` is replaced by one of the same name and words that also asks whether the account was found, so a session whose account is no longer answered sends the person to the sign-in step again, and the library refuses that account's refresh tokens (`invalid_grant`) and its tokens at UserInfo. Studio is one client of the static list, from `settings.studio` and never fetched, whose grant `loadExistingGrant` makes and widens itself, so Studio is never asked to be allowed; every other client is, a registered one or one named by its Client ID Metadata Document. DPoP, pushed authorization requests, introspection and the library's development pages are off.

The sign-in step (`src/authorization-server/interactions.ts`) is the library's interaction, handed to a server's sign-in through `parts.signIn`: `started({ selectAccount })` answers the address of the company's provider and what the sign-in must find again, which the step keeps for 10 minutes in the cookie `__Host-Http-sign-in`, beside the interaction it belongs to; the provider's redirect comes back to `signInCallbackPath`, which sends it on to `/interaction/{uid}/federated`, the library example's way, where the interaction's own cookie is; and `finished(query, pending)` answers whether the person is admitted, by their account id, refused, or gave up, which returns the client `access_denied`. The allow question, a request no longer open and the three refusals are pages `parts.pages` renders, so no word of them lives here; the allow question carries the client's name, the host its Client ID Metadata Document is published at (`publishedAt`, nothing for a client that registered itself) and the address its access is delivered to.

`accessTokenOf(value)` answers who an access token stands for, its client and its scope, where the library issued it for the issuer, it is not bound to a key, it has not ended and its grant still holds it, and nothing otherwise; a server's API admits a token through it.

### Its rows

`hashedAdapterOf(rows)` of `src/authorization-server/hashed-adapter.ts` is the library's adapter: each instance of one of its models is a row of `ProviderRows` keyed by the model and the SHA-256 of its id, so no token, code, session or interaction id is kept, only its hash, and `find` puts the id back. The payload is kept as JSON without the id, and an interaction's payload without the value of the session cookie the library copies into it, which the library never reads back. A session found by its `uid` comes back without its id, which neither of the library's two callers of `findByUid` uses. `consume` marks a row once, by a guarded update, as the library asks of an adapter, and a second consumption ends the whole grant and is refused `invalid_grant`. Rows that ended a day before are swept at most once a minute as rows are kept, the day leaving an interaction that ended readable for the page that says it is no longer open. `everyoneSignedOut(rows)` of `src/authorization-server/signed-out.ts`, which the package's main entry exports so a server need not load the library for it, ends every session, interaction, grant, code and token at once, in one statement, `endedEvery`, and keeps every client registered, as a server does when its set-up is opened again.

The key the server signs ID Tokens with, RS256, is made at the first start (`signingKeyOf` of `src/authorization-server/signing-key.ts`), sealed as a secret through the `KeptSecrets` a server gives, and named by the one row of `auth_signing_key`; a server that starts at the same moment and finds the row written first forgets the secret it sealed and reads the one named, so every server of one database signs with one key. Where the secret the row names is no longer kept, the server makes a new key, seals it, and points the row at it in one guarded update, `UPDATE … WHERE secret_id = {the lost one} RETURNING` (`replaced` of `SigningKeyRows`), so of two servers that find it gone at once one replaces it and the other forgets its own and reads that one. ID Tokens signed with the lost key, which live an hour, can no longer be checked; nothing else is signed with it.

## Who a person is

A person who signed in here is known by the pair of the ID Token's `iss` and `sub`, the only claims OpenID Connect Core 1.0, §5.7, lets a relying party rely on as a stable identifier, and never by an email or a name. `personIdOf({ issuer, subject })` is their id in Auto, and the one place it is made: the lowercase hexadecimal SHA-256 of the UTF-8 octets of the JSON array `[iss, sub]`, written with no whitespace, as `JSON.stringify` and RFC 8785 write an array of two strings. Both are taken exactly as the validated ID Token gave them, with no trimming, no change of letter case and no normalising of the address, so the token's own `iss` counts, not the spelling of `OIDC_ISSUER`. An array, and not the two joined by a mark, because a `sub` may hold any character, so no mark is safe. A canonical JSON form hashed with SHA-256 as an identifier is the method of RFC 7638. The result is 64 characters of `0-9a-f`, with no salt and no secret, so it is the same on every server of an install and survives a restart; it is a pseudonym, which anyone who knows the issuer and the `sub` can compute. The test pins it with made-up pairs and their ids, so it cannot drift: once anything is recorded under an id, the rule is permanent.

Every person who signs in this way acts in one organization, `defaultOrg`, `default`, the one organization of such an install. It is never read from a request or a token, and it is not `local`, which stays the organization of local mode.

`personSignedInOf(person, claims, at)` is what a sign-in keeps of the person in their record, below: their id, the `name` and the `email` the ID Token gave, where it gave them, and the time. Neither is ever a key or a part of one: "The RP MUST NOT rely upon this value being unique" (of `email`, OpenID Connect Core 1.0, §5.1), and §5.7 says the same of every claim but `iss` and `sub`.

## The sign-in's store

The sign-in's state is kept in a store of its own: tables whose names begin `auth_`, in the runtime's one database, the SQLite file or the PostgreSQL database the ledger is kept in, made by this package through the connection of the ledger, under a layout of their own. `authStoreOpened(database)` takes an `AuthDatabase`, the five members of the ledger's `ConnectionPorts` it uses, `dialect`, `read`, `write`, `transaction` and `migrated`, which the server fills with the `LedgerConnection` of `@on.auto/ledger`, so this package names no store and loads no driver, as the workflow host keeps its tables; it answers the `AuthStore`, whose `peopleRows` keep the people who signed in, whose `providerRows` keep the authorization server's rows and whose `signingKeyRows` name its signing key.

None of it is a fact. A session, a grant, a code or a token is security state that is changed in place, expires and is deleted at once when it is revoked or the person signs out, and a person's record is replaced at each sign-in and deleted on demand, which an append-only ledger is not for, so the store is not event-sourced, and adds or changes no fact, stream, projection or read model: CQRS "should only be used on specific portions of a system", and "each Bounded Context needs its own decisions on how it should be modeled" ([Martin Fowler, CQRS](https://martinfowler.com/bliki/CQRS.html)). The tables are the sign-in's own, as in "Private-tables-per-service – each service owns a set of tables that must only be accessed by that service" ([Chris Richardson, Database per service](https://microservices.io/patterns/data/database-per-service.html)), here a module of one process, and they are numbered by a layout of their own, as Django numbers the migrations of each app ("The migration files for each app live in a “migrations” directory inside of that app", [Migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/)) and keeps its sessions in a table of the project's one database, `django_session`. Where a database has no schemas, the owner's name is the prefix of its tables, as Django joins the app's label and the model's name. A table belongs to the ledger's layout when a store of Auto's hosted runtime keeps it or it is filled from the facts; it belongs to the sign-in's when it is state of the server's own sign-in, which no fact names and only the server makes.

### The layout of the store

`authLayout`, 3, numbers the layout of the store's tables, kept in the one row of `auth_layout`, `one_row BOOLEAN NOT NULL PRIMARY KEY DEFAULT TRUE CHECK (one_row)` beside `layout INTEGER NOT NULL`, the shape of the ledger's `ledger_layout`. The store opens at every start of the server, whatever is set, so what a database holds follows from the release and never from a setting. It lists the tables of the schema, `sqlite_master` on SQLite and `pg_tables` in `current_schema()` on PostgreSQL, and reads the number where `auth_layout` is among them; it counts as its own `auth_layout` and the tables it makes, by name, so a table another program keeps in the database is not its business.

- A database with no number and none of the store's tables is new, a database every release before this one made among them: one transaction makes `auth_layout` and writes the number, `ON CONFLICT (one_row) DO NOTHING`, and is kept only when it wrote it, so the table never stands without its row.
- A database in the layout kept opens.
- A database in an earlier layout is carried forward by the steps of `authLayoutSteps`, `{ layout, statements }`, one for each number, all found before any is taken. Each runs in a transaction of its own: its statements, then the number, written last and only while the database is still at the layout before, `UPDATE auth_layout SET layout = <n> WHERE layout = <n - 1>`, and the connection's `transaction` keeps its statements only when the last writes a row. A step that fails rolls back and leaves the database at the layout before it, from which the next start goes on. A layout the store is given no step to refuses the start before any step is taken.
- On PostgreSQL the transaction that lays the layout and that of each step first take an advisory lock of the store's own, `pg_advisory_xact_lock(hashtextextended('auth_layout', 0))`, so servers that open one database together lay it once and take each step once: the later one waits, finds the number written, and keeps nothing. A step's statements are written to leave a database as a new one of its layout would be; a statement that cannot run a second time, such as an `ADD COLUMN`, fails the later of two servers that took its step at the same moment, which is kept from nothing, and that server's next start finds the step taken.
- A database in a newer layout, in a layout before the first, or that holds the store's tables with no number, is refused as an `AuthLayoutRefused`, tagged `auth_layout_refused`, with `found` and `kept`, and left as it was.

Then the tables and indexes of the layout that are missing are made, `CREATE … IF NOT EXISTS`, through `migrated`, so a store whose first opening ended after it laid the layout gets them at its next start, and a step that only brings a table takes no statement, as the ledger's own steps take none for a table it makes as it opens. Layout 1 held `auth_sessions`; step 2 brings `auth_people` and takes no statement; step 3 brings `auth_oidc_models` and `auth_signing_key`, and drops `auth_sessions` and its index, the session of the server's own that the authorization server's replaces.

The store's floor is layout 1, as the release that laid it made it, in `src/store/auth-floor.json`: its statements, the same on both stores. `src/store/auth-floor-behaviour.ts` is the store's twin, as the server's twins are the ledger's: it makes a database at the floor on a database the ledger made, with a session of layout 1 in it, opens the store on it, which carries it forward by every step, and compares its structure with that of a new store (`structureOfTheSQLiteFile` and `structureOfThePostgreSQLDatabase` of `@on.auto/ledger/database-structure`). It runs on a SQLite file and on PostgreSQL. A step that does not leave a store as a new one of its layout fails it.

### The people in the store

Layout 2 holds `auth_people`, one row for each person who signed in here, the list an admin picks a colleague from, its times in milliseconds since 1970:

| Column          | What it holds                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `person`        | the key: the person's id, `personIdOf`, the id their role facts name, which the store keeps beside nothing of `iss` or `sub` |
| `name`          | the `name` claim of their last sign-in, or nothing (OpenID Connect Core 1.0, §5.1)                                           |
| `email_address` | the `email` claim of their last sign-in, or nothing                                                                          |
| `joined_at`     | their first sign-in, the "joined" of the list                                                                                |
| `updated_at`    | the last sign-in that replaced the row, after the claim of §5.1, "Time the End-User's information was last updated."         |

`PeopleRows` is the port: `kept` writes one row in one statement, `INSERT … ON CONFLICT (person) DO UPDATE`, which replaces the name, the address and `updated_at` and leaves `joined_at`, so a name or an address the provider changed is taken up at the next sign-in, one it no longer gives is no longer kept, and a sign-in tried again writes the same row; `listed` reads every row in the order the people joined; `deleted` deletes one person's row. A row does not expire, and is not deleted when an admin removes the person, so the admin can find them and give them a role again; their role facts in the ledger keep only the id. Never kept: any other claim, a picture, groups, a token of the provider. Personal data stays out of the facts, which cannot be erased, and in rows that can, as Verraes's Forgettable Payloads keeps it. `src/people/people-rows-behaviour.ts` holds the store to the port, on both stores.

### The authorization server's rows in the store

Layout 3 holds `auth_oidc_models`, one row for each instance of a model of the library, its times in milliseconds since 1970:

| Column        | What it holds                                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| `model`       | the library's name of the model, such as `Session`, `Grant` or `RefreshToken`                                 |
| `sha256`      | with `model`, the key: the SHA-256, in hexadecimal, of the instance's id, by `sha256Of` of `@on.auto/content` |
| `payload`     | the instance as JSON, without its id                                                                          |
| `grant_id`    | the grant a code or a token belongs to, or nothing                                                            |
| `uid`         | the `uid` of a session, or nothing                                                                            |
| `consumed_at` | when a code or a refresh token was used, or nothing                                                           |
| `expires_at`  | when it ends, or nothing for a registered client                                                              |

`auth_oidc_models_grant_id`, `auth_oidc_models_uid` and `auth_oidc_models_expires_at` index the three columns it is read and swept by. `auth_signing_key` holds one row, `one_row` as `auth_layout` keeps it, `secret_id`, the secret the key is sealed under, and `created_at`, written `ON CONFLICT (one_row) DO NOTHING RETURNING`, so of two servers that write it at once one is answered that it wrote it. `src/authorization-server/provider-rows-behaviour.ts` and `signing-key-rows-behaviour.ts` hold the store to the two ports, on both stores.

Each statement of the store is a transaction of its own, never part of an append's, so a session ended stays ended whatever a transaction of the ledger open at that moment does. On PostgreSQL that holds by the connection, whose statements run on connections of their own. On SQLite the ledger's driver runs a statement issued inside a transaction of the ledger, or by code such a transaction woke, on that transaction's connection, an ambient transaction; so the store captures the async context as it opens, at start and outside any transaction, with `AsyncLocalStorage.snapshot()`, and issues every statement inside that capture, as the ledger does for its kept secrets (see [Kept secrets](../ledger/README.md#kept-secrets)), the way .NET's `TransactionScopeOption.Suppress` and Spring's propagation `NOT_SUPPORTED` suppress one. `src/store/auth-store-behaviour.ts` holds a session's row destroyed from outside a consistent read of the ledger and one destroyed by the code inside it, both rolled back, to staying destroyed, on a SQLite file, on SQLite's private memory, where a consistent read is a transaction of the ledger's one connection, and on PostgreSQL; without the capture, the second was lost on private memory.

`src/store/auth-store-behaviour.ts` is the store's contract: a database the ledger made before laid, every table and index it makes beginning with `auth_`, a database opened again as a restarting server keeping its rows and changing nothing, one opened twice at once laid once, the tables a first opening left out made, steps taken in order and once when two openings carry it together, a failed step left at the layout before, a missing step refused before any is taken, a newer layout, one before the first and tables with no number refused, `peopleRowsBehaviour` on its people, `providerRowsBehaviour` on the authorization server's rows and `signingKeyRowsBehaviour` on its signing key's row. It runs on a SQLite file (`auth-store.test.ts`) and on PostgreSQL where `LEDGER_TEST_POSTGRESQL_URL` names a server (`auth-store-on-postgresql.test.ts`).

The server opens the store at every start, in local mode too and whether or not `OIDC_ISSUER` is set, once the ledger is open (`signInOpened` of `packages/server/src/composition/ledger-store.ts`), and answers a store a newer release carried forward in words of its own, where the ledger is and what to do, as it answers a newer ledger. Its gate pins the store's tables and indexes apart from the ledger's, in `packages/server/src/database/auth-layout.json` under `authLayout`, split from the rest by the one prefix, `authTablePrefix`, which the testing entry exports with `authLayout` (see [The gates of the layout](../ledger/README.md#the-gates-of-the-layout)).

## Testing

`fakeProvider(issuer, options)` of `@on.auto/openid-connect/testing` is an OpenID provider that answers in the process: its metadata, which declares its registration endpoint unless `metadata` takes it out, its authorization server metadata where `authorizationServerMetadata` is given, its keys, which `rotate()` replaces, its registration endpoint, which registers a client for each request, records what each asked (`registrationsAsked()`), merges `registrationAnswer` into its answer and refuses with `registrationError`, and its token endpoint, which checks the client, its own or one it registered and has not withdrawn (`withdraw(clientId)`), by each of the three methods, answering `invalid_client` with a challenge where `challengesTheClient` is set, and the code, issued to that client, the redirect URI and the PKCE verifier, and answers an access token, and a refresh token where `refreshTokens` is set (`refreshTokensIssued()`). Its UserInfo endpoint, declared where `userInfo` is given, answers the access token's subject and those claims, and a challenge for an access token it does not know (`userInfoReads()`); its revocation endpoint, declared where `revocation` is set, checks the client as the token endpoint does, records each token (`tokensRevoked()`) and ends the access token of a refresh token it revokes, as RFC 7009, §2.1, says it should. `signedIn(authorizationUrl, subject)` and `refused(authorizationUrl, error)` give the query it would send a person back with. `requests` answers for the issuer alone and refuses any other address. Tests that need a clock set Vitest's fake `Date`. `browserAt(address, publicUrl)` is a browser of a test: it keeps the cookies it is set, sends them with each request, and reaches a server at `address` for an address under `publicUrl`, as a proxy that ends TLS would. `src/testing/authorization-server-over-http.ts` serves the authorization server over HTTP on a SQLite file, beside a handler of its own, with a sign-in and pages a test chooses, and `src/testing/agents-signing-in.ts` holds the steps of a client that signs a person in there.
