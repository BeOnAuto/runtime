# @on.auto/openid-connect

The runtime as an OpenID Connect relying party of a company's own identity provider, and the session a person holds once they signed in there. A runtime that sets `OIDC_ISSUER`, `OIDC_CLIENT_ID` and a client secret signs its people in this way; the server reads those settings, serves the routes and keeps the sessions (`packages/server/src/settings/openid-connect-settings.ts`, `packages/server/src/sign-in/company-sign-in.ts`). It is a package of its own so that Auto's hosted runtime, which never signs anyone in this way, loads none of it, and so that the library it is built on, which runs on Node, stays out of every other package.

## The library

The protocol is [openid-client](https://github.com/panva/openid-client), MIT, an OpenID Certified relying party for Node, by the author of `jose`, which the runtime already uses for the tokens of the Auto identity service. It runs on the Fetch API and Web Crypto that Node 20 and later carries, below the runtime's floor of Node 26.10, and its package carries its licence, as do the two it depends on, `oauth4webapi` and `jose`, both MIT. Nothing of the protocol is written here: the authorization request, the exchange of the code, the checks of the answer and of the ID Token, and the keys are the library's.

`openid-client` 6.8.9 asks for `jose` 6.2.15 or later, and the catalog of the runtime pins 6.2.12, which the identity package and Auto's hosted runtime use, so pnpm keeps a second `jose`, 6.2.17, for this package alone. 6.8.9 is the newest release older than the seven days `minimumReleaseAge` waits, and the first whose types hold under `exactOptionalPropertyTypes`, which the runtime's TypeScript sets.

The library's own `discovery` is not used: for two hosts of one vendor it does something else, accepting any issuer there, or a template of one, and here nothing depends on a vendor. The package reads the metadata itself and gives it to the library's `Configuration`.

## Discovery

`relyingPartyOf(settings, requests)` reads the provider's metadata once, as the server starts, at `metadataAddressOf(issuer)`: the issuer with `/.well-known/openid-configuration` added, a terminating `/` taken off first (OpenID Connect Discovery 1.0, §4), so an issuer with a path is read where it says. It takes the metadata only when it names the issuer it was read for identically, character for character (§4.3), and names an `authorization_endpoint`, a `token_endpoint` and a `jwks_uri`, each an `https` URL; otherwise it throws an `UnusableIdentityProviderError` that says which, and the server does not start.

The client proves itself at the token endpoint with its secret, by the method `OIDC_TOKEN_ENDPOINT_AUTH_METHOD` names, or else by the first of `client_secret_basic`, `client_secret_post` and `client_secret_jwt` that the metadata declares in `token_endpoint_auth_methods_supported`, `client_secret_basic` where it declares none (OpenID Connect Core 1.0, §9). A method the provider does not declare refuses the start.

Every request to the provider, the metadata, the token endpoint and the keys, goes through `requests.fetch`, bounded as the requests to the Auto identity service are: an answer within 10 seconds, of at most 64 KiB, and no redirect followed. A test gives a fetch of its own, so no request leaves the process.

## A sign-in

`signInStarted()` answers the address to send the person to and what the sign-in must find again when the person comes back: a fresh `state`, `nonce` and PKCE verifier, drawn by the library for each sign-in, sent with the code challenge, `S256`, the `scope` the settings name and the redirect URI. `signInFinished(query, pending)` takes the query the provider sent the person back with and those three, and answers one of:

- `{ signedIn: { issuer, subject }, claims: { name, email } }`, the `iss` and `sub` of the ID Token as the provider gave them, and of its other claims the two Standard Claims of OpenID Connect Core 1.0, §5.1, that a person's record keeps, `name`, the "End-User's full name in displayable form", and `email`, each where the ID Token holds it as text, and nothing else of it;
- `{ refusedByTheProvider: code }`, the `error` the provider answered with, at the redirect or at the token endpoint, when it has the syntax RFC 6749 gives an error code;
- `{ failed: code }`, where the answer could not be read, in the words of the bounds above, or the library refused it, by the library's error code, such as `OAUTH_JWT_CLAIM_COMPARISON_FAILED`.

It checks, through the library: the `state`; the `iss` of the answer where the provider sent one, and its presence where the metadata declares `authorization_response_iss_parameter_supported` (RFC 9207); the code exchanged with the verifier; and the ID Token as OpenID Connect Core 1.0, §3.1.3.7 says, its issuer, its audience, its `nonce`, its times with 60 seconds of leeway either way, and its signature, by a key of the provider's `jwks_uri`, which the library reads again for a key it does not know at most once a minute and keeps at most five minutes. The signature is checked although the ID Token comes straight from the token endpoint, where the section lets the client trust TLS instead. No error of the library reaches the caller: they carry the query, the codes and the tokens, so only the code above leaves this package.

## Sessions

`sessionsOf(rows, now)` keeps a person's session: `begun(person)` draws 32 random bytes, answers them in base64url for the cookie, and keeps only their SHA-256 with the issuer and the subject as given; `personOf(identifier)` answers that person while the session lasts and records its use, at most once in ten minutes; `ended(identifier)` ends it at once. A session ends 7 days after the last use recorded and at most 30 days after the sign-in (`mostUnusedMs`, `mostLifetimeMs`), Grafana's defaults, so 7 days unused is exact to ten minutes. A use recorded is a write, and on a SQLite file a write waits its turn in the ledger's one writer's queue, so a session that is used at every request writes once in ten minutes and not at every request, as Grafana counts inactivity: "The lifetime resets at each successful token rotation (`token_rotation_interval_minutes`)", whose default is "each 10 minutes" ([Configure Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-grafana/)).

`SessionRows` is the port a store implements: `kept`, `found`, `used` and `ended`, each row with the time it expires, and a row that has expired is never found and is removed when another is kept. Its fields take the names of the columns of `auth_sessions`, below: `sha256`, `issuer`, `subject`, `createdAt`, `lastUsedAt` and `expiresAt`. The sign-in's store keeps them in the runtime's database, and the server keeps them nowhere else; `sessionRowsInMemory()` of the testing entry keeps them in the process, for tests, so no server runs on it; `sessionRowsBehaviour` of the testing entry holds a store to the port, and both run it.

## Who a person is

A person who signed in here is known by the pair of the ID Token's `iss` and `sub`, the only claims OpenID Connect Core 1.0, §5.7, lets a relying party rely on as a stable identifier, and never by an email or a name. `personIdOf({ issuer, subject })` is their id in Auto, and the one place it is made: the lowercase hexadecimal SHA-256 of the UTF-8 octets of the JSON array `[iss, sub]`, written with no whitespace, as `JSON.stringify` and RFC 8785 write an array of two strings. Both are taken exactly as the validated ID Token gave them, with no trimming, no change of letter case and no normalising of the address, so the token's own `iss` counts, not the spelling of `OIDC_ISSUER`. An array, and not the two joined by a mark, because a `sub` may hold any character, so no mark is safe. A canonical JSON form hashed with SHA-256 as an identifier is the method of RFC 7638. The result is 64 characters of `0-9a-f`, with no salt and no secret, so it is the same on every server of an install and survives a restart; it is a pseudonym, which anyone who knows the issuer and the `sub` can compute. The test pins it with made-up pairs and their ids, so it cannot drift: once anything is recorded under an id, the rule is permanent.

Every person who signs in this way acts in one organization, `defaultOrg`, `default`, the one organization of such an install. It is never read from a request or a token, and it is not `local`, which stays the organization of local mode.

`personSignedInOf(person, claims, at)` is what a sign-in keeps of the person in their record, below: their id, the `name` and the `email` the ID Token gave, where it gave them, and the time. Neither is ever a key or a part of one: "The RP MUST NOT rely upon this value being unique" (of `email`, OpenID Connect Core 1.0, §5.1), and §5.7 says the same of every claim but `iss` and `sub`.

## The sign-in's store

The sign-in's state is kept in a store of its own: tables whose names begin `auth_`, in the runtime's one database, the SQLite file or the PostgreSQL database the ledger is kept in, made by this package through the connection of the ledger, under a layout of their own. `authStoreOpened(database)` takes an `AuthDatabase`, the five members of the ledger's `ConnectionPorts` it uses, `dialect`, `read`, `write`, `transaction` and `migrated`, which the server fills with the `LedgerConnection` of `@on.auto/ledger`, so this package names no store and loads no driver, as the workflow host keeps its tables; it answers the `AuthStore`, whose `sessionRows` keep the sessions and whose `peopleRows` keep the people who signed in.

None of it is a fact. A session is current state that is changed in place, expires and is deleted at once when the person signs out, and a person's record is replaced at each sign-in and deleted on demand, which an append-only ledger is not for, so the store is not event-sourced, and adds or changes no fact, stream, projection or read model: CQRS "should only be used on specific portions of a system", and "each Bounded Context needs its own decisions on how it should be modeled" ([Martin Fowler, CQRS](https://martinfowler.com/bliki/CQRS.html)). The tables are the sign-in's own, as in "Private-tables-per-service – each service owns a set of tables that must only be accessed by that service" ([Chris Richardson, Database per service](https://microservices.io/patterns/data/database-per-service.html)), here a module of one process, and they are numbered by a layout of their own, as Django numbers the migrations of each app ("The migration files for each app live in a “migrations” directory inside of that app", [Migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/)) and keeps its sessions in a table of the project's one database, `django_session`. Where a database has no schemas, the owner's name is the prefix of its tables, as Django joins the app's label and the model's name. A table belongs to the ledger's layout when a store of Auto's hosted runtime keeps it or it is filled from the facts; it belongs to the sign-in's when it is state of the server's own sign-in, which no fact names and only the server makes.

### The layout of the store

`authLayout`, 2, numbers the layout of the store's tables, kept in the one row of `auth_layout`, `one_row BOOLEAN NOT NULL PRIMARY KEY DEFAULT TRUE CHECK (one_row)` beside `layout INTEGER NOT NULL`, the shape of the ledger's `ledger_layout`. The store opens at every start of the server, whatever is set, so what a database holds follows from the release and never from a setting. It lists the tables of the schema, `sqlite_master` on SQLite and `pg_tables` in `current_schema()` on PostgreSQL, and reads the number where `auth_layout` is among them; it counts as its own `auth_layout` and the tables it makes, by name, so a table another program keeps in the database is not its business.

- A database with no number and none of the store's tables is new, a database every release before this one made among them: one transaction makes `auth_layout` and writes the number, `ON CONFLICT (one_row) DO NOTHING`, and is kept only when it wrote it, so the table never stands without its row.
- A database in the layout kept opens.
- A database in an earlier layout is carried forward by the steps of `authLayoutSteps`, `{ layout, statements }`, one for each number, all found before any is taken. Each runs in a transaction of its own: its statements, then the number, written last and only while the database is still at the layout before, `UPDATE auth_layout SET layout = <n> WHERE layout = <n - 1>`, and the connection's `transaction` keeps its statements only when the last writes a row. A step that fails rolls back and leaves the database at the layout before it, from which the next start goes on. A layout the store is given no step to refuses the start before any step is taken.
- On PostgreSQL the transaction that lays the layout and that of each step first take an advisory lock of the store's own, `pg_advisory_xact_lock(hashtextextended('auth_layout', 0))`, so servers that open one database together lay it once and take each step once: the later one waits, finds the number written, and keeps nothing. A step's statements are written to leave a database as a new one of its layout would be; a statement that cannot run a second time, such as an `ADD COLUMN`, fails the later of two servers that took its step at the same moment, which is kept from nothing, and that server's next start finds the step taken.
- A database in a newer layout, in a layout before the first, or that holds the store's tables with no number, is refused as an `AuthLayoutRefused`, tagged `auth_layout_refused`, with `found` and `kept`, and left as it was.

Then the tables and indexes of the layout that are missing are made, `CREATE … IF NOT EXISTS`, through `migrated`, so a store whose first opening ended after it laid the layout gets them at its next start, and a step that only brings a table takes no statement, as the ledger's own steps take none for a table it makes as it opens. Layout 1 held `auth_sessions`; step 2 brings `auth_people` and takes no statement.

The store's floor is layout 1, as the release that laid it made it, in `src/store/auth-floor.json`: its statements, the same on both stores. `src/store/auth-floor-behaviour.ts` is the store's twin, as the server's twins are the ledger's: it makes a database at the floor on a database the ledger made, with a session in it, opens the store on it, which carries it forward by every step, and compares its structure with that of a new store (`structureOfTheSQLiteFile` and `structureOfThePostgreSQLDatabase` of `@on.auto/ledger/database-structure`), the session kept. It runs on a SQLite file and on PostgreSQL. A step that does not leave a store as a new one of its layout fails it.

### The people in the store

Layout 2 holds `auth_people`, one row for each person who signed in here, the list an admin picks a colleague from, its times in milliseconds since 1970, as the sessions':

| Column          | What it holds                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `person`        | the key: the person's id, `personIdOf`, the id their role facts name, which the store keeps beside nothing of `iss` or `sub` |
| `name`          | the `name` claim of their last sign-in, or nothing (OpenID Connect Core 1.0, §5.1)                                           |
| `email_address` | the `email` claim of their last sign-in, or nothing                                                                          |
| `joined_at`     | their first sign-in, the "joined" of the list                                                                                |
| `updated_at`    | the last sign-in that replaced the row, after the claim of §5.1, "Time the End-User's information was last updated."         |

`PeopleRows` is the port: `kept` writes one row in one statement, `INSERT … ON CONFLICT (person) DO UPDATE`, which replaces the name, the address and `updated_at` and leaves `joined_at`, so a name or an address the provider changed is taken up at the next sign-in, one it no longer gives is no longer kept, and a sign-in tried again writes the same row; `listed` reads every row in the order the people joined; `deleted` deletes one person's row. A row does not expire, and is not deleted when an admin removes the person, so the admin can find them and give them a role again; their role facts in the ledger keep only the id. Never kept: any other claim, a picture, groups, a token of the provider. Personal data stays out of the facts, which cannot be erased, and in rows that can, as Verraes's Forgettable Payloads keeps it. `src/people/people-rows-behaviour.ts` holds the store to the port, on both stores.

### The sessions in the store

Layout 1 holds `auth_sessions`, one row for each session, its times in milliseconds since 1970, as `webhooks_received.kept_until` of the ledger:

| Column         | What it holds                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| `sha256`       | the key: the SHA-256, in hexadecimal, of the identifier the cookie holds, by `sha256Of` of `@on.auto/content` |
| `issuer`       | the `iss` of the ID Token, exactly as given (OpenID Connect Core 1.0, §2, §5.7)                               |
| `subject`      | the `sub` of the ID Token, exactly as given                                                                   |
| `created_at`   | when the person signed in                                                                                     |
| `last_used_at` | the last use recorded                                                                                         |
| `expires_at`   | when it expires: the earlier of 7 days after the last use recorded and 30 days after `created_at`             |

`auth_sessions_expires_at` indexes `expires_at`, as `webhooks_received_kept_until` indexes `kept_until`. `kept` deletes every row that has expired, then inserts its own, so each sign-in sweeps, with no timer and nothing for servers to agree on; `found` reads one row by its key with an `expires_at` after the time given, so a row that has expired is never answered, swept or not; `used` updates the use and the expiry of one row; `ended` deletes one. The identifier itself, the ID Token and every other claim of it, the provider's tokens and the pending sign-in, which stays in the browser's cookie, are never stored. The column names come from GitLab's tokens, `created_at`, `last_used_at` and `expires_at` ([Personal access tokens API](https://docs.gitlab.com/api/personal_access_tokens/)).

Each statement of the store is a transaction of its own, never part of an append's, so a session ended stays ended whatever a transaction of the ledger open at that moment does. On PostgreSQL that holds by the connection, whose statements run on connections of their own. On SQLite the ledger's driver runs a statement issued inside a transaction of the ledger, or by code such a transaction woke, on that transaction's connection, an ambient transaction; so the store captures the async context as it opens, at start and outside any transaction, with `AsyncLocalStorage.snapshot()`, and issues every statement inside that capture, as the ledger does for its kept secrets (see [Kept secrets](../ledger/README.md#kept-secrets)), the way .NET's `TransactionScopeOption.Suppress` and Spring's propagation `NOT_SUPPORTED` suppress one. `src/store/auth-store-behaviour.ts` holds a session ended from outside a consistent read of the ledger and one ended by the code inside it, both rolled back, to staying ended, on a SQLite file, on SQLite's private memory, where a consistent read is a transaction of the ledger's one connection, and on PostgreSQL; without the capture, the second was lost on private memory.

`src/store/auth-store-behaviour.ts` is the store's contract: a database the ledger made before laid, every table and index it makes beginning with `auth_`, a database opened again as a restarting server keeping its sessions and changing nothing, one opened twice at once laid once, the tables a first opening left out made, steps taken in order and once when two openings carry it together, a failed step left at the layout before, a missing step refused before any is taken, a newer layout, one before the first and tables with no number refused, `sessionRowsBehaviour` on the store's sessions and `peopleRowsBehaviour` on its people. It runs on a SQLite file (`auth-store.test.ts`) and on PostgreSQL where `LEDGER_TEST_POSTGRESQL_URL` names a server (`auth-store-on-postgresql.test.ts`).

The server opens the store at every start, in local mode too and whether or not `OIDC_ISSUER` is set, once the ledger is open (`signInOpened` of `packages/server/src/composition/ledger-store.ts`), and answers a store a newer release carried forward in words of its own, where the ledger is and what to do, as it answers a newer ledger. Its gate pins the store's tables and indexes apart from the ledger's, in `packages/server/src/database/auth-layout.json` under `authLayout`, split from the rest by the one prefix, `authTablePrefix`, which the testing entry exports with `authLayout` (see [The gates of the layout](../ledger/README.md#the-gates-of-the-layout)).

## Testing

`fakeProvider(issuer, options)` of `@on.auto/openid-connect/testing` is an OpenID provider that answers in the process: its metadata, its keys, which `rotate()` replaces, and its token endpoint, which checks the client by each of the three methods, the code, the redirect URI and the PKCE verifier. `signedIn(authorizationUrl, subject)` and `refused(authorizationUrl, error)` give the query it would send a person back with. `requests` answers for the issuer alone and refuses any other address. Tests that need a clock set Vitest's fake `Date`.
