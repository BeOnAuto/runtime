# @on.auto/identity

Who calls the runtime: a key, the local developer, or a signed-in person the Auto identity service vouches for. `authenticatorFor` of `src/index.ts` takes the settings, the address the server listens on, the API keys and, where sign-in is on, the identity service, and answers the access mode and an asynchronous `authenticate`, which takes the credential a request presents, the path of the MCP endpoint it reached, if any, and its `Origin`, if it has one, and answers its `Authentication`: the `Principal` of the caller, or a `Refusal` whose `because` says why a token was refused, in words that name a rule or a claim and never a value of the token (`isRefusal` tells the two apart). A principal holds its own caller, `own`, and answers the caller of an org with `callerIn(org)`, or `undefined` for an org it does not admit: a key admits its own org, the local developer every org, whatever credential the request presents, and a signed-in person the org their token names. The access mode follows from what is configured, and `accessModeOf` of `src/access/access-mode.ts` is the one place that says which, for the authenticator and for the server's settings that follow from it: `credentials` with a key or with sign-in, `closed` when `API_KEYS` is set and lists no keys without sign-in, and with neither `local` on a loopback address, `localhost`, `127.0.0.0/8` or `::1` (`listensOnlyOnLoopback` of `src/access/loopback.ts`), a rule wider than the three names by which a URL or a `Host` header names the loopback, `namesTheLoopback` of `@on.auto/operations`, since a server that listens on any address of `127.0.0.0/8` is reachable from this computer alone. On any other address it is `local` too where the operator declares local mode, `accessMode: 'local'` (`DeclaredAccessMode`), for a server whose port only this computer reaches though it listens on every address of its own, such as a container whose port is published on `127.0.0.1` alone, which it cannot see; a key or sign-in still wins over the declaration. On any other address with neither and no declaration it names no mode, and `authenticatorFor` throws `ReachableWithoutCredentialsError`, which names the `HOST` and says that a server reachable beyond this computer needs `PUBLIC_URL`, to sign people in, or `API_KEYS`, or, where only this computer reaches its port, `ACCESS_MODE=local` with a `PUBLIC_URL` on the loopback, so the server stops before it listens. The server reads `listensOnlyOnLoopback` too, to refuse the declaration on another address without a `PUBLIC_URL` its links can point at. The key command, `src/key-command.ts`, prints a new key once and the `API_KEYS` entry that admits it.

## Keys

A key is `abk_<id>_<secret>`, stored as the SHA-256 of the whole key with its org, permissions and playbooks, and verified in constant time. The org `local` is local mode's and the id `local` the local developer's, so `API_KEYS` and the key command refuse both.

## Signed-in persons

`identityServiceOf` of `src/identity-service/identity-service.ts` takes the issuer, `autoIdentityService`, `https://clerk.on.auto`, unless a development runtime names another, `PUBLIC_URL`, the Studio settings and `ALLOWED_ORIGINS`, which the server hands it from its settings as it hands them to the API. A bearer that is not a key is one of two forms of token. An access token holds `aud`, and is what an agent or an agent gateway, a third party acting for a person, obtains through the authorization flow: it is taken for its audience, with the permissions among its scopes. A session holds no `aud`, and is what the identity service gives a page a person signs in to, such as the studio, Auto's own app: it is taken when its `azp` claim names an origin a page may come from and the request that presents it comes from that origin, so it serves its own page and never an agent, and gives every permission in its organization. `pageOriginsOf` of `src/access/page-origins.ts` is the one definition of those origins: the Studio host's, then the runtime's own origin where the runtime serves Studio, and `ALLOWED_ORIGINS`. The identity service gives it `PUBLIC_URL` as the runtime's own origin, and the API's `Origin` check and its CORS, which read it as well, give it the origin the API answers at. `src/access/studio.ts` holds the Studio settings, `StudioSettings`: `origin`, the Studio host, whose default is `defaultStudioOrigin`, `https://studio.on.auto`, and `served`, whether the runtime serves Studio itself at `servedStudioPath`, `/studio/`, since a page on a public origin may not reach an address on the person's machine. `studioBaseOf` is the one base of Studio's address that the runtime writes into a link: `{own origin}/studio/` where it serves Studio, and the Studio host's root otherwise. `signInScopes` are the scopes the runtime asks a client to request of the identity service: `user:org:read`, which binds the access token to the organization the person signs in to, as the `org_id` claim, and the four permissions, `allPermissions` of `@on.auto/operations`, the one definition of them, which the identity service defines as scopes of its own, each with a sentence its consent screen shows. At start it reads the issuer's metadata, from the addresses the MCP authorization specification orders, and its key set, each within 64 KiB and 10 seconds and following no redirect (`src/identity-service/issuer-requests.ts`), and stops with `UnusableIdentityServiceError` naming the service when one cannot be used or its key set holds no keys.

The [`jose`](https://github.com/panva/jose) library verifies the tokens and keeps the key set: `decodeJwt` reads, before anything is verified, whether the token holds `aud`, which decides its form, and a token it cannot decode is judged an access token, so its refusal is the one verification gives; `jwtVerify` then checks the signature with the key of the token's `kid`, or, for a token without one, with the issuer's only key of its type, refusing it when several fit, the algorithm among `RS256`, `PS256`, `ES256` and `EdDSA`, the issuer, the audience of an access token, `exp` and `nbf` with 60 seconds of leeway and that `exp`, `sub` and the org claim of its form, `org_id` or `o`, are present; `createRemoteJWKSet` holds the service's key set, read through the bounded read above, read again for an unknown `kid` once 60 seconds have passed since the last read that succeeded, and at the first token after it is ten minutes old, `jose`'s default age, set in `src/identity-service/issuer-keys.ts`; a token whose key set cannot be read once it is ten minutes old is refused, never verified against the old one. The runtime checks itself what is its own rule (`src/tokens/token-verification.ts`): a token at most 8 KiB before anything is decoded, a `typ` of `at+jwt`, `application/at+jwt`, `JWT` or `application/jwt` or none, an `iat` at most 60 seconds ahead, a `sub` that is a non-empty string of at most 256 bytes without control characters, unpaired surrogates or noncharacters, an org, an access token's `org_id` or the `id` of a session's `o`, that is an org id other than `local`, a `scope` claim, where an access token holds one, that is a string, and a session's `azp` among the origins of `pageOriginsOf`, refused `ERR_JWT_CLAIM_VALIDATION_FAILED on its azp claim` otherwise, as `jose` names a claim it refuses, and then the `Origin` of the request exactly its `azp`, refused `the session was not presented by the page it was issued to` otherwise, a request without `Origin` among them; `identityServiceOf` names the audiences a request may hold, `PUBLIC_URL`, with a final `/` or not, and on an MCP endpoint that endpoint's URL. A token that holds both `aud` and `azp` is an access token, and its `azp` is not read. Each form names its org in a claim of its own, and `orgClaimPaths` of `src/tokens/token-verification.ts` is the one definition of both, since the service's metadata advertises no claim name: an access token names it as `org_id`, which the service puts in it when the person grants `user:org:read`, and a session as the `id` of its `o`, since version 2 of the service's session token, marked `v: 2`, holds the organization the person signed in to as the object `o`, with its slug, `slg`, the person's role, `rol`, their permissions, `per`, and the feature-permission map, `fpm`, beside its `id`. A session without `o` is refused `ERR_JWT_CLAIM_VALIDATION_FAILED on its o claim` and one whose `o` is no object or holds no `id` that is an org id other than `local` is refused `its o.id claim is not an org id other than local`; nothing else of `o` is read, and `v` is not checked, since a format that named the organization elsewhere would hold no `o` and be refused for it. The tests of `src/identity-service/identity-service.test.ts` pin the claim of an access token and those of `src/identity-service/sessions.test.ts` the claim of a session. The person is `person:<sub>`, which `isSignedInPerson` tells apart from a key's id and from `local`, since neither holds a colon, in that org alone, over every playbook, with `allPermissions` for a session, whose `scope` is not read, and for an access token the permissions among the scopes its `scope` claim names, split at each space, in the order of `allPermissions`; any other scope, `user:org:read` among them, grants none, so an access token that grants none of the four, or holds no `scope`, is a person of the org with no permission (`signedInPersonOf` of `src/access/principal.ts`). No org is taken from anything else the token holds, the `org_id` of a session and the `o` of an access token among it, and `user:org:read` is not checked: `org_id` is. The security guide of the documentation sets out every rule.

`fakeIssuer` of `@on.auto/identity/testing` is an issuer for tests: it answers its metadata, its key set and a token endpoint for the client credentials grant, whose token's `scope` claim holds the scopes the request asked for, signs a token with `jose` and a key of each algorithm, issues the session of a page, `session(page, claims)`, in the shape of version 2 of the service's session token: `iss`, `sub`, a `sid`, the page as `azp`, `iat`, `nbf`, an `exp` a minute later, `v: 2` and as `o` the organization `acme` with its `id`, `slg`, `rol`, `per` and `fpm`, under the `typ` `JWT` and with no `aud`, each claim a test gives taking the place of its own, `o` whole, so `{ o: undefined }` issues a session without one, and turns its keys over; `signedTokens` and `principalIn` help tests sign a token, which holds every sign-in scope unless a test gives it a `scope` of its own, or a session, against an identity service that allows `testAllowedOrigin` beside the Studio host, `hostedStudio`, or beside the Studio host and `testPublicUrl` when given `servedStudio`, and read the person it admits.

## Measurement

`pnpm --filter @on.auto/identity measure` starts the identity service 200 times against the fake issuer answered in process, its metadata and a key set of four keys, and verifies 10,000 access tokens of each algorithm one after another through `personOf`: the decoding that decides its form, the `jose` verification with its key, the runtime's own checks and the person it admits. In process, the start measures the runtime's own work; the identity service's two round trips at start add their network time to it, and `jose` imports a key the first time a token names it. On Node v26.10.0 with 16 cores, on 2026-10-14, two runs:

| Measured                                      | Run 1   | Run 2   |
| --------------------------------------------- | ------- | ------- |
| Start: metadata and key set read              | 0.06 ms | 0.04 ms |
| Verification of an `RS256` token, per request | 30.4 µs | 28.7 µs |
| Verification of a `PS256` token, per request  | 30.7 µs | 29.6 µs |
| Verification of an `ES256` token, per request | 54.3 µs | 53.5 µs |
| Verification of an `EdDSA` token, per request | 54.5 µs | 54.3 µs |
