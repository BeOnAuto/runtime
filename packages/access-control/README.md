# @on.auto/access-control

The policy decision point of Auto Runtime: the one place that answers whether a principal may perform an operation on a resource, decided from policies rather than from code written for each role. It holds the engine that decides, Cedar, behind the port of `@on.auto/operations`, the schema and the built-in policies the release ships, the port of the roles a principal holds, and the role assignments themselves: their facts, the one decider that writes them, their read model, the operations that give, take away and list them, and the import of the roles people held before they were kept (see [Role assignments](#role-assignments)). It decides nothing yet: the dispatcher asks it in report-only mode, beside the check that decides (see [Report-only](#report-only)), and the dispatcher's deciding mode, in which its answer is the answer, is composed by no host.

It is a package of its own so that the engine, a WebAssembly module of 4.4 MB, is loaded only where a host composes it. The question, the answer and the port are in `@on.auto/operations`, beside the dispatcher that asks, as `Ledger` is there and its stores are in `@on.auto/ledger`; this package depends on `@on.auto/operations` and nothing in the runtime depends on it but the server (`packages/server/src/composition/served-access-control.ts`), so a host that composes the dispatcher without it loads no Cedar, and a host that bundles its modules, as a Worker does, imports the engine only once it composes a decision point (see [The engine](#the-engine)). A second entry, `@on.auto/access-control/role-assignment-facts`, is the module of the facts of role assignments alone, with the one table that reads the identity service's role keys as the roles those facts hold (see [The import](#the-import)), which imports nothing of the engine, so a host that only reads or keeps those facts, as the cloud's list of the facts its objects record does (`services/hosted-runtime/src/platform/content-holders.ts`), loads none of Cedar either.

## The question and the answer

The question is Cedar's own request, "an authorization request has four parts", in the runtime's words, `AccessRequest` of `@on.auto/operations`:

- `principal`, who acts, `{ type, id }`: `person`, with the subject their sign-in carries, `key`, `playbook` for a playbook acting as itself, or `local_developer`.
- `action`, the operation, `{ scope, name }`.
- `resource`, what it acts on: `{ type: 'org', id }`, `{ type: 'playbook', id, org }` or `{ type: 'definition', id, playbook, org }`.
- `context`: `via`, how the call arrived, `studio`, `agent`, `key`, `conversation`, `run` or `local`; `granted`, what the credential grants, its org, its permissions and its playbooks; and `operation`, what the operation declares about itself, its kind and whether it targets a playbook, only reads, reaches outside, may change outside, cannot be undone or manages permissions, `permissions_management`, an operation that grants or changes who may do what (see [`@on.auto/operations`](../operations/README.md)).

The answer, `AccessDecision`, is `allow` or `deny`, the ids of the policies that determined it, as AWS Verified Permissions names them, and the errors met, if any. Nothing else.

## The schema and the built-in policies

`src/policies/access.cedarschema` declares the entities, `Org`, `Role`, `Person in [Role]`, `Key`, `LocalDeveloper`, `Playbook in [Org]` and `Definition in [Playbook]`, and the context. `accessSchemaOf(declared, permissions, operations)` (`src/schema/access-schema.ts`) adds to it an action group for each permission, generated from `allPermissions` of `@on.auto/operations`, and an action for each operation the dispatcher is handed, `"<scope>/<name>"` in the groups of the permissions it declares, applying to the resources of its scope: `[Org]`, or `[Org, Playbook, Definition]` for an org operation that targets a playbook and for an operation of a playbook. The dispatcher asks an operation of a playbook about the playbook of the call, always; the org is asked only by `mayCall` of `@on.auto/operations`, whether a caller may call it on some playbook, as an MCP endpoint that takes the playbook as an argument lists its tools before a call names one, and it is decided there by the roles held at the org (`src/decision-point/model.test.ts`). Nothing is kept by hand: the server hands it every operation its dispatcher is handed, the catalogs it serves and the workflow host's own, from the one value it gives the host (`packages/server/src/workflows/host-operations.ts`). An operation handed over more than once, as one served in two catalogs, is declared once, and two that share a scope and a name but declare different permissions or targets are refused, so the decision point does not load and denies every request.

`src/policies/built-in.cedar` holds twelve policies, each named by its `@id`:

| Id                                        | What it says                                                                                                           |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `viewer`                                  | A principal in the role `viewer` may do what `org:read` or `playbook:read` permits                                     |
| `editor`                                  | A principal in the role `editor` may do what any of the four permissions permits                                       |
| `admin`                                   | A principal in the role `admin` may do what any of the four permissions permits                                        |
| `key`                                     | A key may do what its grant permits                                                                                    |
| `local-developer`                         | The local developer may do what its grant permits                                                                      |
| `playbook-itself`                         | A playbook acting as itself may do what its grant permits                                                              |
| `run-as-started`                          | A person's call made by a run they started may do what the run's grant permits                                         |
| `enrolment`                               | A person signed in to Studio may call an operation that declares it makes its caller a member, before they hold a role |
| `own-org`                                 | Nobody acts outside the org of their grant                                                                             |
| `within-granted-permissions`              | Nobody calls an operation none of whose declared permissions their grant holds                                         |
| `within-granted-playbooks`                | A grant limited to some playbooks reaches only those, and an operation that targets a playbook must name one of them   |
| `permissions-managed-by-admins-in-studio` | Nobody but an Admin signed in to Studio calls an operation that declares it manages permissions                        |

No policy names an operation, a person, a key, an org or a playbook: only the built-in roles and the permissions operations declare (`src/engine/prepared-policies.test.ts`). A rule may use only what the schema holds, and Cedar's validator refuses one that uses anything else; the policies pass it in strict mode with no error and no warning.

### What a Viewer may do

A Viewer may do what `org:read` or `playbook:read` permits, and nothing else: the operations that read, and the changes an operation declares anyone who may read may make, through `permittedBy` (`@on.auto/operations`), such as a comment, its resolution, activity marked as seen or a comment spoken aloud and written out. Nothing names an operation: a new operation is a Viewer's or not by the permissions it declares, its kind giving `org:read` or `playbook:read` to a query, `org:write` or `playbook:write` to a command, unless it declares others. The policy is a `permit` and nothing forbids a Viewer anything, so a role held beside it, as an Editor of one playbook later, only adds, as role-based access control is additive in NIST's model and in Azure's ("Azure RBAC is an additive model"). How the call arrived changes nothing a Viewer may do, in Studio, through an agent or asking Auto in a conversation, but for one case: a call a run makes, `via` `run`, which only a host's own work sets, the workflow host's calls and the next attempt of a started run among them, never a transport, is decided by `run-as-started` on the grant the run started with, as the runtime documents, "A workflow run keeps acting as the identity that started it, with that identity's permissions and playbooks, for as long as it runs" ([What happens when access is revoked](../../docs/reference/authentication.md#what-happens-when-access-is-revoked)), so a person made a Viewer while their run is under way does not stop it.

`src/decision-point/report-only-agreement-of-viewers.test.ts` runs the same calls as the agreement of 539 with every person a Viewer: once with each person's credential cut to reading, as Auto's cloud cuts a person's credential by their role today, and once deciding on the person's uncut credential, as the decision point will once grants are no longer cut by role; the decision point refuses exactly what today's check refuses a credential cut to reading, so the role alone keeps a Viewer to reading. The policies read, of a request's context, how it arrived, what its credential grants and, of what its operation declares, only whether it targets a playbook, whether it manages permissions and whether it makes its caller a member (`src/engine/prepared-policies.test.ts`).

### Joining an org

A person joins an org by its enrolment, the way it lets the people of its domains join without an invitation, as the identity service calls it a verified domain's enrollment mode, before they hold any role there; and a person with no role is allowed nothing a role gives. So an operation that makes its caller a member declares `enrolment` (`@on.auto/operations`), which only a command of the org may, and the policy `enrolment` lets a person signed in to Studio call it whatever roles they hold, through no agent, conversation or run. It decides by the declaration, never by the operation's name, and the forbids still bound it: the org of the grant and the permissions it holds. Whether the org's enrolment lets this person in is the operation's own rule, which its handler applies (`src/decision-point/model.test.ts`).

The server pins, for every operation it serves, what each role and each kind of caller may call: an Admin, an Editor and a Viewer in Studio, through a connected agent, asking Auto in a conversation and in a run they started, an agent approved to read, a person with no role, a person of another org, a key, a key that reads and a playbook in a run of its own (`packages/server/src/composition/served-decision-table.test.ts`). It reads each operation's declaration from the API document the server serves, which the server writes from the same registrations it hands its decision point, so an operation added or a declaration changed shows there as a changed row, and whether it manages permissions, which the document does not say, from the registrations of `src/operations`, the ones the server serves that declare it.

### What only an Admin does

An operation that grants or changes who may do what declares it, `permissionsManagement` of `@on.auto/operations`, the access level AWS IAM names "Permissions management", as `assign_role` and `unassign_role` do. One policy reads it, `permissions-managed-by-admins-in-studio`: a `forbid` on `context.operation.permissions_management` unless the principal is in the role `admin` and the call arrived `via` `studio`. In Cedar a `forbid` overrides every `permit` ("forbid overrides permit": "even if a permit policy is satisfied, any satisfied forbid policy overrides it, producing a Deny decision", the page Authorization of Cedar's reference guide, read on 15 November 2026), so an Editor, a Viewer, a person who holds no role, an Admin through an agent, asking Auto in a conversation or in a run they started (`run-as-started`), a key, a playbook acting as itself and the local developer are each refused it, whatever their credential grants. It is a declaration and one policy, not a fifth permission, so no credential, key or stored grant changes shape for it. Whom it lets through is the table of the built-in roles' own: a role is let through exactly where it assigns roles, `assignsRoles` of `builtInRoles`, which the decider reads for who may give a role (`src/roles/built-in-roles.test.ts`); and Studio is a person whose credential was issued to no client, the test the operations' own `actorInStudio` makes (`src/operations/role-assignment-shapes.ts`). A rule that depends on what is asked, such as which role may be given, stays with the decider. Self-hosted, where the server takes every signed-in person as an Editor in report-only mode (see [Report-only](#report-only)), each person's call of `assign_role` or `unassign_role` logs one difference, the check allowing and the decision point denying, and the decider answers it as before: it refuses a person who holds no role that gives roles, and no person holds one there before a first admin is named.

## Failing closed

Cedar skips a policy that errors and decides without it, so a `forbid` that errors can leave an `allow` ("the policy does not factor into the authorization response; it is skipped"). This package answers `deny`, with no determining policy, whenever an allow comes with an error (`src/engine/cedar-decisions.ts`), and `deny` where:

- the engine cannot be loaded, or its policies do not parse, have no `@id`, repeat an id, hold a template, or do not pass the schema in strict mode: every request is denied and the reason is logged once as an error, `unloadedMessage`;
- the request does not pass the schema, as an operation the release does not declare;
- Cedar throws;
- the roles of the principal cannot be read;
- no policy permits, which is Cedar's own default.

The enforcement point gives the decision point a second; one that does not answer within it is taken as a deny (`packages/operations/src/access-control/report-only.ts`).

## The engine

Cedar is `@cedar-policy/cedar-wasm`, pinned at 4.14.0, whose one change fixes a "memory leak potential when passing malformed inputs". It is loaded through its `web` entry with a compiled module, the one shape a Worker of Auto's cloud can also take, since a Worker compiles no module from bytes: `cedarOf(module)` instantiates it once in the process (`src/engine/cedar.ts`). In Node, `cedarModuleIn(shippedFiles)` reads its file, `web/cedar_wasm_bg.wasm` of the package, named under this package through `dependencyFileOf` of `@on.auto/shipped-files`, and compiles it once for each reader of files (`src/engine/cedar-module.ts`). A Worker compiles no module from bytes, so its bundler compiles the file as it bundles it, and `cedarModuleBundled(imported)` takes that compiled module through an import the host makes of `web/cedar_wasm_bg.wasm`: it imports it once, on first use, and refuses anything but a compiled module, so the engine is never compiled from bytes there (`src/engine/cedar-module-bundled.ts`). The host makes that import a dynamic `import()`, so a Worker that composes no decision point imports no engine. Both loaders hand a compiled module to `cedarDecisionPoint`, which instantiates it (`cedarOf`) and reads the schema and the built-in policies through the files the host gives it, so there is one engine, one schema, one set of policies and one wrapper, loaded two ways.

- **Loaded on first use.** At start only Cedar's JavaScript glue, about 19 KB, is imported; the WebAssembly, 4.4 MB, is neither read nor compiled. The first request reads the schema and the policies, generates the actions, validates them and reads them into the engine, and later ones find them read (`src/decision-point/cedar-decision-point.ts`). Measured with Node 26.12.1 on arm64 macOS, three times: the first decision took 81 ms and the process grew by 102 to 126 MiB, as V8 compiled the module.
- **Fixed names in the engine's store.** Cedar keeps what it reads in for the life of the process. The schema and the policies are read in under names made from the SHA-256 of their text, so a process holds one of each for the release, never one for each org (`src/engine/prepared-policies.ts`).
- **No network, file or clock while deciding.** The module asks its host for seven functions alone, pinned by a test: turning values into JSON and back, making and throwing its errors, reading a string, telling `undefined` and setting up a table (`src/engine/cedar-module.test.ts`). A decision reads the roles of its principal and asks the engine; it reads no file and no clock.

## Report-only

The server composes `cedarDecisionPoint({ module, files, operations, roles })` over every operation its dispatcher is handed and gives it to its dispatcher as `makeDispatcher(steps, { reportOnly })` of `@on.auto/operations`, which asks it about every call beside today's check, logs a difference with ids alone and answers as today's check decides.

In report-only mode the roles come, by default, from `editorRoleForEveryPerson`: every signed-in person holds the built-in role `editor` in the org asked about, and keys, playbooks and the local developer hold none, as today the runtime keeps no roles and gives a signed-in session every permission whatever role its token names, while Auto's cloud cuts the credential by role before the runtime sees it. What a credential grants still bounds every principal, through `within-granted-permissions` and `within-granted-playbooks`. One switch of the composition chooses the source, `roleAssignmentsFrom(source, reader)` (`src/roles/recorded-role-assignments.ts`): `every_person_an_editor`, today's and the server's (`servedRoleSource` of `packages/server/src/composition/served-access-control.ts`), or `role_assignments`, the roles the ledger records, read from their read model on every call (see [The read model](#the-read-model)). Report-only compares the decision point with today's check whichever it reads, and the pinned table and the agreement of 539 calls hand the decision point roles of their own, so neither changes with the switch.

The dispatcher can also be decided by it, `makeDispatcher(steps, { decidedBy })`, which nothing composes yet (see [the dispatcher, deciding](../operations/README.md#the-policy-decision-point-deciding)). `src/decision-point/deciding-agreement.test.ts` runs the agreement's 539 calls through it: with every person an Editor it answers every call exactly as today's check, in the same words; with every person a Viewer whose credential grants everything it allows and refuses exactly what today's check allows and refuses a credential cut to reading, the 57 calls that reading does not permit refused with the kind `permission_denied`, for the role, and the rest in today's words. The server pins the same for every operation it serves and each kind of caller (`packages/server/src/composition/served-decision-table.test.ts`).

## Role assignments

Who holds which role is recorded as facts, decided by one decider and read through a read model: the write side and the read side of CQRS (Greg Young, "CQRS Documents", 2010), over the ledger's event sourcing.

### The facts

`role_assigned` and `role_unassigned`, each `{ principal, role, scope, source }`, with the ledger's own `{ at, by }` as their context (`src/assignments/role-assignment-facts.ts`):

- `principal`, `{ type: 'person', id }`: the subject the person's sign-in carries, the id that follows `person:` in a caller's id, never a name or an address. Azure's `principalType` and Cedar's entity uid carry the kind beside the id the same way.
- `role`, `{ type: 'built_in', id }`: `admin`, `editor` or `viewer`, the runtime's own ids, never the identity service's keys.
- `scope`, `{ type: 'org', id }` or `{ type: 'playbook', id }`: always written, so a missing field never widens access.
- `source`: `manual`, `invitation`, `enrolment`, `import`, `command`, `identity_service` or `bootstrap`, how it came about, which `by` alone cannot say. A runtime older than the release that added a value cannot read a ledger that holds it, since the list is closed: once the first person has signed in to a runtime with the company's sign-in, and `bootstrap` is recorded, that ledger does not go back to a release before it.

One `role_assigned` starts one assignment and one `role_unassigned` ends exactly that one. A change of role is the two in one append, the role held taken away and the new one given; a role given that is held already, or taken away that is not held, records nothing. The names are Google Workspace's `ASSIGN_ROLE` and `UNASSIGN_ROLE` and Okta's "Assign a user role"; the shape is Azure RBAC's three elements, and a change is an end and a start, as in Kubernetes, where "a binding to a different role is a fundamentally different binding". Their fixtures are in `src/assignments/0.57.0`.

### The stream

The assignments of one scope are one stream of the org, `org/<org>/role-assignments/<id>`, its id a version 5 UUID of the scope's type and id (`roleAssignmentsStreamOf`), so a playbook whose id is the org's never meets it, and the ledger's keyed projections fold it as a stream of the org (`addressedStreamOf` of `@on.auto/operations`). In this release every assignment is at the org, so an org has one such stream.

### The decider

`roleAssignmentDecider` (`src/assignments/role-assignment-decider.ts`) is the one writer of these facts: the Decider of Jérémie Chassaing ("Functional Event Sourcing Decider", 2021), `decide(command, state)` giving the facts and `evolve(state, fact)` the state (`src/assignments/held-assignments.ts`): the assignments the stream holds, by principal, in Effect's `HashMap`, a persistent hash array mapped trie (Phil Bagwell, "Ideal Hash Trees", 2001), a count of the holders of each role, and, for each principal who held a role there and holds none now, the source of the fact that ended the last one, so a stream of n facts folds in n log n rather than in n², and the rule that the org keeps an admin reads a count. The state is folded from the stream at each load and stored nowhere. Measured on 2026-11-14 with Node 26.12.1 on arm64 macOS, on a SQLite file: a change of role in an org of 500 people took 3 ms and in one of 5,000 people 26 ms, the stream read whole each time, and the import of their roles 0.2 s and 8.5 s, each append of eight reading the stream again. The ledger's load-decide-append loop runs it with the version it loaded expected, so two changes made at once meet in the stream and the second is decided again on what the first wrote (see [How a command runs](../ledger/README.md#how-a-command-runs)). It takes five commands: `assign`, by a person, which gives a role in place of the one held there; `unassign`, by a person, which takes a role away; `provision`, by no person, which gives each principal named the role named where they hold none there, recorded with the source it names; `deprovision`, by no person, which ends every assignment a principal holds there, as a person leaves the org; and `enrol`, asked each time a person signs in through a company's own sign-in, which names no role and is decided below. Provisioning and deprovisioning are the identity world's words for giving and ending a person's access as they join and leave: SCIM, the standard identity services use for it, "provides provisioning and de-provisioning of resources in a separate context from authentication" (RFC 7642). Its rules, each decided on the state it loaded:

- **Escalation is prevented on the write path**, as Kubernetes prevents it in its RBAC API, "enforced at the API level, it applies even when the RBAC authorizer is not in use": a role is given or taken away only by a principal who holds there a role that assigns roles, and only a role whose permissions are all among those of a role the giver holds. Which roles assign roles, and what each permits, is the table of the built-in roles, `builtInRoles` (`src/roles/built-in-roles.ts`), never a role's name; `src/roles/built-in-roles.test.ts` holds it to the built-in policies, permission by permission. Today `admin` alone assigns roles. A refusal is `forbidden`.
- **The org keeps an admin**: a change that would leave nobody holding a role that assigns roles is refused, `conflict` of the kind `unworkable`, as the cloud's door refuses it today. The rule is that a change may not leave none, not that there is always one: an org starts with none until the first is given.
- **A role given by no person** is the bootstrap Kubernetes describes, given by a source that holds no role: `provision`, with the source of what it follows, `invitation` for a person who joins by an invitation, `enrolment` for one who joins by their email's domain, `identity_service` for a membership the identity service holds, `import` for the import (see [The import](#the-import)), or `command` for the command that names a self-hosted runtime's first admin (see [Self-hosted and the first admin](#self-hosted-and-the-first-admin)); never `manual`, which is a person's act. It gives a role only to a principal who holds none there, so run twice it changes nothing. There is one exception, for an org whose last admin has left: where nobody there holds a role that assigns roles, it may give such a role to a principal who holds another, in place of the one held, so the org has an admin again. It never puts a role that assigns none in place of one held, so a source that knows two roles where Auto knows three, as the identity service does, never turns a Viewer into an Editor.
- **A person who signs in is enrolled**: `enrol` carries the person and the org, and decides one of four things on the state it loaded, which `enrolledAs(state, principal)` answers so that the sign-in learns which applied and decides nothing itself. Where nobody there holds a role that assigns roles, the person is given one, `bootstrap`, in place of any role they hold, as `provision` does for an org whose last admin has left: the bootstrap Keycloak names in "Bootstrapping and recovering an admin account". Where someone does and the person holds a role, nothing. Where someone does and the person holds none and never held one, or their last was ended other than by `manual`, the person is given the role that permits least, `enrolment`, as Grafana gives "the default role assigned to new users" (`auto_assign_org_role`, `Viewer` by default) and Sema4.ai's people "join the workspace as **Members** the first time they sign in". Where their last role was ended by `manual`, nothing: a person an admin removed stays removed until an admin gives them a role again, as Sema4.ai's "Someone you removed does not rejoin by domain." The two roles are named once, beside the table, `builtInRolesAtSignIn` (`src/roles/built-in-roles.ts`), `admin` and `viewer`, and the decider takes them as it takes the table; `src/roles/roles.test.ts` holds the first to a role that assigns roles and the second to the one that permits least. Two people who sign in at once to an org with no admin meet in the stream: one append wins, the other is decided again on what it wrote and is given the role that permits least, so the org has exactly one first admin. Every sign-in after the first decides nothing, so a sign-in tried again writes no second fact. `enrolledAtSignIn(org, person, { at, by })` (`src/assignments/role-assignments-at-sign-in.ts`) asks it through `OrgWriter` and answers which applied, and `awaitsItsFirstAdmin(state)` whether the next person to sign in is given the role that assigns roles.
- **A person who leaves has their assignments ended**, so a departed admin no longer counts towards the org keeping one. `deprovision` with the source `manual`, a removal asked through Auto, keeps the rule that the org keeps an admin; with `identity_service`, a membership the identity service has ended already, it is recorded whatever it leaves, since the person has gone and the fact has happened. A principal who holds nothing there is deprovisioned with no fact.

### The read model

`roleAssignmentRows`, the table `role_assignments_1` (`src/assignments/role-assignment-rows.ts`), is a keyed projection of the ledger with several rows under one key (see [Several rows under one key](../ledger/README.md#several-rows-under-one-key)): it folds the org's `role-assignments` streams into a row for each role a principal holds and where, under the principal, `person:<id>`, its child the scope and the role, with how, when and by whom it was given. The ledger keeps it inline, in the transaction of the append that records the fact, the inline lifecycle of Marten and Emmett, so a read made after a change is committed reads it: on a self-hosted runtime the next request reads the new role, and in Auto's cloud the org's object, the one writer of its database, does the same.

`roleAssignmentsRecordedIn(reader)` answers the `RoleAssignments` port from it: the rows of the principal in the org asked about, by its key, which the table's own key serves, 100 at a time. A row that does not read as an assignment fails the read, and the decision point then denies.

The projection is new, so a store that opens with it for the first time makes the table and fills it from the facts it holds, as the ledger fills every keyed projection (see [Creating and filling a table](../ledger/README.md#creating-and-filling-a-table)); `src/assignments/role-assignment-facts.test.ts` fills it on SQLite and finds it row for row as one kept from the start, and `packages/server/src/roles/roles-over-http.test.ts` starts a server on a store whose roles were recorded before it kept them. The fill reads the store's facts in the order they were appended, each listing passing over the facts of other kinds, and folds each role fact into its principal's rows. Measured the same way: the first open of a SQLite file of 1,000,000 other facts and none of these took 72 ms against 5 ms for an open that fills nothing, and with 20,000 of these, as many as 5,000 people given four roles each over the years, 3.7 to 4.7 s, about 190 µs a fact; a read of one principal's roles from a table of 20,000 rows took a median of 0.05 ms.

### The operations

| Operation               | Method and route                           | Permission  | What it does                                                                                    |
| ----------------------- | ------------------------------------------ | ----------- | ----------------------------------------------------------------------------------------------- |
| `list_role_assignments` | `GET /role-assignments`                    | `org:read`  | Lists who holds which role and where, how, when and by whom it was given, a page at a time      |
| `assign_role`           | `PUT /role-assignments/{person}/{role}`    | `org:write` | Gives a person of the org a role in place of the one they held, and answers the roles they hold |
| `unassign_role`         | `DELETE /role-assignments/{person}/{role}` | `org:write` | Takes the role away, and answers the roles they hold                                            |

They are served over HTTP alone, as the cloud serves the changes of an org's members, and no endpoint offers them as a tool, so nothing an agent is told gives anyone a role (`src/operations`). A change is asked only by a person signed in to Studio, as the cloud's door asks it today, and `assign_role` gives a role only to a person of the org, as `OrgMembership` of `@on.auto/operations` answers, every person where the composition provides none. Today's check still decides who may call them, by the permission each declares; the decider decides who may change a role. The two changes declare that they manage permissions, so the decision point allows them to an Admin signed in to Studio alone (see [What only an Admin does](#what-only-an-admin-does)), as their handlers and the decider do.

### What the caller may do

`get_caller`, `GET /caller` (`src/operations/get-caller.ts`), answers `permissions`, those of `org:read`, `org:write`, `playbook:read` and `playbook:write` the caller may use in the org: the permissions their credential holds that their role in the org permits, by the table of built-in roles, which `src/roles/built-in-roles.test.ts` holds to the built-in policies permission by permission, so the answer and the decisions never disagree. It is Google Cloud's `testIamPermissions` for an org: a client asks once which of the permissions it would check the caller holds, and shows or turns off each control by the permission its operation declares, never by a role's name. The roles are those of the call, `CallerRoles` (`src/roles/caller-roles.ts`), which a host that decides calls by roles gives the dispatcher as the decision point reads them; where it gives none, as the server, whose dispatchers report, gives none, a person is answered their credential's permissions, as a key, a playbook acting as itself and the local developer always are. It is permitted by either read permission, served over HTTP alone, and changes nothing; what a person may not do is still refused when they ask it, whatever a client shows.

### The import

`rolesImported(org, members, { at, by })` (`src/assignments/imported-role-assignments.ts`) gives each member the role their declared role key names, through one table at the boundary, `roleOfIdentityServiceKey`, the anti-corruption layer of Eric Evans's "Domain-Driven Design" (2003): the identity service's `org:admin` is `admin` and its `org:member` is `editor`. A key the table does not name gives nothing and is answered among `undeclaredKeys`; no role is read from a name or an address. It writes through the decider's `provision`, with the source `import`, in appends of eight at most, the most a store takes in one, so it gives a role only to someone who holds none at the org: run twice, or after a person was given a role by hand, it changes nothing. It answers how many roles it gave, how many members it left unchanged and the keys it did not read. It is recorded as `import`, by whoever the caller names, the runtime in the cloud's import. It is `rolesProvisioned(org, source, assignments, { at, by })` with the source `import`: the same appends of eight through `provision`, for a host that gives roles from another source, as the cloud gives a person who joins by an invitation the role it carried (`invitation`) and one who joins by a domain theirs (`enrolment`), answering how many roles it gave. The table is in the facts' module, `src/assignments/role-assignment-facts.ts`, so a host reads it with nothing of the engine, beside the same boundary the other way, `identityServiceKeyOfRole`, the key the identity service holds an organization membership in for each built-in role, `org:admin` for `admin` and `org:member` for `editor` and `viewer`, by which a host tells whether the identity service still holds a person in the role an invitation gave there; a role added to the table without a key fails to compile, and `src/assignments/role-assignment-facts.test.ts` holds the two directions to each other.

### Self-hosted and the first admin

A self-hosted runtime with no sign-in, in local mode, holds no roles: the local developer and keys hold none and are bounded by their grant alone, as before (`src/decision-point/decision-point.test.ts`). With sign-in on, a signed-in person holds the roles the ledger records, and once the source is `role_assignments` a person who holds none is allowed nothing by the built-in policies, but for the calls a run they started makes, which keep the grant the run started with (`run-as-started`, see [What a Viewer may do](#what-a-viewer-may-do)). A self-hosted runtime keeps no list of members, so there is nothing to import. On a runtime whose members sign in with single sign-on, through the company's own identity provider, `OIDC_ISSUER`, the first person to sign in is its first admin, by `enrol` above, recorded as `bootstrap`, and each person after them is given `viewer`, recorded as `enrolment`, in the one organization of such a runtime (see [single sign-on](../server/README.md#single-sign-on-sso)). A command of the runtime that names an admin when every admin has left is a later step, recorded as `command`, which, being no person's act, needs no admin before it, as the import needs none. The roles recorded decide only who may sign in; they do not yet decide what a person may do: the runtime's source stays `every_person_an_editor` until the server takes `role_assignments` (`servedRoleSource`).

## What the model takes without a change to the question

Each of these leaves the question as it is and takes at most one more policy (`src/decision-point/model.test.ts`, `src/decision-point/decision-point.test.ts`):

- **A role at one playbook.** No new policy: a role held at a playbook applies to the playbook and to every definition in it, a role held at a definition to that definition alone, as the information point gives the principal each role held at the thing asked about or at a place it is in. An Editor of one playbook is the built-in role `editor` held at that playbook, and acts on that playbook and what is in it alone.
- **A level that runs and answers but cannot change.** One permission, `playbook:run`, declared beside `playbook:write` by the operations that run, and one policy for its role over `org:read`, `playbook:read` and `playbook:run`. An Editor keeps running through `playbook:write`.
- **A rule on what an operation declares.** "Nobody but an Admin does what cannot be undone" is one `forbid` on `context.operation.irreversible`.

## The pinned table

`pinnedTableBehaviour` (`src/testing/pinned-table-behaviour.ts`) lists, for each role and each kind of caller, what the decision point allows of each kind of operation the runtime declares, on the org, on a playbook, on another and on a definition in the first. A change to a policy shows as a change to a row. `src/decision-point/pinned-table.test.ts` runs it over the engine each loader loads, and a host that loads the engine its own way runs it over that engine, from the testing entry, `@on.auto/access-control/testing`, so every loader decides the same table.

## Cedar's licence

Cedar is under the Apache License 2.0. Its npm package carries neither its licence, nor its notice, nor the notices of the crates compiled into its WebAssembly, and the container image of the runtime redistributes it, so three files travel beside the code that loads it, as the typefaces of `@on.auto/api` carry theirs, in the image and in the npm package alike:

- `src/engine/Cedar-LICENSE.txt` and `src/engine/Cedar-NOTICE.txt` are `LICENSE` and `NOTICE` of `github.com/cedar-policy/cedar` at the tag `v4.14.0`, commit `5e54be8a16f3f346eb542e4feca587bfb962ebd1`, byte for byte.
- `src/engine/Cedar-THIRD-PARTY-NOTICES.txt`, named as Playwright and the Monaco editor name theirs, `ThirdPartyNotices.txt`, in the capitals of the two beside it, gives the licence and the copyright lines of every other crate compiled into `web/cedar_wasm_bg.wasm`, for which Cedar publishes no list (its `THIRD_PARTY_LICENSES.txt` is that of its command-line tool). These are the crates its `cedar-wasm/build-wasm.sh` builds for `wasm32-unknown-unknown`, resolved from its `Cargo.lock` at the tag: the normal dependencies of `cedar-wasm` with its default features, the build dependencies of Cedar's own crates, whose output is compiled in (`lalrpop`, which writes Cedar's parsers), and the Rust standard library of the compiler the module's producers section names, rustc 1.99.1. Each text comes from the crate's own published package, gathered by [cargo-about](https://github.com/EmbarkStudios/cargo-about); where a crate offers a choice of licences, MIT is taken, as its text carries the crate's copyright line.

`src/files/access-control-files.test.ts` pins the SHA-256 of all three. `cedarNoticeFiles` names them; the release of the npm package reads them (`packages/server/npm/release-reads.ts`), and the image's smoke test reads them inside the image (`.github/smoke/image.sh`).

### When Cedar's version changes

Take `LICENSE` and `NOTICE` from the new tag, and write the notices of the crates again with `scripts/cedar-notices/cedar-notices.ts`. It reads the version from the installed package and the compiler from its WebAssembly, refuses a clone of Cedar at any other commit than the tag's, runs cargo with Cedar's `Cargo.lock` unchanged and offline after one fetch, and builds nothing. It needs a Rust toolchain, so it runs by hand and never in CI, which lints it and runs its tests, none of which needs Rust. Keep the tools in a folder of their own, so that nothing reaches your profile or your `PATH`; read the installer before you run it:

```bash
work=$(mktemp -d)
export RUSTUP_HOME="$work/rustup" CARGO_HOME="$work/cargo" PATH="$work/cargo/bin:$PATH"
curl --proto '=https' --tlsv1.2 --fail --output "$work/rustup-init.sh" https://sh.rustup.rs
sh "$work/rustup-init.sh" -y --no-modify-path --profile minimal
cargo install cargo-about --locked --features cli
git clone --depth 1 --branch "v$(node -p "require('./packages/access-control/node_modules/@cedar-policy/cedar-wasm/package.json').version")" https://github.com/cedar-policy/cedar "$work/cedar"
node scripts/cedar-notices/cedar-notices.ts "$work/cedar"
```

The script names the compiler to add when its library sources are missing (`rustup toolchain install <version> --profile minimal --component rust-src`); add it and run the script again. `scripts/cedar-notices/about.toml` is the configuration of cargo-about: it accepts only the licences of the MIT, Apache-2.0, BSD, ISC, Unicode and Zlib families, so that a crate under any other licence stops the script, and it names, with its SHA-256, the licence file of each crate whose file cargo-about does not recognise. The script stops on a crate whose package carries a licence file that holds none of the texts taken, as happens when such a file changes or a new one goes unrecognised: name the file in a clarification and run it again. Pin the new SHA-256 of each file in `src/files/access-control-files.test.ts`, then remove `$work`.
