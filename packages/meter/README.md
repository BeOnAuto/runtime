# @on.auto/meter

The meter of the runtime: it counts the actions a ledger holds and admits each new run against what the runtime may run. An action is a run of a workflow or a function, counted once by its `run_id`, however often it is run again under that id, retried or resumed. Nothing else is metered: no model call, compute or training costs anything here. The runtime is source-available under the Elastic License 2.0, and its meter is part of it. The server composes `ledgerMeter()` into every runtime it starts, and no setting, environment variable or command removes it; `@on.auto/definitions` refuses every run of a runtime composed without a `RunMeter` as a `metering_fault`. Only a test composes another meter, `recordingMeter` or `admittingMeter` of `@on.auto/definitions/testing`. Auto's hosting composes `ledgerMeterAdmittedBy(authority)` instead, the same projection and the same faults with another authority over admission, below.

## The count is a projection of the ledger

An action is the first `run_started` of a run's stream, `playbook/<org>/<playbook>/runs/<id>`, in the ledger's global order, which `LedgerLog` of `@on.auto/ledger` reads. The count lives in the stream `meter` as `actions_counted` checkpoints, each with the number of actions, the point of the last event counted, that event's id, and a SHA-256 digest of the three. A checkpoint is a cache of the projection, never its source: the ledger is.

At each admission the meter loads the stream `meter` and checks its checkpoint:

- A stream with no checkpoint is counted from the first event of the ledger. One whose digest does not match its checkpoint was edited, and is counted again from the first event, with a warning logged.
- The event at the checkpoint's point must still be the event whose id it holds. When no event stands there, history was removed; when another does, it was rewritten. Either records `metering_faulted`.
- Otherwise the meter counts the run starts after the checkpoint, each the first of its stream when its version is that of the stream's first `run_started`, and reads only the events since the checkpoint.

At its start, and at every 1,000th admission, it counts the whole ledger again and compares: a count lower than the checkpoint's means events it counted are no longer there, and records `metering_faulted`; a higher one means the checkpoint understates the ledger, as when it was edited together with its digest, and the recount replaces it, with a warning logged. An event the log cannot read in that range records `metering_faulted` too, rather than be skipped.

## Faults

A fault is the event `metering_faulted` on the stream `meter`, with its reason, `history_removed`, `history_rewritten` or `unreadable`. It records what the meter found, never why: deleting events it counted, restoring some of a ledger's tables under a newer `meter` stream, a migration that renumbers rows and a disk error all record one, and none of its words says that anyone did anything wrong. A ledger restored whole, its events and its `meter` stream together, records none: it counts what it held when it was copied. While it stands, every run is refused as a `conflict` of the kind `metering_fault`, `This runtime stopped starting runs because <its detail>. We need to repair it; see <studio>/support (runtime id <installation>). Reading, editing and exporting still work.`, with the support page of Studio, at the origin `STUDIO_ORIGIN` names, as its `resolve_at`, and the installation as its `runtime_id` where the meter knows it, its words leaving out the parenthesis where it does not. It survives restarts; reading, editing, exporting and licensing go on, so a faulted runtime still activates and refreshes its license and receives its repair. A meter that another authority admits through, as in Auto's hosting, asks that authority for its repair instead, below. A ledger the meter cannot reach refuses the run as `unavailable` of the kind `meter_unavailable`, which the caller may ask again.

A repair is an answer Auto signs for one installation, `{ v: 1, kind: 'repair', installation, id, reason, issued_at }`, which an activation or a refresh may carry. The meter verifies it as it verifies an entitlement and records `metering_repaired`, which clears a standing fault, then counts its ledger again from the first event and records that count as its checkpoint, the baseline it goes on from. It records each repair once by its `id`, and ignores, with a warning logged, one signed by another key, for another installation or changed after it was signed.

## Unregistered runtimes

A runtime nobody registered admits 100 actions. An admission appends `action_admitted`, which holds a place for the run until its `run_started` is counted, or for ten minutes, with the stream's expected version: of two admissions that read the same version, one appends and the other reads again, so replicas of one ledger admit exactly 100 between them. The 101st is refused as a `conflict` of the kind `license_required`, `This runtime has used its 100 free runs. Get a free key at <resolve_at>, then activate it on the runtime and run this again.`, whose `resolve_at` is the page of Studio that registers the installation, `<studio>/licenses?installation=<id>`, and whose `runtime_id` is that id, which `installation_identified` records on the stream `meter` at its first admission, or as its status is first read. A fresh ledger is a new installation, and counts again from nothing, unless it is given a key first, when it takes the key's installation. The allowance is counted over the whole ledger, every run it holds included, those an account admitted too, and a runtime that holds a key never admits by it, whatever of it is left; started without a key again, it admits by the allowance until the ledger holds 100 runs.

Every refusal of the meter is a `Conflict` of `@on.auto/operations` whose optional `resolve_at` is the absolute URL where a person resolves it and whose `runtime_id` is the installation, which the API carries to the problem document; one for credits says its case in `because`, `none_left`, `free_daily_limit` or `free_month_used`. An org's account can be closed: a licensed runtime's account, as it admits a run or activates or renews a key, and another authority over admission, below, then answer `account_closed`, refused as that `conflict`, never as `meter_unavailable` or `license_invalid`, with the answer's `detail`, `resolve_at` and `because`, one of `AccountClosedBecauseSchema` of `@on.auto/operations`: `org_deleted`, whose org an owner can restore only for a limited time, until the date at its `resolve_at`, after which it is purged, or `org_purged`, whose runs never run again; a licensed runtime leaves out, as for credits, a `because` that is neither and a `resolve_at` that is no absolute URL.

## Licensed runtimes

A runtime is licensed by a key Studio gives the org that registers its installation, `alk.<org>.<installation>.<secret>`, opaque but for the installation it names. The server hands the meter the key of `AUTO_RUNTIME_LICENSE_KEY` or of `license.key` in its configuration file as it starts, as `key` of `LicenseGiven`, `{ key, source }` with the source `environment` or `configuration`, or the key it keeps in its secrets once one was activated through `activate_license` or `auto-runtime license activate`, which `held(key)` takes as `activated`, unless it is the key already in force; `RuntimeLicense` is the port it does so through: `activate(key)`, `held(key)`, `refreshed`, `reported` and `status`.

- **Activation** asks the account service, the port `AccountService`, to activate the key with the count the meter projected, `{ installation, actions, through, last }`, and takes the entitlement it answers only when Auto signed it: Ed25519 over the text of its base64url payload, `{ v: 1, kind: 'entitlement', installation, org, plan, issued_at, expires_at }`, by a key whose `kid` the runtime ships, for the installation `installation_identified` names, and not expired. A fresh ledger takes the installation of its key. The meter records `license_activated`, or `license_refreshed` for the key already active, with the entitlement as it was signed and the SHA-256 of the key, never the key. A key for another installation, or an entitlement not signed by Auto, for another installation or expired, is refused as a `conflict` of the kind `license_invalid`, `This runtime's license does not stand: <why>. Activate a key of this installation, which an owner of its org registers at <resolve_at>`, whose `resolve_at` is Studio's page of the installation, `<studio>/licenses` before the meter knows one, and whose `runtime_id` is the installation it knows. An activation the account refuses with the `because` `key_rotated` or `installation_revoked` is refused in the words of the case, with that `because`: `This runtime's key was replaced. Activate the new key an owner was shown when they rotated it, then run this again. If the key is lost, an owner can rotate it again at <resolve_at>.`, and `This runtime was removed from its org. To use it again, an owner can register it again at <resolve_at>, then activate the new key and run this again.`
- **Admission.** While an entitlement stands, the allowance is not used: each new action is admitted by the account, `POST /v1/installations/actions { run }`, which answers an admission Auto signed for exactly `installation:<installation>/<org>/<playbook>/<run_id in lower case>`. A run already started is admitted without asking. `credits_exhausted` from the account refuses as that `conflict` in its words, with the account's `because` where it is `none_left`, `free_daily_limit` or `free_month_used` and its `resolve_at` where it is an absolute URL; `license_invalid`, for a key rotated away or revoked, refuses as `license_invalid`, in the words of its `because` where the account gives `key_rotated` or `installation_revoked`, and records `license_invalidated` with that `because`, after which no run is asked for until another key is activated, each refused in the same words; an account that cannot be reached, or an admission not signed by Auto for that action, refuses as `meter_unavailable`. An entitlement past its expiry is refreshed as the next run is admitted, and refuses as `license_invalid` when it cannot be, `This runtime's license wasn't renewed by <date>. Check that it can reach billing.on.auto (it renews every day), then run this again.`
- **Refresh and reports.** The server asks `refreshed` at its start and every day, and `reported` every hour and before it stops. A report verifies the count against the whole ledger first, records it as the checkpoint, sends `{ actions, through, last }`, and records `usage_reported` once the account took it; one the account did not take fails, and is asked again. The account takes a report once by its `last`.

`signers` of `ledgerMeter(options, { key, signers })` are the public keys the meter trusts, by `kid`: `autoSigners`, Auto's production key `auto-2026-10` alone, which no setting, variable or command adds to or replaces. Only `testSigners` of the testing entry adds the test key, `test-2026-10`.

The production adapter of `AccountService` is `accountServiceLayer({ origin, fetch })`, which sends each call with the key as `Authorization: Bearer <key>` and bounds it at 10 seconds, and reads a refusal's `kind`, `detail`, `because` and `resolve_at`, `AccountRefusal`.

## Its status

`RuntimeLicense.status` (`src/licensing/license-status.ts`) answers what the runtime holds, `LicenseStatus`, which the server serves as `GET /v1/orgs/{org}/license`:

- `state`: `offline` while an allocation stands and its `refresh_by` is ahead, `invalid` once it is past; otherwise `unregistered` without a key, and with one `licensed` while the entitlement recorded for that key stands and is live, `invalid` while it was invalidated or is past its expiry, or before the key was activated.
- `runtime_id`: the installation the stream `meter` identified; before it identified one, the installation of the key in force, and without a key a new one it records as `installation_identified`, so a runtime nobody registered has an id to register before its first run.
- `free_runs`: `{ used, of }`, the actions the meter projects from its ledger, counted after its checkpoint without recording one, at most the allowance; the checkpoint's count while a fault stands or the ledger cannot be read.
- `org`, `plan`, `expires_at` and `renewed_at`: those of the entitlement recorded for the key in force, `renewed_at` its `issued_at`, and `null` without one.
- `key_source`: where the key in force came from, `environment`, `configuration` or `activated`, and `null` without one.
- `offline`: `{ credits, spent, usable_until }` of a standing allocation, and `null` without one.
- `invalid_because`: while it is `invalid`, the `detail` a run is refused in, and `null` otherwise.

A ledger that refuses to record an installation, or breaks, answers `meter_unavailable`.

## Offline installations

An installation that never reaches Auto spends an allocation instead of asking its account: credits an operator of Auto moves out of the org's account for it, signed by Auto, `{ v: 1, kind: 'allocation', installation, id, credits, issued_at, refresh_by }`. `RuntimeLicense.allocate(signed)` verifies it as it verifies an entitlement, Auto's key, this installation, which a fresh ledger takes from it, and a `refresh_by` still ahead, and records `allocation_received` with the count the meter projected then, the baseline it spends from; the same allocation given again records `allocation_refreshed` only for a later `refresh_by`, and one withdrawn is refused as `license_invalid`. While an allocation stands, it decides admission before a license or the allowance: past its `refresh_by` a new action is refused as `license_invalid`, `These offline credits stopped on <date>. An owner can request new ones at <resolve_at>.`, as an allocation given past it is, and otherwise admitted while the actions counted since the baseline, with the admissions held, are fewer than its credits, held against the stream's version as the allowance is, so replicas admit exactly its credits between them, and refused as `credits_exhausted` after, `This runtime has used all <credits> offline credits. An owner can request more at <resolve_at>.`, with the `because` `none_left`; both resolve at the installation's page of Studio, with the installation as their `runtime_id`. Nothing is asked of Auto for an action.

With a key in hand, the daily refresh asks `POST /v1/installations/allocations/refresh { allocation }`, records the allocation Auto signs again with a later `refresh_by`, and records `allocation_withdrawn` for a `409` `license_invalid`, a closed or frozen allocation, after which admission goes to the key or the allowance; any other failure is logged and the allocation stands. A report, `RuntimeLicense.allocationReport(of?)`, counts the ledger again from the first event, records `allocation_reported` with the next `sequence` and `spent`, all the actions counted since the baseline, and answers `{ report: { allocation, installation, sequence, spent, at }, signature }`, the hex HMAC-SHA256 keyed by the hex SHA-256 of the key's secret, its last part, over the report's fields joined by `.` (`src/allocations/report-signature.ts`). The hourly report makes one and sends it, `POST /v1/installations/allocations/report`, logging an answer other than `taken`; for an installation that never reaches Auto, the server's `report_allocation` and `auto-runtime license report` make one for an owner to upload in Studio. A ledger restored from an older copy reports the lower count under a sequence it used, which Auto freezes.

## Auto's hosting

`ledgerMeterAdmittedBy(authority, options?, signers?)`, or `meterOver({ ledger, log }, options, authority, signers?)`, composes the meter with another authority over admission, `{ installation, admit(run, action), repairFor(fault) }`. `admit` answers `{ admitted: true }` or `{ admitted: false, kind, detail, because?, resolve_at? }`, `kind` being `credits_exhausted`, `license_invalid` or `account_closed`, refused as that `conflict` with its `because` and its `resolve_at` where the authority gives them, and its `action` is `<org>/<playbook>/<run_id in lower case>`. A fault of such a meter names the authority's `installation` as its `runtime_id`. Such a meter has no allowance, no license and no reports; it counts, checkpoints, verifies and faults as every meter does. A promise the authority rejects refuses the run as `meter_unavailable`. While a fault stands, each run it is asked to admit first asks `repairFor(fault)` for a repair Auto signed, `null` when there is none, and takes one signed by a key of `signers` (Auto's own unless the host names others) for its `installation`, as an activation's repair is taken. The run that finds a fault is refused without asking; one the repair clears is admitted, and an authority that cannot be asked leaves the fault standing. `countedFromTheStart(log)` and `countedAfter(log, firstStartOf, counted)` are the projection itself, `{ actions, through, last }`, for a host to report each ledger's count with.
