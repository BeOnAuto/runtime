# @on.auto/meter

The meter of the runtime: it admits each new run against what the runtime may run, and counts what it admitted. A run is a run of a workflow or a function, counted once by its `run_id`, however often it is run again under that id, retried or resumed. Nothing else is metered: no model call or compute costs anything here. The runtime is source-available under the Elastic License 2.0, and its meter is part of it. The server composes `ledgerMeter()` into every runtime it starts, and no setting, environment variable or command removes it; `@on.auto/definitions` refuses every run of a runtime composed without a `RunMeter` as a `conflict`. Only a test composes another meter, `recordingMeter` or `admittingMeter` of `@on.auto/definitions/testing`. Auto's hosting composes `ledgerMeterAdmittedBy(authority)` instead, below. The [self-hosted licensing reference](../../docs/self-host/licensing.md) sets out the rules below for the people who run a runtime, and [License a self-hosted runtime](../../docs/self-host/licenses.md) the steps.

## The count is the meter's own record

The meter counts from its own record of the runs it admitted, the stream `meter` of the ledger, never by counting the history of the runs again, so deleting, redacting or restoring that history never stops a runtime. Each admission appends `action_admitted { run, until, basis }`, with the stream's expected version: of two admissions that read the same version, one appends and the other reads again, so replicas of one ledger admit exactly what they may between them. Its `basis` says what it was admitted on:

- `licensed`, on the license of the key in force, which Auto charges as the runtime reports;
- `first_runs`, one of the 100 a runtime that never held a license runs without a key;
- `free_rate`, at the free rate, 15 a UTC day and 75 a UTC calendar month unless a license carried other numbers;
- `offline`, on offline credits.

The stream's state keeps `actions`, all the runs admitted, `licensed`, those admitted on a license, `first_runs`, and the runs admitted at the free rate in the latest UTC day and month it saw. An admission holds its run for `holdMs`, ten minutes, so a run asked again before it starts counts nothing more; a run already started, whose stream holds its first `run_started`, is admitted without being counted again. A run asked again after its hold lapsed without starting is admitted, and counted, anew.

A refusal of the meter is a `Conflict` of `@on.auto/operations` whose optional `resolve_at` is the absolute URL where a person resolves it, whose `runtime_id` is the runtime's id and whose `because` says its case, which the API carries to the problem document. A refusal at the free rate also has `lifts_at`, 00:00 UTC on the next day for `free_daily_limit` or on the first of the next month for `free_month_used`, and, where the runtime holds a key, `limited_because`, the same reason `limited_because` of its status gives (`src/standing/free-rate-refusals.ts`). A ledger the meter cannot write to, or that breaks, refuses the run as `unavailable` of the kind `meter_unavailable`, which the caller may ask again.

## Without a key

A runtime nobody registered admits its first 100 runs, then at the free rate, `freeRate` of `MeterOptions`, `{ per_day: 15, per_month: 75 }`. It never calls Auto. The run past the rate is refused as a `conflict` of the kind `license_required`, with the limit in `because`, `free_daily_limit` or `free_month_used`, the page of Studio that registers the runtime in `resolve_at`, `<studio>/licenses?installation=<id>`, its id in `runtime_id`, when it lifts in `lifts_at`, and words that say which limit it reached, when it lifts and where to get a key: `This runtime has used its 100 free runs. Without a license key, it's limited to the free rate of 15 runs a UTC day and 75 a UTC month. It has used all of today's free runs, so it can start runs again at 00:00 UTC on 2026-10-29. To run more, get a free license key at <resolve_at> and activate it on this runtime.` The id is the one `installation_identified` records on the stream `meter` at its first admission, or as its status is first read: the runtime of the key it holds, or a new id without one. A fresh ledger, or a stream `meter` deleted, is a new runtime, and counts again from nothing.

## Licensed runtimes

A runtime is licensed by a key Studio gives the org that registers it, `alk.<org>.<runtime id>.<secret>`, opaque but for the runtime it names. The server hands the meter the key of `AUTO_RUNTIME_LICENSE_KEY` or of `license.key` in its configuration file as it starts, as `key` of `LicenseGiven`, `{ key, source }` with the source `environment` or `configuration`, or the key it keeps in its secrets once one was activated through `activate_license` or `auto-runtime license activate`, which `held(key)` takes as `activated`, unless it is the key already in force; `RuntimeLicense` is the port it does so through.

- **Activation** asks the account service, the port `AccountService`, `POST /v1/installations/activate { installation, actions, licensed }`, which answers `{ license }`, a license Auto signed, Ed25519 over the text of its base64url payload by a key whose `kid` the runtime ships:

  ```ts
  { v: 2, kind: 'license', installation, org, org_name?, plan, policy, issued_at, warn_at, limit_at,
    charged_through, admits_through, standing, credits: { available, owed, overage_cap },
    fallback: { per_day, per_month }, features? }
  ```

  `features`, the names of the features the org's agreement includes, is an addition to version 2 rather than a version of its own: a license that leaves it out, as one issued before it was signed does, lists none.

  The meter takes it only when Auto signed it for the runtime it is, records `license_activated` with the license, the licensed count it sent, `licensed_reported`, and the SHA-256 of the key, never the key, and takes `charged_through` as the least of its licensed count, as it does with every license it takes, so a ledger wiped or restored from an older copy and started again with the same key gains nothing. A fresh ledger takes the runtime of its key. A key for another runtime is refused without asking; a license not signed by Auto, for another runtime or of another version as a `conflict` of the kind `license_invalid`, `This runtime's license is invalid: <why>. Activate a license key for this runtime. The account holder or an organization admin can register it at <resolve_at>.`. An activation the account refuses as `license_invalid` records `license_invalidated` with its `because` and is refused in the words of the case: `key_rotated`, `This runtime's key was replaced. Activate the new key an owner was shown when they rotated it, then run this again. If the key is lost, an owner can rotate it again at <resolve_at>.`, and `installation_revoked`, `This runtime was removed from its org. To use it again, an owner can register it again at <resolve_at>, then activate the new key and run this again.` One the account refuses as `account_closed` records `license_invalidated` with `org_deleted` or `org_purged` and is refused as `account_closed` in the account's words, with its `because`, `org_deleted` or `org_purged`, and its `resolve_at` where it is an absolute URL. An account that cannot be reached refuses as `meter_unavailable`.

- **Admission.** No run asks Auto anything. While the license of the key in force stands, that is it was not invalidated and the time is before its `limit_at`, and the licensed count is below its `admits_through`, a run is admitted as `licensed`. Otherwise it is admitted at the free rate the last license carried, and a runtime that held a license once runs no new first runs. Past the rate, a run is refused in words that say why the runtime runs at the free rate, which limit it reached and when it lifts, and how to put it right (`src/standing/free-rate-cases.ts`): as `credits_exhausted` when its org has no credits, `This runtime's organization is out of credits, so the runtime is limited to <the rate>.`, or has reached its overage cap, `This runtime's organization has reached its overage cap of <cap> credits, so the runtime is limited to <the rate>.`, resolved at Billing of the org in Studio; as `license_invalid` when it has not reached Auto since its license's `limit_at`, its key was rotated or removed, its org was closed, or it holds a key it has not activated, resolved at its page of Studio; and as `license_required` without a key. Each has the limit in `because`.
- **Reports.** `reported` activates the key in force while the meter holds no license for it, and otherwise sends `POST /v1/installations/reports { actions, licensed }`, which answers `{ license }`, recorded as `usage_reported` and `license_renewed`. The account takes the licensed runs it has not charged, idempotently by the count, and charges nothing for a count lower than what it charged; the license it answers then lifts the runtime's count to its `charged_through`, so a ledger restored from an older copy reports a lower count once and never again. A report the account refuses as `license_invalid` or `account_closed` records `license_invalidated`, so the runtime runs at the free rate, and goes on reporting, so the account sees a rotated key still in use; one it cannot be asked, or whose answer Auto did not sign for this runtime, fails as `meter_unavailable` and keeps the last license. `reportDue` holds once the runtime has used half of what its license left it, `admits_through` less `licensed_reported`, and the server asks it every minute for an early report.

`signers` of `ledgerMeter(options, { key, signers })` are the public keys the meter trusts, by `kid`: `autoSigners`, Auto's production key `auto-2026-10` alone, which no setting, variable or command adds to or replaces. Only `testSigners` of the testing entry adds the test key, `test-2026-10`.

The production adapter of `AccountService` is `accountServiceLayer({ origin, fetch })`, which sends each call with the key as `Authorization: Bearer <key>` and bounds it at 10 seconds, and reads a refusal's `kind`, `detail`, `because` and `resolve_at`, `AccountRefusal`.

## Its status

`RuntimeLicense.status` (`src/standing/status-document.ts`) answers where the runtime stands, `LicenseStatus`, which the server serves as `GET /v1/orgs/{org}/license` and `activate_license` answers:

- `state`: `offline` while offline credits stand and their `refresh_by` is ahead, `invalid` once it is past; otherwise `unregistered` without a key, `licensed` while it runs on its license, `out_of_touch` from the license's `warn_at` while it still does, and `limited` while it holds a key but runs at the free rate, with `limited_because`, `credits`, `cap`, `out_of_touch`, `key_rotated`, `key_revoked`, `org_closed` or `not_activated`.
- `runtime_id`: the runtime the stream `meter` identified; before it identified one, the runtime of the key in force, and without a key a new one it records as `installation_identified`, so a runtime nobody registered has an id to register before its first run.
- `free_runs`: `{ used, of }` of the first runs while the runtime never held a license, `null` once it has; `fallback`: `{ per_day, per_month, used_today, used_this_month, lifts_at }` while it runs at the free rate.
- `org`, `org_name`, `plan`, `standing`, `credits`, `issued_at`, `warn_at`, `limit_at` and `last_report_at`, when it took the license: those of the license of the key in force, `null` without one; `licensed`, the runs admitted on a license, and `runs_left`, what the license still admits.
- `features`: the features in force, below, `[]` without them.
- `key_source`: where the key in force came from, `environment`, `configuration` or `activated`; `offline`, `{ credits, spent, usable_until }` of standing offline credits; `invalid_because`, the words a run is refused in once they stopped.
- `summary`: where the runtime stands in plain words and how to put it right (`src/standing/standing-words.ts`), which the server prints as it starts.

A ledger that refuses to record a runtime's id, or breaks, answers `meter_unavailable`.

## Features

`LicensedFeatures` is the service that answers whether a feature of the license is on for work of an org, `{ includes({ org, feature }), refusal({ org, feature, which }) }`, `LicensedFeaturesPorts` (`src/standing/licensed-features.ts`). Each answers `meter_unavailable` where the meter cannot read its ledger, as the status does, never a defect, so the work asking can be asked again.

`ledgerMeter` provides it beside `RunMeter` and `RuntimeLicense`, answering from the license the meter holds whatever the org, since a self-hosted license covers the whole runtime, and the server composes it. It reads the license as the status does, through one reading of the key in force, the stream `meter` and the clock (`readLicense` of `src/standing/license-status.ts`), and `includes` answers true only for a feature the license in force lists (`featuresInForceOf` of `src/standing/features-in-force.ts`): the license of the key in force, activated and not invalidated, before its `limit_at`, or past it while live offline credits stand, since a runtime that spends offline credits never reaches Auto to renew its license and keeps its features as it keeps its runs; a license whose org ran out of credits or reached its cap is still in force, so its features stand while runs are admitted at the free rate, and out of touch from its `warn_at` they stand until its `limit_at`. Offline credits whose `refresh_by` has passed stop every feature. Without a key, in local mode as anywhere, no feature is on. `refusal` is the `Conflict` of work that needs a feature that is not on, of the kind `feature_unlicensed`, in the voice of the other refusals of a license (`featureUnlicensed` of `src/licensing/licensing.ts`): `This runtime's license does not include <feature>, which <which>. The account holder or an organization admin can add it at <resolve_at>.`, `resolve_at` the runtime's page of Studio and `runtime_id` its id, where it has one. The status's `features` is the same list. A license's `features` are read as feature names, `FeatureSchema` of `src/licensing/signed-answers.ts`, a lower-case letter and up to 31 more lower-case letters, digits and hyphens: a name of another shape is left out, so a slip in naming one feature drops that feature alone and never the license. The license the meter records, `license_activated` and `license_renewed`, carries `features` from release 0.47.0; a fact of the shape before reads through its reader, `withNoFeatures` of `src/meter-stream/license-events.ts`, as a license that lists none, and `src/meter-stream/meter-events.test.ts` keeps the fixtures of both shapes, `0.46.0/` and `0.47.0/`.

`licensedFeaturesOf(featuresOf, { studio, runtime }?)` is a layer of it for a composition that takes its entitlement from elsewhere: `featuresOf(org)` answers the features of an org's work, so one runtime serving several orgs entitles each its own, and `refusal` names the licenses page of the Studio given, Auto's by default, and the runtime given, as `ledgerMeter`'s does. The server takes it in place of the meter's through `features` of `compositionRootWith`, as [the server's README](../server/README.md#the-license) says; nothing in this repository composes it but its tests.

## Offline runtimes

A runtime that never reaches Auto spends offline credits instead: credits an operator of Auto moves out of the org's account for it, signed by Auto, `{ v: 1, kind: 'allocation', installation, id, credits, issued_at, refresh_by }`, usable until the `refresh_by` Auto signed into them, 30 days after they were issued or refreshed, or 90 under an Enterprise order; the meter assumes no window of its own. `RuntimeLicense.allocate(signed)` verifies them as it verifies a license, Auto's key, this runtime, which a fresh ledger takes from them, and a `refresh_by` still ahead, and records `allocation_received` with the runs admitted then, the baseline it spends from; the same credits given again record `allocation_refreshed` only for a later `refresh_by`, and withdrawn ones are refused as `license_invalid`. While they stand, they decide admission before a license or the free runs: past their `refresh_by` a new run is refused as `license_invalid`, `This runtime's offline credits expired on <date>, so it can't start runs. The account holder or an organization admin can request new offline credits at <resolve_at>.`, and otherwise admitted as `offline` while fewer runs than their credits were admitted since the baseline, and refused as `credits_exhausted` after, `This runtime has used its <credits> offline credits, so it can't start more runs. The account holder or an organization admin can request more offline credits at <resolve_at>.`, with the `because` `none_left`; both resolve at the runtime's page of Studio, with its id as their `runtime_id`.

With a key in hand, `allocationRefreshed`, which the server asks every day, asks `POST /v1/installations/allocations/refresh { allocation }`, records the credits Auto signs again with a later `refresh_by`, and records `allocation_withdrawn` for a `409` `license_invalid`, closed or frozen credits, after which admission goes to the key or the free runs; any other failure is logged and the credits stand. A report, `RuntimeLicense.allocationReport(of?)`, records `allocation_reported` with the next `sequence` and `spent`, all the runs admitted since the baseline, and answers `{ report: { allocation, installation, sequence, spent, at }, signature }`, the hex HMAC-SHA256 keyed by the hex SHA-256 of the key's secret, its last part, over the report's fields joined by `.` (`src/allocations/report-signature.ts`). The hourly report makes one and sends it, `POST /v1/installations/allocations/report`, logging an answer other than `taken`; for a runtime that never reaches Auto, the server's `report_allocation` and `auto-runtime license report` make one for an owner to upload in Studio. A ledger restored from an older copy reports the lower count under a sequence it used, which Auto freezes.

## Auto's hosting

`ledgerMeterAdmittedBy(authority)`, or `meterOver({ ledger }, authority)`, composes the meter with another authority over admission, `{ admit(run, action) }`, which answers `{ admitted: true }` or `{ admitted: false, kind, detail, because?, resolve_at? }`, `kind` being `credits_exhausted`, `license_invalid` or `account_closed`, refused as that `conflict` with its `because` and its `resolve_at` where the authority gives them, its `action` being `<org>/<playbook>/<run_id in lower case>`. Such a meter records nothing of its own and has no free runs, license or reports: it admits a run already started without asking, and asks its authority for every other. A promise the authority rejects refuses the run as `meter_unavailable`. `countedFromTheStart(log)` and `countedAfter(log, firstStartOf, counted)` count the first `run_started` of each run's stream of a ledger, `{ actions, through, last }`, for a host to report each ledger's count with; the meter itself counts nothing that way.

## Testing

`src/meter-testing/meter-behaviour.ts` runs on SQLite and on PostgreSQL, in `src/admission/ledger-meter.test.ts`, each test on a database of its own: counting once per run id, held and started, across orgs and playbooks and on two replicas; history deleted, rewritten, unreadable or restored from an older copy, which never stops the runtime, and a stream `meter` wiped, which makes a new runtime; the first runs and the free rate by UTC day and month, their words and when they lift, and exactly the first runs and the day's rate of 200 admissions asked at once on two replicas; activation, its body and the license it records, the floor of `charged_through`, admission on the license up to `admits_through`, the free rate after it, from the license's numbers, after `limit_at`, after a key was rotated or removed or an org closed, and the license again once credits come; licenses not signed by Auto, for another runtime, tampered or of another version; reports, their body, the license they renew, the last license kept while Auto cannot be reached, early reports and a restored ledger's lower count, reported once and floored after; the status in each state; the features in force, lapsed, of a key replaced or not activated and beside offline credits, and the words that refuse work needing one; and offline credits admitted up to their credits and their 30 or 90 days, exact across two replicas, refreshed, withdrawn and reported in sequence. Its tests change the stored events as an operator could, through `tamperingOn` of `src/testing/ledgers.ts`; the meter itself runs no SQL. They run against `accountFake()` of the testing entry, an account service in memory that keeps each org's credits, `fund(org, books)`, charges as the contract says, signs with the test key, records the activations and reports it took and the counts that went backwards, signs the features an org was granted (`grant`), and fails as told (`revoke`, `close`, `goDown`, `answer`, `at`, `policy`). `accountServerOver(fake, port?)` serves that fake over HTTP on the loopback, on the port given or one free, as a stand-in for `billing.on.auto` beside a runtime composed with `testSigners`, as the server's tests do; `src/accounts/fetched-account-service.test.ts` runs the production adapter against it and holds the bodies it sends. `src/standing/licensed-features.test.ts` covers `licensedFeaturesOf` and the service the meter's layer provides. `src/admission/authority.test.ts` covers a meter another authority admits through, over `src/meter-testing/cloud-metered.ts`. `src/counting/run-starts.test.ts` checks over 2,000 random logs in memory that a host's count from any point equals a count from the first event. Run it with PostgreSQL as the ledger's README says, with `LEDGER_TEST_POSTGRESQL_URL` set.
