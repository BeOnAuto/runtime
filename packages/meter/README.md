# Durable meter

`@on.auto/meter` stores the self-hosted installation identity beside Runtime's ledger. It builds on the pure credit, tariff, license and offline-report contracts in `@on.auto/metering`.

`openInstallation` receives the existing `LedgerConnection` and encrypted `SecretStore`. The database holds one cluster identity and a secret reference; the Ed25519 private key remains in the configured secret keeper. Replicas using the same PostgreSQL database and secret custody share the identity. SQLite retains it across process restarts. A missing or mismatched private key refuses signing instead of silently issuing another identity.

Concurrent initialization chooses one durable identity. Losing candidates delete only their own unused secrets after the stored winner proves which key is in use. A lost acknowledgement is recovered from the database; an uncertain outcome retains its candidate key for recovery.

The returned signer produces installation challenge proofs and cumulative usage-report signatures with separate protocol types. Its public metadata contains no private key or secret reference. Opening an identity does not activate a license, grant credits or authorize a run.

`openLicenseClock` keeps a shared clock checkpoint and refresh receipts in the same database. It uses PostgreSQL's clock when present and combines elapsed monotonic time, a trusted server-to-wall offset and the persisted highest observed time. A wall-clock rollback, regressed monotonic clock or restart on a non-advancing wall clock requires online repair before new protected work. Ordinary small wall adjustments cannot rewind elapsed time. The clock does not change signed license or allocation deadlines.

Only the trusted license client may call `synchronize` after authenticating a fresh online time response, with the durable identity of that exchange. A new verified response may repair an incorrect host clock. The same receipt can never reset the anchor again, even after later refreshes; altered receipt content is refused. Refresh state and its receipt commit together, and replicas recover lost acknowledgements. The protected release configuration and dispatch wiring remain required; this API is not a customer-controlled clock setting. Software cannot establish elapsed downtime after a complete administrator-controlled machine and clock rollback without an external trust source, so restored allocation histories also require central divergence checks.

`licenseProtocol.freshTime` requests a separately signed time observation with a new random identity on every call. It verifies protected public trust, protocol type, authority, deployment ring, canonical bytes and the exact request. It includes the measured round trip conservatively and refuses regressed, invalid or excessively delayed observations. The controller passes that result immediately to `openLicenseClock.synchronize`; time repair neither changes a license deadline nor grants capacity. Clock persistence counts time spent waiting for storage, including a lost acknowledgement, while preserving the original immutable receipt for retries.

`licenseProtocol` connects the installation signer to the fixed HTTPS account authority. Activation sends the owner's credential and the installation's public key; refresh uses the installation identity. Challenge fingerprints bind the request, authority, account, installation, key and purpose. Completion verifies the signed license and its exact challenge-derived serial, generation, credential and issuance window. Its caller supplies a trusted-time callback sampled after the response arrives, so a retry can recover an already issued license after challenge expiry without extending the license deadline or using a stale pre-request timestamp. HTTP redirects, oversized requests/responses and stalled exchanges are refused; network errors expose no raw response or credential details.

The returned license is verified. Its capacity tokens remain separate signed artifacts: each must pass `allocationVerifier` with a current license, persisted epoch and trusted time before it can initialize usable capacity. Receiving an expired or previously closed token never creates another allocation. The protocol adapter does not itself persist a license, synchronize the clock, schedule refreshes or admit runs; durable exchange recovery and the protected composition must connect those operations.

`openLicenseState` records verified responses and their immutable exchange evidence beside a revisioned installation binding. Its controller must capture `head().revision` before starting an exchange and pass that same revision to `record`; it must never rebase a delayed response onto a newer revision. An authenticated refusal advances the revision, so a response already in flight cannot restore the refused license. A later fresh exchange can restore it. Stale refusals cannot disable a newer license.

Duplicate completions recover their original receipt without replacing a newer license or undoing a refusal, including after restart or a lost acknowledgement. A receipt acknowledges past storage and does not authorize work. `current` verifies the active signed license against trusted time and the persisted binding and generation. Its returned revision must guard the subsequent admission transaction so revocation between verification and admission cannot authorize new work. Allocation initialization and Runtime admission remain separate integration steps.

`openLicenseClient` composes installation signing, fresh signed time, durable license state and a shared pending exchange in SQLite or PostgreSQL. Activation transmits the owner-provided secret only to obtain its challenge; the local pending record contains no activation secret. It persists the challenge and the pre-request license revision before sending proof. Restart and lost-response recovery use the installation key and retain the original deadline. An expired historical completion is replaced only through a fresh challenge and proof, with a new captured revision. A delayed response cannot overwrite a later refusal or another accepted license.

`activate`, `refresh` and `resume` perform explicit exchanges. Confirmed refresh authorization failures fence the current license; temporary outages retain an otherwise valid lease. Invalid replacement credentials do not revoke the existing installation. The client never treats an acknowledgement as permission to run and never initializes capacity from an unchecked allocation token.

The maintenance `poll` uses the signed refresh deadline with up to fifteen minutes of installation-specific early jitter, coalesces concurrent local polls, and backs off failed attempts from thirty seconds to at most one hour. Its timer uses process monotonic time, and a detected regression forces another check. A Runtime maintenance driver must invoke it and honor the returned retry interval; opening the client alone starts no background timer. Protected release trust, admission/settlement and the customer-facing control routes remain integration work.

Signed server observations and measured response intervals are stored separately: a fresh faster response may correct a previous conservative estimate, while the authority's actual timestamp cannot regress. Old receipt replay cannot change either anchor or clear a later clock refusal.

Tests exercise encrypted secret storage and real SQLite and PostgreSQL transactions. Set `LEDGER_TEST_POSTGRESQL_URL` to a disposable local PostgreSQL server to run the latter tests. No account service or production credentials are used.

`openOfflineCapacity` initializes local platform capacity from a signed allocation only after verifying the current license, source references, installation binding, time and epoch. The capacity head, immutable signed evidence, original source quantities and zeroed usage counters commit together, guarded by the license and clock revisions. A confirmed refusal or suspicious clock change racing initialization prevents the grant. Foreign keys bind each counter's ceiling to its immutable source quantity, and database checks prevent committed plus reserved units from exceeding that ceiling.

Retries return the existing receipt without refilling usage, including after expiry or a later closed epoch. A new allocation requires the earlier one to be recorded as closed; expiry alone does not permit replacement. Token lookup indexes a bounded SHA-256 digest and checks the original bytes, so a full 64-source token does not exceed PostgreSQL's index-entry bound. Consistent snapshots preserve original source expiry and refuse missing or inconsistent projections. A receipt acknowledges stored capacity and does not admit work. Reservation, dispatch, reporting, acknowledged closure and quarantine recovery remain required before this store can enforce offline spending.
