# @on.auto/meter

The meter of the runtime: it counts the actions a ledger holds and admits each new run against what the runtime may run. An action is a run of a workflow or a function, counted once by its `run_id`, however often it is run again under that id, retried or resumed. Nothing else is metered: no model call, compute or training costs anything here. The runtime is source-available under the Elastic License 2.0, and its meter is part of it. The server composes `ledgerMeter()` into every runtime it starts, and no setting, environment variable or command removes it; `@on.auto/definitions` refuses every run of a runtime composed without a `RunMeter` as a `metering_fault`. Only a test composes another meter, `recordingMeter` or `admittingMeter` of `@on.auto/definitions/testing`. Auto's hosting composes `ledgerMeterAdmittedBy(authority)` instead, the same projection and the same faults with another authority over admission, below.

## The count is a projection of the ledger

An action is the first `run_started` of a run's stream, `playbook/<org>/<playbook>/runs/<id>`, in the ledger's global order, which `LedgerLog` of `@on.auto/ledger` reads. The count lives in the stream `meter` as `actions_counted` checkpoints, each with the number of actions, the point of the last event counted, that event's id, and a SHA-256 digest of the three. A checkpoint is a cache of the projection, never its source: the ledger is.

At each admission the meter loads the stream `meter` and checks its checkpoint:

- A stream with no checkpoint is counted from the first event of the ledger. One whose digest does not match its checkpoint was edited, and is counted again from the first event, with a warning logged.
- The event at the checkpoint's point must still be the event whose id it holds. When no event stands there, history was removed; when another does, it was rewritten. Either records `metering_faulted`.
- Otherwise the meter counts the run starts after the checkpoint, each the first of its stream when its version is that of the stream's first `run_started`, and reads only the events since the checkpoint.

At its start, and at every 1,000th admission, it counts the whole ledger again and compares: a count lower than the checkpoint's means events it counted were removed, and records `metering_faulted`; a higher one means the checkpoint was forged with its digest, and replaces it, with a warning logged. An event the log cannot read in that range records `metering_faulted` too, rather than be skipped.

## Faults

A fault is the event `metering_faulted` on the stream `meter`, with its reason, `history_removed`, `history_rewritten` or `unreadable`. While it stands, every run is refused as a `conflict` of the kind `metering_fault`, whose words link to the support page of Studio, at the origin `STUDIO_ORIGIN` names. It survives restarts; reading, editing, exporting and licensing go on, so a faulted runtime still activates and refreshes its license and receives its repair. A ledger the meter cannot reach refuses the run as `unavailable` of the kind `meter_unavailable`, which the caller may ask again.

A repair is an answer Auto signs for one installation, `{ v: 1, kind: 'repair', installation, id, reason, issued_at }`, which an activation or a refresh may carry. The meter verifies it as it verifies an entitlement and records `metering_repaired`, which clears a standing fault, then counts its ledger again from the first event and records that count as its checkpoint, the baseline it goes on from. It records each repair once by its `id`, and ignores, with a warning logged, one signed by another key, for another installation or changed after it was signed.

## Unregistered runtimes

A runtime nobody registered admits 100 actions. An admission appends `action_admitted`, which holds a place for the run until its `run_started` is counted, or for ten minutes, with the stream's expected version: of two admissions that read the same version, one appends and the other reads again, so replicas of one ledger admit exactly 100 between them. The 101st is refused as a `conflict` of the kind `license_required`, whose words link to the page of Studio that registers the installation, by the id `installation_identified` records on the stream `meter` at its first admission. A fresh ledger is a new installation, and counts again from nothing.

## Licensed runtimes

A runtime is licensed by a key Studio gives the org that registers its installation, `alk.<org>.<installation>.<secret>`, opaque but for the installation it names. The server hands the meter the key of `AUTO_RUNTIME_LICENSE_KEY` or of `license.key` in its configuration file as it starts, or the key it keeps in its secrets once one was activated through `activate_license` or `auto-runtime license activate`; `RuntimeLicense` is the port it does so through: `activate(key)`, `held(key)`, `refreshed` and `reported`.

- **Activation** asks the account service, the port `AccountService`, to activate the key with the count the meter projected, `{ installation, actions, through, last }`, and takes the entitlement it answers only when Auto signed it: Ed25519 over the text of its base64url payload, `{ v: 1, kind: 'entitlement', installation, org, plan, issued_at, expires_at }`, by a key whose `kid` the runtime ships, for the installation `installation_identified` names, and not expired. A fresh ledger takes the installation of its key. The meter records `license_activated`, or `license_refreshed` for the key already active, with the entitlement as it was signed and the SHA-256 of the key, never the key. A key for another installation, or an entitlement not signed by Auto, for another installation or expired, is refused as a `conflict` of the kind `license_invalid`, whose words link Studio's page of the installation.
- **Admission.** While an entitlement stands, the allowance is not used: each new action is admitted by the account, `POST /v1/installations/actions { run }`, which answers an admission Auto signed for exactly `installation:<installation>/<org>/<playbook>/<run_id in lower case>`. A run already started is admitted without asking. `credits_exhausted` from the account refuses as that `conflict` in its words; `license_invalid`, for a key rotated away or revoked, refuses as `license_invalid` and records `license_invalidated`, after which no run is asked for until another key is activated; an account that cannot be reached, or an admission not signed by Auto for that action, refuses as `meter_unavailable`. An entitlement past its expiry is refreshed as the next run is admitted, and refuses as `license_invalid` when it cannot be.
- **Refresh and reports.** The server asks `refreshed` at its start and every day, and `reported` every hour and before it stops. A report verifies the count against the whole ledger first, records it as the checkpoint, sends `{ actions, through, last }`, and records `usage_reported` once the account took it; one the account did not take fails, and is asked again. The account takes a report once by its `last`.

`signers` of `ledgerMeter(options, { key, signers })` are the public keys the meter trusts, by `kid`: `autoSigners`, Auto's production key `auto-2026-10` alone, which no setting, variable or command adds to or replaces. Only `testSigners` of the testing entry adds the test key, `test-2026-10`.

The production adapter of `AccountService` is `accountServiceLayer({ origin, fetch })`, which sends each call with the key as `Authorization: Bearer <key>` and bounds it at 10 seconds.

## Auto's hosting

`ledgerMeterAdmittedBy(authority, options?)`, or `meterOver({ ledger, log }, options, authority)`, composes the meter with another authority over admission, `{ admit(run, action) }`, which answers `{ admitted: true }` or `{ admitted: false, kind, detail }`, `kind` being `credits_exhausted` or `license_invalid`, and whose `action` is `<org>/<playbook>/<run_id in lower case>`. Such a meter has no allowance, no license and no reports; it counts, checkpoints, verifies and faults as every meter does. A promise the authority rejects refuses the run as `meter_unavailable`. `countedFromTheStart(log)` and `countedAfter(log, firstStartOf, counted)` are the projection itself, `{ actions, through, last }`, for a host to report each ledger's count with.

## Testing

`src/meter-testing/meter-behaviour.ts` runs on SQLite and on PostgreSQL, in `src/admission/ledger-meter.test.ts`, each test on a database of its own: counting once per run id across orgs and playbooks, incremental counts equal to counts from the first event over random ledgers, what was started before the ledger was metered, the checkpoint's fields and digest, a catch-up over 100,000 events that reads only the six appended since, verification at the start and at the interval, rebuilds, the faults and their restarts, a ledger that cannot be read, the allowance with its link, holds that lapse, exactly 100 of 200 admissions asked at once on two replicas, and admissions, starts and catch-ups racing on two replicas. Its tests change the stored events as an operator could, through `tamperingOn` of `src/testing/ledgers.ts`; the meter itself runs no SQL. `src/counting/run-starts.test.ts` checks over 2,000 random logs in memory that a count from any checkpoint equals a count from the first event. The same suite covers licenses against `accountFake()` of the testing entry, an account service in memory that signs with the test key: activation from a key given at the start and from one handed to it, entitlements not signed by Auto, for another installation, tampered or expired, revocation, credits exhausted, an admission charged once per run id, refreshes, reports verified before each, retried and taken once by their `last`, and repairs. `src/accounts/fetched-account-service.test.ts` runs the production adapter over HTTP against `accountServerOver(fake)`, which serves that fake on the loopback, as the server's tests do. Run it with PostgreSQL as the ledger's README says, with `LEDGER_TEST_POSTGRESQL_URL` set.
