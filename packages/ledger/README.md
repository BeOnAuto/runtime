# @on.auto/ledger

The ledger keeps track of every single action and interaction that the playbook does. It is the log of the inputs and outputs to all the capabilities.

This package is the event store behind the `Ledger` port of `@on.auto/operations`. It stores events with [Emmett](https://event-driven-io.github.io/emmett/) on SQLite or on PostgreSQL.

## What it stores

- **Streams of events.** The application layer names each stream, for example `org/acme/playbooks` or `playbook/acme/sales/definitions/reasoning`. Names are opaque: the ledger never changes their case, trims them or normalises their Unicode, so two names that differ in any character are two streams.
- **One version per stream.** A stream's version is the number of events in it, and 0 when nobody has written it.
- **Keyed projections.** One row per key in a table of each projection the ledger is opened with, kept inside the append of each fact of the stream kinds the projection names: the outcomes of runs in `run_outcomes_4`, which a playbook's analytics read, and any other projection the composition registers, such as the open requests of interaction functions (see [Keyed projections](#keyed-projections)).
- **Facts as Emmett stores them.** Each event a decider decides, `{ type, data }`, becomes a message `{ type, data, metadata }`. `type` is the fact's name. `data` is the fact's data alone, encoded with `Schema.toCodecJson(decider.eventSchema)`, which must give a JSON object, and holds no copy of the type. Loading decodes `{ type, data }` with the same codec, so a fact comes back exactly as it was decided, dates and big integers included. A stored fact that no longer decodes is a defect.
- **The context of every message in its metadata.** The `Context` the decider answers for a decision, `context(command, state)`, is written once, `metadataOf`, into the metadata of every message of the append beside the store's own fields: `at`, `by`, and where the context holds them `runId`, `definitionType`, `definitionName`, `definitionVersion`, `calledBy`, `callDepth`, `depth` and `trigger`. It is checked first (`checkedContext`), so a context with a character PostgreSQL's `jsonb` refuses is a defect on every store, and nothing is appended. Each fact's schema names the context the fact carries beside its data, `factOf(type, data, context)` of `@on.auto/operations`, such as a run's `RunContext` or a definition's `DefinitionContext`, so each event of a decision is recorded with that decision's context checked against its fact's (`recordingOf`), and a context a fact does not carry is a defect and nothing is appended. The stream read decodes the context with the fact, so a stored record whose context is not its fact's fails to load as one whose data no longer decodes does. The recorded reads, the projections and their fills hand the context back whole, through `contextOf`. Measured on the installed store, every field round-trips unchanged through a stream read and an inline projection; on PostgreSQL the metadata is plain `jsonb`, unwrapped.
- **Secrets, sealed.** Beside its streams and their content, the ledger's database keeps secrets, each sealed under a key the ledger is given, in one table no fact names (see [Kept secrets](#kept-secrets)).
- **An id, a cause and a correlation for every message.** The store's append writes, in each message's metadata, `messageId`, which Emmett also keeps as the message's `message_id` and honours when the caller gives it, `causationId` and `correlationId`. The id is `messageIdOf(stream, position)` of `@on.auto/operations`, a version 5 UUID of the stream and the position the message takes, which the append knows before it writes since every append passes the version it expects; so no two messages share an id, and anyone who knows a stream and a position names its message. The cause and the correlation are the `Lineage` the command was executed with, `null` when it was given none. Messages written before the ledger set its own ids keep the random ids Emmett gave them, and no cause or correlation.

## How a command runs

`execute(stream, decider, command, lineage?)` loads the stream, folds its facts with `decider.evolve`, each handed as it was recorded, `{ type, data, context }`, its context the one its fact carries, and asks `decider.decide`; it asks `decider.context(command, state)` of a decision that appends anything, and the facts it appends carry the lineage and that context, and are folded with it into the state it answers.

- A rejection is returned as it is, and nothing is appended.
- A decision of no events appends nothing and answers with the current state and version.
- Otherwise the events are appended with the version that was read as the expected version. If another writer appended first, the append meets a version conflict: the stream is loaded and the command decided again, up to three more times, and then it fails with `Conflict`. Like the in-memory ledger of `@on.auto/operations`, its detail names no stream.
- A decision of more events than the store takes in one append is a defect: eight on SQLite, 64 on PostgreSQL.
- Any other failure of the database is a defect, never a `Conflict` or a rejection.

## Building on the ledger's loop

Code that keeps its own streams, such as `@on.auto/workflow-engine`, uses the same pieces as the ledger itself rather than a copy of them:

- `sqliteEventStore(optionsOf, { runOutcomes?, projections? })` opens the event store on any of Emmett's SQLite drivers, without the layer, and `postgresqlEventStore({ pools, reportLostConnection, runOutcomes?, projections? })` from `@on.auto/ledger/postgresql` opens it on PostgreSQL; given a run outcome mapping, the store keeps the outcomes of runs, and given projections, their tables. Both are one adapter over an Emmett event store, `emmettEventStore`, given how each keeps an event's data and how many events it takes in one append, beside the store's own read of what a playbook recorded, `EventStore.readRecorded` (see [Reading what a playbook recorded](#reading-what-a-playbook-recorded)).
- `EventStore.read(stream, after)` gives the messages after version `after`, each `{ type, data, context, lineage }`, its lineage `{ id, causationId, correlationId }`, and the version of the whole stream, so a reader that holds a snapshot at version `after` reads only the tail. Emmett answers a read past the end of a stream with version 0; `read` answers with `after` instead. `eventCodecOf(schema).decode(message)` turns one into the event as it was recorded, its data and its context decoded with its fact's schema. `load(stream, fold)` takes a `Fold`, the initial state, `evolve` and the fact schema, which a `Decider` extends with `decide` and `context`, so a reader that only folds a stream declares nothing it never writes.
- `EventStore.mostEventsInOneAppend` is the most events the store takes in one append.
- `eventAppenderOf(store, eventSchema)` encodes and appends decided events at a place, `{ expectedVersion, context, lineage? }`, at most `store.mostEventsInOneAppend` in one append, checks the context first and against each event's fact, and fails with `VersionConflict` when another writer appended first.
- `retriedOnVersionConflict(attempt)` runs a load-decide-append attempt again after a version conflict, up to three more times, and then fails with `Conflict`.
- `EventStore.definitionStreams(type)` names the streams of one type of definition in every playbook, such as each playbook's `definitions/recall`, with the version of each, read from Emmett's table of streams through an index of their own (see [The indexes](#the-indexes)), so a reader that follows the definitions of one type, as the workflow host follows recall functions, finds a playbook whose first definition of the type was saved after it started.
- `appendSignal()` is an in-process signal of appends to playbooks: `raise(stream)` tells every listener the playbook key of a stream, its name through the third `/`, and nothing for a stream of no playbook, and `listen(listener)` answers the function that stops listening. `signalledOn(store, signal)` raises it after each append the store recorded, never after one that failed, and the layers take it as `appends`, `ledgerLayer({ fileName, appends })` and `postgresqlLedgerLayer({ pools, appends })`, so code in the same process that follows a playbook, as the workflow host's projector does, wakes when something was recorded rather than at its next sweep. Appends made by another process raise nothing here.
- `decisionLoop(load, append, decider)` is the load-decide-append loop itself, the one `Ledger.execute` runs: it loads, decides, asks the decider for the decision's context, appends the decided events at `{ expectedVersion, context }`, the loaded version expected, giving the append what the load gave too, retries with `retriedOnVersionConflict`, and answers with what the load gave, the events as they were recorded, each with the context its fact carries, and the state folded with them. The ledger's load folds the whole stream; a caller with snapshots passes a load that folds a snapshot and its tail.

## Reading what a playbook recorded

`Ledger.readRecorded(playbook, selection, page)`, the read the `Ledger` port of `@on.auto/operations` describes, is answered by the store: one SQL read of its own on each store, over Emmett's messages table, with six indexes the ledger adds to it. Each record carries its id, its place, its context, cause and correlation, and the store's trace: the id from `message_id`, its stream, its position in it and its global position from the table's own columns, `stream_id`, `stream_position` and `global_position`, since the SQLite store's metadata holds the position within the append and the PostgreSQL store's holds neither, and the rest from `message_metadata`, which the head of each record a page answers reads whole, its correlation through the expression the fifth index holds. The metadata never holds tenant data: only the identifiers of the context. `Ledger.readRecordedEvent(playbook, id)` reads one message by its id within the playbook, through the seventh index. The selections, the page and its bounds are the port's; this section says how each store answers them.

### The playbook key

Every stream of a playbook is named `playbook/<org>/<playbook>/…`. The store takes the key of a message's stream, its name through the third `/`, with an expression, and compares it to the playbook's key, `playbook/<org>/<playbook>/`, for equality: with `=` on SQLite, and on PostgreSQL with `= ANY` of a list that holds the key alone, for the reason [How PostgreSQL reaches the indexes](#how-postgresql-reaches-the-indexes) gives. It never matches with `LIKE` or any pattern: org and playbook ids may hold uppercase letters and `_`, SQLite's `LIKE` ignores case, and `_` matches any character in both stores. A stream name with fewer than three `/` has no key and belongs to no playbook.

| Store      | The key of a stream                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| SQLite     | `substr(stream_id, 1, …)` to the third `/`, found with nested `instr`, since SQLite has no regular expressions |
| PostgreSQL | `substring(stream_id FROM '^(?:[^/]*/){3}')`, null for a name with fewer than three `/`                        |

The same expression taken to the fourth `/` gives the key of a stream's kind within its playbook, such as `playbook/acme/sales/runs/`. A run is a stream whose kind key ends in `runs/`, so no other stream may be nested under `runs/`.

### The indexes

| Index                                         | SQLite                                                           | PostgreSQL                                                                | What reads it                                                  |
| --------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `ledger_messages_by_playbook`                 | playbook key, position                                           | playbook key, transaction id, position                                    | a playbook's messages, in order, from any cursor               |
| `ledger_messages_by_playbook_and_time`        | playbook key, recorded time                                      | playbook key, recorded time, transaction id, position                     | where a page `since` a time starts                             |
| `ledger_messages_by_stream`                   | stream, position                                                 | stream, transaction id, position                                          | one run's two streams, each in order from any cursor           |
| `ledger_first_messages_by_kind`               | kind key, position, first messages alone (`stream_position = 1`) | kind key, position in the stream, transaction id, position, every message | the runs of a playbook, by the position of their first message |
| `ledger_messages_by_playbook_and_correlation` | playbook key, correlation, position                              | playbook key, correlation, transaction id, position                       | what one run and the runs it caused recorded, in order         |
| `ledger_definition_streams`                   | the type of a definition stream, definition streams alone        | the type of a definition stream, definition streams alone                 | the definition streams of one type in every playbook           |
| `ledger_messages_by_id`                       | message id                                                       | message id                                                                | one event by its id, `get_event`                               |

The read of one run reads each of its two streams through the third index from the cursor on, and merges them, so a page of a run of 100,001 messages costs the same at its start and in its middle, in either order. Without it, SQLite read such a run through Emmett's unique index on the stream and its version and sorted what it read: on a file holding a run of 100,001 messages and 100,000 messages of other streams of its playbook, a page took 24 ms at the start of the run newest first, 14 ms from its middle newest first and 4.7 ms from its middle oldest first, against 0.23 to 0.42 ms with the index.

The read by correlation walks the fifth index, whose second column is the message's correlation taken from its metadata by an expression, `json_extract(message_metadata, '$.correlationId')` on SQLite and `(message_metadata ->> 'correlationId')` on PostgreSQL, as the other indexes take their keys from the stream name, so a page of a run's whole tree costs the same however much else the playbook recorded. On the ledger of [Measurement](#measurement), where every message of a run carries the run as its correlation, a page of the tree of a run of 21 messages took 0.28 to 0.29 ms on SQLite and 1.99 to 2.04 ms on PostgreSQL at the median, a page from the middle of the tree of a run of 100,001 messages 0.26 ms and 1.44 to 2.19 ms, and, behind a million newer messages of other playbooks, 0.26 to 0.31 ms and 1.52 to 1.81 ms, as a page of one run took.

The sixth index is on Emmett's table of streams, `emt_streams`, not on its messages: its key is the type a definition stream holds, the part of a stream's name after `playbook/<org>/<playbook>/definitions/`, such as `recall`, taken with `CASE WHEN … = 'definitions/' THEN substr(…) END` over the playbook key on SQLite and `substring(stream_id FROM '^(?:[^/]*/){3}definitions/([^/]+)$')` on PostgreSQL, and it is partial, holding the streams whose key is not null, so it holds one entry for each playbook and type of definition however many runs and other streams the ledger keeps. `definitionStreams(type)` matches the same expression with `=`, which both planners take as implying the index's `IS NOT NULL`, so the read walks the index; a test reads the plan on each store. Without it the read scans every stream of the ledger.

The list of runs walks the fourth index through the first message of each run, so a page of runs costs the same however many messages the run logs of a playbook hold between two runs. A selection that names `notBeginningWith` leaves out, in the same walk, the streams whose first message is of those types, before the page counts its runs, so the page is full and has no more only once the runs are read; `@on.auto/definitions` leaves out a stream that begins with a caller's cancel, which holds no run, and the ledger itself names no event. Without it, on a ledger of 598,362 messages, PostgreSQL estimated 845 first messages of runs where there were 60,000, and answered a page of runs filtered by status with a sequential scan of the whole table, in 122 to 126 ms; with it, the same pages took 1.4 to 3.5 ms. On SQLite the index holds the first messages alone. On PostgreSQL it holds every message, with its position in its stream as the second column, which the read asks to be 1, because the planner takes no statistics from the expression of an index with a `WHERE` clause: with the index partial, as on SQLite, on the ledger of [Measurement](#measurement), it planned a deep page of failed runs oldest first as a bitmap scan of the playbook's runs and a sort of 49,999 of them, in 73 ms; whole, and with the table analysed, the same page took 4.4 ms.

A selection that names `definitionType` or `name` keeps the runs whose first message's context holds that `definitionType` or `definitionName`, as a run's start, `run_started`, records them: the walk reads the two fields out of the metadata of the first message of each run it examines and the page counts only the runs that hold them, so a page of the runs of one definition is full while the walk finds them, and has no more once the runs are read. On SQLite the walk compares `json_extract(message_metadata, '$.definitionType')` and `json_extract(message_metadata, '$.definitionName')` with `IS`, so a first message without them is no match; on PostgreSQL it compares `message_metadata ->> 'definitionType'` and `message_metadata ->> 'definitionName'` with `=`, a read of plain `jsonb`. Neither reads the first message's data, whose input may be up to 256 KiB, so the fields cost the reading of each first message's metadata alone, a few hundred bytes, whatever the run took; a test reads the plan of the walk on each store, through the fourth index.

The ledger creates the indexes when it opens, but first looks them up by name in the catalog, `pg_class` on PostgreSQL and `sqlite_master` on SQLite, which takes no lock on the messages table, and creates only those missing, with `CREATE INDEX IF NOT EXISTS`. A start that finds them all issues no `CREATE`. That matters on PostgreSQL, where `CREATE INDEX`, even on an index that exists, takes a lock on the messages table that waits for the appends in flight and holds every new append behind it: with an append left open for 2 s, `CREATE INDEX IF NOT EXISTS` on an index that existed took 2,013 ms, and an append begun 200 ms after it waited 1,821 ms; a start that looked first took 15 to 17 ms with the append still open, and a test checks that such a start is not held up. On PostgreSQL the lookup and the creation run in Emmett's `onAfterSchemaCreated` hook, inside the migration's transaction and its migration lock, so servers that start together build each index once; a start that created any index then analyses both tables, `ANALYZE emt_messages, emt_streams`, so the planner has statistics on the new key expressions at once rather than when autovacuum next analyses the table. On SQLite, which serialises writers, they run just after Emmett's migration, on the same connections, and the hooks a caller passes to `sqliteEventStore` are kept as given.

Building the five indexes on an existing ledger of 1,197,287 messages took 6.1 s on PostgreSQL 18.6, with the analysis, and 4.2 s on SQLite, about 5.1 s and 3.5 s per million messages at that size, measured as the time the ledger took to open (see [Measurement](#measurement)). The index on the message id, built alone on a ledger of 1,000,000 messages, took the open 0.22 s on SQLite and 0.98 s on PostgreSQL, with the analysis, and a read of one event by its id then took 0.054 ms on SQLite and 0.49 ms on PostgreSQL at the median of 1,000 (`measure/message-index.ts`, see [Measurement of the read of one event](#measurement-of-the-read-of-one-event)). The read first takes the messages with the id, a `MATERIALIZED` common table expression the planner must answer through that index, and only then matches their playbook, so no statistics can send it down the playbook's index instead. On PostgreSQL the build blocks appends for as long, so the first start after an upgrade holds appends that long. The database's user must own the messages table to create them, as the user that created it does.

### How PostgreSQL reaches the indexes

Each index leads with its key, the playbook's, the stream's or the kind's, then the order of the read, so a page walks the index from its cursor. PostgreSQL's planner may walk another index instead: Emmett's own on `(transaction_id, global_position)`, the order of the whole table, filtering out every message of another playbook. It does so when its statistics say the key is common, as for a large playbook, and the cost then grows with the messages other playbooks have written since: a page of the playbook newest first, behind a million newer messages of other playbooks, took 570 ms that way. Each statement therefore matches its key with `= ANY` of a list that holds the key alone, and orders by the key before the transaction id and the position. A list does not make the key a constant to the planner, so ordering by the key is no longer redundant, and the only index that yields that order without a sort is the ledger's own. The same page then took 1.5 ms, and every page of [Measurement](#measurement) behind those million messages costs what it costs before them. SQLite's planner, without statistics, takes the index on the key for an equality, and the SQLite read matches with `=`.

### Order, and the horizon on PostgreSQL

On SQLite appends are serialised, so global positions follow commits, and the read orders by position.

On PostgreSQL a message takes its global position when it is inserted and becomes visible when its transaction commits, so a later position can be visible before an earlier one. The read therefore orders by transaction id, then global position, as Emmett's own batch read does: `readMessagesBatchSQL` in `@event-driven-io/emmett-postgresql` 0.43.0-beta.50, `dist/index.js` lines 1274 to 1289, orders at line 1287, `ORDER BY transaction_id, global_position`, and reads behind a horizon at line 1285, `AND transaction_id < pg_snapshot_xmin(pg_current_snapshot())`.

The ledger keeps that horizon where it is needed, and narrows it:

- **Oldest first**, a reader follows the tail and goes on from its last record, so a message committed late below that record would be skipped for good. These reads stay behind the horizon: a message whose transaction is still open, and every message after it in the order, waits until that transaction ends, then comes in the next page, once.
- **Newest first**, a read pages downward from a position, and a message committed late appears in its next fresh read, so these reads keep no horizon and show every committed message.
- **The horizon is the ledger's own database's.** Transaction ids belong to the whole PostgreSQL server, and `pg_snapshot_xmin` is the oldest transaction open anywhere on it, so an idle write in another database would hide the newest messages of every ledger on the server for as long as it stays open. The ledger instead takes the oldest id among the transactions the read's own snapshot sees in progress, `pg_snapshot_xip(pg_current_snapshot())`, leaving out the ids that `pg_stat_activity.backend_xid` showed writing in another database when the read looked them up, in a statement of its own just before it (`writesOpenElsewhere` in `src/postgresql-reads/recorded-parts.ts`). The lookup comes first because a statement takes its snapshot before it runs: looked up inside the read, a write of another database that ended between the snapshot and the lookup could not be told from one of the ledger's own database, and held back every message written after it began, a message committed before the read among them, as [the measurement below](#measurement-of-the-horizon) counts. A write of another database open at the lookup is left out whenever it ends, one that ended before the lookup is not in the snapshot, and one that began after it holds an id above every message committed before the read began. An id that is in doubt stays in: one of a write of another database that began after the lookup, which can hold back only messages written after the read began, or an id `pg_stat_activity` does not show, such as a prepared transaction's, which no backend holds, since the lookup takes only the rows with a `backend_xid`. A transaction holds an id once it first writes, so a transaction that has only read holds nothing back, which a probe confirmed.

The read never waits for the horizon: it answers at once with what lies below it. A reader that reaches the newest end oldest first, while a write of the ledger's database is open, cannot tell a quiet playbook from one held back.

### Measurement of the horizon

`measure-horizon.ts` counts how often a read holds back a write of its own database that committed just before it, while 8 connections of another database of the server keep writing, each in a transaction of up to 50 ms. It makes two databases of its own, which it drops afterwards, and takes 3,000 reads each way, each right after a commit, with the lookup of the other database's writes inside the read's own statement, after its snapshot, and with the ledger's own lookup, in a statement before the read; without `LEDGER_MEASURE_POSTGRESQL_URL` it measures nothing:

```bash
LEDGER_MEASURE_POSTGRESQL_URL=postgresql://postgres:ledger-test@127.0.0.1:19632/postgres pnpm --filter @on.auto/ledger measure:horizon
```

| ---------------------------------------------------------- | --------------------------------------------------- | ---------------------------- |
| inside the read's own statement                            | 3 and 9 of 3,000                                    | 5 and 4 of 3,000             |
| in a statement of its own, before the read                 | 0 and 0 of 3,000                                    | 0 and 0 of 3,000             |

One more run, while other work held the machine at a load average of about 47, held back 26 of 3,000 with the lookup inside the read's statement and none with it first.

### The cursor

A cursor is the base64url encoding, without padding, of a JSON array: the playbook key and the position of a record on SQLite, such as `["playbook/acme/sales/","1234"]`; the playbook key, the transaction id and the position on PostgreSQL. Each record carries its own cursor, and `nextCursor` is the cursor of the last record the page examined. A cursor may hold one more part, a whole number, which points inside the record: a read from it begins with that record, in either order, rather than after it, and leaves to the operation that presents the record which of its events to leave out. A cursor that is not such an array, holds a different number of parts than the store keeps, or holds a part that is not a decimal of at most 2^63 − 1 fails the read with `InvalidCursor` of kind `malformed`; one that is well formed but names another playbook fails with kind `of_another_playbook`. The playbook-bound read turns either into `invalid_input` at `/cursor`, with a detail that says which. A cursor is not encrypted: whoever decodes it learns a position of the ledger.

### The version of a record, and a read of heads

Each record carries `version`, its position within its stream, read from Emmett's `stream_position`. A page given `dataOf` loads the data of the records of those types alone and measures the size of those alone: a statement measures a record it examines only when the page wants the record and loads its type, the bound of 4 MiB counts the sizes of the records it loads, and the statement that loads data asks only for their positions, so a page of heads, `dataOf: []`, measures nothing, examines up to its limit and loads nothing (`src/heads/heads-behaviour.ts`, on both stores and the in-memory ledger).

On PostgreSQL a size is `octet_length(message_data ->> 'json')`, which takes the data out of its TOAST table and decompresses it, so measuring a record costs about what loading it costs. `measure-heads.ts` measures the statement that examines a page with `EXPLAIN (ANALYZE, BUFFERS)`, over 20 records of 1,400,000 bytes of text that does not compress in one playbook, 20 reads after 3 to warm:

```bash
LEDGER_MEASURE_POSTGRESQL_URL=postgresql://postgres:ledger-test@127.0.0.1:19632/postgres pnpm --filter @on.auto/ledger measure:heads
```

| The page                                                                | Measuring every record it examines | Measuring the records it loads |
| ----------------------------------------------------------------------- | ---------------------------------- | ------------------------------ |
| a page of heads, `dataOf: []`                                           | 3,598 buffers, 29.6 ms             | 1 buffer, 0.40 ms              |
| the workflow host's follower, which loads the data of definitions alone | 3,598 buffers, 30.4 ms             | 1 buffer, 0.20 ms              |
| every record with its data                                              | 3,598 buffers, 28.1 ms             | 3,598 buffers, 17.8 ms         |

The times are medians, measured on 2026-10-06 on the machine and with the PostgreSQL of [Measurement](#measurement), while the machine ran other work at a load average of about 105, so they are higher than an idle machine gives and vary from one run to the next; the buffers, the pages of 8 KiB the statement touched, do not depend on the load. On SQLite `octet_length(message_data)` reads the length alone, as [The bounds of a page](#the-bounds-of-a-page) says, and the statement measures the same records.

### The bounds of a page

A page examines records in order and ends at the first of its bounds, with `nextCursor`:

- `limit`, 1 to 100 records answered: without a filter, the page examines that many; with a filter of types, it examines up to 1,000 records, or 1,000 runs for a list of runs filtered by the type of their latest message or by the definition type or the name of their first, and answers those that match, possibly none.
- 4 MiB of data loaded, counted from the length of the stored JSON of each record the page loads, before any is loaded: `octet_length(message_data)` on SQLite, which reads the length alone, and `octet_length(message_data ->> 'json')` on PostgreSQL, the text inside the wrapper, so no SQL parses an event's own JSON to measure it; only a list of runs filtered by `definitionType` or `name` parses the first message of each run it examines (see [The indexes](#the-indexes)). The first record a page wants is always loaded, so a record larger than the bound ends a page of its own.

A page takes at most three statements: when `since` is given, one that finds where the page starts; one that examines the page without loading data; and one that loads the data of the records it delivers, by position. Every statement binds at most 15 parameters, far below the 100 the ledger binds at most in one statement on SQLite, but the statement of a list of runs given both `since` and `dataOf`, which no operation asks of it: 18 on SQLite and 17 on PostgreSQL with `definitionType`, `name`, a status, `notBeginningWith` and a cursor, against 15 and 14 as `list_runs` reads it, counted from the parameters each statement binds; SQLite takes each list, of stored types or positions, as one JSON parameter through `json_each`. None needs a transaction.

### Times and data

`recordedAt` is the time the store recorded a message: SQLite's `created`, `CURRENT_TIMESTAMP` in UTC to the second, given as `2026-10-05T09:00:00.000Z`; PostgreSQL's `created`, `now()`, the start of the append's transaction, to the millisecond. `since` finds the first message the playbook recorded at or after it, by recorded time then position, through the second index; the page starts there oldest first and ends there newest first. SQLite rounds `since` down to the second, so a page from a time may begin with messages of the same second recorded just before it.

The data of a record is decoded as the store's `read` decodes it: on SQLite the stored JSON text, parsed as Emmett's serializer parses it, and on PostgreSQL the `{"json": …}` wrapper, read back by the same `dataAsJsonText`. An event that holds U+0000 is read like any other.

## Recorded content

The ledger keeps content whole beside its messages rather than in them, since every decision on a run's stream, every fill of a projection and every follower reads the messages back: the content of a tool call, its arguments and the tool's answer, and any bytes a capability keeps under their digest. It also keeps content staged under a run, which goes when the run's staging ends. Five tables hold it, with an index on the upload of each table of heads, `recorded_content_heads_by_upload` and `staged_content_by_upload`, created when the ledger opens, each looked up first in the catalog as the playbook's indexes are, so a start that finds them creates nothing:

| Table                     | Key                                    | What it holds                                                                                                      |
| ------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `recorded_content_chunks` | playbook key, upload id, chunk         | the bytes one put read, in chunks of 1 MiB, the last one shorter, as `BLOB` on SQLite and `bytea` on PostgreSQL    |
| `recorded_content_heads`  | playbook key, digest                   | the upload whose chunks hold the content, its size in bytes, the number of chunks and the media type, written last |
| `staged_content_chunks`   | playbook key, run id, upload id, chunk | the chunks of a content staged under a run                                                                         |
| `staged_content`          | playbook key, run id, digest           | the head of a content staged under a run                                                                           |
| `unstaged_runs`           | playbook key, run id                   | the runs whose staging ended                                                                                       |

`content.put(playbook, { stream, mediaType, expected? })` gives the put an upload id of its own, a UUIDv7, and reads the stream through `takenInChunks` of `@on.auto/operations` into chunks of 1 MiB, digesting and measuring the bytes as they pass, writing each chunk under its upload once the next has filled, in a statement of its own and so on PostgreSQL in a transaction of its own, since every open write holds back the reads oldest first (see [Order, and the horizon on PostgreSQL](#order-and-the-horizon-on-postgresql)). At the end of the stream it knows the digest and the size, and `requireExpected` refuses a digest or a size other than the one `expected` names as `not_its_digest` or `not_its_size`, as a stream that fails is refused as `stream_failed`, each a `ContentRefused`. A content of one chunk is still in hand then, so when the playbook holds its digest the put writes nothing and answers the head it holds; a put whose expected digest the playbook holds reads its stream through the digest and writes nothing; otherwise the put writes its last chunk, then the head, naming its upload, with `ON CONFLICT DO NOTHING`, and reads the head back. The first head written for a digest stands: a put that finds the head of another upload, whether it raced another put of the digest or found the digest kept, deletes its own chunks and answers the head it found, its size and its first media type, so two puts of one digest never write over each other's chunks, a wrong put racing a right one cannot spoil it, and a second media type never replaces the first. A put that fails part way, refused, by its stream or by its store, deletes its own chunks too, and never chunks a head names. Chunks no head names can still remain: those of a process that stopped between a chunk and its head or before its delete, and on PostgreSQL a chunk whose insert was still on its way, on a connection of its own, when its put was interrupted and deleted its chunks. So the ledger sweeps them, on a schedule of its own that starts when it opens and stops when it closes: once at the start, without holding the open back, and then every hour, it deletes every chunk no head names whose upload began more than an hour before, by the time a UUIDv7 carries in its first 48 bits. The sweep is maintenance: a sweep that fails, the first one among them, is logged as an error and never stops the ledger, and the next runs an hour later. A close waits for a sweep under way to finish before it closes the store, so it never leaves the sweep's connection open or runs the sweep on a closed store. A ledger opened with a content store of its own, `content: { content, sweepContent }` among the options of `ledgerLayer` and `postgresqlLedgerLayer`, keeps its content there and sweeps that store on the same schedule, and its content tables stay empty; the server opens it so when `CONTENT_STORE_URL` names an object store, whose adapter, [`@on.auto/object-storage`](../object-storage/README.md), sweeps the uploads its puts left behind. A put that streams a request body ends within the 300 s Node gives a request, `server.requestTimeout` of the server's `createServer`, well within the hour. `content.get(playbook, sha256)` reads the head and answers `{ stream, bytes, mediaType }`, or nothing for a digest without a head. The stream reads one chunk of the head's upload each time it is pulled, so neither a put nor a get holds the whole content in memory, and digests what it reads through `verifiedStream` of `@on.auto/operations`, the check the object store's reads go through too: a chunk that is missing, or bytes that are not those the digest names, fail the stream as a defect, as the ledger fails on a fact that no longer decodes, and it hands over the last chunk only once the size and the digest are checked, so no reader takes every byte of a content that is not its digest's. The content is keyed by the playbook and the SHA-256 of its bytes, so the key is the content's own address; a text is kept as its UTF-8, so its digest is the SHA-256 of the text the fact names. The digest is Node's own, `createHash('sha256')`, through `sha256Digest` of `@on.auto/operations`. A chunk travels to the store as the hex of its bytes, through `unhex` on SQLite and `decode(…, 'hex')` on PostgreSQL, since the SQL builder binds a byte array as JSON. A fact carries a digest only when its content was kept, so a read never joins content to a fact that kept none. Nothing kept is deleted.

`content.stage(playbook, run, content)`, `content.staged(playbook, run, sha256)` and `content.unstage(playbook, run)` keep, read and remove content staged under a run, by its id, with the rules of a put and a get for the uploads, the heads and the digest, so a server reads what another staged on the same database. `unstage` records the run in `unstaged_runs` and then, in one transaction, removes the run's heads and then its chunks. The record stays, so `unstaged_runs` grows by one small row, the playbook key and the run id, for each run whose staging ended, as many as the runs that stage content; no capability of this repository stages content yet. A stage under a run already unstaged is refused with `StagingEnded` and leaves its stream unread, and a stage looks again once its head is written; if the run was unstaged meanwhile it deletes its own head and chunks and is refused the same way. Since the unstage records the run before it deletes and the stage writes its head before it looks, either the stage sees the record or the unstage's deletes see the head, so a stage that races an unstage leaves nothing behind. A read of a staged content whose run is unstaged while it is read fails at the first chunk it finds gone, as a defect, in words that say so: `The content staged under <digest> has no chunk <n>, as when its run is unstaged while it is read`.

A database whose content tables have another shape than these, a chunk of text or a head without a media type, is refused when the ledger opens, with words that name the columns found and the columns kept and say to delete the local database, since nothing stored before launch is carried over.

## Kept secrets

The ledger keeps secrets apart from its facts and from its content: what the runtime must hold to act for someone, such as a key a person pasted or a token minted for them, which no fact of a stream may carry, since every reader of a stream reads its facts, and no table may hold in the clear, since whoever reads the database or a backup of it would read them. The store is not part of the `Ledger` port: the server opens it at start and gives it to the connections of `@on.auto/connections`, which keep in it the credential a person gives. `sqliteSecretStore({ fileName, keys })` of `@on.auto/ledger/sqlite3` and `postgresqlSecretStore({ pools, keys })` of `@on.auto/ledger/postgresql` each answer an `Effect` of a `SecretStore`, opened on connections of its own from the settings the ledger is opened from, as the workflow host opens its own, once the ledger is open, as the server opens it. On SQLite the store migrates the ledger's schema on its own pool first, which finds everything made when the ledger opened and creates nothing, since a pool of its own on `:memory:` is a database of its own; on PostgreSQL it opens a pool of two connections, from `pools` or any `(bounds) => SecretConnections`, on the database the ledger migrated, and logs a connection it loses as the ledger logs one of its own. One table holds the secrets, created with `CREATE TABLE IF NOT EXISTS` by the same schema step that creates the content tables, on SQLite and on PostgreSQL, through the same dialect, and looked up first in the catalog as they are, so a start that finds it creates nothing:

| Column          | What it holds                                                                        |
| --------------- | ------------------------------------------------------------------------------------ |
| `id`            | the secret's id, a UUIDv7, the table's primary key                                   |
| `kid`           | the id of the key the secret is sealed under                                         |
| `sealed`        | the secret, one JWE in its compact form                                              |
| `version`       | 1 when the secret is kept, one more at each replacement                              |
| `kept_at`       | when the value it holds was kept, an ISO 8601 time in UTC, as text                   |
| `claimed_until` | until when the row is claimed by whoever renews it, the same kind of time, or `NULL` |
| `ends_with`     | the ending of the secret the runtime may show, or `NULL`                             |

A database whose table of secrets has another shape than this is refused when the ledger opens, in the words that refuse an older shape of the content tables, `requireTheShapeKept` of `src/content/content-tables.ts`, naming the columns found and the columns kept and saying to delete the local database.

`keep(value, endsWith?)` takes the value as a `Redacted` string, and the ending of it the runtime may show where it gives one, and answers the id it keeps it under, a UUIDv7 as `randomUUIDv7` of `@on.auto/operations` makes the ledger's other ids. An empty value, or one of more than 8 KiB of UTF-8, is refused before it is sealed, as a `SecretRefused` that is `empty` or `too_large` and says nothing of the value. `read(id)` answers a `StoredSecret`: the value as a `Redacted`, which prints and serializes as `<redacted>`, so a value cannot reach a log by accident, the row's `version`, and `claimedUntil`, the end of a claim while it is open; a caller that wants the value alone takes `value`, so a row is read once whatever the caller wants of it. It answers nothing for an id the store does not keep, never an error. `endingsOf(ids)` answers the ending kept for each of the ids that has one, unsealing nothing, in one query, and nothing for no ids. `forget(id)` deletes the row, the ending with it, and forgetting an id twice is forgetting it once. `kid` is the id of the current key, and `close()` closes the store's connections. A failure of the database is a defect, as it is for the ledger.

A value that is renewed while it is used, such as the tokens a connection holds, lives in one row for its life, replaced under a lease. `replace(id, version, value)` seals the new value under the current key and writes it in one conditional update, only while the row's version is the one the caller read: the version goes up by one, `kept_at` is the time of the replacement, the claim ends and the ending is cleared, since it was the ending of the value before. `claim(id, version, lastingMs)` marks the row claimed until `lastingMs` from now, in one conditional update, only while the row's version is the one the caller read and no claim is open, a claim being open while its end is later than now, so a process that finds the row claimed waits and reads again rather than renew what another process renews. Each answers whether it happened, `{ replaced: true, version }` or `{ replaced: false }`, `{ claimed: true, until }` or `{ claimed: false }`, for a row whose version moved and for a row that is gone alike, never with an error; a value `replace` refuses is a `SecretRefused`, as for `keep`. Every time the store writes or compares, `kept_at`, the claim's end and the moment a claim is judged open, is read from Effect's `Clock`, the clock the times of the facts are read from, so a test drives it with `TestClock`.

Each value is sealed by `jose`, the library that verifies the identity service's tokens in `@on.auto/identity`, as one JWE in its compact form whose protected header is `{ alg: 'A256KW', enc: 'A256GCM', kid }`: `jose` makes a fresh content key for each value, encrypts the value under it with AES-GCM and wraps it under the store's key with AES key wrap, so this is envelope encryption and nothing of it is the ledger's own, no cipher, no nonce and no derivation of a key. A read unseals with those two algorithms alone and refuses a compressed JWE.

A key is 32 bytes, given as a `Redacted` byte array, and its `kid` is the first 16 hex characters of its SHA-256, so no one names a key and one key always has one `kid`; a key of another length stops the store opening, naming the length and never the bytes. The store takes `keys: { current, previous? }`. It seals with the current key and unseals with whichever of the two the `kid` of a JWE names; a JWE of any other `kid` is refused as a `SecretKeyUnknown` that names that `kid` and never the value. `rotated()` reads the rows of the previous key's `kid` 100 at a time, unseals each with the previous key, seals it again under the current one and writes it back only while its row still names the previous key and holds the version it read, so two servers rotating at once re-seal each row once and a replacement made between the read and the write is never written over, and answers how many rows it re-sealed; the rows of the current key and of any other key are left as they are, and so are the time each row was kept, its version and its claim. Without a previous key, or with the current key given as the previous one, it re-seals nothing. Once a rotation has run, nothing is sealed under the previous key any more, so it can be dropped.

A secret is only as recoverable as its key. The ledger keeps no copy of a key and no way around one: a lost key loses every secret sealed under it, and a row whose key is gone can only be forgotten. The server's settings say where its key comes from, `SECRETS_KEY` or a file beside a SQLite ledger, in [Configure the runtime](../../docs/self-host/configuration.md#server-storage-and-logs).

## Keyed projections

The ledger keeps a table for each projection it is opened with, one row per key, inside the appends of the streams of the kinds the projection names: a `KeyedProjection` of `@on.auto/operations`, which names its table, its version, the stream kinds it folds, the stored types that change a row, its columns, its indexes, the key of the row a fact changes, the columns its reader advances and the mapping from a row and an event to the next row, and which the package that owns what a row means supplies at composition: `ledgerLayer({ fileName, projections })` and `postgresqlLedgerLayer({ pools, projections })`. The ledger knows the streams of a playbook, named `<playbook key><kind>/<id>` (see [The playbook key](#the-playbook-key)), and nothing of their events. A projection of runs names the kind `runs` and keys its row by the stream's id, the run's; a projection may name other kinds and key its row by what a fact carries, through `keyOf(event, stream)`, as `topicRows` of `@on.auto/operations/testing` does over two kinds for the ledger's tests. The outcomes of runs are one such projection, which the ledger declares itself over the run outcome mapping it is given as `runOutcomes`, and which keeps its own grouped read, `Ledger.readRunOutcomes(playbook, window, selection)`, beside the generic ones.

### Inline projections

An inline projection of Emmett 0.43.0-beta.50 handles the messages of an append inside the append's own transaction: on SQLite in the `onBeforeCommit` of the append, on PostgreSQL inside the transaction of `appendToStream`. It is handed the messages of the types it names, in their stored form, with their stream's name and position and the message id the ledger gave each, and a projection that throws fails the append, which keeps nothing, the rows the projection changed included; a failed append runs no projection. On PostgreSQL Emmett skips a projection that has a name when it cannot take its advisory lock or its status is not active, so the ledger's projections have none and always run. On both stores a unique-constraint error inside a projection would surface as a version conflict, retried three times and then `conflict` `concurrent_change`; a table has no constraint but its key and is written with an upsert, so it never raises one.

`src/projections/inline-projection.ts` is the facility: an `InlineProjection` names its stored types and handles the messages of an append, each `{ stream, type, data, context, id, position }`, with the executor of the append's transaction. `src/projections` builds every table from its declaration: the statements that create a table and its indexes, read a row and write rows with an upsert keyed by the playbook and the row's key (`projection-statements.ts`), the inline registration (`projection-keeping.ts`), the fill (`projection-fill.ts`) and the reads (`projection-reads.ts`), over a dialect of each store, `sqliteProjectionDialect` and `postgresqlProjectionDialect`, which says how it names column types, reads a whole number back as a number, lists the streams of a projection's kinds and their messages, or the messages of those kinds in the order they were appended, and decodes their data. For each message of its types on a stream of its kinds, a projection decodes the message's data as the store's reads decode it, the JSON object as written on SQLite and the `{"json": …}` wrapper read back on PostgreSQL, and its context from its metadata, finds the key of the row it changes, the stream's id or what `keyOf` answers, and nothing when `keyOf` answers `undefined`, reads that row if there is one, gives the row and the message, `{ id, position, type, data, context }`, to the mapping, and writes the row it answers, or nothing when it answers `undefined`. A fill reads the metadata column beside the data, so a rebuilt row folds the same context. That is one read and one write in the append for each such message, for each projection, and nothing for the messages of any other stream kind or type. A mapping must never throw.

A projection may declare the columns its reader advances, `advanced`, a list of `{ column, setBy }`: `Ledger.advanceRow(projection, playbook, key, { set, when })` writes the columns of `set` of one row, and no other, in one `UPDATE` of its own, outside any append, only while the columns of `when` still hold the values given, the compare-and-set a reader makes against a marker its fold owns, and does nothing for a row that is not there or that no longer holds them; a column the projection does not declare fails the call. The fold's upsert writes every column when it makes the row, and otherwise each advanced column only when the fact's type is one of that column's `setBy`, leaving the rest as they stand, `SET` naming only the columns it writes, so a fold that read the row before an advance committed cannot undo an advance of a column it does not set: on PostgreSQL the fold's `SELECT` does not wait for an advance in flight, and its upsert, which does, updates the row as the advance left it. A test on PostgreSQL holds an advance open while a fold reads the row, and fails with an upsert that writes every column. The fill never applies an advance, since no fact stands for one, so a rebuilt row holds what the folds set.

A store opened without a projection neither creates its table nor writes it, and its reads answer no rows, no groups and no due time rather than reading a table that may not be there, so every writer of a run stream must write through a store that carries the projections. Today that is the server's ledger, through which the workflow host settles runs and the interaction capability records its deliveries too; the workflow host's own stores write only the logs of runs.

### The columns and the reads

A table holds `playbook_key` and `row_key`, its key, and the projection's columns: text; a whole number, `INTEGER` on SQLite and `bigint` on PostgreSQL, read back as a number; or a boolean, `INTEGER` 0 or 1 on SQLite and `boolean` on PostgreSQL; each nullable. An index named `<table>_<index>` is on the playbook key and the index's columns, `row_key` among them when it names it, each kept `NULLS FIRST` on PostgreSQL, the order SQLite keeps nulls in, so that a read of a playbook's rows walks it forwards oldest first and backwards newest first on both stores; or on its columns alone for one across playbooks, in each store's own order, which the reads of due rows, the soonest first, walk; and partial, `WHERE <column> IS NOT NULL`, when it says so. `readProjectedRows` reads a page of a playbook by equal columns, the key `row_key` among them, which the key serves, ordered by its columns and the row's key, `NULLS FIRST` oldest first and `NULLS LAST` newest first on both stores, and goes on after the row values it is given with a comparison of row values, which finds nothing for a value that is not set, so a page that goes on orders by columns that are always set; `countProjectedRows` counts the rows of a playbook by equal columns; `readDueRows` reads the rows of every playbook whose column is set and has come, the soonest first, which a partial index across playbooks serves; and `nextDueOf` answers the smallest value of the column after the time it is given, which the same index serves. Every value is bound, and every column a read names must be the projection's or `row_key`, or the read fails.

### The table of the outcomes of runs

| Column                                                          | What it holds                                                                          |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `playbook_key`, `row_key`                                       | The playbook key of the run's stream and its id, the table's only key                  |
| `started_day`, `started_at`, `last_started_at`                  | The day and time of the run's first start, and the time of its latest                  |
| `definition_type`, `name`, `status`                             | The run's definition and how it stands: `started`, `succeeded`, `failed` or `rejected` |
| `duration_ms`, `input_tokens`, `output_tokens`, `cached_tokens` | Its duration and the tokens it used, each null when unknown                            |

The table is `run_outcomes_4`, with the index `run_outcomes_4_by_playbook_and_day` on `(playbook_key, started_day)`. Days and times are text, `YYYY-MM-DD` and ISO 8601, so that the two stores compare them alike; the numbers are `INTEGER` on SQLite and `bigint` on PostgreSQL. The columns are the ledger's; their meaning is the mapping's, which `@on.auto/definitions` documents.

### Creating and filling a table

When the ledger opens with a projection, it looks its table up by name in the catalog, as it does its indexes, and does nothing more when it finds it. When it does not, it creates the table and its indexes, fills it by replaying every run stream of the store, drops the tables of earlier versions, such as `run_outcomes_3` and below, and analyses the new one, all in one transaction, so that a fill that is interrupted, by a mapping that throws or a process that stops, leaves nothing behind and is done again at the next open. On SQLite this runs after Emmett's migration and the indexes, on the same connections; on PostgreSQL in `onAfterSchemaCreated`, inside the migration's transaction and under its advisory lock, so that servers that start together fill the table once. Emmett's migrator waits 10 s for that lock, `defaultDatabaseLockOptions` in `@event-driven-io/dumbo` 0.13.0-beta.56, `dist/pg.js` line 673, less than the fill of a large ledger takes, and the typed options of Emmett's store and of its `schema.migrate()` offer no longer wait. So the ledger takes the same lock first, in `onBeforeSchemaCreated`, inside the migration's transaction (`migrationLockTakenWithin` in `src/postgresql/postgresql-run-outcomes.ts`): it tries `pg_try_advisory_xact_lock` every 100 ms for up to 60 s, past the longest fill measured below, 42.7 s, and once it has the lock holds it through the migration and the fill until the transaction commits; the migrator, in the same transaction, takes it again at once. A server that starts while another fills a large ledger waits for it, and stops at start, saying why, only when the lock is still held after 60 s.

A projection keyed by its stream is filled a stream at a time. No index lists the streams of a kind across playbooks, so the fill scans the store's streams, `emt_streams`, for the names of the streams of the projection's kinds in the order of their names, with the size of their messages of the mapping's types, and takes of them as many as hold at most 16 MiB of those messages, at least one, so that a ledger of records of 1 MiB does not hold hundreds of megabytes at once. It lists as many streams as the batch before showed fit: one at first, then as many as 16 MiB holds at the bytes per stream of the streams the batch before took, at most twice as many as it listed before and at most 100. On PostgreSQL the size is the length of each record's text, which reads the record, so listing 100 streams of records of 1 MiB would read 100 MiB to load 16 MiB; listed this way, the fill sizes about as many bytes as it loads. For each batch it reads, in one statement, those messages in their order, decodes each as the store's reads do, folds the messages of each stream through the mapping, and writes the rows in upserts of as many rows as 100 parameters hold on SQLite, the most the ledger binds in one statement there, 8 for the outcomes of runs, and of 500 on PostgreSQL. A change to what a table keeps is a new version, `run_outcomes_5`, which the next server fills this way and whose fill drops `run_outcomes_4`. Servers of different versions do not share a database at once.

A projection keyed by its mapping is filled in the order the facts were appended, since the facts of many streams change one row and the last of them must win: the fill reads the messages of its kinds and types 256 at a time, in the order of their position, `global_position` on SQLite and `(transaction_id, global_position)` on PostgreSQL, after the last message of the batch before, folds each into its row, read from the table being filled when the batch has not changed it yet, and writes the rows the batch changed. 256 messages of at most 64 KiB, the most an answer within a delivery takes, hold at most 16 MiB.

### Reading the outcomes of runs

The read answers, in one statement over the index, the rows of the playbook whose `started_day` lies in the window, with the selection's `definitionType` and `name`, grouped by day, definition type, name and status: each group with its count, its token sums, `coalesce(sum(…), 0)`, and the durations that are not null as a JSON array, `json_group_array(duration_ms) FILTER (WHERE duration_ms IS NOT NULL)` on SQLite and `json_agg` with the same filter on PostgreSQL. The playbook key is matched with `=`, and the statement binds five parameters at most.

## The signal of an append

`emmettEventStore` raises `streamAppends`, a `StreamSignal` of the process, after each append it made, with the name of the stream, and raises nothing for an append that met a version conflict. Every store of the process appends through it, the ledger's layer and the workflow host's own store alike, so a listener, `streamAppends.listen(listener)`, which answers the function that stops it, hears every append the process makes, a few microseconds after it commits. A listener is called in the append's own call, after the commit, and must not throw. An append made by another process raises nothing here; a reader that must see those reads the ledger anyway. `streamSignalOf()` makes a signal of one's own, for a test, and `emmettEventStore` takes it as `appended`. It is apart from `appendSignal`: that one tells the playbook key of an append and is raised only by a layer given it, while `streamAppends` tells every stream, a playbook's or not, and every store of the process raises it, so the workflow host's follower hears the appends to the registries of playbooks too.

## Telemetry

Each append passes Emmett the run's lineage as its observability context, so the store's `eventStore.appendToStream` span names the run in `auto.on.run_id` and its chain as its correlation and causation ids, and the `traceId` and `spanId` a message stores are that span's. An `AppendObserver`, `observer` on the layers and the stores, is told of every append after it commits, never of one that met a version conflict, with the events, the expected version, the context and the lineage; it must not throw. The server's observer turns each event into a log record over OTLP. The ledger takes no OpenTelemetry dependency at run time: the server registers Emmett's instrumentation before any store is created. Its tests capture the event store's spans with the trace SDK, `@opentelemetry/sdk-trace-base`, a development dependency.

## The streams appended to

`EventStore.readAppended(after, most)` answers which streams were appended to after a point, for a reader that must see the appends of other processes without reading each playbook in turn. It reads up to `most` messages after `after`, oldest first, and answers the stream of each named through its fourth `/`, so the streams of one kind in a playbook, such as `playbook/acme/sales/events/`, count once, or by its whole name when it has fewer, such as `org/acme/playbooks`; `through`, the point the next read goes on from; and `more`, when it stopped at `most`. Without a point it reads nothing and answers the point a read from now goes on from. It reads no data.

On SQLite it walks the table's key, `global_position`, and goes on from the last message it read. On PostgreSQL it walks Emmett's index on `(transaction_id, global_position)` behind the horizon, as a page read oldest first does (see [Order, and the horizon on PostgreSQL](#order-and-the-horizon-on-postgresql)), so a message whose transaction is still open comes in a later read, once; when it read everything behind the horizon it goes on from the horizon itself rather than from its last message, so a read that finds nothing new starts past every message it read before. Measured with `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL 18.6, on a table of 200,000 messages, a read that found nothing new walked that index and touched 3 buffers in 0.16 ms, and a read that found 10 new messages 5 buffers in 0.30 ms.

## Creating the layer

Each database has an entry of its own, so that code which never uses a database does not load its driver.

```ts
import { ledgerLayer } from '@on.auto/ledger/sqlite3';

const layer = ledgerLayer({ fileName: '/data/ledger.db' });
```

`runOutcomes`, optional on both layers, is the run outcome mapping the ledger keeps the outcomes of runs with, and `projections` the other projections it keeps (see [Keyed projections](#keyed-projections)); the server gives the mapping of `@on.auto/definitions` and the projection of the open requests of `@on.auto/interaction`. Building the layer creates the directory of the database file if it is missing, then opens the database and migrates its tables before the ledger is ready; a directory that cannot be created or a database that cannot be opened is a defect at that point. Disposing the runtime closes every connection. `fileName: ':memory:'` gives a private in-memory database.

Each SQLite connection may cache up to 8 MiB of pages and maps none of the file into memory, where the driver's defaults allow about 1 GB of cache and 256 MiB of mapped file per connection. Every connection, the tests' temporary files included, runs in WAL mode with `synchronous=NORMAL`, the defaults of Emmett's connection layer, dumbo: a committed append survives a crash of the process, and only the latest commits can be lost if the machine loses power, since in that mode SQLite syncs the file at each checkpoint rather than at each commit. Measured on 2026-10-05 on an Apple M4 Max through `sqlite3` 6.0.1, an append of one event of 1.8 KB to a temporary file took 0.20 to 0.23 ms at the median with either setting, since macOS syncs only to the drive's cache; with `fullfsync` on, so that each sync reaches the drive as on a disk that honours syncs, it took 5.9 ms with `FULL` and 0.20 to 0.24 ms with `NORMAL`, whose syncs at checkpoints showed as 5.2 ms at p99.

```ts
import { postgresqlLedgerLayer } from '@on.auto/ledger/postgresql';
import { Pool } from 'pg';

const layer = postgresqlLedgerLayer({
  pools: ({ max }) =>
    new Pool({ connectionString: 'postgresql://playbooks:<password>@db.internal:5432/playbooks', max }),
});
```

`pools`, a `PostgreSQLPools`, opens a pool of `pg` with the most connections it is asked for, and is all the ledger knows of the database: where it is and how a connection signs in, with a password or a token signed for each connection, are the pool's, which the server composes once for the ledger and the workflow host. `plainPoolsOn(url)`, beside it, opens plain pools on a URL, whose password is in the URL: the server's pools when `DATABASE_CREDENTIALS` is `url`, and the tests'.

Building the layer connects to the database and creates or migrates Emmett's tables, functions and sequence in its `public` schema, the way Emmett documents it (`schema.migrate()` with automatic migration off), before the ledger is ready. A database that cannot be reached is a defect at that point, and its message names the host and port, never the password. Emmett's migrator holds an advisory lock on the database while it migrates, so servers that start together on an empty database migrate it once; the ledger takes that lock first and waits for it up to 60 s (see [Creating and filling a table](#creating-and-filling-a-table)). The connections come from `pg`, the pure-JavaScript driver, through one pool for each ledger, opened from `pools` with at most 10 connections, `pg`'s default; disposing the runtime ends the pool. When the database ends a connection, as a restart, a failover or `pg_terminate_backend` does, the ledger logs a warning with the database's message and the pool opens another connection on the next call; the server never stops for it.

The database's user needs `CREATE` on the `public` schema at every start, not only the first: the ledger migrates at every start, and the migrator runs `CREATE TABLE IF NOT EXISTS` on its own table, which PostgreSQL checks for the privilege before it looks whether the table exists, so a user that may only read and write the tables fails to start with `permission denied for schema public`. It also needs to read and write the ledger's tables, and to create its functions and sequence on an empty database.

## PostgreSQL

The ledger on PostgreSQL behaves as it does on SQLite; one suite of tests runs against both (see [Testing](#testing)). What was verified on Emmett's PostgreSQL store, `@event-driven-io/emmett-postgresql` 0.43.0-beta.50 with `pg` 8.23.1 against PostgreSQL 18.6:

- **An append is atomic.** Emmett appends every event of a call in one transaction, through one call of its function `emt_append_to_stream`; an append whose third event PostgreSQL refused left the stream as it was.
- **The expected version is checked exactly.** Expecting 0 of a stream that exists, a version beyond the stream's or one behind it, or any version but 0 of a stream nobody wrote, meets a version conflict and appends nothing. Of eight writers expecting the same version at once, one appended and seven met a conflict, for an existing stream and for a new one.
- **`STREAM_DOES_NOT_EXIST` is no check at all,** as on SQLite: Emmett turns it, `STREAM_EXISTS` and `NO_CONCURRENCY_CHECK` into no expected version and appends at the end. The ledger therefore always appends with a number.
- **A read from a version is exact.** Reading after version 3 of a stream at 5 gives events 4 and 5 and the version 5; past the end, Emmett gives no events and version 0, which `read` answers with the version asked after.
- **Message ids are not deduplicated.** The store keeps two events with the same message id, and the same event appended twice is two events with two ids.
- **The store keeps no JSON as written.** Emmett stores `data` in a `jsonb` column, and `jsonb` refuses the character U+0000 and unpaired surrogates and puts the keys of every object in its own order. The PostgreSQL entry therefore keeps each event's JSON text in that column, as `{"json": "<the event as JSON>"}`, so an event comes back exactly as it was decided, as it does from SQLite's text column. This is a deliberate trade: an exact round trip of tenant data matters more than `jsonb`'s operators. What an operator gives up is querying and indexing events by their data in SQL: reading one takes `(message_data->>'json')::jsonb`, which fails for an event that holds U+0000, and an expression index over event fields would have to parse the text the same way. The context of every message is in its metadata instead, plain `jsonb`, which holds only identifiers the playbook checks where it takes them, so a query over the metadata column answers every delivery of a definition in a week without opening a row, and the list of runs filtered by definition reads it so (see [The indexes](#the-indexes)). A stream name cannot hold U+0000 on PostgreSQL; the application layer's stream names are made of ids that never do.

An append on PostgreSQL binds ten parameters whatever the number of events, one array per column, so PostgreSQL's own limit of 65,535 parameters in one statement never binds. The ledger still bounds a decision, at 64 events, eight times SQLite's eight, so that a decider that runs away is a defect rather than one long transaction. Code that must run on both stores keeps its decisions to eight events.

Every command is a decision appended under an expected version, so concurrent writers never lose an update to playbooks and definitions. Every server runs a workflow host, and one of them runs the database's workflows at a time, under a claim the workflow host keeps in its own table, so several servers may share the database.

## What a store must provide

The ledger runs on Node, the one runtime the server's image carries, so any of its modules may use Node's own, as the digest of recorded content does with `node:crypto`. Its stores are SQLite and PostgreSQL; on SQLite it binds at most 100 parameters in one statement (`src/sqlite-event-store.ts`, `src/projections/sqlite-projections.ts`), and what it asks of a store comes in two parts.

What every store must provide, for the ledger to run at all:

- The event store's own operations, to read a stream or its tail after a version, append with an expected version, migrate and close. A command makes at most one append and needs no transaction of its own.
- The read of what a playbook recorded, with the indexes the ledger creates when it opens; each statement binds at most 15 parameters, and none needs a transaction.
- An append on SQLite carries at most eight events: Emmett binds ten parameters for each event it inserts, and the ledger binds at most 100 in one statement there.
- A SQLite database must provide what the reads use: `octet_length` (SQLite 3.43 and later), window functions (3.25 and later), the JSON functions, of which the reads use `json_each` and `json_group_array` (built in since 3.38), and partial and expression indexes (3.8 and 3.9), and what the rotation of kept secrets uses, an `UPDATE` with `RETURNING` (3.35); `sqlite3` 6.0.1 carries SQLite 3.52.0.
- No adapter or application may nest a stream under `runs/` within a playbook: the key of a stream's kind ends at the fourth `/`, so the list of runs would take any stream named `runs/<id>/…` for a run.
- Only the entries `src/sqlite3.ts` and `src/postgresql/postgresql-ledger.ts` know which driver is in use; the main entry loads neither `sqlite3` nor `pg`.

What a store must provide besides, to keep the keyed projections, the outcomes of runs that a playbook's analytics read and the open requests of interaction functions among them:

- Inline projections inside the append's own transaction: a read and an upsert of a row for each message of a projection's kinds and types, for each projection, which commit with the append and fail it when they fail. An upsert of one row binds two parameters more than the projection has columns, 12 for the outcomes of runs, and SQLite must provide the upsert (3.24), the `FILTER` of an aggregate (3.30), `NULLS FIRST` and `NULLS LAST` (3.30) and comparisons of row values (3.15).
- An `UPDATE` of one row by its key for the reader's advance, binding two parameters more than the columns it advances.
- A transaction for the fill when the table is created, in which the store's streams are read and the rows written, 8 to an upsert of 96 parameters on SQLite, so that an interrupted fill leaves nothing behind.

Opened without the run outcome mapping and the projections, the ledger neither creates nor writes their tables. SQLite and PostgreSQL provide both parts, so the self-hosted runtime opens the ledger on either with the run outcome mapping and its keyed projections, the open requests, the conversations and the builds and models of prediction functions, and serves `get_playbook_analytics` and interaction functions on both (`packages/server/src/composition/ledger-store.ts`).
