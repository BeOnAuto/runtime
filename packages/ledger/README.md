# @on.auto/ledger

The ledger keeps track of every single action and interaction that the playbook does. It is the log of the inputs and outputs to all the capabilities.

This package is the event store behind the `Ledger` port of `@on.auto/operations`. It stores events with [Emmett](https://event-driven-io.github.io/emmett/) on SQLite or on PostgreSQL.

## What it stores

- **Streams of events.** The application layer names each stream, for example `org/acme/playbooks` or `playbook/acme/sales/definitions/reasoning`. Names are opaque: the ledger never changes their case, trims them or normalises their Unicode, so two names that differ in any character are two streams.
- **One version per stream.** A stream's version is the number of events in it, and 0 when nobody has written it.
- **Keyed projections.** One row per key in a table of each projection the ledger is opened with, kept inside the append of each fact of the stream kinds the projection names, of a playbook's streams or an org's: the outcomes of runs in `run_outcomes_5`, which a playbook's analytics read, and any other projection the composition registers, such as the open requests of interaction functions (see [Keyed projections](#keyed-projections)).
- **Facts as Emmett stores them.** Each event a decider decides, `{ type, data }`, becomes a message `{ type, data, metadata }`. `type` is the fact's name. `data` is the fact's data alone, encoded with `Schema.toCodecJson(decider.eventSchema)`, which must give a JSON object, and holds no copy of the type. Loading decodes `{ type, data }` with the same codec, so a fact comes back exactly as it was decided, dates and big integers included. A stored fact that no longer decodes is a defect.
- **Facts kept as they were recorded.** No write of the ledger changes a fact it appended but the scrub of its data, when a person asks for what they wrote to be erased, which leaves its type, position, context, author and time as they were and appends an erasure beside it (see [A fact scrubbed in place](#a-fact-scrubbed-in-place)).
- **The context of every message in its metadata.** The `Context` the decider answers for a decision, `context(command, state)`, is written once, `metadataOf`, into the metadata of every message of the append beside the store's own fields: `at`, `by`, and where the context holds them `runId`, `definitionType`, `definitionName`, `definitionVersion`, `calledBy`, `callDepth`, `depth`, `trigger` and `actsFor`. It is checked first (`checkedContext`), so a context with a character PostgreSQL's `jsonb` refuses is a defect on every store, and nothing is appended. Each fact's schema names the context the fact carries beside its data, `factOf(type, data, context)` of `@on.auto/operations`, such as a run's `RunContext` or a definition's `DefinitionContext`, so each event of a decision is recorded with that decision's context checked against its fact's (`recordingOf`), and a context a fact does not carry is a defect and nothing is appended. The stream read decodes the context with the fact, so a stored record whose context is not its fact's fails to load as one whose data no longer decodes does. The recorded reads, the projections and their fills hand the context back whole, through `contextOf`. Measured on the installed store, every field round-trips unchanged through a stream read and an inline projection; on PostgreSQL the metadata is plain `jsonb`, unwrapped.
- **The true size of a fact.** A fact that offloads payloads (see [Payloads kept outside a fact](#payloads-kept-outside-a-fact)) carries in its metadata `payloadBytes`, the bytes of the payloads it names, and no other fact does; a fact's true size is the length of its stored data and that member, which every bound of a read counts. Each fact is measured by its own schema's declaration in `eventAsAppendedOf` of `src/event-appender.ts`, the step `eventAppenderOf` and `eventAppenderWithOf` share, so an append of the connection, a workflow run log's among them, is measured as every other, and the member is written by Emmett's own insert in the append's transaction, and Emmett's tables gain no column outside the layout. The store checks the holders against that size on `append` and on `appendWithin` alike. The connection's streams are opened with the holders of the ledger they belong to, and so with the holds of content folded in the append's transaction and the check that each payload a fact names has a head, as the ledger's own appends are, so a workflow's run log that keeps a value outside is held where it is appended; a ledger opened with no holders refuses such a fact there as everywhere, since nothing on that path would hold it (`measuredRiddenAppendsBehaviour`). The connection also carries the ledger's content (`ConnectionPorts.content`), the store the ledger keeps its content in, so whatever appends through the connection keeps a payload where the ledger's own facts keep theirs. The pinned shape, `src/appends/payload-metadata.ts`, is read back on both stores and on an object's SQLite.
- **The holds on content.** One row for each stream of a playbook and each digest of a content its facts hold, in `content_references_1`, kept in the append of each fact whose schema declares what it holds, so a content is removed only when nothing holds it (see [The holders of content](#the-holders-of-content)).
- **The rows of kept secrets.** Beside its streams and their content, the ledger's database keeps the rows of the secret store of `@on.auto/secrets`, each value sealed before it reaches the ledger or kept in a secret manager it never reaches, in one table no fact names (see [Kept secrets](#kept-secrets)).
- **An id, a cause and a correlation for every message.** The store's append writes, in each message's metadata, `messageId`, which Emmett also keeps as the message's `message_id` and honours when the caller gives it, `causationId` and `correlationId`. The id is `messageIdOf(stream, position)` of `@on.auto/operations`, a version 5 UUID of the stream and the position the message takes, which the append knows before it writes since every append passes the version it expects; so no two messages share an id, and anyone who knows a stream and a position names its message. The cause and the correlation are the `Lineage` the command was executed with, `null` when it was given none. Messages written before the ledger set its own ids keep the random ids Emmett gave them, and no cause or correlation.

## How a command runs

`execute(stream, decider, command, lineage?)` loads the stream, folds its facts with `decider.evolve`, each handed as it was recorded, `{ type, data, context }`, its context the one its fact carries, and asks `decider.decide`; it asks `decider.context(command, state)` of a decision that appends anything, and the facts it appends carry the lineage and that context, and are folded with it into the state it answers, beside the version after them and `decidedOn`, the state the decision was made on, which a retried decision takes from its last load, so a caller knows what its own decision replaced.

- A rejection is returned as it is, and nothing is appended.
- A decision of no events appends nothing and answers with the current state and version.
- Otherwise the events are appended with the version that was read as the expected version. If another writer appended first, the append meets a version conflict: the stream is loaded and the command decided again, up to three more times, and then it fails with `Conflict`. A deadlock PostgreSQL breaks between two appends, `40P01`, which dumbo answers as its `DeadlockError`, is met as a version conflict too, and decided again the same way (`appendedTo` of `src/emmett/emmett-event-store.ts`). Like the in-memory ledger of `@on.auto/operations`, its detail names no stream.
- An append that an inline projection refuses, as the keeper of the names of definitions refuses a name another definition holds (see [The names of definitions](#the-names-of-definitions)), keeps nothing and fails with the `Conflict` the refusal carries, which is not decided again: the refusal is the store's answer, not a change made meanwhile (`retriedOnVersionConflict` retries a version conflict alone). The appenders that append outside a decision, `eventAppenderOf` and `eventAppenderWithOf`, have no one to answer, and take a refusal as a defect.
- A decision of more events than the store takes in one append is a defect: eight on SQLite, 64 on PostgreSQL.
- Any other failure of the database is a defect, never a `Conflict` or a rejection.

## Building on the ledger's loop

Code that keeps its own streams, such as `@on.auto/workflow-engine`, uses the same pieces as the ledger itself rather than a copy of them:

- `sqliteEventStore(optionsOf, { runOutcomes?, projections? })` opens the event store on any of Emmett's SQLite drivers, without the layer, and `postgresqlEventStore({ pools, reportLostConnection, runOutcomes?, projections? })` from `@on.auto/ledger/postgresql` opens it on PostgreSQL; given a run outcome mapping, the store keeps the outcomes of runs, and given projections, their tables. Both are one adapter over an Emmett event store, `emmettEventStore`, given how each keeps an event's data and how many events it takes in one append, beside the store's own read of what a playbook recorded, `EventStore.readRecorded` (see [Reading what a playbook recorded](#reading-what-a-playbook-recorded)).
- `EventStore.read(stream, after)` gives the messages after version `after`, each `{ type, data, context, lineage }`, its lineage `{ id, causationId, correlationId }`, and the version of the whole stream, so a reader that holds a snapshot at version `after` reads only the tail. Emmett answers a read past the end of a stream with version 0; `read` answers with `after` instead. `eventCodecOf(schema).decode(message)` turns one into the event as it was recorded, its data and its context decoded with its fact's schema. `load(stream, fold)` takes a `Fold`, the initial state, `evolve` and the fact schema, which a `Decider` extends with `decide` and `context`, so a reader that only folds a stream declares nothing it never writes.
- `EventStore.mostEventsInOneAppend` is the most events the store takes in one append.
- `eventAppenderOf(store, eventSchema)` encodes and appends decided events at a place, `{ expectedVersion, context, lineage? }`, at most `store.mostEventsInOneAppend` in one append, checks the context first and against each event's fact, and fails with `VersionConflict` when another writer appended first. It knows a conflict by the tag of the error the append rejects with, `version_conflict`, through `isVersionConflict(error)`, never by its class, so a conflict raised by another copy of the package is known too: `Streams.append` rejects with a `VersionConflict` when the stream is not at the version it expects, and `emmettEventStore` turns Emmett's own conflict into one, so every store of this package rejects the same way (`src/testing/store-behaviour.ts`, on both stores).
- `retriedOnVersionConflict(attempt)` runs a load-decide-append attempt again after a version conflict, up to three more times, and then fails with `Conflict`.
- `EventStore.definitionStreams(type)` names the streams of one type of definition in every playbook, such as each playbook's `definitions/workflow`, with the version of each, read from Emmett's table of streams through an index of their own (see [The indexes](#the-indexes)), so a reader that follows the definitions of one type, as the workflow host follows the definitions whose pages it keeps, finds a playbook whose first definition of the type was saved after it started.
- `ageOfLastAppend(stream)`, which every `LedgerStreams` answers, the event store and the `streams` of `LedgerConnection` alike, answers how long ago the last message of a stream in the default partition was appended, by the database's clock, from the time the database stamped it with: on PostgreSQL `now()` less its `created`, on SQLite `julianday('now')` less its `created`, which SQLite keeps in whole seconds, so the age it answers is at most a second longer than the true one (`src/stream-ages`). A stream with no message is endlessly old. `Ledger.ageOfLastAppend` answers it through the port of the same name.
- `versionOf(stream)`, `messageAt(stream, version)` and `lastMessageOf(stream)`, which every `LedgerStreams` answers too, read a stream for one fact without reading the rest of it. `versionOf` answers the version of the stream's last message, 0 for a stream never appended to, from Emmett's table of streams, `emt_streams`, by its key, and reads no message (`src/stream-versions`). `messageAt` answers the one message at a version, as `read` answers each, or nothing before the first or past the last, through Emmett's own read bounded from and to that version, `readStream(stream, { from, to })`. A reader that needs a stream's first fact, its last, or only whether it holds a version reads those and no more: the data of a run's start may hold 256 KiB and its end 1 MiB, and on a Durable Object every row a statement answers is held at once (`sql.exec(…).toArray()` in the client of `@event-driven-io/dumbo` 0.13.0-beta.56, `dist/cloudflare.js` line 3478). `lastMessageOf(stream)` answers a stream's last message in one statement, as `read` answers it, or nothing for a stream never appended to, reading the one row `ORDER BY stream_position DESC LIMIT 1` with the columns a message needs (`src/recorded/sqlite-last-messages.ts`, `src/postgresql-reads/postgresql-last-messages.ts`), so a check of a waiting call's child costs one statement and reads one row. `src/stream-versions/stream-versions-behaviour.ts` holds all three on each store. `factAt(stream, position, eventSchema)` of the ledger answers the one fact at a position, decoded by the schema given as `load` decodes each, or nothing before the first, past the last or at a position that is not a whole number: the ledger and `streamPortsOf` read it with `messageAt` of the streams they are given, the streams an object lends among them, so a reader holding a position reads that fact and none of the rest of its stream, and lists no size of the facts after it (`src/stream-reader.ts`).
- `appendSignal()` is an in-process signal of appends to playbooks: `raise(stream)` tells every listener the playbook key of a stream, its name through the third `/`, and nothing for a stream of no playbook, and `listen(listener)` answers the function that stops listening. `signalledOn(store, signal)` raises it after each append the store recorded, never after one that failed, and the layers take it as `appends`, `ledgerLayer({ fileName, appends })` and `postgresqlLedgerLayer({ pools, appends })`, so code in the same process that follows a playbook, as the workflow host's projector does, wakes when something was recorded rather than at its next sweep. Appends made by another process raise nothing here.
- `decisionLoop(load, append, decider)` is the load-decide-append loop itself, the one `Ledger.execute` runs: it loads, decides, asks the decider for the decision's context, appends the decided events at `{ expectedVersion, context }`, the loaded version expected, giving the append what the load gave too, retries with `retriedOnVersionConflict`, and answers with what the load gave, the events as they were recorded, each with the context its fact carries, and the state folded with them. The ledger's load folds the whole stream; a caller with snapshots passes a load that folds a snapshot and its tail.
- `streamPortsOf(streams)` is the stream reader and writer of a ledger over any `Streams`, the `read` and `append` of streams and the most events they take in one append: `load(stream, fold)`, `factAt(stream, position, eventSchema)` and `execute(stream, decider, command, lineage?)`, the decision loop over `eventAppenderOf`, which the ledger's own service is made of (`makeLedger`). A program that composes the core over streams it lends a ledger, rather than over a store of this package, makes its `load` and `execute` with it and restates nothing of the loop or the append (`src/decision-loop.test.ts`). Streams lent across a boundary, where an error does not travel as itself, say a conflict the lending store met as any error tagged `version_conflict` on the borrower's side, a `VersionConflict` of `@on.auto/ledger` among them, and the loop loads and decides again; the program knows the conflict on the lending side by the same tag, with `isVersionConflict`, and needs nothing of Emmett for either.

## An append to several streams

`LedgerStore.multiStreamAppend(requests)` appends the facts of several streams in one transaction of the store's database, and keeps all of them or none: an `AppendStreamRequest` for each stream, `{ stream, events, place }`, the version the stream is expected at and the context and lineage of its facts given as `append` takes them (`src/multi-stream/multi-stream-appends.ts`). It is the operation KurrentDB calls a multi-stream append, "Both guarantee that either all writes succeed or the entire operation fails", with "Each stream can only appear once in the request" ([Appending events](https://docs.kurrent.io/clients/dotnet/v1.4/appending-events), from KurrentDB 25.1), and what Marten's session does when it appends to several streams, "the `IDocumentSession` is the sole unit of work for transactional updates", whose appends "ride the session's unit of work exactly as `Store()` does; nothing is written until `SaveChangesAsync`" ([Sessions](https://martendb.io/documents/sessions)), here on the ledger's own stores, each one database: a SQLite file, a PostgreSQL database and an object's SQLite. Each stream keeps its own optimistic concurrency, the version its request expects. Nothing in this release calls it.

- **One transaction, Emmett's own statements.** The store opens one transaction on one connection, the writer's on a SQLite file, one of the pool's on PostgreSQL and one storage transaction on an object, with dumbo's `allowNestedTransactions`, which each of Emmett's drivers sets on the pools it makes (`mapToDumboOptions` of `@event-driven-io/emmett-sqlite/sqlite3`, `@event-driven-io/emmett-sqlite/cloudflare` and `@event-driven-io/emmett-postgresql/pg`, 0.43.0-beta.50), and appends each stream through `appendToStream` of an Emmett store on that connection that runs no inline projection, so each stream's statements are Emmett's own and join the one transaction rather than commit one of their own: on SQLite the read of the stream's version, the insert or update of its row in `emt_streams` and the insert of its messages, on PostgreSQL one call of `emt_append_to_stream`, and on an object the statements of SQLite, each stream's `storage.transaction` nested in the one that holds them all (`src/multi-stream/joined-appends.ts`, the stores' `appendingOn` and `transactionsOnThePool`).
- **The order of its facts.** The streams are appended in the order of their names, compared as JavaScript compares strings, whatever the order of the requests, and each stream's facts in the order given. So the facts of one append are grouped by stream and stand together in the store's order, at consecutive global positions on SQLite and under one transaction id on PostgreSQL, and a decision that needs one fact recorded before another puts both in one stream: across streams, the facts of one append happen together. KurrentDB groups the records of a multi-stream append by stream too, "ordering across streams is not guaranteed".
- **What runs in its transaction.** Once the last stream is appended, every fact of the append is handed at once to each inline projection, in the order the facts were kept, as Emmett hands a projection the facts of one append (`handleProjections` of each store), the keyed projections, the outcomes of runs, the holds on content, the stream projections and the keeper of the names of definitions among them, and then to the work before a commit, a scrub's and, on SQLite, a hook a caller gave (see [The indexes](#the-indexes)). So each projection sees the whole append once, and takes the locks of the whole append in one pass of its own (see PostgreSQL's locks, below).
- **All or nothing.** A stream that is not at the version its request expects fails the append with a `VersionConflict`, as an append to one stream does, and so does a deadlock PostgreSQL breaks anywhere in the transaction, and so does a unique-constraint error anywhere in it: Emmett meets one raised inside an append to one stream, an inline projection's or the work before its commit included, as a conflict (`dist/index.js` line 960 of `@event-driven-io/emmett-sqlite` and lines 1495 and 1509 of `@event-driven-io/emmett-postgresql`, 0.43.0-beta.50), and the projections and the work before the commit of an append to several streams run outside Emmett's append, so the ledger meets it the same way (`src/multi-stream/emmett-multi-stream-appends.ts`); a test makes such a key broken on PostgreSQL, a name the keeper of the names of definitions writes after another transaction claimed it unseen, and on a SQLite file, a row a caller's hook writes twice, and finds an append to one stream and an append to several refused alike, nothing kept. An inline projection that refuses a fact fails it with its `AppendRefused`, which names the stream of the fact it refused, `refusedStreamOf` of `src/refusals/append-refused.ts`; and any other failure fails it with the error as it is, a defect. In each case the transaction rolls back, and no stream keeps a fact, no projection a row and no keeper a name, whichever stream failed and however many were appended before it.
- **PostgreSQL's locks.** An append takes its locks in one order, the rule the PostgreSQL manual gives against deadlocks, "The best defense against deadlocks is generally to avoid them by being certain that all applications using a database acquire locks on multiple objects in a consistent order" ([Deadlocks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-DEADLOCKS), 13.3.4), the same order an append to one stream takes its own in:
  - first the rows of its streams in `emt_streams`, in the order of their names, which Emmett's `emt_append_to_stream` updates or inserts, so two appends that share streams never each hold one the other waits for: a test holds one stream's row, makes an append name the two streams in the other order, and finds the first stream's row locked while the append waits for the second;
  - then the locks of each inline projection, in the order the projections are registered, every lock a projection takes for the whole append in one pass: a keyed projection, the outcomes of runs among them, the rows it folds in the order of their prefix and key (see [Inline projections](#inline-projections)); the holds on content, every playbook and digest whose hold the append changes, in the order of the playbook and then the digest, before it writes any (see [The holders of content](#the-holders-of-content)); a stream projection, the checkpoints of all its streams the append names, in the order of their names, and then, table by table, the rows the facts of the streams it folds change, in the order of their prefix and key (see [Stream projections](#stream-projections)). Tests hold, on PostgreSQL, a lock the append takes between the streams it folds, and find an append to another stream that changes the same holds, or folds into the same rows of a stream projection, kept beside it rather than refused as a deadlock, which it is when the holds or the checkpoints are locked stream by stream (`src/multi-stream/lock-order-on-postgresql.test.ts`);
  - and last the keeper of the names of definitions, which judges every name of the append at once and takes its locks in one order, its definitions, then its names, then its playbooks, each in the order of its key (see [The names of definitions](#the-names-of-definitions)). A deadlock with work outside the ledger that locks in another order is broken by PostgreSQL, `40P01`, after `deadlock_timeout`, 1 s by default, and the ledger meets it as a version conflict, which the decision loads and decides again; a test makes one and finds nothing kept (`src/multi-stream/multi-stream-on-postgresql.test.ts`).
- **Readers.** A reader of a SQLite file reads the snapshot of a reader connection, and on PostgreSQL every fact of the append carries the append's transaction id, which a read oldest first stays behind until the transaction ends, so no reader sees part of an append, and a reader that goes on from a place, the log, the facts appended to a playbook or the streams it names, and a read over several keys, reads each of its facts once, in the order kept; a fact another transaction commits while the append is open waits behind it on PostgreSQL. Tests read a SQLite file and a PostgreSQL database while an append is held open inside its transaction (`src/multi-stream/multi-stream-on-sqlite.test.ts`, `multi-stream-on-postgresql.test.ts`). An object is the one connection to its database, and a read it makes is a statement of that connection, as for every append it makes.
- **Its bounds.** It names at least one stream and each stream once, gives each stream at least one fact and no more than the store takes in one append, eight on SQLite and 64 on PostgreSQL, and no more than 64 facts in all, `mostEventsInAMultiStreamAppend`, the bound the ledger sets on a decision on PostgreSQL, so that a decision that runs away across streams is a defect rather than one long transaction (see [PostgreSQL](#postgresql)), and no more than 4 MiB of event data in all, `mostBytesInAMultiStreamAppend`, each fact's data counted as the JSON text the store keeps, in UTF-8, the stored bytes a fill counts, and a payload kept outside its fact not at all, since it is put before the append and is no part of its transaction. Anything else is a defect, a `RangeError` that names the bound it passed, refused before anything is appended.
  - **Why 4 MiB.** An object's SQLite is the narrowest of the three stores. Cloudflare's [limits of SQLite-backed Durable Objects](https://developers.cloudflare.com/durable-objects/platform/limits/) give 8 MB for a string, a BLOB or a row, 100 KB for the text of a statement and 100 bound parameters, and no bound on a transaction; an append to several streams keeps the statements an append to one stream makes, so none of those grows with it. What binds is memory: "Each isolate can consume up to 128 MB of memory, including the JavaScript heap and WebAssembly allocations" ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)), and an object holds the whole append, its facts decided, their JSON text and what its projections read, inside one storage transaction. 4 MiB is the most the ledger loads in one page of a read, `mostBytesLoadedInAPage` of `@on.auto/operations`, and the most a fill of a projection holds at once on an object, `objectMostBytesFilledAtOnce` of the hosted runtime, which its measurement puts at about 13 MB of heap. It holds 64 facts of 64 KiB; with payload offloading, a fact offloads its larger payloads, and 64 such facts hold far less. Measured on 2026-11-13 on an Apple M4 Max with Node 26.12.1, with made-up facts of distinct random text, five runs each: in the hosted runtime's local Workers pool, on an object's SQLite through the object's own store, an append of 64 facts of 64 KiB over eight streams took a median of 21 ms a visit, 22 ms with a keyed projection folding every fact, against under 1 ms for a visit that opens the store and appends nothing; the pool reports no memory of an object, its `process.memoryUsage()` answering 0, so the heap was read on Node, through the store of a SQLite file, the same ledger and Emmett with another driver, after a full collection inside the append's transaction, as it is about to commit: 4.09 MiB live where the request alone held 4.01 MiB, 4.12 MiB with the projection, and nothing left once it committed. A test appends exactly 4 MiB on each store and is refused one byte more (`keptAtItsBoundInBytes` of `src/multi-stream/multi-stream-append-behaviour.ts`).
- **After it commits.** The signal of an append and the `AppendObserver` hear each stream, in the order it was appended, and nothing of an append that failed (see [The signal of an append](#the-signal-of-an-append)); the layer's `appendSignal` raises the playbook of each stream in the order of the requests, a wake-up whose order carries nothing.
- **Its cost.** Beside the statements its inline projections make for each fact, as an append to one stream makes them, an append to several streams sends on PostgreSQL one statement for each stream and two for its transaction, 66 for 64 streams of one fact where 64 appends of one stream send 192, and on SQLite three statements for each stream, Emmett's, and two for its transaction.
- **Its telemetry.** Each stream's append makes Emmett's `eventStore.appendToStream` span and counts its facts in Emmett's metrics, `emmett.stream.appending.size`, `emmett.event.appending.count` and `emmett.stream.appending.duration`, with the status `success` once that stream's statements succeed inside the transaction: Emmett records them as the stream's `appendToStream` returns (`instrumentAppend`, `dist/index.js` lines 2393 to 2417 of `@event-driven-io/emmett` 0.43.0-beta.50), before the transaction commits, and its stores have no hook after a commit. So for an append to several streams a `success` there says a stream's statements succeeded, not that they were kept: an append rolled back after it, by a conflict on a later stream, a refusal or a failure, leaves the spans and counts of the streams before as they are. What tells an append kept is what the ledger raises after the commit, the signal and the `AppendObserver`, which the server turns into log records. The ledger cannot hold Emmett's span back from outside: giving the joined store a tracer of the ledger's own would change the `traceId` and `spanId` Emmett writes into each fact's metadata from the span of its append (`dist/index.js` line 932 of `@event-driven-io/emmett-sqlite`, 1451 of `@event-driven-io/emmett-postgresql`), so a fact of an append to several streams would name another span than one of an append to one; and counting the metrics again after the commit would restate Emmett's collector. A test rolls an append back on its last stream and finds the span of the stream before it a `success`, the span of the last a `failure`, and the observer told nothing of it (`src/multi-stream/multi-stream-spans.test.ts`). The inline projections of an append to several streams run in no `eventStore.inlineProjection` span.

`multiStreamAppenderOf(store, eventSchema)` appends decided events to several streams as `eventAppenderOf` appends them to one: it checks each stream's context and encodes each fact against it, through the step every append's facts pass through, and fails with a `VersionConflict`, which `retriedOnVersionConflict` decides again, or with a `StreamRefused`, `{ stream, conflict }`, the stream whose fact an inline projection refused and the `Conflict` it refused it with (`src/multi-stream/multi-stream-appender.ts`). `multiStreamAppendBehaviour(entry)` of `@on.auto/ledger/testing`, with `MultiStreamEntry`, a `LedgerEntry` that opens a store keeping the projections and the names a case gives, holds all of the above on SQLite, PostgreSQL and an object's SQLite.

## Reading what a playbook recorded

`Ledger.readRecorded(playbook, selection, page)`, the read the `Ledger` port of `@on.auto/operations` describes, is answered by the store: one SQL read of its own on each store, over Emmett's messages table, with six indexes the ledger adds to it. Each record carries its id, its place, its context, cause and correlation, and the store's trace: the id from `message_id`, its stream, its position in it and its global position from the table's own columns, `stream_id`, `stream_position` and `global_position`, since the SQLite store's metadata holds the position within the append and the PostgreSQL store's holds neither, and the rest from `message_metadata`, which the head of each record a page answers reads whole, its correlation through the expression the fifth index holds. The metadata never holds tenant data: only the identifiers of the context. `Ledger.readRecordedEvent(playbook, id)` reads one message by its id within the playbook, through the seventh index. The selections, the page and its bounds are the port's; this section says how each store answers them.

### The playbook key

Every stream of a playbook is named `playbook/<org>/<playbook>/…`. The store takes the key of a message's stream, its name through the third `/`, with an expression, and compares it to the playbook's key, `playbook/<org>/<playbook>/`, for equality: with `=` on SQLite, and on PostgreSQL with `= ANY` of a list that holds the key alone, for the reason [How PostgreSQL reaches the indexes](#how-postgresql-reaches-the-indexes) gives. It never matches with `LIKE` or any pattern: org and playbook ids may hold uppercase letters and `_`, SQLite's `LIKE` ignores case, and `_` matches any character in both stores. A stream name with fewer than three `/` has no key and belongs to no playbook.

| Store      | The key of a stream                                                                                            |
| ---------- | -------------------------------------------------------------------------------------------------------------- |
| SQLite     | `substr(stream_id, 1, …)` to the third `/`, found with nested `instr`, since SQLite has no regular expressions |
| PostgreSQL | `substring(stream_id FROM '^(?:[^/]*/){3}')`, null for a name with fewer than three `/`                        |

The same expression taken to the fourth `/` gives the key of a stream's kind within its playbook, such as `playbook/acme/sales/runs/`. A run is a stream whose kind key ends in `runs/`, so no other stream may be nested under `runs/`.

### A key that names a definition, and a read over several keys

The key of a stream may name a definition as well as a playbook: a stream named `definition/<org>/<definition>/…` has the key `definition/<org>/<definition>/`, through the same expression, and the ledger reads it by that key as it reads a playbook's by its own, through the same indexes, its runs through the same index of first messages by kind, `definition/<org>/<definition>/runs/`, and its definition streams through the sixth index, `definition/<org>/<definition>/definitions/<type>`. The ledger tells the two apart by nothing but the key, and holds nothing of what either names (`src/keys/recorded-keys-behaviour.ts`, on both stores and on an object's SQLite).

The store reads the records of several keys at once, merged in the order they were appended: `RecordedStore.readRecordedOfKeys({ org, keys }, selection, page)` and `readRecordedEventOfKeys({ org, keys }, id)`, `RecordedKeys` of `src/keys/recorded-keys.ts`, `keys` the keys the read covers, of the org `org`, the first of them the key a cursor names. `readRecorded(key, selection, page)` and `readRecordedEvent(key, id)` read one key, of the org its second segment names, as the same reads of that key alone (`keysOfOne`). Every selection reads over the keys given: every record of the keys, the runs of the keys by the first message of each, a run's two streams under whichever key holds them, the tree of a run, and one event by its id. The read of one key is the read of a playbook as the sections above set it out, statement for statement. Several keys are read as a merge of a walk of each, each walk bounded by the page:

- **On SQLite** by one statement, which binds the keys as one value, a JSON list read with `json_each`, whatever their number, so a read of a few hundred keys binds no more than the 100 values a Durable Object's SQLite takes in one statement: `global_position IN (SELECT … FROM json_each(<keys>) AS keyed JOIN emt_messages AS walked ON walked.global_position IN (SELECT global_position FROM emt_messages WHERE <key> = keyed.value … ORDER BY global_position LIMIT <the page's bound>))`, ordered and bounded again by the read. Each walk is a correlated subquery that walks its key's index in the order of the read and stops at the bound, so a page of several keys reads at most the bound of the page from each key, however much each holds; the plan of each read names the key's index under each walk and no sort inside it (`src/keys/sqlite-key-plans.test.ts`). A list matched with `IN` and ordered by the position is not read this way: SQLite's planner chose the index of the key and the time for it, `ledger_messages_by_playbook_and_time`, which does not keep the order of the position, so the read would sort every record of the keys.
- **On PostgreSQL** by a term for each key, each walking its key's index in the order of the read with the page's bound, joined with `UNION ALL` and ordered and bounded again, as a run's two streams are read (see [Facts appended to a scope](#facts-appended-to-a-scope)); the plan names the key's index under each term (`src/postgresql/ledger-on-postgresql.test.ts`).

A read of several keys binds on SQLite at most 21 values whatever the number of keys, a list of runs given every filter and a cursor, and on PostgreSQL the values of a term for each key, seven more for each key of a list of runs given every filter, far below the 65,535 PostgreSQL takes; counted from the values each statement binds, for one key, three and thirty. The tree of a run and one event are read through the indexes led by the org, below, and keep the records of the keys asked. The `Ledger` port of `@on.auto/operations` reads one playbook, `readRecorded(playbook, …)` and `readRecordedEvent(playbook, id)`, which the ledger answers with the playbook's key alone, of the org its address names, so the port's reads take the org from the address and never from the text of the key (`src/recorded/recorded-reader.ts`).

### The indexes

| Index                                    | SQLite                                                           | PostgreSQL                                                                | What reads it                                                  |
| ---------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `ledger_messages_by_playbook`            | playbook key, position                                           | playbook key, transaction id, position                                    | a playbook's messages, in order, from any cursor               |
| `ledger_messages_by_playbook_and_time`   | playbook key, recorded time                                      | playbook key, recorded time, transaction id, position                     | where a page `since` a time starts                             |
| `ledger_messages_by_stream`              | stream, position                                                 | stream, transaction id, position                                          | one run's two streams, each in order from any cursor           |
| `ledger_first_messages_by_kind`          | kind key, position, first messages alone (`stream_position = 1`) | kind key, position in the stream, transaction id, position, every message | the runs of a playbook, by the position of their first message |
| `ledger_messages_by_org_and_correlation` | org, correlation, position                                       | org, correlation, transaction id, position                                | what one run and the runs it caused recorded, in order         |
| `ledger_definition_streams`              | the type of a definition stream, definition streams alone        | the type of a definition stream, definition streams alone                 | the definition streams of one type in every playbook           |
| `ledger_messages_by_org_and_id`          | org, message id                                                  | org, message id                                                           | one event by its id, `get_event`                               |

The read of one run reads each of its two streams through the third index from the cursor on, and merges them, so a page of a run of 100,001 messages costs the same at its start and in its middle, in either order: on PostgreSQL by a term for each stream, joined with `UNION ALL`, and on SQLite by one `SELECT` that names both, as [Facts appended to a scope](#facts-appended-to-a-scope) says why, whose plan walks the index for each name in the order of the position and stops once the page is full, a page of such a run beside 100,000 messages of other streams taking 0.4 to 1.0 ms. Without it, SQLite read such a run through Emmett's unique index on the stream and its version and sorted what it read: on a file holding a run of 100,001 messages and 100,000 messages of other streams of its playbook, a page took 24 ms at the start of the run newest first, 14 ms from its middle newest first and 4.7 ms from its middle oldest first, against 0.23 to 0.42 ms with the index.

The read by correlation walks the fifth index, which leads with the org of the stream, its name's second segment, taken with an expression that answers nothing for a name of fewer than two `/`, `CASE WHEN … THEN substr(stream_id, …) END` over `instr` on SQLite and `CASE WHEN strpos(…) > 0 THEN split_part(stream_id, '/', 2) END` on PostgreSQL, rather than with a regular expression, whose capture took an index of 1,000,000 messages 5.23 s to build on PostgreSQL against 0.83 s with `split_part`, and whose second column is the message's correlation taken from its metadata by an expression, `json_extract(message_metadata, '$.correlationId')` on SQLite and `(message_metadata ->> 'correlationId')` on PostgreSQL, as the other indexes take their keys from the stream name; it keeps the records of the keys the read names, so a page of a run's whole tree costs the same however much else the org recorded, and a tree whose runs are filed under several keys of the org is one walk. On the ledger of [Measurement](#measurement), where every message of a run carries the run as its correlation, a page of the tree of a run of 21 messages took 0.28 to 0.29 ms on SQLite and 1.99 to 2.04 ms on PostgreSQL at the median, a page from the middle of the tree of a run of 100,001 messages 0.26 ms and 1.44 to 2.19 ms, and, behind a million newer messages of other playbooks, 0.26 to 0.31 ms and 1.52 to 1.81 ms, as a page of one run took; through the index led by the org, measured again on 2026-11-13 with Node 26.12.1 at a load average of 3 to 5, 0.35 to 0.36 ms and 1.91 to 2.92 ms, 0.36 to 0.37 ms and 2.41 to 2.43 ms, and 0.34 to 0.35 ms and 1.92 to 2.70 ms, beside 0.35 to 0.36 ms and 2.62 to 2.86 ms for a page of one run of 21 messages in the same run.

The sixth index is on Emmett's table of streams, `emt_streams`, not on its messages: its key is the type a definition stream holds, the part of a stream's name after `playbook/<org>/<playbook>/definitions/`, such as `workflow`, taken with `CASE WHEN … = 'definitions/' THEN substr(…) END` over the playbook key on SQLite and `substring(stream_id FROM '^(?:[^/]*/){3}definitions/([^/]+)$')` on PostgreSQL, and it is partial, holding the streams whose key is not null, so it holds one entry for each playbook and type of definition however many runs and other streams the ledger keeps. `definitionStreams(type)` matches the same expression with `=`, which both planners take as implying the index's `IS NOT NULL`, so the read walks the index; a test reads the plan on each store. Without it the read scans every stream of the ledger.

The list of runs walks the fourth index through the first message of each run, so a page of runs costs the same however many messages the run logs of a playbook hold between two runs. A selection that names `notBeginningWith` leaves out, in the same walk, the streams whose first message is of those types, before the page counts its runs, so the page is full and has no more only once the runs are read; `@on.auto/definitions` leaves out a stream that begins with a caller's cancel, which holds no run, and the ledger itself names no event. Without it, on a ledger of 598,362 messages, PostgreSQL estimated 845 first messages of runs where there were 60,000, and answered a page of runs filtered by status with a sequential scan of the whole table, in 122 to 126 ms; with it, the same pages took 1.4 to 3.5 ms. On SQLite the index holds the first messages alone. On PostgreSQL it holds every message, with its position in its stream as the second column, which the read asks to be 1, because the planner takes no statistics from the expression of an index with a `WHERE` clause: with the index partial, as on SQLite, on the ledger of [Measurement](#measurement), it planned a deep page of failed runs oldest first as a bitmap scan of the playbook's runs and a sort of 49,999 of them, in 73 ms; whole, and with the table analysed, the same page took 4.4 ms.

A selection that names `definitionType` or `name` keeps the runs whose first message's context holds that `definitionType` or `definitionName`, as a run's start, `run_started`, records them: the walk reads the two fields out of the metadata of the first message of each run it examines and the page counts only the runs that hold them, so a page of the runs of one definition is full while the walk finds them, and has no more once the runs are read. On SQLite the walk compares `json_extract(message_metadata, '$.definitionType')` and `json_extract(message_metadata, '$.definitionName')` with `IS`, so a first message without them is no match; on PostgreSQL it compares `message_metadata ->> 'definitionType'` and `message_metadata ->> 'definitionName'` with `=`, a read of plain `jsonb`. Neither reads the first message's data, whose input may be up to 256 KiB, so the fields cost the reading of each first message's metadata alone, a few hundred bytes, whatever the run took; a test reads the plan of the walk on each store, through the fourth index. A selection that names `called: false` keeps, in the same walk and under the same rule, the runs whose first message's context holds no `calledBy`, the runs no workflow's step started: `json_extract(message_metadata, '$.calledBy') IS NULL` on SQLite and `message_metadata -> 'calledBy' IS NULL` on PostgreSQL.

The ledger creates the indexes when it opens, but first looks them up by name in the catalog, `pg_class` on PostgreSQL and `sqlite_master` on SQLite, which takes no lock on the messages table, and creates only those missing, with `CREATE INDEX IF NOT EXISTS`. A start that finds them all issues no `CREATE`. That matters on PostgreSQL, where `CREATE INDEX`, even on an index that exists, takes a lock on the messages table that waits for the appends in flight and holds every new append behind it: with an append left open for 2 s, `CREATE INDEX IF NOT EXISTS` on an index that existed took 2,013 ms, and an append begun 200 ms after it waited 1,821 ms; a start that looked first took 15 to 17 ms with the append still open, and a test checks that such a start is not held up. On PostgreSQL the lookup and the creation run in Emmett's `onAfterSchemaCreated` hook, inside the migration's transaction and its migration lock, so servers that start together build each index once; a start that created any index then analyses both tables, `ANALYZE emt_messages, emt_streams`, so the planner has statistics on the new key expressions at once rather than when autovacuum next analyses the table. On SQLite, which serialises writers, they run just after Emmett's migration, on the same connections, and the hooks a caller passes to `sqliteEventStore` are kept as given; a hook before a commit takes the ledger's own shape, `(messages, { transaction })`, and runs after the inline projections in every append, once for an append to several streams, which hands it every message of the append at once (see [An append to several streams](#an-append-to-several-streams)), and the store takes no inline projections of Emmett's beside its own, `SQLiteStoreOptions.projections` being `never`, since an append to several streams runs the ledger's alone.

Building the five indexes on an existing ledger of 1,197,287 messages took 6.1 s on PostgreSQL 18.6, with the analysis, and 4.2 s on SQLite, about 5.1 s and 3.5 s per million messages at that size, measured as the time the ledger took to open (see [Measurement](#measurement)); measured again on 2026-11-13, the fifth of them led by the org, 6.1 s and 4.0 s. The two indexes led by the org, of the tree of a run and of an event's id, built on a ledger of 1,000,000 messages, took the open 0.95 s on SQLite and 1.67 s on PostgreSQL, with the analysis, and a read of one event by its id then took 0.061 ms on SQLite and 0.528 ms on PostgreSQL at the median of 1,000 (`measure/message-index.ts`, see [Measurement of the read of one event](#measurement-of-the-read-of-one-event)). The read first takes the messages of the org with the id, a `MATERIALIZED` common table expression the planner must answer through that index, and only then matches the keys of the read, so no statistics can send it down the playbook's index instead. On PostgreSQL the build blocks appends for as long, so the first start after an upgrade holds appends that long. The database's user must own the messages table to create them, as the user that created it does.

### How PostgreSQL reaches the indexes

Each index leads with its key, the playbook's, the stream's or the kind's, then the order of the read, so a page walks the index from its cursor. PostgreSQL's planner may walk another index instead: Emmett's own on `(transaction_id, global_position)`, the order of the whole table, filtering out every message of another playbook. It does so when its statistics say the key is common, as for a large playbook, and the cost then grows with the messages other playbooks have written since: a page of the playbook newest first, behind a million newer messages of other playbooks, took 570 ms that way. Each statement therefore matches its key with `= ANY` of a list that holds the key alone, and orders by the key before the transaction id and the position. A list does not make the key a constant to the planner, so ordering by the key is no longer redundant, and the only index that yields that order without a sort is the ledger's own. The same page then took 1.5 ms, and every page of [Measurement](#measurement) behind those million messages costs what it costs before them. SQLite's planner, without statistics, takes the index on the key for an equality, and the SQLite read matches with `=`.

### Order, and the horizon on PostgreSQL

On SQLite appends are serialised, so global positions follow commits, and the read orders by position.

On PostgreSQL a message takes its global position when it is inserted and becomes visible when its transaction commits, so a later position can be visible before an earlier one. The read therefore orders by transaction id, then global position, as Emmett's own batch read does: `readMessagesBatchSQL` in `@event-driven-io/emmett-postgresql` 0.43.0-beta.50, `dist/index.js` lines 1274 to 1289, orders at line 1287, `ORDER BY transaction_id, global_position`, and reads behind a horizon at line 1285, `AND transaction_id < pg_snapshot_xmin(pg_current_snapshot())`.

The ledger keeps that horizon where it is needed, and narrows it:

- **Oldest first**, a reader follows the tail and goes on from its last record, so a message committed late below that record would be skipped for good. These reads stay behind the horizon: a message whose transaction is still open, and every message after it in the order, waits until that transaction ends, then comes in the next page, once.
- **Newest first**, a read pages downward from a position, and a message committed late appears in its next fresh read, so these reads keep no horizon and show every committed message.
- **The horizon is the ledger's own database's.** Transaction ids belong to the whole PostgreSQL server, and `pg_snapshot_xmin` is the oldest transaction open anywhere on it, so an idle write in another database would hide the newest messages of every ledger on the server for as long as it stays open. The ledger instead takes the oldest id among the transactions the read's own snapshot sees in progress, `pg_snapshot_xip(pg_current_snapshot())`, leaving out the ids that `pg_stat_activity.backend_xid` showed writing in another database when the read looked them up, in a statement of its own just before it (`writesOpenElsewhere` in `src/postgresql-reads/recorded-parts.ts`). The lookup comes first because a statement takes its snapshot before it runs: looked up inside the read, a write of another database that ended between the snapshot and the lookup could not be told from one of the ledger's own database, and held back every message written after it began, a message committed before the read among them, as [the measurement below](#measurement-of-the-horizon) counts. A write of another database open at the lookup is left out whenever it ends, one that ended before the lookup is not in the snapshot, and one that began after it holds an id above every message committed before the read began. An id that is in doubt stays in: one of a write of another database that began after the lookup, which can hold back only messages written after the read began, or an id `pg_stat_activity` does not show, such as a prepared transaction's, which no backend holds, since the lookup takes only the rows with a `backend_xid`. A transaction holds an id once it first writes, so a transaction that has only read holds nothing back, which a probe confirmed.

The read never waits for the horizon: it answers at once with what lies below it. A reader that reaches the newest end oldest first, while a write of the ledger's database is open, cannot tell a quiet playbook from one held back.

### The cursor

A cursor is the base64url encoding, without padding, of a JSON array: the playbook key and the position of a record on SQLite, such as `["playbook/acme/sales/","1234"]`; the playbook key, the transaction id and the position on PostgreSQL. Each record carries its own cursor, and `nextCursor` is the cursor of the last record the page examined. A cursor may hold one more part, a whole number, which points inside the record: a read from it begins with that record, in either order, rather than after it, and leaves to the operation that presents the record which of its events to leave out. A cursor that is not such an array, holds a different number of parts than the store keeps, or holds a part that is not a decimal of at most 2^63 − 1 fails the read with `InvalidCursor` of kind `malformed`; one that is well formed but names another playbook fails with kind `of_another_playbook`. The playbook-bound read turns either into `invalid_input` at `/cursor`, with a detail that says which. A cursor is not encrypted: whoever decodes it learns a position of the ledger.

### The version of a record, and a read of heads

Each record carries `version`, its position within its stream, read from Emmett's `stream_position`. A page given `dataOf` loads the data of the records of those types alone and measures the size of those alone: a statement measures a record it examines only when the page wants the record and loads its type, the bound of 4 MiB counts the sizes of the records it loads, and the statement that loads data asks only for their positions, so a page of heads, `dataOf: []`, measures nothing, examines up to its limit and loads nothing (`src/heads/heads-behaviour.ts`, on both stores and the in-memory ledger).

On PostgreSQL a size is `octet_length(message_data ->> 'json')`, which takes the data out of its TOAST table and decompresses it, so measuring a record costs about what loading it costs. `measure-heads.ts` measures the statement that examines a page with `EXPLAIN (ANALYZE, BUFFERS)`, over 20 records of 1,400,000 bytes of text that does not compress in one playbook, 20 reads after 3 to warm:

```bash
LEDGER_MEASURE_POSTGRESQL_URL=postgresql://postgres:ledger-test@127.0.0.1:19632/postgres pnpm --filter @on.auto/ledger measure:heads
```

| The page                                                                | Measuring every record it examines | Measuring the records it loads |
| ----------------------------------------------------------------------- | ---------------------------------- | ------------------------------ |
| a page of heads, `dataOf: []`                                           | 3,598 buffers, 29.6 ms             | 1 buffer, 0.40 ms              |
| the workflow host's follower, which loads the data of definitions alone | 3,598 buffers, 30.4 ms             | 1 buffer, 0.20 ms              |
| every record with its data                                              | 3,598 buffers, 28.1 ms             | 3,598 buffers, 17.8 ms         |

The times are medians, measured on 2026-10-06 on the machine and with the PostgreSQL of [Measurement](#measurement), while the machine ran other work at a load average of about 105, so they are higher than an idle machine gives and vary from one run to the next; the buffers, the pages of 8 KiB the statement touched, do not depend on the load. On SQLite `octet_length(message_data)` reads the length alone, as [The bounds of a page](#the-bounds-of-a-page) says, and the statement measures the same records.

### The bounds of a page

A page examines records in order and ends at the first of its bounds, with `nextCursor`:

- `limit`, 1 to 100 records answered: without a filter, the page examines that many; with a filter of types, it examines up to 1,000 records, or 1,000 runs for a list of runs filtered by the type of their latest message, by the definition type or the name of their first, or by whether a step started them, and answers those that match, possibly none.
- 4 MiB of data loaded, counted from the true size of each record the page loads, before any is loaded: the length of its stored JSON, `octet_length(message_data)` on SQLite, which reads the length alone, and `octet_length(message_data ->> 'json')` on PostgreSQL, the text inside the wrapper, and the `payloadBytes` of its metadata, so a page counts the payloads a reader may resolve as it does the data it loads, and no SQL parses an event's own JSON to measure it (`dataBytesOf` of `src/recorded/sqlite-indexes.ts` and of `src/postgresql-reads/playbook-indexes.ts`; a fill counts the stored size alone, below); only a list of runs filtered by `definitionType` or `name` parses the first message of each run it examines (see [The indexes](#the-indexes)). The first record a page wants is always loaded, so a record larger than the bound ends a page of its own.

A stream is read whole with `Streams.read(stream, after)`, or a page at a time with `Streams.readPage(stream, after, mostBytes)`: the facts after `after` whose true sizes fit `mostBytes`, at least one, at most 1,000, with `through`, the position of the last, and `more`, whether facts follow. It takes two statements, the sizes by position and then Emmett's own read up to `through`, so no page loads more than it was asked plus one fact, which is how a stream an object lends crosses a call between objects.

A page takes at most three statements: when `since` is given, one that finds where the page starts; one that examines the page without loading data; and one that loads the data of the records it delivers, by position. Every statement binds at most 15 parameters, far below the 100 the ledger binds at most in one statement on SQLite, but the statement of a list of runs given both `since` and `dataOf`, which no operation asks of it: 18 on SQLite and 17 on PostgreSQL with `definitionType`, `name`, a status, `notBeginningWith` and a cursor, against 15 and 14 as `list_runs` reads it, counted from the parameters each statement binds; SQLite takes each list, of stored types or positions, as one JSON parameter through `json_each`. None needs a transaction.

### Times and data

`recordedAt` is the time the store recorded a message: SQLite's `created`, `CURRENT_TIMESTAMP` in UTC to the second, given as `2026-10-05T09:00:00.000Z`; PostgreSQL's `created`, `now()`, the start of the append's transaction, to the millisecond. `since` finds the first message the playbook recorded at or after it, by recorded time then position, through the second index; the page starts there oldest first and ends there newest first. SQLite rounds `since` down to the second, so a page from a time may begin with messages of the same second recorded just before it.

The data of a record is decoded as the store's `read` decodes it: on SQLite the stored JSON text, parsed as Emmett's serializer parses it, and on PostgreSQL the `{"json": …}` wrapper, read back by the same `dataAsJsonText`. An event that holds U+0000 is read like any other.

## Recorded content

The ledger keeps content whole beside its messages rather than in them, since every decision on a run's stream, every fill of a projection and every follower reads the messages back: the content of a tool call, its arguments and the tool's answer, and any bytes a capability keeps under their digest. Two tables hold it, with two indexes of its table of heads, created when the ledger opens, each looked up first in the catalog as the playbook's indexes are, so a start that finds them creates nothing: `recorded_content_heads_by_upload`, on the upload, and `recorded_content_heads_expiring`, a partial index on `expires_at` of the heads that have one, `WHERE expires_at IS NOT NULL`, the form of the due indexes of the projections, such as `assets_1_expiring`, so a read of the heads whose content is due reads them alone, however many heads a store keeps:

| Table                     | Key                            | What it holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `recorded_content_chunks` | playbook key, upload id, chunk | the bytes one put read, in chunks of 1 MiB, the last one shorter, as `BLOB` on SQLite and `bytea` on PostgreSQL                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `recorded_content_heads`  | playbook key, digest           | the upload whose chunks hold the content, its size in bytes, the number of chunks, the media type, `kept_at`, when its content was last put, `kept_in`, where its bytes are, `ledger` or `external`, `removing_since`, the mark of a removal under way, written last, and `expires_at` and `erased_at`, when its content expires and when its bytes were erased, in milliseconds as `kept_at` is, which a head holds only where a put gave its content an expiry, as no writer of the runtime does yet (see [Content that expires](#content-that-expires)) |

`content.put(playbook, { stream, mediaType, expected? })` gives the put an upload id of its own, a UUIDv7, and reads the stream through `takenInChunks` of `@on.auto/content` into chunks of 1 MiB, digesting and measuring the bytes as they pass, writing each chunk under its upload once the next has filled, in a statement of its own and so on PostgreSQL in a transaction of its own, since every open write holds back the reads oldest first (see [Order, and the horizon on PostgreSQL](#order-and-the-horizon-on-postgresql)). At the end of the stream it knows the digest and the size, and `requireExpected` refuses a digest or a size other than the one `expected` names as `not_its_digest` or `not_its_size`, as a stream that fails is refused as `stream_failed`, each a `ContentRefused`. A content of one chunk is still in hand then, so when the playbook holds its digest the put writes nothing but the time it was kept and answers the head it holds; a put whose expected digest the playbook holds writes that time first, then reads its stream through the digest and writes nothing more; otherwise the put writes its last chunk, then the head, naming its upload and the time, with `ON CONFLICT (playbook_key, sha256) DO UPDATE SET kept_at = excluded.kept_at`, and reads the head back. The time is `kept_at`, the milliseconds of Effect's `Clock` at the put, which a put of a digest the playbook holds writes again, an `UPDATE … RETURNING` of its head (`headTouched` of `src/content/content-places.ts`), so a head's `kept_at` is when its content was last put, the time a removal judges it by (see [The holders of content](#the-holders-of-content)). The first head written for a digest stands: a put that finds the head of another upload, whether it raced another put of the digest or found the digest kept, deletes its own chunks and answers the head it found, its size and its first media type, so two puts of one digest never write over each other's chunks, a wrong put racing a right one cannot spoil it, and a second media type never replaces the first. A put that fails part way, refused, by its stream or by its store, deletes its own chunks too, and never chunks a head names. Chunks no head names can still remain: those of a process that stopped between a chunk and its head or before its delete, and on PostgreSQL a chunk whose insert was still on its way, on a connection of its own, when its put was interrupted and deleted its chunks. So the ledger sweeps them, as a chore on no clock of its own: both layers provide, beside `Ledger`, the chores of the ledger, `LedgerChores` of `@on.auto/ledger`, whose `sweepOrphans(now)` deletes every chunk no head names whose upload began more than an hour before `now`, by the time a UUIDv7 carries in its first 48 bits, and answers the next time it is due, an hour after `now`, whose `eraseExpired(most)` erases the content whose expiry has passed (see [Content that expires](#content-that-expires)), which nothing calls yet, and whose `heldContentFound(most)` looks for the first `most` contents the facts hold, by the key of their playbook and their digest, where the ledger keeps content now: a head of its own tables where it has no store outside it, and the head of the object in that store where it has one. It decides found as a read decides it, through `found` of the ledger's content: with no store outside it, a head of its own tables, `kept_in` `ledger`, which its reads take; with one, `found` of `keptOutside` of `@on.auto/content`, which asks the store whatever head stands, as its reads do, so a content a store outside kept before heads were, or whose head its own tables took over, is found where the store holds its bytes. A content not found is counted kept in the other place where its head says so, `kept_in` `external` with no store outside it or `ledger` with one, and missing otherwise; a content whose bytes were erased is passed over. It reads one statement of the holds and the heads, `firstHeldHeads` of `src/references/references-table.ts`, and at most `most` heads of the store outside it; a look the store fails, any answer but its object found or not found, fails the chore with `HeldContentUnchecked` and its failure, never counts the content missing, and a ledger opened without the facts that hold content fails it as a defect (`heldContentFoundBy` of `src/content/content-sweep.ts`, `src/content/held-content-found-behaviour.ts`, on both stores). The server asks it as it starts, and refuses to start on any it finds. Whatever runs the ledger calls the sweep on its own clock, and nothing in the ledger forks a timer: the server's workflow host performs it in its wake-up, at the first and then whenever it is due (see [Due rows](../workflow-host/README.md#due-rows)). The sweep is maintenance: a sweep that fails is logged as an error, never fails the chore, and is due again an hour on. A close waits for a sweep under way to finish before it closes the store, so it never leaves the sweep's connection open or runs the sweep on a closed store. A ledger opened with a content store of its own, `content` among the options of `ledgerLayer` and `postgresqlLedgerLayer`, a `ContentStore` of `@on.auto/content`, keeps the bytes of its content there and their heads in `recorded_content_heads`, `kept_in` `external`, and its table of chunks stays empty (see [The holders of content](#the-holders-of-content)); its chore sweeps its own chunks no head names first, as a ledger without such a store does, and then that store, so the chunks of a database that kept its content itself before it was given a store, which a removal through the store leaves named by no head, go too. The ledger's own reads and puts take only the heads of its own chunks, `kept_in` `ledger`: a digest a store outside it kept is not found, as [A deployment that already has content](../../docs/self-host/object-storage.md#a-deployment-that-already-has-content) says, and a put of it, whole or by its digest, writes its chunks and takes the head over, its upload, size, chunks and media type, `kept_in` `ledger` and no mark, so the content is read again; a store outside it reads its bytes whatever head stands, so the content it kept is read again once it is given that store again, with the media type of the head the ledger took over, which a put of the digest then answers too (`src/content/switched-stores-behaviour.ts`, on both stores); the server opens it so when `CONTENT_STORE_URL` names an object store, whose adapter, [`@on.auto/object-storage`](../object-storage/README.md), sweeps the uploads its puts left behind. A put that streams a request body ends within the 300 s Node gives a request, `server.requestTimeout` of the server's `createServer`, well within the hour. `content.get(playbook, sha256)` reads the head and answers `{ stream, bytes, mediaType }`, or nothing for a digest without a head or whose bytes were erased. The stream reads one chunk of the head's upload each time it is pulled, so neither a put nor a get holds the whole content in memory, and digests what it reads through `verifiedStream` of `@on.auto/content`, the check the object store's reads go through too: a chunk that is missing, or bytes that are not those the digest names, fail the stream as a defect, as the ledger fails on a fact that no longer decodes, and it hands over the last chunk only once the size and the digest are checked, so no reader takes every byte of a content that is not its digest's. `content.getPart(playbook, sha256, asked)` reads the head and streams only the chunks the range covers, every chunk but the last holding exactly 1 MiB, the first cut to start at the range's first byte and the last to end at its last, held to the part's length by `measuredStream` (`readPartOn` of `src/content/content-places.ts`). `content.getHead(playbook, sha256)` reads the head alone and answers its size, its media type and its `kept_at` as `{ bytes, mediaType, keptAt }`, with `expiresAt` and `erasedAt` where it holds them, or nothing for a digest without a head in the ledger's own tables (`keptHeadOn`), and a ledger whose content is kept outside answers the head it keeps for the store, by `read` of its `ContentHeads`; a reader of a payload tells by it whether a content it did not find was kept within the hour. The content is keyed by the playbook and the SHA-256 of its bytes, so the key is the content's own address; a text is kept as its UTF-8, so its digest is the SHA-256 of the text the fact names. The digest is Node's own, `createHash('sha256')`, through `sha256Digest` of `@on.auto/content`. A chunk travels to the store as the hex of its bytes, through `unhex` on SQLite and `decode(…, 'hex')` on PostgreSQL, since the SQL builder binds a byte array as JSON. It comes back in the shape its driver answers, a `Uint8Array` or an `ArrayBuffer`, which the standard byte APIs take as the same bytes, and the read takes either through one function, `viewOf` in `src/content/content-places.ts`, which hands on a `Uint8Array` view of the bytes without copying them; `sqlite3` 6.0.1 and `pg` 8.23.1 both answer a Node `Buffer`, a `Uint8Array`. A fact carries a digest only when its content was kept, so a read never joins content to a fact that kept none. The port keeps no removal: a content is removed only through `Ledger.removeUnheld`, when nothing holds it (see [The holders of content](#the-holders-of-content)). Beneath it, `removalWithin(playbook, sha256, before)` of the ledger's store deletes, within the transaction the removal holds, the head, only where its `kept_at` is before `before`, `RETURNING` the upload it named, and then that upload's chunks, and answers `removed`; where it deleted no head it reads whether one stands, and answers `fresh` for a head kept at or after that time and `removed` for a digest without a head, which deletes nothing and fails nothing (`keptRemovedWithin` of `src/content/content-places.ts`). So no read finds a removed content and no chunk of it stays, even on PostgreSQL where a put of the digest commits its head between the two statements: that head is not the one deleted, and keeps its chunks; and a put whose `UPDATE` of `kept_at` commits first leaves the head the `DELETE` then reads again fresh, as `READ COMMITTED` reads a row a statement waited for, while a `DELETE` that commits first leaves the put no head to touch, and the put writes the content again. A put whose head a removal took between its write and its read back answers what it put and deletes its own chunks, as a put that found another upload's head does. A stream already reading the content fails as a defect at the first chunk it had not read, `The content kept under <sha256> is missing its chunk <n>`, after the chunks it read before (`src/content/content-behaviour.ts`).

These tables and their indexes are part of the layout of the ledger, so a change to them raises `ledgerLayout` and ships the step, in `ledgerLayoutSteps`, that carries a database of the layout before forward (see [The layout of the ledger](#the-layout-of-the-ledger)).

`measure/recorded-content.ts` runs `measuredContent` of `measure/content-measurement.ts` on each store. It puts the answers the tests keep, `answerOfAbout` of `@on.auto/content/testing`, of 100 bytes to 20 MB of JSON, three times each, the second time as it is and the third with its digest expected, and reads each back and parses it; it puts the 64 MiB of bytes the tests generate, `generatedStream`, as a stream the same three ways and streams them back, their digest checked. The content is made before each put is timed, and SQLite is opened as the server opens it, with a page cache of 8 MiB and no memory map. ### Content that expires

A put may give its content an expiry, `expiresAt` of `ContentToKeep` of `@on.auto/content`, in milliseconds as `kept_at` is; a put that gives none keeps its content for good, as every put of the runtime does today, since no writer passes one yet. It is the pattern Forgettable Payloads (Mathias Verraes, _Eventsourcing Patterns: Forgettable Payloads_, 2019) on the content the ledger already keeps by Claim Check (Hohpe and Woolf, _Enterprise Integration Patterns_): a fact names its content by its digest and size, the bytes are what is forgotten, and the fact, its holds and every projection stay as they were. The expiry and the erasure live on the head, the one mutable record of a content, so nothing reads or writes a fact for them.

- **The later expiry, and none wins.** A head holds `expires_at`, the later of the expiries its puts gave, and none once any put gave none, so a content any put kept for good, such as a run's output whose bytes are a tool's answer, is never erased by the expiry of another, whatever the order of their puts. A put that gives no expiry sets it to none; one that gives an expiry keeps the later of the two, `CASE WHEN expires_at IS NULL OR <the put's> IS NULL THEN NULL WHEN expires_at < <the put's> THEN <the put's> ELSE expires_at END` (`laterExpiry` and `expiryKept` of `src/content/content-tables.ts`); so a put that gives none, every put today, runs the statement of the release before with `expires_at` set to none and the erased head left out: the `INSERT … ON CONFLICT … DO UPDATE` of a put whole with `WHERE erased_at IS NULL` (for a store outside, `OR removing_since IS NOT NULL`, so a head under a removal's or an erasure's mark is still answered) and `RETURNING`, so the put knows whether it wrote, the `UPDATE` of a put of a digest the playbook holds with `AND erased_at IS NULL`, and the read back after a put whole, which leaves an erased head out. None of them names an indexed column the release before did not, but `expires_at`, whose partial index SQLite's program passes over for a head with none, and which, staying none, does not by itself keep PostgreSQL's update from being heap-only. Where that first statement wrote nothing, as for an erased head, a second runs: an `INSERT … ON CONFLICT … DO UPDATE` with no guard and no filter on `kept_in`, which applies the whole rule to whatever stands by then and inserts where nothing does. In the ledger's own tables an erased head, whether its own tables or a store outside kept it, is taken over with the put's upload, size, chunks, media type and expiry, and one of its own that another put kept meanwhile keeps its upload and takes the later expiry, none winning; for a store outside, the `CASE`s take an erased head's size, chunks, media type and `kept_in` from the put and keep a standing one's. So two puts of one content that meet its erased head at once, one for good and one with an expiry, keep it for good whichever statement runs first, and a ledger opened without its store outside keeps again a content whose head that store kept and erased. A put whose expiry is no whole number of milliseconds is a defect of its writer, refused before anything is kept (`expiryOf` of `@on.auto/content`). A put with its digest expected applies its expiry at the touch, before it reads its stream, as it always moved `kept_at`: so a put refused after it, its stream failing or of other bytes, has already lengthened the expiry, or kept the content for good; it never shortens one, so it never erases what was kept.
- **An erased head names an upload of no bytes.** The record of an erasure points the head's `upload_id` at a new upload id, which names no chunk, and deletes the chunks of the upload it named. So no head names the chunks of an erased upload, the sweep of chunks no head names is the statement of the release before, and it takes them where a stop came between the record and their delete. It reads the heads through the index of their upload, `recorded_content_heads_by_upload`: on SQLite and an object through that index alone, as a covering index; on PostgreSQL through the index and each head's row, since a `DELETE` that joins another table also takes the row identity (`ctid`) of each row it joins, which no index holds, so no index-only scan can serve it, for the release before's statement as for this one (`EXPLAIN (VERBOSE)` shows the heads' `ctid` among what the join outputs). A put that keeps the content again writes chunks under an upload of its own, which no delete of an erasure names.
- **The erasure.** `eraseExpired(most)` of `LedgerChores` erases at most `most` contents whose expiry is at or before the time Effect's `Clock` reads, the soonest first, of every playbook of the store, and answers `{ erased, more }`: how many it erased, and whether it read as many as it may, so more may be due. It reads them with `expires_at IS NOT NULL AND expires_at <= now`, the predicate of the partial index `recorded_content_heads_expiring` word for word, `ORDER BY expires_at LIMIT most`, so the index can serve it in its order, needing no scan of the table and no sort, however many heads the store keeps (`src/content/expired-heads-behaviour.ts` reads the plan on SQLite, PostgreSQL and an object). SQLite and an object read it so. PostgreSQL chooses by cost: the test reads its plan with sequential scans and explicit sorts switched off for the session, `enable_seqscan` and `enable_sort`, which keep the planner from either wherever another plan exists (PostgreSQL's _Planner Method Configuration_, and _Examining Index Usage_ for the method), and the plan then reads the index in its order under the limit, so the index can serve the read with neither; on a table of a few rows with no statistics, as in the test, the planner left to itself reads the index as a bitmap and sorts what it finds; every other statement of the erasure is by a head's key or an upload's.
  - **Its own content** (`ownExpiredErasedOn` of `src/content/content-sweep.ts`): an `UPDATE` records the erasure, `erased_at` set and `expires_at` cleared, where the head still names the upload it read and is still due, and points the head at a new upload; then the chunks of the upload it read are deleted. A put racing it keeps its own upload, so the delete never takes its chunks, and a pass that stops between the two leaves chunks the sweep takes: no window remains here.
  - **Content in a store outside** (through `keptOutside` of `@on.auto/content` over `externalHeadsOn`): it marks the head, `removing_since` the time the clock reads, where the expiry has passed and no removal or erasure marked it within ten minutes; it deletes the bytes only while that mark is younger than `erasureDeletesWithinMs`, half the ten minutes, by the clock read just before the delete, and waits for the delete no longer than what is left of that half; then it records the erasure in one statement that asks the mark is still its own. Its mark grown older before the delete is let go, and nothing is deleted. A delete that fails lets go of the mark, so the content stays whole and due. A delete that has not ended is given up: it records nothing and keeps its mark, since the store may still apply it, so a put waits on the mark as on a removal's, and is refused as `unavailable` after 5 s, until the mark is ten minutes old; then the next erasure takes the mark over, or a put finishes it.
  - **A put that meets a stale mark** on a head whose expiry has passed finishes it as an erasure: it marks the head as its own, deletes the bytes as the erasure does, records the erasure, and only then keeps the content again, so a stop anywhere between leaves the content read as erased, never as missing. A stale mark on a head with no expiry passed is a removal's, which the put finishes as it always did.
  - **What window remains**: for the bytes in a store outside alone, a delete held on its way to the store, or by the store, for more than five minutes after the erasure stopped waiting for it, where a put kept the content again once the mark was taken over; a pause of the process longer than what was left of the five minutes, between the clock read and the delete it sends; and the clocks of two processes of one store more than five minutes apart, since each reads the age of a mark by its own. The bytes a put places again are the same bytes under the same key, and `delete` of `Bucket` takes keys alone, so nothing a delete could be conditioned on tells the bytes the erasure meant from the ones placed again; a lease of the mark by time is what the store allows, and only a key, or a version, of each keeping, a change of how content is kept in the store, would close it.
  - Each step asks again that the content is due and the step's own, so a pass may stop anywhere and run again, and two at once, of one store from two processes, erase each content once; one ledger runs one at a time, with its sweep, and a close waits for it. A ledger opened without a store outside erases the content of its own tables alone, so content an earlier opening kept in a store outside stays due until the ledger is given that store again, and every pass walks past it: the index gives those heads, `kept_in = 'ledger'` passes them over, and their number does not shrink until then. That happens only after a deployment switched its store outside off.
- **What must be true from the release whose writers first give an expiry.** From then on, a put that meets a stale mark on a head whose expiry has passed runs an erasure, whether or not anything schedules the chore. So, from that release and not only from the one that schedules the chore:
  - the owner accepts in words the window that remains for the bytes in a store outside, above, or the store keeps each keeping under a key or a version of its own; the window is not silent, since the hosted runtime's check of held content alerts on bytes a fact holds that are gone;
  - a bound is set on how long a put may wait when it finishes a stale mark, an open duty: today it waits for the store's delete for as long as is left of the five minutes, `Effect.timeoutOption(left)` in `erasureFinished` of `keptOutside`, where a put on a request should wait no longer than it may wait for anything else;
  - the self-hosted servers that share one store keep their clocks within seconds of each other, as NTP or the platform's time service does, since each judges the age of a mark by its own clock ([Keep content on object storage](../../docs/self-host/object-storage.md#permissions) says so);
  - the step that schedules the chore does what the next point says.
- **What the caller of the chore must do.** Nothing calls the chore yet: no host chore, alarm or timer performs it, and the server's wake-up performs `sweepOrphans` alone. The step that schedules it must: catch, log and pass over a head it cannot erase, as `orphansSweptOf` does for the sweep, so one head whose delete fails, or whose key names no playbook and so stays first in order, never stops every pass; size its batch and the store's delete against the 5 s a put waits on a mark, `removalWaitMs`, and against the alarm's own budget, since the deletes of a pass run one after another under the chore's lock; and read when the next expiry falls due, which is not built, with the same predicate, `expires_at IS NOT NULL`, so the index answers it.
- **What reads an erased content.** A read, whole or of a part, answers nothing, and a put of its digest keeps it again as new, its bytes written or placed again with the media type and the expiry of that put, of one chunk, of several or with its digest expected. `getHead` answers `expiresAt` and `erasedAt` beside the size, the media type and `keptAt`, so a reader tells a content erased on purpose, or past its expiry with its bytes gone, from one that is lost: a payload reader answers it `PayloadErased`, never `PayloadMissing` (see [Payloads kept outside a fact](../operations/README.md#payloads-kept-outside-a-fact)). The append refuses a fact that names as its payload a content whose bytes were erased, as it refuses one with no head, and a removal of an erased content nothing holds deletes its head, as of any content.
- **Nothing is read at open.** The erasure reads what is due when it runs, by the predicate of the partial index, and the puts, touches and reads go by the head's key, as before.

`expiringContentBehaviour` and `interleavedErasureBehaviour` of `@on.auto/content/testing` and `erasedContentBehaviour` of `@on.auto/operations/testing` are the suites: the later expiry and none winning on every path of a put, and for two puts of an erased content at once, either held until the other kept it, an erasure that leaves the head saying when and reads nothing, a content kept again after it, batches across playbooks, two erasures at once, the refusals; through a store outside, a put that meets an erasure, a content kept for good while an erasure ran, a failed delete, a delete given up once its mark is half the ten minutes old, which keeps its mark and takes nothing of the bytes a put places after the erasure that took the mark over, a put that meets a stale erasure's mark, whole and with its digest expected, which records the erasure first so the content reads as erased meanwhile, an erasure whose mark another took over while it deleted, which records nothing, and bytes gone before their record; and a held content erased with its fact and its hold standing, an erased payload refused by the append and read as erased. The ledger runs them on its own content and on a store outside it, on SQLite, PostgreSQL and an object, with its own cases of the plan, of the puts of a head that stands, which set its upload only where a put whole of several chunks of the ledger's own takes the head over, as before, of the sweep, which reads the heads through the index of their upload, of a stop of its own erasure between its record and its delete, of a put that keeps a content again while its own erasure is on its way, of a head of its own tables erased through a store outside, of a head of a key that names no playbook, of two puts of an erased content, one for good and one with an expiry, the one held after its first statement while the other keeps the content whole, in its own tables and outside it, in both orders, and of a put in its own tables of a content whose head a store outside it kept and erased (`src/content/erased-puts-behaviour.ts`); the in-memory ledger and the content kept in memory run them too, and the object over R2 in the hosted runtime.

## The holders of content

A content is kept under its playbook and its digest, so two records that keep identical bytes keep one content, and a removal for one of them would take the bytes of the other. So the ledger knows every record that holds a digest, and a content is removed only when nothing holds it.

**What a fact holds.** A fact's schema declares the content it holds and releases beside its shape, in the fourth argument of `factOf(type, data, context, { content })` of `@on.auto/operations`: `content: { holds?: readonly JsonPointer[]; releases?: 'all' | readonly JsonPointer[]; payloads?: readonly { sha256: JsonPointer; bytes: JsonPointer }[] }`, each pointer, as RFC 6901 writes one, naming a field of the fact's data that carries a SHA-256 digest, but for one token RFC 6901 does not have: `*` stands for every element of the list at that place, so `/parts/*/sha256` names the digest of each part. `payloads` names the pairs of a payload kept outside the fact (see [Payloads kept outside a fact](../operations/README.md#payloads-kept-outside-a-fact)), the digest and its size, two members of one object, so a pair with `*` names the digest and the size of the same element; a fact holds each digest its pairs name as it holds one of `holds`, and a fact whose pair names a value that is not a SHA-256 in lowercase hex, or one beside no whole number of bytes, is a defect of its writer, which fails its append (`payloadsNamed` of `src/held-content/held-digests.ts` of `@on.auto/operations`). The declaration is an annotation of the fact's schema, so it travels with the schema through a union, a reader of an earlier shape and the server's composition, which gives the ledger, beside the schemas of the facts it reads, the holders of the same schemas, `factsKnownWith(declared)` of `packages/server/src/composition/known-holders.ts`, which answers the schemas `factSchemasKnownWith(declared)` of `known-facts.ts` makes and `contentHoldersOf` of them, so a fact a capability declares on runs, an extension's among them, declares what it holds the same way, and `providedCapabilityOf` refuses an extension whose declaration does not decode. `contentHoldersOf(schemas)` refuses a type two schemas declare otherwise, a pair of `payloads` that is not two members of one object, and a schema whose facts both keep payloads and release every hold of their stream, since `releases: 'all'` would leave a payload unheld while a fact names it; it compares the facts of one schema, the union a stream's decider is written with, and not two schemas whose facts share a stream, so a stream's facts are declared in one union. A fact with `holds` adds one hold to its stream for each pointer that names a digest, 64 lowercase hexadecimal digits, and none for a pointer that names no field or another value; a fact with `releases: 'all'` lets go of every hold of its stream, and one with `releases: [pointers]` of one hold of each digest its pointers name, never below none; a fact that does both releases first. A fact of a type that declares nothing holds nothing (`heldAfter` of `src/held-content/held-digests.ts` of `@on.auto/operations`).

**Where the holds are kept.** `content_references_1` is a projection of the ledger's own, one row for each stream of a playbook and each digest it holds, keyed by `playbook_key`, `stream`, the stream's name within its playbook, `<kind>/<id>`, and `sha256`, with `held`, the count of its holds, and the index `content_references_1_by_digest` on `(playbook_key, sha256)`. A row whose count falls to none is deleted, so a digest is held where any row of its playbook names it with `held` above none; a stream of an org holds nothing. The ledger keeps the table when it is opened with `holders`, `ledgerLayer({ fileName, holders })` and `postgresqlLedgerLayer({ pools, holders })`, inside the append of every fact of a type that declares content, in the append's own transaction (`keepingReferences` of `src/references/references-folds.ts`): it reads the rows of the digests the append's facts name, or every row of the stream where one releases all, folds the facts over them, and writes the rows that changed in upserts of as many rows as the store binds. The rows of a stream change only in an append to that stream, which the stream's version serialises, so no fold of another append writes them; but on PostgreSQL the fold takes, before it writes any row, the lock of each digest whose row the append changes, `pg_advisory_xact_lock(hashtextextended('content_references_1:<playbook key><sha256>', 0))` (`keyLocks` of the dialect), held until the append commits, the lock a removal takes: every playbook and digest of the append once, in the order of the playbook and then the digest, across all its streams, so an append to several streams and any other append lock the digests they share in one order (see [An append to several streams](#an-append-to-several-streams)); SQLite's one writer serialises them. When the ledger opens with `holders` and does not find the table, it makes it and fills it, in one transaction, from the facts of those types on every stream of every playbook, 256 at a time in the order they were appended, and drops a table of an earlier version, as it fills a keyed projection (see [Creating and filling a table](#creating-and-filling-a-table)); a change to what a type of fact holds is a new version, `content_references_2`, which the next server fills. A scrub folds the holds of the scrubbed fact's stream again from every fact of the stream, inside the scrub's transaction and under the same locks, so a scrubbed shape that no longer carries a digest lets go of its hold (`referencesRefolded`). A ledger opened without `holders` keeps no such table and removes no content: its removal fails as a defect, since it cannot tell a held content from an unheld one.

**The removal.** `Ledger.removeUnheld(playbook, sha256)` answers `removed`, `held` or `fresh`. In one transaction, under the lock of the digest on PostgreSQL and SQLite's one writer, which its transaction takes as it begins, `IMMEDIATE`, it reads whether a row of the playbook holds the digest, and answers `held`; otherwise it removes the content only where its `kept_at` is more than `keptContentGraceMs` of `@on.auto/operations`, one hour, before now, by Effect's `Clock`, and answers `removed`, or `fresh` for a content kept within the hour, and `removed` for a digest never kept (`unlessHeldOn` of `src/references/content-references.ts`). The ledger's own content is removed by `removalWithin` of its tables in that same transaction, its head and then its chunks, with no request outside the database, so it needs no mark: a put of the digest either commits its `kept_at` before the removal reads it, and the removal answers `fresh`, or finds no head after it, and writes the content again. Content kept outside the ledger is removed in two transactions around the delete of its bytes, as the next paragraph says, so no transaction waits for a request of the store.

**Content kept outside the ledger.** A ledger given a content store of its own, an object store, keeps the head of each content it puts there in `recorded_content_heads`, with `kept_in` `external`, its size and its media type, an `upload_id` of the put that wrote it and no chunks, so the time a content was last kept is the ledger's for every store, and the bytes are the store's (`externalHeadsOn` of `src/content/external-heads.ts`, the `ContentHeads` of `@on.auto/content` that `keptOutside` of that package runs its puts and removals over). A put stages its bytes in the store first, under an upload of its own, since only their end gives their digest; then one statement keeps the head, `INSERT … ON CONFLICT (playbook_key, sha256) DO UPDATE SET kept_at = …`, which moves `kept_at` only where no removal has marked the head and answers the row either way, the head this put wrote, whose `upload_id` is its own, or the one that stood; then it places the bytes under their digest, conditional on no object being there, or, where the head stood and the store holds its object, discards its upload, so a put of a digest the playbook holds costs one statement of the ledger and one look at the store, and no object is written again to keep it. A put whose expected digest the playbook holds moves the head's `kept_at` with one `UPDATE … RETURNING`, looks that the store holds the object, and reads its stream through the digest alone. A read streams the object with the media type of its head where one stands, the media type a put answers, and with the object's own where none does. A removal is three steps: in one transaction, under the lock of the digest and after the look for a hold, an `UPDATE` marks the head, `removing_since` set to now, only where it is unmarked and kept before the hour, or marked more than `removalLastsMs`, ten minutes, before, by a removal that stopped, and where no head stands an `INSERT … ON CONFLICT DO NOTHING` writes a head of the mark alone, with no `upload_id`, no size and no media type, so a content the store holds with no head, as one kept there before the heads were, is removed too; it commits, deletes the object outside any transaction, and in a second statement deletes the head whose mark it wrote. A put that finds the mark waits, polling every `removalPollMs`, 100 ms, until the head is gone, and then keeps the content as new, placing its bytes again; past `removalWaitMs`, 5 s, it is refused as `unavailable`, a `ContentRefused` a caller asks again, and a mark older than ten minutes is the mark of a removal that stopped, which the put finishes itself, the delete and the head, before it keeps the content. A removal whose delete fails lets go of its mark before it fails, `removing_since` set back to nothing where it is still its own, and the head of its mark alone deleted, so a put after it keeps the content at once and the next removal marks it again. So a put that keeps the head before the removal marks it leaves the removal `fresh`, and one after it waits until the bytes are deleted and then writes them, with two limits. A removal that stalls for more than ten minutes between its mark and its delete is taken for one that stopped: a put after those ten minutes finishes it and places the bytes again, and the stalled delete, when it goes on, takes those bytes, so a hold the put's fact then records names bytes the store no longer holds. And a put whose bytes take more than the hour to reach the store, after it kept their head, meets a removal that takes the head, so the bytes it then places stand with no head: they are read, and held where a fact holds them, until a removal of their digest, which marks a head of its own and deletes them. A removal that finds a mark it did not write answers `removed`, as the content is on its way out. `interleavedRemovalBehaviour(entry)` of `@on.auto/operations/testing` holds a removal at its delete, with a store whose delete and placing can be paused (`pausableStore` of `@on.auto/content/testing`): a put during the paused delete, whole or by its digest, waits and then keeps the bytes whole, and the hold its fact records then answers `held`; a removal while a put's bytes are on their way answers `fresh`; two removals stalled after their marks are finished, one by a put and one by a removal, once their ten minutes ran out, and take back no mark as they fail at last; a removal whose delete fails lets go of its mark, and of the head of its mark alone, so a put keeps the content at once and a removal after it removes it; and the bytes a store holds with no head are removed, while a put that meets that removal waits. The in-memory ledger runs it, the ledger on SQLite and on PostgreSQL over an in-memory store and over `@on.auto/object-storage`'s fake bucket, and over a real S3-compatible server.

The in-memory ledger runs it, the ledger on SQLite and on PostgreSQL with its own content and with its content in an in-memory store, a ledger in memory, on SQLite and on PostgreSQL whose content is on the fake bucket of `@on.auto/object-storage`, and a ledger on SQLite over a real S3-compatible server. On PostgreSQL a test holds the lock of a digest while a removal waits and answers `held` once the fold holding it commits, and while a fold waits for a removal that holds it (`src/postgresql/references-on-postgresql.test.ts`); `src/references/references-behaviour.ts`, on both stores, fills the table of a database recorded before, drops an earlier version, finds the table again, keeps an empty one for no holders, and refuses a removal without them.

### Payloads kept outside a fact

A fact may keep a payload, a value it carries for a person such as a run's input, in the playbook's content, naming it by its digest and size (see [Payloads kept outside a fact](../operations/README.md#payloads-kept-outside-a-fact) of `@on.auto/operations`). It declares where with `content: { payloads: [{ sha256, bytes }] }`, a pair of pointers that may hold `*` in the same places, read element by element, and each payload it names is one hold of its stream, as a `holds` pointer is; nothing releases one. So nothing expires a kept payload: the ledger removes its content only after a scrub has taken its digest from every fact that names it, recorded by the erasure the scrub appends (see [A fact scrubbed in place](#a-fact-scrubbed-in-place)), and a removal asked for the digest then finds nothing else of the playbook holding it and its hour passed. The ledger's chores remove no content a fact holds: only chunks no head names, and the uploads a content store left unplaced (see [Recorded content](#recorded-content)).

- **Two checks at the append.** The store's holders must count, for each fact, exactly the bytes its schema's declaration names, `payloadBytes` as `eventAppenderOf` measured it, or the append fails as a defect of the writer, so a ledger opened without the schema of a fact that keeps a payload refuses the fact rather than recording it with no hold (`requireHeldAsMeasured` of `src/appends/payloads-declared.ts`). And inside the append's transaction each digest a fact names through `payloads` has a head that is not being removed and whose bytes were not erased in `recorded_content_heads` of its playbook, one statement for the digests of the append, or the append fails as a defect: a payload is put before the fact that names it (`requirePayloadsHeaded` of `src/references/references-folds.ts`). A fact of an org's stream holds nothing and is not checked, as no content of an org is kept.
- **What a refill reads.** A type that declares `payloads` alone is read by a refill or a refold of the holds only where its metadata names `payloadBytes`, since a fact without it keeps no payload, so the old facts that carry their values inline are passed over; and a batch ends at 16 MiB of stored size as well as at 256 facts, the length of the stored data alone (`storedBytesOf`), since a refill reads no payload and loads only what is stored, measured by a statement of sizes before the facts are loaded, which lists as many facts as the batch before showed fit and is followed by a read of the facts up to the last it takes, as the fill of a projection keyed by its mapping lists and reads below. A refill reads no content.
- **A new way of holding needs no new version.** A change to what a type of fact holds is a new version of the table, so that facts already recorded gain the holds of the new declaration; a declaration that adds a way of holding which no recorded fact uses needs none, as no recorded fact holds a payload, and `content_references_1` stays.
- **A scrub** rewrites `payloadBytes` with the data, in the same statement, so a scrubbed fact that keeps a payload no longer, or keeps another, is measured as it now is.

`payloadHoldsBehaviour` of `@on.auto/operations/testing`, part of `unheldContentBehaviour`, runs these on every store: a page counts the payloads its facts name, a scrub measures a fact again, a digest with no head and a fact the holders do not declare are refused and leave nothing, and a payload on an org's stream is recorded and held by nothing; `src/appends/payload-bytes-behaviour.ts`, on both stores, reads the metadata back against the pinned shape, the scrub's rewrite both ways, a refill in batches of 16 MiB, and a stream in pages.

## Kept secrets

The ledger keeps the rows of the secret store of [`@on.auto/secrets`](../secrets/README.md) apart from its facts and from its content: what the runtime must hold to act for someone, such as a key a person pasted or a token minted for them, which no fact of a stream may carry, since every reader of a stream reads its facts. It keeps the rows alone and seals nothing: a value reaches it as its keeper holds it, sealed under a data key of its own that the store's custodian wraps, as that package's README sets out under [Sealing](../secrets/README.md#sealing), or not at all, where a secret manager keeps it and the row holds the name and the version of the value there, as its README sets out under [The keeper](../secrets/README.md#the-keeper), so the ledger knows no key and neither its database nor a backup of it holds a value anyone can read without the custodian's or the manager's. The rows are not part of the `Ledger` port; each opening answers an `Effect` of the `SecretRows` port of `@on.auto/secrets`. On a SQLite file, `sqliteLedgerFile(fileName)` of `@on.auto/ledger/sqlite3` opens the ledger and its rows together: its `ledgerLayer(options)` is the ledger's layer, which `ledgerLayer({ fileName, … })` builds too, and opens the file's one pool, and its `secretRows` answers the rows on the pool the open ledger holds, so the file has one writer, in whose queue a secret's write waits its turn behind the ledger's, and the rows' reads go to the pool's readers, which wait for no writer. A pool of their own would be a second writer on the file, which SQLite does not let write beside the first: a secret's write that met the ledger's writer holding the file for more than dumbo's 5 s would fail with `SQLITE_BUSY`, as `src/secrets/sqlite-ledger-file.test.ts` shows when its rows are opened on a pool of their own. The rows close nothing, since the ledger's layer owns the pool, and while no ledger of the file is open they are refused as a defect, `LedgerNotOpen`, that names the file; the server opens them once the ledger is open. Whether a statement of the rows can run inside a transaction of the ledger depends on the store, as the end of this section sets out. On `:memory:` the rows are in the ledger's own private database. `postgresqlSecretRows({ pools })` of `@on.auto/ledger/postgresql` answers the rows on PostgreSQL, opened on connections of their own from the settings the ledger is opened from, once the ledger is open, as the server opens them, since PostgreSQL's row locks let many connections write at once. `sqliteSecretRowsOn(optionsOf)` of the main entry answers the rows on a pool of their own on any of Emmett's SQLite drivers, as `sqliteEventStore` opens the store on one, for code that opens the ledger on a driver of its own, such as a Durable Object's SQLite, one connection that runs each statement at once; it migrates the ledger's schema on that pool first, which finds the layout the ledger wrote and creates nothing. On PostgreSQL the rows open a pool of two connections, from `pools` or any `(bounds) => SecretConnections`, on the database the ledger migrated, and log a connection they lose as the ledger logs one of its own. One table holds them, `kept_secrets`, created with `CREATE TABLE IF NOT EXISTS` by the same schema step that creates the content tables, on SQLite and on PostgreSQL, through the same dialect, and looked up first in the catalog as they are, so a start that finds it creates nothing:

| Column          | What it holds                                                                            |
| --------------- | ---------------------------------------------------------------------------------------- |
| `id`            | the secret's id, a UUIDv7, the table's primary key                                       |
| `version`       | 1 when the secret is kept, one more at each replacement                                  |
| `kept_at`       | when the value it holds was kept, an ISO 8601 time in UTC, as text                       |
| `claimed_until` | until when the row is claimed by whoever renews it, the same kind of time, or `NULL`     |
| `ends_with`     | the ending of the secret the runtime may show, or `NULL`                                 |
| `kept_by`       | the keeper that holds the value                                                          |
| `held`          | what the keeper handed back, for the `ledger` keeper the sealed value                    |
| `wrapped_key`   | the value's data key as the custodian wrapped it, or `NULL` for a keeper that wraps none |
| `kid`           | the kid of the custodian's key that wrapped it, or `NULL` for a keeper that wraps none   |

The table is part of the layout of the ledger, as the content tables are (see [The layout of the ledger](#the-layout-of-the-ledger)).

Each operation of the port is one statement, every value bound: `keep` an `INSERT`; `read` a `SELECT` that answers `claimed_until` only while the claim is open; `replace` and `claim` one conditional `UPDATE` each with `RETURNING`, under the version read, the claim's also under no claim being open; `endingsOf` one `SELECT` of the ids named, and nothing asked for no ids; `forget` a `DELETE` that returns the holding it deleted; `heldBy` a `SELECT` of a keeper's rows, under a kid where one is named and after an id where one is named, `ORDER BY id` with the `LIMIT` asked; and `reheld` a conditional `UPDATE` of the four columns of the holding, only while the row's version, `kept_by` and `held` are the ones read and its `wrapped_key` and `kid` too, compared through `COALESCE(…, '')` so that a holding that has none compares alike on both stores. Every time the rows write or compare, `kept_at`, the claim's end and the moment a claim is judged open, is read from Effect's `Clock`, the clock the times of the facts are read from, so a test drives it with `TestClock`. A failure of the database is a defect, as it is for the ledger.

A secret must never join a transaction of the ledger: a refreshed token records what its provider has already done and must outlive an append that fails, and a secret forgotten must stay forgotten. A kept secret is a consistency boundary of its own, never part of an append's, and each statement of the rows is meant to be an autonomous transaction. On PostgreSQL that holds by the connection: the rows send each statement to a pool of their own, a transaction of the ledger runs on a connection of the ledger's pools, which the rows never use, and dumbo's PostgreSQL build keeps no transaction in an async context. On a ledger file what holds is narrower. The rows' own statements are never routed to a transaction's connection: each write of theirs takes its turn in the one writer's queue, so it runs after every transaction of the ledger that took its turn before it, and is kept whether that transaction commits or is rolled back. That keeps a secret out of the ledger's transactions only as long as every other write takes its turn in the queue too, and one write does not: a write of the ledger issued by an Effect fiber that was woken inside a transaction of the ledger keeps that transaction's async context, so its own statements and transactions run on the writer's connection at once, outside the queue, and a secret written by anyone while such a transaction is open runs inside it and is lost if that transaction is rolled back, though its write answered success. That is a leak of the ledger's own, and this does not close it. Nothing on a file wakes a fiber inside a transaction of the ledger today; on `:memory:` a consistent read runs the reads of a capability's Effect inside one, so a fiber woken there carries its context. The rows' statements stay in the queue because of how dumbo routes a statement. Its `sqlite3` build keeps the connection of the transaction that code runs in in a Node `AsyncLocalStorage`, and runs a statement issued in that async context on that connection at once, ahead of the queue: an ambient transaction. A statement of the rows issued from inside a transaction of the ledger would join it, and so would one issued by a fiber that such code wakes, which resumes in that context and keeps it for as long as it runs. `sqliteLedgerFile` suppresses the ambient transaction for the rows, as .NET's `TransactionScopeOption.Suppress` and Spring's propagation `NOT_SUPPORTED` do: it captures the async context with `AsyncLocalStorage.snapshot()` before it makes the file's pool, whose own context dumbo makes inside `dumbo(...)`, and issues every statement of the rows inside that capture. On a file a read of the rows goes to the readers; on `:memory:` it runs on the one connection at once, as every read outside a transaction does there, so it finds only what was committed of the rows unless a transaction that went around the queue is open with a write of theirs inside it. A transaction of the ledger that waits for a secret write of its own waits for a write that cannot start before it ends: the write fails at the queue's limit of 30 s, dumbo's `maxTaskIdleTime`, as a defect that says `Task was not started within the maximum waiting time`, and keeps nothing, a lock wait time-out ending a wait that nothing else would end. The transaction holds the one writer for those 30 s and then commits or fails as its own code decides, and every other write of the file queued meanwhile waits behind it, so any of them that waits 30 s fails at its own limit too. Nothing refuses such a wait at once, since it cannot be told from a fiber merely woken inside a transaction: the async context is all there is to see, and it is the same in both. On `:memory:` a consistent read is a transaction on the one connection, so a secret written and waited for inside one fails the same way. The writes of the rows share the writer's queue with the ledger's, so beside the 30 s a write that finds 1,000 tasks waiting is refused at once with `Too many pending tasks. Please try again later.` `src/secrets/sqlite-ledger-file.test.ts` holds the writer inside a real append, through the `onBeforeCommit` of the file's opening, and holds on a file and on `:memory:` that a secret is kept, once the transaction ends, when its write is started inside one that is rolled back, when a fiber woken inside one writes it, and when such a fiber writes it later while a later one is open and is rolled back, and that a write the transaction waits for is refused at 30 s and keeps nothing; with the statements issued in their callers' context, each of the first three lost the secret while its write answered success. On a Durable Object, `sqliteSecretRowsOn` is not covered by this guarantee and is unchanged: the ledger and the rows it opens there are two pools over the object's one storage, whose dumbo build has no queue and no async context, so a statement of the rows runs at once, and nothing here keeps it out of a transaction of the ledger that the object has open at that instant. `sqliteLedgerFileOn`, which builds a ledger file on any of Emmett's SQLite drivers, is not exported, since both the file's one writer and the suppressed transaction rest on the queue and the async context of the `sqlite3` build, which another driver, such as a Durable Object's, does not have. A ledger file records one open ledger at a time: built twice at once, its second build takes the record and the first one's close clears it, so its rows are refused as `LedgerNotOpen` until it is built again; the server builds it once, and a second ledger file of the same path would be a second writer whatever the record held.

## Webhooks received

A connection's service may answer a request by a webhook it signs (see the [API's README](../api/README.md#answers-a-service-signs)), and the specification it signs by gives each webhook an id, the same on every attempt to send it, which a receiver keeps to take a webhook once. The signature covers the id, the time and the body, never the address, so the ledger keeps each id of each connection with what took it, and a webhook sent again to another address finds the id taken. It keeps them in one table no fact names, `webhooks_received`, beside the kept secrets and part of the layout as they are:

| Column       | What it holds                                                                               |
| ------------ | ------------------------------------------------------------------------------------------- |
| `org`        | the org of the connection                                                                   |
| `connection` | the connection, by the name its address gives it                                            |
| `webhook_id` | the id the webhook carried, its `webhook-id`                                                |
| `taken_for`  | what took it, `<playbook>/<run id>` for an answer                                           |
| `kept_until` | until when the id is kept, in milliseconds since 1970: past it, the webhook's time is stale |

The key is the first three, and `webhooks_received_kept_until` indexes the last. `ReceivedWebhooks` is the port, `taken(receipt)`, which keeps an id for what takes it first and answers what holds it, in two statements, every value bound, each sent as a command since each writes, the `INSERT` answering its `RETURNING` rows as a command does: a `DELETE` of every row whose `kept_until` has passed by Effect's `Clock`, then an `INSERT` that, where the id is held, updates nothing and returns what holds it, `ON CONFLICT … DO UPDATE SET kept_until = webhooks_received.kept_until RETURNING taken_for`, so two webhooks of one id at once are one taken and the other answered the first's holder. On a ledger file, `sqliteLedgerFile(fileName)` of `@on.auto/ledger/sqlite3` answers it as its `receivedWebhooks`, as it answers its `secretRows`: on the pool its open ledger holds, each statement taking its turn in the one writer's queue, issued in the async context captured before the file's pool is made, so each is a transaction of its own, and an id taken stays taken whether a transaction of the ledger open meanwhile commits or is rolled back, with the one exception the section on kept secrets names for a write of the ledger that goes around the queue; refused as `LedgerNotOpen` while no ledger of the file is open. `sqliteReceivedWebhooksOn(optionsOf)` of the main entry answers it on a pool of its own, as on a Durable Object, and `postgresqlReceivedWebhooks({ pools })` of `@on.auto/ledger/postgresql` on PostgreSQL, on a pool of two connections of its own, opened once the ledger is open, as the secret rows are. `receivedWebhooksBehaviour` of the testing entry holds both stores to the same behaviour.

## The names of definitions

The ledger keeps, beside its streams, the name each definition holds, in `definition_names_1`, so that a name is held by one definition at a time among the definitions of its type in its playbook, across the streams of many definitions. It is a lookup table owned by the write side and updated in the append's own transaction, the form Marten ships as natural keys, "a separate lookup table that maps natural key values to stream ids", "Updated transactionally alongside event appends" ([Natural Keys](https://martendb.io/events/natural-keys.html)), and Axon describes for set-based validation, where "these lookup tables are always owned by the command side only and should not be exposed by using a Query API" ([Set Based Consistency Validation](https://www.axoniq.io/blog/2020set-based-consistency-validation)). Oskar Dudycz, of a unique key on a snapshot "updated in the same transaction as the appended event", writes: "Let's be honest, however, that this is a pragmatic trick. It is not a "by the book" solution." ([How to ensure uniqueness in Event Sourcing](https://event-driven.io/en/uniqueness-in-event-sourcing/)), the book's being a reservation of the name by events of its own; kept in the same database and the same transaction as the fact that claims the name, it leaves no moment at which the fact stands without its claim, or the claim without its fact. The table answers no read: what turns a name into a definition for a reader, and every list of definitions, is a read model's.

| Column                                    | What it holds                                                                                                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `playbook_key`, `definition_type`, `name` | The name, unique among the definitions of its type in its playbook, the table's key: the playbook's key, `playbook/<org>/<playbook>/`, the definition's type and its name                  |
| `definition_key`                          | The key of the streams of the definition that holds the name, `definition/<org>/<definition>/`, unique in the table, `definition_names_1_by_definition`, since a definition holds one name |
| `status`, `has_triggers`                  | How the definition stands, `active`, `paused` or `retired`, and whether it starts runs on its own, which the bounds on a playbook's definitions count                                      |

The ledger makes the table as it opens, empty, as it makes `webhooks_received`, and it is part of [the layout of the ledger](#the-layout-of-the-ledger), brought by step 22 and filled from the facts by step 23. It keeps the table when it is given `definitionNames`, a `DefinitionNames` the package that owns definitions declares, as it is given `holders`: the stored types that change a name, `types`; the streams that hold names, `holdsNames(stream)`, a fact of any other stream changing none; the key of the definition a fact is about, `definitionKeyOf(message)`, which the declaration gives, never the ledger from a stream's name, since several definitions may share a stream; the name a definition holds after a fact, `nameAfter(held, message)`, from the name it held and the fact, `'released'` for a fact after which it holds none, or `undefined` for a fact that changes none; the `Conflict` that refuses a name another definition holds, `takenBy(claimed, holder)`; and the bounds, `bounds`, each the fact types it checks, which names it counts, the most a playbook keeps of a type and the `Conflict` that refuses one more, `beyond(claimed, type, countedBefore, most)`, all in the words of the package that declares it.

The keeper judges the names of an append at once, at the end of the append, as one change, by the judgement of `@on.auto/operations/definition-names`, which the in-memory ledger of `@on.auto/operations/testing` runs too, so the two cannot disagree: it groups the append's facts of those types by definition, takes the lock of every definition in the order of their keys, reads the row each holds and folds its facts through `nameAfter` to the name it holds at the end, then takes the lock of every name claimed, in the order of the playbook and the name, and of every playbook and type whose names change, in that order, and only then reads. A name another definition holds refuses the append with the conflict `takenBy` answers, unless that definition gives it up in the same append, so a name one definition gives up another may claim in it, whatever the order of their keys; a bound refuses it when, after the append, a definition one of its checked facts leaves counted stands among more counted definitions of its playbook and type than the bound, with the count before the append. Then it removes the row of every definition the append changed and writes the name each holds at the end, so a name given up is free the moment it is given up, as Marten's natural keys are: "the previous value immediately becomes available for another stream to claim". A definition retired keeps its row and so its name; one released holds none. Each row is read under the lock that guards it, and every lock in one order across every append: a definition's row under its definition's lock, and the holders of the names it claims and the definitions of a playbook's type, which the bounds count, under the locks of those names and that playbook and type, taken after every definition's lock; so the order is the definitions', then the names', then the playbooks', each in the order of its key, the rule the PostgreSQL manual gives against deadlocks (see [An append to several streams](#an-append-to-several-streams)), and two appends that claim names in opposite orders wait for each other and never meet in a cycle: a test holds a name's lock, appends two facts that claim it and another name in the other order, and finds the other name already locked while the append waits (`src/definition-names/names-on-postgresql.test.ts`). The count a bound judges is read by a statement of its own once the lock of its playbook and type is held, and an append to PostgreSQL runs at its default isolation, `READ COMMITTED`, under which each statement sees what committed before it began, so of two appends that each add the last definition a bound allows the second counts the first's and is refused; a database whose `default_transaction_isolation` an operator set to `repeatable read` would keep each name, which the table's key holds, but not each bound. The table's key stands behind the locks, and a key broken all the same is met as a version conflict, which the decision loads and decides again. SQLite serialises every append and locks nothing. A release that declares no names keeps the table empty, and a fact of any type changes no row (`definitionNamesBehaviour` of `@on.auto/ledger/testing`, on both stores and on an object's SQLite, which runs `namesAtThePortBehaviour` of `@on.auto/operations/testing` through each store's decisions, the suite the in-memory ledger runs too, and beside it what a store alone shows: a refusal outside a decision a defect, an empty table when no names are declared, and an append to several streams that frees a name for another and one refused beyond a bound naming its stream; `src/definition-names/whole-append-names-behaviour.ts` and `definition-names-behaviour.ts`).

### Step 23, the names filled from the facts

Layout step 23 fills `definition_names_1` from the facts a store holds, so a store recorded before the keeper holds the names it would have kept. It is a step in code (see [A layout step](#a-layout-step)), `definitionNamesFilledBy(names, mostBytes)` of `src/definition-names/names-filled.ts`, given the same declaration the keeper is given, its bounds left out, since a bound judges an append and not what a store already holds. In the step's own transaction it makes the table and its index where they are not there yet, `IF NOT EXISTS`, and, where `emt_streams` is there, lists the store's streams in it, one row a stream, keeps those the declaration's `holdsNames` names, and for each lists the position and the stored bytes of its facts of the declared types by the stream's key, groups them into pages of at most `mostBytes`, at least one fact a page, 4 MiB on a Durable Object and 16 MiB elsewhere, as the fill of a projection counts them, and reads each page in one statement, in the order of the stream, each statement with the store's partition and no archived fact, as every other read of `emt_messages` has; it folds each page by the judgement the keeper runs, `definitionsInTheAppend` and `judgedOf` of `@on.auto/operations/definition-names`, over what the pages before it left, so that only the names held, one row a definition, outlive a page. A definition's facts are all on one stream, so the order of the streams changes no row. It reads no fact of a stream that holds no names, such as a run's. Then it deletes every row of the table and writes the name each definition holds at the end. A store with no `emt_streams`, one whose first opening stopped after it wrote its layout, holds no fact and is left with an empty table. The rows are the keeper's over the same facts, whatever the pages: the step's tests keep a store by the keeper, empty the table and fill it again with pages of 4 MiB and of one fact, and find the same rows. Before it writes, the step requires every definition the facts name to hold a name, or to have given one up, and no name of a playbook and type to be held by two definitions; a store that breaks either is refused, the step's transaction rolled back, and the store stays at 22, in words that say how many: `The names of definitions were filled with 1 definition whose facts give it no name; the store stays at the layout before`. The step writes no fact and moves none, and the key of each row is the one the declaration gives (see [The names of definitions](#the-names-of-definitions)). `src/definition-names/names-step-behaviour.ts`, on both stores and on an object's SQLite, holds the fill, the store whose first opening made no table of its facts, the store carried from 21 in one opening, and both refusals.

On an object it runs as the object opens, inside `blockConcurrencyWhile`, and reads one row a stream and the facts of definitions, each once. Measured on 2026-11-13 in the hosted runtime's local Workers pool on an Apple M4 Max, on objects of made-up facts, the median of three: the first opening of the ledger, 22 to 23, took 4 ms for an object of 1,831 facts, 26 of them saves of 13 definitions, 0.28 MiB, the shape of the largest store of the nightly copy that day, reading 2,602 rows; 14 ms for one of 15,000 facts in the same share, 220 saves, reading 4,612 rows, 1,850 of them the rows of its streams; and 650 ms, at most 666 ms, for one of 15,000 saves of 16,384 bytes, 233 MiB, read in 60 pages; an opening at 23 took 2 ms whatever the store held. So its cost grows with the store's streams and its facts of definitions, not with its facts of runs.

## Keyed projections

The ledger keeps a table for each projection it is opened with, one row per key, inside the appends of the streams of the kinds the projection names: a `KeyedProjection` of `@on.auto/operations`, which names its table, its version, whose streams it folds, the stream kinds it folds, the stored types that change a row, its columns, its indexes, the key of the row a fact changes, the columns its reader advances and the mapping from a row and an event to the next row, and which the package that owns what a row means supplies at composition: `ledgerLayer({ fileName, projections })` and `postgresqlLedgerLayer({ pools, projections })`. The ledger knows the streams of a playbook, named `<playbook key><kind>/<id>` (see [The playbook key](#the-playbook-key)), and the streams of an org, named `org/<org>/<kind>/<id>`, and nothing of their events. A projection names the streams it folds in `scopes`, `playbook`, `org` or both, and folds a playbook's streams alone when it names none, as every projection of the server but what callers have seen of the organization's activity does; a fact of a stream of a scope it does not name changes none of its rows (`foldsStream` and `rowKeyOf` of `@on.auto/operations`, through `addressedStreamOf`, which reads a stream's scope, prefix, kind and id). A row keeps the address of its streams, its org and, for a playbook's streams, its playbook: `ProjectedKeyedRow` is `{ org, playbook?, key, row }`, with no `playbook` for a row of an org's streams. A projection of runs names the kind `runs` and keys its row by the stream's id, the run's; a projection may name other kinds and key its row by what a fact carries, through `keyOf(event, stream)`, as `topicRows` of `@on.auto/operations/testing` does over two kinds for the ledger's tests. The outcomes of runs are one such projection, which the ledger declares itself over the run outcome mapping it is given as `runOutcomes`, and which keeps its own grouped read, `Ledger.readRunOutcomes(playbook, window, selection)`, beside the generic ones.

The organization's activity is four more, which `@on.auto/activity` supplies and the server composes, and which `list_activity` reads together for its caller, beside the newest 100 facts of the org's `playbooks` stream, which it reads itself, since that stream has no id and no projection folds it. Each is a table of its own because a fact changes one row of a projection, and a run that succeeds both makes its own row and resolves its definition's broken one. The new items, `activity_1`, fold a playbook's `runs` and `definitions`: a run no other run started that succeeded, keyed `runs/<run id>`, and each version of a definition saved, `definitions/<type>/<name>/<version>`. The open requests of the activity, `activity_requests_5`, fold its `runs`, keyed by the run's id, with who started the run and whom the request waits on, a person by id where its party names one, from a request that takes an answer to its answer, its expiry or the end of its run, the run of a workflow's call included. The broken definitions, `activity_broken_1`, fold its `runs` and `definitions`, one row per definition keyed `<type>/<name>`: a run no other run started that failed, or was rejected but neither cancelled nor left unanswered, at the definition's current version opens it, and a run at that version or a later one that succeeds, a new version saved or the definition's retirement resolves it. A request or a broken definition that is resolved folds to `open: false` and stays in its table, closed, and `list_activity` never serves it. What each caller has seen, `activity_seen_1`, folds the org's `activity` streams, `scopes: ['org']`, one row per caller keyed by the caller's id: the place they marked everything seen through, when, and the newest 1,000 items they marked seen after it. Each time a caller marks items seen, one `activity_seen` is appended to `org/<org>/activity/<id>`, the id being the version 5 UUID of the caller's id, since an id such as `person:<subject>` holds characters a stream name does not.

The comments of a playbook are one more, `comments_1`, which `@on.auto/activity` supplies too, since an open comment is a row of the activity as much as a thing of its own. It folds a playbook's `comments` streams, one per comment, `playbook/<org>/<playbook>/comments/<id>`, the id a version 7 UUID the runtime gives the comment, and keys its row by the stream's id: `comment_made`, whose `made_by` is the caller's `{ id, name }` as `definition_created` keeps `created_by`, writes the row, its `address`, `text`, `by`, `by_name`, `at` and `open: true`, and `comment_resolved` closes it with `resolved_at`, `resolved_by` and `resolved_how`, and leaves it in its table, where `list_comments` reads it as history. The activity's comment rows are the open rows of the same table: `list_activity` reads them as it reads a playbook's other tables, each keyed `comments/<id>`, with the first line of `text` as its `message`, `by_name` beside `by`, `address` as its `about`, and the definition and the run that address names as its `definition` and `run_id`, read from the address and not looked up, so no table holds a comment twice, `activity_1` keeps its shape, and the fact that resolves a comment takes its row out of the activity. A comment counts for a caller in `comments` while it is open, made by someone else, after their `through` and not marked seen, as a `new` row does.

### Inline projections

An inline projection of Emmett 0.43.0-beta.50 handles the messages of an append inside the append's own transaction: on SQLite in the `onBeforeCommit` of the append, on PostgreSQL inside the transaction of `appendToStream`. It is handed the messages of the types it names, in their stored form, with their stream's name and position and the message id the ledger gave each, and a projection that throws fails the append, which keeps nothing, the rows the projection changed included; a failed append runs no projection. On PostgreSQL Emmett skips a projection that has a name when it cannot take its advisory lock or its status is not active, so the ledger's projections have none and always run. On both stores a unique-constraint error inside a projection would surface as a version conflict, in an append to one stream and in an append to several alike (see [An append to several streams](#an-append-to-several-streams)), retried three times and then `conflict` `concurrent_change`; a table has no constraint but its key and is written with an upsert, so it never raises one. An inline projection may instead refuse the append, as the keeper of the names of definitions does (see [The names of definitions](#the-names-of-definitions)): it throws an `AppendRefused` of `src/refusals/append-refused.ts`, which Emmett hands back as it is, since it is no constraint error, and the decision fails with the `Conflict` the refusal carries, the append keeping nothing. A refusal is known by its tag, `append_refused`, and its shape, its `detail` and its kind, never by its class, as a version conflict is, so one raised by another copy of the package, or across a boundary where an error does not travel as itself, is known too.

On PostgreSQL, where appends to different streams run at once, two of them can fold into one row, a row keyed by a mapping over several streams or by the stream of a projection of several kinds; each would read the row before the other committed and write a row folded from that, so the later write would drop the earlier fact. So a fold locks every row it folds before it reads one: first `pg_advisory_xact_lock(hashtextextended('<table>:<prefix><key>', 0))`, which covers a row not yet written, then `SELECT … FOR UPDATE` of the row, which also waits for an advance of it in flight, each held until the append's transaction ends; the rows of one append are locked once each and in the order of their prefix and key, so two appends lock the rows they share in the same order (`rowsLocked` of `src/projections/projection-statements.ts`, the statements `rowLocks` of the dialect). A deadlock with work that locks in another order, such as a scrub's fold, is retried as a version conflict. SQLite serialises every append and locks nothing. A test holds such a row while two appends fold into it, and while a scrub and an append fold into it, and both fail without the locks (`src/postgresql/advances-on-postgresql.test.ts`).

`src/projections/inline-projection.ts` is the facility: an `InlineProjection` names its stored types and handles the messages of an append, each `{ stream, type, data, context, id, position }`, with the executor of the append's transaction. `src/projections` builds every table from its declaration: the statements that create a table and its indexes, read a row and write rows with an upsert keyed by the playbook and the row's key (`projection-statements.ts`), the inline registration (`projection-keeping.ts`), the fill (`projection-fill.ts`) and the reads (`projection-reads.ts`), over a dialect of each store, `sqliteProjectionDialect` and `postgresqlProjectionDialect`, which says how it names column types, reads a whole number back as a number, lists the streams of a projection's kinds and their messages, or the messages of those kinds in the order they were appended, and decodes their data. For each message of its types on a stream of its kinds, a projection decodes the message's data as the store's reads decode it, the JSON object as written on SQLite and the `{"json": …}` wrapper read back on PostgreSQL, and its context from its metadata, finds the key of the row it changes, the stream's id or what `keyOf` answers, and nothing when `keyOf` answers `undefined`, reads that row if there is one, gives the row and the message, `{ id, position, type, data, context }`, to the mapping, and writes the row it answers, or nothing when it answers `undefined`. A fill reads the metadata column beside the data, so a rebuilt row folds the same context. That is one read and one write in the append for each such message, for each projection, and on PostgreSQL, before the reads, two lock statements for each row they fold, its advisory lock and its `SELECT … FOR UPDATE`; and nothing for the messages of any other stream kind or type. A mapping must never throw.

A projection may declare the columns its reader advances, `advanced`, a list of `{ column, setBy }`: `Ledger.advanceRow(projection, address, key, { set, when })` writes the columns of `set` of one row of a playbook or an org, and no other, in one `UPDATE` of its own, outside any append, only while the columns of `when` still hold the values given, the compare-and-set a reader makes against a marker its fold owns, and does nothing for a row that is not there or that no longer holds them; a column the projection does not declare fails the call. The fold's upsert writes every column when it makes the row, and otherwise each advanced column only when the fact's type is one of that column's `setBy`, leaving the rest as they stand, `SET` naming only the columns it writes, so a fold cannot undo an advance of a column it does not set: on PostgreSQL the fold's lock of the row waits for an advance in flight, and its upsert updates the row as the advance left it. A test on PostgreSQL holds an advance open while a fold waits for the row, and fails with an upsert that writes every column. The fill never applies an advance, since no fact stands for one, so a rebuilt row holds what the folds set.

A store opened without a projection neither creates its table nor writes it, and its reads answer no rows, no groups and no due time rather than reading a table that may not be there, so every writer of a run stream must write through a store that carries the projections. Today that is the server's ledger, through which the workflow host settles runs and the interaction capability records its deliveries too; the workflow host's own stores write only the logs of runs.

### The columns and the reads

A table holds `playbook_key` and `row_key`, its key, and the projection's columns. `playbook_key` holds the prefix of the streams the row folds: the playbook key, `playbook/<org>/<playbook>/`, for a playbook's streams, and `org/<org>/`, `streamPrefixOfOrg`, for an org's, which no playbook key equals, since every playbook key begins `playbook/`; the column keeps its name, so a projection that folds an org's streams keeps the shape, and the version, of its table, and the table of every projection made before keeps its own (`streamPrefixOfAddress` and `addressOfStreamPrefix` of `@on.auto/operations` turn an address into its prefix and back). The other columns are text; a whole number, `INTEGER` on SQLite and `bigint` on PostgreSQL, read back as a number; or a boolean, `INTEGER` 0 or 1 on SQLite and `boolean` on PostgreSQL; each nullable. An index named `<table>_<index>` is on the playbook key and the index's columns, `row_key` among them when it names it, each kept `NULLS FIRST` on PostgreSQL, the order SQLite keeps nulls in, so that a read of a playbook's rows walks it forwards oldest first and backwards newest first on both stores; or on its columns alone for one across playbooks, in each store's own order, which the reads of due rows, the soonest first, walk; and partial, `WHERE <column> IS NOT NULL`, when it says so. `readProjectedRows(projection, address, query)` reads a page of a playbook, `{ org, playbook }`, or of an org, `{ org }`, by its conditions, each `=`, `>` or `<` in the statement: a column equal to a value, `{ column, equals }`, the key `row_key` among them, which the key serves, or a number or text column strictly after or before one, `{ column, after }` or `{ column, before }`, which a column that is not set never meets, ordered by its columns and the row's key, `NULLS FIRST` oldest first and `NULLS LAST` newest first on both stores, and goes on after the row values it is given with a comparison of row values, which finds nothing for a value that is not set, so a page that goes on orders by columns that are always set; `countProjectedRows` counts the rows of a playbook or an org by the same conditions; `readDueRows` reads the rows of every playbook and every org whose column is set and has come, each under its address, and none under a prefix that names neither, the soonest first, which a partial index across playbooks serves; and `nextDueOf` answers the smallest value of the column after the time it is given, which the same index serves. Every value is bound, and every column a read names must be the projection's or `row_key`, and a comparison must compare a number with an integer column or a text with a text column, never a boolean, or the read fails (`comparedColumnOf` of `@on.auto/operations`, which the in-memory ledger checks too). A text is compared and ordered by the database's collation on PostgreSQL and byte by byte on SQLite, so a reader that pages or compares on text keeps to texts both order alike, such as texts of lower-case letters and digits alone, since a collation such as `en_US.UTF-8` orders `a` before `B` and, with the C library of Linux, passes over punctuation such as `-` and `/`.

### Several rows under one key

A projection may keep several rows under one key, as a junction table keeps one row for each link between two things: a `ChildRowsProjection` of `@on.auto/operations` declares `rowsAfter(rows, message)` in place of `rowAfter`, is handed every row of the key the fact changes, by its child key, and answers every row of the key after the fact, or `undefined` when the fact changes nothing. Its table gains `child_key`, and its key is `(playbook_key, row_key, child_key)`. Each fold replaces the rows of its key, a `DELETE` of the key's rows and an insert of those it answers, in as many statements as the values a statement binds allow, `childRowsInAWrite` (`src/child-rows/child-row-statements.ts`); on PostgreSQL the fold locks the key as a fold of one row does, its advisory lock and `SELECT … FOR UPDATE` of every row under it. Every path of a projection folds such a table: the inline fold, the fill by stream and in order, which folds the facts of each key of a batch over the rows the key held before, and the fold again after a scrub, which folds the key from no rows. A read answers each row with its `child`, orders after `row_key` by `child_key`, goes on after a page by both, and takes a condition on `child_key`, a text. Its reader advances no column, since an advance names one row by its key alone (`checkedProjection`). `src/projections/projections-behaviour.ts` holds the rows kept, replaced, dropped and read, on SQLite, PostgreSQL, an object's SQLite and in memory, `src/projections/projection-table-behaviour.ts` their fill as the ledger opens, and `refoldedRowsBehaviour` of `@on.auto/operations` their fold again after a scrub.

### Stream projections

A stream projection is a read model of one kind of a playbook's streams, kept by an inline projection with a checkpoint per stream and brought up to date by catch-up from that checkpoint: the pattern of a read model rebuildable from its events (Greg Young's "CQRS Documents"), kept by Marten's and Emmett's inline lifecycle, inside the append's transaction, with the checkpoint stored beside the rows it guards and a catch-up that reads on from it, as EventStoreDB's catch-up subscriptions read on from theirs. A `StreamProjection` of `@on.auto/operations` names its kind, the ids of the streams of that kind it folds under each playbook, such as `definitions` and the types of definition the runtime serves, its tables, keyed projections of one row or several under a key (see [Several rows under one key](#several-rows-under-one-key)), each of the projection's own version, and the counts that check it once built; the package that owns its meaning declares it, and the composition gives it to the layers as `streamProjections` (`checkedStreamProjection` refuses a table of another version or of other streams). Its tables follow the ledger's naming, `<name>_<version>`, and its checkpoints are `<name>_checkpoints_<version>`: one row a stream of a playbook, `(playbook_key, stream, folded_through)`, the stream's name after the playbook key and the position the rows are folded through.

- **Inline, while contiguous.** The append of facts at positions p to q of one of its streams reads that stream's checkpoint, after its advisory lock and `SELECT … FOR UPDATE` on PostgreSQL; when it is p − 1 the append folds the facts into every table and writes q, and otherwise folds nothing and leaves the stream to catch-up. An append to several of its streams locks and reads the checkpoint of each first, in the order of the streams' names, and then folds the facts of the streams it found contiguous table by table, each table locking the rows they change in one pass, so no append holds a row of the projection while it waits for one of its checkpoints (see [An append to several streams](#an-append-to-several-streams)). A fact at or below a checkpoint is never folded again, so a retried append, a release that appended without folding and a catch-up beside an append all leave each fact folded once (Hohpe and Woolf's Idempotent Receiver). The tables together name every type their streams hold; a fact of a type none folds is not handed to the fold, which then finds the stream ahead of its checkpoint, and catch-up reads on past it.
- **Catch-up, a page at a time.** In one transaction a page takes the stream's checkpoint lock, lists the sizes of the facts after the checkpoint, takes as many as the store fills at once, `mostBytesFilledAtOnce`, 4 MiB on a Durable Object and 16 MiB elsewhere, counted in stored bytes as the fill counts them, and at least one, reads those facts in one statement, folds them and writes the checkpoint; then the next page, listing as many as the page before showed fit, as the fill does, until the stream is at its head (`src/stream-projections/catch-up.ts`). Each page commits on its own, so a page that fails loses that page alone, and the next read goes on from the checkpoint the last page wrote; no fact of a page is held once the page ends.
- **Before every read.** `readProjectedRows` and `countProjectedRows` of a table of a stream projection under a playbook first compare, in one statement, each checkpoint of the playbook with the version of its stream in `emt_streams`, read by its key, and catch up every stream behind, so a reader never reads rows behind the facts; a read under an org, which folds no playbook's streams, compares nothing.
- **Reset.** A checkpoint ahead of its stream, a fact of one of its streams scrubbed in place (inside the scrub's transaction), a reader that asks, `resetStreamProjection(name, address)`, or checks that fail once it is built, delete the playbook's rows and checkpoints in one transaction, and the next read builds them again from the facts. Two declared checks run after a read that built anything, each one statement that reads no fact's data: for each count the projection declares, the rows of its table and the facts of its types up to the checkpoints (`counts_differ`); and for each group-wise maximum it declares, the rows of one table that are not, on the columns it names, the row of their group with the greatest value of a column in another table (`groupwise_maximum_differs`), the rows holding the group-wise maximum of a column found by grouping and joining back, which needs no index of its own (`src/stream-projections/build-checks.ts`). If a check still fails once the rows are built again, the rows are emptied again, the read dies with `StreamProjectionRefused` of `@on.auto/operations`, and a circuit breaker opens for that read model and playbook (Michael Nygard, "Release It!", 2007; Martin Fowler, "CircuitBreaker", 2014): for an hour every read of its tables is refused the same way without a statement or a build, then one read builds and checks once more, the breaker opened again before it, so that no other read builds beside it, nor after it should it throw, and closed if the checks pass (`src/stream-projections/guarded-builds.ts`). The breaker is the ledger's own, in memory, one for each read model and playbook, and goes with the process; since the rows that failed are emptied, a new process builds and checks again rather than answer from them. Nothing is ever answered from rows that failed their checks. The in-memory ledger runs the same two checks on every read of such a table, and dies with the same refusal.
- **As the ledger opens.** When any of its tables is missing at its version, the ledger makes them all, empties them, and drops the tables of earlier versions, in one transaction, and fills nothing: each playbook is built on its next read. A shape change is the next version of every table and of the checkpoints together. A release that keeps no stream projection ignores the tables and appends without folding; the checkpoints fall behind, and the release that keeps it catches up on its next read. The tables are a projection's own, made as the ledger opens, so they take no step of [the layout of the ledger](#the-layout-of-the-ledger).
- **Logs.** Every build logs `A read model was brought up to date from its facts` with the stream, the checkpoint it began from and the one it reached, the facts read, their stored bytes, the pages and the milliseconds it took; every reset its reason, `checkpoint_ahead`, `counts_differ`, `groupwise_maximum_differs` or `asked`; a disagreement after a build again is an error. Each names ids, counts, sizes, positions and durations alone.

`src/stream-projections/stream-projection-behaviour.ts`, `stream-recovery-behaviour.ts` and `stream-rebuild-behaviour.ts` hold, on SQLite, PostgreSQL and an object's SQLite, the rows kept inline, built by catch-up and built a fact a page all alike; a page that fails and the read after it; the facts a release without the projection appended; a checkpoint ahead; a reset asked; a scrub; a new version; counts that disagree; and a row that is not the greatest of its group. `src/postgresql/stream-catch-up-on-postgresql.test.ts` holds an append that meets a catch-up's page on PostgreSQL, and `services/hosted-runtime/src/platform/ledger-store.workers.test.ts` a catch-up on an object over more than four times 4 MiB of facts with no statement reading more than 4 MiB. In memory, `memoryLedger` keeps a stream projection's tables inline, its streams alone, and builds a playbook's rows again from its log when asked to reset.

### Creating and filling a table

When the ledger opens with a projection, it looks its table up by name in the catalog, as it does its indexes, and does nothing more when it finds it. When it does not, it creates the table and its indexes, fills it by replaying every run stream of the store, drops the tables of earlier versions, such as `run_outcomes_4` and below, and analyses the new one, all in one transaction, so that a fill that is interrupted, by a mapping that throws or a process that stops, leaves nothing behind and is done again at the next open. On SQLite this runs after Emmett's migration and the indexes, on the same connections; on PostgreSQL in `onAfterSchemaCreated`, inside the migration's transaction and under its advisory lock, so that servers that start together fill the table once. Emmett's migrator waits 10 s for that lock, `defaultDatabaseLockOptions` in `@event-driven-io/dumbo` 0.13.0-beta.56, `dist/pg.js` line 673, less than the fill of a large ledger takes, and the typed options of Emmett's store and of its `schema.migrate()` offer no longer wait. So the ledger takes the same lock first, in `onBeforeSchemaCreated`, inside the migration's transaction (`migrationLockTakenWithin` in `src/postgresql/postgresql-run-outcomes.ts`): it tries `pg_try_advisory_xact_lock` every 100 ms for up to 60 s, past the longest fill measured below, 42.7 s, and once it has the lock holds it through the migration and the fill until the transaction commits; the migrator, in the same transaction, takes it again at once. With the lock held, the same hook checks the layout of the ledger before anything else (see [The layout of the ledger](#the-layout-of-the-ledger)). A server that starts while another fills a large ledger waits for it, and stops at start, saying why, only when the lock is still held after 60 s.

A projection keyed by its stream is filled a stream at a time. No index lists the streams of a kind across playbooks, so the fill scans the store's streams, `emt_streams`, for the names of the streams of the projection's kinds, of a playbook or an org as its `scopes` name, in the order of their names, matching each name against a pattern of each scope and kind, `*/*/*/<kind>/*` or `org/*/<kind>/*` with `GLOB` on SQLite and `^[^/]+/[^/]+/[^/]+/[^/]+/[^/]+$` with the kind fourth or `^org/[^/]+/[^/]+/[^/]+$` with the kind third on PostgreSQL, with the stored size of their messages of the mapping's types, and takes of them as many as hold at most 16 MiB of those messages, at least one, so that a ledger of records of 1 MiB does not hold hundreds of megabytes at once. 16 MiB is the bound of a store opened without one; a store opened with `mostBytesFilledAtOnce` among its kept tables, `sqliteLedgerLayer(opening, { mostBytesFilledAtOnce })`, fills in reads of at most that many bytes, by stream, in order and the holds of content alike, as a Durable Object's ledger does with 4 MiB, since an object answers every row of a statement at once inside the 128 MB of its isolate (`src/projections/keyed-fill-behaviour.ts`). It lists as many streams as the batch before showed fit: one at first, then as many as 16 MiB holds at the bytes per stream of the streams the batch before took, at most twice as many as it listed before and at most 100. On PostgreSQL the size is the length of each record's text, which reads the record, so listing 100 streams of records of 1 MiB would read 100 MiB to load 16 MiB; listed this way, the fill sizes about as many bytes as it loads. For each batch it reads, in one statement, those messages in their order, decodes each as the store's reads do, folds the messages of each stream through the mapping, and writes the rows in upserts of as many rows as 100 parameters hold on SQLite, the most the ledger binds in one statement there, 7 for the outcomes of runs, and of 500 on PostgreSQL. On SQLite a projection of more than 98 columns is refused as its fill is written, since not one of its rows fits in 100 parameters beside the two of its key (`itemsInAStatement`, `src/connection/bound-values.ts`). A change to what a table keeps is a new version, `run_outcomes_6`, which the next server fills this way and whose fill drops `run_outcomes_5`, as the layout step that ships with it does (see [A layout step](#a-layout-step)). Servers of different versions do not share a database at once.

A projection keyed by its mapping is filled in the order the facts were appended, since the facts of many streams change one row and the last of them must win: the fill lists the next messages of its kinds, of the scopes it names, and of its types, in the order of their position, `global_position` on SQLite and `(transaction_id, global_position)` on PostgreSQL, after the last message of the batch before, with the stored size of each and not its data, the length of its stored data alone and not the `payloadBytes` it keeps outside, since a fill folds what is stored and never loads a payload, takes of them as many as hold at most 16 MiB, at least one, and reads, in a second statement, the messages up to and including the last it took, as the fill of a projection keyed by its stream takes its streams and the fill of the holds of content takes its facts. It lists as many as the batch before showed fit, one at first, then as many as 16 MiB holds at the bytes per message of the messages the batch before took, at most twice as many as it listed before and at most 256. The read is bounded by the last message taken, not by a count, so on PostgreSQL, where the fill runs at `READ COMMITTED` and each statement sees what committed before it, a message committed between the two statements below that point is read and folded too, and the last message listed is never pushed out of the read (`src/postgresql/keyed-fill-on-postgresql.test.ts`). On PostgreSQL the listing takes its messages in a subquery and sizes only those, since a sort followed by a limit computes the size of every message after the point first: a listing of 15 of 200 messages of 1 MiB took 98.7 ms sizing all 200, and 10.5 ms sizing the 15 (`EXPLAIN ANALYZE` on PostgreSQL at 127.0.0.1:19623, 2026-11-10). It folds each into its row, read from the table being filled when the batch has not changed it yet, and writes the rows the batch changed. The bound is in bytes because a projection keyed by its mapping may fold facts as large as a run's start and its end: `activity_1` and `activity_broken_1` fold `run_started`, whose input may hold 256 KiB, and `run_succeeded`, whose output may hold 1 MiB, so 256 of them could hold 256 MiB. A test fills such a projection from 220 facts of 80 KiB, 17 MiB in all, and finds that no read of the fill loads more than 16 MiB of data, on each store (`src/projections/keyed-fill-behaviour.ts`, run by `keyed-fill-on-sqlite.test.ts` and `src/postgresql/keyed-fill-on-postgresql.test.ts`). Another fills the holds of 100 facts that each keep a mebibyte outside and store a few dozen bytes, at 4 MiB a read: they are read 1, 2, 4, 8, 16, 32 and 37 at a time as the listing grows, where counting what they keep outside would read them three at a time.

**One read held at a time.** Every fill, by stream, in order and of the holds of content, reads, folds and writes a batch in a function of its own that answers only where the next batch starts and how many it lists, `batchFilled`, `batchFilledInOrder` and `batchFolded`, and walks from one batch to the next through `batchesFilledFrom` of `src/projections/projection-fill.ts`, which holds that answer and nothing else of the batch, so the facts of a batch are let go before the next is read, and the heap a fill holds is bounded by what one read loads, whatever the length of the history; the bound on each read is the bound of the fill. A fill that went on to its next batch from inside the function that held the batch before kept every batch it had read until the last one ended, the whole history of the projection's types, since a function waiting on another keeps what it holds: the fill in order of 16 MiB of facts of 64 KiB at 2 MiB a read held, at its most, 17,082,936 to 17,083,616 bytes of heap beside what it held before it began on SQLite and 17,098,488 on PostgreSQL, and holds 2,152,696 to 2,163,288 on SQLite and 2,182,256 to 2,183,728 on PostgreSQL walked this way, each read loading at most 2,033,197 bytes either way: the heap in use after two collections at the start of each statement, by `filled-heap.ts` with `--expose-gc` on Node 26.12.1, which `src/projections/keyed-fill-heap.test.ts` runs on both stores and holds to less than twice the bound, with the row the fill builds equal to the row the appends kept. Walked this way, the statements a fill runs are the statements it ran before, value for value: five generated histories of 500 facts of two projections, one keyed by its mapping and one by its stream, filled at 256 KiB a read, ran the same statements with the same values and built the same tables on SQLite, and three built the same tables with the same number of statements on PostgreSQL, measured on 2026-11-11. Since the heap a fill holds does not grow with the history, the fill stays one transaction, so that the table's presence in the catalog still says it is whole, and earlier versions are dropped, and the new one analysed, only once it is.

### Reading the outcomes of runs

The read answers, in one statement over the index, the rows of the playbook whose `started_day` lies in the window, with the selection's `definitionType` and `name`, grouped by day, definition type, name and status: each group with its count, its token sums, `coalesce(sum(…), 0)`, its cost, `sum(cost_micro_usd)`, null when no run of the group recorded one and otherwise the sum over those that did, and the durations that are not null as a JSON array, `json_group_array(duration_ms) FILTER (WHERE duration_ms IS NOT NULL)` on SQLite and `json_agg` with the same filter on PostgreSQL. The playbook key is matched with `=`, and the statement binds five parameters at most.

## A fact scrubbed in place

`Ledger.scrubFact(stream, position, scrub)` rewrites the stored data of one fact, so that a person's data can be erased from the ledger when they ask: a fact that holds what a person wrote, such as a remark, keeps that it was recorded, by whom and when, while what they wrote goes. It is the only write of the ledger that changes a fact already recorded. `scrub` is a `FactScrub` of `@on.auto/operations`: `eventSchema`, the schema of the stream's facts, as a decider's; `data`, the fact's data once scrubbed, as JSON; `erasure`, the fact the caller appends to say what it erased, of the same schema; the `context` of the erasure; and its `lineage`, `noLineage` when left out. It answers the version of the stream after the erasure, `{ version }`.

It never changes the fact's type, its position, its message id, its context, who recorded it, its `by`, or when, its `at` and the store's `created`, and no other fact: of the fact's row in `emt_messages`, only `message_data` changes.

- **One read, then the checks.** One statement reads the stream's version from `emt_streams` and, joined, the type and the context of the fact at the position (`factAtOn`, `src/scrub/scrubbed-facts.ts`). The scrub is refused, as a `ScrubRefused` of `@on.auto/operations`, tagged `scrub_refused`, whose `because` says why: `no_stream` for a stream nothing was appended to, `not_its_position` for a position that is not a whole number from 1 to the stream's version, and `not_its_shape` for data that does not decode under `eventSchema` as the data of the fact, with its own type and context. A refused scrub writes nothing.
- **The fact's own shape, and nothing beside it.** The data that decodes is encoded again through the same schema, `Schema.toCodecJson(eventSchema)`, and that encoding is what is stored and what the projections fold, so a key the fact's schema does not read, which its decoding passes over, is never stored: data given as `{ text: '', kept: '…' }` for a fact whose data is `{ text }` is stored as `{ text: '' }` (`src/scrub/fact-scrub.ts`).
- **One transaction.** The erasure is checked and encoded as an append's facts are, and appended at the head, expecting the version read, by the store's own append, `appendWithin` of `src/emmett/emmett-event-store.ts`: its id, its metadata, the inline projections it folds into, the signal and the observer of the append are those of any append. Inside that append's transaction, before it commits, the ledger reads the fact, rewrites its data with one `UPDATE` of its row, the JSON text on SQLite and the `{"json": …}` wrapper on PostgreSQL, as the dialect stores data (`storedData`), and folds again every projection row the fact folded into. It does so in Emmett's `onBeforeCommit` hook, which Emmett 0.43.0-beta.50 calls inside the append's transaction once the inline projections have run (`dist/index.js` of `@event-driven-io/emmett-sqlite`, line 461, and of `@event-driven-io/emmett-postgresql`, line 900), with the messages of the append, each carrying, by reference, the very `data` it was given (lines 921 and 1442); the hook runs the work of the append whose erasure's `data` is that reference, the same value and not an equal one, and of no other append (`appendRiders`, `src/scrub/append-riders.ts`). On PostgreSQL that reference reaches the hook unchanged only because the ledger configures no `schema.versioning`, under which `downcastRecordedMessages` of `@event-driven-io/emmett` (`dist/index.js`, lines 3018 to 3021) would hand on copies. If a store ever ran no hook, the erasure would stay appended, with the fact's data as it was, and the scrub would fail as a defect, so that it is never taken for done; a test holds an Emmett store that runs none to that. A failure inside the transaction, such as a projection's mapping that throws, rolls back the erasure, the scrubbed data and every row together.
- **A conflict is retried.** Another append that reached the stream first makes the erasure's append meet a version conflict, as a deadlock does; the scrub reads the stream again and is retried, up to three more times, and then fails with `Conflict`, as a command does.
- **The rows folded again.** For each projection that folds the fact's type, the rows the fact keyed before and after its scrub, the stream's id or what `keyOf` answers of each, are locked as a fold locks them (see [Inline projections](#inline-projections)), and only then folded again from nothing over their facts, in the order they were appended, read 256 at a time inside the transaction (`rowsRefolded`, `src/projections/projection-refold.ts`). So on PostgreSQL an append that folds into the row while the scrub is open folds from the row as the scrub left it, or before the scrub folds it again, which then reads that append's fact as well; neither brings back what the scrub erased, nor drops the other's fact. A row is written by one upsert with the columns its reader advances left as they stand where the row is, so a scrub never undoes an advance, and whole where it is not; a row that folds to nothing is deleted. The outcomes of runs are one such projection. The holds on content of the fact's stream are folded again too, from every fact of the stream, under the lock of each digest whose hold changes (see [The holders of content](#the-holders-of-content)).
- **What a fold again reads.** For a projection keyed by its stream, the streams `<prefix><kind>/<id>` of its kinds, through `ledger_messages_by_stream`. For one keyed by its mapping, every message of its types on the streams of its kinds under the same playbook, through `ledger_messages_by_playbook` under the playbook key, or under the same org, through the same index under the key of each kind, since the key of an org's stream, its name through the third `/`, is `org/<org>/<kind>/`. Each stream or key is a lane of its own, read by a statement of its own in the order of its key and position, matched on PostgreSQL with `= ANY` of a list that holds the key alone, for the reason [How PostgreSQL reaches the indexes](#how-postgresql-reaches-the-indexes) gives, and binding five values on SQLite and six on PostgreSQL, so a projection of any number of kinds stays within the 100 values the ledger binds in one statement on SQLite and joins no lanes into a compound `SELECT`, whose terms a SQLite build may bound, which a test proves by folding again a row of twenty-one kinds, whose lanes would bind 105 values as one statement, through an executor that refuses a statement of more than 100 (`src/scrub/sqlite-refold-bound.test.ts`); the lanes of a batch are merged in the ledger's order by the order key each statement answers, the position on SQLite and the transaction id and the position on PostgreSQL, each written out to 20 digits (`messagesInOrderAfter` of each dialect, `src/projections/projection-refold.ts`). A scrub of a fact keyed by its mapping therefore walks the whole lane of its playbook, every message of the playbook's index from the first, or of each of the org's kinds, so its cost grows with the playbook or the org, not with the row; and on SQLite, whose one writer the transaction holds, every other write of the ledger waits for it. Read with `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL 18.4 over 200,000 messages of 100 playbooks, a first batch of a playbook's row read in the order of the position alone walked Emmett's index on `(transaction_id, global_position)` and filtered out 198,000 messages, in 221 ms; read as a lane, it walked `ledger_messages_by_playbook` with the cursor in the index's condition, in 5.2 ms, and a stream's lane `ledger_messages_by_stream`. SQLite's plan of the same lanes searches `ledger_messages_by_playbook` and `ledger_messages_by_stream` by the key and the position after the cursor, which a test reads (`src/scrub/sqlite-refold-plans.test.ts`).

From then on every read the ledger answers gives the scrubbed data: the stream's read, the reads of what a playbook recorded, its facts appended and the fill of a projection made later. A reader that read the fact before keeps what it read; the erasure is how a follower learns of the scrub. The fixtures of the facts are unaffected: a fixture is what a release wrote, not what a store holds now, and the erasure is the caller's fact, with a fixture of its own beside the module that makes it.

What a scrub does not reach: what other code keeps of the fact beside the ledger's own rows, the views the pages of a playbook fold from facts, the datasets of prediction functions, the run logs of workflows and the chunks of their snapshots that carried the text, and the recorded content a fact names by its digest, which a scrub of the fact leaves kept, though a scrubbed shape that no longer names the digest lets go of the fact's hold, so the content is removed once nothing else holds it and a removal is asked (see [The holders of content](#the-holders-of-content)); the log records the server exported of the append before the scrub, through its observer; and what the database itself still holds of the bytes it replaced, the dead tuples of the old row until a vacuum, the write-ahead log and the replicas it feeds, free pages of a SQLite file, and every backup taken before. Erasing those is the work of whoever keeps them.

## The signal of an append

`emmettEventStore` raises the `StreamSignal` its options give as `appended`, or `streamAppends`, the signal of the process, when they give none, after each append it made, with the name of the stream, and raises nothing for an append that met a version conflict. Every store of the process appends through it, the ledger's layer and the workflow host's own store alike, so a listener, `streamAppends.listen(listener)`, which answers the function that stops it, hears every append the process makes to a ledger given no signal of its own, a few microseconds after it commits. The layers and the stores take the signal as `appended`, beside `observer`, the two an `AppendListeners`: `ledgerLayer`, `postgresqlLedgerLayer`, `sqliteEventStore` and `postgresqlEventStore`, a ledger's store and the streams of its connection raising the same one. A program that opens many databases in one process gives each a signal of its own, `streamSignalOf()`, and the workflow host over the database that signal as `reactions.appended`, so an append to one database wakes no follower of another; the server gives none, and every ledger it opens raises `streamAppends` (`src/signal/store-signals-behaviour.ts`, which the suite runs on both stores, and `src/signal/append-signal.test.ts`). A listener is called in the append's own call, after the commit, and must not throw. An append made by another process raises nothing here; a reader that must see those reads the ledger anyway. `streamSignalOf()` makes a signal of one's own. It is apart from `appendSignal`: that one tells the playbook key of an append and is raised only by a layer given it, while `streamAppends` tells every stream, a playbook's or not, and every store of the process raises it, so the workflow host's follower hears the appends to the registries of playbooks too.

## Telemetry

Each append passes Emmett the run's lineage as its observability context, so the store's `eventStore.appendToStream` span names the run in `auto.on.run_id` and its chain as its correlation and causation ids, and the `traceId` and `spanId` a message stores are that span's. An `AppendObserver`, `observer` on the layers and the stores, is told of every append after it commits, never of one that met a version conflict, with the events, the expected version, the context and the lineage; it must not throw. The server's observer turns each event into a log record over OTLP. The ledger takes no OpenTelemetry dependency at run time: the server registers Emmett's instrumentation before any store is created. Its tests capture the event store's spans with the trace SDK, `@opentelemetry/sdk-trace-base`, and carry a span across awaits with the API, `@opentelemetry/api`, and its context manager, `@opentelemetry/context-async-hooks`, all three development dependencies.

A write of the ledger on SQLite that waits its turn in a queue of its pool runs in its caller's async context, as one that finds the queue idle does, so the spans it makes, such as the `eventStore.inlineProjection` an append makes inside its transaction, sit under the span of its caller. A statement of the secret rows of a ledger file is the exception: it is issued in the async context captured before the file's pool was made, never in its caller's (see [Kept secrets](#kept-secrets)), which costs no span, since dumbo makes none for a statement, its `tracer` only logging, and no instrumentation the server registers makes one either. As published, dumbo 0.13.0-beta.56 starts a task that waited in a queue of its `taskProcessor` in whatever context the queue resumed in, so such a span had no parent, or took the span of another caller's write, as the server's `src/telemetry/traced-reasoning.test.ts` saw when a projection's span sat under a call of a tool; its newest release, 0.13.0-rc.2, does the same. `patches/@event-driven-io__dumbo@0.13.0-beta.56.patch`, which `pnpm-workspace.yaml` names and the image copies before it installs its dependencies, makes `schedule` of the `taskProcessor` in `dist/sqlite3.js` and `dist/sqlite3.cjs`, the build of the `sqlite3` driver, take the caller's context as it queues a task, `AsyncLocalStorage.snapshot()`, and start the task in it; dumbo's own context, which names the connection a transaction holds, is set inside the task as before, so a statement inside a transaction still runs on that transaction's connection. Taking and entering the snapshot cost 0.49 to 0.54 µs a task, against 0.02 µs without, over 200,000 tasks in each of three rounds (measured on 2026-11-11 on an Apple M4 Max with Node 26.12), beside the 0.20 to 0.23 ms an append takes. Every queue of that build queues its tasks through that one function: the writer's, which `execute.command`, `execute.batchCommand`, `withTransaction` and a `withConnection` that is not read-only wait in; the readers', which a read waits in for a free connection; and the one that opens the database. The builds that PostgreSQL and a Durable Object load are left as published: dumbo's PostgreSQL build queues no task, and a Durable Object's pool starts every task at once. A patch applies only where this workspace installs its dependencies, so the npm package `@on.auto/runtime` uses dumbo as published, and there a queued write's spans can still lose their parent. `src/emmett/queued-append-spans.test.ts` holds the writer in a transaction, appends under a span of its own, waits until the append has handed its write to the writer, then lets go, and finds the append's span under the caller's and the projection's span under the append's, on a busy writer as on an idle one; with dumbo as published, the busy case fails every time, the projection's span with no parent. With Node's pool at one thread, which makes SQLite's statements wait their turn and so lengthens the writer's queue, the server's `src/telemetry/traced-reasoning.test.ts` failed 55 of 120 runs as published, each with a projection's span under the call of a tool, and 0 of 120 with the patch, in eight copies side by side, alternating 40 runs of each. The patch goes when dumbo keeps the caller's context itself.

## The streams appended to

`EventStore.readAppended(after, most)` answers which streams were appended to after a point, for a reader that must see the appends of other processes without reading each playbook in turn. It reads up to `most` messages after `after`, oldest first, and answers the stream of each named through its fourth `/`, so the streams of one kind in a playbook, such as `playbook/acme/sales/events/`, count once, or by its whole name when it has fewer, such as `org/acme/playbooks`; `through`, the point the next read goes on from; and `more`, when it stopped at `most`. Without a point it reads nothing and answers the point a read from now goes on from. It reads no data.

On SQLite it walks the table's key, `global_position`, and goes on from the last message it read. On PostgreSQL it walks Emmett's index on `(transaction_id, global_position)` behind the horizon, as a page read oldest first does (see [Order, and the horizon on PostgreSQL](#order-and-the-horizon-on-postgresql)), so a message whose transaction is still open comes in a later read, once; when it read everything behind the horizon it goes on from the horizon itself rather than from its last message, so a read that finds nothing new starts past every message it read before. Measured with `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL 18.6, on a table of 200,000 messages, a read that found nothing new walked that index and touched 3 buffers in 0.16 ms, and a read that found 10 new messages 5 buffers in 0.30 ms.

## Facts appended to a scope

`EventStore.readAppendedFacts(scope, { after?, most, dataOf })` is the store's side of `Ledger.readAppendedFacts` of `@on.auto/operations`: the facts appended to a playbook, `{ kind: 'playbook', playbookKey }`, or to the streams it names, `{ kind: 'streams', streams }`, oldest first, where a name of three segments that ends in `/`, such as `org/acme/comments/`, names every stream of that kind, selected through the first index by the stream's first three segments, as a playbook is (`isAKind` of `src/event-store.ts`). It runs over the statements of [Reading what a playbook recorded](#reading-what-a-playbook-recorded), the playbook through the first index and each stream through the third, and reads heads alone, measuring nothing, with the data of the types of `dataOf` loaded after them by position. Each read first takes the point of now, `readAppended(undefined, 0)`, the newest position on SQLite and the horizon on PostgreSQL ([The streams appended to](#the-streams-appended-to)), and reads no further than it, `to` among the bounds of the read; on PostgreSQL that point lies behind the horizon, so the read needs no lookup of its own and a fact whose transaction is still open waits for a later read, once. Without a place it answers the newest fact of the scope at or before that point, by one statement newest first, so a reader that starts from now skips nothing that commits late; from the start, `after: null`, it reads from the first fact of the scope; and from a place, `{ point, id }`, it reads from the place itself, `at`, and the first record it reads must be the fact of that id at that point, else the read answers `held: false`. It answers `facts`, `last`, the place the next read goes on from, `through`, the point of now or, when it stopped at `most`, the point of its last fact, and `more`. On SQLite the streams of a scope are read by one `SELECT` whose condition joins them with `OR`, `stream_id =` for a whole name and the key of the first index for a kind, which SQLite plans as a multi-index `OR`, each term through its index, sorted by position: a compound `SELECT` of a term for each stream would hold six terms for the org's playbooks, connections and comments, the whole name and the kind of each, and a SQLite build may allow as few as five terms in one compound (`SQLITE_MAX_COMPOUND_SELECT`, refused as `too many terms in compound SELECT`), where Node's allows 500. A test reads six such streams in one statement and pins its plan (`src/recorded/sqlite-streams.test.ts`). PostgreSQL bounds no compound, and keeps a term for each stream, each ordered by its key so that the planner walks the ledger's index rather than Emmett's ([How PostgreSQL reaches the indexes](#how-postgresql-reaches-the-indexes)), joined with `UNION ALL`. The ledger's service makes the cursor of a place the base64url encoding of the JSON array of its point and its id, and of the start the empty array, and `through` the encoding of the point alone (`src/appended/appended-reader.ts`).

`EventStore.waitForAppend(scope, after, signal)` answers `appended` once a fact of the scope was appended after the point `after`, and `ended` when its `AbortSignal` aborts or the store ends its waits; `Ledger.waitForAppend` gives it the signal of the fiber that waits, and answers `ended` at the deadline. Every store keeps one watch of its appends however many requests wait (`src/appended/append-watch.ts`): while any wait is open, it reads which streams were appended to, `readAppended` from its own point, each time the store's signal of an append is raised, the signal of [The signal of an append](#the-signal-of-an-append) that its `appended` names, `streamAppends` when it names none, and once a second, for what another process appended to the same database and for what the horizon held back. A read gives the point of the last message of each stream or kind it names, and ends each wait whose scope holds one of them later than the wait's point; a wait that begins after the watch read past its point moves the watch's next read back to that point, so no wait misses an append. Reads are one at a time: a signal raised while one is under way asks for one more, so a burst of appends costs one read, and reads go on while `more` says the last stopped at 1,000 messages. A read that fails ends no wait: the watch tells `watchFailed` of the `AppendListeners` once, when reads begin to fail, which the layers log as an error in the context they are built in, and reads again a second later, so the waits stay held until their deadline or the next read that succeeds. `endWaits()` ends every open wait with `ended` and every wait after it at once; the chores of the ledger offer it as `LedgerChores.endWaits`, which the server performs first when it stops, so a request it holds is answered at once rather than holding the stop, and the store performs it when it closes. The watch stops looking once no wait is open. The cost of a wait is that of the reads the watch makes for every wait at once, the read of [The streams appended to](#the-streams-appended-to) that touched 3 buffers in 0.16 ms on PostgreSQL when it found nothing new.

## The log

`LedgerLog`, a service of the ledger's layer and `log` of its store, reads every event of every stream in the ledger's global order: on SQLite through Emmett's own reads, `readMessagesBatch` and `readLastMessageGlobalPosition`, and on PostgreSQL through statements of its own (`src/log/postgresql-log.ts`) that read behind the ledger's own horizon, as its other reads do, rather than Emmett's, whose horizon is the oldest write open anywhere on the server, so that a write left open in another database never hides the newest events of this one from it. They read only the columns of where each event stands, never its data. Each event comes as a `LoggedEvent`: its id, its stream, its version in the stream, its type and its `point`, where it stands in the global order, a position on SQLite and a transaction id with a position on PostgreSQL, which commits out of order. `after(point, most)` reads at most `most` events after a point, or from the first event without one, with the point the next read goes on from and whether more follow; `at(point)` answers the event at a point, or nothing when none stands there; `head()` answers the point of the last event. The meter of `@on.auto/meter` counts the actions of a ledger over it. An event whose stored data no longer parses on SQLite fails a read with `UnreadableEvent`, which names the point the read went on from, so a reader can tell a ledger it cannot read from one it cannot reach. `src/testing/log-behaviour.ts`, exported as `logBehaviour(entry)`, runs on both stores, and `src/log/sqlite-log.test.ts` tests an unreadable event on SQLite.

## Creating the layer

Each database has an entry of its own, so that code which never uses a database does not load its driver.

```ts
import { ledgerLayer } from '@on.auto/ledger/sqlite3';

const layer = ledgerLayer({ fileName: '/data/ledger.db' });
```

`runOutcomes`, optional on both layers, is the run outcome mapping the ledger keeps the outcomes of runs with, and `projections` the other projections it keeps (see [Keyed projections](#keyed-projections)), `holders` the types of fact that hold content and what each holds, whose holds it keeps (see [The holders of content](#the-holders-of-content)), `layoutSteps` the steps that carry a database of an earlier layout forward (see [A layout step](#a-layout-step)), and `floor` the earliest layout it carries one forward from, `ledgerLayoutFloor` where it is not given (see [The layout of the ledger](#the-layout-of-the-ledger)); the server gives the mapping of `@on.auto/definitions`, the projection of the open requests of `@on.auto/interaction` and the steps it composes. Building the layer creates the directory of the database file if it is missing, then opens the database and migrates its tables before the ledger is ready; a directory that cannot be created or a database that cannot be opened is a defect at that point. Disposing the runtime closes every connection. `fileName: ':memory:'` gives a private in-memory database. `sqliteLedgerReads({ fileName })`, beside it, opens the file of a ledger for reads alone and answers its `read(statement)` and `close()`: it runs no migration, so it takes none of the write lock the open of the ledger takes to keep its layout, and its reads go to the pool's readers, which in WAL mode wait for no writer, so a test can poll a file a running server writes without slowing it (`src/connection/sqlite-reads.test.ts`, which reads while another connection holds the file `BEGIN IMMEDIATE`).

Each SQLite connection may cache up to 8 MiB of pages and maps none of the file into memory, where the driver's defaults allow about 1 GB of cache and 256 MiB of mapped file per connection. Every connection, the tests' temporary files included, runs in WAL mode with `synchronous=NORMAL`, the defaults of Emmett's connection layer, dumbo: a committed append survives a crash of the process, and only the latest commits can be lost if the machine loses power, since in that mode SQLite syncs the file at each checkpoint rather than at each commit. Measured on 2026-10-05 on an Apple M4 Max through `sqlite3` 6.0.1, an append of one event of 1.8 KB to a temporary file took 0.20 to 0.23 ms at the median with either setting, since macOS syncs only to the drive's cache; with `fullfsync` on, so that each sync reaches the drive as on a disk that honours syncs, it took 5.9 ms with `FULL` and 0.20 to 0.24 ms with `NORMAL`, whose syncs at checkpoints showed as 5.2 ms at p99.

```ts
import { postgresqlLedgerLayer } from '@on.auto/ledger/postgresql';
import { Pool } from 'pg';

const layer = postgresqlLedgerLayer({
  pools: ({ max }) =>
    new Pool({ connectionString: 'postgresql://playbooks:<password>@db.internal:5432/playbooks', max }),
});
```

`pools`, a `PostgreSQLPools`, opens a pool of `pg` with the most connections it is asked for, and is all the ledger knows of the database: where it is and how a connection signs in, with a password or a token signed for each connection, are the pool's, which the server composes once for the ledger and the workflow host. `plainPoolsOn(url)`, beside it, opens plain pools on a URL, whose password is in the URL: the server's pools when `DATABASE_CREDENTIALS` is `url`, and the tests'.

Building the layer connects to the database and creates or migrates Emmett's tables, functions and sequence in its `public` schema, the way Emmett documents it (`schema.migrate()` with automatic migration off), before the ledger is ready. A database that cannot be reached is a defect at that point, and its message names the host and port, never the password. Emmett's migrator holds an advisory lock on the database while it migrates, so servers that start together on an empty database migrate it once; the ledger takes that lock first and waits for it up to 60 s (see [Creating and filling a table](#creating-and-filling-a-table)). The connections come from `pg`, the pure-JavaScript driver, through one pool for each ledger, opened from `pools` with at most 10 connections, `pg`'s default; disposing the runtime ends the pool. When the database ends a connection, as a restart, a failover or `pg_terminate_backend` does, the ledger logs a warning with the database's message and the pool opens another connection on the next call; the server never stops for it.

The database's user needs `CREATE` on the `public` schema at every start, not only the first: the ledger migrates at every start, and the migrator runs `CREATE TABLE IF NOT EXISTS` on its own table, which PostgreSQL checks for the privilege before it looks whether the table exists, so a user that may only read and write the tables fails to start with `permission denied for schema public`. It also needs to read and write the ledger's tables, and to create its functions and sequence on an empty database.

## The connection of the ledger

Both layers provide, beside `Ledger`, the connection of the ledger, `LedgerConnection` of `@on.auto/ledger`, a `ConnectionPorts`, through which code in the same process keeps tables of its own in the ledger's database and appends streams of its own beside the ledger's, as the workflow host keeps its tables and its run logs (see the [workflow host README](../workflow-host/README.md#where-a-run-is-kept)), without opening the database again. The ledger opens it with its own store, when its layer is built, and closes it with its store, when its runtime is disposed; whoever runs its statements stops first. `LedgerServices` names the three, the chores of the ledger among them (see [Recorded content](#recorded-content)).

- `dialect` is the SQL the database speaks, `sqlite` or `postgresql`, for the few statements that differ.
- `streams` is an event store over the ledger's own connections, a `LedgerStreams`, without the ledger's projections and run outcomes and outside the signal of its appends, so a stream appended there is recorded in the ledger's database, tells the `AppendObserver` the layer was given, raises the signal it was given, `streamAppends` when none, and folds into no projection.
- `appendWith(stream, events, place, statements)` appends the events to the stream as `streams.append` does and runs the statements, in order, in the transaction of the append, after its events and before it commits, so both are kept or neither: an append that meets a version conflict fails as one and runs none of them, and a statement that fails, one that breaks a key among them, keeps none of the events and fails the append as `StatementsFailed` of `@on.auto/ledger`, the driver's error its `cause`, never as a version conflict, so a decision is not made again for statements that cannot succeed: on SQLite, Emmett reads a key broken inside its append as a conflict of its own, and the connection tells the two apart by whether the statements ran and failed (`src/connection/appends-with.ts`). It is how the workflow host records the end of a run with the event that ends it. With no statement it is an append alone. `eventAppenderWithOf(connection, schema)` encodes the facts of an append for it as `eventAppenderOf` does for `streams.append`, each event through the one function every append's events pass through, `eventAsAppended` of `src/event-appender.ts` (`src/connection/appends-with-statements-behaviour.ts` holds it on every store).
- `read(statement)` and `write(statement)` run one statement; `transaction(statements)` runs them in order in one transaction and keeps them only when the last writes a row, answering what the last answers; `readConsistently(reads)` gives the reads one snapshot of the database and keeps nothing; `migrated(statements)` makes tables and indexes, on PostgreSQL in one transaction under an advisory lock of its own, so that servers that open together make them once, and on SQLite one after another; `sharedClock()` reads the database's own clock in milliseconds on PostgreSQL, which every server on the database shares, and is `null` on SQLite, where one server holds the file. Each answers with the driver's error when the database refuses.
- `mostBoundValues` is the most values one statement may bind, for code that builds a statement with a value per row: 32,766 on SQLite, `sqliteMostBoundValues`, the ceiling, unless the `SQLiteOpening` names fewer for a host whose SQLite allows fewer, but never fewer than the floor, the 100 the ledger binds in one statement on any SQLite (`mostValuesTheLedgerBindsOnSQLite`), which an opening below it is refused for; and 65,535 on PostgreSQL (`src/connection/bound-values.ts`, whose numbers the [workflow host](../workflow-host/README.md#where-a-run-is-kept) sets out). `chunksWithin(items, { mostBoundValues, valuesEach, valuesBeside })` splits the items of such a statement into chunks of as many as fit beside the values it binds anyway, and refuses a statement that cannot hold one, and a count that is not a whole number, at least 1 for the bound and for the values of an item and at least 0 for those beside.

A statement is a `Statement`, written with the tag `statement`, or made with `statementOf(parts, values)` of the texts between its values, one more than the values, for a statement whose text, such as the name of a table, is known only at run time, and whose values are bound, never written into its text: on SQLite through the SQL builder of `@event-driven-io/dumbo`, and on PostgreSQL numbered `$1`, `$2` and so on in the order they appear, `textOnPostgreSQL`. On SQLite the connection runs on the ledger's one pool, its writer serialising every write of the ledger and of the code beside it, its snapshots on one of the pool's readers, or, in a private database in memory, on the pool's one connection, which holds every write until the snapshot ends. Every statement the ledger sends outside a transaction that writes is a command, `execute.command`, never a query, the head of a content among them, over a `ReturningExecutor` of `src/event-store.ts`, whose commands answer the rows a `RETURNING` names: outside a transaction, dumbo's pool of a file sends a query to one of its readers, whose connections can write too, so a write sent as a query would wait for SQLite's lock beside the writer rather than in turn behind it, for at most the 5 s of dumbo's `busy_timeout`, and then fail with `SQLITE_BUSY`; and since `sqlite3` runs each statement on one of the four threads of Node's pool, four such waits leave the writer no thread to commit on, so all of them fail. A write sent as a command waits in turn in the writer's queue, holding no thread, for at most the 30 s dumbo's writer queue gives a task to start, `maxTaskIdleTime`, which the ledger leaves at its default, and one not started by then fails with dumbo's `Task was not started within the maximum waiting time`, not with `SQLITE_BUSY` after 5 s. The rows of secrets send their writes as commands too, on the same pool (see [Kept secrets](#kept-secrets)), so a file of a ledger has one writer. Measured on 2026-11-11 on an Apple M4 Max of 16 cores, four copies of the server's test of a reasoning run whose 1 MB answers are kept on object storage, `large-answers-on-stores.test.ts`, run side by side failed 6 of 36 runs that way, and a probe of the content store's statements over 16 of those runs named each statement that failed, a head's write sent as a query, after 5.2 to 5.4 s of waiting, or 10.5 s for two that waited behind others; with Node's pool at 64 threads the same code failed 0 of 20 runs, and with every such write a command, 0 of 48. `src/connection/sqlite-one-writer.test.ts` holds each such write, on connections that wait for no lock, to keeping its row once a transaction of the writer ends. On PostgreSQL its statements run on a pool of at most four connections of their own and its streams on the ledger's pool of ten, both opened from `pools`, their lost connections logged as the ledger's own. `src/connection/sqlite-connection.test.ts` holds the connection to what it does on SQLite, and `src/postgresql/postgresql-connection.test.ts` to each statement it sends on PostgreSQL, through fake connections.

## The layout of the ledger

A release reads what the releases before it recorded, and carries their databases forward: a change to a table or an index ships a layout step, and a change to the shape of a fact ships a reader for the shape before, each pinned by a fixture. Upgrades go forward only. The exceptions are what releases before this one recorded of prediction builds, of memories and of recall functions, which this release does not read: the facts of builds and their versions, such as `version_built`, and the records of runs that hold a kind of refusal of prediction this release no longer has, such as a `run_rejected` of the kind `model_process_busy`, in a run's stream or in a workflow's run log; and the facts of a memory, `memory_remembered`, `memory_forgotten`, `memory_erased` and `memory_moved`, a `run_started` whose `output_shape` is `memories` and a `run_rejected` of the kind `memories_full`; and the records of runs refused while what a recall function kept of the history was still being built, a `run_rejected` of the kind `rebuilding`, in a run's stream or in a workflow's run log. A database whose newest fact of a type is one of them is refused as it opens, as `ledger_facts_refused`, and one recorded before the newest of its type is refused when it is read, as any fact this release does not read.

facts](#step-23-the-names-filled-from-the-facts)). `ledgerLayoutFloor`, beside it, is the earliest layout a database is carried forward from, 6, so a database made in a layout before 6 is not carried. A layer given `floor` carries a database forward from that layout instead, and refuses one below it, so a host whose databases were made under an earlier floor keeps carrying them when a later release raises the floor of the databases the server makes (`src/ledger-layer.test.ts`, and `src/postgresql/ledger-on-postgresql.test.ts` on PostgreSQL). Releases before this one kept layout 6 while the shapes of their facts changed beneath it: the meter of 0.42.1, the published package `@on.auto/runtime` of that release, made `license_refreshed` and `metering_faulted`, which this release does not read, and `license_activated` in the shape of its `LicenseSchema`, where 0.43.0 made it in that of `LicenseRecordSchema`, the shape this release reads. So a database is carried forward when the facts it holds are ones this release reads, and refused as it opens otherwise, as the list below says. The tables Emmett and its database library make, whose names begin with `emt_` and `dmb_`, are theirs and outside the layout; Emmett migrates them itself.

The ledger keeps the number in the one row of `ledger_layout` on every store, `layout INTEGER NOT NULL` beside a key, `one_row BOOLEAN NOT NULL PRIMARY KEY DEFAULT TRUE CHECK (one_row)`, that allows a single value. The key is `NOT NULL` because SQLite lets a primary key other than an `INTEGER PRIMARY KEY` hold `NULL`: without it, a second row with a null key went in on SQLite 3.53.4. The ledger keeps the layout first, as the store migrates, before Emmett's migration and before any table of its own or of the host is looked up or made, in transactions of its own: on SQLite one dumbo begins `IMMEDIATE` (`@event-driven-io/dumbo` 0.13.0-beta.56, `dist/sqlite3.js` line 3017), so it holds the write lock from its first statement (`sqliteLayoutKept` of `src/layout/sqlite-schema.ts`); on PostgreSQL one on a connection of the ledger's pool that first takes the advisory lock Emmett's migrator takes, waiting for it up to 60 s as the migration does (`postgresqlLayoutKept` of `src/postgresql/postgresql-layout.ts`). Every open applies one rule in one code path, `requireTheLayoutKept` of `src/layout/layout-kept.ts`: a statement lists the tables of the schema, the one thing each store says for itself, through `sqliteLayout` and `postgresqlLayout` of `src/layout/layout-dialects.ts`, of which the rule takes the ledger's own alone, and, when `ledger_layout` is among them, a second reads its row. The ledger's own tables are those of its layout, `ledger_layout`, the content tables and `kept_secrets`, the tables of the projections it is opened with, of every version, named by the one rule by which the ledger drops the earlier versions of a projection's table (`versionOfTable` of `src/projections/projection-fill.ts`), and those of the store it keeps its streams in, Emmett's and its database library's, whose names begin with `emt_` and `dmb_`. The host's tables are not among them: the host makes them only once the ledger has kept its layout, so a database the rule finds new holds none of them, and one the rule refuses is refused before the host makes anything. A table anyone else keeps in the database, such as a platform's own bookkeeping table, is not the ledger's business: it neither makes a database look old nor is changed.

- A database in the layout kept opens, and the tables and indexes it lacks are created, each looked up first.
- A database without a number that holds none of the ledger's own tables, `sqlite_master` naming none on SQLite and `pg_tables` none in `current_schema()` on PostgreSQL, is new: it is given the number in the transaction that found it new, so the table never stands without its row and ledgers that open a new database together agree, and the ledger goes on. Of 20 pairs of SQLite pools that took the step on one new file at once, one failed with `table ledger_layout already exists` when it ran statement by statement, and none in the transaction.
- A database in an earlier layout, the floor or later, is carried forward: the ledger finds the steps that lead from its layout to the one kept, one for each number, before it takes any, the statements of every step it is given for a number taken together as that number's step, in the order the steps are given, and takes them in order, each in a transaction of its own that reads the layout again, takes the step only while the database is still behind it, and writes the step's number last. Ledgers that open the database together take each step once, and a step the database refuses rolls back its own transaction and leaves the database in the layout before it, from which the next start goes on. A ledger given no step for a number it needs refuses to start, naming the number, as a defect of its composition, and takes no step.
- A database in the layout kept, or one it carries forward, is read for the facts it holds, once, in the transaction that found its layout, before any step is taken and any projection rebuilt, when the ledger is given the schemas of the facts its server reads, `factSchemas` (`requireTheFactsRead` of `src/layout/ledger-facts-refused.ts`, which `requireTheLayoutKept` of `src/layout/layout-kept.ts` calls). One statement, the same on both stores, scans `emt_messages` for the newest position of each type and joins back the fact at that position; the ledger decodes each of those facts through the schemas that read its type, its readers of earlier shapes among them (`factsReadBy`). A database that holds a fact of a type no schema reads, or whose newest fact of a type no reader of that type decodes, is refused as a `LedgerFactsRefused` of `@on.auto/ledger`, tagged `ledger_facts_refused`, with `unknown`, the types it does not read, and `unreadable`, the type and the position of each newest fact it cannot decode, in words that name them and say an earlier or a later release made the database than this one reads, and left as it was; the server answers it with words of its own, where the ledger is, the types or the facts and their positions, and what to do whether a newer version made it or an earlier one. Only the newest fact of each type is decoded: a database in which a later release recorded a type in a shape this release reads after an earlier release recorded it in one it does not passes the start, and that earlier fact is refused when it is read, as any unreadable fact is. The server gives the ledger every fact schema it composes, `knownFactSchemas` of `packages/server/src/composition/known-facts.ts`, of 71 types, and `ledger-store.test.ts` requires those types to be the types of every fixture the packages keep, so a fact any module of the server records is one it reads. Beside them it gives the schema of each fact the prediction capability declares on runs, which it makes before the ledger opens, an extension's among them (`factSchemasKnownWith` of the same file), so a type an extension declares is read at every start the extension is listed at, and refused at one it is not. The read scans the table twice, once for the newest positions and once for their facts, on PostgreSQL by a hash join, as no index there leads with the global position: on one laptop, warm, it took 24.2 ms for 100,000 messages and 288 ms for 1,000,000 on SQLite, and 22.4 ms and 209 ms on PostgreSQL 18.4, with 40 types and 400 bytes of data each, the median of five reads.
- A database in a newer layout, or in one older than the floor, or one that holds tables of the ledger but no number, is refused as a `LedgerLayoutRefused` of `@on.auto/ledger`, tagged `ledger_layout_refused`, with `found`, the layout found or none, `kept`, the layout this server keeps, and `floor`, the earliest it carries forward, and left as it was. Its words say that upgrades go forward only, and a newer database wants a newer release, or that a database older than the floor is not carried forward, and to delete the local database. The server, which knows where the ledger is kept, answers it with words of its own: where the ledger is, the layout it keeps, the earliest it carries forward and the one it found, what to do, and where to ask, which for a newer ledger is to start the version that made it, or to restore the backup taken before the upgrade, and for an older one to delete it.

### A layout step

A step is a `LayoutStep` of `@on.auto/ledger`, `{ layout, statements }`: the layout it leads to, from the one before, and the statements that lead there, run in order. A statement is a `Statement`, written with the tag `statement` and run as it is on both stores, or, only where the dialects differ, a `StatementInEachDialect`, `{ sqlite, postgresql }`, of which the step runs the one of its database (`sqlOn` of `src/layout/layout-steps.ts`); or, where SQL cannot say what a step does, such as a value computed by a hash, a `StepInCode`, `{ inCode(execute, dialect) }`, a function the step runs in its turn with the executor of the step's own transaction and the `LayoutDialect` of its database, through which it reads and writes the database as a statement does, so what it reads and writes is part of the step and a failure in it rolls the whole step back (`stepStatementTaken` of the same file). A step in code is the form Flyway calls a Java-based migration, "a great fit for all changes that can not easily be expressed using SQL" ([Migrations](https://github.com/flyway/flywaydb.org/blob/gh-pages/documentation/concepts/migrations.md), Flyway's documentation); like a statement it is run once, inside the step's transaction. Its rule: it reads and writes only through the executor it is handed, and touches nothing else, no file, no network and no other connection, so that what it does is part of the step and nothing else is; it catches no error, since on PostgreSQL a statement that fails aborts the transaction and on SQLite it does not, so a step that caught one would be left half-done on a SQLite file and an object; and it runs before Emmett's schema and the ledger's own tables are made, since the ledger keeps the layout first, as this section says, so a table it reads or writes may not be there yet, in a store carried from an earlier layout in the same opening or one whose first opening stopped after writing its layout, and it makes what it needs as the layout stands at its number, `IF NOT EXISTS`, and reads a missing table as empty. The package that owns a table registers the steps of its tables beside them: the ledger its own, the content tables and `kept_secrets` in `ledgerLayoutSteps` (`src/layout/ledger-steps.ts`), the workflow host its tables and the views of its projector in `hostLayoutSteps` (`src/database/host-layout-steps.ts` of `@on.auto/workflow-host`), the prediction capability its own in `predictionLayoutSteps` (`src/dataset/dataset-statements.ts` of `@on.auto/prediction`), the steps of the datasets of prediction functions, which the server takes whichever capability answers those functions, since the tables are the runtime's, and the generation capability those of the projections of its assets in `generationLayoutSteps` (`src/assets/asset-layout.ts` of `@on.auto/generation`). The server composes them in the order of their numbers, the steps to one number in the order the packages are given, as it gives the ledger its projections, and gives them to the layers as `layoutSteps` (`packages/server/src/composition/layout-steps.ts`); an extension's tables take no step, since a change of their shape takes a new table; a layer given none keeps its layout as before and carries nothing. A step leaves the database as a new database of its layout would be, so its statements write a table and an index exactly as their creation statements do, and a column it adds goes last, where a new table's statement then names it. A projection whose shape changes takes a new version, and so a new table, which the ledger fills from the facts as it opens; its step drops the retired table. Step 7 is the first, and two packages give it statements, which the server composes in the order the ledger's, the host's and the prediction capability's steps are given (`packages/server/src/composition/layout-steps.ts`): the ledger's drops, where a database holds them, the three tables of content staged under a run, `staged_content_chunks`, `staged_content` and `unstaged_runs`, which this release no longer keeps, and the prediction capability's two tables of prediction functions this release no longer keeps and the two tables of their datasets, whose rows changed shape, which the host makes again as it opens and fills from the history. Step 8 is the ledger's: it drops `run_outcomes_4`, the outcomes of runs before they kept the cost of a run, which the ledger fills again as `run_outcomes_5` as it opens. Step 9 is the workflow host's: it drops `recall_views`, where a database holds it, since the views of pages fold their rows again from the history. Step 10 is the ledger's and takes no statement: it came with `memories_1`, a projection's table, which the ledger makes as it opens with the projection and step 15 drops. Step 11 is the generation capability's (`generationLayoutSteps` of `@on.auto/generation`, `src/assets/asset-layout.ts`): it brings the two projections of the assets generation functions make, `assets_1` and `asset_totals_1`, and gives them no statement either. Step 12 is the ledger's: it adds three columns to `recorded_content_heads`, last and in the order a new table's statement then names them, `kept_at`, `BIGINT NOT NULL DEFAULT 0`, `kept_in`, `TEXT NOT NULL DEFAULT 'ledger'`, since every head before the step names chunks of the ledger, and `removing_since`, `BIGINT`, unmarked, and sets `kept_at`, by the clock of each store's database, to the moment of the step, so a content kept before the step counts, for a removal, as kept then; the table of the holds, `content_references_1`, takes no step, since the ledger makes and fills it as it opens with the holders, as it does the table of a keyed projection. Step 13 is the generation capability's again: it brings the projection of the generations a playbook waits for, `generations_due_1`, and gives it no statement, as step 11 gives the assets none. Step 14 is the workflow host's: it brings `workflow_pauses`, the workflows of each playbook the host keeps paused, and gives it no statement, since the host makes its tables as the server opens. Step 15 is the ledger's: it drops `memories_1`, where a database holds it, and its indexes with it, since this release keeps no projection of that table and the ledger drops only the earlier versions of a projection it is opened with. Step 16 is the workflow host's: it adds four columns to `workflow_reaction_refusals`, last and in the order a new table's statement then names them, `kind`, `because`, `trigger_kind` and `trigger_reference`, each `TEXT` and unmarked, since a refusal counted before the step has none of them and is recorded without them. Step 17 is the workflow host's: it adds two columns to `workflow_runs`, last and in the order a new table's statement then names them, `ended_time` and `closed_at`, each `BIGINT` and unmarked, since a run that ended before the step has no time of its end recorded and none of its calls closed; it writes no row, so no run that ended before it is closed by the host's due work, which closes only the runs with an `ended_time` (see [Closing the calls of an ended run](../workflow-host/README.md#closing-the-calls-of-an-ended-run)), and the two indexes the closing reads, `workflow_runs_closing` and `workflow_calls_unclosed_by_run`, are made by the host as the server opens. Step 18 is the workflow host's: it adds `held_due` to `workflow_subscriptions`, last, `BIGINT` and unmarked, the due time of a schedule's start held while its workflow cannot be read from storage, which no schedule holds before the step; and it keeps `workflow_reaction_refusals` one row a trigger of a workflow instead of one a workflow, under the key `(playbook_key, workflow, trigger_kind, trigger_reference)`, whose trigger columns become `TEXT NOT NULL`, empty for a refusal with no trigger, as a listen task's. It copies the table aside, drops it, makes it again by the statement a new database makes it with, writes back each row counted before the step with an empty trigger where it had none, and drops the copy. A table made again under a new key is copied and not renamed, since PostgreSQL names a primary key after its table and keeps that name through a rename, so a renamed table would hold its key under another name than a new database's. Step 19 is the workflow host's: it adds four columns to `workflow_followed_playbooks`, last and in the order a new table's statement then names them, `held_since` and `held_until`, each `BIGINT` and unmarked, `holds`, `INTEGER NOT NULL DEFAULT 0`, and `held_for`, `TEXT` and unmarked, the hold of a playbook's follower (see [A held playbook](../workflow-host/README.md#a-held-playbook)), which no follower holds before the step; it writes no row, so every place a follower kept reads as it did, with no hold, and the index through which the follower finds the next hold, `workflow_followed_playbooks_held`, is made by the host as the server opens. A release before the step refuses a database the step carried, as any database of a newer layout, so the step goes forward only; the code before it names every column it reads and writes of the table, so a release that keeps the step and not the code that reads the hold runs over the four columns and leaves them as they are. Each step of the workflow host that changes a table, 16 to 19, first makes the tables it changes as they stood before it, `CREATE TABLE IF NOT EXISTS`, which changes nothing on a store that holds them: the ledger keeps its layout before the host makes its tables, so a store whose first opening ended between the two, as a playbook's object can, holds a layout and none of the host's tables, and is carried forward at its next opening all the same, the host making the rest (`database-floor-sqlite.test.ts`, `database-floor-postgresql.test.ts` and `object-layout.workers.test.ts` of the hosted runtime). Step 20 is the ledger's: it brings `webhooks_received`, which the ledger makes as it opens, as it makes `kept_secrets`, so the step takes no statement. Step 21 is the ledger's: it adds two columns to `recorded_content_heads`, last and in the order a new table's statement then names them, `expires_at` and `erased_at`, each `BIGINT` and unmarked, when a content expires and when its bytes were erased, which no head has before the step. It writes no row and makes no index, and no release reads or writes either column yet, so every head reads as it did. A column with no default and no constraint is added on SQLite by a change to the statement the schema keeps of the table, which "is independent of the amount of data in the table" ([ALTER TABLE](https://www.sqlite.org/lang_altertable.html)), and on PostgreSQL without a rewrite of the table ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)), so the step takes as long for a store of a million heads as for one of none. The layout it leads to also holds `recorded_content_heads_expiring`, the partial index of the heads whose content expires, which the ledger makes as it opens, after the step, as it makes every index of the content tables it finds missing, so a store the step carried and a store made at 21 hold the same index once each has opened (`src/content/heads-step-behaviour.ts`, on both stores and on an object's SQLite). Its build is the one part of the open that reads every head, once, at the first open of a store at 21: no head has an expiry yet, so it writes an empty index and holds no row in memory, and on PostgreSQL it "performs the entire index build with a single scan of the table" ([CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)), inside the transaction in which Emmett makes its schema and the ledger then prepares its projections, so a put that writes a head, on another server, waits until that transaction commits, since "a lock is normally held until the end of the transaction" ([Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)), and reads go on. As each step of the workflow host that changes a table does, it first makes `recorded_content_heads` as it stood before it, `CREATE TABLE IF NOT EXISTS`, which changes nothing on a store that holds it: the ledger keeps its layout before Emmett's migration and before it makes the content tables, so a store whose first opening ended between the two holds a layout and no heads, and is carried forward at its next opening all the same, the ledger making the rest (`src/content/heads-step-behaviour.ts`, on both stores, and on an object's SQLite in `ledger-store.workers.test.ts` of the hosted runtime). A release before the step refuses a database the step carried, as any database of a newer layout, so the step goes forward only; the code before it names every column of the heads it reads and writes, so a release that keeps the step and no code that writes the two runs over them and leaves them empty. Step 22 is the ledger's: it drops `ledger_messages_by_playbook_and_correlation` and `ledger_messages_by_id`, the indexes of the tree of a run and of an event's id, which the playbook's key and the message id led, where a database holds them, and the ledger makes the indexes that take their place, `ledger_messages_by_org_and_correlation` and `ledger_messages_by_org_and_id`, led by the org, as it opens, after the step, as it makes every index of its own it finds missing, beside `definition_names_1` and its index, which it makes empty, as it makes `webhooks_received`; so a database the step carried and a database made at 22 hold the same tables and indexes once each has opened (`src/layout/ledger-steps-behaviour.ts`, on both stores). It writes no row. Building the two indexes is the part of the open that reads every message, once, at the first open of a database at 22: the open that built them took 0.95 s on SQLite and 1.67 s on PostgreSQL, with the analysis, on a ledger of 1,000,000 messages, and 0.01 s and 0.13 s on one of 10,001 (see [Measurement of the read of one event](#measurement-of-the-read-of-one-event)), and on PostgreSQL the build holds appends that long, inside the transaction in which Emmett makes its schema, as the first open after the indexes of a playbook were built did. A release before the step refuses a database the step carried, as any database of a newer layout, so the step goes forward only. Step 23 is the ledger's, and the first step in code: it fills `definition_names_1` from the facts (see [Step 23, the names filled from the facts](#step-23-the-names-filled-from-the-facts)). The next change to a table raises `ledgerLayout` to 24 and ships step 24, such as:

```ts

  {
    layout: 24,

      statement`ALTER TABLE workflow_calls ADD COLUMN tool TEXT`,
      {
        sqlite: statement`UPDATE workflow_calls SET tool = json_extract(call, '$.tool')`,
        postgresql: statement`UPDATE workflow_calls SET tool = call::jsonb ->> 'tool'`,

```

### A reader for an earlier shape

A fact is decoded by its schema wherever it is read: through its codec, `eventCodecOf`, when a stream folds and when the workflow host reads a run log, and by the projections, the presenters and the readers of the other packages. A fact whose shape changed is made with `readingEarlierShapes(current, [earlierShapeOf(earlier, raise)])` of `@on.auto/operations` (`src/fact-shapes/earlier-shapes.ts`), so its schema decodes with the current shape first and then, in turn, with each earlier shape, a schema of its own, which its reader, `raise`, lifts to the current shape, and encodes in the current shape alone. Every read decodes through the one schema, so one reader serves them all. A release that changes the shape of a fact ships the reader for the shape before, and never removes one:

```ts
const ConnectionAddedBefore = factOf('connection_added', DataOfTheShapeBefore, ActedContextSchema);

readingEarlierShapes(factOf('connection_added', Data, ActedContextSchema), [
  earlierShapeOf(ConnectionAddedBefore, ({ data, ...fact }) => ({ ...fact, data: { ...data, paused: false } })),
]);
```

A reader that throws is a decode failure of the shape it reads, as the schema reports any, never an exception (`raisedBy` of `src/fact-shapes/earlier-shapes.ts` of `@on.auto/operations` runs it in `Effect.try`), so a decoder that passes over a fact it cannot read passes over that one too, and a strict one refuses it.

A fact a capability records on a run is read through the one schema its capability declares, with its readers. The run stream takes a fact of a capability's type only where that schema decodes it (`runFactsOf` of `packages/definitions/src/run-work/declared-facts.ts`), so it reads an earlier shape through its reader and refuses a shape no reader knows; the capability reads the run's work through the same schema, as does a projection that reads those facts, with `factReaderOf(schema)` of `@on.auto/operations` (`src/fact-shapes/fact-readers.ts`), which passes over a fact of a type the schema does not read and refuses one of its types in a shape no reader knows, as any unreadable fact is refused: the interaction capability through `InteractionRunFactSchema`, and its conversations through `ConversationCallEventSchema` of `@on.auto/tool-servers`. The outcome of a run and the start of a run a reaction reads go through the run's own schemas the same way (`runOutcomeMapping` and `runStartedOf` of `@on.auto/definitions`).

The baseline is release 0.46.0: no shape before it is read.

### The fixtures of the facts

Every fact type has a recorded fixture for each of its shapes, the JSON exactly as the release that recorded it wrote it, `{ type, data, context }` as the store keeps them, in `<release>/<type>.json` in the folder of the module that makes the fact, beside its tests, such as `packages/connections/src/registry/0.46.0/connection_added.json`. `recordedFactsBehaviour({ schema, folder, releases })` of `@on.auto/ledger/testing` (`src/recorded-facts/recorded-facts-behaviour.ts`) is the gate of one schema: `releases` names, for each release, the fact each of its fixtures is read as, today's shape of it; the gate requires the newest fixture of each fact type to be what this release writes for its fact, through the real encoder, `eventAppenderOf`, so a change of shape cannot ship without a fixture of the new shape; it decodes every fixture through the codec and compares it with the fact expected, so a change of shape cannot ship without the reader of the shape before; and it requires a fixture of every fact type the schema reads, and the fixtures of those types in the folder to be the ones its releases name. A missing fixture is recorded, never overwritten, by the package's tests run with `LEDGER_RECORD_FACTS=1`, as `LEDGER_RECORD_FACTS=1 pnpm --filter @on.auto/connections test`, which runs vitest in the package itself, and only into the folder of a release after the version the repository has shipped, the `version` of the `package.json` beside its `pnpm-workspace.yaml` (`shippedVersionOf` of `src/recorded-facts/fixture-manifest.ts`): with the repository at 0.45.0, 0.46.0 is open, and a missing fixture of 0.45.0 or before is refused, in words that say to restore it as its release recorded it, so once a release ships its fixtures are never recorded again. A fixture is kept exactly as the recorder writes it and is never formatted: `.oxfmtrc.json` ignores every release folder under a package's `src`, `**/src/**/[0-9]*.[0-9]*.[0-9]*/*.json`, so the bytes recorded are the bytes the manifest hashes. Each package keeps a manifest of its fixtures, `recorded-facts.json` beside its `package.json`, the path of every fixture in the package and the SHA-256 of its file (`src/recorded-facts/fixture-manifest.ts`): recording adds the fixtures it writes, one recording at a time under a lock, the gate requires the fixtures of its folder to be the ones the manifest keeps of it, each unchanged, and `scripts/recorded-facts.test.ts` requires the same of every package, so a fixture an earlier release recorded cannot be deleted or rewritten, nor a change of shape pass by deleting one, without the manifest saying so in the change. Release 0.46.0 records the baseline, 73 fixtures of the 70 fact types the server's ledger records, the three of a tool call made both on a run and by the tool servers. The gate of all of them, `scripts/recorded-facts.test.ts`, derives their list from the code: it walks every module the server's command, `packages/server/src/main.ts`, reaches, through static imports and dynamic imports of a literal, across the packages, finds each call of `factOf`, and requires a literal type in every call, a fixture of each type beside the module that makes it, and no fixture of a type no module beside it makes. Its test of a fact that has an earlier shape, `src/recorded-facts/recorded-facts.test.ts`, records the earlier shape in one release and reads it in the next through its reader.

### The gates of the layout

The server pins the layout over the whole database it opens (`packages/server/src/database/database-layout.test.ts`). It starts a server on a new SQLite file and stops it, reads from `sqlite_master` the name and the statement of every table and index whose name begins with neither `emt_`, `dmb_` nor `sqlite_`, each statement on one line, and compares them, sorted by name, and `ledgerLayout` with the catalog it keeps for the layout in `database-layout.json` beside it, so a change to anything the ledger, the host or a folder makes there fails it, in words that say to raise `ledgerLayout`, register the step and pin the catalog again. ## PostgreSQL

The ledger on PostgreSQL behaves as it does on SQLite; one suite of tests runs against both (see [Testing](#testing)). What was verified on Emmett's PostgreSQL store, `@event-driven-io/emmett-postgresql` 0.43.0-beta.50 with `pg` 8.23.1 against PostgreSQL 18.6:

- **An append is atomic.** Emmett appends every event of a call in one transaction, through one call of its function `emt_append_to_stream`; an append whose third event PostgreSQL refused left the stream as it was.
- **The expected version is checked exactly.** Expecting 0 of a stream that exists, a version beyond the stream's or one behind it, or any version but 0 of a stream nobody wrote, meets a version conflict and appends nothing. Of eight writers expecting the same version at once, one appended and seven met a conflict, for an existing stream and for a new one.
- **`STREAM_DOES_NOT_EXIST` is no check at all,** as on SQLite: Emmett turns it, `STREAM_EXISTS` and `NO_CONCURRENCY_CHECK` into no expected version and appends at the end. The ledger therefore always appends with a number.
- **A read from a version is exact.** Reading after version 3 of a stream at 5 gives events 4 and 5 and the version 5; past the end, Emmett gives no events and version 0, which `read` answers with the version asked after.
- **Message ids are not deduplicated.** The store keeps two events with the same message id, and the same event appended twice is two events with two ids.
- **The store keeps no JSON as written.** Emmett stores `data` in a `jsonb` column, and `jsonb` refuses the character U+0000 and unpaired surrogates and puts the keys of every object in its own order. The PostgreSQL entry therefore keeps each event's JSON text in that column, as `{"json": "<the event as JSON>"}`, so an event comes back exactly as it was decided, as it does from SQLite's text column. This is a deliberate trade: an exact round trip of tenant data matters more than `jsonb`'s operators. What an operator gives up is querying and indexing events by their data in SQL: reading one takes `(message_data->>'json')::jsonb`, which fails for an event that holds U+0000, and an expression index over event fields would have to parse the text the same way. The context of every message is in its metadata instead, plain `jsonb`, which holds only identifiers the playbook checks where it takes them, so a query over the metadata column answers every delivery of a definition in a week without opening a row, and the list of runs filtered by definition reads it so (see [The indexes](#the-indexes)). A stream name cannot hold U+0000 on PostgreSQL; the application layer's stream names are made of ids that never do.

An append on PostgreSQL binds ten parameters whatever the number of events, one array per column, so PostgreSQL's own limit of 65,535 parameters in one statement never binds. The ledger still bounds a decision, at 64 events, eight times SQLite's eight, so that a decider that runs away is a defect rather than one long transaction. Code that must run on both stores keeps its decisions to eight events.

Every command is a decision appended under an expected version, so concurrent writers never lose an update to playbooks and definitions. Every server runs a workflow host, and one of them runs the database's workflows at a time, under a claim the workflow host keeps in its own table, so several servers may share the database.

## What a store must provide

The ledger runs on Node, the one runtime the server's image carries, so any of its modules may use Node's own, as the digest of recorded content does with `node:crypto`. Its stores are SQLite and PostgreSQL; on SQLite it binds at most 100 parameters in one statement (`mostValuesTheLedgerBindsOnSQLite`, `src/sqlite-event-store.ts`, `src/projections/sqlite-projections.ts`, and the endings of the kept secrets, read in chunks of 100 ids there and of 65,535 on PostgreSQL, `src/secrets/secret-rows.ts`), and what it asks of a store comes in two parts.

What every store must provide, for the ledger to run at all:

- The event store's own operations, to read a stream or its tail after a version, or the one message at a version, append with an expected version, migrate and close, and a read of a stream's version from Emmett's table of streams, binding two parameters. A command makes at most one append and needs no transaction of its own.
- The read of what a playbook recorded, with the indexes the ledger creates when it opens; each statement binds at most 15 parameters, and none needs a transaction.
- An append on SQLite carries at most eight events: Emmett binds ten parameters for each event it inserts, and the ledger binds at most 100 in one statement there.
- A SQLite database must provide what the reads use: `octet_length` (SQLite 3.43 and later), window functions (3.25 and later), the JSON functions, of which the reads use `json_each` and `json_group_array` (built in since 3.38), and partial and expression indexes (3.8 and 3.9), what the rows of kept secrets use, an `UPDATE` and a `DELETE` with `RETURNING` (3.35), and what the layout of the ledger uses, the literal `TRUE` (3.23); `sqlite3` 6.0.1 carries SQLite 3.52.0.
- No adapter or application may nest a stream under `runs/` within a playbook: the key of a stream's kind ends at the fourth `/`, so the list of runs would take any stream named `runs/<id>/…` for a run.
- Only the entries `src/sqlite3.ts` and `src/postgresql/postgresql-ledger.ts` know which driver is in use; the main and testing entries load neither `sqlite3` nor `pg` (`src/portable-entry.test.ts`).

What a store must provide besides, to keep the keyed projections, the outcomes of runs that a playbook's analytics read and the open requests of interaction functions among them:

- For an append to several streams, a transaction on one connection that each stream's append through Emmett joins, dumbo's `allowNestedTransactions`, which Emmett's drivers set (see [An append to several streams](#an-append-to-several-streams)).
- Inline projections inside the append's own transaction: a read and an upsert of a row for each message of a projection's kinds and types, for each projection, which commit with the append and fail it when they fail. An upsert of one row binds two parameters more than the projection has columns, 12 for the outcomes of runs, and SQLite must provide the upsert (3.24), the `FILTER` of an aggregate (3.30), `NULLS FIRST` and `NULLS LAST` (3.30) and comparisons of row values (3.15).
- An `UPDATE` of one row by its key for the reader's advance, binding two parameters more than the columns it advances.
- On PostgreSQL, the locks of a fold: `pg_advisory_xact_lock` and `SELECT … FOR UPDATE` of each row before it is read, each binding one or two parameters.
- For a scrub, work inside the transaction of an append before it commits, Emmett's `onBeforeCommit`: a read of one message and an `UPDATE` of its data, binding at most four parameters, and for each row it folds again its locks, a read of each lane of its facts in each batch, binding five parameters on SQLite and six on PostgreSQL, an upsert of the row as a fold writes it, and a delete of a row that folds to nothing (see [A fact scrubbed in place](#a-fact-scrubbed-in-place)).
- For the holds on content, a read of a row of the holds of a stream and digest for each digest an append names, or of every row of its stream, an upsert of the rows that changed, binding four parameters for each, and a delete of each row that folds to nothing; on PostgreSQL, the lock of each digest whose row changes; and for a removal, one transaction that takes the lock of its digest, reads whether a row holds it and deletes the head of a content kept before a time, `RETURNING` its upload (see [The holders of content](#the-holders-of-content)).
- A transaction for the fill when the table is created, in which the store's streams are read and the rows written, 8 to an upsert of 96 parameters on SQLite, so that an interrupted fill leaves nothing behind.

Opened without the run outcome mapping and the projections, the ledger neither creates nor writes their tables. SQLite and PostgreSQL provide both parts, so the self-hosted runtime opens the ledger on either with the run outcome mapping and its keyed projections, the open requests, the conversations and the assets of generation functions and their totals, and serves `get_playbook_analytics`, interaction functions and generation functions on both (`packages/server/src/composition/kept-projections.ts`).
