# @on.auto/prediction-onnx

The model runtime of the release for the format `onnx`: [ONNX](https://onnx.ai) models, executed by `onnxruntime-node`, pinned at 1.30.0, behind the contract of [`@on.auto/prediction-contract`](../prediction-contract/README.md). It is an extension as any other is: its main entry exports `manifest`, which fills `prediction/model-runtime` for the format `onnx`, and the server lists it among the extensions of the release, after those its settings list, as [Model runtimes](../../docs/reference/model-runtimes.md) says. The prediction capability, [`@on.auto/prediction`](../../capabilities/prediction/README.md), imports nothing from it, and it imports nothing of the capability but in its tests. User documentation of the signature it checks is [The signature of a candidate](../../docs/reference/prediction-format.md#the-signature-of-a-candidate); update it alongside the check.

## The manifest

`manifest` (`src/runtime/onnx-runtime.ts`) is named `@on.auto/prediction-onnx`, at the version of the release, read from the repository's `package.json`, and provides one model runtime, `onnxRuntime`: the name `onnxruntime-node`, the version of `onnxruntime-node` installed, read from its own `dist/version.js`, the one format `onnx`, every capability, `features`, `given` and `totals`, and a process binding whose module is `src/sessions/model-sessions.ts`, which a model process imports when a job of a candidate or a version of the format asks for it.

## A model's session

`loadModel(path, threads)` (`src/sessions/model-sessions.ts`) turns the telemetry of onnxruntime off, `ORT_DISABLE_TELEMETRY=1` set before its session is made, so a process that loads a model sends that telemetry nothing and leaves no file of it in its temporary folder, then makes onnxruntime's session of the file on `threads` intra-op threads, one inter-op thread, executing in sequence, logging errors alone. It answers the loaded model of the contract: its signature, `{ opset, inputs, outputs }`, each input and output with its `name`, `type` and `shape`, a value that is not a tensor typed `non-tensor`; its length, the second axis of `y` when that is a number; the issue of its signature with what a function feeds, below; and its run, which feeds `y`, `x` and `given` as float32 tensors and `h` as int64, and answers `q` and its dimensions, or `badly` when the model answers no `q` of float32. A failure whose first line names an allocation is thrown again as a `RangeError`, `The model's memory allocation failed: <its words>` (`rethrownNamingAllocation`), so the process loop ends the process as out of memory.

The models cache keeps each file in a folder of its own, named by its digest, so a tensor whose data names a file outside that folder, through `../`, beside it by another model's digest or in another model's folder, finds none and is refused as the model loads.

## The check of a candidate

`signatureIssue(fed, found)` (`src/sessions/signature-check.ts`) is the issue of a model's tensors with what a function feeds, in words, or none: `y` `[1, L]`, `x` `[1, L, F]` with features, `given` `[1, H, G]` with given features, `h` `[1]` of int64 with `accumulates`, and `q` `[1, H, 3]`, or `[1, 1, 3]` with `accumulates`, each float32 but `h`; the first axis 1 or dynamic, `L` any length or dynamic, `H` the longest horizon or dynamic, and dynamic with `accumulates`, `F` and `G` the counts the document names, and no other input or output. Its names are told first, then the type and axes of a tensor, then the opset, which is 13 or later. `opsetOf` (`src/sessions/onnx-opset.ts`) reads the opset from the file's own bytes, the version of the default domain, `ai.onnx` or empty, among the operator sets the model imports, through the protobuf wire format alone, and is 0 for a file that is not a model or that ends inside a field.

## Memory

A model process runs under the limit of every model process, `PREDICTION_PROCESS_MEMORY`. The image's build imports `src/sessions/model-sessions.ts` under `prlimit --data` at 768 MiB, so an image whose runtime cannot load is not built (`packages/server/Dockerfile`), and keeps the binding of onnxruntime of its own architecture alone. Every pull request's build of the image in CI walks a model of 64 MiB over the widest rows the bounds admit under the default 1,280 MiB, and the workflow `Model process memory` searches for the least data under which it walks, as [the capability's measurements](../../capabilities/prediction/README.md#measurements) say; both name this package's paths.

## Measurements

`pnpm --filter @on.auto/prediction-onnx measure:models` writes the mean model and the model of 64 MiB of the measures into a scratch folder (`measure/model-files.ts`) and runs the capability's `measure-models.ts` with this runtime's module and them, whose figures are in [the capability's README](../../capabilities/prediction/README.md#measurements). `pnpm --filter @on.auto/prediction-onnx measure:large-model <path>` writes the model of 64 MiB alone (`measure/large-model.ts`), as CI does.

## Testing

The candidate models are in `candidates/`: small ONNX models, each a graph whose answer the tests know (`candidates/candidate-graphs.ts`), among them a mean, a last value, a model that answers whole numbers or a sequence, one with an input the function does not feed, one that allocates 16 GiB, three whose tensor reads its data from a file outside its own folder, one through `../`, one from a sibling named by its digest and one from another model's folder, one of opset 12, a running total and a file that is not a model. `pnpm --filter @on.auto/prediction-onnx candidates` writes them again from `candidates/build-candidates.ts`, through the writer of ONNX's protobuf form in `candidates/onnx-writer.ts`, byte for byte the same; `src/candidates-testing/onnx-candidates.ts` names them for the tests. `src/sessions/model-sessions.test.ts` loads them in onnxruntime, `src/sessions/signature-check.test.ts` and `onnx-opset.test.ts` hold the check, and `src/sessions/model-process.test.ts` checks, answers and walks a candidate in a model process of the capability through `testPorts` of `@on.auto/prediction/testing`, and holds what such a process loads to the capability, the contract, this package, the engine's process loop, Effect and onnxruntime. The server's tests of prediction functions upload these files through the release's extension, loaded as the server loads it.

## Source

`src/index.ts` is the entry point. `src/runtime` holds the manifest and the runtime it provides; `src/sessions` the module of the binding, the check of a signature and the reader of the opset; and `src/candidates-testing` the candidates the tests name. `candidates/` holds the candidate models and their writer, and `measure/` the models of the measures.
