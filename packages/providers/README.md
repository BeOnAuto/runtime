# @on.auto/providers

The providers a person may connect: services the runtime knows how to reach, each an entry of data, an MCP server or an HTTP API described by an OpenAPI document, with how a credential reaches it and the values that differ from one connection to the next. A person who connects a provider names it and gives those values; the entry gives the rest. This package holds the schema of an entry, the reading of the entries the runtime ships, and the one resolution of a provider and what a caller gives into the addition `@on.auto/connections` takes, which then passes every check a connection given by hand passes. The runtime's code names no provider: every entry is data, handled by the same reading and the same resolution. The package sits above `@on.auto/config`, for the YAML reader, the credential check and the grammar of a placeholder, `@on.auto/tool-servers`, whose `ServerEntrySchema` the server part of an entry picks from, and `@on.auto/definitions`, in whose grammar of a function's tool blocks the conversations part is written and checked, and below `@on.auto/connections`, which depends on it.

## An entry

`ProviderEntrySchema` (`src/entry/provider-entry.ts`) checks an entry whole and names each problem at its place:

- `{name}` in `url`, `document`, `base_url`, the `issuer` of a way or one of its endpoints, a header value or a query value is a placeholder, in the grammar `placeholdersIn` of `@on.auto/config` reads, a lowercase letter and then lowercase letters, digits and underscores; each one placed is declared or set by a choice, and each one declared or set is placed somewhere. A placeholder is required unless `required: false`, and an optional one stands only as the whole value of a header or a query parameter, which is left out where it is not given.
- A placeholder of choices sets other placeholders' values through each choice's `sets`, every choice setting the same names; a name a choice sets is never declared and never asked, and its value is placed as it is written, a host with its dots among them, since nothing but a listed value is ever placed. A choice's value and what it sets hold no `$`, since a reference begins with it.
- `{client_id}` stands only in a header or a query value, and only in an entry whose every way is `client_credentials` or `authorization`, the ways whose connection holds a client id, `holdsAClientId` of `src/entry/credential-ways.ts`, the one place that names them, from which the words of the refusals are made and which `@on.auto/connections` asks too: the one the person gives on Studio's page for `client_credentials`, and for `authorization` the client the connection was made with, recorded when its consent finishes, which the serving of the connection places.
- `marks` names each tool once, by a tool name, and in one of `reads` and `acts`, as `markIssuesOf` of `@on.auto/tool-servers` checks the `marks` of an entry of `tool_servers` too, so one schema, `ServerEntrySchema`, serves both.
- `failure_codes` stands on an `openapi` entry alone, and names its two pointers as JSON pointers into the answer, a list of codes with one code at least, and each code once, as `failureCodeIssuesOf` of `@on.auto/tool-servers` checks an entry of `tool_servers` too. A connection of an HTTP API from the provider takes the entry's `failure_codes` when it is served, as it takes its `marks`, so a release that names them serves the connections made before it. A connection whose recorded type is not its provider's type now is refused when it is served, in words that tell the person who added it to remove it and add it again.
- `conversations` names its tools by tool names, and `reply.sent` and `automatic` as JSON pointers, into the answer and into a listed message, as a function's `deliver` names its own, and each argument of `reply.with` and `react.with` is a template, in the grammar of a function's tool blocks, `templatesIssues` of `@on.auto/definitions/tool-blocks`, over `to`, `sent.conversation`, `sent.id`, `message`, `reply.id` and `reply.to` alone, `conversationTemplates` of `src/entry/conversation-parts.ts`, which renders a value that is text: `message` is the line Auto says, `reply.id` the person's message and `reply.to` the message it answers, empty where it answers none. A problem is refused at its argument, such as `/conversations/reply/with/body/text`, in the words a function's own templates are refused with. `conversationsOf(list, provider, signedInThrough?)` answers the part of the provider a server names, and nothing for a server added by hand, whose provider is `null`, or for a provider whose entry has none; its `read_limit` is kept where the limit names no `clients`, or names the client source `signedInThrough`, and left out otherwise.
- `ending_codes` stands on a way of the kind `authorization` alone, and names the codes with which the way's token endpoint refuses a refresh because the consent has ended, beside OAuth's `invalid_grant`, which ends every consent already and is refused there, `Expected no invalid_grant, which ends a consent at every token endpoint already`, none of the errors OAuth names for a token request that never say a consent has ended, `invalid_request`, `invalid_client`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`, `server_error` and `temporarily_unavailable`, `Expected no invalid_client, an error of OAuth that never says a consent has ended`, each a code of at most 64 letters, digits, underscores, dots and hyphens, from one code to sixteen, and each code once, `Expected invalid_refresh_token once in ending_codes`, as Auto's consent service takes them with a refresh. `@on.auto/connections` reads them from the provider's way when it serves a connection, as it reads `failure_codes`, and a refresh refused with one of them breaks the connection as a consent that has ended, where any other refusal fails the call and leaves the connection connected.
- A pattern is anchored with `^` and `$`, and its example matches it.
- A way of the kind `secret` says how a person makes its key, so none ships without it: `instructions`, Markdown without HTML of 1 to 1,000 characters, a `<` before a letter, `/`, `!` or `?` refused, `Expected Markdown without HTML: write a link as [the page](https://…) and no tag`, which says where the key is made, with a link to that page, the plan or role it needs, the permissions it needs and its format; and `key_page`, the https address of that page, written out from `https://` with no user name or password in it. Its `description` is the short name of the key, the label of the field the person gives it in, such as `GitHub fine-grained personal access token`, apart from the instructions. It may give `example`, what a key looks like in at most 100 characters, with an ellipsis, `…`, in place of the key's characters, so that it never reads as a key, `Expected an ellipsis, …, in place of the characters of the key, as in ghp_…, so that an example never reads as a key`, and `pattern`, beside an `example`, which shows the person the format the pattern holds the key to, the regular expression of at most 200 characters every key matches, by which `@on.auto/connections` refuses a key of another format. Each is `keyFields` of `src/keys/key-fields.ts`, the one place of their checks, which the credential of a connection given by hand takes too; another kind takes none of them.
- A key's pattern is a regular expression JavaScript reads with the `u` flag, from `^` to `$`, of characters, `.`, `\d`, `\w` and character classes, such as `[A-Za-z0-9_-]`, each repeated with `?`, `*`, `+`, `{n}`, `{n,}` or `{n,m}` of at most 1,000, and no group, alternative, lookaround, back reference or lazy repeat, `Expected a regular expression from ^ to $ of characters and character classes, …` (`keyPatternIssueOf` of `src/keys/key-patterns.ts`). The runtime never hands it to the engine of JavaScript to match, whose backtracking a hostile pattern would hang: `matchesKeyPattern(pattern, key)` reads it into its parts, each a set of characters and its bounds, and walks the key once for each part, keeping the places each part can end at, so a check takes time in proportion to the key's length and the pattern's parts, whatever the pattern. It matches no key of more than 8,192 characters, so no check runs longer than one of that length: a pattern of 196 parts against a key of 8,192 characters took 36 milliseconds, measured on 2026-11-05 with Node 26.12.1 on an Apple M4 Max. A pattern the runtime does not read matches no key. The patterns and keys of `src/keys/key-patterns.test.ts` match as JavaScript matches them.
- An address, `url`, `base_url`, the `issuer` of a way and its `authorization_endpoint`, `token_endpoint` and `revocation_endpoint`, and a `document` but `documents/<name>.openapi.json`, writes out its scheme and `://` and holds no placeholder before its host, so no address is a placeholder whole or in its scheme. With every placeholder in its place, and for each choice with what it sets in its place, it is an https URL, or an http URL on a loopback address, so the host of every address of an entry the schema takes is read. `isPinnableTemplate` is the rule for an address with nothing to place in its placeholders, and `pinnedTemplateShape` its words, with which `@on.auto/connections` judges the issuers of the clients whoever runs the runtime registered.
- A reference, `${NAME}`, stands in a header or a query value alone, for a value that belongs to whoever runs the runtime, such as a developer token of their registration at the vendor. A header or a query value is written as a file's entry writes one, `$$` for a `$` that is no reference, since the serving substitutes the provider's references from the runtime's environment; `NAME` is then one of the variables the runtime reads for itself, which `connections.variables` may not name.
- The server part and the placeholders are checked with `credentialProblems` of `@on.auto/config`, so no value that looks like a credential ships; a placeholder's name is never judged as a credential's name, and the entry's prose, `title`, `description`, a way's `description` and `instructions`, and a way's `example`, which holds an ellipsis in place of a key's characters, is not checked for the shape of one.
- A way that asks a `scope` says, in `says`, what a connection can do through each scope it asks, by the scope's name, one sentence of at most 120 characters, `mostSentenceCharacters` of `src/entry/scope-groups.ts`, that opens with a capital letter and ends with its one period, and says nothing of a scope it does not ask: a scope left without words is refused at `/credentials/<n>/says`, `Expected words for the scope files.read: one sentence of at most 120 characters that says what a connection can do through it`, and words for a scope not asked at their key, `Expected words only for a scope the way asks`. The sentence opens with a bare verb, names the provider's own nouns and no person by a pronoun, and is written from the provider's description of the scope, following what the scope grants where those words claim less or more; the schema holds its length and its shape, and `src/reading/shipped-words.test.ts` holds the shipped entries to the rest. The resolution carries the words of the way it takes as the addition's `says`, which `@on.auto/connections` keeps with the connection, and `scopesIn(scope)` answers the scopes of a scope in their order, the one reading of a scope into its names; `scopeWith(scope, added)` answers the scopes of the one with those the other adds, each once and in their order, the scope a consent that asks more asks.
- A way of the kind `authorization` that asks a `scope` grows its grant through `more`, the groups of scopes a later consent may add to it, at least one where it is given, each `{ name, for, scope, says }` (`ScopeGroupSchema` of `src/entry/scope-groups.ts`): `name`, 1 to 32 lowercase letters, digits and underscores, starting with a letter, by which a tool and `reconnect_connection` name the group, such as `share`; `for`, what the group is for in one sentence of the person's words, held to the shape of a scope's words, such as `Share your files with other people.`; `scope`, the scopes it adds; and `says`, their words, under the rule of a way's. A group whose name an earlier group has is refused at its `name`, `Expected a name no earlier group of more has`, a scope that the way's `scope` or an earlier group asks already at its `scope`, `Expected no files.read, which scope or an earlier group of more asks already`, a scope the group names twice there too, `Expected files.share once in the scope of the group`, a scope left without words, or words for a scope it does not add, as a way's are, `Expected words only for a scope the group adds`, and `more` on a way that asks no scope at `more`, `Expected more only on a way that asks a scope, to which each group adds its own`. A consent that asks a group sets the way's `parameters` as any consent of the way does, and nothing more: it names the scopes the connection holds of those it asked beside the group's, so the token it gets holds what the person allowed this connection and no grant of another connection to the same client. `@on.auto/connections` reads a connection's groups from the way of its provider of the connection's kind, so a group a release adds to a provider is offered to the connections made before it.
- A way takes the fields of its kind and no other, and a provider takes one way of each kind, since a kind has one way, whose grant a consent that asks more grows: a way of a kind an earlier way has is refused at its `kind`, `Expected a kind no earlier way has, since a provider takes one way of each kind, and an authorization way names in more what a later consent may add`. A kind the runtime does not take is refused, so no entry ships with one.
- A way of the kind `authorization` names the authorization server by its `issuer`, which also keys the client whoever runs the runtime registered there. `consentIssuesOf` (`src/entry/credential-ways.ts`), which `@on.auto/connections` runs over the credential of such a connection too, refuses a `scope` that is not scopes separated by single spaces, `isScope` of `@on.auto/tool-servers`, the rule a granted scope is held to too, a name among the `parameters` that the authorization request sets itself, `response_type`, `response_mode`, `client_id`, `redirect_uri`, `code_challenge`, `code_challenge_method`, `state`, `scope`, `resource`, `request` and `request_uri`, while `prompt` is taken and replaces the one the request would carry, one of `authorization_endpoint` and `token_endpoint` given without the other, or `revocation_endpoint` given without them, for a server that publishes no metadata, which gives its revocation endpoint beside them where it has one, `pkce` given without them, since the metadata of a server the runtime discovers says the challenges it takes, or on a way whose `clients` are other than `registered` alone, where `pkce: none`, its one value (`WayPkceSchema` of `@on.auto/tool-servers`), says that the server takes no PKCE challenge, so that its start sends none and its finish no verifier, which only a confidential client does without, since its secret or its assertion binds the code to the client where nothing but a challenge binds the code of a public client, and without a challenge nothing ties the code to the start it came from beyond the `state` that guards the return and the single use the server gives a code, a cost of such an endpoint the runtime accepts, and `clients`, the client sources the server takes, `registered`, `metadata_document` and `dynamic` (`WayClientSourceSchema` of `@on.auto/tool-servers`), empty, naming one twice or out of the order the runtime takes them in, `wayClientSources`, the runtime's own order less `auto`, which no way names and a way that takes `registered` takes as well, so an entry never lists `dynamic` before a client whoever runs the runtime registered; it is `registered` alone when left out. `oauth_client: required`, its one value, says that consent runs under the organization's own OAuth client alone, a client the organization registers with the provider and whose client ID and client secret the person gives on the page, so the way names no `clients`, which no other client would take, and is refused with them; a way that leaves it out offers the organization's own OAuth client beside the clients the runtime has, which the listing of `@on.auto/connections` answers as `optional`, or as `required` where no client the runtime has covers the way. The parameters' values are checked for a credential and a reference as the server part is, and the endpoints are judged by their values alone, since the names of the fields name a token.

- A way of the kind `authorization` may name `gateway`, the gateway a connection is made through, a service of whoever runs Auto that makes the consent with its own client, keeps the vendor's tokens itself and hands the runtime a key of the connection's own (Gateway Offloading of Microsoft's Azure Architecture Center: "Offload shared or specialized service functionality to a gateway proxy"): `url`, the https URL, or an http URL on a loopback address, with no placeholder, where the start, the hand-off and the end of a connection are asked; `audiences`, `{ connections, calls }`, the `aud` of the note the gateway takes with those three steps and with a call, two values apart so one note never stands for the other ("The "aud" (audience) claim identifies the recipients that the JWT is intended for", RFC 7519, section 4.1.3); and `claims`, what the note may carry beside the ids, each once: `name`, the person's display name, as OpenID Connect names it, `playbook_name`, the playbook's, and `takes_answer`, `true` on the note of a call that delivers a request, which takes an answer, as the runtime marks such a delivery in its metadata, `auto.on/takes_answer` (`takesAnswerKey` of `@on.auto/tool-servers/policy`), and the host reads it beside the call's request ([the fetch of a call](../tool-servers/README.md#the-fetch-of-a-call)); ids alone where it is left out (`src/entry/gateway-ways.ts`). The runtime reads `url` alone; the rest is for the host that signs the note. Such a way takes `issuer`, the authorization server the gateway's client signs in at, `gateway`, `in` and `name`, and `scope`, `says` and `permissions` beside them, and nothing of a consent the runtime makes with a client of its own, so `parameters`, the endpoints, `pkce`, `clients`, `oauth_client`, `more`, `ending_codes` and `scheme` are refused, `Expected no clients: an authorization way through a gateway takes issuer, gateway, in, name, scope, says, and permissions`. Its `in` is `security`, `Expected in: security, since the key a gateway hands over is sent under a security scheme of the document, in a header of its own`, and `name` names that scheme, which the document beside the entries declares as an `apiKey` in a header other than `Authorization`, in any case, so the key travels in a header of its own and never in the query or in `Authorization`, which the host's note takes (`gatewayKeyProblemsOf` of `src/reading/shipped-providers.ts`, refused at the way's `name` as the entries are read). Only an entry the runtime ships, with its document beside it, names a gateway: one whose document is named by its address, or that has none, is refused at its `gateway` as the entries are read, `Expected a document beside the entries, whose security scheme says the header the key a gateway hands over is sent in`, and a provider whoever runs the runtime adds is refused it (`AddedProviderEntrySchema`), `Expected no gateway: only an entry the runtime ships names one, since the document beside it says the header its key is sent in, and a provider whoever runs the runtime adds names its document by its address`. A gateway URL that is no https URL written out is refused at `/credentials/<n>/gateway/url`, two audiences alike at `audiences/calls`, and a claim the note carries twice at `claims/<n>`. No entry this runtime ships names a gateway (`src/reading/shipped-gateways.test.ts`).
- A way of the kind `authorization` may say in `permissions` whether a connection made through it acts as the app, `application`, or as the person who connects, `delegated`, Microsoft's two "Types of permissions" ("Delegated permissions … allow the application to act on a user's behalf"; "Application permissions … are used in the app-only access scenario, without a signed-in user present"); left out, it is `delegated`, as every sign-in is. The runtime acts on it nowhere, and `list_providers` of `@on.auto/connections` passes it on exactly as a way declares it and only where it does; it is the entry's word for what reads a request sent through the connection.
- `replaces` names the providers the entry takes the place of, the relation Dublin Core names `replaces`, "A related resource that is supplanted, displaced, or superseded by the described resource" (DCMI Metadata Terms), as when a service is connected another way and the connections made the earlier way are to be connected again: an empty list is refused at `/replaces`, a name that is not a provider's name at its place, `Expected a name of 1 to 32 lowercase letters, digits and hyphens, starting with a letter`, the entry's own name, `Expected another provider: a provider does not replace itself`, and a name given twice, `Expected each provider once`. It is data alone, read where a list serves both providers: a provider that is not served, as one a runtime does not offer an org, replaces nothing there, and a provider it names that the list does not hold is passed over.
- `aliases` names the other names the provider is found by, the word Apache Avro's specification gives the names a reader also knows a renamed type by ("Named types and fields may have aliases", [Aliases](https://avro.apache.org/docs/1.12.0/specification/#aliases)): an empty list is refused at `/aliases`, a name that is not a provider's name at its place, `Expected a name of 1 to 32 lowercase letters, digits and hyphens, starting with a letter`, the entry's own name, `Expected another name: the provider's own name finds it already`, and a name given twice, `Expected each name once`.

The fields of a way, `wayFields`, are the one place of the placement, `in`, `name` and `scheme`, of the issuer and of the scope, of the fields of consent, `parameters`, the three endpoints, `pkce`, `clients` and `oauth_client`, of `more` and of `ending_codes`, and of `gateway` and `permissions`, from which the credential of a connection picks its own and the listing of `@on.auto/connections` its fields; the rules of a header's name and of a scheme stay with the connection's credential, where the addition checks them. Which of them are addresses is `wayAddresses` (`src/entry/templates.ts`), the issuer and the three endpoints, from which `consentEndpoints`, the templates, the values an entry is checked by, the resolution, the hosts of a way and, in `@on.auto/connections`, the record's checks and the policy's hosts all take them.

### How a service sends

`events` (`src/events`) says, as data, how the provider's service tells Auto that something changed where a request waits. What arrives makes Auto read the conversation now, through the reading the request already does, Martin Fowler's Event Notification, so a wrong `filter` can only make Auto read sooner or not at all. A destination that proves every byte of what it sends may also say, in `filter.reply`, where a delivery carries the person's reply itself, Fowler's Event-Carried State Transfer, so that Auto need not read to take it; that part names where a reply is, never what it may say. `eventDestinationOf(list, provider, type)` (`src/reading/provider-list.ts`) answers the destination of a type a provider's entry declares, the provider found by any name it is found by, and nothing for a server added by hand, whose provider is `null`, a provider unknown or a type it does not declare, so a shell asks the entry, never a provider's name, whether a request's provider sends what happens where it waits. The pieces that subscribe and receive read the rest as they come. It is checked whole, and every problem is refused at its pointer, as the rest of an entry is.

`destinations` lists the ways the service sends, one of each `type`, in the order the runtime tries them, the first it can take serving, as Stripe's event destinations list a webhook endpoint beside Amazon EventBridge and Azure Event Grid: `webhook`, an HTTP request to the runtime's address; `websocket`, down a socket the runtime opens to the service, as Slack's Socket Mode and Zoom's WebSockets send; and `queue`, into a queue in the company's own account the runtime reads, `kind` naming it as its vendor does, `azure-event-hubs`, `google-cloud-pubsub` or `amazon-eventbridge`. A webhook or a queue says how it is arranged in `per`: `subscription`, by a call Auto makes for each place requests wait in, as GitHub's repository webhooks and Microsoft Graph's subscriptions are made, or `app`, once on the app at the vendor for everyone who connects through it, as Slack's and Zoom's event subscriptions are set. Each destination takes the fields of its type and of how it is arranged, and no other, refused as a way's are, `Expected no topic: a webhook destination per app takes verify, connection, and handshake`:

| `queue` per subscription   | `kind`, `topic`, `subscribe` and `unsubscribe`; `renew`, `lease_seconds` and `needs` where it has them                |

Every destination takes `filter`. Where an arrival says something is written as a runtime expression of its transport, so no field is named in words of the runtime's own: for a webhook, OpenAPI's runtime expressions into the request, `$request.header.<name>`, `$request.query.<name>` and `$request.body#/<pointer>`; for a socket or a queue, AsyncAPI's into the message, `$message.header#/<pointer>` and `$message.payload#/<pointer>`. A call's answer is read by JSON Pointers, as a function's `deliver.sent` reads its own.

- `filter` says which arrivals make Auto read, an event filter as CloudEvents Subscriptions names one (`filters`, "If any filter expression in the array evaluates to false, the event MUST NOT be sent to the sink"): `when`, each expression with the values it may equal, every one of which holds, at least one; `subscription`, per subscription, where an arrival names the subscription it is for, as GitHub's `X-GitHub-Hook-ID` does; `conversation`, where it names the conversation it is about, as the delivery of a request names it in `sent.conversation`; and `automatic`, where it holds something only when an app posted the message, which then makes Auto read nothing, as `automatic` of `conversations` passes such a message over.
- `reply`, within `filter`, says where a delivery carries the person's reply, so that Auto can take it as it arrives, by the rule a reading takes one by, and goes on reading on its timer for whatever no delivery brought. `id`, `sender`, `text` and `to` are where the reply's identity, who wrote it, its words and the message it answers are, the four a function's `replies.read.each` names in a reply it reads, and each is required, since without `to` a delivery cannot say which request it answers; `id` is the very identity a reading lists the reply by, so that a reply is taken once whichever way it came, as CloudEvents lets a consumer take events of the same `id` as duplicates. `time` is where it names when the reply was written, CloudEvents' `time`, "Timestamp of when the occurrence happened", which orders the replies that arrive together and decides nothing else; it is not `verify`'s `timestamp`, when the service sent the delivery. `changed` is where a delivery holds something only when it is no new message, an edit, a deletion or a notice, the change Microsoft Graph's change notifications name in `changeType`, `updated` or `deleted`; such a delivery carries no reply and only makes Auto read, as `automatic` makes an app's own message read nothing. Each is read from the body alone, which the proof covers: `$request.body#/<pointer>`, or `$message.payload#/<pointer>` from a message, refused at its place otherwise, `Expected $request.body#/<pointer>, a runtime expression of OpenAPI into the request, since a reply is read from the body alone, which the proof covers`. A destination declares `reply` only where its `verify` proves every byte of the body and a time, as `standard-webhooks` does, and `hmac` where it signs `{payload}` and a `timestamp`, named in `signed_payload` or a field of the body `{payload}` signs; otherwise it is refused at `/filter/reply`, `Expected reply only where verify proves every byte of the body and a time, as standard-webhooks does, and hmac where it signs {payload} and a timestamp: a secret or a signed token in a header proves who sent a delivery, not that its body is theirs, so such a destination only makes Auto read`, as for `bearer`, `jwt`, whose token is signed apart from the body, and a socket or a queue, which takes no `verify`. It also names `connection`, so that a delivery says whose it is, refused at `/filter/reply` otherwise, `Expected reply only beside connection, where a delivery names the account it happened in, so that a reply is taken only for the connections made in it`, so a destination per subscription, which takes no `connection`, carries none. It also names `conversation` in the same `filter`, refused at `/filter/reply` otherwise, `Expected reply only beside conversation, where a delivery names the conversation the reply was posted in, since a message's id may be unique only within its conversation, so that a reply is taken only for the request sent there as the message it answers`. Only an entry the runtime ships declares `reply`, as [The providers whoever runs the runtime adds](#the-providers-whoever-runs-the-runtime-adds) sets out, and no shipped entry does. The one reader of what arrives reads it, and nothing calls that reader yet.
- `connection`, for a destination of the app, says where an arrival names the vendor's `account`, such as Slack's workspace, and, where the service sends for each person, its `user`, so that the runtime finds the connections it is for.
- `topic`, as WebSub names the unit one subscribes to, is a Liquid template over `with`, the arguments of the call that delivered a request, `sent.conversation` and `sent.id`, rendering the place one subscription serves, such as a repository or a chat, so that the requests waiting in one place share one subscription. It is the one template rendered from what asks for a subscription: the calls below read what it renders, never the place.
- `subscribe`, `renew` and `unsubscribe` are each a call: a tool of the connection, `{ tool, with }`, or an HTTPS request that carries the connection's own credential as a bearer token, in the `Authorization` header as RFC 6750 sends one (section 2.1), `{ method, url, body? }`, its URL `https` and written out up to its host, since the credential goes there, and never both. An entry declares a request only where one of its ways gives a bearer token, read from what the way declares and from nothing else: `authorization` without a `gateway`, `client_credentials`, or a `secret` in the header `Authorization` with the scheme `Bearer`, the name and the scheme read whatever their case, as HTTP reads them (RFC 9110, sections 5.1 and 11.1). An entry none of whose ways does, such as one whose key goes in the query, in a header of the vendor's own name or under a security scheme of its document, as the key a gateway hands over does, has each request refused at its call, `Expected tool: a request carries the connection's credential as a bearer token, and no way of this entry gives one`, and calls a tool of the connection instead, which places the credential as the way says. Their templates read `topic`, what the destination's `topic` renders, as WebSub's subscription request names what it subscribes to in `hub.topic`, so that a call is the same whichever request asked first, and a part of it is taken with Liquid's own filters, `{{ topic | split: "/" | first }}`; a template that reads the place, `with`, `sent.conversation` or `sent.id`, is refused as one that reads anything else its call does not have, `Reads with, which a template of the call that unsubscribes does not have; it reads topic, subscription.id and subscription.expires_at`. They also read what each call has: subscribing, the runtime's address, `webhook_url`, the name n8n gives it, or `queue_url`, and for a webhook the secret Auto makes, `secret`, WebSub's `hub.secret`, placed in a request's `body` or a tool's `with` and never in a URL, where it is refused, `Expected {{ secret }} in body, not in url`, since a URL is logged along the way (RFC 6750, section 2.3) and WebSub sends `hub.secret` in the body; renewing and unsubscribing, `subscription.id` and `subscription.expires_at`; subscribing and renewing, `lease.seconds` and `lease.expires_at`, WebSub's lease. `subscribe.subscribed` points to the `id` of the subscription in what the call answers, and where the service answers them, to when it lapses, `expires_at`, and to a `secret` it made; `renew.renewed.expires_at` to when it lapses after. A destination that `renew`s gives `lease_seconds`, the most a subscription lasts, or the `expires_at` subscribing answers. No subscription is made without `unsubscribe`, so Auto never arranges what it cannot remove.
- `needs` names the group of `more` of the entry's authorization way whose scopes subscribing takes, where the way's own scope does not cover it.
- `verify` is the proof of a delivery, taken before anything is read, from a header alone, never from an address or from the message: `hmac`, a keyed hash, with its `hash`, `sha256`, `sha384` or `sha512`, its `signed_payload`, Stripe's word, `{payload}`, the body as sent, once, joined to `{timestamp}` and `{id}` where the service signs them, as Slack's `v0:{timestamp}:{payload}`, the `signature` header, its `prefix`, such as `sha256=`, its `encoding`, `hex` or `base64`, and where the delivery's `timestamp` and `id` are; `standard-webhooks`, a delivery signed as the Standard Webhooks specification signs one, whose headers it fixes; `bearer`, the secret itself in the header `token` names, after its `prefix`, as RFC 6750 defines a bearer token; and `jwt`, a JSON Web Token in that header, signed by `alg`, `HS256`, `HS384` or `HS512`. `secret` says which secret proves it: `subscription`, the subscription's own, which Auto makes, placing `{{ secret }}` in the call that subscribes, or the service answers at `subscribed.secret`, one of the two; or `app`, the app's own, set once on the app at the vendor, which a destination per app always takes.
- `handshake` is how the service checks the address before it sends, WebSub's verification of intent: the arrival it is, by `when`, where its `challenge` is, a `response` of JSON fields, each the `challenge` as it came or its `hmac` under the destination's secret, beside an `hmac` proof alone, or the challenge as text where it gives none, as Slack's `url_verification` takes and Zoom's `endpoint.url_validation` answers with `plainToken` and `encryptedToken`; and `signed`, whether the service proves it as it proves a delivery.
- `open` is how the runtime finds the socket's address: an HTTPS request of the app, its `method`, `GET` or `POST`, and its `url`, `https` and written out whole, which carries the app's `credential` as a bearer token, and the JSON Pointer to the `address` of the socket in what it answers, as Slack's `apps.connections.open` takes the app-level token in the `Authorization` header and answers `url`; a URL that is not `https`, or holds a template, is refused at `/open/url`, `Expected an https URL written out whole`. A socket serves every connection of the app, and its service answers the address only to the app's own value, so `open` names no tool, which a connection calls with its own credential, and no fixed `wss` address, at which the entry could not say how the app proves itself. `credential` names the value of the app that opens it as its vendor names it, such as Slack's app-level token, `app_level_token`; `acknowledge` is where a message names the id the runtime acknowledges it by, as Slack's `envelope_id`; and `heartbeat_seconds` how often the service asks for a heartbeat.

The part holds no credential: a value that looks like one is refused, `Looks like a credential, which a provider's entry never holds: Auto makes the secret of a subscription, or keeps the one the service answers`, and a template holds no `${`.

One reader reads what arrives as a destination declares it, `arrivalReadingOf(destination, arrival)` (`src/events/arrival-readings.ts`), and nothing that runs calls it yet: the addresses and sockets that receive will, each after it has checked the proof `verify` declares. The same reader reads that proof, `presentedProofOf(destination, arrival)`, and checks none of it: the `signature`, the `timestamp`, the `id` and the `token`, each from where `verify` says it is, a time as text or as a number a body holds, and, for `standard-webhooks`, the request's headers, read by name whatever its case, since the specification names its own; and nothing for a message, for a destination that declares no `verify`, or for an arrival that lacks a part `verify` names or holds it as empty text. `checkedProof` of `@on.auto/identity` checks what it reads, with the secrets and the body's bytes as they arrived, so that this package holds no secret and no cryptography. An arrival is an HTTP request, its headers, its query and its body parsed as JSON, or a message, its headers and its payload, as AsyncAPI's message names them. An expression's value is read as OpenAPI and AsyncAPI define it, by the grammar the checks use (`src/events/runtime-expressions.ts`): a header by its name whatever its case, as HTTP's field names are (RFC 9110, section 5.1), the values of one name joined by a comma and a space, as a recipient may combine them (section 5.3); a parameter of the query by its name as written; and a field of the body, of the message's headers or of its payload by its JSON Pointer, as RFC 6901 resolves one, `~1` a slash and `~0` a tilde, an array's item by an index written without a leading zero, and only a member the object itself holds. A condition holds where its expression's value is text equal to one of its values, and a `when` where it names one at least and every one holds; an expression holds something where its value is neither missing nor `null`, as the reading takes `conversations.automatic`. The reading has a part for each thing an arrival is, each only where it is that, so that a part added later changes none: `handshake`, where `handshake.when` holds, with the `challenge` where it is text that is not empty; `wake`, where `filter.when` holds and `automatic` holds nothing, with the `subscription` and the `conversation` where each is text that is not empty, a wake that names neither still waking, so that Auto reads whatever waits through the connection; within it the `reply`, where the wake names its conversation, `changed` holds nothing, the connection names its account, `id`, `sender` and `to` are text that is not empty and `text` is text, empty or not, with `time` where it is text or a number; and `connection`, with the `account` and the `user` where each is text that is not empty, read whether or not the arrival wakes. It names no service and reads only what the entry declares, and it holds no clock, no secret and no network.

One performer makes the calls a destination per subscription declares, `subscriptionCallsOf(ports)` (`src/subscriptions/subscription-calls.ts`), and only the loop below calls it, which records what it answers. `subscribe`, `renew` and `unsubscribe` each render the call's templates with the renderer of a function's tool blocks, `renderedArguments` of `@on.auto/definitions/tool-blocks`, over the names the call's set gives it: `topic`, as the asker rendered it; for `subscribe`, the address deliveries reach, `webhook_url` or `queue_url`, which the port `callbackOf` answers, and, where the call places it, the `secret`, which the port `madeSecret` makes and the call never makes itself; for `renew` and `unsubscribe`, `subscription.id` and, where it is known, `subscription.expires_at`; and `lease.seconds` and `lease.expires_at`, the lease from the clock's now, where the destination declares `lease_seconds`. A call whose templates cannot be rendered, as one that reads `subscription.expires_at` of a subscription whose lapse is not known, sends nothing. The call is made through the connection, by the port: a tool of the connection by `callOnce`, the call the tool access of `@on.auto/tool-servers` makes, asked to keep no content of the call, `recordContent: false`, whatever the connection's `record_content`, since its arguments may hold the secret Auto made and its answer the secret the service made; or a request by `requestOnce`, the tool access's own way to send a request an entry declares, which keeps nothing, its URL rendered and still `https` at the origin the entry writes out, or nothing is sent. Where `callbackOf` answers no address, as on a runtime nothing outside reaches, a webhook is not subscribed and nothing is sent, while a queue the runtime reads is; a socket's destination arranges nothing. What the call answers is read by the entry's pointers with the reader of a function's tool blocks, RFC 6901's, in an answer no larger than one Auto reads by pointers: the subscription's id as text or a whole number, when it lapses as an RFC 3339 time (JSON Schema's `date-time`), a time in any other form left out, and the secret the service made, as text, held `Redacted`. Only `subscribe` needs an answer: an `unsubscribe` or a `renew` answered with nothing, as a request answered with no body, is done. A failure is a `SubscriptionCallFailed` with two words: `because`, the word the tool access answered, which for a call or a request that was sent and failed is the reason the connection layer gave, the word a call refused before it was sent carries, such as `scope_lacking` or `key_refused`, and its outcome where the layer gave none, or `unreadable` for an answer without what its entry declares, or `not_sent`; and `kind`, what it comes to, `connection_broken`, `scope_lacking`, `tool_error`, `unreachable` or `not_sent`. A failure holds nothing the service said, so a secret the service echoes is in no failure, log or span. It stores nothing: the subscription's id, when it lapses and whose its secret is are the caller's to record.

One loop decides which subscriptions a playbook holds with the services of its connections and arranges them, `subscriptionLoopOf(ports)` (`src/subscriptions/subscription-loop.ts`), and the server runs it for a playbook as due work of its workflow host, one round of a playbook at a time, after each fact after which a request may wait in another place and when the record says the playbook is next due (see the server's README). It is a control loop over desired and current state, as Kubernetes' controllers are ("Controllers", kubernetes.io/docs/concepts/architecture/controller): each round reads what is wanted and what is recorded, decides with one pure function, `decided(situation)` (`src/subscriptions/subscription-decisions.ts`), acts on the difference through the performer above (`src/subscriptions/subscription-acts.ts`), and answers when it next has work, `nextDueAt`. It holds nothing between rounds, so a round cut anywhere is made good by the next one. What is wanted is each pair of a connection and a topic that at least one asker names, an open request or a saved trigger, each behind the one port shape `Asker`, which is given the destination arranged for each connection and renders its topic over it; the loop never asks who wants a topic, only whether anyone does, so two askers share one subscription, and it stays while either asks. A connection's destination is arranged only where its entry declares it, in the entry's order, the first the runtime can take serving: one the runtime receives that way, `receives`, and, for a webhook or a queue, one whose address deliveries reach the runtime knows, `callbackOf`. Where that first destination is per subscription, the loop arranges it; otherwise the app or a socket serves, or the reading on its timer. So a runtime nothing outside reaches never arranges a webhook, and still arranges a queue it reads.

A removal is idempotent, as HTTP says of `DELETE` (RFC 9110, 9.2.2) and controller-runtime's `client.IgnoreNotFound` does on a delete: an `unsubscribe` the service answers `not_found`, that it has no such subscription, is a removal done, whatever took it away (a person in the service, the place deleted, a stop of Auto's between the service's removal and its record). A subscription nobody wants whose removal the service refuses (`tool_error`, as through a tool, which answers no status) is forgotten, with its secret, rather than held, since holding it would keep its place under the bound for ever and free nothing; it may still deliver to Auto's address, where nothing names it, as for a removed connection. A removal Auto cannot make for want of the sign-in or a permission is held until the connection is connected again, as before. What is recorded comes and goes through `records`, keyed by the playbook, the connection and the topic, which `@on.auto/connections` keeps on the ledger. The classes and the reasons of a failure are `SubscriptionFailureKindSchema` and `SubscriptionFailedBecauseSchema`, the reasons read from the performer's own table of which class each falls under, so a fact that records them reads none it does not class. A request's topic is `topicOf(destination, place)` (`src/subscriptions/subscription-topics.ts`): the destination's `topic` rendered with the renderer of the tool blocks over the request's place, `with`, the arguments of the call that delivered it, and `sent`, where it was sent, at most one byte past the bound of a part, and nothing where the destination declares none, the template does not render or renders nothing. Three facts, as Event Sourcing keeps what happened: `made`, with the destination's type, the app's id for the subscription, the id of its secret in the secret store and never the secret, and the digest of the declaration it was made by; `failed`, with the performer's `kind` and `because` and what the attempt saw, when the connection was last connected and that digest, or nothing where no call was attempted; and `removed`. Beside them, positions moved in place and not recorded as facts, as a Kafka consumer commits its offset: the lease's end, the next due time and the faults that passed in a row, which restart at their defaults after a rebuild. The loop subscribes what is wanted and missing; renews what is due, halfway through its lease, as DHCP renews a lease at T1 (RFC 2131, section 4.4.5), and at once where its positions were lost and its destination lapses; subscribes again where the destination declares no `renew`, where the lease has lapsed, or where the renewal reads the end of a lease a rebuild forgot; replaces a subscription made by another declaration or through another destination, unsubscribing it first; unsubscribes what is no longer wanted; and forgets, without a call, what cannot be called or what the app has already ended: a subscription whose connection or declared destination is gone, or whose lease has lapsed. Where subscribing again answers a new id or a new secret, the subscription is removed then made, the old one unsubscribed where it has a different id; where it answers the same id and secret, it was a renewal, and nothing is recorded. Auto makes the secret through `secrets` before the call that places it, gives the one it holds when it subscribes again, keeps the one the service answers where it differs, and forgets a secret no subscription holds. A failure is recorded once. One that will not pass by itself, every `kind` but `unreachable`, holds the subscription's acts until the connection is connected again or its declaration changes, as a Kubernetes controller acts again on a changed `generation`; one that passes, `unreachable`, is tried again after the wait of the connection backoff the socket uses, and on a subscription already made it is not recorded. One that passes is the same failure for as long as its kind and the attempt's generation stay the same, whatever its reason, so an outage whose reason changes from one try to the next records one fact, not one a try. A subscribe sent and not answered in time, `timed_out`, may have been made by the app: one whose declared `method` is idempotent, `GET`, `PUT` or `DELETE` (RFC 9110, 9.2.2), makes no second subscription when it is repeated, and is tried again after the usual wait; any other, a `POST`, a `PATCH` or a tool, is tried again no sooner than `resyncedAfterMs`, the period after which the loop looks again at whatever it holds. So an app that keeps making the subscription and answering too late gets at most one subscription Auto does not know for each of those periods, rather than one at every try; a connection cut after the call was sent, and a stop of Auto's while the call is out, are tried again as before. Through one connection the loop makes no subscription past `mostPerConnection`, counting every one it holds there, wanted or being removed; past it, the rest are recorded failed, `not_sent`, without a call, and taken in the order of their topics as room is freed, a removal under way making the rest wait for it rather than fail. A topic the record cannot hold, `holds`, is not arranged, and an id the app answers that it cannot hold is unsubscribed at once and recorded failed, `unreadable`. A stop between the app's answer and the record leaves one subscription Auto does not know: the next round makes the one Auto then records, and no other. The loop logs nothing and adds no span.

A `websocket` destination is received by `receivingOverASocket(listening)` (`src/sockets/socket-listening.ts`), which nothing starts yet: Hohpe and Woolf's Event-Driven Consumer over a Channel Adapter. It is given the destination, the value of the app its `credential` names, held as `Redacted`, and two ports (`src/sockets/socket-ports.ts`): `opens`, which opens the socket outward, given the destination whole and the value at each opening, and `arrived`, which is handed the reading of each message and nothing of the message besides, since the format refuses `reply` on a socket, so its arrival only wakes. How `open` is made into an opening, the call that answers the address and where the value is sent, is the opening's, below. Each message's text is parsed as JSON and read as a message whose payload it is, with no headers, since a message of RFC 6455 has none (`src/sockets/socket-messages.ts`); a reading that has a part is handed on, and a message whose `acknowledge` names an id, text that is not empty or a number, is then acknowledged by the JSON object that holds the id at the place the expression names, as Slack's Socket Mode takes `{"envelope_id": …}`. That is delivery at least once: a message `arrived` could not take, where it dies, is logged and left unacknowledged, for the service to send again, and the socket goes on. Every `heartbeat_seconds` it sends a Ping (RFC 6455, section 5.5.2, a keepalive), and closes a socket from which nothing, a Pong or a message, was heard between two Pings, as the `ws` library's README detects a broken connection. After every end, a socket closed by the service, one it closed for its silence, or an opening refused or not open within 20 seconds, it opens another after a wait that grows as gRPC's connection backoff does (`doc/connection-backoff.md` of grpc/grpc): 1 second, then 1.6 times longer for each end in a row, at most 120 seconds, each spread by up to 20 % either way, and 1 second again once a socket has opened, so a close is never followed by an opening at once (RFC 6455, section 7.2.3, asks for a backoff). It logs each end with its wait, and a close's code where it names one, and never the value or a message's content. Its clock and timers are Effect's `Clock`, so its tests drive them with `TestClock` against the fake socket server of `src/testing/socket-servers.ts`.

The opening is `opensAsDeclared(ways)` (`src/sockets/socket-openings.ts`), an `OpensASocket` that nothing composes yet, built on two ports of its own (`src/sockets/socket-ports.ts`): `sends`, the bearer request, whose shape `bearerRequestOnce` of `@on.auto/tool-servers` has, and `constructs`, the socket's constructor, as the WebSocket standard names `new WebSocket(url)`; beside them `sending`, the fetch, what the runtime reaches and the bounds of a call, which the request and the answered address share. It sends `open`'s request, its `method` and its `url` and no body, with the app's value as the one bearer token, in the `Authorization` header as RFC 6750 sends one (section 2.1), to the origin `open.url` writes and to no other, so the value goes to no host but the one the entry names; it sets that origin and that value itself, from the destination and the opening, and takes neither, nor a connection to mark broken, from whoever composes it. The send refuses an `http` URL, one that names a user, a host the runtime does not reach, and follows no redirect, as it does for any request an entry declares. The socket's address is read at the JSON Pointer `address` in what a successful request answered, and a socket is opened only where it is a `wss` URL that names no user and whose host the runtime reaches, checked by the same `reaches` before the constructor is called. From there the address is held `Redacted`, since it may carry a one-time ticket, and the constructor is handed the address alone, never the value, so nothing of the app's credential reaches the socket's host. Anything else, a refused value, a redirect, an answer that is no success, a pointer that finds no text, an address that is not `wss`, a host the runtime does not reach or cannot look up, ends as `SocketEnded`, `not opened`, with nothing opened and nothing of the value, the answer or the address in it, and the adapter opens again after its wait. The opening logs nothing and adds no span: the request's own span holds its method, its origin and its outcome's word. The constructor it is handed follows no redirect either, as the WHATWG WebSocket standard's does not.

`requestOriginsOf(entry)` (`src/events/event-destinations.ts`) answers the origins the calls of a subscription written as requests, `method` and `url`, are written out to, each once: the hosts the entry's author says the connection's credential may go to beside its own server. A URL the format takes that `URL.parse` cannot read, such as one with a port past 65535, names none, so no credential goes to it and reading never throws. A call that is a tool names none, and so does a socket's `open`, whose request carries the app's value and not a connection's. `@on.auto/connections` gives them to the tool access with each connection it serves.

### An app's events, as Slack sends them

No shipped entry declares `events` (`src/reading/shipped.test.ts`): a provider that hears its service's events is one whoever runs the runtime adds. An entry that hears the events of a Slack app declares a `webhook` destination `per: app`, since Slack sends every event of an app to the one Request URL set on the app, for each workspace and person it is installed for ("The events sent to you are directly tied to the OAuth permission scopes granted as users install your Slack app", docs.slack.dev/apis/events-api). The proof is the app's signing secret, as Slack's page on verifying requests sets it out: `v0=` and the hex HMAC-SHA256 of `v0:{timestamp}:{payload}`, in `X-Slack-Signature`, with `X-Slack-Request-Timestamp`; the handshake is the `url_verification` whose `challenge` is answered, signed as every request is; it wakes on an `event_callback` whose event is a `message`, names the conversation at `event.channel`, which is what `sent.conversation` reads of `chat.postMessage`'s answer, and passes over a message an app posted, `event.bot_id`, as `conversations.automatic` does. The `connection.account`, which a destination of the app must name, is the outer `team_id`, the workspace of the installation Slack sent the event for, which is not always the workspace the conversation began in: in a channel shared between two organizations, Slack's page says the outer `team_id` "will mirror the first element in the `authorized_users` array", which may be the other organization's installation (docs.slack.dev/apis/slack-connect, read 12 Nov 2026). So a reader that finds the requests an event is about finds them by its conversation, never by `team_id`, and keeps `connection.account` for what the field says, whose installation the event was sent to. Whether an event reaches an installation is the app's own setting at Slack, not the entry's: the entry says only what an event looks like once it arrives.

## The shipped entries

`readProviders(shippedFiles)` (`src/reading/shipped-providers.ts`) reads the entries once, at start, from `src/entries` of the package, `shippedEntries`, with a listing of the folder, through the `ShippedFiles` of `@on.auto/shipped-files` it is given, which the server composes, then `readYaml` of `@on.auto/config` and the schema, and answers `ProviderList`: the providers sorted by their names, not by the names of their files, and `documents`, each document beside the entries as its text and the bytes it takes, both of the bytes read through the same reader while the entry naming it is checked (`shippedDocumentOf` of `@on.auto/tool-servers`), keyed by the name the entry writes, which the tool servers describe the provider's API from, so no package reads a shipped document again. A provider is its entry and its `address`, the address its calls go to as the entry writes it: `url`, `base_url`, the first server a document beside the entries names, read at start, or the URL of a document that is not. ### Other names

`providerFoundBy(list, name)` (`src/reading/provider-list.ts`) is the one resolver of a provider by a name: the provider whose `name` it is, else the one whose `aliases` hold it, and nothing for a name no entry declares or for a server added by hand, whose provider is `null`. `providerNamed`, `conversationsOf`, `rendersOf` and `eventDestinationOf` each find their provider through it, so each answers by any name a provider is found by, and `providerNamesOf(entry)` answers those names, its own first, for a shell that matches a name it is handed against a list of its own, as the hosted runtime's gateways and wakes do. With no entry declaring `aliases`, every answer is the one a lookup by `name` alone gave.

Within a list no name finds two providers, the rule Avro's specification gives aliases: "Aliases are alternative names, and thus subject to the same uniqueness constraints as names." `readProviders` refuses an alias that is another entry's name or alias, at each entry that declares it, `Expected a name no other provider is found by: the provider notes is found by notes`, as it refuses any problem of an entry, and the setting of connections of `@on.auto/connections` refuses one among its own providers in the same words (`aliasesTakenIn` of `src/entry/provider-names.ts`); `joinedProviders` keeps a joined list so too.

A name an entry gives in `replaces` names the provider it finds, by its name or one of its aliases, so an entry replaces a provider by any name it is found by: `replacementOf(list, provider)` answers the provider whose entry replaces the one the name given finds, whichever of its names either uses, and `replacedNamesOf(list, entry)` the providers an entry replaces by the names the list gives them now, each once, and one the list does not hold as it is written, so a listing never shows a name a provider had before. An entry is never found by a name it replaces, `Expected a name the provider does not replace: a provider is not found by the name of one it replaces`, at the alias, so a provider asked by any of its own names is never one it replaces.

`asNamedIn(list, { provider, document })` answers a provider's name and its document as a connection recorded them, read as the list names them now: where the name recorded is another name of a provider, that provider's own name, and where the document recorded and the provider's own are both documents beside the entries, the provider's own, since such a document is a file of the release, `documents/<name>.openapi.json`, and never a value of the org's; where the name recorded is the provider's own or no provider's, both as recorded. `@on.auto/connections` reads every connection's addition through it, so a release that renames an entry, its old name kept as an alias, serves the connections made before it under the new name without rewriting any fact ([The facts and the fold](../connections/README.md#the-facts-and-the-fold)).


The translation, `src/translating/translate-discovery.ts`, takes each path from the method's `flatPath`, writes each method's scopes as its `security`, one requirement for each, since any one of them serves, keeps the `fields` parameter that trims an answer and the global parameters a manifest's `global_parameters` name for a method, and writes none of the other global parameters, which a call never needs, nor the media upload of a method a manifest's `uploads` does not name. It writes the operations in the order of the methods kept, and the query parameters, the schemas, their keywords and their properties and the scopes by name, since a Discovery document lists them in an order that differs from one fetch to the next, so a document made again differs from the one committed only where the vendor changed what it describes.

| `scheme`                | The `name` of the one `oauth2` scheme every operation requires; where an operation lists its scopes, either the keys, each inside the one before, it lists them under, `scopes_at`, as Zoom's vendor extension holds them, or the scheme of the vendor's document whose requirement in the operation lists them, `scopes_from_scheme`, as Amazon's `OAuth2` does, exactly one of the two, a scheme that writes both or neither being refused; and the endings of the scopes it leaves out, `leaving_out`, with `because`; or, in place of the four, `lists_no_scopes`, why no operation lists a scope, the vendor's documents naming none, so every operation requires the scheme at the document's root alone, as a converted Swagger document's does |
| `keeps_responses`       | Whether the operations keep the answers the vendor describes, or say only that they answer                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

The translation, `src/translating/translate-openapi.ts`, writes each kept operation at its path with each value in its place, with the parameters its path declares before its own, but one it declares itself in the same place by the same name, requiring the scheme at the document's root and once for each scope the operation lists and keeps, any one of which serves, in the order of their names, since a vendor may list them in another order from one fetch to the next; `src/translating/oauth2-scheme.ts` writes the scheme and those requirements for every kind alike. The sources must name the same version of OpenAPI and the same servers, which the document names. A kept operation's `$ref` is carried with what it reaches: the document holds each component the kept operations refer to, and those the components refer to in turn, from the source that holds the operation, and no other, and refuses a reference to a component its source does not hold, and one two sources hold each their own way. Where the `discriminator` of a schema, in a component or in an operation, maps a value to a schema the document does not hold, by its reference or by its name, which names `#/components/schemas/<name>`, the translation leaves that entry of the mapping out, since a mapping names the subtypes of a schema where no `$ref` reaches them and a subtype is carried only where one does; it reads the keyword in schemas alone, walked by `mappedSchema` of `@on.auto/tool-servers`, and never a property or an example of that name. The translation also refuses, in words, an operation no source holds or two hold, a parameter or a schema the manifest names that its operation lacks, a manifest's change to an operation it does not keep, a description left out of an operation that has none, a path value no kept path holds, and an operation that lists no scope the scheme keeps. The vendor's descriptions, examples and answers stay as the vendor wrote them, so the bytes one run writes differ from those committed only where the vendor changed what it describes. The command fetches the sources and the metadata and writes the document alone, its manifest being read and never written. Every kind of translation fetches each address once in a run, however many manifests name it, and reads its answer with `documentInText` of `@on.auto/tool-servers`, the reader of a tool server's document, as JSON or, where it is no JSON, as YAML; an address that answers with a failure refuses every kind in the same words, `<address> answered 404, so nothing is translated from it`, and one that answers no document in JSON or YAML, or YAML that is no mapping, in words that name the line and the column.

## Converting Swagger documents

Some vendors publish Swagger 2.0 documents, some beside OpenAPI 3 ones, whose operations the runtime cannot use as they are: it reads OpenAPI 3, and Swagger 2.0 writes parameters, bodies and schemas another way. A document converted from them has a manifest of the `type` `swagger` beside it, read by the same command and module:

| Field                     | What it holds                                                                                                                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sources`                 | Each the `address` of a vendor's document in JSON or YAML, Swagger 2.0 or OpenAPI 3, fetched as it is named, and the `operations` the document keeps from it; `<name>=<file>` is refused, as for OpenAPI documents |
| `authorization_server`    | The address of the metadata of the authorization server, whose `authorization_endpoint` and `token_endpoint` the `oauth2` scheme of the document names, as for the other kinds                                     |
| `info`                    | The `title`, `version` and `description` of the document made                                                                                                                                                      |
| `path_prefix`             | The `prefix` every kept path starts with, left out of each path with the path parameter it holds, since the entry's `base_url` gives it, with `because`                                                            |
| `headers_left_out`        | The `names` of the header parameters left out of every operation, since the runtime or the entry sends them, with `because`; the conversion writes no header, so it refuses any other                              |
| `lists_as_text`           | Why a list in a query is written as one string, its values comma-separated, which its description lists                                                                                                            |
| `boolean_values_left_out` | Why a boolean parameter keeps no list of values                                                                                                                                                                    |

The conversion, `src/translating/swagger-conversion.ts`, writes an OpenAPI 3.1 document: each kept operation at its path below the prefix, with its tags, summary and description, its path and query parameters, its body as a JSON request body and its answers as JSON content, an answer the vendor does not describe named by its status. A query parameter keeps its type, format, default, values, minimum and maximum, and where its description is joined to the values of a list, the description ends its sentence first. `src/translating/schema-conversion.ts` reads each source and writes the schemas the kept operations reach, and those they reach in turn, as OpenAPI 3.1 writes them, a `nullable` type as one that takes `null` and an `example` as `examples`, and refuses a schema its source lacks and one two sources hold each their own way. The document requires its `oauth2` scheme at its root, which `oauth2-scheme.ts` writes, with no scope, since the vendor's operations name none; it writes the operations in the order the manifest keeps them and the schemas by name. The conversion also refuses, in words, an operation its source does not hold or holds twice, a parameter in a place it writes nowhere, and a path that does not start with the prefix.

## Source

`src/index.ts` is the entry point, and `translate-documents.ts` the command `documents:translate` runs, which writes what `src/translating/document-manifests.ts` translates: the command reads the manifests through `shippedFilesOnDisk(providersShippedRoots())` of `@on.auto/shipped-files/on-disk`, and the file a `<name>=<file>` names, which is no file the package ships, itself, and writes each document the translation answers as a file of the package where it is shipped. `providersShippedRoots()`, of the main entry, answers the root of the package, which the server gives the reader it composes, only when it is called, so the entry loads where `import.meta.url` names no file (`src/reading/shipped-providers.test.ts`). `src/entry` holds the schema of an entry, its ways, its placeholders and the reading of its templates; `src/reading` the reading of the shipped entries, the list and what a provider reaches; `src/resolution` the resolution and the checks of a placeholder's value; `src/sockets` the adapter that receives the messages of a `websocket` destination, the opening its `open` declares, and their ports; `src/subscriptions` the performer of a destination's `subscribe`, `renew` and `unsubscribe`, and the loop that decides and arranges a playbook's subscriptions, with their ports; `src/translating` the translations of a Discovery document and of OpenAPI documents, the conversion of Swagger documents, the `oauth2` scheme they write, and the reading of the manifests of each kind; `src/entries` the shipped entries, their documents and the manifests of those translated; `src/testing` what the tests share, and `src/testing/index.ts`, the entry `@on.auto/providers/testing`, the fixture providers `tracker`, `ledgers`, `regions` and `metrics` and their list, `fixtureProviders`, `drive` and `adverts`, whose way is consent, the one discovering its server's metadata and the other giving its endpoints with a placeholder in them, and `audiences`, whose header holds `{client_id}` beside its way of consent, `providerOf(entry, documentServer?)`, `providerListOf(...providers)` and `providersOf(...entries)`, which the tests of the resolution and of the connections use in place of the shipped ones.

The runtime's `pnpm docs:providers`, `scripts/docs-providers.ts`, publishes what a reader may be shown of the shipped entries as `docs/assets/providers.json`, which the website's integration pages are made from: each provider's title, description, website and the hosts of its server; its ways, each with its description, the words of the scopes it asks and of the groups of `more`, whether it takes the organization's own OAuth client, and for a key where it is made and how; its placeholders with their descriptions and choices; whether it handles money; and, for an HTTP API whose document lies beside the entries, each operation of the document as the tool the runtime lists, by its `operationId`, with its mark, by the entry's `marks` first and its method after. No issuer, endpoint, header, query parameter, pattern or example is published. `pnpm docs:check` fails while the asset differs from the entries, so a changed entry ships with the asset made from it.
