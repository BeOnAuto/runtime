# @on.auto/secrets

The secret store of the runtime: what it must hold to act for someone, such as a key a person pasted, a client secret whoever runs it registered, a registration it made for itself or the tokens a person's consent gave it. The server opens the store at start and gives it to the connections of [`@on.auto/connections`](../connections/README.md), which keep in it the credential a person gives, through their port `SecretKeeping`. Behind the store are three seams: the **rows**, which keep the bookkeeping of each secret and which the ledger implements over SQLite and PostgreSQL, as its README's [Kept secrets](../ledger/README.md#kept-secrets) says; the **keeper**, which holds each value; and the **custodian**, which holds the key that wraps each value's own data key. This package holds the store, the three ports, the custodian of a key in hand and the custodian of a key in AWS KMS, and the keeper that seals a value into its row and the keeper of values in AWS Systems Manager Parameter Store, so the ledger knows no key, the connections know no ledger, and only the `aws` subpath loads any part of the AWS SDK, which a server whose settings name no key in KMS and no keeper in Parameter Store never imports.

## Words

- **The secret store**: `SecretStore`, what the connections are given: `keep`, `read`, `replace`, `claim`, `endingsOf` and `forget`, with `rotated`, `moved` and `close` for the server.
- **A row**: the record of a secret: its id, its version, its claim, its ending, when it was kept, and its holding.
- **A holding**: how a value is held, `{ keptBy, held, wrappedKey?, kid? }`: the keeper that holds it, what the keeper handed back, and for a sealed value the wrapped data key and the custodian's kid.
- **The keeper**: where a value rests: in the row itself, sealed, by the keeper named `ledger`, or as it is in a secret manager of the operator's, AWS Systems Manager Parameter Store, by the keeper named `aws-parameter-store`.
- **Sealed**: encrypted under a data key made for that value alone, the data key wrapped by the custodian's key and kept beside the value.
- **The custodian**: who holds the key that wraps data keys: a key in hand, or a key in AWS KMS, which never leaves it.
- **The kid**: the id of the custodian's key, written on each sealed row and in the log, never the key.
- **Rotation**: a new custodian named beside the previous one; at start every data key the previous one wrapped is wrapped again by the current one, and no value is touched.
- **A move**: a new keeper named beside the previous one; at start every value the previous one holds is held by the current one and released by the previous one.

## Entry

`@on.auto/secrets` (`src/index.ts`) exports:

- the ports, each an interface of functions: `SecretRows`, with `Holding`, `SecretRow`, `HeldRow`, `Holder` and the answers `Replacement` and `Claim`; `Custodian`, `{ kid, wrap(dataKey), unwrap(wrapped) }`, each failing with a `KeepingFailure`, and `Custodians`, `{ current, previous? }`; and `Keeper`, `{ name, hold(id, value), reveal(holding), release(holding) }`, whose `hold` fails with a `KeepingFailure`, or with a `SecretRefused` for a value it will never keep, whose `release` fails with a `KeepingFailure` and whose `reveal` with a `ReadingFailure`, and which reveals nothing for a value it no longer holds, and `Keepers`, `{ current, previous? }`;
- `secretStoreOn(rows, keepers, custodians?)`, the `SecretStore` over them, its refusal of a value, `SecretRefused`, and its three failures, `SecretKeyUnknown`, `CustodianRefused` and `KeeperUnavailable`, with `KeepingFailure`, the last two, and `ReadingFailure`, all three;
- `localCustodian(key)`, the custodian of a key in hand, and `secretKeyBytes`, the length of such a key, 32;
- `sealedKeeper(custodians)`, the keeper that seals a value into its row, and `sealedSecretStoreOn(rows, custodians)`, the store whose one keeper it is;
- `custodianProbed(custodian)`, the probe the server makes of a custodian at start: one data key made, wrapped and unwrapped within the store's bound, both copies then filled with zeros, failing as the custodian does;
- `keeperProbed(keeper)`, the probe the server makes of a keeper other than the ledger at start: one value held under an id of its own, `probe-<uuidv7>`, which no secret's id is, so a probe left behind is never taken for a secret, revealed and released within the store's bound, failing as the keeper does, or as a `KeeperUnavailable` where the keeper reveals no value or another one, `The keeper aws-parameter-store did not read back the value it had just held under <what it held>`, the value held being released all the same.

`@on.auto/secrets/aws` (`src/aws/index.ts`) is a subpath of its own, as `@on.auto/outbound/aws` is, so that only a server whose settings name a key in KMS or a keeper in Parameter Store loads it, and with it `@aws-sdk/client-kms` and `@aws-sdk/client-ssm`, pinned to the version of the other AWS clients: it exports `kmsCustodian(options)`, `kidOfKey(keyId)`, `encryptionContext`, `parameterStoreKeeper(options)` and `awsWaits`, below.

The server composes them in `packages/server/src/secrets/`: the rows for its database, a custodian of the current key and one of the previous key where the ledger keeps secrets, a `localCustodian` for a key in hand and a `kmsCustodian` for a key in KMS, a keeper of each keeper its settings name, the `sealedKeeper` of the custodians for the ledger and a `parameterStoreKeeper` for Parameter Store, and the store over the three.

## The row

The ledger keeps the rows in one table, `kept_secrets`, with these columns:

| Column          | What it holds                                                                                                                                                                      |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`            | the secret's id, a UUIDv7, the table's primary key                                                                                                                                 |
| `version`       | 1 when the secret is kept, one more at each replacement                                                                                                                            |
| `kept_at`       | when the value it holds was kept, an ISO 8601 time in UTC, as text                                                                                                                 |
| `claimed_until` | until when the row is claimed by whoever renews it, the same kind of time, or `NULL`                                                                                               |
| `ends_with`     | the ending of the secret the runtime may show, or `NULL`                                                                                                                           |
| `kept_by`       | the keeper that holds the value, `ledger` or `aws-parameter-store`                                                                                                                 |
| `held`          | what the keeper handed back: for `ledger`, the sealed value, one JWE in its compact form; for `aws-parameter-store`, the name and the version of the parameter, `<name>:<version>` |
| `wrapped_key`   | for `ledger`, the value's data key wrapped by the custodian, one JWE in its compact form; `NULL` otherwise                                                                         |
| `kid`           | for `ledger`, the kid of the custodian's key that wrapped it; `NULL` otherwise                                                                                                     |

`SecretRows` is that table's SQL as a port, and seals nothing: `keep(id, holding, endsWith?)` writes a row at its first version, `kept_at` now, and fails as a defect for an id it keeps already; `read(id)` answers its holding, its version and `claimedUntil`, the end of its claim while that is open, or nothing for an id it does not keep; `replace(id, version, holding)` writes a new holding in one conditional update, only while the row's version is the one the caller read, at the next version, `kept_at` now, its claim ended and its ending cleared; `claim(id, version, lastingMs)` marks the row claimed until `lastingMs` from now, only while its version is the one read and no claim is open, a claim being open while its end is later than now; `endingsOf(ids)` answers the ending of each id that has one, in one read, and nothing for no ids; `forget(id)` deletes the row and answers the holding it held, and forgetting an id twice is forgetting it once. Two more serve the start: `heldBy({ keptBy, kid? }, limit, after?)` answers at most `limit` rows a keeper holds, under a kid where one is named and after an id where one is named, `{ id, version, holding }` in the order of their ids; and `reheld(read, holding)` writes another holding of a row in one conditional update, only while its version and its holding are still the ones `read` names, and answers whether it did, so that two servers starting at once hold each row again once and a replacement made between a read and the write is never written over; the version, the claim, the ending and `kept_at` stay. `replace` and `claim` answer `{ replaced: true, version }` or `{ replaced: false }`, `{ claimed: true, until }` or `{ claimed: false }`, for a row whose version moved and for a row that is gone alike, never with an error. The rows read every time they write or compare, `kept_at`, the end of a claim and the moment a claim is judged open, from the clock they are given, Effect's `Clock` for the ledger's, so a test drives it with `TestClock`. `close()` closes the rows' connections.

## Sealing

A value the `ledger` keeper holds is sealed by `jose`, the library that verifies the identity service's tokens in `@on.auto/identity`, as one JWE in its compact form whose protected header is `{ alg: 'dir', enc: 'A256GCM' }`: the value is encrypted with AES-GCM under a data key of 32 random bytes made for it alone, from `crypto.getRandomValues`, and nothing else is in the header. The custodian wraps the data key, and the wrapping goes in `wrapped_key` and the custodian's kid in `kid`, beside the value and not in its header, which is authenticated data, so a rotation rewrites those two columns and never the value. A replacement seals the new value under a new data key. Every data key made or unwrapped is filled with zeros once its seal, its unseal or its wrapping again is done, so none outlasts its one use. Nothing of it is the runtime's own: no cipher, no nonce and no derivation of a key.

## The custodian

`localCustodian(key)` takes a key of 32 bytes as a `Redacted` byte array, and a key of another length stops it, naming the length and never the bytes: `A key that seals secrets is 32 bytes, and this one is 16`. Its `kid` is the first 16 hex characters of the key's SHA-256, `sha256Of` of `@on.auto/operations`, so no one names a key and one key always has one kid. `wrap(dataKey)` answers one JWE in its compact form, `{ alg: 'A256KW', enc: 'A256GCM' }`, of the data key under the key, `jose`'s envelope of AES key wrap around a content key of its own; `unwrap(wrapped)` answers the data key, taking those two algorithms alone and no compression, so a wrapping under another key, or of another algorithm under this one, is refused as a `CustodianRefused` in its own words, `The custodian of the key <kid> refused to unwrap a data key: its wrapped key does not open under this key`. Under the kid it names, that means a wrapping changed outside the runtime.

`kmsCustodian({ keyId, region, proxy, credentials, endpoint?, waits? })` makes the custodian of a key in AWS KMS, `keyId` the ARN of a symmetric key or of an alias, as an effect: for the ARN of a key it asks nothing, and for the ARN of an alias it asks `DescribeKey` once, within the store's bound, and takes the ARN of the key the alias names from the answer, so the custodian is pinned to that key and never to the alias. An alias pointed at another key therefore makes the custodian of another key at the next start, under which the rows the key before wrapped are wrapped again once its ARN is the previous custodian's. A `DescribeKey` KMS refuses fails the making as a `CustodianRefused`, `The custodian of the alias alias/auto-runtime refused to describe the key it names: <the service's words>`, and one it does not answer as a `KeeperUnavailable`, `… did not answer a request to describe the key it names: …`, each with the alias as its kid. The custodian's `kid` is the key's id, the last path segment of the key's ARN, `kidOfKey`, so the kid a row keeps names the key and no account. `wrap(dataKey)` is `Encrypt` with that key's ARN as `KeyId`, the data key as `Plaintext` and the encryption context `{ 'on.auto/runtime': 'secret data key' }`, `encryptionContext`, which names the purpose in the account's trail and binds the wrapping to it, and answers the ciphertext blob as base64; `unwrap(wrapped)` is `Decrypt` with the same key and context, so KMS opens the blob under that key and that context alone, and answers the data key. The client is an `@aws-sdk/client-kms` of the region given, with the settings of `awsClientSettingsOf(proxy)` of [`@on.auto/outbound/aws`](../outbound/README.md#aws-clients), and the server gives it the credentials of `awsCredentialChain(proxy)`, as the object store's are; `endpoint` points it elsewhere than the region's KMS, which the tests do. Every request is bounded as the S3 client's are, by the client's own waits, `awsWaits` (`src/aws/aws-requests.ts`, the one rule of them for both AWS clients), 5 seconds to connect and 10 seconds for an answer, the store's bound, after which it fails as a `TimeoutError`, and the store's bound holds the whole of it. An answer KMS refuses as the caller's fault, `DisabledException`, `KMSInvalidStateException` for a key pending deletion, `AccessDeniedException`, `NotFoundException`, `InvalidCiphertextException` and `IncorrectKeyException` among them, is a `CustodianRefused` in the service's words with the kid, `The custodian of the key 1234abcd-12ab-34cd-56ef-1234567890ab refused to unwrap a data key: DisabledException: key/1234abcd-12ab-34cd-56ef-1234567890ab is disabled.`, the account of every ARN in those words left out; a request that is not answered, a throttled one, which is `ThrottlingException`, `LimitExceededException` or anything else `isThrottlingError` of the SDK's own retry, `@smithy/core/retry`, judges throttling, a fault of the service and a credential that cannot be found are a `KeeperUnavailable` with the kid, `The custodian of the key <kid> did not answer a request to wrap a data key: <the failure's words>`, so the log of each cause tells the custodians apart. Nothing of a data key, of a credential or of the account reaches those words. KMS's own rotation of a key's material needs nothing of the runtime, since KMS decrypts under the material that encrypted.

The store takes `custodians: { current, previous? }`: the current one wraps every data key, and a read asks the one its row's kid names. A previous custodian with the current one's kid is no previous at all. Each read unwraps its data key again and nothing keeps one unwrapped, since a row is read when a connection is first used in a process and when its tokens are renewed.

## The keeper

`sealedKeeper(custodians)` is the keeper named `ledger`. `hold(id, value)` makes a data key, seals the value under it, has the current custodian wrap it, and answers `{ keptBy: 'ledger', held, wrappedKey, kid }`; the id names nothing in what it holds. `reveal(holding)` asks the custodian the holding's kid names to unwrap the data key, and opens the value with `dir` and `A256GCM` alone and no compression; a kid that is neither the current custodian's nor the previous one's, or a holding that names none, is refused as a `SecretKeyUnknown`. `hold` and `reveal` fail as their custodian does. `release(holding)` does nothing, since the row is the value.

`parameterStoreKeeper({ prefix, region, proxy, credentials, endpoint?, waits? })` (`src/aws/parameter-store-keeper.ts`) is the keeper named `aws-parameter-store`, of values kept as they are in AWS Systems Manager Parameter Store, under the manager's own encryption and not sealed first, since the manager is the operator's custody and the operator reads, rotates and audits there. `hold(id, value)` is `PutParameter` of the name `<prefix>/<id>`, `Type: SecureString` and `Overwrite: true`, the value as it is, and answers `{ keptBy: 'aws-parameter-store', held: '<name>:<version>' }` with the version the write returned and no wrapped key or kid. The tier is one rule, `tierOf`: a value of more than 4 KB of UTF-8, 4096 bytes, names the advanced tier, which holds 8 KB, and a value of 4 KB or less names none, so a new parameter takes the account's default tier, the standard tier unless the operator changed it, and a parameter already in the advanced tier keeps it, since the service lets no parameter leave that tier and refuses a write that names the standard tier for one. Bytes are counted rather than characters, so the rule names the advanced tier for every value the standard tier could refuse. `reveal(holding)` is `GetParameter` of `<name>:<version>` with decryption, so a reader reads exactly the value its row's version names, whatever a later write left as the latest; `release(holding)` is `DeleteParameter` of the name, which takes every version at once. A parameter or a version the manager no longer has, `ParameterNotFound` or `ParameterVersionNotFound`, is a value gone for good: `reveal` answers nothing, as the rows answer nothing for a row that is gone, and `release` of a parameter gone already is done. Any other failure is a `KeeperUnavailable` in the manager's words, the account of every ARN in them left out as the KMS custodian leaves it out: a denied identity, `AWS Parameter Store could not write the parameter /auto-runtime/secrets/<id>: AccessDeniedException: User: user/runtime is not authorized to perform: ssm:PutParameter on resource: parameter/auto-runtime/secrets/<id> because no identity-based policy allows the ssm:PutParameter action`, a throttle the SDK's own retry did not wait out, `… ThrottlingException: Rate exceeded`, a request not answered within the client's waits, `awsWaits`, 5 seconds to connect and the store's 10 for an answer, `… TimeoutError: …`, a port that cannot be reached and a fault of the service. A value the service will never keep, whatever a retry does, is a `SecretRefused` in its words, which lead with the parameter, since the probe's value is a UUID, `AWS Parameter Store refused to keep the parameter <name>: <the service's words>`: `over_the_keepers_quota` for `ParameterLimitExceeded`, past the ten thousand standard parameters of an account in a region, and `refused_by_the_keeper` for `PoliciesLimitExceededException`, `ParameterMaxVersionLimitExceeded`, where the oldest of a hundred versions bears a label, and a `ValidationException` of a write, such as a value that holds a reference in double braces, `{{ssm:<name>}}`, which the service refuses, since the probe at start has shown the names under the prefix are valid. Nothing of a value or a credential reaches those words. The client is an `@aws-sdk/client-ssm` of the region given, with the request handler of `awsClientSettingsOf(proxy)` and the credentials the server gives it, `awsCredentialChain(proxy)`, as the KMS custodian's; `endpoint` points it elsewhere than the region's Parameter Store, which the tests do. The client retries in the adaptive mode of the SDK, its own rate limiter, which slows the requests it sends once the service throttles one, unless `AWS_RETRY_MODE` or the profile names another mode, which the SDK reads itself, as it reads `AWS_MAX_ATTEMPTS`; a throttled write is waited out in three attempts at most. Parameter Store takes three writes a second by default, which the keeps, finishes and renewals of a runtime stay well under, and which a move of many secrets meets.

## The failures

A value the store cannot read now fails the call that asked for it, and nothing else: the store keeps the row as it was, and reads it again at the next call. There are three such failures, each a tagged error that names no value and no key, its words in `detail`:

- `SecretKeyUnknown`, `secret_key_unknown`, `{ kid, detail }`: the row is sealed under a kid that is neither the current custodian's nor the previous one's, `The secret is sealed under the key <kid>, which is neither the current key nor the previous one`.
- `CustodianRefused`, `custodian_refused`, `{ kid, detail }`: the custodian of the kid failed to wrap or unwrap a data key, and says why, `The custodian of the key <kid> refused to unwrap a data key: <the custodian's words>`.
- `KeeperUnavailable`, `keeper_unavailable`, `{ kid?, detail }`: the keeper, or the custodian it asks, did not answer, the kid naming the custodian where it can tell, or the store gave up at the bound it sets, 10 seconds through Effect's `timeoutOrElse` (`src/store/answer-bound.ts`, the one rule of it), shorter than the fifteen seconds a renewal's claim keeps for its write in `@on.auto/tool-servers`, so a write the store cannot make now fails while the claim still holds, `The keeper of the secret, or the custodian of its key, did not answer within 10 seconds`; or the row is kept by a keeper that is neither the current keeper nor the previous one, which a change of keeper without a move leaves, `The secret is kept by the keeper aws-parameter-store, which is neither the current keeper nor the previous one`.

A read fails with any of the three, a `ReadingFailure`; a keep and a replacement with the last two, a `KeepingFailure`, and keep nothing then, so a value is kept or replaced only when its keeper and its custodian answered. A custodian or a keeper answers the last two itself where it can tell, and the store answers `KeeperUnavailable` for one that is still silent at the bound.

## The store

`secretStoreOn(rows, keepers, custodians?)` answers the `SecretStore`: the current keeper holds every value it keeps and every replacement, a read asks the keeper its row's holding names, and the custodians, where there are any, serve its rotation.

- `keep(value, endsWith?)` takes the value as a `Redacted` string, and the ending the runtime may show where it is given one, makes an id, a UUIDv7 as `randomUUIDv7` of `@on.auto/operations` makes the ledger's other ids, has the current keeper hold the value under it and keeps the row, and answers the id. An empty value, or one of more than 8 KiB of UTF-8, is refused before anything is sealed, as a `SecretRefused` that is `empty` or `too_large` and says nothing of the value: `A secret to keep is empty`, `A secret to keep holds more than 8 KiB`. A keeper that does not hold the value fails it with a `KeepingFailure`, and no row is kept.
- `read(id)` answers a `StoredSecret`: the value as a `Redacted`, which prints and serializes as `<redacted>`, so a value cannot reach a log by accident, the row's `version`, and `claimedUntil`; it answers nothing for an id the store does not keep, or whose keeper no longer holds its value, never an error, and fails with one of the three failures above.
- `replace(id, version, value)` has the current keeper hold the new value and replaces the row's holding under the version read, refusing a value and failing as `keep` does, the row then as it was; `claim`, `endingsOf` and `close` are the rows' own.
- `forget(id)` forgets the row and has the keeper its holding names release it, within the store's bound. A keeper that does not, or one that is neither the current keeper nor the previous one, leaves the value where it is: the store forgets the row all the same and logs a warning in the keeper's words, never the value, `A value no secret names any more is left where it was kept, until it is deleted there: <the keeper's words>`.
- `rotated()` holds again under the current custodian what the previous one wrapped: it reads with `heldBy({ keptBy: 'ledger', kid })` the rows of the previous custodian's kid, 100 at a time, has the previous custodian unwrap each data key and the current one wrap it, writes the new `wrappedKey` and `kid` with `reheld`, and answers how many rows it held again. Rows of the current kid, of any other kid and of any other keeper are left as they are, and so is each row's value, its version, its claim and the time it was kept. Without a previous custodian, with the current one given as the previous, or without custodians at all, it holds nothing again. Once a rotation has run, nothing is wrapped under the previous key any more, so it can be dropped. Each row's unwrapping and wrapping again is bounded as a read is, and a custodian that refuses or does not answer fails the rotation with its `KeepingFailure`, the rows held again before it under the current custodian and the rest as they were; the server stops its start on it, naming the setting of the previous key before the custodian's words.
- `moved()` holds under the current keeper what the previous one holds (`src/store/move.ts`): it reads with `heldBy({ keptBy }, 100, after)` the rows of the previous keeper, 100 at a time, each batch after the last id of the batch before, has the previous keeper reveal each value and the current one hold it under the row's id, each within the store's bound, writes the new holding with `reheld`, and, once the row took it, has the previous keeper release the holding it held, a release that does not happen being logged as `forget` logs it; it answers how many rows it moved. Each row's version, claim, ending and the time it was kept stay as they were. A row replaced between its read and its write is left as the replacement left it, and nothing of it is released, since a release in a secret manager takes every version of the name; a row whose value the previous keeper no longer holds is left where it is, read as gone while that keeper is named, and the batches go on past it. A row sealed under a key neither custodian holds is left where it is, as the rotation leaves it, and logged once for its kid, `Secrets are left with the previous keeper, unmoved, until their key is given: The secret is sealed under the key <kid>, which is neither the current key nor the previous one`; a value the current keeper refuses, a `SecretRefused`, is left where it is and logged with the secret's id, `A secret is left with the previous keeper, unmoved, since the current one refused its value: <the keeper's words>`; the count skips both. A refusal over the keeper's quota, `over_the_keepers_quota`, is the account's and would meet every later row, so it fails the move with it, the rows moved before it moved and the rest as they were. Without a previous keeper, or with the current one given as the previous, it moves nothing. A keeper that does not reveal or does not hold fails the move with its failure, the rows moved before it moved and the rest as they were; the server stops its start on it, naming the setting of the previous keeper before the keeper's words.

A failure of the rows, of the keeper or of the custodian other than these is a defect, as a failure of the ledger's database is.

A secret is only as recoverable as its key, or as its manager keeps it. The store keeps no copy of a key and no way around one: a lost key loses every data key wrapped under it and so every value, and a row whose key is gone can only be forgotten. The server's settings say where its key comes from, in [Configure the runtime](../../docs/self-host/configuration.md#storage).

## Testing

`@on.auto/secrets/testing` (`src/testing/index.ts`) holds what the tests of the rows and of the store share:

- `memoryRows({ now })`, rows kept in memory under the rule of the lease, whose claims and times are read from `now`, and which fail as a defect for an id they keep already, as the ledger's table does: the one copy of the lease beside the ledger's SQL. `kept()` answers each row by its columns, in the order of its ids.
- `valuesInTheClear({ now, mostCharacters })`, values a test holds in the clear over `memoryRows`, `{ keptBy: 'memory', held }`, under ids it gives: it keeps, reads, replaces, claims, answers endings and forgets as the rows do, refuses a value to keep or a replacement past its bound, `A secret to keep holds more than <n> characters`, and answers what it holds, `values()` and `endings()`. The tool-servers package's `memoryTokens` and the connections package's harness keep their values in it.
- `recordingCustodian(custodian?)`, the custodian it is given, one of a random key in hand unless it is given one, that counts its wraps and unwraps, `wraps()` and `unwraps()`, and holds the data keys it wrapped and unwrapped, `dataKeys()`, so a test sees them filled with zeros. Told to `refuse()`, it refuses both as a `CustodianRefused` in the words `custodianRefusal`, `the key is disabled`; told to `stall()`, it answers neither, and the promise `stall()` answers settles once it is first asked; told to `answer()`, it answers again.
- `rowsBehaviour(entry)`, every claim on a `SecretRows`: a holding kept, with and without a wrapped key and a kid, read back and forgotten twice as once, no second row under an id kept, the endings, a replacement at the version read, after which the next version may be claimed at once, and none at another or of a row that is gone, a claim a read answers while it is open and none while one is open, of a moved version or of a row that is gone, the rows a keeper holds under a kid and after an id, in order and at most as many as asked, a row held again only while its version and its holding are the ones read, its version, claim, ending and time kept, and a sealed row replaced or held again with the holding of another keeper, its wrapped key and kid then empty.
- `serveFakeKms({ keys, aliases? })` (`src/fakes/fake-kms.ts`), an HTTP server on a loopback port answering the KMS JSON protocol for `Encrypt`, `Decrypt` and `DescribeKey` under `X-Amz-Target`, for the key ARNs it is given and the alias ARNs that name them: its blob is the key, the context and the plaintext sealed under AES-GCM by a key of its own, so it never holds a plaintext in the clear and opens only under the key and the context it was made with, `IncorrectKeyException` and `InvalidCiphertextException` otherwise, and a key it was not given is `NotFoundException`. `tell(keyId, state)` makes a key `disabled`, `pending_deletion`, `denied`, which KMS answers for a key unknown to the caller or one it may not use, `stalling`, which answers nothing, or `enabled` again; `failWith(keyId, { type, status })` makes a key answer that error, such as `ThrottlingException`, until it is told a state; `point(aliasArn, keyArn)` points an alias at another key; `DescribeKey` answers the key's id and ARN for a key or an alias that names it, enabled, disabled or pending deletion, as KMS does, and `NotFoundException` for an alias or a key it does not know; `calls()` answers each call with its key id, and the context of an `Encrypt` or a `Decrypt`.
- `serveFakeParameterStore({ region?, account? })` (`src/fakes/fake-parameter-store.ts`, its answers in `src/fakes/fake-parameter-answers.ts`), an HTTP server on a loopback port answering the Parameter Store JSON protocol for `PutParameter`, `GetParameter` and `DeleteParameter` under `X-Amz-Target`, dispatched by one switch over the three names: it keeps each parameter's versions and its tier in memory, answers the latest version or the one a `name:version` selector names, with decryption alone, `ParameterVersionNotFound` for a version it does not have and `ParameterNotFound` for a name it does not keep, refuses a write over a parameter that names no overwrite, a value of more than 4 KB in the standard tier, any value of more than 8 KB and a write that names the standard tier for a parameter in the advanced one, counting bytes, and keeps a parameter's tier where a write names none, its first write taking the standard tier. `tell(state, operations?)` makes the operations named, or all three, answer `denied`, an `AccessDeniedException` whose words name the user and the parameter by their ARNs as the service's do, `stalling`, which answers nothing, `faulting`, an `InternalServerError` of HTTP 500, or `answering` again; `throttle(writes?)` answers the next write, or the next `writes`, with a `ThrottlingException`, and `refuse(type)` the next write with the error `type`; `keepAtMost(parameters)` answers a write of a new parameter with `ParameterLimitExceeded` once it keeps that many, and still takes a new version of one it keeps; a value that holds a reference in double braces is refused as a `ValidationException`, as the service refuses it; `remove(name)` takes a parameter away as an operator deleting it would; `parameter(name)` answers its tier and versions; `calls()` answers each call with its operation, its name, the tier it named, the version it wrote or read, its answer and the retry mode its client names in its user agent, `adaptive` or `standard`, and never a value, and the fake logs nothing.
- `memoryKeeper(name?)` (`src/fakes/memory-keeper.ts`), a keeper in memory, `memory` unless it is named otherwise, that holds each value as it is, one version more at each hold under an id, `<id>:<version>`, reveals the version a holding names and nothing for one it does not hold, releases every version of an id, answers what it holds, `valueOf(holding)`, and what it released, `released()`, loses an id as an operator deleting it would, `lose(holding)`, and, told to `refuse()`, fails each request as a `KeeperUnavailable` in the words `memoryKeeperRefusal` until it is told to `answer()`; `inMemoryKeepers()` answers one as the keepers of the keeper suite, `TestKeepers`, which the file defines beside it, so that `src/fakes` imports nothing from `src/testing`.
- `storeBehaviour(entry, custodians?)`, what the store adds over any rows and any custodians, local ones unless it is given others, and over a keeper in memory beside the ledger's, the claims of the rows themselves being `rowsBehaviour`'s: a value kept under a UUIDv7 with its ending and read back redacted, sealed as a `dir` JWE under a data key of its own that the row's `wrapped_key` holds under the row's `kid` and never in the clear, a wrap at each keep and an unwrap at each read with each data key then filled with zeros, a forget twice as once, through which the keeper releases, the empty and the oversized value refused before anything is wrapped, as a replacement, a replacement at the next version under a new data key, and a rotation over more than one batch that wraps again the data keys of the previous key's rows, touches no value, keeps each row's version and claim and leaves a stray kid, and none without a previous key. Its failures are a suite of their own in `src/testing/failure-behaviour.ts`: a value under another key not read, `secret_key_unknown` with that key's kid; a value and a replacement a refusing custodian does not wrap, `custodian_refused`, the row as it was; and a value a refusing custodian does not unwrap, `custodian_refused`, and one a stalled custodian leaves unanswered, `keeper_unavailable` at 10 seconds of `TestClock` and not a millisecond before, read again once the custodian answers, its row as it was and no failure naming the value.
- `keeperBehaviour(entry, keepers?)` (`src/testing/keeper-behaviour.ts`), what the store does over a keeper other than the ledger, `inMemoryKeepers()` unless it is given others: a value kept as it is in the keeper under the id of its row, whose holding says where the value is, holds no value and no wrapped key or kid, and is read back redacted; a replacement at the next version of the row, the version the row named before still revealed; a forget twice as once, after which the keeper holds none of the value's versions; the empty and the oversized value refused before the keeper is asked; and the rows sealed under a key neither custodian holds left where they are by a move, logged once with their kid, the rest moved, and those rows moved once their key is given as the previous one. Its moves are a suite of their own in `src/testing/move-behaviour.ts`: more than a hundred values the ledger seals moved into the keeper and back, released from each keeper they leave, each row keeping its version, claim, ending and time kept; a replacement made between a move's read of a row and its write, either way, never written over and nothing of its row released; a hundred rows whose values the keeper lost left where they are, read as gone while it is named and as kept by a keeper neither current nor previous once it is not, and the row after them moved; nothing moved without a previous keeper or with the current one as the previous, and the rows of a third keeper left alone; and a move whose previous keeper cannot reveal failing in its words, every row as it was.

An entry, `SecretsEntry`, is `{ aDatabase, rowsOn, rowsIn }`: a fresh database, the rows on one, and the rows of one as its table holds them, by their columns in the order of their ids. The custodians a suite takes, `{ aCustodian }`, answer a custodian of a key of its own at each call; the keepers `keeperBehaviour` takes, `TestKeepers`, `{ aKeeper, valueIn, lose }`, answer a keeper, the value it holds for a holding as it is there, and the loss of a holding's value, as an operator deleting it in the manager would. `src/testing/memory-rows.test.ts` runs both suites over `memoryRows`, and the ledger runs them over SQLite and PostgreSQL, the keeper suite with them. `src/aws/kms-store.test.ts` runs `storeBehaviour` over keys in the fake KMS, and `src/aws/kms-custodian.test.ts` holds what the KMS custodian adds: its kid, the `Encrypt` and the `Decrypt` it sends with their key and context, a blob that holds no data key in the clear, an alias resolved once by `DescribeKey` and its key pinned, a custodian of another key once the alias is pointed at another, an alias KMS does not know or will not describe, its refusals in the words of KMS without the account, `ThrottlingException`, `LimitExceededException` and a `TooManyRequestsException` of HTTP 429 as a keeper that does not answer, with the kid, and a KMS that stalls or cannot be reached, given up on within waits of 100 ms on the real clock, since the SDK's request handler keeps its own timers. `src/aws/parameter-store-store.test.ts` runs `keeperBehaviour` over the keeper of values in the fake Parameter Store, and `src/aws/parameter-store-keeper.test.ts` holds what the keeper adds: the `PutParameter` it sends, a `SecureString` overwritten under the prefix and the id, the value as it is and a holding of the version the write returned; The same suites run against a real server of the AWS APIs when `SECRETS_TEST_AWS_URL` names one with its credentials, `http://access:secret@host:port`, one variable for both. `src/aws/kms-on-a-server.test.ts` runs `storeBehaviour` over keys it makes through `CreateKey`, one for each custodian it asks for, and adds an alias made with `CreateAlias`, whose custodian is pinned to its key and reads, once `UpdateAlias` points the alias at another key and the key before is the previous custodian, what the key before wrapped, a key the server does not know, refused as `NotFoundException` in the server's words, a data key the server opens under the purpose's context and under no other, and nothing written to `console.warn` by the SDK. `src/aws/parameter-store-on-a-server.test.ts` runs `keeperBehaviour` over parameters under a prefix of its own, and adds the tier at 4 KB and one byte over as `DescribeParameters` answers it, kept for a smaller value, an earlier version read after a later write, a parameter deleted on the server read as gone, a write the test throttles on its way to the server written once the SDK retried it, and nothing written to `console.warn` by the SDK. ## Source

`src/rows` holds the port of the rows, `src/custodians` the port of the custodian, its refusal, its probe and the custodian of a key in hand, `src/aws` the custodian of a key in KMS, the keeper of values in Parameter Store, the waits and the words of their requests, and their tests, `src/keepers` the port of the keeper, its probe, the ledger's keeper, its data keys, the unknown kid and the keeper that does not answer, `src/store` the store, the bound of an answer, the keepers a holding names, its rotation, its move and its refusal, `src/fakes` the fake KMS, the fake Parameter Store and the keeper in memory, and `src/testing` the rows in memory, the values in the clear, the recording custodian, the suites and the entry of the tests.
