# @on.auto/object-storage

The content port of [`@on.auto/operations`](../operations/README.md#recorded-content), `RecordedContent`, kept on an object store that speaks the S3 API, the second adapter of the port beside the ledger's own database. The server chooses it when `CONTENT_STORE_URL` is set, checks its bucket at start, and hands it to the ledger as its content store; the ledger keeps every other record in its database as before, and the database adapter stays the default. This package holds the adapter alone, so the ledger depends on no part of the AWS SDK.

## Entry

`@on.auto/object-storage` (`src/index.ts`) exports three functions and a failure, and `@on.auto/object-storage/location` (`src/location/content-location.ts`) a fourth, a subpath of its own so that the settings of the server read `CONTENT_STORE_URL` without loading the S3 client, which the entry of the adapter reaches (`src/location/location-entry.test.ts`):

- `contentLocationOf(url)`, of `@on.auto/object-storage/location`, reads `CONTENT_STORE_URL`, an `s3://bucket/prefix` URL, into `{ bucket, prefix }`, or nothing for a URL that is not one: the scheme is `s3:`, the bucket follows the S3 naming rule, 3 to 63 lowercase letters, digits, dots and hyphens, and the URL names no user, password, port, query or fragment. The prefix is the path without its leading, trailing and doubled slashes, and may be empty.
- `storageClientOf({ endpoint, region, proxy }, credentials, waits?)` makes the `S3Client`. A custom endpoint is addressed by path, `http://host:9000/bucket/key`, as S3-compatible servers expect; without one the client addresses the S3 endpoint of its region by host. Without a region the SDK finds one by its own chain, and fails the first request when it finds none. With the environment proxy on, `NODE_USE_ENV_PROXY=1`, the client's requests go through the proxy as the credential chain's do, through `awsClientSettingsOf` of [`@on.auto/outbound/aws`](../outbound/README.md#aws-clients). A connection waits at most 5 s to open and a request at most 60 s for its answer, after which it fails as a `TimeoutError`, so a store that stops answering never holds a check, a put, a get or the cleanup of a failed put; `waits` sets other bounds, which the tests use. The client computes a request checksum and checks a response checksum only where the S3 API requires one, `WHEN_REQUIRED`, since the SDK's default of a checksum on every request is one many S3-compatible servers refuse; the content's own SHA-256 proves every byte read back.
- `objectStoreReached(client, location)` asks the store for the bucket with `HeadBucket` and fails with `ObjectStoreUnreachable`, `{ bucket, answer }`, when it cannot: the answer is the store's, its name and status, such as `NotFound (404)` or `AccessDenied (403)`, or the failure of the request itself, such as `Error: connect ECONNREFUSED 127.0.0.1:9000` or `Error: Region is missing`; it carries no credential.
- `objectContentOn(client, location, waits?)` answers a `ContentStore` of `@on.auto/operations`, `{ content, sweepContent }`: `content`, the port, and `sweepContent(before)`, the sweep of uploads below. `client` is a function that answers the client, so that nothing passes the client itself, whose fields are not read-only, as a parameter.

The server composes them in `packages/server/src/composition/content-store.ts`: the location and the endpoint from the content store settings, the region from `AWS_REGION`, the environment proxy as the server reads it once for every client it makes, and the credentials from `awsCredentialChain` of `@on.auto/outbound/aws`, the default credential chain of the AWS SDK that the Bedrock provider of the reasoning capability uses too. It imports the entry of the adapter only when the settings name a bucket, so a server whose content is kept in the ledger never loads `@aws-sdk/client-s3` and `@aws-sdk/lib-storage`, which were 26 files and 0.7 MiB of its start, and 11 ms of it in a CPU profile (`packages/server/src/composition/content-entries.test.ts`; measured on 2026-10-23, at the median of 11 starts and of 7 profiles). Before the ledger opens, `packages/server/src/composition/ledger-store.ts` checks the bucket with `objectStoreReached`, and a bucket it cannot reach stops the server at start, naming `CONTENT_STORE_URL`, the bucket, the endpoint's host and the store's answer.

`@on.auto/object-storage/testing` (`src/testing/index.ts`) is the entry the tests of this package and of the server take a real S3-compatible server through, so the reading of its URL and the making of its bucket are written once: `testObjectStoreOf(url)` reads `http://access:secret@host:port/bucket` into the bucket, with a client of its own, the endpoint and the credentials; `bucketReady(bucket)` makes the bucket when it is missing, and finds it when another test made it at the same moment; `keysIn(bucket, prefix)` and `openUploadsIn(bucket, prefix)` list what a prefix holds, and `emptied(bucket, prefix)` aborts and deletes it.

## The keys

| Key                                                         | What it holds                                                                                                   |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `<prefix>/playbook/<org>/<playbook>/<sha256>`               | a content kept under a playbook: its bytes, its media type as the object's content type and its size as its own |
| `<prefix>/staging/playbook/<org>/<playbook>/<run>/<sha256>` | a content staged under a run, the run's id URI-encoded so that it is one segment of the key                     |
| `<prefix>/staging/playbook/<org>/<playbook>/<run>/.ended`   | the empty marker of a run whose staging ended                                                                   |
| `<prefix>/uploads/<upload id>`                              | the bytes of a put on their way, under the put's own UUIDv7                                                     |

`playbook/<org>/<playbook>/` is the playbook key the ledger's content tables keep a playbook under, `streamPrefixOfPlaybook` of `@on.auto/operations`, which the ledger's `playbookPlaceOf` writes as `playbook_key`, so the two adapters name a playbook alike. A key is the prefix and the rest joined by `/`, or the rest alone when the prefix is empty. The presence of an object is the head the database adapter writes last: there is no other record of a content.

## A put

`content.put(playbook, { stream, mediaType, expected? })` reads the stream through `takenInChunks` of `@on.auto/operations`, in chunks of 1 MiB, digesting and counting the bytes as they pass, and `requireExpected` refuses a digest or a size other than the one `expected` names, as a stream that fails is refused, each a `ContentRefused`; the database adapter takes the same intake and the same refusals.

- A put whose expected digest the playbook holds reads its stream through the digest, writes nothing, and answers the object it found.
- A content of one chunk is still in hand at the end of its stream. When the playbook holds its digest, the put writes nothing and answers the object it found, as the database adapter does; otherwise it writes the chunk under its digest with `If-None-Match: *`, so a second put of the digest that wrote first stands, and the put answers that one's media type and size.
- A larger content is uploaded while it is read, under `<prefix>/uploads/<upload id>`, through `Upload` of `@aws-sdk/lib-storage`: as one `PutObject` when it fits a part and as a multipart upload in parts of 5 MiB, the least the S3 API takes, two at once, otherwise. The upload finishes, the expected digest and size are checked, and the put looks for the object of the digest: when one is held it deletes its upload and answers the one held, so the first media type stands and nothing is written over it; otherwise it copies the upload under the digest with `CopyObject` and `If-None-Match: *` and deletes the upload. A copy refused because another put of the digest copied first answers that one. `CopyObject` copies at most 5 GiB, so a content larger than that fails as a defect once its upload is done, and its upload is deleted.
- A conditional write the store answers with `409 ConditionalRequestConflict`, which S3 answers when another write or a delete of the key lands during it, is made again, three times in all, before it fails the put as a defect.
- A store that ignores the condition on a copy, as MinIO and versitygw do, copies the same bytes over the first: of two puts of one digest made at the same moment with two media types, the later one's media type is left over identical bytes, after the earlier put answered a media type the store no longer holds. A put of a digest held is never copied, so a later put does not do this.
- A put refused, or failed by its stream or by its store, deletes its upload; `Upload` aborts a multipart upload it began. A failure of the store fails the put as a defect, as the database adapter fails on its database.

## A read

`content.get(playbook, sha256)` asks for the object with `GetObject` and answers `{ stream, bytes, mediaType }`, or nothing when the object does not exist; any other answer of the store fails the read as a defect. The stream is the object's body read through `verifiedStream` of `@on.auto/operations`, the verification the database adapter reads its chunks through: it digests every piece, hands over the piece that reaches the object's size only once the size and the digest are checked, and fails the stream as a defect with `notTheBytesOfItsDigest` otherwise, so no reader takes every byte of an object that is not its digest's. A store that sends no piece of the body for the wait of a request, 60 s, fails the stream and lets go of the body; the wait runs only while the stream waits for the store, never while its reader holds it back.

## Staging

`content.stage(playbook, run, content)` keeps a content under the run as a put keeps it under the playbook, and `content.staged(playbook, run, sha256)` reads it as a get reads. `content.unstage(playbook, run)` writes the run's marker first, an empty object, and then lists every object under the run's prefix and deletes them, a thousand to a request. A stage looks at the marker before it reads its stream and is refused with `StagingEnded`, leaving the stream unread, when the marker is there; it looks again once its object is written, and when the marker is there then, it deletes the object and is refused the same way. Since the unstage writes the marker before it lists, and an S3 store answers a read made after a write with what was written, either the stage sees the marker or the unstage's listing sees the object, so a stage that races an unstage keeps nothing, as the database adapter's `unstaged_runs` record ensures there. The markers stay, one empty object for each run whose staging ended. A read of a staged content that began before its run was unstaged reads the whole object, since the store answers a `GetObject` it began; the database adapter, which reads a chunk at a time, fails such a read part way.

## The sweep of uploads

An upload can outlive its put: a process that stops between the upload and its delete leaves it, and a multipart upload begun before the stop stays open. `sweepContent(before)` deletes every object under `<prefix>/uploads/` whose UUIDv7 time is before the time it is given, `uuidV7Before` of `@on.auto/operations`, reading the listing in key order, which is the order of the time a UUIDv7 carries in its first 48 bits, and stopping at the first upload begun after it. It then lists the open multipart uploads of the whole bucket, since MinIO lists none by a prefix, keeps those whose key is under `<prefix>/uploads/`, and aborts each that began before that time. The ledger runs it on the schedule of its own sweep, at the open and every hour, with the time an hour before, and waits for a sweep under way before it closes, as the [ledger README](../ledger/README.md#recorded-content) says.

## What the bucket needs

The bucket exists before the server starts; the server creates none, and checks it at start with `HeadBucket`. The server's credentials may read, write, copy and delete objects under the prefix, list the bucket, and list and abort multipart uploads: `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`, `s3:ListBucket`, which `HeadBucket` needs too, `s3:ListBucketMultipartUploads` and `s3:AbortMultipartUpload` in the S3 API's terms. Versioning is not required, and with versioning on every delete leaves a noncurrent version behind, so such a bucket needs a lifecycle rule that expires noncurrent versions. A lifecycle rule is otherwise optional: the sweep removes what puts left behind, and a rule that aborts incomplete multipart uploads after a day changes nothing the sweep does. Several servers may share a bucket and a prefix, as they share the ledger's database.

## Measurement

`measure/object-content.ts` runs the measurement of the ledger's database adapter, `measuredContent` of [`@on.auto/ledger/content-measurement`](../ledger/README.md#recorded-content), on this adapter: the answers of 100 bytes to 20 MB of JSON put three times, the second time as they are and the third with their digest expected, and read back and parsed, then 64 MiB of bytes as a stream the same three ways, read back with their digest checked, and the most the process held while it put and got the 64 MiB once more for another playbook. It needs `CONTENT_MEASURE_OBJECT_STORE_URL`, the URL of an S3-compatible server with its credentials and a bucket, which it makes when it is missing, and deletes what it kept:

```bash
CONTENT_MEASURE_OBJECT_STORE_URL=http://access:secret@127.0.0.1:9000/content-measure pnpm --filter @on.auto/object-storage measure:content
```

| Store          | Content          | Kept     | Kept again | Kept again, its digest given | Read back and parsed | Joined back exactly |
| -------------- | ---------------- | -------- | ---------- | ---------------------------- | -------------------- | ------------------- |
| Object storage | 100 B            | 5.7 ms   | 1.4 ms     | 1.1 ms                       | 1.6 ms               | yes                 |
| Object storage | 64 KiB           | 2.3 ms   | 0.98 ms    | 0.97 ms                      | 1.0 ms               | yes                 |
| Object storage | 1 MB             | 5.0 ms   | 1.3 ms     | 1.2 ms                       | 3.3 ms               | yes                 |
| Object storage | 5 MB             | 33.0 ms  | 16.7 ms    | 2.6 ms                       | 11.3 ms              | yes                 |
| Object storage | 20 MB            | 85.2 ms  | 49.3 ms    | 8.8 ms                       | 44.1 ms              | yes                 |
| Object storage | 64 MiB, streamed | 267.1 ms | 137.7 ms   | 25.9 ms                      | 69.6 ms              | yes                 |

Kept again, a content of one chunk costs one `HeadObject`; a larger one is uploaded again, found held and its upload deleted, about half what the first put cost, which also copied; given its digest, a put of a content the playbook holds reads its stream through the digest and writes nothing.

The memory a put holds is bounded by its construction, not by its content: `Upload` gathers a part of 5 MiB whole before it sends it and sends two at once, so a put under way holds about (2 + 1) × 5 MiB, some 15 MiB, for the parts in flight and the one it gathers, besides the chunk of 1 MiB the intake has in hand and, for a moment, the copy `Upload` makes when it joins a part's pieces, about 20 MiB at the most; puts under way at once hold that each, so ten hold about 200 MiB. The 64 MiB file never sits in the heap whole: the most the process held above its start while it put the 64 MiB, sampled every 5 ms, was 16.6 to 19.8 MiB of heap and array buffers over four runs. A read holds what the body of the response has buffered ahead of its reader, at most 11.9 MiB of the 64 MiB.

Measured on 2026-10-12 on an Apple M4 Max with 16 cores, with Node 26.10.0, against MinIO RELEASE.2025-10-15T17-29-55Z serving one drive on the loopback, each figure the median of three runs, at a load average of 3.7 to 4.4. The ledger's own figures for SQLite and PostgreSQL are in its [README](../ledger/README.md#recorded-content).

## Testing

The unit tests run the adapter against a fake bucket, `src/testing/fake-bucket.ts`: an `S3Client` made by `storageClientOf` whose middleware answers every command the adapter sends from a bucket, objects and multipart uploads it keeps in memory, listed in the byte order of their keys as S3 lists them, with pages of the size it is given and the markers S3 pages by, a conditional copy honoured or ignored, and requests it can be told to answer otherwise once, so that every path of the adapter, the failures of the store among them, runs without a server. A store that stops answering is a socket that never writes, in `src/client/storage-client.test.ts`, which gives each request of the client 100 ms, and its connection the 5 s of production, since the socket takes the connection and leaves only the request unanswered, and holds the check, the read and the put of that store to giving up within 20 s together, on the real clock on purpose, since the AWS SDK's request handler and its retries keep those waits and take no clock. `src/content/stalled-reads.test.ts` gives the same 100 ms to the wait for the next piece of a body its store stops sending, and nothing else: every other wait of the store in either test is production's, `storageWaits`. `src/testing/object-content-behaviour.ts` holds what is particular to objects, the check of the bucket, the keys, a read of an object filed under another digest and the sweep, and `src/testing/object-store-entry.ts` gives each test a prefix of its own and empties it afterwards.

The behaviour suite of the port, `recordedContentBehaviour` of `@on.auto/operations/testing`, the one the ledger runs on SQLite and PostgreSQL, runs here on the fake bucket, honouring a conditional copy and ignoring it, and on a real S3-compatible server when `CONTENT_TEST_OBJECT_STORE_URL` names one with its credentials and its bucket, which the tests make when it does not exist; without it the suite is skipped, and its title says how to run it. On the real server the suite also holds that the SDK writes nothing to `console.warn`, which would reach stderr outside the server's structured log:

```bash
CONTENT_TEST_OBJECT_STORE_URL=http://access:secret@127.0.0.1:9000/content-test pnpm --filter @on.auto/object-storage test
```

CI runs it against RustFS, an S3-compatible server whose image runs from its environment alone, as a service beside PostgreSQL; locally it passes against MinIO, versitygw and RustFS alike. The server's own test of a reasoning run that keeps 25 answers of 1 MB, `packages/server/src/reasoning/large-answers-on-stores.test.ts`, runs on the same server too, with its content on object storage.

## Source

`src/location` holds the URL and the keys, `src/client` the client, `src/content` the adapter, and `src/testing` the fake bucket, the suites and the entry of the tests.
