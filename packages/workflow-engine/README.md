# @on.auto/workflow-engine

The contract of the workflow machine that runs on the ledger: the DSL it runs, the state it keeps, the inputs it takes and the ports to the adapters that store, time and execute for it. The machine's state is shaped by the workflow DSL, so this package is the workflow machine's contract, not a generic runtime. It knows workflows, their DSL and an executor that performs calls. It does not know playbooks, prompts, models, definitions or capabilities: the functions a workflow may call come from the caller, and whatever an adapter needs to know about a run, such as who started it, it passes as opaque `attributes` and gets back with every output.

The machine runs in Node, in the server: [`@on.auto/workflow-host`](../workflow-host) hosts it over the ledger, keeping its runs in the ledger's database, a SQLite file or PostgreSQL, where one server at a time runs the workflows and any other stands by, and the workflow adapter runs every workflow on it. The machine decides each input (below).

## How a run moves

1. An adapter submits an input for a run, with `at`, the time on its own clock. The machine never reads a clock. It takes `max(at, lastInputAt)` as the time of the input, and for a fired timer at least the time it was due, so time in a run never goes back however the adapters' clocks drift (`inputTimeOf`).
2. Holding the run's serialisation, the engine runs the ledger's own load-decide-append loop, `decisionLoop` from `@on.auto/ledger`, with a load of its own: the run the engine kept after the input before, when its stream has no event after the version it kept, or else `RunLogStore.load`, the latest snapshot and the events after it, which `loadedRunOf` folds (`runLoopOf`, and The cache of loaded runs below).
3. `staleReasonOf(state, input)` says whether the input can still change the run. An input to a run whose `started` has not arrived is `not_started`: the engine answers `{ outcome: 'not_started' }`, which an adapter answers as `not_found` so the caller tries again, as the API does today. Any other reason is `stale`. Neither appends anything (`submissionOf`).
4. Otherwise the machine decides, and the decision is one event, appended with the version the loop read as the expected version. After a version conflict the loop loads and decides again, up to three more times, and then fails with the ledger's `Conflict`. The engine answers `{ outcome: 'applied' }`.
5. When a snapshot is due, the engine saves one.
6. It dispatches the outputs of every event above the run's dispatch watermark, in the order of the stream, and stops at the first output that fails. The watermark moves to the last event whose outputs were all dispatched. An event that arms, cancels or fires a timer also notes the run's next due time in the record (`runDueOf`), so a run whose last timer fired while it went on to wait for an event is no longer due (`src/engine/sweep.test.ts`); a note that fails is a dispatch failure too, so the watermark stays where it was, below the stream's version, and the next wake or input dispatches the events again and notes the time (`src/engine/wake.test.ts`). The run a dispatch is for is the one the input or the wake names, never the loaded state's, so a wake of a run that has no event reads and moves that run's watermark.
7. `wake(runId)` does step 6 again. `sweep(before)` wakes the runs that are overdue (below).

## The DSL

`policyOf(functions)` gives the policy a document is checked against. The caller gives the functions a workflow may call, each with the checks of its arguments, a description of a call for the messages it raises, and the words that explain where a workflow reaches the world and how it starts; the workflow adapter gives `run_definition` (`capabilities/coordination/src/document/workflow-functions.ts`). The DSL itself names no function.

The engine strips no types and holds no compiler: every program and expression it evaluates is the JavaScript the check at save made of the author's TypeScript, which the definitions package keeps beside the document (see `@on.auto/definitions`, The check at save), and no module of the engine, its tests and measures among them, imports `typescript` or `ts-blank-space`, nor does its `package.json` name either (`src/programs/no-compiler.test.ts`).

An expression's budget is checkpoints of the sandbox (below): 250 for one expression and 500 for one input, `mostExpressionWork` and `mostWorkPerInput`, so the machine decides the same way when a history is replayed. Beside it stands the input's deadline, 2 seconds, `mostInputMs`, read on the clock the host gives the machine beside `now`, since a checkpoint bounds the interpreter's work and not the engine's native work: one checkpoint may hold a `JSON.stringify` of a megabyte. The handler reads that clock only at a checkpoint, so native work holds a thread past the deadline for as long as it runs; the host therefore evaluates the expressions of `decide` in the pool's evaluation worker, which the thread that decides waits for until the answer or the deadline, and ends at the deadline (see [The evaluation worker](#the-evaluation-worker)). `runExpression(unit, source, values, { now, mostWork, deadlineAt })` evaluates an expression in a unit of the sandbox, the `Date` of the sandbox answering `now`, and gives its value or its problem; an expression stopped by its work, its memory or the deadline is exhausted, its `limit` says which, and the machine raises it as a `runtime` error, status 500; one that raised, overflowed its stack or answered what JSON cannot carry raises an `expression` error, status 400, which the workflow's `try` catches. The memory driver's clock is virtual and never reaches the deadline, so the machine's rule 2 holds in every test and replay; the machine's engine, `workflowEngineOf`, sets an instance aside for an input before it loads the run, or waits for the evaluation worker to be ready, through the sandbox's `reserve`, so `decide` itself never waits for either and a worker's start never spends an input's deadline.

## The sandbox

Every program a person writes inside the playbook, a computation function, a recall function's fold and answer, a workflow's expressions and the `data` of a filter, is TypeScript in the erasable subset, run by QuickJS compiled to WebAssembly: `quickjs-emscripten-core` with the synchronous release variant, `@jitl/quickjs-wasmfile-release-sync`, both pinned at 0.32.0, since the work a program costs is counted by that build. `src/programs` is the one place that knows the sandbox, and it is portable: it imports the library by type alone and is given an instance and a clock. Each host compiles the module once, asynchronously, and makes instances of it (`src/instances`): a fresh instance, with a `WebAssembly.Memory` whose `maximum` is the unit's memory bound and whose `grow` is wrapped so the host sees a refusal even when the program catches the engine's `out of memory` (`freshInstance`).

- **A fresh instance for every unit.** Every program job, every page of folds, every input of `decide` and every group of filters takes an instance of its own, discarded after the unit, so nothing of one unit reaches the next and a memory stop never leaves a wounded module behind. The memory's maximum is the one memory wall, in bytes: 256 MiB for a run, 64 MiB for a page, a group of filters and an input. A unit holds what the module's own memory of that maximum holds: when it needs more, the glue asks to grow by a fifth more than it needs, then a tenth, then a twentieth, and gives up after the three, so the host marks a refusal only when three attempts in a row fail and not at the first, and a program keeps 58 strings of a MiB under a maximum of 64 MiB, as the module alone does (`src/instances/fresh-instances.test.ts`). The engine's own `setMemoryLimit` counts allocations, not bytes, in this build, and is not relied on.
- **The prelude** (`src/programs/sandbox-prelude.ts`) makes a context the playbook's: `Date` answers the run's moment with no argument, takes one number, one `Date`, a date alone or a date and time that names its offset, and refuses whatever reads the server's time zone, its original constructor out of reach through `getPrototypeOf`, `Reflect.construct`, `bind` and `class extends`; `Math.random`, `eval`, the `Function` constructors, `WeakRef`, `FinalizationRegistry` and `Promise`, whose callbacks the sandbox never runs, go, with every local-time method of `Date`, from the one list `sandboxRemovals` (`src/programs/sandbox-names.ts`), which also says that `Date` is not called and takes at most one argument, the rule the prelude keeps and the definitions package writes the lib of its check from. An expression runs as strict code, `'use strict'` the first line of the function it is wrapped in, as the check compiles it. Nothing is added: no `console`, no timers, no `fetch`, no `Intl`, no module loader.
- **Frozen where a context serves many evaluations.** A program job's context and each expression's serve one evaluation. A page's context and a group of filters' serve many, so once the module and the filters are loaded the prelude freezes every object reachable from `globalThis`, from the intrinsics no global names, which it takes before any program runs (the prototypes of the iterators of arrays, maps, sets, strings and `matchAll`, of generator and async generator functions and their generators, of async functions, of iterator helpers and of wrapped iterators), and from the module's exports, with `name`, `message` and `constructor` of the intrinsic prototypes made accessors first, so an `Error` subclass still names itself; the freezing part of the prelude is loaded only into the contexts that freeze.
- **The work** is counted in checkpoints: the engine calls the interrupt handler once every 10,000 of its polls, a call or a loop's jump each, and the handler counts the call, ends the program past its budget, ends it at the first checkpoint after the memory refused to grow, and ends it once the clock the host gives passes the deadline (`src/programs/sandbox-counter.ts`). The interruption is the one ending a program cannot catch, and `finally` does not resume. A fresh context's first poll is a checkpoint, and where a context serves many evaluations each starts a fresh period in a loop the handler interrupts, so every fold's count depends on the view and the event alone and not on where the page began.
- **The stack** is the place's bound, 1 MiB for a program or a fold in a worker of the pool and 256 KiB for an expression or a filter wherever it runs, in the pool's evaluation worker, where a unit starts from the same shallow stack every time, and on a host's own thread, as the in-thread sandboxes of `dsl.ts` and the tests run it, where 512 KiB and more overflow the host's own stack first, so an expression that catches its own overflow answers the same on every host; a stack overflow is `InternalError: stack overflow`, at the same depth for the same bound every time, which a program may catch; one the host's stack meets first ends the unit, `limit` `stack`, and the runtime answers no more.
- **The answer** is read by `JSON.stringify` with a refusing replacer, in insertion order, which compares each member it is given with the member as it stands, tests each object's prototype and keeps each object's depth: a `Date`, a `Map`, a `Set`, a class instance, a boxed number, text or boolean, a typed array, a function, a `BigInt`, a symbol, `NaN`, `Infinity`, an empty place, a cycle, a value deeper than 512 levels, a `toJSON` and a member that changes as it is read are refused with the path of the member, found by a walk on refusal alone; `undefined` answers `null` for an expression and is refused in a module's answer. The depth stays in the replacer, at one lookup in a map for each object, since `JSON.stringify` of this build checks each object against every object it is inside of, so writing a value of 100,000 levels unbounded took 10.1 s in a pool's worker, against 24 ms refused at its 513th. An answer longer than the unit allows is refused by its length before it crosses. What a program throws crosses as its name and message, cut at 4,096 characters in the sandbox and 1,024 bytes outside it, with the line it was thrown on.
- **Types were stripped at save.** The check at save blanks a document's types where they stood once it passes, so a thrown error's line is the document's, and the save keeps that JavaScript; syntax with runtime meaning never reaches the sandbox, since the check refused it, and TypeScript handed to the sandbox anyway does not load, as a `SyntaxError` (`src/programs/module-runs.test.ts`).

A unit answers a `ProgramRun`: `answered` with the text of its JSON, `raised` with the issue and its line, `exhausted` with its `limit` (`work`, `memory`, `stack` or `deadline`), `unfit` with the member JSON cannot carry, or `oversized`, each with the checkpoints it spent (`src/programs/program-run.ts`). `moduleRun(instance, settings, request)` runs a module's entry over its arguments, as JSON text, in one context; `expressionUnitOf(instances, settings)` evaluates the expressions of one input, each in a fresh context of one runtime on the instance it takes when it first needs one; `filterContextOf` and `foldingUnitOf` keep a frozen context over a group of filters and over a page's folds.

`programPool({ workers, heapMegabytes })` runs a `ProgramRequest` (the source, the entry, the arguments, the moment of `Date`, the budget in checkpoints, the instance's `memoryBytes`, the `stackBytes`, `deadlineMs`, the most bytes its output may take as JSON, and optionally the `worker` module that runs it and a JSON `context` that module reads from the request, as the checked worker of `@on.auto/definitions` checks an output against the schema it names; a pool given its own `worker` in its settings, as tests do, runs every program with that one) in a worker thread of that module, kept warm between jobs, at most `workers` at once (`src/program-pool`; see [The workers of the pool](#the-workers-of-the-pool)). A run waits for a permit until its deadline, and the deadline also stops it there: the worker's handler reads the deadline at every checkpoint, and the pool terminates the worker when the deadline passes, so a run whose worker never answers still ends. The program and the arguments cross to the worker as copies, the arguments as JSON text, and the answer comes back as JSON text with its size, so the thread that holds the ledger never waits on a program. Every worker has a heap of `heapMegabytes`, its own limit, which bounds no WebAssembly memory, a stack of `workerStackMegabytes`, 64 MiB, none of the server's flags, and an empty environment unless the pool's settings give it one, `environment`, which the server never does, so no setting of the server, its keys among them, reaches a worker. A worker given no `execArgv` takes the flags of the process that starts it, and Node would then read an `--env-file` of the server, which the development runner gives, into every worker over the environment the pool gives, and run a preload of the server, `--import`, in every worker; the pool therefore gives each an empty `execArgv` (`src/program-pool/worker-flags.test.ts`), and Node strips the types of a worker module without a flag. The tests give only `NODE_V8_COVERAGE`, so the coverage of a worker is measured. An outcome is the worker's answer, `oversized` for an output over its bytes, which the worker measures as JSON before it crosses, `refused` for a program the worker would not load, `mismatched` with the issues a request's worker found in the output, each a `pointer` and a `detail` cut at 1,024 bytes apart, and the detail of every issue in an answer cut at `mostIssueBytes`, 1,024 bytes of UTF-8, marked with `…` (`textWithin`), `stopped` because of the `deadline`, `memory` (the worker's own heap, `ERR_WORKER_OUT_OF_MEMORY`), `busy` when no worker came free, `cancelled` by the caller's signal or `closing`, or `crashed` for any other ending, and each says how many `milliseconds` it took. `close()` turns away the runs still waiting and terminates every worker, idle or busy, a busy job ending `closing`.

`programPool` also runs a page of folds in a worker, `fold(request, signal)` (see [A page of folds](#a-page-of-folds)), and a check, `check(request)`, on a permit of its own beside the `workers` of runs, `checkPermits`, 1, so a save never waits behind the runs that take every worker: the request names the module that checks, gives the expressions and the programs of a document with the schemas of its types, and waits for its permit at most its deadline, after which the check ends `busy`. Its deadline counts from when its worker is ready, which the job loop says once it listens, `{ ready: true }`, so starting the worker and loading its modules, a compiler among them, never spend it: the start has a bound of its own, `mostCheckStartMs`, 10 seconds, after which the check ends `busy` and the worker, still starting, is kept for the next check rather than ended, and a check that runs past its deadline ends `deadline`. The worker of the checks never idles out, since a save would pay its start again; it is still let go of after its 1,000th check (`src/program-pool/pool-checks.test.ts`).

## A page of folds

`foldPage(page, host)` (`src/folds/fold-page.ts`) folds a page of events into views, each view by its own module, its own filters and its own checks, as the workflow host's projector folds the views recall functions keep. The page holds the events, in the order they were recorded, and for each view its module, its filters, each a mapping of the attributes `literalFilterOf` reads (`type`, and `source`, `subject` and `data` when given), the view before the page, its optional JSON Schema, and the indexes of the events it considers, so the caller decides which events each view is past. Each view takes an instance of the `host`'s, in which its module is loaded, its filters defined over `$data`, and the context frozen, under the page's `budget`, `memoryBytes` and `stackBytes`; the view stays inside the context for the whole page and each event crosses in. It folds event by event, every view in turn: a view folds an event it considers whose attributes one of its filters has (`src/folds/fold-filters.ts`), a `data` expression that raises on the event not matching it; the fold, the module's export `fold(view, event)`, runs with the time of its event as the moment of `Date`, under the page's budget in checkpoints and its own deadline, `foldDeadlineMs`, on the clock the `host` gives; after every fold the view is written out, must take at most `mostViewBytes` as JSON, and must pass the check the `host` makes of the view's schema, `checkOf(schema)`, since the engine imports no reader of JSON Schemas, so a view stalls at the event that broke it whatever the size of the page, though the next fold would shrink it back (`src/folds/fold-page-sizes.test.ts`); and the next fold is handed that text parsed again in the context, not the object the fold returned, so no fold sees what JSON drops, an object two members share, a negative zero or a member keyed by a symbol, and a page folds as pages of one event do (`src/folds/fold-isolation.test.ts`).

A view whose module does not load or exports no `fold`, whose fold raises, overflows its stack, does more work than its budget, uses more memory than its instance, answers what JSON cannot carry or a value deeper than 512 levels, answers a view over its bytes or one its check refuses, stalls at that event, `{ at, kind, message, line }`, the kind `refused`, `raised`, `work`, `memory`, `unfit`, `size` or `schema`, the message cut at `mostIssueBytes` and the line the module's own, and folds nothing more in the page; one whose filter or fold ran past the fold's deadline, which the two share, is marked `overtime` at that event and folds nothing more, so its caller can try it again. Neither touches another view. Before each fold the page checks its budget, `pageBudgetMs`, counted from the start of its first fold, so starting a worker and loading the page's modules never spend it: it runs at least one fold, and once the budget is spent it ends early, before the next fold, so at most one fold runs past the budget and a slow fold never makes the folds after it look slow. Each view answers `through`, the index of the last event it considered, so a page that ended early between two views of the same event says how far each went, and `work`, the checkpoints its folds spent, which are the same for the same events at every size of page, over 3,000 events in pages of 7 as in pages of 1,000 (`src/folds/fold-page.test.ts`, `src/folds/fold-page-sizes.test.ts`).

`programPool`'s `fold(request, signal)` runs such a page in a worker, the events and views crossing as JSON text and the views coming back so: the request's `worker` module, which serves the page with `foldAnswerOf` and the view checks it gives the job loop, as the checked worker of `@on.auto/definitions` checks a view against its schema for the recall capability, or the pool's own fold worker, which refuses every view that keeps a schema, since it checks none. The page waits for a permit at most `waitMs` and gives the worker `deadlineMs` from the moment it takes the page, so a page that waited for a worker never loses its time to the wait, while the worker's start counts against the deadline and not against the page's budget. The worker marks, in memory it shares with the pool, the event and the view of each fold before it matches the event against the view's filters, so a page the pool stops at its deadline, by its memory or because it crashed names the fold that was going as `progress`, and its caller can count that against the one view it belongs to.

## The evaluation worker

The handler of the sandbox reads the deadline only at a checkpoint, and native work, such as a `JSON.stringify` of a large value in a loop, holds no checkpoint: on the thread that decides, an expression stringifying a value of 1 MiB in a loop held the thread 10.8 s against its deadline of 2 s, the time growing with the value (`measure/evaluations.ts`). So the pool keeps two evaluation workers beside its workers, `evaluations`: one a host on Node hands the engine as the sandbox of `decide`, `evaluations.machine`, and one it matches its own filters on, `evaluations.filters` (`src/program-pool/evaluation-thread.ts`, `src/program-pool/evaluation-loop.ts`, `src/workers/evaluation-worker.ts`). Nothing starts before it is needed: the first input's `reserve` starts the deciding worker, and the first group of filters the filters' one, and each waits, without blocking, until its worker has compiled the module and made an instance, 103 ms, and a worker holds the process open only while it starts.

A unit of `decide` and a group of filters cross to the worker as requests on a channel of their own, `evaluate`, `prepare`, `test` and `close` (`src/jobs/evaluation-messages.ts`), an expression with only the values it names as JSON text. The thread that decides posts a request and blocks on `Atomics.wait` over memory it shares with the worker until the worker answers or the remaining deadline passes, with 50 ms of grace, `answerGraceMs`, so `decide` stays synchronous and pure, given an evaluator that blocks (`src/jobs/remote-evaluations.ts`). Filters never block: the host posts each of their requests to the filters' worker and awaits the answer, one request at a time, with a timer at the filter's deadline and the same grace, so the main thread goes on with its timers and requests while a filter churns. At the deadline the pool terminates the worker and starts another, and the unit's expression and every later one in it end `exhausted` by the `deadline`: an expression stringifying a value of 4 MiB in a loop ends its input in 2,055 ms through `decide`, and the next input is decided on the fresh worker, ready 96 ms later; in a trigger's filter after a plain one it ends both in 256 ms, while a timer of every 5 ms on the main thread goes at most 6.3 ms without firing (`measure/evaluations.ts`), and `src/filters/filter-workers.test.ts` checks that such a timer fires before the churning filter's verdict. After a memory refusal the pool terminates the worker and starts another too, and the unit ends `memory` without asking again. A worker that never loads is never terminated while it loads: an evaluation waiting for it ends at its deadline, and the next input starts another. An expression costs 0.56 ms through the worker against 0.52 ms on the thread that decides, at the median (`measure/evaluations.ts`). The worker's units run on the stack bound an expression has on every host, 256 KiB, from the same shallow stack every time, so an expression that catches its own stack overflow answers the same from a host 5,000 frames deep as from a shallow one and as on a host's own thread (`src/program-pool/evaluation-thread.test.ts`).

`filterVerdictsOf(filters, event, sandbox, now)` matches one group of filters, a trigger's or a listener's, in a frozen context of its own, each filter under a deadline of its own, 200 ms counted from its start, `mostFilterMs`, a tenth of an input's, since a filter runs on every event of its type, and a fresh context for the filters after one the sandbox stopped by its work, memory, stack or deadline, so one filter's bomb fails no other; an expression of a filter that fails says so in a filter's words, as "one filter may take 200 ms" (`src/filters/filter-verdicts.ts`). The verdict of a filter the sandbox stopped by its deadline or its memory, which the event cannot cause, says so, `stopped`, and the workflow host stops a filter for its version after 3 such verdicts in a row; one stopped by its work, or that raises, is the event's as much as the filter's and is not marked. The filters' worker remembers which worker each group was prepared on, and a test of a group prepared on a worker since replaced answers `unprepared`, so the session prepares it again on the fresh worker and tests again under the wait the filter started with (`src/jobs/remote-evaluations.ts`). The workflow host matches each group in turn.

`filterTestingOf(filters, sandbox)` serves the same filters over many events, as a page of a projection takes them: it prepares the filters once, in a session it opens at the first event it is asked about, and answers `verdictsOf(event, now)` for each event in that session, as `filterVerdictsOf` answers the group for one, each filter under its own 200 ms; once the sandbox stops a filter by its work, memory, stack or deadline it lets the session go, tests the event's remaining filters as `filterVerdictsOf` does, in fresh contexts of their own, and opens a fresh session at the next event, so one event's bomb fails no other event. Events asked about at once share the one session. `close()` lets the session go, and a session still being prepared is closed once it opens; an event asked about after the close, or while the session it waited for was closing, is answered in a session of its own, so no session outlives the testing. A filter is matched in the order of its attributes, so a caller that names `type` first never runs a test of a filter of another type, and one that names `data` first does (`src/filters/filter-testing.test.ts`). The datasets of prediction functions test each page's events so.

## The workers of the pool

The pool keeps the workers of each module URL between jobs, every module's workers sharing the pool's permits (`src/program-pool/pool-workers.ts`), and the workers of its checks apart, on their own permit. A job takes a permit, then the most recently used idle worker of its module or, when there is none, starts one, and posts it an envelope, `{ job, kind, request }`, the job's id from a counter of the pool's, `program`, `fold` or `check`, and the request as its schema in `src/jobs` encodes it, `context` among its fields; a page's progress buffer, a `SharedArrayBuffer`, travels beside the request as `progress`. The worker answers `{ job, answer, keep }`, and the pool matches the answer to the job by its id: a message that is not an envelope, an answer naming another job or one the job's kind does not decode ends the job `crashed` and lets the worker go, and a message, an error or an exit of an idle worker forgets that worker and ends nothing. An answer that arrives after the pool terminated its worker is never read.

A worker module runs `serveJobs({ program, fold, check, checks })` of the `job-loop` entry, which listens on the parent port, decodes each envelope with the schema the pool encoded it with, and hands the whole request to the handler of its kind with a host: the clock, a fresh instance of the sandbox for a program and one for each view of a page, prepared while the job before ran, and the output check of the request's `context` or the view checks of each view's schema, compiled once for each schema from the `checks` the module gives and kept, by schema, in a cache of at most 262,144 characters (`src/jobs/job-kit.ts`); with no `checks` a program goes unchecked and a view that keeps a schema stalls. A request the loop cannot read is answered `unreadable`, which a page's job reads as such and a program's as a crash, and the worker is not kept. The pool's own `src/workers/program-worker.ts` and `fold-worker.ts` serve `answerOf` and `foldAnswerOf` so; the pool names them for a request that names no worker, as the engine's own tests do, while the capabilities name the checked worker of `@on.auto/definitions` for every run.

The answer says whether the worker may be kept, by the rule of its kind: a program keeps it unless its evaluator ended it at the deadline, since the thread was busy past the job's deadline; a page keeps it unless a view ran past its fold's deadline, `overtime`, or the page was `unreadable`. The pool lets a worker go, terminating it before the job's permit is released:

- after any job the pool stopped, by its deadline, the memory, a cancellation or the closing, after any job that crashed, and after any answer that says not to keep it;
- after its 1,000th job, `jobsPerWorker`, and after a minute idle, `idleMs`, on a timer that is unreferenced, as an idle worker is, so neither holds the process open. Both are settings of the pool for tests, never for the operator.

A worker keeps between jobs its loaded modules, the compiled WebAssembly module and its compiled checks, which are pure functions of their text, and nothing of a job: every job runs in an instance of its own, discarded after it, so the same program on the same input spends the same checkpoints in a warm worker as in a fresh one, and a program that writes to `Object.prototype` leaves nothing a later job sees (`src/program-pool/job-loop.test.ts`, `capabilities/computation/src/run/warm-isolation.test.ts`). Jobs never queue on a worker, only for a permit; a worker is let go of while its last job still holds the permit, and a job whose module has no idle worker when the threads alive equal the permits first lets go of the oldest idle worker of any module, so the threads alive never exceed `workers` (`src/program-pool/pool-permits.test.ts`). Nothing starts before it is needed: the first job of a module pays its worker's start inside its own deadline. A job cancelled while it waits for its seat ends `cancelled` without a worker being started for it, and a warm worker taken for a job already cancelled goes back to rest without serving it (`src/program-pool/warm-workers.test.ts`). Since the oldest idle worker is let go of to start one of another module, jobs that alternate between two modules on a full pool keep letting go of the worker the next job needs; production therefore names one module for every job.

## The processes of the pool

`processPool({ processes, longJobs, memoryBytes, path })` runs a job in a child process: a job names the module the process runs, a key, a kind, a payload and a deadline, `{ module, key, kind, payload, deadlineMs, long? }`, and the pool hands the kind and the payload to the process without reading them (`src/process-pool/process-pool.ts`). It is the roster, shelf and fleet of [the workers of the pool](#the-workers-of-the-pool) over a thread backed by a process (`src/process-pool/process-thread.ts`), since the roster takes the way its threads start. A process is kept for its module and the caller's key, a model's digest for the prediction capability, as a worker is kept for its module. A job takes a permit of the pool's own `poolSlots`, `processes` of them, then the most recently used idle process of its module and key or, when there is none, starts one, first letting go of the oldest idle process when the processes alive equal the permits, so they never exceed them. A job marked `long` first takes one of `longJobs` permits, fewer than `processes`, so the long jobs together never hold every permit and a short job always finds one. A job waits for its permits within its own deadline, and a job that finds none in time ends `busy`; once it holds its permits its deadline counts again from that moment, so a wait for a permit never shortens the time the job itself has, and the first job of a key pays its process's start inside it.

A process is started as `node <module>`, on the server's own Node, with an empty environment, no standard input, output or error, and one channel, the IPC pipe, over which it says it is ready and then takes one job at a time. The pool looks for `prlimit` in the absolute directories of the `path` it is given, the caller's `PATH`, and reads no environment of its own. Where it finds it, as in the image, the process is started under `prlimit --core=0 --data=<memoryBytes>`. `RLIMIT_DATA`, the limit `--data` sets, counts the process's writable private address space, the native allocations of a runtime as well as V8's heap, and V8 reserves much of it eagerly, for its code range and its heap, before any work is done, so the bound limits the data a process reserves, not its resident memory, which stays far below it. With `--core=0` the kernel writes no core file; a host whose core pattern pipes dumps to a helper still hands the dump to that helper, and the job's ordinary deadline remains the guard while the helper reads it (2.2 s measured on CI). Elsewhere, as on a development machine, it is started without; on macOS a process dumps no core by default (`src/process-pool/memory-limit.ts`). The messages are JSON, `{ job, kind, payload }` to the process and `{ job, answer, keep }`, `{ job, exhausted: 'memory' }` or `{ job, failed }` back, and a typed array of any of the eleven kinds crosses as `{ "$typed": "<its kind>", "base64": "<its bytes>" }`, typed again on the other side, both ways through one Effect Schema codec (`src/process-pool/process-values.ts`). An object of those two names alone is the wire's own: the codec sends no value that holds one as an object, and reads nothing from one that is not a typed array. A number that is not finite, which JSON would carry as `null`, is not sent either. A job ends:

- `answered`, with the answer, when the process answers the job it was given;
- `timed_out` at its deadline, at which the pool sends the process `SIGKILL` and reads that signal from its `exit` event; an answer that arrives once the kill is sent is not read;
- `out_of_memory` when the loop answers `exhausted`, as it does when its handler raises the `RangeError` of an array buffer it could not allocate, or when the process dies by `SIGABRT` or `SIGTRAP`, as Node and V8 end a process whose heap or other allocation failed; they end a process by the same signals on other fatal native errors too, so the death of a native runtime by an abort reads as out of memory as well. The pool lets the process go in each case;
- `crashed`, with the detail, when the process dies otherwise, answers another job or something the pool cannot read, names a kind its module does not serve or its handler raises, or the job's payload or its answer holds what the pipe cannot carry;
- `cancelled` when the caller's signal aborts it, and `closing` when the pool closes, the process killed in both.

The pool keeps a process after a job it answered and lets it go after any other ending, after its 1,000th job and after a minute idle, `jobsPerProcess` and `idleMs`, settings for tests alone as for the workers. An idle process holds the server open no longer, and `close()` kills every process, idle and busy (`src/process-pool/process-pool.test.ts`, `process-permits.test.ts`, `process-limits.test.ts`). On Linux, where `prlimit` is, one test starts a process under the system's `prlimit` at 1 GiB, reads its limits back, and has it fill twice that in arrays of 32 MiB, which ends `out_of_memory`; it is skipped elsewhere, where the same endings are reached by a process that aborts and by one whose handler raises that `RangeError`.

A module the pool runs serves its jobs with `serveProcessJobs(handlers, process)` of the `process-loop` entry, a handler for each kind it serves, which takes the payload and answers a value or a promise of one (`src/process-pool/process-loop.ts`). The engine knows no runtime and no module of a capability's: the module is the caller's, and the tests run one written for them (`src/process-testing/fake-processes.ts`).

The server composes one such pool for the model processes of prediction functions; its settings, among them the data each process may reserve, 1,280 MiB unless set and at least 768 MiB, which the image proves by loading the `process-loop` entry under that bound, and the memory to plan for them are in [Configure the runtime](../../docs/self-host/configuration.md#prediction-functions) and [Plan memory](../../docs/self-host/production.md#plan-memory).

## Event filters

A `listen` task matches each event against its filters (`src/tasks/listen-task.ts`). `literalFilterOf(filter, pointer)` reads one filter of the same shape, `{ with: { … } }`, so that an event can be matched without a run. Its `with` names a `type`, written out as text that is not empty; it may name a `source` and a `subject`, written out the same way, and a `data`, either written out, which is compared as JSON, or an expression over `$data`, the event's data, which takes the event unless it answers `false` or `null`. The reading refuses any other attribute, any key of the filter but `with`, and what the policy refuses in a `listen` filter, `correlate`, through the same check, `eventFilterRejections`. A filter names nothing but `$data`, which the check at save holds it to, so every filter is matched over its event alone, in the host as in the run.

A `listen` filter reaches events beyond its run when its `with` names a `type` written out, text that is not an expression and not empty: `playbookWideFilterOf(filter)` answers its `with`, or nothing. `listenerFilterOf(with, pointer)` reads such a `with` for a reader that matches without a run; any attribute may be an expression, not only `data`.

`filterVerdictsOf(filters, event, sandbox, now)` answers, for each filter of one group, whether the event has its attributes, given each filter's `reference` and `attributes` alone, so a trigger keeps no more of a filter than it matches, by the comparison a `listen` task and a page of folds make, the one `attributeHolds` of `src/filters/attribute-match.ts`: `true`, `false`, or `{ error, stopped }`, the `DslError` a run would raise, for a `data` expression that fails, does more than the 250 checkpoints one expression may, or runs past the 200 ms of its filter, with `stopped` when the sandbox stopped it by its deadline or its memory rather than its work or the expression raising. It defines the group's expressions in one session the `sandbox` opens, `session(opening)`, freezes it, and matches the event in it, each test answered as a promise, each filter under a meter and a deadline of its own, the `Date` of the sandbox answering `now`, and opens a fresh context for the filters after one the sandbox stopped (`src/filters/filter-verdicts.ts`; see [The evaluation worker](#the-evaluation-worker)).

## Inputs

| Input              | Carries                                                                         | Stale when                                                                           |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `started`          | the document, the input, the limits, the attributes and a seed for random draws | the run has started (`started_before`)                                               |
| `timer_fired`      | the timer id                                                                    | the timer is not armed: never armed, fired, cancelled                                |
| `call_answered`    | the call key and the result: succeeded, rejected, failed or unreachable         | the call is not open: never started, answered, cancelled                             |
| `event_received`   | the event, with an `id` of 1 to 256 characters and a `type`                     | the run has received an event with that id                                           |
| `event_offered`    | the key of the offer, 1 to 256 characters, the key of a listener, and the event | the run took an offer of that key, holds no such listener, or the listen declines it |
| `cancel_requested` | the cancel: who asked, its kind and its reason, and optionally its cause        | a cancel was requested before                                                        |

Every input carries the run id and `at`. Any input but `started` is `not_started` for a run that has not started and `run_ended` for one that has ended. Three inputs are never taken as stale, because they mean an adapter routed wrongly: an input for another run, and a second `started` with another document or another input. `staleReasonOf` dies on them with `RunMismatch`.

An offer is an event a reader found beyond the run, for a listen that may want it (see [Listeners and offers](#listeners-and-offers)). The machine applies it only while that listen is open: it evaluates the listen's filters that name a type, in the session of the input and under its meter, takes the offer into the first of them it fits, and carries that verdict into the decision, so the filters are evaluated once. An offer the listen declines is stale and appends nothing; one whose check fails, as an expression that runs past the input's deadline, is stale too, and `submit` answers it with `declined`, the words of the error, for the adapter to report, since an offer is speculative; an event sent to the run whose check fails raises in the run, as before.

For `send_run_event`, the API answers an event the run received before (`event_received_before`) with success, since the event is delivered, and an event for a run that has ended (`run_ended`) with `not_found`, as today. A repeated event appends nothing, so it does not count toward the 1,024 events and 4 MiB a run takes over its life.

## The run's log

A run's stream is a state-transition log, not classic event sourcing. Each event records the change an input made to the run's state, as a patch, rather than a domain fact for the fold to interpret. Replaying a run applies patches and evaluates nothing: no expression, no retry arithmetic, no version of the machine's code. What the events give up in meaning they get back in two fields written for people reading the log.

Each event, `input_applied`, holds:

- `format`: the state format its patch applies to.
- `receipt`: the kind of the input, the key it is deduplicated by and its time; for an answer, the result's status, and for a rejection that names them, its `rejection`, the `kind` and `because` of the result, and for an external event, its type. The input's payload is not stored again: what it changed is in the patch.
- `steps`: one entry for each run of a task the input moved, in the order the runs first moved in the input, with the outcome it had when the input ended (`src/steps`). An entry is `{ reference, run, outcome, name, times, caused_by }`, with `error`, `waits_for` and `child` when they apply:
  - `outcome` is `started`, `skipped`, `waiting`, `completed`, `raised`, `timed_out` or `cancelled`. A task records `started` when it starts, before anything of its own is evaluated, a call's arguments included, and a later outcome of the same run in the same input replaces it in its place: a task that starts and finishes in one input has only `completed`, a call only `waiting`, a skipped task only `skipped`, and `started` stays only for a task still running when the input ends, a `do`, `for`, `fork` or `try` whose tasks wait. `raised` is recorded for the task that raised and for each frame the error leaves; a cancelled task records `cancelled`, with no error.
  - `name` is the task's name, cut at 256 bytes of UTF-8 at a code point.
  - `times` counts the entries of the run's log so far with the same reference, run and outcome, from 1, so the four name one entry within the run. It goes past 1 only for a listen for all of several events, which records `waiting` again in each input whose event does not complete it; its frame keeps the count, `waited`.
  - `caused_by` is the reference, run, outcome and times of the entry whose outcome made this one move, or `input` when the input itself did, as for the first step of a run. A task that starts in the input is caused by the step before it: the one before it in its list, after a `then` jump included, so the branch a `switch` takes by the switch; the first task of a list by the task that runs the list; each branch of a `fork` by the fork; the attempt a retry starts by the entry that failed the attempt before it; and the task after a yield by the entry before the yield. A task that started in an earlier input is caused by its own latest entry there: `waiting` for a wait, a listen or a call, `started` for a task that runs others, which the runner tells the journal as it resumes or cancels the task (`continues`). An entry that a later outcome replaces keeps its cause, and the entries it caused name it as it ended the input, so every cause names an entry of this event or of one before it. A `cancelled` entry does not move the cause on.
  - `error`, for `raised` and `timed_out`, is the error's `type` and `title`, the title cut at 1 KiB.
  - `waits_for`, on a `waiting` entry, is what the step waits for: `timer` for a wait, `event` for a listen, `call` for a call.
  - `child`, on the `waiting` entry of a call, is the id of the run the call starts, which the machine takes from `childOf` of the functions it is given, called with the function's name, the call's reference and run, its arguments and the run's attributes; it answers nothing for arguments the function would refuse, so an invalid call names no child.
- `resumed`: the reference, run and times of the `waiting` entry the input resumed: a wait its timer ended, a call its answer or its deadline ended, a listen an event moved. It is null for `started`, for a timer of a yield, a timeout, a retry's delay, an attempt's limit or the run's deadline, for an event no listen took, and for `cancel_requested`.
- `patch`: the change to the state, as JSON Patch operations (RFC 6902 `add`, `replace` and `remove`) addressed by JSON Pointer. A list that grew is patched at the positions it had and appended to, with an `add` at `<list>/-` for each new item, so the ids a run received cost one operation each, not the whole list again; a list that lost items is replaced whole.
- `outputs`: what the engine must do because of this input.

An input that is stale or not started appends nothing; logging it is the adapter's job.

### History bytes

The state counts the bytes of its own history, `historyBytes`: the UTF-8 bytes of every event in the stream as JSON (`eventBytesOf`), the event that sets it included. The machine builds an event, measures it, and adds `replace /historyBytes` with the count before it plus the bytes of the event that carries that operation (`withHistoryBytes`, which solves for the few digits the number adds). So `decide` knows the history before it appends, and bounds it as it bounds inputs. A load checks the count: a state whose `historyBytes` is not the snapshot's count plus the bytes of the events after it is `UnreadableRun`.

Compression is not part of the format. A run store may compress the events and snapshots it keeps; `historyBytes`, and every bound on a history, counts their JSON uncompressed, so the bounds of a run are the same in every store.

## State formats

Every event and every snapshot names its state format; `stateFormat` is 9. A change to the state's schema, or to the schema of an event or a snapshot, is a new format, and:

- an event and a snapshot are read with the schemas of the format they name: an older format's are frozen copies in `src/run-log/formats/`, one reader for each format with its test beside it, read strictly, and an event of an older format is measured as it was written (`eventBytesOf`), so its bytes are those its history counted;
- each event is folded under its own format, and a state that crosses to a newer format is read strictly under the old one and upcast by that format's upcaster (`OlderFormat.read`, `OlderFormat.upcast`) before the next event applies;
- formats never go back within a stream, and a format newer than the code is refused, both when the run loads (`UnreadableRun`);
- `packages/workflow-engine/corpus/format-<n>.json` holds a committed stream and snapshot of every format, which must load to the state it recorded (`src/run-log/corpus.test.ts`). A new format adds its corpus and keeps every older one loading.

Format 2 came with the machine: a frame records when it started and the context it started with, since a task that waits evaluates its `output.as` and its listen filters later with the variables it started with; an armed timer records when it was armed, since a timeout names the milliseconds it allowed; a fork branch can yield before it starts, as a task in a list can; and a failed branch records the order it failed in, since a competing fork that loses every branch raises the first failure. A list always names what it waits for, the task it runs or the timer due at once it yields to, and a loop always holds the list of the iteration it is in, so neither is ever null: the machine only stores a list or a loop that waits. Format 1 is read strictly with its own frozen schema (`src/run-log/formats/format-one.ts`) and upcast: frames start at the last input with the context then, timers were armed at the last input, and failures are ordered as their branches. A format-1 state with a list between its tasks has no format-2 form and does not load; no runtime ever wrote one, since format 1 had no machine.

Format 3 came with the kind and because of a rejection: a call's result, `CallResultSchema` of `@on.auto/operations`, may name the `kind` and `because` of a rejection, and the error it raises, `DslError`, keeps them, so a failed branch, a `try` backing off and a run that ended raised hold them, and a `catch` reads them in its error. A state of format 2 is a state of format 3 as it is: format 2 is read strictly with its own frozen schema (`src/run-log/formats/format-two.ts`), which refuses an error with either member, and passed on unchanged. Format 1 reads its errors and its outcome with format 2's frozen schemas, as it did, and both read with frozen copies of every schema they use, the instant, the call key, a received event, the run's limits and the purposes of timers among them, so a change to the current schemas cannot change how a state of format 1 or 2 reads.

Format 4 came with the step entries: across inputs the state keeps, in a list waiting for a yield's timer, `after`, the entry that came before the yield, so the task after it is caused by that entry; in a `try` backing off, `failed`, the entry that failed the attempt, so the next attempt is caused by it; and in a listen, `waited`, the `waiting` entries it recorded, so the next one counts on. Format 3 is read strictly with its own frozen schema (`src/run-log/formats/format-three.ts`) and upcast: a yield and a back-off were caused by `input`, and a listen waited once. Events of formats 1 to 3 keep their steps as they were recorded, `{ reference, run, outcome }`, one for each run of a task with how it ended the input, and no `resumed`; the event schema reads both.

Format 5 came with reactions: the state keeps `listeners`, the listen tasks open with a filter that names a type, by the key of their task run; `emitted`, the count and the bytes of the events the run emitted; `inbox.offeredIds`, the keys of the offers it took, a list apart from `receivedIds`; and a listen for all of several filters keeps its events by filter, `consumed[i]` the event of filter `i` or null, since it takes events in any order. Format 4 is read strictly with its own frozen schema (`src/run-log/formats/format-four.ts`) and upcast: no offers and no emissions, a listener for every open listen whose task names a type in a filter, found in the document the state holds, and its events, taken in filter order, already where format 5 keeps them.

Format 6 came with waiting calls and cancellations: the run's limits may hold `longestCallMsByTask`, the longest a call of each task may take, by its reference, and a cancelled outcome holds `cancel`, who asked, the kind (`requested`, `deadline` or `parent_ended`) and the reason, so the run's settlement says who cancelled it and why. Format 5 is read strictly with its own frozen schema (`src/run-log/formats/format-five.ts`) and upcast: a cancelled outcome gains a cancel by `unknown`, of the kind `requested`, whose reason says it was recorded before a cancel named who asked.

Format 7 came with the one vocabulary: the state, its call keys, the outputs of an event and the envelope of a snapshot name the run `runId`, where formats 1 to 6 named it otherwise. Format 6 is read strictly with its own frozen schema (`src/run-log/formats/format-six.ts`) and upcast by naming the run `runId` in the state, in the keys of its calls and listeners, and in the key of every call frame. The events and snapshots of formats 1 to 6 are read strictly with the frozen schemas of `src/run-log/formats/format-six-records.ts`, which give their outputs and envelope the new name, and are written back and measured with the old. What a run holds as data, its document, its held values and a call's function and arguments, keeps the words it was written with.

Format 8 came with tool servers of two kinds: a rejection names a tool server that failed `tool_server_failed` and one not configured for the playbook `tool_server_not_configured`, where the words of format 7 named the transport; a call's result reaches the state through `raised-error.ts`, so the error a failed branch, a `try` backing off and a run that ended raised holds them. Format 7 is read strictly with its own frozen schema (`src/run-log/formats/format-seven.ts`) and upcast by giving the kind and the because of each of those errors the words of format 8. The events and snapshots of format 7 are read strictly with the frozen schemas of `src/run-log/formats/format-seven-records.ts`, and those of formats 1 to 6 with theirs, which give the settlement of an output and the rejection of a receipt the words of format 8, and are written back and measured with the words they were written with. Format 8 has no `not_testable`, which was the refusal of a test of a tool and which no run's settlement ever held outside a workflow's own raise, so a receipt and a raised error, which hold their words as strings, keep it as written, and a settlement that holds it is refused when it is read rather than mapped (`isNotATestRefusal`), so the run that holds it does not load. What a run holds as data, its held values and the output it ended with, keeps its words.

Format 9 came with the issues of a refusal: a call's result, `CallResultSchema` of `@on.auto/operations`, may carry the `issues` of a rejection, each a `pointer` and a `detail`, and the error it raises, `DslError`, keeps them, so a failed branch, a `try` backing off and a run that ended raised hold them, a `catch` reads them in its error, a `raise` that names them raises them again, and a run that ended on an uncaught `invalid_input` settles with them. A state of format 8 is a state of format 9 as it is: format 8 kept the shape of format 7, so it is read strictly with the frozen schema of `src/run-log/formats/format-seven.ts`, which refuses an error with `issues`, and passed on unchanged (`src/run-log/formats/format-eight.ts`). The events and snapshots of format 8 have the schemas of format 9 and are read with them. Its corpus, `corpus/format-9.json`, is the run of the recorded path `refused-input` of the workflow capability, which ends on a refused input: its snapshot holds a failed branch whose error carries the issues, and its last event the run that ended raised with them.

Patches are never rewritten: a patch applies only to the format it was written for. `evolve` applies a patch strictly, `add` to a member that exists or `replace` and `remove` of one that does not die with `PatchFailed`, and the result must decode as the state with no member the format does not describe (`onExcessProperty: 'error'`), so a skew between a log and the code that reads it is caught when the run loads, never folded into a wrong state.

## Held data and the size of a patch

Values a run holds live once, in the state's value table, `machine.values`: the run's input, the result of a call, the arguments of a call, the data of an event, the output of an expression. Each value has an id that counts up within the run and is never reused, and its size in bytes of UTF-8 JSON. Frames, list cursors, variables, branches, the context and the workflow's input refer to values by id, so passing a value on moves an id, not a copy.

After each decision the machine sweeps the table: a value stays while the frames, the context or the workflow's input reach it, and the others leave with `remove /machine/values/<id>` (`withReachableValuesOnly`). The data a run holds, `heldBytes`, is the bytes of the values reached, plus 4 KiB for each frame, plus the document (`heldBytesOf`); a property test over 400 generated states checks it against the values an independent walk finds. That bounds the state, and every snapshot, at 4 MiB of held data. It also bounds a patch: an input adds each value it made once and otherwise moves ids, so a call that answers with 1 MiB gives a patch of about 1 MiB however many places the answer lands.

A transformation can still make more data than it was given. The machine measures each event before the append; one over 1.5 MiB ends the run with a `raised` runtime error, status 500, the ending today's limits give, recorded as a small final event.

So a value a run holds across a wait or a yield is bounded by one event, not by the 4 MiB a run holds: the event of the input that made the value carries it whole, with the rest of that input's change, and that event holds at most 1,572,864 bytes of JSON. A value larger than that, less the rest of its event, ends the run raised, `An input changed the run by N bytes, more than the 1572864 one event holds`; in the three tasks of `src/decider/run-bounds.test.ts`, a string of 1,570,322 characters is kept across a wait and one character more is not, the rest of the event taking the other 2,542 bytes. A value made and let go of within one input never reaches an event and is not bounded by one.

Frames never store the document: they name tasks by reference, a JSON Pointer into `workflow.document`. A call frame holds the opaque `function` the call names, its `arguments` as a value id, a `label` for people reading the log, and the id of its `call_deadline` timer, which it disarms when it is answered or cancelled; the machine knows nothing of what the arguments mean.

## Outputs and receipts

| Output            | Carries                                                        | Idempotent by  | Port                 | Receipts                                                                        |
| ----------------- | -------------------------------------------------------------- | -------------- | -------------------- | ------------------------------------------------------------------------------- |
| `arm_timer`       | timer id, due time, purpose, a label                           | timer id       | `Timers.arm`         | `armed`, `already_armed`, `refused_after_cancel`                                |
| `cancel_timer`    | timer id                                                       | timer id       | `Timers.cancel`      | `cancelled`, `already_fired`, `tombstoned`                                      |
| `start_call`      | call key, the function, its arguments, the longest it may run  | call key       | `Executor.start`     | `started`, `started_again`, `running`, `answered_again`, `refused_after_cancel` |
| `cancel_call`     | call key, and the reason, `deadline` or `parent_ended`         | call key       | `Executor.cancel`    | `cancelled`, `already_answered`, `tombstoned`                                   |
| `arm_listener`    | the key of the listen's task run, its filters that name a type | the key        | `Listeners.arm`      | `armed`, `already_armed`, `refused`                                             |
| `cancel_listener` | the key                                                        | the key        | `Listeners.cancel`   | `cancelled`, `not_armed`                                                        |
| `emit_event`      | the key of the emit's task run, the event                      | the event's id | `Emitter.emit`       | `recorded`, `already_recorded`, `refused`                                       |
| `settle`          | run id and settlement                                          | run id         | `RecordStore.settle` | `recorded`, `already_recorded`, `settled_otherwise`, `unknown_run`              |

`Timers.arm`, `Executor.cancel` and `RecordStore.settle` are also given the origin of the output, `{ version, lastStep }`: the version of the event that holds it and the key of that event's last step entry, or null. An adapter keeps the version an arm came from, so the record of a timer's fire can name the record that armed it, settles a run with the last step of the event that ended it as the cause, and cancels the run a cancelled call waited for with that entry as the cause.

The run store's `append` takes, with the event, its lineage, `{ cause, attributes }`: the run's attributes, and what caused the input, `start` for `started`, `resumed` with the key of the `waiting` entry for an input that resumed one, `timer` with the timer id for any other fire, and `none` otherwise. An adapter turns them into the ids its store writes; the engine knows no ids of messages.

Answers come back as inputs: a fired timer as `timer_fired`, a finished call as `call_answered`. Every receipt is final; only a failure to answer, `DispatchFailed`, leaves an output to be dispatched again, except that a `start_call` that fails for a run that has ended is passed over, since nothing can use it any more and it would hold the run's later outputs, its `settle` among them; a `cancel_call` is never passed over, since the run its call waits for must still be cancelled, and neither is a `settle`. A settle receipt of `settled_otherwise` or `unknown_run` is troubling (`isTroubling`): the engine hands it to `RunReporter.unsettled`, which the adapter logs, as `reportUnsettled` does today.

A call is idempotent by its key in this sense: it is answered at most once. A start for a key the executor has answered delivers the answer again (`answered_again`); a start for a key it is running leaves it running (`running`); a start for a key that is neither, because the host that ran it died, starts it again (`started_again`), as the Node spike's `ensureJob` restarted a call. And every open call is answered eventually: each `start_call` comes with an `arm_timer` of purpose `call_deadline`, due at the input's time plus the longest the call may take, which is `longestCallMsByTask` of the call's task when the limits name it and `longestCallMs` otherwise, never later than the run's own deadline; when it fires with the call still open the task fails with a `timeout` error, status 408, which a retry policy matches only when it names it, and the call is cancelled with the reason `deadline`. A dead executor host therefore holds a run for at most that long, not until its 30-day deadline.

Every cancel the timer store or the executor takes for a key that has not fired or been answered is recorded as a tombstone, whether the key was armed, running or never seen, so an arm or a start of that key that arrives later is refused (`refused_after_cancel`). Dispatch takes outputs in the order of the stream, so a start always reaches the port before its cancel; tombstones matter when a dispatch is repeated from a watermark left behind, as a due note that fails leaves it, which sends an arm or a start again after the cancel that followed it, and to an executor that takes work asynchronously, such as from a queue, where a cancel can overtake its start.

The machine checks only the size of a call's arguments, at most 264 KiB as JSON. The executor checks what they mean, such as a type, a name and an input, and answers `rejected` with reason `invalid_arguments` and a detail when they are wrong. The machine maps a rejection's reason to the task's error through one table (`callErrorOf` in `src/dsl/raised-error.ts`), with `invalid_arguments` as a `validation` error, status 400, carrying the executor's detail.

| Key          | Made of                                                     | Deduplicated in                                 |
| ------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| run id       | given by the adapter that starts the run                    | the run's status; `RecordStore` by run id       |
| timer id     | `<n>`, counting up within the run                           | `state.timers.armed`; `Timers` by run and id    |
| call key     | run id, the task's reference, the run of that task          | `state.calls`; `Executor` by `callKeyText(key)` |
| event id     | the external event's own `id`                               | `state.inbox.receivedIds`                       |
| offer key    | given by the adapter that offers, the id of what it found   | `state.inbox.offeredIds`                        |
| listener key | run id, the listen's reference, the run of that task        | `state.listeners`; `Listeners` by the key       |
| emitted id   | a version 5 UUID of the emit's call key, `emittedEventIdOf` | the store the `Emitter` writes                  |
| value id     | n counting up within the run                                | `state.machine.values`                          |

A run keeps one counter of runs for each task reference, `state.runs`, so the third time a task runs its run is 3, and a call it starts has that run in its key. An adapter that gives a call its own run, as a call to a definition has, derives that run's id from the call key, so a call dispatched twice is one run.

The event store deduplicates nothing: Emmett appends a message with an id it has seen before as a new message, on SQLite and on PostgreSQL alike. Deduplication lives in the run's state.

## The dispatch watermark

The watermark of a run is a stream version. Every output of every event at or below it has been dispatched at least once. A dispatch takes the outputs above it in the order of the stream and stops at the first that fails; the watermark then moves to the last event whose outputs were all dispatched, `dispatchedThrough(watermark, events, firstFailed)`, and never goes down. A crash between the append and the dispatch loses nothing: the outputs are in the event, and the next wake dispatches them.

## Serialisation

One input at a time for each run is the adapter's job: it is the one host that holds the claim on the database's workflows, with a lock per run in memory; a second host on the same database stands by, and a claim of each run is a later step (`@on.auto/workflow-host`). Whatever slips past, the expected version of the append catches.

On Node the timers table goes through the ledger's own SQLite driver or lives in a separate file: written through a second SQLite library to the ledger's file, committed cancels were lost.

## Due runs and the sweep

The record keeps, for each live run, its next due time, the earliest of its armed timers (`RunDue`). The engine writes it while dispatching an event that arms, cancels or fires a timer, idempotent by the event's version, and when a dispatch stops at a failure. A run whose dispatch fell behind is not written down anywhere: its watermark is below the version of its stream, so it has outputs not yet dispatched and is due now, and `DispatchWatermark.behindRuns(limit)` names such runs. The ledger's database holds every run's stream, so the adapter finds them by joining its watermarks to its streams. A failed note of the due time is such a failure: the watermark stays below the event, so the run is behind until a dispatch notes its time, whether its timer fired or was lost. While notes keep failing, every input to the run dispatches again the outputs above the watermark it holds, and the ports, idempotent by key, take them as already done. An adapter learns that a dispatch fell behind from `wake`, whose `dispatchedThrough` is then below `version`. A running run always has a timer armed, its deadline, and its due time noted or its dispatch behind, so it is always due at some time.

`sweep(before)` asks `RecordStore.dueRuns(before)` for the runs due before that time and `DispatchWatermark.behindRuns` for at most 1,024 runs that are behind, those a sweep took longest ago first, each run marked with the time it was taken (the memory watermark counts its hand-outs), so a run left out of one sweep is taken before any run is taken twice (the watermark's probes of `src/testing/store-probes.ts`), and takes only those: for each it calls `wake`, and `Timers.sweep` with the run's armed timers, which arms again any the timer store lost. It folds no other run. The workflow host sweeps every `WORKFLOW_SWEEP_INTERVAL`, a second by default, and passes a time one minute ago, so a run is swept once its timer is a minute late (`@on.auto/workflow-host`, `src/loop/host-loop.ts`).

## State and snapshots

A run's state is plain JSON: no `Map`, `Set`, `Date`, `undefined`, class or function, so `JSON.parse(JSON.stringify(state))` is the state.

A snapshot is `{ format, runId, version, historyBytes, state }`, the state folded from events 1 to `version`, written only once event `version` is durable; the run store keeps only the latest. A snapshot is due once the events since the last one take as many bytes as that snapshot did, and at least 1 MiB, so writing snapshots never costs more bytes than the history they cover.

A snapshot holds at most about 5.3 MiB: the held data (4 MiB: the values, the document and the frames), the events waiting in the inbox (1 MiB), the ids of the events received (1,024 of at most 256 characters), and the timers, calls and run counters, a few dozen bytes for each frame. It is stored in chunks of at most 1 MiB of UTF-8, cut by `TextEncoder.encodeInto` at a code point, never inside one; a 5.2 MB snapshot took 4 ms to encode and chunk.

## The machine

`workflowMachine(options)` is the run's decider. It is given the functions a workflow may call and the runtime its expressions see as `$runtime`, and `decide(input, state)` gives the one event an input makes.

- A decision opens a session over the state (`src/runner/session.ts`): the value table, the armed timers, the open calls, the inbox, the run counters, a meter of the input's work and a journal of its steps and outputs. The event's patch is the difference between the state before and the state the session ends with (`src/decider/state-diff.ts`), so nothing writes the patch by hand.
- A run is a tree of frames, one for each task that waits, under the root list. An input becomes a signal, a timer fired, a call answered or events arrived, passed down the tree; the frame whose timer, call or listen it is resumes, and the others stay as they are.
- A task starts as soon as its list reaches it, and finishes in the same input unless it waits: on a timer (a wait, a retry's delay, an attempt's limit, a timeout), on a call or on events. A list that ran 100 tasks, or 250 checkpoints of expression work, in one input arms a timer due at once and goes on when it fires (`src/runner/list-runner.ts`).
- `started` arms the run's deadline, due when the run has run the most it may, `mostDurationMs`; its fire ends the run `overran`, settled as `cancelled` of the kind `overrun`. A call arms its `call_deadline` and keeps its id. A cancel, an end or a timeout cancels what the frames under it wait for, and a task that raises before it waits disarms its own timeout. A call cancelled by a timeout, an attempt's limit or its own deadline is cancelled with the reason `deadline`, and one cancelled because its run ended or its branch lost a race with the reason `parent_ended`.
- A run ends `completed`, settled `succeeded`; `raised`, settled `rejected` by the error's status, or as `conflict` of the kind `tools_called` or `effect_unknown`, or `unavailable` of the kind `tools_unfinished`, for those types, the last two with the error's `because`; an uncaught error of the type `cancelled`, raised by a call whose run was cancelled, settles by its status too, 409, since the workflow itself was not cancelled; an uncaught error of the type `unanswered`, raised by a call whose request nobody answered, status 410, settles `rejected` as `unanswered` with its kind, `expired` or `undelivered`, as the request it waited for ended; `cancelled`, settled `rejected` as `cancelled` with the cancel's kind, reason and actor; `oversized`, settled `rejected` as a `conflict` of the kind `oversized`; and `broken`, settled `failed`. An uncaught error of the problem type of a conflict and the kind `unworkable`, which an output the functions refuse raises, settles as that conflict. The detail of a rejection is `describeError`'s: the error's title, or else its type, then the step that raised it by the name its document gives it (`stepNamedAt` of `src/dsl/tasks.ts`), never its pointer, then its detail, so the place is said before a long detail and binds to no sentence of it; an error of the whole workflow names no step and one outside the steps names its pointer. The error of a call that was rejected is titled with the definition and what its reason did, in the plain words of `refusalInWords` of `@on.auto/operations`, such as `The computation function month-window refused its input`, never the reason's code, unless the functions the machine is given word it, with `refusal(name, arguments, rejection)`, the rejected call as `CallResult` gives it, its `kind` and `because` among its fields (`src/tasks/call-refusals.test.ts`); the workflow capability says a workflow it ran `stopped` when one of its steps did, and `refused its input` when the rejection is of the kind `input_schema` (`src/document/workflow-functions.test.ts` of `@on.auto/coordination`). A rejection as `invalid_input` keeps the issues of the error.
- An event leaves out a timer or a call that the same input opened and closed (invariant 26), and its other outputs keep the order the session emitted them in.
- A run ends with its outcome, settled once in its last event. An input that would pass a bound (inputs, history, held data, the size of one event) ends the run, raised, in a small event of its own.
- The machine's tests run it through the memory driver of `src/testing`; each piece of the design has one that fails without it, the step entries and their causes in `src/steps`. The workflow adapter runs its tests of how a workflow runs through this driver (`capabilities/coordination/src/workflows`), and replays its 16 recorded input logs through the machine (`capabilities/coordination/input-logs/`).

## Listeners and offers

A `listen` task that waits arms a listener when at least one of its filters names a type: its event carries `arm_listener`, with the key of the task run, `{ runId, reference, run }`, and the `with` of those filters, and the state keeps the key in `listeners`. When the listen ends, by taking its events, by a timeout, a cancel or the end of the run, its event carries `cancel_listener`. A listen that an event already waiting satisfies at once never arms one. An adapter keeps the listeners its dispatch hands it and offers them the events it finds, as `event_offered`, keyed by what it found them by; the machine applies an offer only while that exact listen is open. A listen for one or any filter takes an offer that one of its filters naming a type accepts; a listen for all takes it into the first of those filters, in list order, that no event satisfies yet and that it fits, and hands its events on in filter order once each filter has one. Events sent to the run take the same order-free way: each filter takes the earliest waiting event it fits. A filter that names no type keeps its meaning: it sees only the events sent to its run. The keys of offers and the ids of sent events are two lists, so neither blocks the other, and both count toward the 1,024 events a run takes (`src/tasks/listen-offers.test.ts`, `src/tasks/listen-orders.test.ts`).

## Emitting an event

An `emit` task, `emit: { event: { with: { type, source, … } } }`, evaluates `with` as a template on its input and emits the event: `type` and `source` are text that is not empty, and `id` is refused, since the runtime gives the event `emittedEventIdOf` its call key, a version 5 UUID, so a run that is stopped and resumed emits it once; `specversion` is 1.0, and `time` is the time given or the time of the input. Its event carries `emit_event` with the key and the event, and the state counts it in `emitted`. The task hands its input on. The functions a machine is given may refuse more: `emitRejections(with, pointer)` when a document is checked, and `emitRefusal(event)` when the event is made, which the task raises as a `validation` error (`src/tasks/emit-task.test.ts`).

## The output of a run

The functions a machine is given may refuse the output a run ends with: `outputRefusal(document, output)`, given the run's document and its output after `output.as`, which the workflow adapter gives to check an `output.shape` (`capabilities/coordination`). A refusal ends the run `raised` at the root with an error of the problem type `https://on.auto/problems/conflict`, status 409, of the kind `unworkable`, whose title is the refusal (`unworkableOutputOf` in `src/dsl/raised-error.ts`), which settles `rejected` as a `conflict` of the kind `unworkable`. Nothing catches it, since every task has ended, and a run with no refusal ends as it did (`src/decider/run-lifecycle.test.ts`). The state keeps the error as it keeps any other, so the state's format is unchanged.

## A schedule

The policy refuses `schedule` unless the functions it is given check it, with `scheduleRejections(schedule, pointer)`, which the workflow adapter gives (`capabilities/coordination`). The machine never reads a schedule: a run starts the same way however it was started.

## The cache of loaded runs

Each engine keeps the runs it loaded between their inputs (`src/cache/run-cache.ts`), so an input does not load again the snapshot and the events the input before it left. A kept run is the state, the version and the bytes since its snapshot that the decision of the last input gave, and it is used only while its stream has no event after that version: the engine asks the run store for the events after it, and a run whose stream moved on, written by another process or by an append whose answer was lost, is loaded from the store again (`src/cache/cached-inputs.test.ts`).

- An append that fails, a conflict or an outcome the store never told, lets go of the kept run, so the retry after a conflict, and the next input after a lost answer, load the run from the store (`src/cache/kept-runs.test.ts`).
- A kept run counts the bytes of the events since the snapshot the store holds, and a saved snapshot lets go of it, so the next load reads the snapshot's bytes as the store keeps them and each snapshot is written when it is due (`src/cache/cached-snapshots.test.ts`).
- The cache keeps at most 1,024 runs and 64 MiB of the data they hold (`heldBytes` and the bytes of the events waiting in their inboxes), letting go of the run used longest ago (`runCacheBounds`); a run that alone holds more is not kept. An adapter can give its engine a cache of other bounds.
- The machine never writes to a state in place: the memory driver keeps every run frozen to its leaves, so every test that drives a run, the workflow adapter's on the machine and its recorded input logs among them, decides each input on a frozen state, where a write throws (`src/testing/frozen-runs.ts`, `src/cache/kept-runs.test.ts`).

## Open design points

- A history takes 2,305 bytes an input for the loop above; it was 1,804 before format 4 gave each step entry its name, its count and its cause. Its 20,001st event is 2,313 bytes: 18 patch operations (1,282 bytes: the list's data and the frame's run, start, inputs and timer, three run counters, a value in and a value out, a timer in and a timer out, and the counters of the state), four step entries (695 bytes), an `arm_timer` (147 bytes) and the receipt (55 bytes). Within 512 MiB a run of 100,000 such inputs takes 220 MiB, so no bound moves. The patch stays RFC 6902, so what remains to shrink it is a store that compresses what it keeps (see History bytes).
- `evolve` decodes the whole state after each patch, about 19 µs an event over the 40,000 inputs above: a cold fold of all of them took 0.76 s, and a load with the most events a snapshot leaves after it, 453, took 8.10 ms. With the cache of loaded runs an input folds one event, and only a run loaded again pays for its tail, so checking only the patched paths is not needed yet.
- The limits on a run's history are 100,000 inputs and 512 MiB; real use may move them.
