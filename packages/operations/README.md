# @on.auto/operations

The application layer of Auto Runtime: where operations are defined and run.

An **operation** is a **query**, which reads, or a **command**, which changes something. Its **scope** is `org` or `playbook`. Transports such as HTTP and MCP serve the operations of a catalog; this package knows nothing about them.

## Defining an operation

```ts
import { NotFound, OrgReader, defineQuery, factOf, type Decider } from '@on.auto/operations';
import { Effect, Result, Schema } from 'effect';

const LabelSchema = Schema.Struct({ name: Schema.String, text: Schema.String });

type Label = typeof LabelSchema.Type;

const LabelWrittenSchema = factOf('label_written', LabelSchema);

type LabelWritten = typeof LabelWrittenSchema.Type;

export const labels: Decider<readonly Label[], Label & { readonly by: string; readonly at: string }, LabelWritten> = {
  initialState: [],
  evolve: (written, { data }) => [...written, data],
  decide: ({ name, text }) => Result.succeed([{ type: 'label_written', data: { name, text } }]),
  context: ({ by, at }) => ({ by, at }),
  eventSchema: LabelWrittenSchema,
};

export const getLabel = defineQuery('org', {
  name: 'get_label',
  title: 'Get label',
  description: 'Reads one label of the org.',
  route: { method: 'GET', path: '/labels/{name}' },
  inputSchema: Schema.Struct({ name: Schema.String }),
  outputSchema: LabelSchema,
  reasons: ['not_found'],
  handle: Effect.fnUntraced(function* ({ name }) {
    const { state } = yield* (yield* OrgReader).load('labels', labels);
    const label = state.find((written) => written.name === name);
    if (label === undefined) {
      return yield* new NotFound({ detail: `There is no label ${name}` });
    }
    return label;
  }),
});
```

The compiler holds a definition to these rules:

- A query's route uses `GET`, or `POST` for an input a query string cannot carry, such as an object, which a transport then takes from the body; a command's uses `POST`, `PUT` or `DELETE`. A `GET` and a `DELETE` take no body, so a transport takes their input from the path and the query string, as `takesNoBody(route)` says. The method decides nothing else: a query by `POST` is a query, permitted by the read permission of its scope and marked read-only over MCP. Only a command may answer `201` instead of `200`.
- The route path is relative to the scope's prefix. Each `{parameter}` must be a string field of the input.
- The input may not have an `org` field, nor a `playbook` field at playbook scope.
- The handler may fail only with the rejections it declares in `reasons`: `NotFound`, `Conflict`, `Unavailable`, `InvalidInput`, `RunCancelled`, the rejection of a run that was cancelled, with the kind `requested`, `deadline`, `overrun` or `parent_ended`, answered with HTTP 409 and no `Retry-After`, `RunUnanswered`, the rejection of a run whose request nobody answered, with the kind `expired`, `undelivered`, `declined`, `signed_out` or `no_person`, answered with HTTP 410 and no `Retry-After`, or `Forbidden`, for an operation that authorizes its caller itself (below).
- The handler may ask only for the services of its scope and kind:

| Scope      | Query                                                              | Command also gets               |
| ---------- | ------------------------------------------------------------------ | ------------------------------- |
| `org`      | `Caller`, `OrgContext`, `OrgReader`                                | `OrgWriter`                     |
| `playbook` | `Caller`, `PlaybookContext`, `PlaybookLifecycle`, `PlaybookReader` | `PlaybookWriter`, `CallLineage` |

When an operation is defined, it checks again what the compiler cannot see, on the encoded form of its schemas, the form that travels:

- the name matches `^[a-z][a-z0-9_]{0,63}$` and the route path is well formed;
- the input and the output are objects that declare their fields, or unions of such objects, with no empty struct at any depth (an input with no fields is `Schema.Record(Schema.String, Schema.Never)`);
- no input field is named `org`, nor `playbook` at playbook scope;
- each route parameter is a required string field of every member of the input;
- a field the handler calls `playbook` also travels as `playbook`.

At run time, when a handler fails with a reason it did not declare, the call fails; it is not rejected.

A definition may give `linkToOpen`, a function of its output that answers `{ message, url }`, or nothing where the output holds no link: a page the person is to open, such as Studio's page that approves a connection, and a sentence of what to do there. It gives `answerAfterTheLink` with it, `{ idOf, read, linkLastsMs }`: the id of what the link is for, read from the output, `read({ id, url })`, which answers the output as it stands once the person is back from the page, with the services a handler of its scope and kind may use, and how long the link lasts, in milliseconds, so the retry is answered as long; a definition that gives one of the two without the other is refused. The registration carries them as `link`, `{ toOpen, idOf, answerAfter, linkLastsMs }`, `toOpen` and `idOf` functions of the output as JSON, `answerAfter(link)` a registration like its own whose run decodes the call's input as its own does and answers what the read gives. An MCP tool asks a client that opens links to open the page and answers the client's retry with `answerAfter` (`@on.auto/api`); the output holds the address either way.

A definition sets `reachesOutside: true` when its handler calls a system outside the server, such as a model provider, and `mayChangeOutside: true` when that call may change something there, such as a tool that writes; the registration carries both, `false` when left out, and a transport can tell its callers, as the MCP tools do with `openWorldHint`. A command sets `readsOnly: true` when what it calls only reads, though the call is recorded, such as `query_connection` of `@on.auto/tool-servers`, which calls only a tool marked `reads`; the registration carries it, `false` when left out.

A command sets `irreversible: true` when what it does cannot be undone, such as retiring a playbook or cancelling a run, and `repeatable: true` when a repeat of the same call records nothing more, such as an update that changes nothing or retiring what is already retired. The registration carries both, `false` when left out; the MCP tools take `readOnlyHint` from a query or `readsOnly`, `destructiveHint` from every tool that is not read-only, whatever it changes, and `idempotentHint` from a query or `repeatable`.

`Unavailable` and `Conflict` may carry a `kind` and with it a `because`, one of `RejectionBecauseSchema`. Both reach the rejected outcome, where `explanationOf` and `unsuccessfulWords` turn them into plain words, and the problem document, as its extension members `kind` and `because`. An operation's `plainLanguage` may give `remedies` by `because`, which `unsuccessfulWords` puts in place of the shared remedy for that operation alone.

Plain words have the bounds of [`@on.auto/phrasing`](../phrasing/README.md#bounds): an outcome takes at most `mostOutcomeCharacters`, 400, the words of a refusal at most `mostRefusalCharacters`, 600, and the words an operation relays at most `mostRelayedCharacters`, 1,000, each kept within its bound by `withinCharacters(text, most)`. `PlainLanguage.relayed(output)` gives the words an output holds for the agent to pass on to the person as they stand, such as the `welcome` of `list_playbooks`, which a tool answers in place of its outcome; an operation that gives none relays nothing.

A `Conflict` with no `kind` may carry the `because` `input_missing`, `answer_missing`, `workflow_document_missing` or `function_document_missing`: a run's input, an answer it was given, or the document of its workflow or of its function, which its playbook kept in its stored content, can no longer be found there, so the run could not go on. The two last name the definition's type, so a person is told which is missing, a step's cause included.

A `Conflict` of the kind `unworkable` or `effect_unknown` may carry the `because` `max_tool_calls`, a run that needed more tool calls than it may make, or `max_input_tokens`, a run that needed to read more input tokens than a run may read, so it stopped before it finished. A run that reached one of those limits and answered from what it had, or whose answer was cut off at the most output tokens a model call of its definition may write, succeeded, and its ending says which with `IncompleteDetailsSchema` (`src/outcome/incomplete-details.ts`), `{ reason }`, one of `IncompleteReasonSchema`: `max_tool_calls`, `max_input_tokens` or `max_output_tokens`, the same word a `because` uses for the same limit. The reasoning capability writes both, by its function's `exit_behavior`; the release before that one shipped the readers alone, since a release that does not know a `because` refuses the rejection that carries it. A deploy may go back to that release, and no further, without leaving a fact it cannot read.

`Conflict` may carry a `kind`: `taken`, `retired`, `paused`, a definition paused, which starts no runs until someone resumes it, `concurrent_change`, `unworkable`, `stalled`, a view the runtime keeps for a definition stopped at an event its fold could not take, which only a corrected version puts right, `history_too_short`, a series whose history is too short for a prediction function's forecaster to backtest an answer, which more periods of history put right, `feature_unlicensed`, work that names a feature of the license which this runtime's license does not include, which the license including the feature puts right, `connections_full`, a connection added to an org that holds as many as it may, which removing one puts right, `effect_unknown`, a run that called a tool not marked `reads` and could not finish, so that whether the tool changed something is not known, with the becauses of `tools_unfinished` and a problem type of its own at 409, or `tools_called`, a run that called tools and did not succeed, or that started and calls tools and may still be in progress, and so is not run again under its id. The words of `effect_unknown` and `tools_called` never say that nothing was changed: `Explanation` carries `mayHaveChanged` for them, since the tools of the run may have changed something even when the refused request ran nothing; but `tools_called` with the because `only_read`, a run that ended without success after calling only tools that read, has words of its own, which do. Those of `tools_unfinished` do, since every tool the run called is marked `reads`, and say that a new run, or a workflow's retry, may make it.

`account_closed` is the conflict of a run whose org's account is closed, with a problem type of its own at 409 as the meter's other refusals, `credits_exhausted`, `license_required` and `license_invalid`, have, and a `because` of `AccountClosedBecauseSchema`, `org_deleted`, whose runs are refused until the org is restored, which can be done only for a limited time, after which it is purged, or `org_purged`, whose runs never run again; its words say so, pointing for the date to the `resolve_at` link, or, said of a run's record, which keeps no `resolve_at`, to the rejection's detail, its `remedyOnRecord`.

A settlement rejected for any reason but a cancellation may carry a `cause`, `RejectionCauseSchema`: the step whose work ended a workflow run, `step`, its reference without its leading `/` as a run's `within` names a step, the run that step started, `run_id`, where its call was of a definition, how that work ended, `status`, `rejected`, `failed` or `unreachable` as the call answered or `timed_out` when the step's time limit or the call's deadline passed first, and with `rejected` the `reason`, `kind` and `because` of the run the step started, or, where that run is a workflow a step of its own ended, of the run that ended it, each one of the vocabulary above (`RejectionReasonSchema`, `RejectionKindSchema`, `RejectionBecauseSchema`). A rejected call's result, `CallResultSchema`, may carry the `cause` of the workflow run it answers, so the step that called that workflow names those codes. It holds codes, a step and an id, never words: the rejection's `detail` says the same in words, and the run the step started keeps its own record. The workflow engine sets it when a step's uncaught error ends the run (see [the workflow engine](../workflow-engine/README.md#state-formats), format 11), and the run's rejection carries it to `get_run`, `list_runs` and the history.

`InvalidInput` is for input that matches the input schema but that the handler finds wrong, such as a document it parses. It carries a detail and its issues, each a `detail` and a JSON Pointer `pointer` into the input. A handler that declares `invalid_input` and fails with it is rejected with reason `invalid_input` and those issues, the same rejection the dispatcher gives input that breaks the schema. Every rejection carries at most 100 issues, and each issue only its `detail` and `pointer`.

`InvalidInput`, `Unavailable` and `Conflict` may also carry a `record`, a JSON object of what was done before the rejection, such as the tokens a model call spent. No outcome or problem document shows it; `@on.auto/definitions` keeps it on a run its runtime adapter rejected.

`getLabel.registration` is what a catalog stores: the route, the kind, the success status, the reasons, the permissions that let a caller call it, whether the operation targets a playbook, whether it reaches outside the server, the JSON Schemas of the input and of the output, `input` and `output`, each with its definitions kept apart, and `refusesEmptyBody`, whether the input, its route parameters aside, refuses `{}` by its fields or by its checks, which a JSON Schema cannot say. Its `run` decodes an input, runs the handler and encodes the output; only the dispatcher calls it, because it checks nothing about the caller.

`getLabel.call(input)` runs the handler in process with typed input and output, checking both against their schemas. This is how one operation calls another. The call runs with the authority of the calling operation: it does not check the permission of the operation it calls, nor run the pipeline steps.

An operation served over HTTP alone is defined with `defineHttpOperation(scope, kind, definition)`, a definition of the same fields as a query's or a command's but for the MCP annotations, its plain language and its typed `call`, with a `body` beside its output schema. The `body` is `{ kind: 'json' }`, the JSON object every operation takes, or `{ kind: 'none' }`, nothing. The method of its route decides which it may take, and the compiler holds a definition to it: a `GET` and a `DELETE` take `none`, as they take no body; a query by `POST` takes `json`, as a query defined with `defineQuery` does; and a command by `POST` or `PUT` takes either. Its output is answered as JSON, as every operation's is, its schema held to the rules of an output schema. The registration carries the body as `servedOverHttpAlone`, which makes it an `HttpRegistration`, and its `output` as every registration does; a `Registration`, which carries no body, is served as a route and a tool, a `RouteRegistration` is either, and a transport serves an HTTP registration over HTTP alone.

`makeCatalog([getLabel, ...])` rejects a name used twice in one scope, and two operations with the same method and route once parameter names are ignored, where an org route is under `/orgs/{org}` and a playbook route under `/orgs/{org}/playbooks/{playbook}`, the path `catalogPathOf(registration)` answers, which the HTTP routes put under `/v1` and the OpenAPI document under its server URL. It lists the operations of each scope. A name may be used once at each scope, by two operations of one kind, a query beside a query or a command beside a command, so a command never takes the place of a query on a connection that serves both, in one of two ways. The org operation takes `playbook`, so that it answers for the org, or for the playbook it names, beside the playbook operation that answers for the playbook of the call, as `search` of `@on.auto/tool-servers` does; a transport that serves both scopes on one connection, as the MCP endpoint `/mcp` does, offers the org one there. Or the org operation takes no `playbook` and takes, answers and is served as the playbook operation is, the same input and output documents and both served as tools or both over HTTP alone, so that it answers for the org's own of what the playbook operation answers for a playbook, as `list_comments` and `resolve_comment` of `@on.auto/activity` do; such a transport offers one tool for the two, with the org operation's description and an optional `playbook`, and a call that names a playbook goes to the playbook operation, one that names none to the org's. Any other name at both scopes is refused.

### The playbook of an org operation

An org operation targets at most one playbook, and names it `playbook`. When its input declares a `playbook` field, the dispatcher checks that the caller may access that playbook, wherever the field arrives from: path, query or body. A second field that names a playbook is not checked and must not be used. Whether that playbook exists, and whether its id is well formed, is the handler's business at org scope, because the org's playbook records are the handler's.

`canAccessPlaybook(access, playbook)` is the access check the dispatcher applies, for a handler that lists only the playbooks its caller may access.

## The dispatcher

`makeDispatcher(steps)` returns `dispatchToOrg` and `dispatchToPlaybook`, which run one call through this pipeline. The first three steps authorize the call; the fourth confirms that its org and playbook exist.

1. The caller's org must equal the org of the call, or the call is rejected with `forbidden`.
2. The caller must hold one of the operation's `permissions`: the permission of its kind and scope, `org:read`, `org:write`, `playbook:read` or `playbook:write`, unless its definition names others, or the call is rejected with `forbidden`, whose detail names each.
3. At playbook scope, and for an org operation that targets a playbook, the caller must have access to that playbook. A caller limited to some playbooks that calls an org operation that takes `playbook` without one is refused with the detail `The caller may access only some playbooks of this org; name one of them in playbook`, so it knows to name one; any other playbook it may not access gets `The caller may not access this playbook`.
4. The org id must be well formed and, at playbook scope, the playbook id must be well formed and the playbook must exist, or the call is rejected with `not_found`. An ill-formed id is never echoed back. A retired playbook stays readable: a query runs on it as on an active playbook, while a command is rejected with `conflict`, kind `retired`, and the detail `The playbook <id> is retired and cannot change until it is restored`, the words `update_playbook` uses for a retired playbook. The status the dispatcher read reaches the handler as `PlaybookLifecycle`, `active` or `retired`, so a query that answers what a command would do, as `dry_run` of `@on.auto/tool-servers` does, can say that a retired playbook takes no command without reading the registry, which no handler sees.
5. The pipeline steps run in order.
6. The input is decoded, rejecting unknown keys and pointing at every problem, up to 100 of them. Input nested too deeply to decode is rejected the same way.
7. The handler runs.
8. The output is checked against the output schema and encoded as JSON.

A caller of one org gets the same `forbidden` rejection for an existing and a missing playbook of another org. A caller's identity can be decoded with `CallerIdentitySchema`: its `id`, its `name`, the caller in words, its `org`, its `permissions` and its `playbooks`, and, for a person signed in with an access token issued to a client, `client`, `CallingClientSchema`: its `id`, the token's `client_id`, its `name` and its `domain`, as `@on.auto/identity` reads them. A record names who did something by `RecordedCallerSchema`, the caller's `id` and `name` alone, which `recordedCallerOf(caller)` takes from a caller, so what a playbook, a definition, a connection or a run records of who made it says whom an agent reads, while the context of the fact keeps `by`, the id alone.

A playbook request may carry a `lineage`, `{ causationId, correlationId }`: the message that caused the call and the run the call belongs to, a `depth`, the reaction depth of the run it starts (see the workflow host's reactions), a `callDepth`, the number of calls above the run it starts, a `calledBy`, the call that run answers (`CallLink`: the run id of the workflow, the call's reference and its run), a `trigger`, the trigger of a workflow that started the run (`TriggerLink`: its kind, `event`, `cron` or `every`, and its reference in the document), an `actsFor`, the id of the person whose sign-ins the run uses where it acts as the playbook, a triggered run and the runs its steps start, which grants nothing, and `attemptDied: true` when the caller knows that the attempt it made of the run before died, as the workflow host knows of a call it performs again after the host that ran it stopped. Only callers in the same process set them, as the workflow host does when a workflow calls a function or a trigger starts a workflow; a transport never does, so no input reaches them. The playbook binding gives them to a playbook command as the `CallLineage` service, `{ lineage, depth, callDepth, calledBy, trigger, actsFor, attemptDied }`, `lineage`, `calledBy`, `trigger` and `actsFor` `null`, the depths 0 and `attemptDied` `false` when the request carried none, and the command passes the lineage to `PlaybookWriter.execute` with the events it appends.

A definition sets `permittedBy` when a permission other than the one of its kind and scope lets a caller call it: `list_playbooks` of `@on.auto/playbooks`, an org query that answers only the playbooks its caller may access, is permitted by `org:read` or `playbook:read`, so a key that may only read inside some playbooks can find them. The registration carries the list as `permissions`, the permission of the kind and scope when left out; a definition permitted by no permission is refused when it is defined. A transport that lists what a caller may call, as the MCP tools do, checks the same list.

`playbookCallerOf({ org, playbook })` is the caller a playbook acts as itself, for the work no person started, such as a run a reaction starts: `playbook:<playbook>`, named by the playbook's id, with `playbook:read` and `playbook:write` on that playbook and no other, an id no API key can hold, since key ids take no `:`.

A caller is a person when it is a person signed in, whose id is `signedInPersonPrefix`, `person:`, and the subject the identity service gave them, or the local developer, `localDeveloperId`, `local`, in local mode; a key, a playbook acting as itself and the runtime are none. `@on.auto/identity` names its callers by these two. `personOfTheOrg(org, id)` answers the id where it is a person still a member of the org, and nothing otherwise, which is how a triggered run's person is found (see [The person a run acts for](../definitions/README.md#the-person-a-run-acts-for)): whether a person is still a member is the host's to say, through `OrgMembership`, a reference of the call, `(org, person) => Effect<boolean>`, whose default takes every person as a member, as a runtime that keeps no list of an org's members does; a host that keeps one puts its own in the context of the call.

The outcome is `succeeded`, `rejected` or `failed`. The error boundary turns any defect into a `failed` outcome with an incident id. The `IncidentReporter` receives the id, the original defect and the call: the operation, the org, the playbook when there is one, and the caller's id, never the input. It has two seconds; when it fails or takes longer, the incident id is logged with `Effect.logError`, and the outcome stays `failed`.

A transport runs a call with `settle(call, signal)` and always gets a `Settled` value: the outcome, or `cancelled` when the signal aborts the call or the call interrupts itself. Any other failure settles as `failed` with a reported incident. A defect the call raises once the signal has aborted it, such as a finalizer whose write the ledger refuses, is reported as an incident too, though the call settles as `cancelled`; `settle` answers once the call's finalizers have run.

The dispatcher needs a `Ledger`, a `PlaybookRegistry`, which answers the status of a playbook, `active`, `retired` or `unknown`, and an `IncidentReporter`. Handlers can see none of them, neither in their types nor at run time. A handler can read any other service present in the runtime's context, so the runtime must expose only these three at its top level, and an adapter must keep its own dependencies, such as a database client, inside its layer.

`CallFetch` is the fetch of one call, for a shell that sends the requests of each call through the invocation that performs it. The shell puts it in the context it makes of a request, `callContext` of `@on.auto/api`, and the tool access and the consent client of `@on.auto/tool-servers` send that call's requests through it, not through the fetch they were made with. The server puts none, so they send through their own. Its shape is `FetchOfACall`: a fetch that takes, beside the request, the metadata of the tool call the request is sent for, `CallMeta`, keys such as `auto.on/run_id` and `auto.on/takes_answer` to strings or a boolean, as a third argument the tool access gives with the request of a call of an HTTP API alone. A plain `fetch` ignores it, so `globalThis.fetch` is a `FetchOfACall` and sends nothing more for it.

`OperationsServed` says which operations are served beside a call, a reference whose default serves every one, as HTTP does: an MCP endpoint of `@on.auto/api` puts in the context of each call of its tools the tools it lists to the caller, so an operation, or a capability it runs, names another operation only where the caller can call it there, as the check of an interaction function names `add_connection` only where it is served (`src/dispatch/operations-served.ts`).

## The ledger ports

A `Decider` holds the event-sourced rules of a stream: its initial state, how an event evolves the state, how a command decides on new events or a rejection, the context of the events a command decides, and the schema of its events. An event is a fact named for what happened, `{ type, data }`: the `type`, which the ledger records as the message's type, and the `data`, the fact's own fields and nothing else, which the ledger stores without the type. `factOf(type, schema, context, { content? })` makes the schema of one fact from its name, the schema of its data and the context it carries, and the schema a decider decodes is the union of its facts, so no fact declares its name twice. Its last argument declares the content the fact holds and releases beside its shape, `content: { holds?: readonly JsonPointer[]; releases?: 'all' | readonly JsonPointer[]; payloads?: readonly PayloadPointers[] }`, each pointer naming a field of its data that carries a SHA-256 digest, and each of `payloads` a pair, `{ sha256, bytes }`, naming the digest of a payload the fact keeps outside and its size (see [Payloads kept outside a fact](#payloads-kept-outside-a-fact)), as an annotation of the schema; a pointer may hold `*` as a whole token, which names every element of a list there and nothing in an object, and the two pointers of a pair hold it in the same places, so they are read element by element; `contentHoldersOf(schemas)` (`src/held-content/content-declaration.ts`) reads the declarations of every fact of the schemas, through unions and the readers of earlier shapes, into the `ContentHolders` the ledger keeps the holds on content by, and refuses a type two schemas declare otherwise or a declaration that does not decode, and `heldOver(holders, facts)` (`src/held-content/held-digests.ts`) folds the holds of one stream over its facts, as every ledger does (see [The holders of content](../ledger/README.md#the-holders-of-content)). A fact whose shape a release changed is made with `readingEarlierShapes(current, [earlierShapeOf(earlier, raise)])` (`src/fact-shapes/earlier-shapes.ts`): its schema decodes the current shape first and then, in turn, each earlier shape, a schema of its own that its reader, `raise`, lifts to the current shape, and encodes the current shape alone, so every reader of the fact, the ledger's codec among them, reads what an earlier release recorded (see [A reader for an earlier shape](../ledger/README.md#a-reader-for-an-earlier-shape)). A reader that throws is a decode failure of the shape it reads, reported as the schema reports any, never an exception, so a fact it cannot raise is refused as any unreadable fact is. `factReaderOf(schema)` (`src/fact-shapes/fact-readers.ts`) reads a recorded fact of a type the schema reads, through its readers, refuses one of such a type in a shape no reader knows, and passes over a fact of any other type, as a projection or a capability reads the facts of a stream it shares with others; `factTypesOf(schema)` is the types a schema reads, those its readers of earlier shapes read among them.

`context(command, state)` answers the `Context` of the events of one decision, which the ledger writes once into the metadata of every message of the append: `at`, when the fact happened, the command's time; `by`, who acted; `runId`, the run the fact belongs to; `definitionType`, `definitionName` and `definitionVersion`, the definition the run executes or the fact is about; `calledBy`, the call the run answers, `{ runId, reference, run }`, and `callDepth`, the calls above it; `depth`, the reaction depth; `trigger`, `{ kind, reference }`, the trigger that started the run; and `actsFor`, the id of the person whose sign-ins the run uses. Every field but `at` and `by` is present only where the context holds it, a depth only above 0. The names are the store's convention, camel case beside `correlationId` and `causationId`, and none is a name the store overwrites on read. `ContextSchema` refuses in every text the characters a CloudEvent refuses in an attribute, control characters, unpaired surrogates and noncharacters (`refusingForbiddenCharacters`), and in the two references, a call's and a trigger's, more than 256 bytes (`mostReferenceBytes`); the ledger checks the context of a decision with `checkedContext` before it appends anything, so a context PostgreSQL's raw `jsonb` would refuse fails on every store alike, as a defect, and nothing is appended. A start takes its definition and chain from its command, and every later fact from the state. `evolve(state, recorded)` is handed each event as it was recorded, `{ type, data, context }` (`Recorded<Event>`), on a load and for the events a decision has just appended (`recordedWith(context)`), so a state reads the context beside the data. `contextOf(metadata)` reads the context out of a message's stored metadata, leaving the store's own fields, and is the one place any reader parses metadata.

`Ledger` is the unbound port. It addresses streams by full name, loads a stream's state and version by folding its events, reads what a playbook recorded and the outcomes of its runs (below), and runs a command through a decider, answering the state its events leave, the version after them and the state it decided on (`decidedOn`), rejecting with
`conflict` on a version conflict, when another write reached the stream between reading it and appending to it. The version of a stream is the number of events in it, 0 for a stream that does not exist. A conflict's detail must not name the stream. Its implementation lives with the ledger.

`Ledger.scrubFact(stream, position, scrub)` (the port `FactScrubber`, `src/ledger/fact-scrub.ts`) rewrites the data of one fact a stream recorded, for the erasure of a person's data on request, and leaves the fact's position, type and context, who recorded it and when, as they are. `scrub` is a `FactScrub`: `eventSchema`, the schema of the stream's facts; `data`, the fact's data once scrubbed, as JSON, which must decode under that schema as the data of the fact, and which is stored as that schema encodes it again, so nothing given beside the fact's shape is kept; `erasure`, the fact of that schema the ledger appends at the head of the stream to say what was erased, with its `context` and, optionally, its `lineage`. The rewrite, the erasure and every row of a keyed projection folded again from the scrubbed fact are one transaction, retried on a conflict as a command is; it answers the stream's version after the erasure, `{ version }`, and refuses with `ScrubRefused`, whose `because` is `no_stream`, `not_its_position` or `not_its_shape`, when the stream holds nothing, the position is not one of the stream's, or the data does not decode, writing nothing. The ledger's README sets out how each store does it, under [A fact scrubbed in place](../ledger/README.md#a-fact-scrubbed-in-place).

Every message the ledger writes has an id, a cause and a correlation. Its id is `messageIdOf(stream, position)`, a version 5 UUID of the JSON array `[stream, position]` in a namespace of the ledger's own, so anyone who knows a stream and a position names the message without reading it; `uuidV5(namespace, name)` makes such ids. `execute(stream, decider, command, lineage?)` takes the `Lineage` of the events it appends, `{ causationId, correlationId }`: the id of the message that directly led to them, and the id of the run they belong to, the top-level run of a tree of runs. Both are `null` when left out. `randomUUIDv7()` makes the ids of a time, which sort in the order a process made them, as method 1 of section 6.2 of RFC 9562 sets out: the first 48 bits are the milliseconds an id was made at, the 12 bits after the version a counter, seeded at random below 2048 when the millisecond changes and counted up by one for each id made in the same millisecond, and the 62 bits after the variant random. An id made past the counter's ceiling, 4095, takes the next millisecond and seeds the counter again, so only a burst of more than 2048 ids in one millisecond carries a time ahead of the clock, and a clock that stands still or goes back makes ids of the last id's millisecond, never one below it. `uuidV7TimeOf(milliseconds)` is the 12 hex digits such an id starts with, which a database compares against the start of an id, and `uuidV7Before(id, milliseconds)` says whether an id was made before a time; the sweeps of both content stores read the age of an upload through them.

For each call the dispatcher binds the ledger to the call's address. `OrgReader` and `OrgWriter` prefix a stream name with `org/{org}/`; `PlaybookReader` and `PlaybookWriter` with `playbook/{org}/{playbook}/`. A handler names its streams relative to its org or playbook: one or more segments of letters, digits, `_` and `-`, each at most 64 characters, joined by `/`, at most 256 characters in all. Any other name fails the call. So a handler has no way to name another org's or playbook's streams. Stream names are case-sensitive, and a ledger implementation must treat them as opaque strings.

`Ledger.ageOfLastAppend(stream)` (the port `StreamAges`) answers how long ago, in milliseconds by the database's own clock, the last fact of a stream was appended, and an endless age for a stream never appended to; `PlaybookReader` reads it relative to the playbook, as it loads (`prefixedAges`). A caller that judges whether the writer of a stream may still be at work reads it, as `run_definition` judges a run that resumes, so the clocks of two servers that share a database never enter the judgement. The memory ledger of `@on.auto/operations/testing` answers it by the `Clock` it appended at.

`streamPrefixOfOrg({ org })` returns the prefix of an org's streams, so code that holds the unbound `Ledger`, such as a `PlaybookRegistry`, reads the same stream a handler names relative to its org. `streamPrefixOfPlaybook({ org, playbook })` does the same for a playbook's streams. `playbookOfStreamPrefix(prefix)` is its inverse: the playbook a prefix names, as an `Option`, and none for a prefix that names no playbook, such as an org's; `orgOfStreamPrefix(prefix)`, its sibling, is the org an org's prefix names, and none for any other. `addressOfStreamPrefix(prefix)` reads either, the address a keyed projection keeps a row under, and `streamPrefixOfAddress(address)` gives the prefix back; `addressedStreamOf(stream)` reads the stream of a projected fact through them, its scope, `playbook` or `org`, its prefix, its address, its kind and its id, so a keyed projection keeps the rows of a playbook's streams and of an org's, each under its address. Such code must accept only well-formed org and playbook ids (`OrgIdSchema`, `PlaybookIdSchema`), as the dispatcher does, so that a prefix names exactly one org or playbook.

## Reading what a playbook recorded

`Ledger.readRecorded(playbook, selection, page)` reads one page of what a playbook recorded, in the order the ledger recorded it, and answers `{ records, hasMore, nextCursor }`. Each record is `{ id, cursor, causationId, correlationId, stream, version, globalPosition, type, data, context, traceId?, spanId?, recordedAt }`: `id` is the message id, `causationId` and `correlationId` its lineage, `cursor` the record's own cursor, `version` its position within its stream, from 1, `globalPosition` the store's sequence across every playbook, with gaps, `data` the stored fact as JSON, `context` the `Context` it was written with, `traceId` and `spanId` the store's trace of the append when it wrote one, and `recordedAt` the time the store recorded it in ISO 8601. `Ledger.readRecordedEvent(playbook, id)` reads one record by its message id, within that playbook alone, and answers nothing for an id the playbook does not hold; `PlaybookReader.readRecordedEvent(id)` is the same read bound to the playbook of the call. The playbook is matched exactly: a read of `acme/sales` never answers a record of `acme/Sales`, `acme/sales2` or `acme/sales_x`.

- The selection is `{ kind: 'everything' }`, the whole partition of the playbook; `{ kind: 'run', run }`, the two streams of one run, `runs/<id>` and its run log, `run-logs/<id>`; `{ kind: 'correlated', correlation }`, every message of the playbook whose correlation is that run, in the playbook's order; or `{ kind: 'runs', notBeginningWith?, definitionType?, name?, called? }`, the first and the latest message of every run stream, ordered by the position of the first, leaving out the streams whose first message is of a type `notBeginningWith` names, which the store passes over before it counts the page, so a page of runs is full and `hasMore` true only while runs remain. `definitionType` and `name` keep the runs whose first message's context holds that `definitionType` and that `definitionName`, as a run's start records them; the store reads them from the first message as it examines each run, before it counts the page, so a page of the runs of one definition is full while it finds them and `hasMore` true only while runs remain. `called: false` keeps, the same way, the runs whose first message's context holds no `calledBy`, those no workflow's step started. A `definitionType` or `name` must hold neither U+0000 nor an unpaired surrogate, as no definition's does: PostgreSQL fails the read for one, `22P05` and `22P02`, where SQLite and the in-memory ledger find no run.
- The page is `{ cursor?, order, limit, since?, types?, dataOf? }`. `order` is `asc`, oldest first, or `desc`, newest first. `since` is the lower bound of the page in either order, by the time the store recorded. `types` keeps the records of those stored types; with `runs` it keeps the runs whose latest message is of those types, which is how a status filter is answered. `dataOf` reads the heads of the records: only the records of those stored types carry their `data`, and the others come with their id, cursor, lineage, stream, version, type and time, `data` left out, and count nothing toward the 4 MiB a page loads, so a reader that follows a playbook passes a run log's records of up to 1.5 MiB at the cost of their heads; `dataOf: []` loads no data at all.
- A page is bounded by what the store examines and loads: it answers at most `limit` records, 1 to 100, examining that many without a filter, and with a `types` filter, or a `definitionType`, `name` or `called` of `runs`, up to `mostExaminedInAPage`, 1,000 records, or 1,000 runs for `runs`, of which it answers those that match, possibly none; and it loads at most 4 MiB of stored data, though the first record a page wants is always delivered. A bound ends the page with `nextCursor`, possibly with fewer records than asked or none. `boundedPage` applies these bounds over what a store examined, so every ledger bounds a page the same way.
- `nextCursor` is null when nothing remains. A reader at the end of the playbook keeps the cursor of the last record it read and reads on from it later.
- `lastExamined` is the place of the last record the page examined, `{ cursor, recordedAt }`, or null when it examined none: the record `nextCursor` reads on after when a bound ends the page, and at the end of the playbook the last record there, even one of a type the page did not want, so a reader that keeps a checkpoint of what it has examined, as the workflow host's projector does, moves past records it filters out. `boundedPage` names it as `lastExamined`.
- A cursor is opaque to callers: the base64url encoding, without padding, of a JSON array, the playbook key first (`cursorOfParts`, `partsOfCursor`). A record's cursor reads on after the record. `cursorWithin(cursor, index)` adds one more part, a number, the index of the last event of the record a page answered; a read from such a cursor begins with that record, and the events of the record up to that index are left out by whoever presents them. A cursor that does not decode as one fails the read with `InvalidCursor` of kind `malformed`, and one that another playbook gave with kind `of_another_playbook`.

`PlaybookReader.readRecorded(selection, page)` is the same read bound to the playbook of the call, so a handler never reads another playbook. It names streams relative to the playbook, as `load` and `execute` take them, and turns `InvalidCursor` into `InvalidInput` at `/cursor`, which a handler that declares `invalid_input` passes on: `The cursor is malformed` for a malformed cursor, and `The cursor was not given by a read of this playbook` for another playbook's. A run's id must be a well-formed stream segment and a page must hold 1 to 100 records from a valid time; anything else fails the call.

The pieces of the operations that read the ledger:

- `PublicEventSchema` is an event as a caller reads it, `{ id, type, summary, data, metadata }`, its `data` at most 4 KiB as JSON in UTF-8: `id` the message id, or for a part of a record, such as a workflow's step, the message id, an underscore, `stepIdSeparator`, and the part's number, and `metadata`, `EventMetadataSchema`, the record's context under wire names, `eventMetadataOf(record, streamPrefix)`: `stream`, `position` and `global_position` from the table's columns, `correlation_id`, `causation_id`, the id of the event that directly led to it, or `null`, `at`, `by`, and where the context holds them `run_id`, `definition`, `called_by`, `call_depth`, `depth`, `trigger`, `acts_for`, `trace_id` and `span_id`. `WholeEventSchema` is the same event without the bound on its data, which `get_event` answers.
- `shownData(data, view)` applies one rule to every field that may be large, `input`, `output`, `record`, `answer`, `arguments`, `result`, `messages`, `response`, `tool_calls`, `warnings`, `issues`, `repair` and `data`: on a page, `view` `page`, a field is whole within 2 KiB as JSON, `mostShownFieldBytes`, and otherwise its size under its name and `_bytes`, the largest replaced first while the data passes 4 KiB, `mostPublicEventDataBytes`, and `result` is left out beside its `answer`; `whole` shows every field; `tool`, for an event served as a tool's result, which `ServedAsTool` says, sizes the same fields past 64 KiB, `mostToolFieldBytes`, one list for both rules. `keptContentOf(records, mostBytes, holders)` reads, for the facts of a page, the recorded content under the digests they have, and nothing for a fact without one, at most `mostBytes` an answer, as the `KeptContent` a presenter joins; it passes over every member the `payloads` of a fact's declaration in `holders` name, so a page never reads a payload, which only a `PayloadReader` reads. `holders` is required, so every operation that reads a page is given the holders its shell opened its ledger with: `list_playbook_events`, `get_event` and `get_run_history` take them from the server's composition and from a playbook's object.
- A `Presenter` turns a record of one stream kind into a list of public events, possibly empty, and declares, for each stored type of its kind, the public names it presents it under, none for a type it hides.
- `presentationOf(presenters)` presents a record by the presenter of its stream kind, the name of its relative stream up to the first `/` (`streamKindOf`), and hides a record of a kind no presenter presents, or of a stored type its presenter declares no public name for. It lists the public types of all its presenters and translates one to the stored types it stands for, which is how a filter by public type is read. Two presenters of one stream kind are refused.
- `eventsPageOf(presentation, page, paging)` turns a page of records into a page of events, `limit` of them at most: each record's events in their order oldest first and backwards newest first, those a cursor inside the record says were answered left out, and those `keeps` refuses. When the limit falls inside a record, the page ends there, with `cursorWithin` the record's cursor and the index of the last event answered. The page carries the cursor; no event does.
- `PagingInputFields` holds the optional input fields of a page, `limit` (1 to 100, `defaultPageLimit` 20 when left out), `cursor`, `order`, `since` and `type`, and `PagingOutputFields` the fields of an answer, `has_more` and `next_cursor`, which the run and interaction lists share; the two event reads take `EventPagingInputFields` and `EventPagingOutputFields` of their own, whose words say that a page of events may end between the events of one record.

## Facts appended to a scope, and the changes they make

`Ledger.readAppendedFacts(scope, { after?, most, dataOf })` reads, oldest first, the facts appended to a scope after a cursor, so a reader learns what changed in it without paging what it recorded. A scope is `{ kind: 'playbook', playbook }`, every stream of a playbook, or `{ kind: 'streams', streams }`, the streams it names in full, a name of three segments that ends in `/`, such as `org/acme/comments/`, naming every stream of that kind. `OrgReader.readAppendedFacts(kinds, request)` reads, for each kind it is given, the org's stream of that name and every stream of that kind, so the changes of the org name both a register, `org/<org>/playbooks`, and the comments of its own, `org/<org>/comments/<id>`. It answers `{ facts, cursor, through, more }`: each fact is `{ cursor, id, stream, type, context, data }`, `id` the id of its message, its data loaded only for the types of `dataOf`, so a reader that names its resources by stream and context reads no record whole; `cursor` is where the next read goes on from, the last fact read, or the cursor given when nothing came after it; `through` is the point of the ledger the read reached; and `more` says it read `most` facts, 1 to 1,000, and more follow. Without `after` it reads nothing and answers the cursor of now, the last fact of the scope, or the start of a scope that holds none. A cursor names a fact of the scope by its place in the ledger and its id, so a cursor that names no fact the ledger holds in that scope, malformed, of another scope or of another database, fails the read with `CursorNotHeld`.

`Ledger.waitForAppend(scope, after, deadline)` answers `appended` once a fact of the scope was appended after `through`, the point a read answered, and `ended` once the deadline, in the milliseconds of Effect's `Clock`, has passed or the ledger ended its waits, as a server that stops ends them; it is interruptible, so a call that goes away stops waiting. Every store answers it at once for a fact appended after the point before the wait began, so a reader that reads and then waits misses nothing. `OrgReader` binds both to the org, `readAppendedFacts(streams, request)` and `waitForAppend(streams, after, deadline)` taking stream names relative to the org, and `PlaybookReader` to the playbook of the call, `readAppendedFacts(request)` and `waitForAppend(after, deadline)`; the facts they answer name their streams relative to the scope. The in-memory ledger of `@on.auto/operations/testing` answers both over its log, and `appendedFactsBehaviour(entry)` of the same entry is the suite every ledger runs.

A change names a resource and its identity alone. `changeKindOf(kind, description, fields, readBy?)` declares a kind, such as `run` with `run_id`: its `schema`, `{ kind, ...fields }`, every field a string, `of(identity)`, which makes a change of it, and `readableBy(reader, change)`, whether a caller reads it: one of the permissions `readBy.permittedBy` names, where it names any, and access to the playbook its field `readBy.playbook` holds, where it names one, as `canAccessPlaybook` judges. `eventChanged`, `{ kind: 'event', event_id }`, names an event of the feed of a playbook by the id of its message, the id `list_playbook_events` lists it by. A `ChangeNaming` says, for the stream kind it names, which kinds of change its facts make and, for every type of fact the stream records, the function that names the resources a fact changes, a list that may hold none, one or several, or `null` for a fact that changes none; `changingOne(kind, types, name)`, `changingEvents(types)` and `changingNothing(types)` make the common ones. Every `Presenter` carries one, `changes`, so the presenters of a playbook's stream kinds, the catalogue of its facts, say what each fact changes as they say how each is shown; at a playbook the name of a change is read from a fact's id, stream and context, never its data. `changeCatalogOf(namings)` composes the namings into a `ChangeCatalog`: its kinds, each once, the stream kinds and the types whose facts name a change, `changesOf(fact)`, the changes a fact makes, by the kind of its stream, its first segment, and its type, none for a fact the catalogue does not name, and `readableBy(reader)`, whether a caller reads a change, by its kind, and of a kind it does not declare never. It refuses two namings of one stream kind, two declarations of one kind of change and namings that name no kind at all. `presentedChangeCatalogOf(presenters)` is the same over presenters, and refuses a presenter whose namings and presented types are not the same types, so a fact type is never left out of the catalogue.

## The outcomes of runs

`Ledger.readRunOutcomes(playbook, window, selection)` reads the outcomes of a playbook's runs, one row per run, that the ledger keeps as their events are appended, and answers them in groups: one for each day a run first started, its `definitionType`, its `name` and its `status`, `started`, `succeeded`, `failed` or `rejected`, with how many `runs` the group holds, the sums of their `inputTokens`, `outputTokens` and `cachedTokens`, 0 where none recorded a number, the sum of their `costMicroUsd` over the runs that recorded a cost, `null` where none did, and the `durations` of the runs that have one, in no order. The `window` is `{ from, to }`, two days as `YYYY-MM-DD`, both included; the `selection` keeps one `definitionType`, one `name`, or both. The groups come in no order. The playbook is matched exactly, as for the read of what a playbook recorded.

What a row holds is not the ledger's to know: a `RunOutcomeMapping`, `{ types, rowAfter }`, which the package that owns the run events supplies and the composition root gives the ledger, names the stored types that change a row and turns the row of a run, or none, and one of its messages, `{ id, position, type, data, context }` (`ProjectedMessage`), its data as the ledger's reads decode it and its context beside it, into the row to keep, or `undefined` to keep the row as it is. A `RunOutcome` holds `startedDay`, `startedAt`, `lastStartedAt`, `definitionType`, `name`, `status`, `durationMs`, the three token counts and `costMicroUsd`, the model cost in millionths of a US dollar, each `null` when unknown. The mapping must never throw: the ledger calls it inside the append. `runStreamOf(stream)` tells whether a stream is a run's, named `<playbook key>runs/<id>` with nothing nested under it, and answers its playbook key and run id; `addressedStreamOf(stream)` answers the prefix, the address, the kind and the id of any stream of a playbook or of an org with nothing nested under it, `playbook/<org>/<playbook>/<kind>/<id>` or `org/<org>/<kind>/<id>`.

`PlaybookReader.readRunOutcomes(window, selection)` is the same read bound to the playbook of the call.

## Keyed projections

A `KeyedProjection` is a table the ledger keeps, one row a key, inside the append of each event of the types it names on a stream of the kinds it names, as it keeps the outcomes of runs; the package that owns what a row means declares it and the composition root registers it with the ledger. It names its `name` and `version`, whose table is `projectedTableOf`, `<name>_<version>`, so a change to what it keeps is a new version and a new table; the `scopes` whose streams it folds, `playbook`, `org` or both, a playbook's streams alone when left out (`scopesOf`); the stream `kinds` it folds, `runs` for a projection of runs; the stored `types` that change a row; its `columns`, each `text`, `integer` or `boolean`, beside the `playbook_key` and `row_key` that key every row; its `indexes`, each on the playbook and its columns, which may name `row_key`, the key every ordered read ends with, or on its columns alone across playbooks with `acrossPlaybooks`, and partial with `whereSet` on a column of its own that is set; `keyOf(message, stream)`, the key of the row a message changes, the stream's id when left out and none when it answers `undefined`; `advanced`, the columns its reader advances, each `{ column, setBy }` with the types whose fold sets that column, so a fold leaves alone a column it does not mean to change; and `rowAfter(row, message)`, which turns the keyed row, or none, and the message, `{ id, position, type, data, context }`, its data as a read decodes it and the context it was written with, into the row to keep, or `undefined` to keep the row as it is. It must never throw. `checkedProjection` refuses a name, a version, no scope, a kind, a column, an index or an advanced column a table cannot hold, an advanced column declared twice and one said to be set by a type the projection does not fold, and `foldsStream`, whether a projection folds a stream of its scope and kind, `rowKeyOf` and `advancedColumnsLeftBy`, the advanced columns a fact's fold leaves as they stand, say what the ledger's fold does with a fact.

A row is a `ProjectedKeyedRow`, `{ org, playbook?, key, row }`: its address, a `ProjectedAddress`, its org and, for a row of a playbook's streams, its playbook, then its key and its columns. `Ledger.readProjectedRows(projection, address, query)` reads the rows of one playbook, `{ org, playbook }`, or one org, `{ org }`, that meet every condition of `query.where`, a `ProjectedCondition`: a column equal to a value, `{ column, equals }`, `row_key` among them for one row, or a number or text column strictly after or before a number or a text, `{ column, after }` or `{ column, before }`, which a column that is not set never meets, ordered by `orderBy` and then the row's key, `asc` or `desc`, after the values `after` names when it is given, at most `limit`; `countProjectedRows(projection, address, where)` counts them; `readDueRows(projection, { column, through, limit })` reads the rows of every playbook and every org whose integer `column` is set and at most `through`, the soonest first, and `playbookRowsOf(projection, rows)` answers them as `PlaybookProjectedRow`s, for a reader of a projection that folds a playbook's streams alone, and fails, as a defect, on a row that names no playbook, which such a projection never folds; and `nextDueOf(projection, column, after)` answers the smallest value of the column after `after`, or `null`, so a reader that holds back rows already due still learns when the next one comes; and `advanceRow(projection, address, key, { set, when })` writes the columns the projection's reader advances of one row, and no other, while the columns of `when` still hold the values given, which the fold leaves as they stand unless it sets them. A projection the ledger does not keep answers no rows and advances nothing. A condition on a column the projection does not declare, or a comparison of a boolean column or with a value of the other kind, fails the read as a defect, on every store (`comparedColumnOf`). `PlaybookReader` holds the first two, bound to the playbook of the call, `BoundProjectionReader`, and `OrgReader` the same two bound to the org of the call, so an org operation reads the rows of the org's streams, and beside them `readPlaybookRows(playbook, projection, query)` and `countPlaybookRows(playbook, projection, where)`, the same two bound to one playbook of the org, `OrgProjectionReader`, so an org operation reads the rows of each of its playbooks in turn. They bind the address and nothing more: which playbooks the caller may read is the operation's to check, against `Caller`'s `playbooks`. `lineageAttributeNames` are the extension attributes of an event that carry the lineage of a record, `causationid` and `correlationid`. A window whose days are not days of the calendar, such as `2026-02-30`, or whose `to` comes before its `from`, fails the call: the operation that reads it checks its input first. `isCalendarDay(text)` is that check, a `YYYY-MM-DD` that names the same day when read back; `PagingInputFields.since` holds its date to it as well, and its hours, minutes and offset to their ranges, so `2026-02-30T00:00:00Z` is refused rather than read as 2 March and `2026-10-05T24:00:00Z` rather than read as the next midnight.

## Recorded content

A tool call's arguments and a tool's answer are kept whole, whatever their size, beside the messages rather than in them, and so is any content a capability keeps by its digest, through the `RecordedContent` port of [`@on.auto/content`](../content/README.md), which keeps bytes under a playbook and their SHA-256. The `Ledger` carries the port as `content`, and `PlaybookReader.readContent(sha256)` and `readContentHead(sha256)`, its `PlaybookContentReader`, read it and its head bound to the playbook of the call, and `PlaybookWriter.keepContent(content)`, its `PlaybookContentWriter`, keeps it there. The port removes nothing, since two records may keep identical bytes under one digest: `Ledger.removeUnheld(playbook, sha256)` (the port `UnheldContentRemover`, `src/held-content/unheld-removal.ts`) removes a content only where no fact of its playbook holds it and `keptContentGraceMs`, one hour, has passed since it was last kept, answering `removed`, `held` or `fresh`, and a ledger opened without the facts that hold content fails it as a defect (see [The holders of content](../ledger/README.md#the-holders-of-content)); the reads of what a playbook recorded join the kept content of a fact as text when its media type is text or JSON, `text/*`, `application/json` or a `+json` type, and leave any other content's digest and size as they are.

## Payloads kept outside a fact

`@on.auto/operations/payloads` (`src/payloads/index.ts`) is the entry of what follows, a whole of its own kept apart from the main entry, whose `src/index.ts` is at the 300 lines a file may have; its files reach `effect` and `@on.auto/content` alone, never the dispatcher (`src/module-testing/package-entries.test.ts`).

`@on.auto/operations/definition-names` (`src/definition-names/name-judgement.ts`) is the judgement of the names of definitions over one append, as one change: `DefinitionNames`, the declaration a package that owns definitions gives (the stored types that change a name, the key of the definition a fact is about, the name a definition holds after a fact, `'released'` when it holds none, the conflict that refuses a name another holds, and the bounds on a playbook's definitions of a type), and the steps both keepers of `definition_names_1` take, the ledger's inside an append's transaction and the in-memory ledger's: the facts grouped by definition in the order of their keys, each folded to the name it holds at the end, the names claimed, a name refused only when another definition holds it at the end of the append, and a bound refused only when a fact it checks leaves one more counted than it allows (see [the names of definitions](../ledger/README.md#the-names-of-definitions) of the ledger). It is an entry of its own because the main entry's `src/index.ts` is at the 300 lines a file may have, and it reaches no package (`src/module-testing/package-entries.test.ts`).

A **payload** is a member of a fact's data that is a person's data the runtime only carries: a run's input, output and answer, the prompt a run's record holds, a definition's document, a value a workflow holds. A payload may leave its fact; nothing else of a fact ever does, so the context, a status, the times, who acted, a version and a run's `record`, with its tokens and cost, stay in the row, where every table the ledger keeps folds them, but for the prompt the record holds, a payload of its own. A payload is held in one of two arms, `Payload<Value>` (`src/payloads/payload-fields.ts`): `{ inline: value }`, the value in the fact as recorded before payloads could leave it, or `{ kept: { sha256, bytes } }`, the SHA-256 and the size of its text, kept in the content of the fact's playbook.

- **In the fact**, a payload `x` is `x` inline, or `x_sha256` and `x_bytes` and no `x` kept outside, members of the fact the schema declares, never a wrapper inside the value, so a value shaped like a digest and a size is held as the value it is. `payloadFields(name, schema)` makes the three optional members, `withPayloads(schema, held, mayBeAbsent?)` refuses a fact with both arms of a payload, a digest without its size or a size without its digest, and neither arm of a payload of `held`, each in its own words, and types what it decodes with one arm of each payload of `held`, a `PayloadArm`; `payloadOf(data, name)` answers the payload as one tagged value, failing for neither arm, which such a schema refuses, `payloadIfAny` the same or nothing for a payload the fact may lack, `inputPayloadOf`, `outputPayloadOf` and `answerPayloadOf` a run fact's own, from data typed with its arm, and `payloadMembers(name, payload)` the members to write. `payloadPointersOf(name, within?)` is the pair a fact declares in `payloads`: two members of one object, so a pair with `*` for each element of a list names the digest and the size of the same element (`contentHoldersOf` refuses any other pair). The digest member `payloadFields` makes carries the name of its payload, and `contentHoldersOf` refuses a fact whose schema has such a member, at any depth, in a list or a value that may be absent, and however its object was checked or built afterwards, unless the fact declares that pair in `payloads`, since nothing would hold the content it keeps.
- **Its text** is the JSON of a value as written, never canonicalised, `application/json`, or a document as it stands, `text/plain; charset=utf-8` (`jsonPayloadText`, `textPayloadText`), measured in bytes of UTF-8. `payloadChosen(value, text, keepsOutside)` keeps it inline while the switch is off and up to `mostInlinePayloadBytes`, 16,384, the payload size threshold, and a text with a lone surrogate inline, since UTF-8 cannot carry it; past them it answers the kept arm and the text to keep. A kept value costs a read wherever it is needed, while the bytes a playbook keeps differ little for a threshold anywhere from 2 KiB to 64 KiB, so it is 16,384 rather than lower, provisional until the latency of the store is measured. It is never below `mostShownFieldBytes`, the 2,048 bytes within which a page of events shows a field whole, so a payload kept outside is one a page shows as its size anyway, and no page reads one (`payload-fields.test.ts`); a value between the two stays in its fact, and a page shows it as its size, as it does while the switch is off. The switch is `PayloadOffloading`, a reference whose default is off. The server turns it on in no source: its `payloads-kept-inline.test.ts` fails on a source of the runtime that provides it, and a shell that composes the core turns it on by providing it.
- **Put, then append.** `payloadKept(content, owner, toKeep, { cache?, gate? })` puts the text under its digest, as an expected one, so a digest the playbook keeps already costs no upload, before the fact that names it is appended, and the fact's declaration holds it in the append's transaction, as any content. An operation keeps a payload in the playbook of its call through `playbookPayloadKept(toKeep)` (`src/ledger/playbook-writer.ts`), over `PlaybookWriter.keepContent`. No fact releases a payload's hold: `contentHoldersOf` refuses a fact that keeps payloads among the facts of its schema, or a fact itself, that release every hold of their stream.
- **The wait.** A put and a read of a payload wait `payloadWaitOf(bytes)`: `payloadWaitMs`, 5 s, and a second more for each `payloadBytesASecond`, 256 KiB, so 6 s for an input at its bound of 256 KiB, 9 s for 1 MiB and 37 s for 8 MiB, the most a read takes at once, within the 60 s an object store gives a request. 5 s is the wait the design proposes until the latency of the store is measured; the second for each 256 KiB keeps a large payload keepable on a link of 2 Mbit/s. A put that waits longer answers `unavailable`, "A large value could not be kept just now; try again in a moment", and logs a warning that names the digest; the fact is not appended, and the put is let go of where it stands. That is safe: a head kept without its bytes is read back as `unavailable` within its hour, never as `missing`, and the next put of the digest places the bytes again (`payload-keeping.test.ts`).
- **Reading one back.** `payloadReaderOf({ owner, content, cache?, readsAtOnce? })` reads a payload of the playbook `owner` from its `content`, the port's `get` and `getHead`, so the playbook it reads and the playbook it caches for are one: `text`, `json`, or `all` of a set, each digest once and `readsAtOnce` at a time, `payloadReadsAtOnce`, 6, unless given another number. It refuses a payload or a set past `mostPayloadBytesReadAtOnce`, 8 MiB, as a defect of its caller. It compares the size the store answers with the fact's before it reads a byte, reads no further than the piece that passes the size, digests the bytes as its pieces arrive and decodes them once, whole, so the text it answers is a string of its own and never a rope of its pieces, and lets go of the store's stream when it stops early, gives up waiting, or another read of its set fails. It fails with one of three outcomes, never a defect: `unavailable`, where the store did not answer, failed on the way or not within its wait, or found nothing twice for a digest whose head was kept within the hour, since its bytes may still be on their way, which a caller asks again; `PayloadMissing`, where the store found nothing twice and the playbook keeps no head of the digest or one last kept before the hour, `not_held`, keeps other bytes, `not_its_bytes`, or bytes that are not text or JSON of the kind asked, `not_its_kind`; and `PayloadErased`, `The payload kept under <sha256> expired and was erased`, where the store found nothing twice and the head `getHead` answers records that its bytes were erased, `erasedAt`, or an expiry that has passed, `expiresAt`, since the erasure deletes the bytes before it records the erasure, which no store answers before a writer gives a content an expiry. A read of N bytes holds the text, N bytes for text in Latin-1 and up to 2 N otherwise, and the piece in hand, at most 1 MiB from the ledger, and `all` holds at most 16 MiB of texts and six pieces. A put fails as `unavailable` the same way, and a put whose bytes the store finds other than the digest given fails as a defect of its writer. An operation reads the payloads of the playbook of its call through `playbookPayloadReader` of the main entry (`src/ledger/playbook-reader.ts`), a reader over `PlaybookReader.readContent` and `readContentHead` for the playbook `PlaybookContext` names, so it never reads another's.
- **One set a process.** A process keeps the texts it reads and puts, and the gate before its store, once: a `SharedPayloads`, `sharedPayloadsWithin(bytes)` (`src/payloads/shared-payloads.ts`), which a shell gives its runtime as `PayloadsShared`, the server one for its process of 64 MiB and hosted one for an isolate of 16 MiB, for every object it holds. Every reader and writer of the process's content takes that one: `playbookPayloadReader` and `playbookPayloadKept` from `PayloadsShared` in their context, and the workflow host from the context its shell gives it. Each takes it whatever `PayloadOffloading` says, which decides only whether a new payload leaves its fact: a payload kept while the switch was on is read through the cache and the gate after it is turned off, so turning the switch off never takes the gate away during an outage, and a process whose facts keep every payload inline reads nothing through either. A shell that gives none has `noSharedPayloads`, which keeps nothing and holds nothing back. So a payload is held once in a process, whichever reader read it or writer kept it, and one failure of the store holds back every reader and writer of the process, never one cache or gate beside another; a payload is the same text for as long as its digest names it, so nothing kept is ever out of date.
- **The cache.** `payloadCacheWithin(mostBytes)` keeps the texts put and read by their playbook and digest, measured at two bytes a UTF-16 code unit, the most an engine keeps a string in, the least recently read or kept let go of first once past its bytes, so no playbook reads through it a text only another keeps. Two reads of one digest at once both go to the store; the workflow host merges them for its runs.
- **The gate.** `payloadGateOf()` is the gate a process puts before its content store (`src/payloads/payload-gate.ts`), given to `payloadReaderOf` as `gate` and to `payloadKept` with its cache: after the store fails to answer, every read and put through the gate answers `unavailable` at once, without calling the store, until its next try, `tryAgainAfter(n, factor)`, `min(60 s, 1 s × 2^(n−1))` after the nth failure in a row times a factor between 0.5 and 1 that `Random` draws; any answer of the store, a value or a payload it does not hold, opens it. So however many runs and callers wait on a store that fails, it is called at most once a window, at most once a minute at the cap. A reader or a put given no gate calls the store every time.
- **No table reads a payload.** A projection, the outcomes of runs and the holds read the row and nothing else, so a fill or a refold never reads the content store. `payloadReadsOf(tables, holders, facts)` of `@on.auto/operations/testing` folds each table over each fact and over two twins of it for each payload it holds inline, at the top or in each element of a list: one with the payload kept outside instead, and one with another value of its kind, a text or a number changed, a flag turned over, an object that answers a member it lacks. It folds them after every fact before it in the order given and after each alone, and names each table, type and payload, `because: 'folded'`, whose rows or keys differ: a read of a payload's value, its presence or its shape, or a schema that cannot read the kept arm it declares. That is stricter than a table needs, which may read a payload's arm and size, and a table that does is named too. It also names, `because: 'unsampled'`, a payload of a folded type that no fact given holds inline, so the check is never left empty. `recordedFactsUnder(runtimeFolder)` reads the recorded fixtures of every package and capability; the server runs the check over every table it keeps (`kept-projections.test.ts`).
