# @on.auto/operations

The application layer of Auto Runtime: where operations are defined and run.

An **operation** is a **query**, which reads, or a **command**, which changes something. Its **scope** is `org` or `playbook`. Transports such as HTTP and MCP serve the operations of a catalog; this package knows nothing about them.

## Defining an operation

```ts
import { NotFound, OrgReader, defineQuery, factOf, type Decider } from '@on.auto/operations';
import { Effect, Result, Schema } from 'effect';

const LabelSchema = Schema.Struct({ name: Schema.String, text: Schema.String });

type Label = typeof LabelSchema.Type;

const LabelWrittenSchema = factOf('label_written', LabelSchema);

type LabelWritten = typeof LabelWrittenSchema.Type;

export const labels: Decider<readonly Label[], Label & { readonly by: string; readonly at: string }, LabelWritten> = {
  initialState: [],
  evolve: (written, { data }) => [...written, data],
  decide: ({ name, text }) => Result.succeed([{ type: 'label_written', data: { name, text } }]),
  context: ({ by, at }) => ({ by, at }),
  eventSchema: LabelWrittenSchema,
};

export const getLabel = defineQuery('org', {
  name: 'get_label',
  title: 'Get label',
  description: 'Reads one label of the org.',
  route: { method: 'GET', path: '/labels/{name}' },
  inputSchema: Schema.Struct({ name: Schema.String }),
  outputSchema: LabelSchema,
  reasons: ['not_found'],
  handle: Effect.fnUntraced(function* ({ name }) {
    const { state } = yield* (yield* OrgReader).load('labels', labels);
    const label = state.find((written) => written.name === name);
    if (label === undefined) {
      return yield* new NotFound({ detail: `There is no label ${name}` });
    }
    return label;
  }),
});
```

The compiler holds a definition to these rules:

- A query's route uses `GET`, or `POST` for an input a query string cannot carry, such as an object, which a transport then takes from the body; a command's uses `POST`, `PUT` or `DELETE`. A `GET` and a `DELETE` take no body, so a transport takes their input from the path and the query string, as `takesNoBody(route)` says. The method decides nothing else: a query by `POST` is a query, permitted by the read permission of its scope and marked read-only over MCP. Only a command may answer `201` instead of `200`.
- The route path is relative to the scope's prefix. Each `{parameter}` must be a string field of the input.
- The input may not have an `org` field, nor a `playbook` field at playbook scope.
- The handler may fail only with the rejections it declares in `reasons`: `NotFound`, `Conflict`, `Unavailable`, `InvalidInput`, `RunCancelled`, the rejection of a run that was cancelled, with the kind `requested`, `deadline`, `overrun` or `parent_ended`, answered with HTTP 409 and no `Retry-After`, `RunUnanswered`, the rejection of a run whose request nobody answered, with the kind `expired` or `undelivered`, answered with HTTP 410 and no `Retry-After`, or `Forbidden`, for an operation that authorizes its caller itself (below).
- The handler may ask only for the services of its scope and kind:

| Scope      | Query                                                              | Command also gets               |
| ---------- | ------------------------------------------------------------------ | ------------------------------- |
| `org`      | `Caller`, `OrgContext`, `OrgReader`                                | `OrgWriter`                     |
| `playbook` | `Caller`, `PlaybookContext`, `PlaybookLifecycle`, `PlaybookReader` | `PlaybookWriter`, `CallLineage` |

When an operation is defined, it checks again what the compiler cannot see, on the encoded form of its schemas, the form that travels:

- the name matches `^[a-z][a-z0-9_]{0,63}$` and the route path is well formed;
- the input and the output are objects that declare their fields, or unions of such objects, with no empty struct at any depth (an input with no fields is `Schema.Record(Schema.String, Schema.Never)`);
- no input field is named `org`, nor `playbook` at playbook scope;
- each route parameter is a required string field of every member of the input;
- a field the handler calls `playbook` also travels as `playbook`.

At run time, when a handler fails with a reason it did not declare, the call fails; it is not rejected.

A definition may give `linkToOpen`, a function of its output that answers `{ message, url }`: a page the person is to open, such as Studio's page that approves a connection, and a sentence of what to do there. The registration carries it as a function of the output as JSON, and an MCP tool asks a client that opens links to open it (`@on.auto/api`); the output holds the address either way.

A definition sets `reachesOutside: true` when its handler calls a system outside the server, such as a model provider, and `mayChangeOutside: true` when that call may change something there, such as a tool that writes; the registration carries both, `false` when left out, and a transport can tell its callers, as the MCP tools do with `openWorldHint` and `destructiveHint`.

A command sets `irreversible: true` when what it does cannot be undone, such as retiring a playbook or cancelling a run, and `repeatable: true` when a repeat of the same call records nothing more, such as an update that changes nothing or retiring what is already retired. The registration carries both, `false` when left out; the MCP tools take `destructiveHint` from `irreversible` or `mayChangeOutside`, and `idempotentHint` from a query or `repeatable`.

`Unavailable` and `Conflict` may carry a `kind` and with it a `because`, one of `RejectionBecauseSchema`. Both reach the rejected outcome, where `explanationOf` and `unsuccessfulWords` turn them into plain words, and the problem document, as its extension members `kind` and `because`. An operation's `plainLanguage` may give `remedies` by `because`, which `unsuccessfulWords` puts in place of the shared remedy for that operation alone.

Plain words have bounds: an outcome takes at most `mostOutcomeCharacters`, 400, and the words of a refusal at most `mostRefusalCharacters`, 600. `withinCharacters(text, most)` keeps the whole sentences that fit and ends with "The rest is in the details below.", since the detail is in the structured result beside the words; a first sentence longer than the bound is cut at a word with an ellipsis.

`Conflict` may carry a `kind`: `taken`, `retired`, `concurrent_change`, `unworkable`, `stalled`, the view a recall function keeps stopped at an event its fold could not take, which only a corrected version puts right, `no_active_version`, a function that answers from a version it builds, as a prediction function does, asked before any version is active, which a build puts right, `data_changed`, a function whose data part changed since its active version was built, which a build over the new data puts right, `build_in_flight`, a build asked while another of the function is in flight, `dataset_too_large`, a dataset past the bounds a build reads, `baseline_perfect`, a build whose dataset a baseline it must beat already predicts as well as a score can over the periods held back, which no candidate can beat until the series moves, `unscorable`, a build whose series did not move over the periods it trains on, so that `mase`, which scales each error by that movement, judges no candidate against its baselines, `not_a_build` and `build_ended`, a route of a build's trainer called on a run that is no build or a build that no longer waits for its answer, `already_active`, a version activated that is already the active one, `connections_full`, a connection added to an org that holds as many as it may, which removing one puts right, `effect_unknown`, a run that called a tool its server does not mark read-only and could not finish, so that whether the tool changed something is not known, with the becauses of `tools_unfinished` and a problem type of its own at 409, or `tools_called`, a run that called tools and did not succeed, or that started and calls tools and may still be in progress, and so is not run again under its id. The words of `effect_unknown` and `tools_called` never say that nothing was changed: `Explanation` carries `mayHaveChanged` for them, since the tools of the run may have changed something even when the refused request ran nothing; but `tools_called` with the because `only_read`, a run that ended without success after calling only tools that read, has words of its own, which do. Those of `tools_unfinished` do, since every tool the run called only reads, and say that a new run, or a workflow's retry, may make it.

`InvalidInput` is for input that matches the input schema but that the handler finds wrong, such as a document it parses. It carries a detail and its issues, each a `detail` and a JSON Pointer `pointer` into the input. A handler that declares `invalid_input` and fails with it is rejected with reason `invalid_input` and those issues, the same rejection the dispatcher gives input that breaks the schema. Every rejection carries at most 100 issues, and each issue only its `detail` and `pointer`.

`InvalidInput`, `Unavailable` and `Conflict` may also carry a `record`, a JSON object of what was done before the rejection, such as the tokens a model call spent. No outcome or problem document shows it; `@on.auto/definitions` keeps it on a run its runtime adapter rejected.

`getLabel.registration` is what a catalog stores: the route, the kind, the success status, the reasons, the permissions that let a caller call it, whether the operation targets a playbook, whether it reaches outside the server, the JSON Schemas of the input and of the output, `input` and `output`, each with its definitions kept apart, and `refusesEmptyBody`, whether the input, its route parameters aside, refuses `{}` by its fields or by its checks, which a JSON Schema cannot say. Its `run` decodes an input, runs the handler and encodes the output; only the dispatcher calls it, because it checks nothing about the caller.

`getLabel.call(input)` runs the handler in process with typed input and output, checking both against their schemas. This is how one operation calls another. The call runs with the authority of the calling operation: it does not check the permission of the operation it calls, nor run the pipeline steps.

An operation served over HTTP alone is defined with `defineHttpOperation(scope, kind, definition)`, a definition of the same fields as a query's or a command's but for the MCP annotations, its plain language and its typed `call`, with a `body` and an `answer` in place of its output schema. The `body` is `{ kind: 'json' }`, the JSON object every operation takes, `{ kind: 'none' }`, nothing, or `{ kind: 'octet-stream' | 'csv', mostBytes }`, bytes as a stream of `application/octet-stream` or `text/csv`, at most `mostBytes`, a whole number above 0, or the definition is refused. The method of its route decides which it may take, and the compiler holds a definition to it: a `GET` and a `DELETE` take `none`, as they take no body; a query by `POST` takes `json`, as a query defined with `defineQuery` does; and a command by `POST` or `PUT` takes any of them. The `answer` is `{ kind: 'json', outputSchema }`, an output encoded as JSON as every operation answers, its schema held to the rules of an output schema, or `{ kind: 'stream', mediaType }`, bytes the transport answers as a stream of that media type. The handler takes the input and, for a streamed body, the body as a `StreamedContent` second, and answers the output for a JSON answer or `{ stream, bytes }` for a stream; the compiler holds a handler to the answer its definition declares, and refuses an `answer` whose type is of either kind, since a handler could then answer either. The registration carries the body as `servedOverHttpAlone`, which makes it an `HttpRegistration`, and its `answer` in place of an `output`, a `RegisteredAnswer`: `{ kind: 'json', output }`, the JSON Schema of the output, or `{ kind: 'stream', mediaType }` and no schema; a `Registration`, which carries none, is served as a route and a tool, a `RouteRegistration` is either, and a transport serves an HTTP registration over HTTP alone (`mediaTypeOfBody`, `isStreamedBody`). A success is `Succeeded`, either `Answered`, `{ status: 'succeeded', output }`, or `Streamed`, `{ status: 'succeeded', streamed }`, a `StreamedContent` with the declared media type; `Outcome` and `Settled` take the success they may hold, `Answered` unless said, so the dispatcher answers an `Outcome` for a `Registration` and an `Outcome<Succeeded>` for any other `Runnable`, and only a route that serves an HTTP registration meets a stream. The dispatcher hands a request's `body` to the registration's `run`. An operation that takes a streamed body and is run without one fails as a defect.

`makeCatalog([getLabel, ...])` rejects a name used twice in one scope, and two operations with the same method and route once parameter names are ignored, where an org route is under `/orgs/{org}` and a playbook route under `/orgs/{org}/playbooks/{playbook}`, the path `catalogPathOf(registration)` answers, which the HTTP routes put under `/v1` and the OpenAPI document under its server URL. It lists the operations of each scope. A name may be used once at each scope only when the org operation takes `playbook`, so that it answers for the org, or for the playbook it names, beside the playbook operation that answers for the playbook of the call, as `search` of `@on.auto/tool-servers` does; a transport that serves both scopes on one connection, as the MCP endpoint `/mcp` does, offers the org one there, and a name at both scopes whose org operation takes no `playbook`, or whose two operations are not of one kind, a query beside a query or a command beside a command, is refused, so a command never takes the place of a query there.

### The playbook of an org operation

An org operation targets at most one playbook, and names it `playbook`. When its input declares a `playbook` field, the dispatcher checks that the caller may access that playbook, wherever the field arrives from: path, query or body. A second field that names a playbook is not checked and must not be used. Whether that playbook exists, and whether its id is well formed, is the handler's business at org scope, because the org's playbook records are the handler's.

`canAccessPlaybook(access, playbook)` is the access check the dispatcher applies, for a handler that lists only the playbooks its caller may access.

## The dispatcher

`makeDispatcher(steps)` returns `dispatchToOrg` and `dispatchToPlaybook`, which run one call through this pipeline. The first three steps authorize the call; the fourth confirms that its org and playbook exist.

1. The caller's org must equal the org of the call, or the call is rejected with `forbidden`.
2. The caller must hold one of the operation's `permissions`: the permission of its kind and scope, `org:read`, `org:write`, `playbook:read` or `playbook:write`, unless its definition names others, or the call is rejected with `forbidden`, whose detail names each.
3. At playbook scope, and for an org operation that targets a playbook, the caller must have access to that playbook. A caller limited to some playbooks that calls an org operation that takes `playbook` without one is refused with the detail `The caller may access only some playbooks of this org; name one of them in playbook`, so it knows to name one; any other playbook it may not access gets `The caller may not access this playbook`.
4. The org id must be well formed and, at playbook scope, the playbook id must be well formed and the playbook must exist, or the call is rejected with `not_found`. An ill-formed id is never echoed back. A retired playbook stays readable: a query runs on it as on an active playbook, while a command is rejected with `conflict`, kind `retired`, and the detail `The playbook <id> is retired and can no longer change`, the words `update_playbook` uses for a retired playbook. The status the dispatcher read reaches the handler as `PlaybookLifecycle`, `active` or `retired`, so a query that answers what a command would do, as `dry_run` of `@on.auto/tool-servers` does, can say that a retired playbook takes no command without reading the registry, which no handler sees.
5. The pipeline steps run in order.
6. The input is decoded, rejecting unknown keys and pointing at every problem, up to 100 of them. Input nested too deeply to decode is rejected the same way.
7. The handler runs.
8. The output is checked against the output schema and encoded as JSON.

A caller of one org gets the same `forbidden` rejection for an existing and a missing playbook of another org. A caller's identity can be decoded with `CallerIdentitySchema`.

A playbook request may carry a `lineage`, `{ causationId, correlationId }`: the message that caused the call and the run the call belongs to, a `depth`, the reaction depth of the run it starts (see the workflow host's reactions), a `callDepth`, the number of calls above the run it starts, a `calledBy`, the call that run answers (`CallLink`: the run id of the workflow, the call's reference and its run), a `trigger`, the trigger of a workflow that started the run (`TriggerLink`: its kind, `event`, `cron` or `every`, and its reference in the document), and `attemptDied: true` when the caller knows that the attempt it made of the run before died, as the workflow host knows of a call it performs again after the host that ran it stopped. Only callers in the same process set them, as the workflow host does when a workflow calls a function or a trigger starts a workflow; a transport never does, so no input reaches them. The playbook binding gives them to a playbook command as the `CallLineage` service, `{ lineage, depth, callDepth, calledBy, trigger, attemptDied }`, `lineage`, `calledBy` and `trigger` `null`, the depths 0 and `attemptDied` `false` when the request carried none, and the command passes the lineage to `PlaybookWriter.execute` with the events it appends.

A definition sets `permittedBy` when a permission other than the one of its kind and scope lets a caller call it: `list_playbooks` of `@on.auto/playbooks`, an org query that answers only the playbooks its caller may access, is permitted by `org:read` or `playbook:read`, so a key that may only read inside some playbooks can find them. The registration carries the list as `permissions`, the permission of the kind and scope when left out; a definition permitted by no permission is refused when it is defined. A transport that lists what a caller may call, as the MCP tools do, checks the same list.

`playbookCallerOf({ org, playbook })` is the caller a playbook acts as itself, for the work no person started, such as a run a reaction starts: `playbook:<playbook>`, with `playbook:read` and `playbook:write` on that playbook and no other, an id no API key can hold, since key ids take no `:`.

The outcome is `succeeded`, `rejected` or `failed`. The error boundary turns any defect into a `failed` outcome with an incident id. The `IncidentReporter` receives the id, the original defect and the call: the operation, the org, the playbook when there is one, and the caller's id, never the input. It has two seconds; when it fails or takes longer, the incident id is logged with `Effect.logError`, and the outcome stays `failed`.

A transport runs a call with `settle(call, signal)` and always gets a `Settled` value: the outcome, or `cancelled` when the signal aborts the call or the call interrupts itself. Any other failure settles as `failed` with a reported incident. A defect the call raises once the signal has aborted it, such as a finalizer whose write the ledger refuses, is reported as an incident too, though the call settles as `cancelled`; `settle` answers once the call's finalizers have run.

The dispatcher needs a `Ledger`, a `PlaybookRegistry`, which answers the status of a playbook, `active`, `retired` or `unknown`, and an `IncidentReporter`. Handlers can see none of them, neither in their types nor at run time. A handler can read any other service present in the runtime's context, so the runtime must expose only these three at its top level, and an adapter must keep its own dependencies, such as a database client, inside its layer.

## The ledger ports

A `Decider` holds the event-sourced rules of a stream: its initial state, how an event evolves the state, how a command decides on new events or a rejection, the context of the events a command decides, and the schema of its events. An event is a fact named for what happened, `{ type, data }`: the `type`, which the ledger records as the message's type, and the `data`, the fact's own fields and nothing else, which the ledger stores without the type. `factOf(type, schema)` makes the schema of one fact from its name and the schema of its data, and the schema a decider decodes is the union of its facts, so no fact declares its name twice.

`context(command, state)` answers the `Context` of the events of one decision, which the ledger writes once into the metadata of every message of the append: `at`, when the fact happened, the command's time; `by`, who acted; `runId`, the run the fact belongs to; `definitionType`, `definitionName` and `definitionVersion`, the definition the run executes or the fact is about; `calledBy`, the call the run answers, `{ runId, reference, run }`, and `callDepth`, the calls above it; `depth`, the reaction depth; and `trigger`, `{ kind, reference }`, the trigger that started the run. Every field but `at` and `by` is present only where the context holds it, a depth only above 0. The names are the store's convention, camel case beside `correlationId` and `causationId`, and none is a name the store overwrites on read. `ContextSchema` refuses in every text the characters a CloudEvent refuses in an attribute, control characters, unpaired surrogates and noncharacters (`refusingForbiddenCharacters`), and in the two references, a call's and a trigger's, more than 256 bytes (`mostReferenceBytes`); the ledger checks the context of a decision with `checkedContext` before it appends anything, so a context PostgreSQL's raw `jsonb` would refuse fails on every store alike, as a defect, and nothing is appended. A start takes its definition and chain from its command, and every later fact from the state. `evolve(state, recorded)` is handed each event as it was recorded, `{ type, data, context }` (`Recorded<Event>`), on a load and for the events a decision has just appended (`recordedWith(context)`), so a state reads the context beside the data. `contextOf(metadata)` reads the context out of a message's stored metadata, leaving the store's own fields, and is the one place any reader parses metadata.

`Ledger` is the unbound port. It addresses streams by full name, loads a stream's state and version by folding its events, reads what a playbook recorded and the outcomes of its runs (below), and runs a command through a decider, rejecting with `conflict` on a version conflict, when another write reached the stream between reading it and appending to it. The version of a stream is the number of events in it, 0 for a stream that does not exist. A conflict's detail must not name the stream. Its implementation lives with the ledger.

Every message the ledger writes has an id, a cause and a correlation. Its id is `messageIdOf(stream, position)`, a version 5 UUID of the JSON array `[stream, position]` in a namespace of the ledger's own, so anyone who knows a stream and a position names the message without reading it; `uuidV5(namespace, name)` makes such ids. `execute(stream, decider, command, lineage?)` takes the `Lineage` of the events it appends, `{ causationId, correlationId }`: the id of the message that directly led to them, and the id of the run they belong to, the top-level run of a tree of runs. Both are `null` when left out. `randomUUIDv7()` makes the ids of a time, which sort in the order a process made them, as method 1 of section 6.2 of RFC 9562 sets out: the first 48 bits are the milliseconds an id was made at, the 12 bits after the version a counter, seeded at random below 2048 when the millisecond changes and counted up by one for each id made in the same millisecond, and the 62 bits after the variant random. An id made past the counter's ceiling, 4095, takes the next millisecond and seeds the counter again, so only a burst of more than 2048 ids in one millisecond carries a time ahead of the clock, and a clock that stands still or goes back makes ids of the last id's millisecond, never one below it. `uuidV7TimeOf(milliseconds)` is the 12 hex digits such an id starts with, which a database compares against the start of an id, and `uuidV7Before(id, milliseconds)` says whether an id was made before a time; the sweeps of both content stores read the age of an upload through them.

For each call the dispatcher binds the ledger to the call's address. `OrgReader` and `OrgWriter` prefix a stream name with `org/{org}/`; `PlaybookReader` and `PlaybookWriter` with `playbook/{org}/{playbook}/`. A handler names its streams relative to its org or playbook: one or more segments of letters, digits, `_` and `-`, each at most 64 characters, joined by `/`, at most 256 characters in all. Any other name fails the call. So a handler has no way to name another org's or playbook's streams. Stream names are case-sensitive, and a ledger implementation must treat them as opaque strings.

`Ledger.ageOfLastAppend(stream)` (the port `StreamAges`) answers how long ago, in milliseconds by the database's own clock, the last fact of a stream was appended, and an endless age for a stream never appended to; `PlaybookReader` reads it relative to the playbook, as it loads (`prefixedAges`). A caller that judges whether the writer of a stream may still be at work reads it, as `run_definition` judges a run that resumes, so the clocks of two servers that share a database never enter the judgement. The memory ledger of `@on.auto/operations/testing` answers it by the `Clock` it appended at.

`streamPrefixOfOrg({ org })` returns the prefix of an org's streams, so code that holds the unbound `Ledger`, such as a `PlaybookRegistry`, reads the same stream a handler names relative to its org. `streamPrefixOfPlaybook({ org, playbook })` does the same for a playbook's streams. `playbookOfStreamPrefix(prefix)` is its inverse: the playbook a prefix names, as an `Option`, and none for a prefix that names no playbook, such as an org's; `playbookStreamOf` reads the stream of a projected fact through it, so a keyed projection keeps rows of a playbook's streams alone, each with its playbook. Such code must accept only well-formed org and playbook ids (`OrgIdSchema`, `PlaybookIdSchema`), as the dispatcher does, so that a prefix names exactly one org or playbook.

## Reading what a playbook recorded

`Ledger.readRecorded(playbook, selection, page)` reads one page of what a playbook recorded, in the order the ledger recorded it, and answers `{ records, hasMore, nextCursor }`. Each record is `{ id, cursor, causationId, correlationId, stream, version, globalPosition, type, data, context, traceId?, spanId?, recordedAt }`: `id` is the message id, `causationId` and `correlationId` its lineage, `cursor` the record's own cursor, `version` its position within its stream, from 1, `globalPosition` the store's sequence across every playbook, with gaps, `data` the stored fact as JSON, `context` the `Context` it was written with, `traceId` and `spanId` the store's trace of the append when it wrote one, and `recordedAt` the time the store recorded it in ISO 8601. `Ledger.readRecordedEvent(playbook, id)` reads one record by its message id, within that playbook alone, and answers nothing for an id the playbook does not hold; `PlaybookReader.readRecordedEvent(id)` is the same read bound to the playbook of the call. The playbook is matched exactly: a read of `acme/sales` never answers a record of `acme/Sales`, `acme/sales2` or `acme/sales_x`.

- The selection is `{ kind: 'everything' }`, the whole partition of the playbook; `{ kind: 'run', run }`, the two streams of one run, `runs/<id>` and its run log, `run-logs/<id>`; `{ kind: 'correlated', correlation }`, every message of the playbook whose correlation is that run, in the playbook's order; or `{ kind: 'runs', notBeginningWith?, definitionType?, name? }`, the first and the latest message of every run stream, ordered by the position of the first, leaving out the streams whose first message is of a type `notBeginningWith` names, which the store passes over before it counts the page, so a page of runs is full and `hasMore` true only while runs remain. `definitionType` and `name` keep the runs whose first message's context holds that `definitionType` and that `definitionName`, as a run's start records them; the store reads them from the first message as it examines each run, before it counts the page, so a page of the runs of one definition is full while it finds them and `hasMore` true only while runs remain. A `definitionType` or `name` must hold neither U+0000 nor an unpaired surrogate, as no definition's does: PostgreSQL fails the read for one, `22P05` and `22P02`, where SQLite and the in-memory ledger find no run.
- The page is `{ cursor?, order, limit, since?, types?, dataOf? }`. `order` is `asc`, oldest first, or `desc`, newest first. `since` is the lower bound of the page in either order, by the time the store recorded. `types` keeps the records of those stored types; with `runs` it keeps the runs whose latest message is of those types, which is how a status filter is answered. `dataOf` reads the heads of the records: only the records of those stored types carry their `data`, and the others come with their id, cursor, lineage, stream, version, type and time, `data` left out, and count nothing toward the 4 MiB a page loads, so a reader that follows a playbook passes a run log's records of up to 1.5 MiB at the cost of their heads; `dataOf: []` loads no data at all.
- A page is bounded by what the store examines and loads: it answers at most `limit` records, 1 to 100, examining that many without a filter, and with a `types` filter, or a `definitionType` or `name` of `runs`, up to `mostExaminedInAPage`, 1,000 records, or 1,000 runs for `runs`, of which it answers those that match, possibly none; and it loads at most 4 MiB of stored data, though the first record a page wants is always delivered. A bound ends the page with `nextCursor`, possibly with fewer records than asked or none. `boundedPage` applies these bounds over what a store examined, so every ledger bounds a page the same way.
- `nextCursor` is null when nothing remains. A reader at the end of the playbook keeps the cursor of the last record it read and reads on from it later.
- `lastExamined` is the place of the last record the page examined, `{ cursor, recordedAt }`, or null when it examined none: the record `nextCursor` reads on after when a bound ends the page, and at the end of the playbook the last record there, even one of a type the page did not want, so a reader that keeps a checkpoint of what it has examined, as the workflow host's projector does, moves past records it filters out. `boundedPage` names it as `lastExamined`.
- A cursor is opaque to callers: the base64url encoding, without padding, of a JSON array, the playbook key first (`cursorOfParts`, `partsOfCursor`). A record's cursor reads on after the record. `cursorWithin(cursor, index)` adds one more part, a number, the index of the last event of the record a page answered; a read from such a cursor begins with that record, and the events of the record up to that index are left out by whoever presents them. A cursor that does not decode as one fails the read with `InvalidCursor` of kind `malformed`, and one that another playbook gave with kind `of_another_playbook`.

`PlaybookReader.readRecorded(selection, page)` is the same read bound to the playbook of the call, so a handler never reads another playbook. It names streams relative to the playbook, as `load` and `execute` take them, and turns `InvalidCursor` into `InvalidInput` at `/cursor`, which a handler that declares `invalid_input` passes on: `The cursor is malformed` for a malformed cursor, and `The cursor was not given by a read of this playbook` for another playbook's. A run's id must be a well-formed stream segment and a page must hold 1 to 100 records from a valid time; anything else fails the call.

The pieces of the operations that read the ledger:

- `PublicEventSchema` is an event as a caller reads it, `{ id, type, summary, data, metadata }`, its `data` at most 4 KiB as JSON in UTF-8: `id` the message id, or for a part of a record, such as a workflow's step, the message id, an underscore, `stepIdSeparator`, and the part's number, and `metadata`, `EventMetadataSchema`, the record's context under wire names, `eventMetadataOf(record, streamPrefix)`: `stream`, `position` and `global_position` from the table's columns, `correlation_id`, `causation_id`, the id of the event that directly led to it, or `null`, `at`, `by`, and where the context holds them `run_id`, `definition`, `called_by`, `call_depth`, `depth`, `trigger`, `trace_id` and `span_id`. `WholeEventSchema` is the same event without the bound on its data, which `get_event` answers.
- `shownData(data, view)` applies one rule to every field that may be large, `input`, `output`, `record`, `answer`, `arguments`, `result`, `messages`, `response`, `tool_calls` and `data`: on a page, `view` `page`, a field is whole within 2 KiB as JSON, `mostShownFieldBytes`, and otherwise its size under its name and `_bytes`, the largest replaced first while the data passes 4 KiB, `mostPublicEventDataBytes`, and `result` is left out beside its `answer`; `whole` shows every field; `tool`, for an event served as a tool's result, which `ServedAsTool` says, sizes the same fields past 64 KiB, `mostToolFieldBytes`, one list for both rules. `keptContentOf(records, mostBytes)` reads, for the facts of a page, the recorded content under the digests they have, and nothing for a fact without one, at most `mostBytes` an answer, as the `KeptContent` a presenter joins.
- A `Presenter` turns a record of one stream kind into a list of public events, possibly empty, and declares, for each stored type of its kind, the public names it presents it under, none for a type it hides.
- `presentationOf(presenters)` presents a record by the presenter of its stream kind, the name of its relative stream up to the first `/` (`streamKindOf`), and hides a record of a kind no presenter presents, or of a stored type its presenter declares no public name for. It lists the public types of all its presenters and translates one to the stored types it stands for, which is how a filter by public type is read. Two presenters of one stream kind are refused.
- `eventsPageOf(presentation, page, paging)` turns a page of records into a page of events, `limit` of them at most: each record's events in their order oldest first and backwards newest first, those a cursor inside the record says were answered left out, and those `keeps` refuses. When the limit falls inside a record, the page ends there, with `cursorWithin` the record's cursor and the index of the last event answered. The page carries the cursor; no event does.
- `PagingInputFields` holds the optional input fields of a page, `limit` (1 to 100, `defaultPageLimit` 20 when left out), `cursor`, `order`, `since` and `type`, and `PagingOutputFields` the fields of an answer, `has_more` and `next_cursor`, which the run and interaction lists share; the two event reads take `EventPagingInputFields` and `EventPagingOutputFields` of their own, whose words say that a page of events may end between the events of one record.

## The outcomes of runs

`Ledger.readRunOutcomes(playbook, window, selection)` reads the outcomes of a playbook's runs, one row per run, that the ledger keeps as their events are appended, and answers them in groups: one for each day a run first started, its `definitionType`, its `name` and its `status`, `started`, `succeeded`, `failed` or `rejected`, with how many `runs` the group holds, the sums of their `inputTokens`, `outputTokens` and `cachedTokens`, 0 where none recorded a number, and the `durations` of the runs that have one, in no order. The `window` is `{ from, to }`, two days as `YYYY-MM-DD`, both included; the `selection` keeps one `definitionType`, one `name`, or both. The groups come in no order. The playbook is matched exactly, as for the read of what a playbook recorded.

What a row holds is not the ledger's to know: a `RunOutcomeMapping`, `{ types, rowAfter }`, which the package that owns the run events supplies and the composition root gives the ledger, names the stored types that change a row and turns the row of a run, or none, and one of its messages, `{ id, position, type, data, context }` (`ProjectedMessage`), its data as the ledger's reads decode it and its context beside it, into the row to keep, or `undefined` to keep the row as it is. A `RunOutcome` holds `startedDay`, `startedAt`, `lastStartedAt`, `definitionType`, `name`, `status`, `durationMs` and the three token counts, each `null` when unknown. The mapping must never throw: the ledger calls it inside the append. `runStreamOf(stream)` tells whether a stream is a run's, named `<playbook key>runs/<id>` with nothing nested under it, and answers its playbook key and run id; `playbookStreamOf(stream)` answers the playbook key, the kind and the id of any stream of a playbook with nothing nested under it.

`PlaybookReader.readRunOutcomes(window, selection)` is the same read bound to the playbook of the call.

## Keyed projections

A `KeyedProjection` is a table the ledger keeps, one row a key, inside the append of each event of the types it names on a stream of the kinds it names, as it keeps the outcomes of runs; the package that owns what a row means declares it and the composition root registers it with the ledger. It names its `name` and `version`, whose table is `projectedTableOf`, `<name>_<version>`, so a change to what it keeps is a new version and a new table; the stream `kinds` it folds, `runs` for a projection of runs; the stored `types` that change a row; its `columns`, each `text`, `integer` or `boolean`, beside the `playbook_key` and `row_key` that key every row; its `indexes`, each on the playbook and its columns, which may name `row_key`, the key every ordered read ends with, or on its columns alone across playbooks with `acrossPlaybooks`, and partial with `whereSet` on a column of its own that is set; `keyOf(message, stream)`, the key of the row a message changes, the stream's id when left out and none when it answers `undefined`; `advanced`, the columns its reader advances, each `{ column, setBy }` with the types whose fold sets that column, so a fold leaves alone a column it does not mean to change; and `rowAfter(row, message)`, which turns the keyed row, or none, and the message, `{ id, position, type, data, context }`, its data as a read decodes it and the context it was written with, into the row to keep, or `undefined` to keep the row as it is. It must never throw. `checkedProjection` refuses a name, a version, a kind, a column, an index or an advanced column a table cannot hold, an advanced column declared twice and one said to be set by a type the projection does not fold, and `rowKeyOf` and `advancedColumnsLeftBy`, the advanced columns a fact's fold leaves as they stand, say what the ledger's fold does with a fact.

`Ledger.readProjectedRows(projection, playbook, query)` reads the rows of one playbook whose columns equal the values of `query.where`, `row_key` among them for one row, ordered by `orderBy` and then the row's key, `asc` or `desc`, after the values `after` names when it is given, at most `limit`; `countProjectedRows(projection, playbook, where)` counts them; `readDueRows(projection, { column, through, limit })` reads the rows of every playbook whose integer `column` is set and at most `through`, the soonest first; and `nextDueOf(projection, column, after)` answers the smallest value of the column after `after`, or `null`, so a reader that holds back rows already due still learns when the next one comes; and `advanceRow(projection, playbook, key, { set, when })` writes the columns the projection's reader advances of one row, and no other, while the columns of `when` still hold the values given, which the fold leaves as they stand unless it sets them. A projection the ledger does not keep answers no rows and advances nothing. `PlaybookReader` holds the first two, bound to the playbook of the call. `lineageAttributeNames` are the extension attributes of an event that carry the lineage of a record, `causationid` and `correlationid`. A window whose days are not days of the calendar, such as `2026-02-30`, or whose `to` comes before its `from`, fails the call: the operation that reads it checks its input first. `isCalendarDay(text)` is that check, a `YYYY-MM-DD` that names the same day when read back; `PagingInputFields.since` holds its date to it as well, and its hours, minutes and offset to their ranges, so `2026-02-30T00:00:00Z` is refused rather than read as 2 March and `2026-10-05T24:00:00Z` rather than read as the next midnight.

## Recorded content

A tool call's arguments and a tool's answer are kept whole, whatever their size, beside the messages rather than in them, since every decision on a stream and every projection rebuild reads its facts back, and so is any content a capability keeps by its digest. `RecordedContent`, the port the ledger implements, takes bytes as a stream and computes their digest itself:

- `put(playbook, { stream, mediaType, expected? })` reads a web `ReadableStream<Uint8Array>` in chunks of `mostContentChunkBytes`, 1 MiB, digests it with SHA-256 as it passes and measures it, keeps it under the playbook and its digest, and answers `ContentKept`, `{ sha256, bytes, mediaType }`. `expected`, `{ sha256?, bytes? }`, is what the caller asserts of the bytes: a stream whose digest or size is not the one expected is refused with `ContentRefused` of `because: 'not_its_digest'` or `'not_its_size'`, carrying as `found` the digest and size the port read, so a route words the mismatch without digesting the bytes again, and a stream that fails before its end with `because: 'stream_failed'`, carrying the stream's own error as `cause`; each carries a `detail` sentence, so a route answers every refusal as one `invalid_input`. Nothing of a refused put is kept: no read finds it, and the ledger deletes the chunks it wrote, as its README says.
- A put of a digest the playbook already holds keeps the content it holds, with the media type it was first kept with, and answers that one, so an identical answer is kept once however often it comes and a second media type never replaces the first, with one exception: on an object store that ignores `If-None-Match` on a copy, two puts of one digest made at the same moment with two media types leave the later one's media type over identical bytes, after the earlier put answered a media type the store no longer holds, as the [object storage README](../object-storage/README.md#a-put) says.
- `get(playbook, sha256)` answers a `StreamedContent`, `{ stream, bytes, mediaType }`, or nothing for a digest the playbook does not hold; a read whose bytes are not its digest's fails as a defect before it hands over the last of them (`notTheBytesOfItsDigest`). `verifiedStream(sha256, bytes, source)` is that check for every adapter: it reads the stream an adapter has, digests and counts each piece, hands over the piece that reaches the size the adapter knows only once the size and the digest are checked, and fails on a stream that ends short of the size, goes past it, or gives a piece that is not bytes.
- A `ContentStore`, `{ content, sweepContent }`, is an adapter of the port with the sweep of what its puts left behind, `sweepContent(before)`, which deletes the pieces of puts that began before that time and never finished; the ledger runs the sweep of its own store or of the store it is given.
- A second namespace of the same port keeps content for the life of a run: `stage(playbook, run, content)` keeps and answers as `put` does, by the run's id, `staged(playbook, run, sha256)` reads it, and `unstage(playbook, run)` removes all of it and ends the run's staging, so a stage under a run once unstaged is refused with `StagingEnded`, leaving its stream unread, and a stage that races an unstage keeps nothing.

The digest is Node's, behind the one module of the repository for it: the digest of what is in hand, `sha256Of(text or bytes)`, is the one-shot form, `hash('sha256', content, 'hex')`, and the digest of a stream, `sha256Digest()`, is the incremental one, `createHash('sha256')`, which takes the stream in parts; a text is digested and kept as its UTF-8, so its digest is the SHA-256 of the text. `takenInChunks(stream, chunkBytes, take)` reads a stream through the digest in chunks, answering its digest, size and number of chunks or a `stream_failed` refusal, and `requireExpected(expected, taken)` refuses a digest or a size that is not the one expected; the ledger, the object store of `@on.auto/object-storage` and the in-memory content keep through both, and the ledger and the object store read back through `verifiedStream`. `textToKeep(text, mediaType)` makes the content of a text to put, `contentOfText` and `contentOfBytes` a `StreamedContent` of a text or of bytes in hand, and `textOfContent(content)` reads one back as text, failing as a defect on bytes that are not UTF-8. The `Ledger` carries the port as `content`, and `PlaybookReader.readContent(sha256)` reads it bound to the playbook of the call; the reads of what a playbook recorded join the kept content of a fact as text when its media type is text or JSON, `text/*`, `application/json` or a `+json` type, and leave any other content's digest and size as they are.

## The names of the loopback

`loopbackNames` (`src/addresses/loopback-names.ts`) are the names by which a URL or a `Host` header names this computer, `localhost`, `127.0.0.1` and `[::1]`, as a URL writes its host, and `namesTheLoopback(hostname)` says whether a host is one of them. It is the one rule of an http URL on a loopback address, which an issuer, a server or a document of a tool server may be (`isPinnableUrl` of `@on.auto/tool-servers`) and `PUBLIC_URL` may be, and of the `Host` header local mode takes (`@on.auto/api`), there with a port and in any case. The rule of the address the local-mode listener takes is the [identity README](../identity/README.md)'s.

## The folder of a cache

`cacheFolderProblem(directory, owner?)` (`src/folders/cache-folder.ts`) is the one rule of a folder the server keeps files of its own in, which it later trusts: it makes the folder when it is not there, with `cacheFolderMode`, `0700`, and answers what is wrong with it, that it could not be made, is not a folder, belongs to another user than the server's, or may be written by other users, or nothing. The model cache of prediction functions and the Studio the server serves read it, so no other user can make or change the files either serves from.

## The files a package ships

`ShippedFiles` (`src/shipped-files/shipped-files.ts`) is the port through which a package reads the files it ships beside its code: `text(file)`, `bytes(file)` and `list(folder)`, the names of the files directly in a folder, sorted, each a `ShippedFile`, the name of the package the file is shipped in and its path within it, as `{ package: '@on.auto/providers', path: 'src/entries/slack.yaml' }`; `shippedFileIn(folder, name)` is a file of a folder, and `shippedFileName(file)` the name a file goes by in an error and among the files a pool hands its workers, `@on.auto/providers/src/entries/slack.yaml`. No module computes where a file is when it loads, so a host that bundles the modules names the files as the server does, and loads them where `import.meta.url` names no file. A package that ships files declares its root once, a function that answers a `ShippedRoots` of its name, `new URL('../../', import.meta.url)` of the module that names the files, only when it is called, and exports it from the entry that reads them: `providersShippedRoots()`, `apiShippedRoots()` and `checkShippedRoots()` of `@on.auto/definitions/check`. A file a dependency ships, the engine's WebAssembly or the compiler's lib, is named under the package that depends on it, in the folder of the dependency, `node_modules/<dependency>/<its path>`, by `dependencyFileOf(dependent, dependency, path)`, since pnpm's layout lets the dependent alone find it; the reader finds the dependency as Node finds it from the root of that package, in its own `node_modules` and then in that of each folder above it, where the npm package's install puts it, so no module resolves a package when it loads (`sandboxModuleFile` and `sandboxShippedRoots()` of `@on.auto/workflow-engine/dsl`, and the lib `sandboxLibOf` of `@on.auto/definitions` reads). A package names its files and never says how they are read: it takes the reader as a dependency of the function or factory that reads, never from an import of the reader, and the reader never knows what a file is for, so how they are read is one decision, taken once by the server that composes the packages. What a package read it hands on as content, never as a path for another package to read again: `@on.auto/providers` hands the tool servers the texts of the documents beside its entries, and a pool of `@on.auto/workflow-engine` is handed the bytes its workers start with. `shippedFilesOnDisk(roots)` (`src/shipped-files/shipped-files-on-disk.ts`) is the one reader: it reads a file under the root `roots` gives its package, resolves no package but a dependency whose file it is asked for, with `findPackageJSON` of `node:module` from that root, which finds the dependency's own folder whatever its `exports` map says, one that hides its `package.json` and gives no entry to `require` among them, and refuses the file of a package it is given no root for; the server gives it the roots of every package whose files it reads (`packages/server/src/server-options/shipped-roots.ts`). It is the one module of the port that imports `node:fs`; it is an entry of its own, `@on.auto/operations/shipped-files-on-disk`, as the drivers of `@on.auto/ledger` are, so that the main entry, which every package imports, and the testing entry reach no file system for it (`src/shipped-files/shipped-files-entries.test.ts`).

## Testing

`@on.auto/operations/testing` exports an in-memory `Ledger`, `PlaybookRegistry` and `IncidentReporter` for the tests of packages that define or serve operations. The in-memory ledger names and links its messages as the ledger does. `memoryPlaybookRegistry(active, retired)` takes the active playbooks and, optionally, the retired ones; any other playbook is unknown. `memoryLedger(runOutcomes)` keeps the outcomes of runs with the mapping it is given, and none without one; an append whose mapping throws keeps nothing. `runTallies` is a small `RunOutcomeMapping` over `runFacts`, a decider that appends the `run_began` and `run_ended` facts it is given, for the tests of a ledger. `memoryLedger(runOutcomes, projections)` keeps the projections it is given too, and `runTallyRows`, `tallyRowsOf(version)` and `readTallyRows` are a small projection over the same facts and a query of it, and `topicRows` over `topicFacts` a projection keyed by its mapping over two stream kinds with columns its reader advances, for the tests of a ledger's projections. The in-memory ledger reads what a playbook recorded as the ledger does, with the context of each message, and the behaviour suite of `@on.auto/ledger` runs on it; it keeps recorded content whole in memory, `memoryRecordedContent()`, by the rules of the port the ledger keeps, its refusals, its first media type and its end of staging among them, which the tests of other packages take alone too, and `keptTextOf(content, playbook, sha256)` reads a kept text back as text. `internalTermsIn(text, measuredIn?)` (`src/plain-language/internal-terms.ts`), beside the plain words it guards, finds the terms a person's words must not hold, which the tests of every package that words a result run: the internal words, a name in capitals with underscores, an id, a path, and a number from 100 to 599 that reads as a status code, unless a unit follows it, one of the units the runtime measures in or one the text names in `measuredIn`, such as the unit of a prediction function, alone or after a range written `N to M`, as in `100 to 160 orders`; a number before `and` is not in a range, so the `404` of `404 and 3 rows` is still found.

`shippedFilesInMemory(files)` (`src/shipped-files/shipped-files-in-memory.ts`) is a `ShippedFiles` over a record of contents by package and by path within it, each a text or bytes, for the unit tests of a package that reads what it ships: a folder lists the files directly under it, and a file it does not hold is refused, as is a folder that holds none, since it holds no empty folder; the same tests run on it and on the reader on disk (`src/shipped-files/shipped-files.test.ts`).

`recordedContentBehaviour(entry)` is the behaviour suite of the content port, in `src/content-testing`: a content of no bytes to 64 MiB kept and streamed back, a text kept once with its first media type in its playbook alone, a content put again whole or with its digest, the refusals of a wrong digest, a wrong size and a stream that fails, wrong bytes put with the digest of a content held, a wrong put racing a right one, and staging, read through a second client, ended, refused and raced. An adapter runs it with a `ContentEntry` whose `aStore()` answers `{ content, elsewhere, unnamedLeft }`: the port, the port of a second client of the same store, and how many pieces of puts no kept content names the store holds, which is 0 after every test. This package runs it on `memoryRecordedContent`, the ledger on SQLite and PostgreSQL, and `@on.auto/object-storage` on its fake bucket and on a real S3-compatible server. The samples it is made of are exported with it: `generated(bytes, seed)` and `generatedStream`, bytes made the same for a seed, `answerOfAbout(bytes)`, a JSON answer of about that size, `readBack` and `readThrough`, which digest what a read streams, `deliveredBeforeFailing(stream)`, how many bytes a failing stream handed over, `brokenAfter(bytes)` and `unread()`, streams that fail or are never read, and `resultOf`, `refusalOf` and `present`, which run an effect for its value, its failure or its value present.

`spawnForTheTest(command, args, options)` (`src/process-testing/test-processes.ts`) is how a test of the repository starts a process it runs itself. It starts it as `spawn` of `node:child_process` does and registers its end with `onTestFinished` of Vitest, the hook that runs once the test finished, whether it passed, failed or timed out: a process still there is sent SIGTERM, on which the server stops, and SIGKILL if it is still there `stoppedWithinMs`, 10 s, later, a bound the server's test of its longest stop holds that stop under, and well within the 60 s a hook may take. `endWithTheTest(pid)` ends in the same way, by its pid, a process the test did not start itself, such as a server started in the background, and signals no pid that `kill(pid, 0)` finds gone or another user's; it cannot tell a pid the system gave to another process of the same user since. `endWithTheTest(reader)` takes a `PidReader` in place of the pid, registered before the process is started: once the test finished, it reads the pid with `read()` again and again while `stillToCome()` holds, for at most `readWithinMs`, and ends the pid it read, if any. A worker of the test runner that dies runs no hook, so it ends nothing.

`measuredEnvironment` (`src/process-testing/measured-environment.ts`) is the environment a test gives a worker or a process in place of its own: `NODE_V8_COVERAGE` alone, when the run measures coverage, so the coverage of what it starts is measured and no other variable of the test reaches it.

`modulesReachedFrom(folder, entry)` (`src/module-testing/modules-reached.ts`) answers the files an entry of a package reaches through the imports that load when it runs, a type import left out, each relative to the folder of its sources, and the packages those files import, by which the tests of the entries of this package, of `@on.auto/ledger` and of `@on.auto/workflow-engine` keep what an entry must not reach behind another.

`importedWithoutAnAddress(module)` (`src/module-testing/unaddressed-modules.ts`) imports a module, with every module it imports outside `node_modules`, under a URL of its own scheme, `unaddressed:`, that names no file and is the base of no URL, so `new URL(path, import.meta.url)`, `fileURLToPath(import.meta.url)` and `import.meta.filename` fail or are undefined as they are where `import.meta.url` is no URL of a file, and answers the module's namespace; a module that makes a URL of `import.meta.url`, or reads `fileURLToPath(import.meta.url)` or `import.meta.dirname`, as it loads fails to load, one import deep or more as well. `import.meta.resolve` it cannot catch, since its hooks resolve every specifier, so a module that calls it as it loads loads; `scripts/module-addresses.test.ts` refuses it, and `import.meta.url`, outside a function in every module an entry of a shipped package but the server reaches, read with the parser of `typescript6`, an immediately called function counted as loading. It resolves and loads them through hooks of `registerHooks` of `node:module`, which it registers for the import and lets go of after it, and takes the packages of `node_modules` and the modules of other schemes as they are. The tests of the modules that read an address only when a file is read, a worker started or a job made import them so, and the npm package's check imports every subpath but the testing ones so (see the [server README](../server/README.md)).

`aFolderOfTheTestRun(runningIn)` (`src/process-testing/test-run-folder.ts`) is the global setup of the tests of every package, which `vitest.shared.ts` names with its default, `aFolderOfTheTestRun()`. Each run makes a folder of its own in the temporary folder, `auto-runtime-test-run-<project>-<random>`, and sets `TMPDIR` to it before any worker starts, so `tmpdir()` of `node:os` answers it in every worker and in every process a test starts with the environment it inherits, and two runs at once have two folders. Its teardown, which a worker that dies, a hook that times out or a child that is killed does not keep from running, lists what the tests left there, ends each `RunningProcess` that `runningIn(entry)` finds still running in an entry, with SIGTERM and with SIGKILL if `isStillRunning()` still holds `stoppedWithinMs` later, sending a signal only while it holds, fails the run naming each entry and each process it ended, and removes the folder whatever happened. A package whose own processes may outlive their test gives it a `runningIn` of its own, as the server does for the runtimes its tests start in the background, through `@on.auto/operations/test-run-folder`. That is an entry of its own because a global setup runs in Vitest's own process and not in a worker, so neither it nor anything it imports takes Vitest, with whose hooks `@on.auto/operations/testing` registers what it ends; `endedWhileItRuns(running)` of `@on.auto/operations/testing` is the same end for the hook of a test, over the same `RunningProcess`.
