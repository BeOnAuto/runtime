# Connect an agent over MCP

These instructions cover this development checkout.

The server is also an [MCP](https://modelcontextprotocol.io) server, so an agent can call the same operations as tools. Connect it to `/mcp`, with an [API key](../../self-host/security.md#api-keys):

```json
{
  "mcpServers": {
    "auto-runtime": {
      "type": "http",
      "url": "http://localhost:5555/mcp",
      "headers": { "Authorization": "Bearer <key>" }
    }
  }
}
```

Most MCP clients take an entry of this shape. In Claude Code, `claude mcp add --transport http auto-runtime http://localhost:5555/mcp --header "Authorization: Bearer <key>"` adds the same. In [local mode](../../self-host/security.md#local-mode), leave out the header. Where `PUBLIC_URL` turns sign-in on, a client that runs the MCP authorization flow connects without the header and signs the person in through the Auto identity service, as the [security guide](../../self-host/security.md#what-signed-in-people-can-do) describes.

`/mcp` serves every tool on one connection, so an agent can create a playbook and work in it at once. The org is the key's own, since a key belongs to one org, or, for a signed-in person, the org their token names, and never an argument; in local mode, where no key names one, it is `local`, so the playbooks an agent creates there are the ones `GET /v1/orgs/local/playbooks` lists. The org id `local` is reserved for local mode: the key command refuses it, and an `API_KEYS` entry with it stops the server at start-up, so no key can reach the playbooks made in local mode. The playbook tools (`create_playbook`, `list_playbooks`, `update_playbook` and `retire_playbook`), `list_models`, the connection tools (`add_connection`, `list_connections`, `reconnect_connection` and `remove_connection`) and `activate_license` are as on HTTP; the five routes of Studio's page that connects a connection are HTTP alone, and so are `list_providers`, which a page reads, `get_playbook`, `get_connection`, `get_run_history`, `get_playbook_analytics`, `validate`, `activate_allocation` and `report_allocation`, since `list_playbooks`, `list_connections`, `list_playbook_events` given a `run_id` and `dry_run` answer what an agent needs of them and Studio reads the rest. Every tool that works inside a playbook (`create_definition`, `list_definitions`, `get_definition`, `update_definition`, `retire_definition`, `run_definition`, `get_run`, `cancel_run`, `list_runs`, `get_event`, `list_playbook_events`, `publish_event`, `introspect`, `dry_run`, `execute`, `list_interactions`, `answer_interaction` and `send_run_event`) takes the playbook's id as a required `playbook` argument, `search` takes it as an optional one, and `get_guide` reads the guides on every endpoint: thirty tools for a key that may call them all. `search` answers the tool servers the playbook may use and their tools, which an agent names in a reasoning function's `tools`, found by the words of `terms` where it gives them, and without `playbook` every server set up for the org, each with the playbooks it serves, so an agent sees what is set up before it makes a playbook, and, to a caller who may add a connection, `providers`, the providers a person may connect that no server serves yet, so an agent asked for a service no server serves can offer to connect one; it is the org's operation, `GET /v1/orgs/{org}/tool-servers/search`, which the org endpoint serves too; `introspect` reads one tool whole and `dry_run` answers what `execute` would check, its arguments against the tool's input schema among it, the three reading and calling nothing, and `execute` calls one tool as a run would and answers what the run's model would see, under `playbook:write` whatever the tool does, recorded in the playbook's history and never a run; the [HTTP reference](../../reference/http.md#tool-servers) describes them. `list_runs` and `list_playbook_events` page with `limit` and `cursor`, answer `has_more` and `next_cursor`, and read a retired playbook, and `get_event` reads one event whole, each field the 2 KiB rule of a page names, an input, output, record, answer, arguments, result or event data, whole within 64 KiB and its size beyond, since a tool result carries its output twice; the [HTTP reference](../../reference/http.md#run-history-and-playbook-events) describes their fields. A connection lists the tools its key may call, so a read-only key is offered the queries alone, and a key that may only read inside some playbooks is offered `list_playbooks` too, which lists those playbooks. Every endpoint gives a connecting agent instructions, `instructionsActingAs` of `@on.auto/api`, built per request for its caller, the tools listed and the definition types the server runs: first, whom the connection acts as, by name and id, and in which org, then that whatever the person wants done that keeps working after the conversation, however they put it and in any line of business, is a playbook here and not a document, a plan, a note or a one-off answer, then what a playbook is and a sentence for each type it runs, that what the person wants kept goes in a recall function and not in the agent's own notes where the server runs recall functions, what the connection acts on, where the formats are and that each definition is given an overview, where `list_models` is listed and `search` is not that it lists the models a reasoning function names, where `search` and `add_connection` are both listed that a service a playbook will use is connected on this server, whatever connector the agent has of its own, by `search` with the service's words and `add_connection` with the name of a provider that matches, and that a service cannot be connected only when no provider or server matches, that an answer to what a run waits on goes to its request through `answer_interaction` and no new run, what to say of what was done and what the person can do next, in which words, and what a refusal says. | Endpoint                                    | Tools                                                                                                                       | Use it                                                             |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `POST /mcp`                                 | every tool, those inside a playbook taking a `playbook` argument, optional for `search`                                     | by default                                                         |
| `POST /orgs/{org}/mcp`                      | `create_playbook`, `list_playbooks`, `update_playbook`, `retire_playbook`, `list_models`, `search` and the connection tools | to manage one org’s playbooks and discover models and tool servers |
| `POST /orgs/{org}/playbooks/{playbook}/mcp` | the tools inside a playbook, acting in that playbook, without a `playbook` argument                                         | to lock a connection to one playbook, such as for one agent        |

Every endpoint speaks streamable HTTP without sessions. It serves the current stateless revision (`2026-07-28`) and the earlier ones the SDK supports (`2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05` and `2024-10-07`), so agents built on older SDKs connect too. Each tool carries the operation's description and the JSON Schema of its input, and no output schema, and is marked read-only when it only reads. A tool that cannot do what was asked returns `isError` with the same problem document HTTP would answer with, as text, so the agent can read the `reason` and the `detail`, and correct its arguments when the `reason` is `invalid_input`. The key's permissions and playbooks hold as they do over HTTP: a read-only key is offered `list_playbooks` and not `create_playbook`, which it would be refused, a key limited to some playbooks gets `forbidden` for any other, and a playbook the org does not have is `not_found`. [`packages/api`](https://github.com/BeOnAuto/runtime/blob/main/packages/api/README.md) describes the mappings in full.

## Reading tool results

On success, use `structuredContent` for the operation's output. The first text block is a plain-language summary; the second text block contains the same output as JSON text for clients that do not read structured content. No tool advertises an output schema, so a client takes `structuredContent` as it comes instead of checking it against one. Do not parse `content[0].text` as JSON.

On failure, the result has `isError: true` and no `structuredContent`. The first text block explains what could not be done, and the second contains the JSON problem document. Check its `reason` and `detail` before deciding whether to correct input or retry.

Authentication and origin failures can occur before a tool runs, producing an HTTP problem document. Protocol errors can produce JSON-RPC errors. Use an MCP client to handle the protocol rather than treating every response as an operation result.

## Start a useful conversation

After connecting, ask your agent to list the playbooks and available operations. Describe a recurring piece of work and the criteria you use. Ask it to propose a small reusable function, explain the inputs it needs and create it after you agree.

`get_guide` serves the format of each definition type, and a client that shows MCP prompts offers `first-playbook`, the first conversation of the quick start, served by the playbook itself. Ask the agent to call `list_models` and choose a concrete model or alias id. Model discovery requires `org:read` on `/mcp` or the org endpoint. Wildcard entries describe supported prefixes; they are not runnable model ids. An incomplete listing may need a concrete reference confirmed by the deployment operator. Follow the [first-playbook guide](../get-started/self-hosted.md) for an example that works with the current runtime.
