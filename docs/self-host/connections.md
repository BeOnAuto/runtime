# Let people add connections

A connection is a tool server that a person adds to an org through their agent, rather than one you set up in Auto's settings file. The org owns it, and every playbook of the org may use it, or only the playbooks it names. The person approves it, and gives its credential where it takes one, on a page of Studio. The agent never sees the credential.

This page is for whoever runs Auto. It says how a connection is added, the providers a person may connect by name, what a connection holds, how a function uses it, how one that needs attention is reconnected, the rules you set for it in `auto-runtime.yaml`, consent through Auto's clients, and the clients you register there. A tool server you set up yourself is still added as [Add a tool server](tool-servers.md) shows.

## How a person adds a connection

1. The person asks their agent to connect a service, such as their code host. Where Auto knows the service as a [provider](#the-providers-auto-ships), the agent calls `add_connection` with the provider's name and the values its placeholders take, such as a site's subdomain. Otherwise it gives the server by hand: its address, its options and how it is credentialled. Either way, never the credential itself.
2. Auto keeps the connection, `pending`, and answers with a link to Studio's page `connect`, which lasts ten minutes: `/studio/connect` on Auto's own address where Auto serves Studio, as it does in [local mode](security.md#studio-served-by-the-runtime), naming the connection and its token alone, and `https://studio.on.auto/connect` otherwise, naming Auto's address and the org too. An agent whose client opens links asks the person to open it; any other agent gives the person the link from its answer, as a link named `Approve the <title> connection` with its provider's title, or `Approve the connection` for a server given by hand, never as its address.
3. On the page, signed in, the person approves the connection. Where it takes a secret or client credentials, the person types the credential there, with the client id where the agent left it out, and giving it approves the connection. Where its provider takes consent, or an MCP server given by hand signs people in itself, the page sends the person to sign in at its authorization server and allow Auto, and the authorization server sends them back to Studio, which finishes the consent. The connection is then `connected`.
4. An agent whose client asked the person to open the page retries its call once the person is done there or declined, and Auto answers the connection as it stands then, adding nothing: `connected`, with no link, and words that say nothing is left to open; `pending` with its link while the link lasts, where the person has not approved it yet or declined to open the page, so the agent gives them the link; `pending` with no link once its ten minutes are over, with words that say to reconnect it for a new link; or `removed`, where the person pressed Cancel on the page, which removes a pending connection, with words that say nothing is connected.

On a runtime that signs people in, only the person who added a connection may approve it, signed in as themselves. In [local mode](security.md#local-mode), the link alone binds: whoever holds it within its ten minutes approves the connection. A link is gone after its ten minutes, and `reconnect_connection` gives the connection another, as [A connection that needs attention](#a-connection-that-needs-attention) sets out.

`list_connections` shows the connections of the org and whether each is `pending`, `connected`, `broken` or `removed`, which is how an agent sees whether the person approved one; `get_connection`, served over HTTP alone, reads one by its id. `reconnect_connection` gives a connection a new link, and `remove_connection` removes one for good: no playbook may use it any more, and Auto forgets its credential. An org holds at most 50 connections that are not removed; `add_connection` refuses another with `409`, `conflict` of the kind `connections_full`, until one is removed. The [MCP reference](../reference/mcp.md#connections) describes the four tools, and the [HTTP reference](../reference/http.md#connections) the routes, those of Studio's page among them.

The documents of Adobe's and Amazon's HTTP APIs are made from the descriptions the vendors publish, of the operations a function needs, and every operation of each is a tool; a report's file of `amazon-ads` is a download a call does not fetch.

Auto reads the providers when it starts, and nothing is fetched from anywhere to list them. A provider's hosts pass your `allowed_hosts` as any connection's do, and one your rules could not allow is not listed. A connection a person makes from a provider keeps its provider's name and the values given in its record, beside the entry it resolved to, so a later version that changes the provider changes no connection there is.

None of the providers this version ships names a variable of yours in its entry. A provider whose entry sends a value of your own registration at the vendor, such as a developer token, names it as an environment variable: set it in Auto's environment and start Auto again, and Auto sends it to that provider's server alone, in the header or the query parameter the provider names, and scrubs it from what it records. Until it is set, `list_providers` shows the provider's ways as ones you set up first, `search` leaves the provider out of the providers it lists to an agent, and `add_connection` refuses it. The variable is one Auto reads for itself, so `variables` may not name it.

## Add providers of your own

You can add providers of your own beside those Auto ships, under `providers` in the `connections` section of `auto-runtime.yaml`. A person then connects one by its name as they connect a provider Auto ships: `list_providers` lists it for Studio's page, `search` offers it to an agent, and an entry of the settings file may name it, as [Add a tool server](tool-servers.md#name-a-provider) shows. A provider of yours named as one Auto ships takes its place, so you can point that provider at a proxy of your own.

```yaml
connections:
  providers:
    - name: crm
      title: CRM
      description: Read and change the accounts and contacts of your CRM.
      website: https://developer.crm.example.com
      type: mcp
      url: https://{tenant}.crm.example.com/mcp
      placeholders:
        tenant:
          description: The tenant of your CRM, as in https://<tenant>.crm.example.com
          pattern: '^[a-z0-9-]{1,63}$'
          example: acme
      credentials:
        - kind: secret
          in: header
          name: Authorization
          scheme: Bearer
          description: An API token from the settings of your CRM.
```

| `title`        | What a person reads                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `description`  | What a function may do through it, in at most 300 characters                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

| `type`         | `mcp` for an MCP server, `openapi` for an HTTP API described by an OpenAPI document                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `url`          | For `mcp`, the `https` URL of the server, each `{name}` in it a placeholder                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `document`     | For `openapi`, the `https` URL of the OpenAPI document. A document beside the entries is one Auto ships, so a provider of yours names its document by its address                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `base_url`     | For `openapi`, where the calls go when the document names no server                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

Auto reads them when it starts, and an entry it cannot take stops it, naming the line and the key: one whose address is neither `https` nor on a loopback address, a name another of your providers has, or a way `add_connection` would always refuse, such as one that sends its credential in a header the entry sends already, in any case. A value of yours that an entry refers to, such as `${NOTES_WORKSPACE}`, stops Auto at start while its variable is not set where the section comes from `auto-runtime.yaml`, as every reference of the file does, and where it comes from `CONNECTIONS` in the environment, the provider is listed with its ways as ones you set up first, as a provider Auto ships is. The `title`, the `description` and a way's `description` are prose, which the settings file's check for a credential written out does not judge; Auto judges the rest of an entry as it judges a provider it ships. The rules below apply to a provider of yours as to any: it is listed where its hosts pass `allowed_hosts` and its ways `credential_kinds`.

## How a function uses a connection

A connected connection is a tool server of its org, for every playbook of the org or the playbooks its entry names. A function names its tools as it names those of any tool server, by the connection's name and the tool, as in `crm/search` or `crm/*`, and calls them in the same way, with the same bounds and the same scrubbing of its credential from everything Auto records. `search` lists it beside the tool servers of the settings file, with `connection`, its id, and `introspect`, `dry_run` and `execute` reach it. Each call it records, a run's, one made by hand with `execute` and one an interaction function makes in a conversation, names the connection's id beside the server's name as `connection_id`, so the history stays plain once another connection takes the name.

A connection that is not ready is refused, and `search` lists it unavailable with the same words:

| -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nobody has approved it yet                                                                                           | `connection_pending`                     | The person who added it opens its link, or reconnects it for a new link                                                                                                                                                       |
| Its credential cannot be read just now, since Auto's secret store cannot unwrap it or does not answer                | `connection_unavailable`                 | `The credential of the connection crm cannot be read now:` and the store's words. It stays connected, and you put the store right; Auto logs those words once for each cause                                                  |
| Its server answered `401` as Auto listed its tools or called one                                                     | `connection_broken`                      | Why, by its kind of credential, and that the person who added it reconnects it, or for `none` removes it and adds it again with a credential, or for `reference` that you set the variable right and the person reconnects it |
| Its credential is no longer in Auto's secret store, or is not the tokens of a consent                                | `connection_broken`                      | Why, and that the person who added it reconnects it                                                                                                                                                                           |
| Its consent was revoked or has ended, or the client it was made with is no longer registered                         | `connection_broken`                      | Why, and that the person who added it reconnects it                                                                                                                                                                           |

| `people_may_add` is now `false`                                                                                      | `connection_not_allowed`                 | That this runtime uses no connection, since you set up its tool servers yourself                                                                                                                                              |

Auto checks the rules, and checks the entry as `add_connection` checks it, when a connection is first used after Auto starts, once for each connection, and reads its credential then. A rule you change reaches a running Auto when it starts again. A connection Auto cannot read the credential of, or whose server refuses its credential, is broken: Auto records why, and it stays broken until the person reconnects it. Where Auto cannot record it broken, it logs why, refuses it all the same, and finds the break again at its next use, recording it again.

Auto places the credential in the entry as the settings file places a reference to an environment variable, and reads the entry as it reads one of the file, with the same checks and the same secrets to scrub; the entry itself is sent as it is written, a `$` in it too. The document of an HTTP API is read when a function first uses the connection. A document that cannot be read just now, because its address does not answer in time, answers an error or answers a page that is no document, such as a proxy's error page, is read again at the next use; one refused for what it says stays refused until Auto starts again, and the person removes the connection and adds it again once the document is put right.

## A connection that needs attention

Auto records the status of each connection, `pending` while nobody has approved it, with its link open or run out, `connected`, or `broken`, with the reason in one sentence, and `search` says in its own words why a connected connection's server could not be used just now. `list_connections` and `search` answer these to an agent, and Studio shows the same to the person.

Auto marks a connection `broken` when using it shows that its credential no longer serves:

- its server answers `401` when Auto lists its tools or calls one, after Auto renewed the tokens of a consent, or of client credentials, and tried once more. The reason follows the kind of credential: for a secret, client credentials or a consent, `The tool server answered HTTP 401: it refused the credential the connection holds, so the person who added it reconnects it`; for `none`, `The tool server answered HTTP 401: it asks for a credential the connection does not hold, so the person who added it removes it and adds it again with one`; and for `reference`, `The tool server answered HTTP 401: it refused the value of the variable CRM_API_KEY, so whoever runs the runtime sets it right and starts it again, and the person who added the connection reconnects it`: Auto reads its variables when it starts, so you set the variable right and start Auto again, and the reconnection finds the variable set;
- its credential is gone from the secret store, or is not the tokens of a consent;
- its consent was revoked or has ended, the client it was made with is no longer registered, or Auto's consent service does not know its key.

Any other failure of the server, as a `500` or a `429`, fails that call alone and leaves the connection connected. So does a `403` with `insufficient_scope` in its `WWW-Authenticate` challenge or its body, since the person may have allowed less than the provider asks: the call, or the listing of its tools, fails as `scope_lacking`, in words that name the scope it lacks where the server names one and say that a credential granted that scope would allow it. A tool server of your settings file fails the same way.

Auto records the break once, as the first use that meets it finds it, and that use, a search among them, already says the connection is broken. Calls later in the same run still reach the server until the run ends; the next run, and the next call outside a run, refuse the connection without a request to its server. A use that began before the person connected the connection again breaks nothing.

The way back is to reconnect it. `reconnect_connection`, `POST /connections/{id}/link`, under `org:write`, gives a connection that is `broken`, `connected`, or `pending` with its link run out a new link to Studio's page, which lasts ten minutes, and answers the connection with `connect`, as `add_connection` does; nothing else of the connection changes. A broken connection of a `reference` takes no link: Auto checks that its variable is set and connects it again at once, or refuses with `409` while it is not, so set it and start Auto again first. A pending or connected one takes a link as any other does, since only the person's approval connects a connection. Where people sign in, only the person who added the connection may reconnect it, as only they may use its link, and a key may not; in local mode the local developer reconnects any. It refuses with `409` a connection that is removed, which is added again instead, and any connection whose link is still open, saying when that link expires. Studio offers the reconnection beside the connection. On the page the person who added the connection approves it again, gives its credential again or signs in again, and the connection is `connected` again with the new credential: Auto forgets the secret it held before, and records who connected it and when. A consent reconnected with another client than before has its old tokens revoked at the provider, as removing the connection does, and one reconnected with the same client has them forgotten without a revocation, since some providers end the person's whole grant to the client on one revocation, the new tokens with it. A consent is reconnected with the sign-in setup recorded when the connection was added, so a connection of a provider whose way of consent has changed since is removed and added again. A function that names it uses the new credential from its next run.

## Which runtimes take connections

A person approves every connection, so a connection is added by a person, and a runtime takes connections only where a person reaches it as themselves:

| Runtime                                         | Who adds a connection                                                                                                                                                                                                      | The runtime the link names     |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| One that signs people in, with `PUBLIC_URL` set | A person, through an agent signed in as them. `add_connection` refuses a key with `403`, since no person would approve what it adds                                                                                        | `PUBLIC_URL`                   |
| One in [local mode](security.md#local-mode)     | The local developer                                                                                                                                                                                                        | The runtime's loopback address |
| One of `API_KEYS` alone, which signs nobody in  | Nobody: `add_connection` refuses every connection with `403`, since no person could approve it. Set `PUBLIC_URL` to sign people in, or add the server to `auto-runtime.yaml` as [Add a tool server](tool-servers.md) shows |                                |

## What a connection holds

A connection has a name, which a function will give it as a tool server's name, a type, an entry and a credential, and the provider it was made from, with the values given for its placeholders.

| Part         | What it holds                                                                                                                                                                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`       | 1 to 32 lowercase letters, digits and hyphens, starting with a letter. It may not be the name of a tool server of the settings file, nor of another connection of the org that is not removed                                                                        |
| `type`       | `mcp` for a remote MCP server, `openapi` for an HTTP API described by an OpenAPI document, as the `type` of an entry of the settings file says                                                                                                                       |
| `entry`      | The server without its credential: `url` for `mcp`, or `document` and `base_url` for `openapi`, with `headers`, `query_params`, `allowed`, `playbooks`, `record_content` and `request_id` as an [entry of the settings file](configuration.md#tool-servers) has them |
| `credential` | How the server is credentialled, below, never its value: one object, its `kind` and the fields that kind takes                                                                                                                                                       |
| `provider`   | The provider it was made from, or `null` for a server given by hand, and `placeholders`, the values given for that provider's placeholders                                                                                                                           |

Auto checks an entry as it checks an entry of the settings file, and refuses one that holds a value that looks like a credential, or a reference to an environment variable such as `${CRM_API_KEY}`. A connection's `url` and document are each an `https` URL, or an `http` URL on a loopback address; a document is never a file on Auto's disk.

## The kinds of credential

| Kind                 | What the person gives                                                                                                                                                                                                                                                                                       | Where the value is kept                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `none`               | Nothing; the server takes no credential                                                                                                                                                                                                                                                                     | Nowhere                                                                                    |
| `reference`          | Nothing; `variable` names an environment variable of Auto, such as `CRM_API_KEY`, that you set and list in the rule `variables`, and `name` and `in` say where its value goes, as for a `secret`                                                                                                            | In Auto's environment, where you put it                                                    |
| `secret`             | A key or token, on Studio's page. `name` and `in` say where it goes: `in: header` and the header's name, never one Auto sets itself such as `Content-Type`, `Host` or `Mcp-Session-Id`, or for an HTTP API `in: query` and a query parameter's name, or `in: security` and a scheme of its OpenAPI document | Sealed in Auto's secret store                                                              |
| `client_credentials` | The client secret, or a private key with its algorithm, on Studio's page, with the client id where `client_id` is left out. `issuer`, `client_id` and `scope` name the authorization server and the client                                                                                                  | Sealed in Auto's secret store                                                              |
| `authorization`      | Nothing on the page: the person signs in and allows Auto, on the page of the authorization server. A provider's way, or an MCP server given by hand that names its authorization server, which Auto connects with a client it registers there for itself                                                    | The tokens the authorization server gives, sealed in Auto's secret store and renewed there |

A `secret` or a `reference` sent in a header may name its `scheme`, such as `Bearer`: Auto writes the scheme and a space before the value, so the person pastes the token alone, the variable you set for a reference holds the token alone, and the server receives `Authorization: Bearer <token>`. Auto refuses a token pasted with the scheme before it, saying to paste the token alone.

Auto seals a secret under its secret key, `SECRETS_KEY`, the file `SECRETS_KEY_FILE` names, by default `secrets.key` beside a SQLite ledger, or a key in AWS KMS that `SECRETS_KEY_KMS` names, as [the configuration reference](configuration.md#storage) sets out, or keeps it in AWS Systems Manager Parameter Store where `SECRETS_KEEPER` names it, as [Keep secrets in your secret manager](secret-manager.md) sets out. No record of the org, no answer and no history holds the value, and the link's token is kept only as its SHA-256. Of a secret or a client secret of twelve characters or more, Auto also keeps its last four characters beside the sealed value in the secret store, never in the org's record, and `list_connections` and `get_connection` answer them as `credential_ends_with`, so the person can tell which key a connection holds; a private key, or a shorter value, has none. Removing a connection forgets its secret, and the ending with it, and first revokes at the provider the tokens of a connection connected by consent.

Every value of a credential is a secret Auto scrubs from what it records and answers, in each form it may take, as it scrubs the value of a reference of the settings file. A value in a header that is a scheme and a credential, such as `Bearer <token>`, is scrubbed whole and its credential alone; where the credential names its `scheme`, the value is the token, scrubbed whole.

A secret is only as recoverable as the key it was sealed under. While Auto cannot read a credential because its store does not answer or will not unwrap it, a call that needs it is refused with `connection_unavailable` in the store's words, and the connection stays connected; the call is made once the store can read it again. Auto keeps a key of its own beside the credentials, so it does not start with a key other than the one they were sealed under, unless that one is given as the previous key, and a ledger whose key is lost for good cannot be started again, as [Secrets at rest](security.md#secrets-at-rest) says. Auto marks a connection `broken` only when its server refuses its credential, its credential is gone from the store or is not the tokens of a consent, its consent was revoked or has ended, or its client is no longer registered, with a sentence that says why, as [A connection that needs attention](#a-connection-that-needs-attention) sets out.

## Set the rules in `auto-runtime.yaml`

A `connections` section of `auto-runtime.yaml` says what people may add. Every rule has a default, so a file without the section lets people add any connection but one of the credential `reference`.

```yaml
connections:
  people_may_add: true
  allowed_hosts: ['*.example.com', 'crm.example.com']
  credential_kinds: [none, reference, secret, client_credentials, authorization]
  variables: [CRM_API_KEY]
```

| Rule               | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | When left out                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `people_may_add`   | `false` refuses every new connection, and Auto uses none of those already added: `list_connections` still lists them as they are, `connected` among them, and a function that names one is refused. You set up every tool server yourself                                                                                                                                                                                                                                                                                                                                                                   | `true`                                                                                                                                       |
| `allowed_hosts`    | The hosts a connection may reach. A pattern is a host, or `*.` and a host for every host under it, so `*.example.com` takes `crm.example.com` and not `example.com`. Auto checks the host of an `mcp` connection's `url`, of an `openapi` connection's `document` and `base_url`, or of the server named by a document Auto ships with a provider that gives no `base_url`, of the `issuer` of client credentials, where the client secret or the key's assertion goes, and of the issuer and the endpoints of a way of consent, and then every request a call makes, or a consent sends, before it is sent | Every host, addresses inside your network such as `localhost` or `10.0.0.5` among them, so set it wherever a connection must not reach those |
| `credential_kinds` | The kinds of credential a connection may take, of the five above                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Every kind                                                                                                                                   |
| `variables`        | The environment variables a `reference` may name. A reference sends the value of a variable of Auto to the server the person names, so you list each one a connection may send; Auto refuses to start on a list that names a variable it reads for itself, such as `SECRETS_KEY`, `API_KEYS` or a provider's key                                                                                                                                                                                                                                                                                            | None, so every `reference` is refused                                                                                                        |
| `providers`        | Providers of your own beside those Auto ships, as [Add providers of your own](#add-providers-of-your-own) shows                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | None                                                                                                                                         |

`add_connection` refuses a connection a rule does not take with `403`, saying which rule, such as `A connection may not reach the host api.billing.example.org on this runtime, which allows *.example.com and crm.example.com`. A connection added before a rule changed is refused the same way when it is first used after Auto starts again, `connection_not_allowed` with the same sentence. A rule the file gives that Auto cannot read stops it at start, naming the line. `CONNECTIONS`, the same rules as JSON, wins over the file. The [configuration reference](configuration.md#connections) lists the section.

`allowed_hosts` holds more than the addresses a connection names: the server an HTTP API's document names, where `base_url` is left out, is checked once Auto reads the document, and every request a call makes is checked before it is sent, those to an authorization server and those a redirect leads to among them. A call of an HTTP API follows no redirect, and the MCP client follows one only within the origin it asked.

## Consent through Auto

Auto registers its own client at the vendors of the providers it ships and has it verified there; at a vendor that verifies in tiers, Auto has a client for each tier, and its consent service lists each client with the vendor's issuer and the scopes it covers. A runtime that has no client of yours at a vendor can take a person's consent through Auto's client instead, through Auto's consent service, so the person connects the provider and nobody registers anything at the vendor. It serves a runtime on your laptop, a container on your own machine in [local mode](security.md#local-mode), and a runtime whose people use the hosted Studio, `https://studio.on.auto`.

1. The person presses Continue on Studio's page. Where you list no client at the provider's issuer under `registered_clients` that covers the scope its way asks, Auto asks its consent service to start the consent with Auto's client that covers it, and sends it the challenge of a secret the runtime alone holds.
2. The person signs in to the provider and allows Auto, under Auto's name. The provider sends them back to the Studio host, `https://studio.on.auto`, where they sign in to Auto, once, if they are not signed in already.
3. The consent service redeems the code with Auto's client and holds the tokens. The Studio host sends the person on to the Studio they started from: the one the runtime serves on their own computer, or the hosted Studio. That Studio finishes the consent, and the runtime takes the tokens from the service, once, with its secret, and keeps them sealed in its secret store, as it keeps every credential.

The person sees the provider's page, Auto's sign-in once, a moment on the Studio host and their own Studio again; nothing of a port or an address of theirs is registered anywhere.

What passes through Auto, and what Auto keeps:

- The code and the tokens pass through the consent service at the consent, and the refresh token and the new tokens at every renewal, since only Auto's client can redeem and refresh them. They pass in transit, and wait for the runtime for at most ten minutes; the service keeps no token after that.
- The service keeps a start for ten minutes, the tokens it hands to the runtime for ten minutes or until the runtime takes them, the hash of the connection key it gives the runtime with them, beside the issuer and the person who allowed the consent, and a line for each redeem, renewal and revocation naming the person, the issuer and the Studio the person went back to. The runtime keeps the connection key sealed with the tokens and sends it with every renewal and revocation, so a refresh token alone renews nothing.
- The runtime renews the tokens through the service, under the same rules as a renewal at the provider, and removing the connection revokes them through it.

Turn it on with `auto_clients` in the `connections` section, or `AUTO_CLIENTS` in the environment, which wins over it. It is `true` by default in local mode, where only the person's own browser on this computer reaches the runtime's Studio, and `false` otherwise, so a team whose people use the hosted Studio turns it on knowing that its tokens pass through Auto at the consent and at every renewal:

```yaml
connections:
  auto_clients: true
```

A client you register always comes first: where `registered_clients` lists a client at a provider's issuer that covers the scope its way asks, Auto uses it and asks the service nothing for that provider. Auto's client serves a provider whose way takes a registered client, `registered` among its `clients` or no `clients` at all, at a vendor where the service lists a client that covers the way's scope; the runtime asks the service for its list when it is first needed and again every hour, waiting at most five seconds for it, and logs at WARN when the service does not answer, after which no provider takes Auto's client for five minutes, when the runtime asks again. Where the service lists a client at the provider's vendor that covers its scope, `list_providers` shows the way as offered, `search` offers the provider to an agent and `add_connection` takes it. The runtime reaches the service at `CONSENT_SERVICE_URL`, `https://consent.on.auto` unless it is set, whatever `allowed_hosts` says, as it reaches the Auto identity service.

Register your own clients instead, as the section below sets out:

- on a runtime on a private network with a Studio of its own, served at an address other than the person's own computer: the service sends a person back only to their own computer or to the hosted Studio, so Auto's client is not offered there; a provider whose way lists another client takes that one, and a start with none is refused before the person is sent anywhere, saying that whoever runs the runtime registers a client;
- wherever no token is to pass through Auto, and leave `auto_clients` off.

## Register your clients

A registered client is the client identity you registered with a service's authorization server: a client id with a secret, a private key, or nothing for a public client. `registered_clients`, in the `connections` section of `auto-runtime.yaml`, lists the clients you registered, one entry for each client, with the issuers it is registered at:

```yaml
connections:
  registered_clients:
    - issuers: [https://accounts.example.com]
      client_id: 1234.apps.example.com
      client_secret: ${EXAMPLE_CLIENT_SECRET}
    - issuers: ['https://login.example.net/{tenant}/v2.0', https://login.example.net/common/v2.0]
      client_id: 9f1c0d2e-example
      private_key: ${EXAMPLE_PRIVATE_KEY}
      algorithm: RS256
    - issuers: [https://public.example.org]
      client_id: auto-runtime
```

| Field                        | What it holds                                                                                                                                                                                               |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `issuers`                    | The issuers the client is registered at, one at least, each an `https` URL or an `http` URL on a loopback address. One written with a placeholder, such as `{tenant}`, is kept as it is written             |
| `client_id`                  | The client id the service issued                                                                                                                                                                            |
| `client_secret`              | The client secret, as a reference to the variable that holds it, such as `${EXAMPLE_CLIENT_SECRET}`                                                                                                         |
| `private_key`                | A private key in PEM that signs the client's assertion, as a reference, with `algorithm`, such as `RS256` or `ES256`, in place of a secret                                                                  |
| `token_endpoint_auth_method` | Where the service's metadata leaves the choice, how the client authenticates: `client_secret_basic` or `client_secret_post` with a secret, `private_key_jwt` with a key, `none` without either              |
| `scopes`                     | The scopes the client may ask, each written as a provider's way writes it, at least one. Name them for each client where several clients serve one issuer, and leave them out for a client that may ask any |

A client that gives neither a secret nor a key is a public client. A way takes the first client at its issuer whose `scopes` cover the scope it asks, every scope of the way being one the client names, as written, and a client that names no `scopes` covers every way. Where several clients serve one issuer, each names its `scopes`: a client without them at an issuer another client names too, the same but for a trailing slash, stops Auto at start, since it would serve every way there that no client before it covers, and a client after it never, as a secret written out instead of referenced and a variable that is not set do, and the [configuration reference](configuration.md#connections) lists every check. A way no client covers is one you set up first. `client_secret` and `private_key` are the only fields that hold a reference: one anywhere else in the section, such as in an issuer or a `client_id`, stops Auto at start too. Auto keeps the references as they are written, so no secret of a client reaches `CONNECTIONS`, reads the values when it starts, and scrubs each secret and key from everything it records and answers, as it scrubs the secrets of its tool servers. The variables they name are ones Auto reads for itself, so `variables` may not name them.

## Let people connect by consent

A provider whose way is `authorization` is connected by consent: the person signs in to the provider and allows Auto, and Auto is the client the provider's authorization server gives the tokens to. The way names the authorization server by its `issuer`, the `scope` the person allows, the `parameters` its authorization request carries beside the standard ones, such as `access_type: offline`, where a `prompt` replaces the one Auto would send and a parameter the request sets itself, such as `redirect_uri` or `state`, is refused, and, for a server that publishes no metadata for the flow, its `authorization_endpoint` and `token_endpoint`, the two together, and its `revocation_endpoint` beside them where it has one, without which removing a connection revokes nothing and its tokens end on their own; and `clients`, the client sources that server takes, in the order Auto takes them, `registered`, `metadata_document`, then `dynamic`, and `registered` when it names none; a way that lists them in another order is refused, so a client you registered is always taken before a registration of Auto's own.

```yaml
connections:
  providers:
    - name: files
      title: Files
      description: Read the files of an account.
      website: https://developer.files.example.com
      type: mcp
      url: https://mcp.files.example.com/mcp
      credentials:
        - kind: authorization
          issuer: https://accounts.files.example.com
          scope: files.read
          parameters:
            access_type: offline
          clients: [registered, dynamic]
          description: Sign in to Files and allow Auto to read your files.
```

Auto takes the first source it has:

| Source              | What you set up                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `registered`        | A client you register at the provider's authorization server, with the return address of the runtime as its redirect address: the Studio host's `/connect-return`, `STUDIO_ORIGIN` followed by it, `https://studio.on.auto/connect-return` unless it is set, or the runtime's address followed by `/studio/connect-return` where Auto serves Studio, as it does in local mode. A runtime has one return address at a time, the one its connect link opens, so a client is registered with both only where it serves several runtimes, some serving Studio and some not. List the client under `registered_clients` with the issuer the provider names, and, where several clients serve that issuer, the scopes it may ask, as [Register your clients](#register-your-clients) shows |
| `metadata_document` | Sign-in at an `https` `PUBLIC_URL`: where Auto signs people in there, it names its client by the address `{PUBLIC_URL}/oauth/client.json`, where the authorization server advertises that it takes such a client, and serves the document at that address without a key, naming that address and the return address Auto sends people back to, as the [authentication reference](../reference/authentication.md#client-metadata-document) lists                                                                                                                                                                                                                                                                                                                                      |
| `auto`              | Nothing, where [consent through Auto](#consent-through-auto) is on and Auto's consent service lists a client at the issuer that covers the way's scope: Auto's client, through the service, taken by a way that takes `registered`, after a client you registered and before the two below. A way never lists it in `clients`                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `dynamic`           | Nothing: where the authorization server offers it, Auto registers itself once for each issuer, as a public client where the server's token endpoint takes public clients alone, and once more for each server origin given by hand there, keeps the registration sealed in its secret store, and uses it again for every later connection there until the secret the server gave it ends                                                                                                                                                                                                                                                                                                                                                                                             |

Until Auto has a source a provider's way takes, `list_providers` shows the way as one you set up first, `search` leaves the provider out of the providers it lists to an agent, and `add_connection` refuses it. `allowed_hosts` applies to the issuer and to every endpoint the way names when a connection is added, to every endpoint the authorization server's metadata names when a consent starts, before the person is sent anywhere, and to every request a consent, a renewal of its tokens or their revocation sends. Leaving `authorization` out of `credential_kinds` lists no provider whose only way it is.

The consent starts on Studio's page and has ten minutes of its own. The person signs in to the provider and allows Auto, the provider sends them back to the return address of the Studio the connection's link opens, the page `connect-return` of the Studio Auto serves at `/studio/` where it serves one, as it does in local mode, and otherwise the Studio host's `/connect-return`, `STUDIO_ORIGIN` followed by it, `https://studio.on.auto/connect-return` unless it is set, and Studio finishes the consent, which keeps the tokens sealed in the secret store; no record, answer or history holds a token, a code or the state of a consent. The connection records the client it was made with and, as `granted_scope` beside the scope its credential asked, the scope the person allowed, which is narrower than the way asks where the person unticks a scope on the provider's page, so Studio and an agent see a connection that holds less than its provider asked; where the metadata Auto discovers for the authorization server lists `offline_access` and the way's scope lacks it, Auto asks for it too, so the server gives a refresh token, and a consent that grants no scope where one was asked, or a scope that is not one, is refused and its tokens revoked.

A connection connected by consent serves its tools as any connected connection does, sending the access token the provider gave. Auto renews the tokens itself, with the refresh token and the client the connection was made with, a minute before the access token ends or halfway through a shorter life, and keeps the new ones in the same sealed row; every server that shares the ledger serves that row, and one renews it at a time while the others wait for it and take what it renewed. A token the provider gave without an end, or without a refresh token, is used until the provider refuses it. The connection breaks, and the person who added it reconnects it, when the provider refuses to renew the tokens because the consent was revoked or has ended, when it refuses an access token that no refresh token can renew, and when the client the connection was made with is no longer under `registered_clients` with its id; any other failure to renew fails that call and breaks nothing. The server that failed holds the row for 45 seconds from when it claimed the row to renew it, the 30 seconds a request to the provider may take and 15 more, so no server renews it in that time: its later calls in that time use the access token while it lasts and otherwise fail at once in the same words, without waiting, and the first call after that tries again. Removing the connection revokes its tokens at the provider first, with the client it was made with; where the provider refuses, does not answer or cannot be asked, since `allowed_hosts` refuses its host or the client is no longer under `registered_clients`, Auto logs at WARN why the tokens end on their own, in words that hold no token, and removes the connection all the same.

An MCP server given by hand connects by consent too, where it signs people in itself, as the MCP authorization specification describes. The agent gives `authorization` with its `kind` alone, and when the connection is added Auto reads the protected resource metadata the server names in its 401, or at its well-known address where the 401 names none or nothing is there, as every consent, renewal and revocation reads it again, takes the first of the first five authorization servers it names whose metadata Auto reads, and records its issuer, the scope the server asks and the client Auto takes there, `dynamic` where the authorization server registers clients dynamically and else `metadata_document`. The issuer comes from the server's own metadata; the client is one Auto registers at that issuer for each server origin given by hand, named `Auto Runtime for <host>` so the person sees which server they allow, never one under `registered_clients`, the one a provider's way or a server on another origin uses there, nor Auto's client through its consent service, and Auto's client metadata document only where the authorization server registers no clients dynamically; every authorization request asks `prompt=consent`, so an authorization server that honours it shows its consent screen even for a client it saw before; and the token request names the server as the resource at every step, Auto refusing a consent or a renewal, in words that say to remove the connection and add it again, where the server no longer publishes its metadata, while removing the connection still revokes its tokens at the authorization server it recorded, so none stays alive; so a server given by hand is never handed tokens a person consented to elsewhere. The agent's words tell the person the host they sign in at. `allowed_hosts` applies to the server, to its authorization server and to every endpoint its metadata names, and a server that names no authorization server, or whose authorization server takes no code with `S256`, names an endpoint that is neither `https` nor on a loopback address, or registers no client, is refused as it is added, in words that name it. An HTTP API given by hand takes no consent, since its document names no authorization server.

### The providers Auto ships that take consent

Each way names as its issuer the authorization server its server names in its own metadata, or, for Zoom's HTTP API, which names none, the issuer of Zoom's own metadata; asks the scope its tools need, or, at Zoom, none, so that Zoom grants the scopes of its app; and takes the client sources its authorization server takes. A client you register at the vendor takes the return address of your runtime as its redirect address, as `registered` above says, and goes under `registered_clients` with the issuer below. Every host of a way passes `allowed_hosts`, those of its endpoints among them. Google's sixteen share one issuer, with one client for the APIs you offer and another for the Workspace servers, and Microsoft's two, Amazon's two and Adobe's two each take a setup of their vendor's, as [The Google providers](#the-google-providers), [The Microsoft providers](#the-microsoft-providers), [The Amazon providers](#the-amazon-providers) and [The Adobe providers](#the-adobe-providers) set out after the five below.

| Provider   | Issuer                                                                                                                                                                                                                                                                                                                              | Scope asked                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Client sources                               | What you do at the vendor                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
