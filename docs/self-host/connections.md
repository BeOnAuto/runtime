# Let people add connections

A connection is a tool server that a person adds to an org through their agent, rather than one you set up in Auto's settings file. The org owns it, and every playbook of the org may use it, or only the playbooks it names. The person approves it, and gives its credential where it takes one, on a page of Studio. The agent never sees the credential.

This page is for whoever runs Auto. It says how a connection is added, the providers a person may connect by name, what a connection holds, how a function uses it, the rules you set for it in `auto-runtime.yaml`, and the clients you register there. A tool server you set up yourself is still added as [Add a tool server](tool-servers.md) shows.

## How a person adds a connection

1. The person asks their agent to connect a service, such as their code host. Where Auto knows the service as a [provider](#the-providers-auto-ships), the agent calls `add_connection` with the provider's name and the values its placeholders take, such as a site's subdomain. Otherwise it gives the server by hand: its address, its options and how it is credentialled. Either way, never the credential itself.
2. Auto keeps the connection, `pending`, and answers with a link to Studio's page `connect`, which lasts ten minutes: `/studio/connect` on Auto's own address where Auto serves Studio, as it does in [local mode](security.md#studio-served-by-the-runtime), and `https://studio.on.auto/connect` otherwise. An agent whose client opens links asks the person to open it; any other agent gives the person the link from its answer.
3. On the page, signed in, the person approves the connection. Where it takes a secret or client credentials, the person types the credential there, with the client id where the agent left it out, and giving it approves the connection. Where its provider takes consent, the page sends the person to sign in to the provider and allow Auto, and the provider sends them back to Studio, which finishes the consent. The connection is then `connected`.

On a runtime that signs people in, only the person who added a connection may approve it, signed in as themselves. In [local mode](security.md#local-mode), the link alone binds: whoever holds it within its ten minutes approves the connection. A link is gone after its ten minutes, and nothing gives a pending connection another, so the way on is to remove the connection and add it again.

`list_connections` shows the connections of the org and whether each is `pending`, `connected`, `broken` or `removed`, which is how an agent sees whether the person approved one; `get_connection`, served over HTTP alone, reads one by its id. `remove_connection` removes one for good: no playbook may use it any more, and Auto forgets its credential. An org holds at most 50 connections that are not removed; `add_connection` refuses another with `409`, `conflict` of the kind `connections_full`, until one is removed. The [MCP reference](../reference/mcp.md#connections) describes the three tools, and the [HTTP reference](../reference/http.md#connections) the routes, those of Studio's page among them.

The documents of Google's HTTP APIs are made from the descriptions Google publishes of them, of the methods a function needs, and every operation of each is a tool. `google-search-console` reaches domain properties, named as `sc-domain:example.com`, since the address of a property of a URL prefix holds a `/`, which Auto never places in a path; and a report's file of `campaign-manager-360` or `display-video-360-reports` is a download or sits in Cloud Storage, which a call does not fetch.

Auto reads the providers when it starts, and nothing is fetched from anywhere to list them. A provider's hosts pass your `allowed_hosts` as any connection's do, and one your rules could not allow is not listed. A connection a person makes from a provider keeps its provider's name and the values given in its record, beside the entry it resolved to, so a later version that changes the provider changes no connection there is.

None of the providers this version ships needs a value of yours. A provider whose entry sends a value of your own registration at the vendor, such as a developer token, names it as an environment variable: set it in Auto's environment and start Auto again, and Auto sends it to that provider's server alone, in the header or the query parameter the provider names, and scrubs it from what it records. Until it is set, `list_providers` shows the provider's ways as ones you set up first, `search` leaves the provider out of the providers it lists to an agent, and `add_connection` refuses it. The variable is one Auto reads for itself, so `variables` may not name it.

## Add providers of your own

You can add providers of your own beside those Auto ships, under `providers` in the `connections` section of `auto-runtime.yaml`. A person then connects one by its name as they connect a provider Auto ships: `list_providers` lists it for Studio's page, `search` offers it to an agent, and an entry of the settings file may name it, as [Add a tool server](tool-servers.md#name-a-provider) shows. A provider of yours named as one Auto ships takes its place, so you can point that provider at a proxy of your own.

```yaml
connections:
  providers:
    - name: crm
      title: CRM
      description: Read and change the accounts and contacts of your CRM.
      website: https://developer.crm.example.com
      type: mcp
      url: https://{tenant}.crm.example.com/mcp
      placeholders:
        tenant:
          description: The tenant of your CRM, as in https://<tenant>.crm.example.com
          pattern: '^[a-z0-9-]{1,63}$'
          example: acme
      credentials:
        - kind: secret
          in: header
          name: Authorization
          scheme: Bearer
          description: An API token from the settings of your CRM.
```

| Field          | What it holds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`         | The provider's name, and the name a connection to it takes unless the person gives another: 1 to 32 lowercase letters, digits and hyphens, starting with a letter                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `title`        | What a person reads                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `description`  | What a function may do through it, in at most 300 characters                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `website`      | The `https` page where a person reads about the server and makes a credential                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `type`         | `mcp` for an MCP server, `openapi` for an HTTP API described by an OpenAPI document                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `url`          | For `mcp`, the `https` URL of the server, each `{name}` in it a placeholder                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `document`     | For `openapi`, the `https` URL of the OpenAPI document. A document beside the entries is one Auto ships, so a provider of yours names its document by its address                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `base_url`     | For `openapi`, where the calls go when the document names no server                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `headers`      | Headers sent with every request, never a credential; `query_params`, for `openapi`, the same for the query. A value of your own registration at the vendor, such as a developer token, is written `${NAME}`: Auto keeps the reference and sends that provider's server the value of the variable. Where every way is `client_credentials` or `authorization`, `{client_id}` in a value is the client id of the connection, the one the person gives for client credentials or the client a consent was made with                                                                                                                                                                                                        |
| `request_id`   | The response header in which the server returns its own id of a request                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `placeholders` | The values that differ from one connection to the next, by name: each a `description`, a `pattern` anchored with `^` and `$` and an `example`, or a `description` and its `choices`; `required: false` for one a person may leave out                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `credentials`  | The ways a credential reaches the server, in the order a person is offered them, the first the default: an agent that names no way takes the first `list_providers` marks offered, and an entry of the settings file the first but `authorization`, which a person gives on Studio's page alone. The kinds: `secret` with `in`, `name` and, for a header, `scheme`; `client_credentials` with `issuer` and `scope`; `none`; or `authorization`, the way a person connects by consent, with `issuer`, `scope`, `parameters`, `clients` and, where the server publishes no metadata, its endpoints, as [Let people connect by consent](#let-people-connect-by-consent) sets out; each with a `description` a person reads |

Auto reads them when it starts, and an entry it cannot take stops it, naming the line and the key: one whose address is neither `https` nor on a loopback address, a name another of your providers has, or a way `add_connection` would always refuse, such as one that sends its credential in a header the entry sends already, in any case. A value of yours that an entry refers to, such as `${NOTES_WORKSPACE}`, stops Auto at start while its variable is not set where the section comes from `auto-runtime.yaml`, as every reference of the file does, and where it comes from `CONNECTIONS` in the environment, the provider is listed with its ways as ones you set up first, as a provider Auto ships is. The `title`, the `description` and a way's `description` are prose, which the settings file's check for a credential written out does not judge; Auto judges the rest of an entry as it judges a provider it ships. The rules below apply to a provider of yours as to any: it is listed where its hosts pass `allowed_hosts` and its ways `credential_kinds`.

## How a function uses a connection

A connected connection is a tool server of its org, for every playbook of the org or the playbooks its entry names. A function names its tools as it names those of any tool server, by the connection's name and the tool, as in `crm/search` or `crm/*`, and calls them in the same way, with the same bounds and the same scrubbing of its credential from everything Auto records. `search` lists it beside the tool servers of the settings file, with `connection`, its id, and `introspect`, `dry_run` and `execute` reach it. Each call it records, a run's, one made by hand with `execute` and one an interaction function makes in a conversation, names the connection's id beside the server's name as `connection_id`, so the history stays plain once another connection takes the name.

A connection that is not ready is refused, and `search` lists it unavailable with the same words:

| The connection                                                                                                       | A function that names it is refused with | Its words say                                                                                                        |
| -------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Nobody has approved it yet                                                                                           | `connection_pending`                     | The person who added it opens its link, or removes it and adds it again for a new link                               |
| Its credential cannot be read                                                                                        | `connection_broken`                      | Why, and that the person who added it removes it and adds it again                                                   |
| Its consent was revoked or has ended, or the client it was made with is no longer registered                         | `connection_broken`                      | Why, and that the person who added it removes it and adds it again                                                   |
| A rule of `auto-runtime.yaml` no longer takes it                                                                     | `connection_not_allowed`                 | The rule, in the sentence `add_connection` would give                                                                |
| `people_may_add` is now `false`                                                                                      | `connection_not_allowed`                 | That this runtime uses no connection, since you set up its tool servers yourself                                     |
| Its entry is no longer one Auto takes, as when a model provider you set up since has its name                        | `connection_not_allowed`                 | What `add_connection` would refuse in it                                                                             |
| Its `reference` names a variable that is not set                                                                     | `connection_not_allowed`                 | The variable, and that you set it and start Auto again                                                               |
| Its name is that of a tool server of the settings file, for any org, which a later edit added                        | `connection_not_allowed`                 | That the settings file sets up a tool server of that name, and that it is removed and added again under another name |
| Its document names a server, or a call meets a redirect or an authorization server, on a host the rules do not allow | `connection_not_allowed`                 | The rule                                                                                                             |

Each comes as `unavailable` of the kind `tool_not_offered`, before the function calls anything. A name that is neither a tool server of the settings file nor a connection of the org stays `tool_server_not_configured`.

Auto checks the rules, and checks the entry as `add_connection` checks it, when a connection is first used after Auto starts, once for each connection, and reads its credential then. A rule you change reaches a running Auto when it starts again. A connection Auto cannot read the credential of is broken for good: Auto records why, and the person removes it and adds it again, since nothing mends a broken connection. Where Auto cannot record it broken, it logs why, refuses it all the same, and reads the credential again at its next use, recording the break again.

Auto places the credential in the entry as the settings file places a reference to an environment variable, and reads the entry as it reads one of the file, with the same checks and the same secrets to scrub; the entry itself is sent as it is written, a `$` in it too. The document of an HTTP API is read when a function first uses the connection. A document that cannot be read just now, because its address does not answer in time, answers an error or answers a page that is no document, such as a proxy's error page, is read again at the next use; one refused for what it says stays refused until Auto starts again, and the person removes the connection and adds it again once the document is put right.

## Which runtimes take connections

A person approves every connection, so a connection is added by a person, and a runtime takes connections only where a person reaches it as themselves:

| Runtime                                         | Who adds a connection                                                                                                                                                                                                      | The runtime the link names     |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| One that signs people in, with `PUBLIC_URL` set | A person, through an agent signed in as them. `add_connection` refuses a key with `403`, since no person would approve what it adds                                                                                        | `PUBLIC_URL`                   |
| One in [local mode](security.md#local-mode)     | The local developer                                                                                                                                                                                                        | The runtime's loopback address |
| One of `API_KEYS` alone, which signs nobody in  | Nobody: `add_connection` refuses every connection with `403`, since no person could approve it. Set `PUBLIC_URL` to sign people in, or add the server to `auto-runtime.yaml` as [Add a tool server](tool-servers.md) shows |                                |

## What a connection holds

A connection has a name, which a function will give it as a tool server's name, a type, an entry and a credential, and the provider it was made from, with the values given for its placeholders.

| Part         | What it holds                                                                                                                                                                                                                                                        |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`       | 1 to 32 lowercase letters, digits and hyphens, starting with a letter. It may not be the name of a tool server of the settings file, nor of another connection of the org that is not removed                                                                        |
| `type`       | `mcp` for a remote MCP server, `openapi` for an HTTP API described by an OpenAPI document, as the `type` of an entry of the settings file says                                                                                                                       |
| `entry`      | The server without its credential: `url` for `mcp`, or `document` and `base_url` for `openapi`, with `headers`, `query_params`, `allowed`, `playbooks`, `record_content` and `request_id` as an [entry of the settings file](configuration.md#tool-servers) has them |
| `credential` | How the server is credentialled, below, never its value: one object, its `kind` and the fields that kind takes                                                                                                                                                       |
| `provider`   | The provider it was made from, or `null` for a server given by hand, and `placeholders`, the values given for that provider's placeholders                                                                                                                           |

Auto checks an entry as it checks an entry of the settings file, and refuses one that holds a value that looks like a credential, or a reference to an environment variable such as `${CRM_API_KEY}`. A connection's `url` and document are each an `https` URL, or an `http` URL on a loopback address; a document is never a file on Auto's disk.

## The kinds of credential

| Kind                 | What the person gives                                                                                                                                                                                                                                                                                       | Where the value is kept                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `none`               | Nothing; the server takes no credential                                                                                                                                                                                                                                                                     | Nowhere                                                                        |
| `reference`          | Nothing; `variable` names an environment variable of Auto, such as `CRM_API_KEY`, that you set and list in the rule `variables`, and `name` and `in` say where its value goes, as for a `secret`                                                                                                            | In Auto's environment, where you put it                                        |
| `secret`             | A key or token, on Studio's page. `name` and `in` say where it goes: `in: header` and the header's name, never one Auto sets itself such as `Content-Type`, `Host` or `Mcp-Session-Id`, or for an HTTP API `in: query` and a query parameter's name, or `in: security` and a scheme of its OpenAPI document | Sealed in Auto's secret store                                                  |
| `client_credentials` | The client secret, or a private key with its algorithm, on Studio's page, with the client id where `client_id` is left out. `issuer`, `client_id` and `scope` name the authorization server and the client                                                                                                  | Sealed in Auto's secret store                                                  |
| `authorization`      | Nothing on the page: the person signs in to the provider and allows Auto, on the provider's own page. Only a provider's way takes it, never a server given by hand                                                                                                                                          | The tokens the provider gives, sealed in Auto's secret store and renewed there |

A `secret` or a `reference` sent in a header may name its `scheme`, such as `Bearer`: Auto writes the scheme and a space before the value, so the person pastes the token alone, the variable you set for a reference holds the token alone, and the server receives `Authorization: Bearer <token>`. Auto refuses a token pasted with the scheme before it, saying to paste the token alone.

Auto seals a secret under its secret key, `SECRETS_KEY` or the key file beside a SQLite ledger, as [the configuration reference](configuration.md#storage) sets out. No record of the org, no answer and no history holds the value, and the link's token is kept only as its SHA-256. Of a secret or a client secret of twelve characters or more, Auto also keeps its last four characters beside the sealed value in the secret store, never in the org's record, and `list_connections` and `get_connection` answer them as `credential_ends_with`, so the person can tell which key a connection holds; a private key, or a shorter value, has none. Removing a connection forgets its secret, and the ending with it, and first revokes at the provider the tokens of a connection connected by consent.

Every value of a credential is a secret Auto scrubs from what it records and answers, in each form it may take, as it scrubs the value of a reference of the settings file. A value in a header that is a scheme and a credential, such as `Bearer <token>`, is scrubbed whole and its credential alone; where the credential names its `scheme`, the value is the token, scrubbed whole.

A secret is only as recoverable as the key it was sealed under. When the key is lost, Auto can no longer read the credentials sealed under it, so their connections are broken. Auto marks such a connection `broken` when it first needs the credential, with a sentence that says why; the person removes it and adds it again.

## Set the rules in `auto-runtime.yaml`

A `connections` section of `auto-runtime.yaml` says what people may add. Every rule has a default, so a file without the section lets people add any connection but one of the credential `reference`.

```yaml
connections:
  people_may_add: true
  allowed_hosts: ['*.example.com', 'crm.example.com']
  credential_kinds: [none, reference, secret, client_credentials, authorization]
  variables: [CRM_API_KEY]
```

| Rule               | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | When left out                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `people_may_add`   | `false` refuses every new connection, and Auto uses none of those already added: `list_connections` still lists them as they are, `connected` among them, and a function that names one is refused. You set up every tool server yourself                                                                                                                                                                                                                                                                                                                                                                   | `true`                                                                                                                                       |
| `allowed_hosts`    | The hosts a connection may reach. A pattern is a host, or `*.` and a host for every host under it, so `*.example.com` takes `crm.example.com` and not `example.com`. Auto checks the host of an `mcp` connection's `url`, of an `openapi` connection's `document` and `base_url`, or of the server named by a document Auto ships with a provider that gives no `base_url`, of the `issuer` of client credentials, where the client secret or the key's assertion goes, and of the issuer and the endpoints of a way of consent, and then every request a call makes, or a consent sends, before it is sent | Every host, addresses inside your network such as `localhost` or `10.0.0.5` among them, so set it wherever a connection must not reach those |
| `credential_kinds` | The kinds of credential a connection may take, of the five above                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Every kind                                                                                                                                   |
| `variables`        | The environment variables a `reference` may name. A reference sends the value of a variable of Auto to the server the person names, so you list each one a connection may send; Auto refuses to start on a list that names a variable it reads for itself, such as `SECRETS_KEY`, `API_KEYS` or a provider's key                                                                                                                                                                                                                                                                                            | None, so every `reference` is refused                                                                                                        |
| `providers`        | Providers of your own beside those Auto ships, as [Add providers of your own](#add-providers-of-your-own) shows                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | None                                                                                                                                         |

`add_connection` refuses a connection a rule does not take with `403`, saying which rule, such as `A connection may not reach the host api.billing.example.org on this runtime, which allows *.example.com and crm.example.com`. A connection added before a rule changed is refused the same way when it is first used after Auto starts again, `connection_not_allowed` with the same sentence. A rule the file gives that Auto cannot read stops it at start, naming the line. `CONNECTIONS`, the same rules as JSON, wins over the file. The [configuration reference](configuration.md#connections) lists the section.

`allowed_hosts` holds more than the addresses a connection names: the server an HTTP API's document names, where `base_url` is left out, is checked once Auto reads the document, and every request a call makes is checked before it is sent, those to an authorization server and those a redirect leads to among them. A call of an HTTP API follows no redirect, and the MCP client follows one only within the origin it asked.

## Register your clients

A registered client is the client identity you registered with a service's authorization server: a client id with a secret, a private key, or nothing for a public client. `registered_clients`, in the `connections` section of `auto-runtime.yaml`, lists the clients you registered, one entry for each client, with the issuers it is registered at:

```yaml
connections:
  registered_clients:
    - issuers: [https://accounts.example.com]
      client_id: 1234.apps.example.com
      client_secret: ${EXAMPLE_CLIENT_SECRET}
    - issuers: ['https://login.example.net/{tenant}/v2.0', https://login.example.net/common/v2.0]
      client_id: 9f1c0d2e-example
      private_key: ${EXAMPLE_PRIVATE_KEY}
      algorithm: RS256
    - issuers: [https://public.example.org]
      client_id: auto-runtime
```

| Field                        | What it holds                                                                                                                                                                                   |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `issuers`                    | The issuers the client is registered at, one at least, each an `https` URL or an `http` URL on a loopback address. One written with a placeholder, such as `{tenant}`, is kept as it is written |
| `client_id`                  | The client id the service issued                                                                                                                                                                |
| `client_secret`              | The client secret, as a reference to the variable that holds it, such as `${EXAMPLE_CLIENT_SECRET}`                                                                                             |
| `private_key`                | A private key in PEM that signs the client's assertion, as a reference, with `algorithm`, such as `RS256` or `ES256`, in place of a secret                                                      |
| `token_endpoint_auth_method` | Where the service's metadata leaves the choice, how the client authenticates: `client_secret_basic` or `client_secret_post` with a secret, `private_key_jwt` with a key, `none` without either  |

A client that gives neither a secret nor a key is a public client. Each issuer belongs to one client: two clients whose issuers are the same but for a trailing slash stop Auto at start, as a secret written out instead of referenced and a variable that is not set do, and the [configuration reference](configuration.md#connections) lists every check. `client_secret` and `private_key` are the only fields that hold a reference: one anywhere else in the section, such as in an issuer or a `client_id`, stops Auto at start too. Auto keeps the references as they are written, so no secret of a client reaches `CONNECTIONS`, reads the values when it starts, and scrubs each secret and key from everything it records and answers, as it scrubs the secrets of its tool servers. The variables they name are ones Auto reads for itself, so `variables` may not name them.

## Let people connect by consent

A provider whose way is `authorization` is connected by consent: the person signs in to the provider and allows Auto, and Auto is the client the provider's authorization server gives the tokens to. The way names the authorization server by its `issuer`, the `scope` the person allows, the `parameters` its authorization request carries beside the standard ones, such as `access_type: offline`, where a `prompt` replaces the one Auto would send and a parameter the request sets itself, such as `redirect_uri` or `state`, is refused, and, for a server that publishes no metadata for the flow, its `authorization_endpoint`, `token_endpoint` and `revocation_endpoint`, the three together; and `clients`, the client sources that server takes, in the order Auto takes them, `registered`, `metadata_document`, then `dynamic`, and `registered` when it names none; a way that lists them in another order is refused, so a client you registered is always taken before a registration of Auto's own.

```yaml
connections:
  providers:
    - name: files
      title: Files
      description: Read the files of an account.
      website: https://developer.files.example.com
      type: mcp
      url: https://mcp.files.example.com/mcp
      credentials:
        - kind: authorization
          issuer: https://accounts.files.example.com
          scope: files.read
          parameters:
            access_type: offline
          clients: [registered, dynamic]
          description: Sign in to Files and allow Auto to read your files.
```

Auto takes the first source it has:

| Source              | What you set up                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `registered`        | A client you register at the provider's authorization server, with the return address of the runtime as its redirect address: the Studio host's `/connect-return`, `STUDIO_ORIGIN` followed by it, `https://studio.on.auto/connect-return` unless it is set, or the runtime's address followed by `/studio/connect-return` where Auto serves Studio, as it does in local mode. A runtime has one return address at a time, the one its connect link opens, so a client is registered with both only where it serves several runtimes, some serving Studio and some not. List the client under `registered_clients` with the issuer the provider names, as [Register your clients](#register-your-clients) shows |
| `metadata_document` | Sign-in at an `https` `PUBLIC_URL`: where Auto signs people in there, it names its client by the address `{PUBLIC_URL}/oauth/client.json`, where the authorization server advertises that it takes such a client, and serves the document at that address without a key, naming that address and the return address Auto sends people back to, as the [authentication reference](../reference/authentication.md#client-metadata-document) lists                                                                                                                                                                                                                                                                 |
| `dynamic`           | Nothing: where the authorization server offers it, Auto registers itself once for each issuer, keeps the registration sealed in its secret store, and uses it again for every later connection there until the secret the server gave it ends                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

Until Auto has a source a provider's way takes, `list_providers` shows the way as one you set up first, `search` leaves the provider out of the providers it lists to an agent, and `add_connection` refuses it. `allowed_hosts` applies to the issuer and to every endpoint the way names when a connection is added, to every endpoint the authorization server's metadata names when a consent starts, before the person is sent anywhere, and to every request a consent, a renewal of its tokens or their revocation sends. Leaving `authorization` out of `credential_kinds` lists no provider whose only way it is.

The consent starts on Studio's page and has ten minutes of its own. The person signs in to the provider and allows Auto, the provider sends them back to the return address of the Studio the connection's link opens, the page `connect-return` of the Studio Auto serves at `/studio/` where it serves one, as it does in local mode, and otherwise the Studio host's `/connect-return`, `STUDIO_ORIGIN` followed by it, `https://studio.on.auto/connect-return` unless it is set, and Studio finishes the consent, which keeps the tokens sealed in the secret store; no record, answer or history holds a token, a code or the state of a consent. The connection records the client it was made with and the scope the person allowed, which may be narrower than the way asks; where the metadata Auto discovers for the authorization server lists `offline_access` and the way's scope lacks it, Auto asks for it too, so the server gives a refresh token, and a consent that grants no scope where one was asked, or a scope that is not one, is refused and its tokens revoked.

A connection connected by consent serves its tools as any connected connection does, sending the access token the provider gave. Auto renews the tokens itself, with the refresh token and the client the connection was made with, a minute before the access token ends or halfway through a shorter life, and keeps the new ones in the same sealed row; every server that shares the ledger serves that row, and one renews it at a time while the others wait for it and take what it renewed. A token the provider gave without an end, or without a refresh token, is used until the provider refuses it. The connection breaks, and the person who added it removes it and adds it again, when the provider refuses to renew the tokens because the consent was revoked or has ended, when it refuses an access token that no refresh token can renew, and when the client the connection was made with is no longer under `registered_clients` with its id; any other failure to renew fails that call and breaks nothing. The server that failed holds the row for 45 seconds from when it claimed the row to renew it, the 30 seconds a request to the provider may take and 15 more, so no server renews it in that time: its later calls in that time use the access token while it lasts and otherwise fail at once in the same words, without waiting, and the first call after that tries again. Removing the connection revokes its tokens at the provider first, with the client it was made with; where the provider refuses, does not answer or cannot be asked, since `allowed_hosts` refuses its host or the client is no longer under `registered_clients`, Auto logs at WARN why the tokens end on their own, in words that hold no token, and removes the connection all the same.

### The providers Auto ships that take consent

Each way names as its issuer the authorization server its server names in its own metadata, asks the scope its tools need, and takes the client sources its authorization server takes. A client you register at the vendor takes the return address of your runtime as its redirect address, as `registered` above says, and goes under `registered_clients` with the issuer below. Every host of a way passes `allowed_hosts`, those of its endpoints among them. Google's thirteen share one issuer and one client, as [The Google providers](#the-google-providers) sets out after the three below.

| Provider   | Issuer                                                                                                                                        | Scope asked                                                                                                                                                                                                                                                               | Client sources                               | What you do at the vendor                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `github`   | `https://github.com/login/oauth`, whose endpoints are on `github.com`                                                                         | `read:org repo`, and `offline_access`, which GitHub's authorization server lists, so Auto asks for it too and GitHub gives a refresh token                                                                                                                                | `registered`                                 | Register an OAuth app, as GitHub names that kind, and not a GitHub App, which takes no scope: the scope and an organization's approval are an OAuth app's. ### The Google providers

Thirteen of the providers this version ships are Google's, each a provider of its own with a consent of its own, so a person who connects Drive and Gmail allows Auto twice, once for each. Each takes consent at Google's authorization server, the issuer `https://accounts.google.com`, through a client you register there, `registered`, the one source Google takes, since it registers no client itself and names no client by a metadata document. Each asks Google for `access_type: offline`, without which Google gives no refresh token, and `prompt: consent`, with which it gives one again to a person who allowed Auto before, and asks the least scope its tools need, the scope that reads before the one that writes, each written in full as `https://www.googleapis.com/auth/` and the name below. What you do at Google, once for every Google provider you offer:

1. Make one Google Cloud project, and turn on in it the APIs of each provider you offer, in the table above.
2. Set up its consent screen in the Google Auth Platform: the branding a person sees when they allow Auto, the audience, External for people of any Google account or Internal for the people of your Google Workspace organization alone, and, under data access, the scopes of each provider you offer.
3. Make one client of the type web application, with the return address the `registered` source above names among its authorized redirect addresses, and with Use this client for an AI-powered agent selected, since the Workspace servers refuse the requests of a client without it. List it under `registered_clients` with the issuer `https://accounts.google.com`:

   ```yaml
   connections:
     registered_clients:
       - issuers: [https://accounts.google.com]
         client_id: 1234567890-example.apps.googleusercontent.com
         client_secret: ${GOOGLE_CLIENT_SECRET}
   ```

4. Have the client verified, for every provider you offer: Google verifies the brand of the consent screen and reviews the sensitive scopes the providers ask. Where a provider asks a scope the table above marks restricted, Google also asks for a security assessment by an assessor it approves, since Auto reaches that data from a server, and asks for it again every year. An Internal app, for the people of your Workspace organization alone, needs none of this.

Until Google verifies the client, its consent screen says the app is not verified to the person who allows Auto. While the publishing status of an External app is Testing, the app takes the test users you list alone, and Google ends each refresh token it gives seven days after it gave it, so Auto cannot renew the tokens of a connection after that: the connection breaks, and the person who added it removes it and adds it again.

The five Workspace providers, `google-drive`, `google-sheets`, `google-docs`, `google-slides` and `gmail`, are Google's MCP servers in its developer preview: you join the Google Workspace Developer Preview Program, which each of them asks, and the project turns on the MCP API of each server, as `drivemcp.googleapis.com`, beside the API the server calls, as `drive.googleapis.com`. The Google Ads API gives the project Test access when it is turned on, which reaches test accounts alone; the project applies for Explorer access or more on the Google Ads API overview of the console before a person connects a production account. Auto sends Google Ads no developer token, which Google no longer asks for since 9 September 2026.
